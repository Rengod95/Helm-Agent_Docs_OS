## 1. 에이전트 하네스 루프 기초 ([34]~[37])

### 1.1 사용자 요청

- X2-1-01 L1086 [사용자] "내가 멍청해서 전반적인 흐름과 맥락을 이해못하고있어 일반적인 에이전트 하네스 루프가 어떻게 동작하고 각 개념을 어떻게 부르고 사용하는지에 대한 기초부터 다시 쌓고 RLM과 일반 harness 런타임의 차이를 이해해야할거같아". 이 요청 뒤 Claude는 개념 설명을 "직접 돌려 보는 작은 실험"과 함께 했다(L1089).

### 1.2 정의 (0.1절)

- X2-1-02 L1103 [Claude] 설명의 기준 틀: 에이전트를 "while 루프 하나와, 매 바퀴 통째로 전송되는 배열 하나"로 본다. 모든 개념은 이 루프의 특정 지점에 붙는 부품으로 설명한다.
- X2-1-03 L1112–1114 [Claude] 용어 정의
  - 모델(LLM): 텍스트를 받아 텍스트를 내는 함수. API 호출 한 번에 한 번 답하고 끝난다.
  - 하네스(harness): 이 함수를 반복 호출하고, 모델이 요청한 행동을 실제로 실행하는 프로그램. pi, Claude Code, Codex가 하네스다. "런타임"도 같은 뜻으로 써 왔다.
  - 에이전트: 모델과 하네스를 합친 전체.
- X2-1-04 L1118–1129 [Claude] 하네스 본체 의사 코드(실습 코드 `mini-harness.mjs`의 루프 부분).

  ```js
  const messages = [system, userMessage];        // 대화 전체를 담는 배열
  while (true) {
    const reply = await model(messages);          // ① 배열 전체를 모델에 보낸다
    messages.push(reply);                         // ② 모델의 응답을 배열에 붙인다
    if (reply.type === "text") break;             // ③ 툴 요청이 없으면 끝
    const result = await runTool(reply);          // ④ 툴 요청이면 하네스가 실행한다
    messages.push({ role: "tool", content: result }); // ⑤ 결과를 배열에 붙이고 ①로
  }
  ```

  요약: 에이전트는 "모델 호출 → 툴 실행 → 결과를 배열에 추가"를 모델이 멈출 때까지 반복하는 while 루프다(L1129).

### 1.3 메시지 배열 (0.2절)

- X2-1-05 L1135 [Claude] 모델 API는 무상태(stateless)다. 이전 호출을 기억하지 않는다. 대화가 이어지는 것처럼 보이는 이유는 하네스가 대화 전체를 매번 다시 보내기 때문이다.
- X2-1-06 L1139–1144 [Claude] 배열 항목의 네 역할

  | 역할 | 누가 만드나 | 예 |
  |---|---|---|
  | `system` | 하네스 | "You are a coding agent…", AGENTS.md 내용, 툴 목록 |
  | `user` | 사람 | "src 폴더의 TODO를 세어 줘" |
  | `assistant` | 모델 | 답변 텍스트, 또는 툴 호출 요청(`tool_use`) |
  | `tool` (tool_result) | 하네스 | 툴을 실행한 결과 |

- X2-1-07 L1146 [Claude] 컨텍스트 창은 매 호출에 실려 가는 이 배열의 토큰 수 상한이다.
- X2-1-08 L1148 [Claude] 툴 결과가 배열에 한 번 들어가면 이후 모든 호출에 다시 실려 간다(예: 2만 토큰 로그를 읽고 10번 더 호출하면 10번 더 전송). 프롬프트 캐시는 비용을 줄이지만 컨텍스트 창 점유와 "모델이 무뎌지는 문제"는 남는다.

### 1.4 최소 하네스 실험 (0.3절)

- X2-1-09 L1154 [Claude][실험] 실험 설계: "대본대로 답하는 가짜 모델" + 실제 bash 툴 + `rm` 명령을 막는 훅 하나. 가짜 모델은 `rm` 시도 → `grep` → 답 순서로 움직인다. 파일: `/home/claude/rlm-lab/mini-harness.mjs`(L1092, 대화 환경 경로).
- X2-1-10 L1158–1167 [실험] 결과

  ```
  [step 1] 보낸 메시지 2개(~29 tok) → 모델 응답: tool_use
           툴 결과 → "ERROR: rm은 금지된 명령입니다"
  [step 2] 보낸 메시지 4개(~66 tok) → 모델 응답: tool_use
           툴 결과 → "src/b.ts:1:// TODO: 캐시\nsrc/a.ts:1:// TODO: 로그인\nsrc/a.ts:2:// TODO: 로그아웃"
  [step 3] 보낸 메시지 6개(~118 tok) → 모델 응답: text

  최종 답: TODO는 3개입니다: 로그인, 로그아웃, 캐시.
  모델 호출 3회, 누적 입력 ~213 tok (마지막 배열 크기 ~139 tok)
  ```

- X2-1-11 L1170–1172 [Claude] 해석
  - 배열이 2 → 4 → 6개로 커진다. 한 바퀴마다 `assistant`와 `tool` 항목이 하나씩 붙는다.
  - 누적 입력(213)이 마지막 배열(139)보다 크다. 같은 앞부분이 매번 재전송되기 때문이다.
  - 훅은 모델이 아니라 하네스 코드다. 모델이 `rm`을 요청했지만 실행되지 않고 거절 메시지가 툴 결과로 돌아갔다. 앞선 대화의 "강제는 모델 밖에서"가 이 지점이다.
- X2-1-12 L1174 [Claude] 용어: 모델 호출 한 번 = 스텝(step) 또는 턴(turn). 사람이 메시지 하나를 보내고 에이전트가 최종 답을 낼 때까지 전체 = 런(run). 텍스트로 답하며 멈추는 것 = stop, 이유 = stop reason. 하네스마다 용어가 조금씩 다르다. (참고: 브리프 §3.2의 `rn`=에이전트 실행(run), `tc`=도구 호출과 대응한다.)

### 1.5 루프에 붙는 부품: 용어 지도 (0.4절)

- X2-1-13 L1180–1200 [Claude] 하네스 기능은 네 지점 중 하나에 붙는다: 루프 시작 전, 모델 호출 직전, 툴 실행 앞뒤, 루프 바깥.

  ```

         │
         ▼
  ┌─▶ [모델 호출 직전]   컴팩션(배열이 너무 크면 요약), 리마인더 주입
  │      │
  │      ▼  model(messages)
  │      │
  │      ▼  응답이 tool_use면
  │   [툴 실행 앞]   훅·권한 검사 (차단 가능)
  │      │
  │      ▼  툴 실행: 내장 툴 / 커스텀 툴 / MCP 툴 / 서브에이전트
  │      │
  │   [툴 실행 뒤]   훅 (결과 수정·기록)
  │      │

  ```

### 1.6 서브에이전트 (0.5절)

- X2-1-17 L1224–1231 [Claude] 서브에이전트는 하네스 입장에서 툴 하나다. 실행 내용이 "새 메시지 배열을 만들고 while 루프를 한 번 더 돌린 뒤 최종 텍스트를 돌려주는 것"이다.

  ```js
  tools.subagent = async ({ task }) => {
    const childMessages = [childSystem, { role: "user", content: task }]; // 새 배열 (fresh)
    return await runLoop(childMessages);    // 0.1의 while 루프를 그대로 재사용
  };                                        // 자식의 최종 텍스트만 부모 배열에 들어간다
  ```

- X2-1-18 L1235–1237 [Claude] 변형 용어
  - fresh vs fork: 자식 배열을 빈 상태로 시작하면 fresh, 부모 배열을 복사해 시작하면 fork.
  - sync vs async(background): 툴이 자식 루프 끝까지 기다리면 동기, ID만 돌려주고 나중에 결과를 메시지로 넣으면 비동기.
  - Agent Teams: 자식 루프끼리 메시지를 주고받게 한 것.
- X2-1-19 L1239 [Claude] 핵심 이점은 자식 배열이 부모 배열과 분리된다는 점이다(자식이 파일 100개를 읽어도 부모 배열엔 요약 한 단락). 대가: 자식을 띄울지, 몇 개 띄울지를 부모 모델이 매 턴 판단한다. 사용자가 처음 대화에서 짚은 "서브에이전트 스폰조차 비결정성에 의존한다"가 이것이다.

### 1.7 RLM이 바꾸는 위치 (0.6절)

- X2-1-20 L1245 [Claude] RLM은 새 종류의 루프가 아니다. 같은 루프에서 두 가지를 바꿨다: (1) 툴을 "코드 실행기(REPL) 하나"로 바꿈, (2) 큰 데이터를 메시지 배열 밖의 변수로 옮김.

### 2.6 한 턴의 행동 단위 (3.5절)

- X2-2-20 L1454 [Claude] codemode는 "한 번에 끝내는 프로그램"을 유도한다. VM이 스크립트 한 번 뒤 사라지고 `store()`는 1MB까지만 담으므로 큰 데이터를 다음 턴으로 넘길 수 없다. "읽기 → 거르기 → 위임 → 합치기"를 스크립트 하나에 담는 것이 자연스럽다. 다음 턴에 다시 필요하면 툴로 다시 읽는다.
- X2-2-21 L1456 [Claude] RLM은 "노트북처럼 조금씩 쌓는 탐색"을 유도한다. 변수가 턴을 넘어 살므로 턴 1에서 엿보고, 턴 2에서 거르고, 턴 3에서 위임할 수 있다. 데이터 모양을 모르고 시작해도 된다.
- X2-2-22 L1458 [Claude] 대가: codemode는 데이터 구조를 처음부터 알아야 좋은 스크립트를 쓸 수 있고, 모르면 탐색 스크립트를 여러 번 돌리며 매번 다시 읽는다. RLM은 턴마다 모델 호출이 한 번씩 더 들고, 큰 변수를 붙잡은 프로세스를 그동안 유지해야 한다.

### 2.7 분해: 코드와 호출 트리 (3.6절)

- X2-2-23 L1462 [Claude] 분해(decomposition): 큰 문제를 하위 호출이 감당할 크기로 나누는 방식. RLM에서는 사람이 미리 정하지 않고 루트 모델이 실행 중에 코드로 쓴다.
- X2-2-24 L1464–1480 [Claude] 모델이 쓸 법한 분해 정책을 고정해서 돌린 코드(`decomp-lab.mjs`)

  ```js
  function rlm(query, context, d = 0, maxDepth = 1) {
    const rows = context.split("\n");
    // ① 엿보기: 구조 파악. 모델은 이 출력만 본다
    // ② grep: 코드로 거를 수 있으면 먼저 거른다 (LLM 호출 없음)
    const hit = d === 0 ? rows.filter(l => target.test(l)) : rows;
    // ③ 크기에 따라 분해 방식 선택
    if (hit.length <= 25) return llmQuery(hit.join("\n"));        // 작으면 바로 위임
    const size = d < maxDepth ? Math.ceil(hit.length / 3) : 25;   // 크면 쪼갬
    const parts = chunk(hit, size);
    const results = parts.map(p => d < maxDepth
      ? rlm(query, p.join("\n"), d + 1)                            // 하위 RLM (재귀)
      : llmQuery(p.join("\n")));                                   // 하위 LM
    // ④ 합치기는 코드로
    return results.reduce((a, b) => a + b, 0);
  }
  ```

  단계: ① 엿보기 → ② 코드로 거르기(LLM 호출 없음) → ③ 크기 기준 분해(25행 이하면 바로 `llm_query`, 아니면 깊이 상한 전엔 3조각으로 하위 RLM, 상한에선 25행 조각으로 하위 LM) → ④ 코드로 합치기(`reduce` 합).

### 7.2 정의와 출발점 (1절)

- X2-7-04 L1851 [Claude][원문 요약] 한 문장 정의: "Helm은 사람이 방향과 판단의 주인으로 남으면서 AI와 함께 탐구하고, 실행하고, 결과를 전체에 반영하게 하는 시스템이다."
- X2-7-05 L1853 [Claude] 출발 문제: 에이전트의 실행 속도와 병렬성이 사람이 이해·감독하는 속도보다 빨라졌다. 병목은 코드 생성 능력이 아니라 사람 쪽 능력이다. 놓치는 것 다섯 가지: 지금 무엇이 진행 중인지, 무엇이 사실이고 무엇이 추측인지, 어떤 선택이 중요한지, 완료했다는 말을 믿어도 되는지, 하루 뒤 돌아왔을 때 어디서 다시 시작해야 하는지. (참고: 브리프 결정 1은 이후 출발 동기를 "원함 발견"으로 정했다. [이후 변경 가능: 브리프 결정 1] — 이 복습의 출발 문제는 v0.1·v0.2 문서 기준이다.)
- X2-7-06 L1855–1866 [Claude] 일반 하네스는 "프롬프트 한 번으로 결과를 완성"을 최적화한다. Helm은 `justified progress under bounded human attention`(사람의 주의력이 제한된 조건에서의 정당화된 진척)을 최적화한다. 정당화된 진척의 네 조건(모두 필요):
  1. 실제로 무언가가 가치 있는 방향으로 바뀌었다.
  2. 그 변화가 목적에 맞다고 믿을 근거가 있다.
  3. 누가 어떤 trade-off와 책임을 받아들였는지 명확하다.
  4. 지역적인 변화가 전체와 맞고, 다음 변화에 대응할 능력이 남아 있다.
  - 공리 A2(파일을 많이 바꿨거나 보고서가 길다고 진척이 아니다)가 여기서 나온다(L1868).

### 7.3 세계 모델 (2절, 위젯 `helm_world_model_nem_ap`)

- X2-7-07 L1872, L1878–1881 [Claude] 세 의미 세계와 두 통치 평면
