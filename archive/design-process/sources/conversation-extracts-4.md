## 0. 범위 직전 맥락 (발췌 3 범위, 연결용)

이 구간의 튜터링은 바로 앞(발췌 3 범위)의 내용을 이어받는다. 이 구간을 읽는 데 필요한 것만 행 번호와 함께 적는다. 상세는 `conversation-extracts-3.md`를 본다.

- 0-1. 구분 확인(discriminating check): "원인이 무엇이냐에 따라 결과가 달라지는 관찰"이 쓸모 있는 확인이다. "캐시 코드가 없다"는 원인이 DB 쿼리여도 똑같이 나오므로 추측을 가려 주지 못한다. "서버 응답 2초 중 DB 쿼리가 1.8초"는 구분 확인이다. L3012 [Claude]
- 0-2. E 칸 승격 구조: `관찰 → 추측 → 판단`, 승격에 `근거 + 반대 근거 + 구분 확인`이 필요하다. L3016–3020 [Claude]
- 0-3. 승격 조건 코드(`claim/promote`): `hasEvidence`(근거가 있고 모든 근거 id가 `state.toolResults`에 있음) 그리고 `checkedAgainst`(`c.counterChecked === true && c.counterEvidence.length === 0`). 사용자가 "반증 조건이 없고 증거가 명확히 확인된것"이라고 답했고(L3119 [사용자]) Claude가 "반증이 없다"를 "반증을 찾아봤는데 없었다"로 다듬어 `counterChecked` 칸을 따로 두었다. L3125–3135 [Claude] [정정: "반증 없음" → "반증을 찾아봤는데 없음"]
- 0-4. A 루프를 사람만 하는 이유: 사용자 답 "책임소재를 질 대상이 없음, 확인과 반영이라는 것 또한 LLM이 진행하면 불확정성이 반드시 따라올 수 밖에 없기때문"(L3069 [사용자]). Claude 대응: 공리 A6(사람이 최종 약속의 저자), 작업한 모델이 자기 결과를 확인하면 같은 착각을 반복하는 "스스로 채점하는 구조". L3074–3075 [Claude]
- 0-5. helm.mjs 실행 결과: 21번 시도 중 8번 거부. 거부 행: `3 claim/promote 근거 없음`, `4 claim/link 근거 T9는 실제 실행 결과가 아님`, `5 tool/result 도구 결과는 런타임만 기록 가능`, `7 claim/promote 반증을 찾아보지 않음`, `10 claim/promote 반대 근거 있음: T2`, `17 result/submit 근거 모델설명는 실제 실행 결과가 아님`, `19 result/accept 결과 확인은 사람만 가능`, `21 (직접 수정 시도) 상태는 읽기 전용`. 최종 상태: C1 "캐시가 없어서 느리다"는 추측에 머묾, C2 "DB 쿼리가 느리다"는 판단, 결과는 사람이 확인(근거 T4). 거부된 시도도 기록에 남는다. ### 1.3 A/P

- 1-5. 정의. L3228–3229 [Claude]
  - A(참여자): 행위자마다 할 수 있는 일의 목록
  - P(정책): 그 일을 어떤 조건에서 할 수 있는지에 대한 규칙
- 1-6. helm.mjs는 `action.actor !== "human"`처럼 "누구냐"로 검사했다. Helm v0.2는 이 방식을 쓰지 않고 행위자를 능력 목록으로 정의한다. L3231 [Claude]
- 1-7. 연습 문제: 행위자 셋(사람, 작업 에이전트 "코드를 고치는 모델", 검증 에이전트 "작업 에이전트의 결과를 따로 확인하는 다른 모델") × 능력 넷(제안하기, 코드 변경 실행, 근거가 맞다고 증언하기, 결과 확인(받아들이기)). L3235–3245 [Claude]
- 1-8. 사용자 답. L3250–3252 [사용자]

| | 제안하기 | 코드 변경 실행 | 증언하기 | 결과 확인 |
|---|---|---|---|---|
| 사람 | O | O | O | O |
| 작업 에이전트 | O | O | X | X |
| 검증 에이전트 | X | X | O | X |

- 1-9. [정정] 검증 에이전트의 "제안하기"는 X에서 "부분적으로 O"로 고쳤다. 검증자는 코드 변경은 제안하지 않지만 반대 근거는 제안할 수 있어야 한다(앞의 미리보기에서 검증자가 "setSearchParams에 replace 옵션이 없다"를 찾아낸 장면). "같은 '제안'이라도 무엇을 제안하느냐에 따라 허용이 달라지는 셈". L3257 [Claude]
- 1-10. `actor !== "human"` 한 줄로 이 표를 표현할 수 없다. 작업 에이전트와 검증 에이전트는 둘 다 사람이 아닌데 "증언하기" 칸이 다르다. 그래서 Helm은 "누구냐" 대신 "무엇을 할 수 있냐"로 적는다. L3259 [Claude]
- 1-11. 능력표 코드. L3261–3268 [Claude]

```ts
const A = {
  human:    ["propose", "execute", "attest", "accept"],
  worker:   ["propose", "execute"],
  verifier: ["propose:counterEvidence", "attest"],
};
const can = (actor, cap) => A[actor].includes(cap);
```

  - 주의: `propose:counterEvidence`처럼 능력에 제안 대상 종류가 붙는다.
- 1-12. 표만으로 부족한 규칙: "작업 에이전트는 코드를 바꿀 수 있다"는 O지만 실제로는 "합의된 폴더 안에서만" 바꿀 수 있어야 한다. 그때그때 상황에 따라 붙는 조건이 P다. L3270 [Claude]
  - A: 고정된 능력표("이 행위자가 이 종류의 일을 할 수 있는가")
  - P: 지금 상황에서의 조건("지금 이 범위, 이 시점에 해도 되는가") L3272–3273
- 1-13. A/P 연습 a~d와 사용자 답 "A A P P". L3277–3283 [Claude]/[사용자]
  - a) 작업 에이전트는 결과를 확인할 수 없다
  - b) 작업 에이전트는 합의된 폴더 안에서만 코드를 바꿀 수 있다
  - c) 검증 에이전트는 코드를 고칠 수 없다
  - d) 어떤 결과든, 그 결과를 만든 행위자는 그 결과의 근거를 증언할 수 없다
- 1-14. A/P 판별 시험(판별 질문). L3288–3289 [Claude]
  > **일하는 도중에 상황이 바뀌면 답도 바뀌는가?**
  > 바뀌면 P, 언제나 같으면 A입니다.
  - 브리프 용어집 "A / P" 항목의 판별 질문과 같다.
- 1-15. 정답 표. a와 d는 사용자 답이 맞고, b와 c가 서로 바뀌었다. L3286, L3293–3298 [Claude]

| 규칙 | 상황이 바뀌면? | 답 |
|---|---|---|
| a) 작업 에이전트는 결과 확인 불가 | 어떤 작업이든 항상 불가 | A |
| b) 합의된 폴더 안에서만 코드 변경 | 합의가 바뀌면 바꿀 수 있는 폴더도 바뀜 | P |
| c) 검증 에이전트는 코드 수정 불가 | 어떤 상황이든 항상 불가 | A |
| d) 결과를 만든 행위자는 그 결과를 증언 불가 | 이번 결과를 누가 만들었는지에 따라 달라짐 | P |

- 1-16. 판별 요령: 금지 문장인지 허용 문장인지는 상관없다. 능력표의 X 칸도 A다. "~할 수 있다"로 시작해도 조건이 지금의 합의 상태에 따라 달라지면 P다. L3300 [Claude]
- 1-17. 추가 확인 e) 사람은 결과를 확인할 수 있다, f) 배포처럼 되돌리기 어려운 행동은 작업 에이전트라도 사람이 승인한 뒤에만 할 수 있다. 사용자 답 "A P", 둘 다 정답. L3304–3311 [Claude]/[사용자]
- 1-18. 자기 결과 증언 금지(d)는 P로 분류된다. 설계에서 "결과를 만든 행위자"를 레코드에서 계산해야 한다는 뜻이다(정책 엔진 입력에 결과 작성자가 필요). L3298 [Claude]의 판정에서 나온 설계 함의(발췌자 메모).

### 1.4 effect class(R0~R4)와 맡긴 범위

- 1-19. Helm kernel v0.2 문서의 effect class 정의를 프론트엔드 예시와 함께 옮긴 표. 행동을 "되돌리기 얼마나 어려운가"로 다섯 등급으로 나눈다. L3313–3321 [Claude]

| 등급 | 문서 정의 | 예 |
|---|---|---|
| R0 | 로컬, 읽기만 | 파일 읽기, grep, 로컬에서 성능 측정 |
| R1 | 로컬, 되돌릴 수 있는 변경 | 파일 수정, 로컬 브랜치 커밋 |
| R2 | 공유되거나 밖에서 보이지만 되돌릴 수 있음 | 브랜치 push, PR 생성, 스테이징 배포 |
| R3 | 비용이 크거나, 민감하거나, 복구가 어려움 | 프로덕션 배포, 유료 API 대량 호출 |
| R4 | 되돌릴 수 없거나 기본 금지 | main에 force push, 프로덕션 데이터 삭제 |

## 2. 사용자의 다섯 아이디어([120])와 응답([121])

### 2.1 사용자 진술 (L3411 [사용자], 원문)

> 그리고 내가 아까전에 말했던 mode라는 얘기가 이거랑 연관이 됐던건데, 모델이 자율적으로 판단해 어떤 결정사항을 내렸을 때, 이를 차후 확인할 수 있는 방안이 있어야 할 것 같다고도 생각했어. 혹은 질문을 얼마나 자주 하냐에 대한 기준이 있고 조건을 세개 다 만족해야만 질문을하도록 할건지 , 하나만 있어도 질문하도록 할건지 등을 선택할 수 있으면 유용하지 않을까 싶었던거랑, inquiry 같은 탐구작업을 할 때, 문제 frame을 구성하는 관점이 매우 다양하게 접근할 수 있도록 하던지, 어느정도 범위 내에서 inquiry를 진행할 수 있게 할것인지에 대한 자율성과 탐구 범위 등에 대한 정도를 조정할 수 있는 옵션이 그때그때 필요하지 않을까 싶긴했음. 이걸 유저가 세팅에서 조정하는 방법도 있겠지만, 각 역할별  에이전트 모델링을 미리 내가 해놓고, 유저의 입력값에 따라 어떤 에이전트 모델을 쓸지를 라우팅 하는 방식도 괜찮을 거 같기도 하다는 생각이고, inquiry 과정 자체가 repl구조로 이루어지는것도 어떤가 싶기도 하고

다섯 아이디어로 정리하면 다음과 같다.
1. 모델이 혼자 정한 결정을 나중에 확인하는 방안
2. 질문 빈도 기준: 세 조건 AND인지 하나만으로(OR) 묻는지를 고를 수 있게
3. 탐구의 관점 폭(frame 관점 다양성), 범위, 자율성을 그때그때 조정하는 옵션
4. 설정 화면 대신 역할별 에이전트 모델을 미리 만들어 두고 입력에 따라 라우팅
5. 탐구 과정을 REPL 구조로

#### Goal, Concern, WorkUnit (1차 정의)

- 2-21. 표. L3475–3479 [Claude]

| 단위 | 뜻 | 수명 | 런타임에서 |
|---|---|---|---|
| Goal | 이루려는 것 | 몇 주~몇 달 | 기록만 있음 |
| Concern | 지금 주의가 필요한 상황 (문제, 기회, 위험) | 며칠 | O/I/C/A 상태 기계 하나 |
| WorkUnit | 합의 하나로 맡긴 구체적인 작업 | 몇 시간 | 내부 에이전트 루프 실행 |

- 2-24. 레코드 승격 순서: `captured(적힘) → structural(형식 갖춤) → qualified(근거 갖춤) → accepted(받아들여짐)`. 옆길 상태 셋: contested(이의 걸림), stale(낡음), superseded(다른 것으로 대체됨). L3487–3491 [Claude]

- 2-26. 투영: 같은 기록에서 보는 사람과 시점에 맞게 뽑아낸 읽기 전용 화면. Redux의 selector와 같다. 복귀 요약은 사람이 돌아왔을 때의 투영이고, 모델에게 주는 컨텍스트도 투영이다. L3497–3498 [Claude]

## 4. 비판 라운드([123], L3555–3736)

Claude는 2번(선택 요청 기준)과 4번(OICA)에 반대 시각과 외부 레퍼런스를 넣고, 5번(Projection)은 Helm 자료를 다시 찾아 확인했다. L3555 [Claude]

### 4.1 선택 요청 기준을 다른 분야의 틀에 대 보기

- 4-1. 세 조건은 코딩 전용은 아니지만 질적으로 적혀 있어서 판정이 애매하다. L3559 [Claude]
- 4-2. 결정 이론의 정보 가치(Value of Information, VoI): "물어서 얻는 기대 개선 > 묻는 비용"일 때 묻는다. Helm의 세 조건은 이것을 말로 풀어 쓴 형태다. L3561–3565 [Claude]
  - 조건 1 ≈ 에이전트의 기본 선택이 틀릴 확률
  - 조건 2 ≈ 틀렸을 때의 손실 차이
  - 조건 3 ≈ 묻는 비용
- 4-3. 셋은 곱셈 관계라 하나라도 0이면 묻지 않는다. AND는 임의로 고른 규칙이 아니라 이 구조에서 나오는 결과다. L3567 [Claude]
- 4-4. 그래서 다이얼은 AND/OR가 아니라 "비용 항의 크기"로 두는 것이 맞다. L3567 [Claude] [정정: [121]의 "조건별 문턱 다이얼"(2-6)을 "묻는 비용 항의 크기"로 다시 정리] [이후 변경: 브리프 결정 16. 최종은 AND 기본 + 조건별 문턱 다이얼 [제안], AND/OR 옵션은 사용 후 결정]
- 4-5. Horvitz의 mixed-initiative 원칙(CHI 1999): 시스템이 "실행 / 확인 질문 / 아무것도 안 함" 셋 중 기대 효용이 가장 큰 것을 고른다. 강조점 셋: 사용자의 주의 상태를 보고 타이밍을 정한다, 잘못 추측했을 때의 비용을 줄인다, 불확실할수록 서비스 범위를 좁힌다(예: 끝까지 하지 않고 초안까지만). L3569–3573 [Claude]
- 4-6. Helm에는 "묻는다 / 혼자 정한다" 둘만 있고 "범위를 줄여서 진행"하는 중간 선택지가 없다. L3575 [Claude] (브리프 §3.5 "06 보완(범위를 줄여 진행 …)" → P6(11))
- 4-7. Parasuraman, Sheridan, Wickens(2000)의 자동화 유형과 수준: 자동화를 정보 수집, 분석, 결정 선택, 실행 네 기능으로 나누고 기능마다 자동화 수준을 따로 정한다. 질문 빈도 다이얼도 하나로 두지 말고 기능별로 둘 수 있다는 근거. L3577–3578 [Claude]
- 4-8. 인터럽션 연구: McFarlane은 끼어드는 방식을 즉시, 협상, 중재, 예약 넷으로 나눴다. Iqbal과 Bailey의 연구에서는 작업 경계에서 끼어들면 비용이 작았다. 조건 3은 "묻는가"보다 "언제, 어떤 방식으로 묻는가"로 나누는 편이 정확하다. L3580–3581 [Claude]
- 4-9. 최근 LLM 에이전트 연구. L3583–3585 [Claude]
  - Ask-when-Needed(2024): 도구 호출 전마다 지시가 충분한지 확인하고 부족하면 묻는다.
  - Ask or Assume?(2026): 작업 에이전트와 별도로 의도 감시 에이전트를 두고, 빠진 맥락을 감지하면 사용자에게 묻게 했다. 일부러 덜 명세한 SWE-bench 과제에서 해결률 61.2% → 69.4%. 완전히 명세한 경우 70.8%. 저자들은 인과를 단정하지 않는다.
- 4-10. 묻는 판단을 작업 에이전트가 아니라 별도 감시자에게 맡기는 구조는 Helm의 검증 에이전트 분리와 같은 방향이다. L3587 [Claude] (뒤에서 중재자로 이어짐, 5-8)

### 4.3 선택 요청의 세 부분 재작성

- 4-12. 선택 요청은 세 부분으로 다시 쓸 수 있다. L3600–3604 [Claude]

```text
권리 게이트   이 결정이 사람의 권리인가 → 그렇다면 묻는다
정보 게이트   틀릴 확률 × 손실 차이 > 묻는 비용 → 그렇다면 묻는다
방식          지금 묻기 / 모아서 묻기 / 가정하고 진행하며 기록
```

- 4-13. 질문 빈도 다이얼은 "묻는 비용"의 크기를 정하는 값이 된다. L3606 [Claude]
- 4-14. [브리프 결정 12와 같음: 권리 게이트와 정보 게이트, 기록과 전달 분리] 브리프 용어집: 권리 게이트 = 사람만 정할 권리가 있는 것, 정보 게이트 = 사람의 답이 정보로서 가치가 있는 것.
- 4-15. 긴장 관계(설계 시 유의): 같은 메시지 안에서 "권리 게이트(send, 돈, 대리 발언)와 되돌리기 판별은 앞서 정하신 대로 권한 레이어에서 처리합니다"라고도 했다(L3670 [Claude]). 권리 게이트를 Helm 묻기 쪽(4-12, 5-11의 "권리 게이트 → 즉시")에 둘지 권한 레이어에 둘지 대화 안에서 정리되지 않았다. 브리프 결정 12는 권리 게이트를 Helm 묻기 재설계에 포함하고, 결정 2는 가역성 판별만 권한 레이어로 보낸다. 21(d) 참고.

### 4.4 OICA에 대한 반대 측 비판 다섯

- 4-16. 비판 1 "숙련자는 탐구하지 않는다". Boyd의 OODA에는 Orient에서 Decide를 거치지 않고 Act로 가는 경로가 있다. Klein의 Recognition-Primed Decision에서 현장 전문가는 대안을 비교하지 않고 처음 떠오른 안을 머릿속 시뮬레이션으로 확인한 뒤 실행한다. 범용 작업의 상당수는 I 없이 O → C로 가는 것이 정상이다. 보강: I를 건너뛰는 경로를 정상 경로로 인정하고 건너뛰었다는 사실만 기록한다. L3612–3614 [Claude]
- 4-17. 비판 2 "순서는 상황의 종류에 따라 달라진다". Cynefin 네 상황과 순서(명확: 감지 → 분류 → 대응, 복잡: 감지 → 분석 → 대응, 복합: 탐침 → 감지 → 대응, 혼돈: 행동 → 감지 → 대응). OICA는 "복잡" 상황을 전제로 한 순서다. 글의 방향, 사람 사이의 일, 시장 반응 같은 복합 상황에서는 C(작게 실행)가 I보다 먼저 와야 한다. 보강: Concern에 상황 유형을 붙이고 유형별 기본 순서를 둔다. 실험 WorkUnit을 I의 일부로 인정한다. L3616–3627 [Claude]
- 4-18. 비판 3 "C 루프는 실행에 치우쳐 있다". 범용 작업 다수는 산출물(글, 조사 보고, 계획)을 만드는 일이라 초안이 곧 결과이고 곧 검토 대상이어서 C와 A가 겹친다. 조사나 의사결정 지원처럼 I에서 끝나는 작업도 많다. 보강: 루프를 혼자서도 돌 수 있는 모드로 둔다. L3629–3631 [Claude]
- 4-19. 비판 4 "A 루프의 확인 기준이 없는 작업이 있다". 창작이나 전략에는 근거로 받아들일 정답이 없고 결과 확인은 취향 판단이다. 보강(당시): 작업 유형별로 확인 방식을 다르게 두고, 취향형 작업은 "비교 가능한 대안 2~3개 + 선택"이 확인 방식. L3633–3635 [Claude] [정정: [124]에서 사용자가 "2~3개 + 선택"을 거부, [125]에서 Claude 동의(6.3)] [이후 변경: 브리프 결정 18]
- 4-20. 비판 5 "사람과 에이전트 둘만 있다고 가정한다". 범용 작업에는 제3자가 끼어든다(메일 수신자 답장, 회의 참석자 결정). A 평면에는 외부 행위자가 있지만 루프에는 "외부 응답을 기다리는 상태"가 없다. 보강(당시): 대기를 정식 상태로 두고 외부 응답을 관찰로 받는다. L3637–3639 [Claude] [정정: [124]~[125]에서 별도 대기 상태 대신 "탐구 중 발견된 관찰 + 기대 레코드"로 정리(8장)] [브리프 결정 9]
- 4-21. 뒷받침 증거: Parasuraman 등의 네 기능(정보 수집, 분석, 결정 선택, 실행)은 O, I, C, A와 거의 같은 분할이다. 다른 분야에서 비슷한 4단계 구분이 나왔다는 뜻이다. 동시에 그 모델은 네 기능을 순환이 아니라 기능별로 따로 자동화하는 대상으로 다룬다. 루프가 순차가 아니라는 판단과 일치한다. L3641 [Claude]

### 4.6 능력은 원시 행동으로 (두 층)

- 4-25. 동의. "코드 변경"은 도메인 용어였다. 능력을 두 층으로 나눈다. L3656–3659 [Claude]

  - 기록 능력(Helm 커널 action): observe, propose, attest, accept, integrate. 무엇을 기록에 쓸 수 있는지를 정한다.
  - [브리프 결정 4와 같음]
- 4-26. 모드 묶음은 두 층에서 각각 일부를 고르고 다이얼 값을 붙인 것. L3661 [Claude] [브리프 결정 3과 같음]

| 묶음 | 원시 행동 | 기록 능력 |
|---|---|---|
| 탐색 | read, execute(읽기 목적), spawn | observe, propose |
| 실행 | read, write, execute | observe, propose |
| 검증 | read, execute | observe, propose(반대 근거), attest |
| 복귀 안내 | read | observe |

  - 이 표에서 accept, integrate는 어느 묶음에도 없다. accept는 사람만 하므로(0-4, 2-31) 에이전트 묶음에 없는 것이 맞다. integrate의 소유자는 정해지지 않았다(21(d)).
  - send, ask는 어느 묶음에도 없다.
- 4-28. 권리 게이트(send, 돈, 대리 발언)와 되돌리기 판별은 앞서 정한 대로 권한 레이어에서 처리한다. L3670 [Claude] (4-15의 긴장 관계 참고)

### 4.7 개념 정정: Goal, Concern, Projection

- 4-29. Goal: 사용자 정의에 동의. Helm v0.2 정제 문서(`docs/foundations/10-refinement-candidate.md`)의 C7 항목은 Purpose가 초기화 때 한 번 저장되고 바뀌지 않는 것을 모순으로 짚었고 "Goal은 versioned normative entity다"로 정리했다. 수정, 중단, 대체를 이벤트로 남기고, Goal이 바뀌면 관련 컨텍스트와 합의를 무효화할 수 있게 한다. L3674–3676 [Claude] [사용자 진술 L3546에 동의] [브리프 결정 11과 같음]
  - 의존 규칙 (5) "Goal 변경 시 사람 확인"(브리프 결정 15, [제안])과 연결된다.
- 4-30. Concern: [정정] Claude의 "주의가 필요한 상황"은 영어 단어를 옮긴 것에 가까웠다. 문서 정의도 "문제, 기회, 위험, 불확실성일 수 있다". Concern은 "10단계 과정을 돌릴 후보가 되는 상황 그 자체"로 본다. L3678–3680 [Claude] [사용자 진술 L3548에 동의] [브리프 결정 11과 같음]
- 4-31. Projection: 사용자가 말한 개념은 Helm 자료에 있으나 이름은 Projection이 아니라 Method Transfer(방법론 전이)다. 위치: `docs/research/method-transfer-map.md`(35개 방법론), `docs/research/method-cards/`(20개 카드), `docs/research/README.md`. L3686–3687 [Claude] [자료 확인]
- 4-32. Method Transfer 절차(7단계). L3690–3698 [Claude]

```text
원래 분야와 그 분야의 실패
  → 그 분야의 환경 가정
  → 분야와 무관하게 유지되는 메커니즘
  → 복사하면 안 되는 것
  → Helm 요소로 번역
  → 반증 가능한 가설
  → 프로토타입과 지표
```

- 4-33. 예: 군의 Mission Command에서 계급 구조는 복사하지 않고 "상위의 의도·제약 + 현장의 판단 자율"이라는 원리만 뽑아 Purpose, 맡긴 범위, 상향 조건으로 옮겼다. L3700 [Claude]
- 4-34. Helm 문서에서 Projection이라는 단어의 다른 두 뜻. L3702–3704 [Claude]
  1. ContextProjection: 기록에서 대상별로 뽑은 읽기 전용 화면(kernel, 아키텍처 문서)
  2. 상황 인식(Endsley) 3단계 중 "앞으로 어떻게 될지 예측"(복귀 요약의 Changes–Assessment–Projection)
- 4-35. 차이: 자료에서 Method Transfer는 Helm 자체를 설계하기 위한 연구 방법이었고, 런타임 안에서 사용자 문제에 적용하는 기능은 아니었다. 사용자가 말한 것은 이 절차를 탐구 루프 안의 동작으로 옮기는 것이다. 런타임 동작 5단계: L3706–3712 [Claude]
  1. 지금 문제와 구조가 비슷한 실패를 겪은 다른 분야를 찾는다
  2. 그 분야의 해법에서 환경과 무관한 원리를 뽑는다
  3. 복사하면 안 되는 것을 적는다
  4. 지금 문제의 가능성 후보로 넣는다
  5. 반증 조건을 붙인다
- 4-36. 발산 표의 "렌즈" 열이 이 자리이고, 이미 정리된 35개 방법론이 렌즈 목록의 초기값이 된다. 이름은 Projection과 겹치지 않게 "방법 전이"나 "렌즈"로 두자고 제안. L3714 [Claude] [이후 변경: 브리프 결정 13 / HANDOFF §2.2-3. 이름은 Method Transfer, "투영"은 정본을 읽어 만든 화면·컨텍스트에만 씀]
  - [127]에서 Method Transfer는 가능성 탐구의 중심 방법으로 자리 잡는다(10-4). 브리프 용어집: "가능성 탐구 내 동작".

## 5. McFarlane 전달 방식의 전개([124]~[125])

### 5.1 사용자 진술

- 5-0. "'끼어드는 방식을 즉시, 협상, 중재, 예약 네 가지로 나눴습니다.' 이게 나는 핵심인 것 같은데, 이게 어쩌면 결정 이론의 정보가치의 세 조건의 미흡하거나 불확정적인 부분을 채울 수 있을 것 같아 조금더 디벨롭 해줘". L3739 [사용자]

### 5.2 McFarlane(2002) 실험과 권고

- 5-1. 원문을 다시 확인하고 정리. 실험은 36명이 참여한 실험실 이중 과제 실험. L3750, L3756 [Claude] [확인 수준: 원문 확인, 출처 L3912 McFarlane HCI 2002 PDF]
- 5-2. 네 방식의 정의와 결과. L3758–3763 [Claude]

| 방식 | 정의 | 결과 |
|---|---|---|
| 즉시 | 생기는 즉시 전달하고, 사람은 하던 일을 멈추고 답해야 함 | 응답은 가장 빨랐지만, 입력 오류가 가장 많고 원래 작업 정확도가 나빴음. "가장 방해받았다"고 느낌 |
| 협상 | 질문이 왔다는 것만 알리고, 언제 볼지(볼지 말지)는 사람이 정함 | 종합적으로 가장 좋았음. 원래 작업 정확도가 높고 오류가 적었으며 가장 많이 선호됨. 대신 답이 가장 늦었음 |
| 중재 | 대리자가 받아 두고, 사람의 작업 부하를 보고 전달 시점을 정함 | 대부분 중간 성적. 원래 작업의 효율은 좋았음 |
| 예약 | 정해진 시간표에 맞춰 전달 (실험에서는 25초마다) | 작업 전환은 가장 적고 예측하기 쉬웠지만, 원래 작업 정확도와 응답 속도가 가장 나빴음 |

- 5-3. 논문 권고 셋. L3765–3768 [Claude]
  - 응답 속도가 결정적인 경우가 아니면 협상을 기본으로 한다.
  - 사람마다 선호가 크게 다르니(약 4분의 1은 협상을 싫어했음) 방식을 고를 수 있게 한다.
  - 작업이 잠시 쉬는 지점에 전달하면 두 작업 모두 좋아진다.
- 5-4. 예약 방식이 나빴던 것은 시간표가 작업 흐름과 무관하게 고정되어 있었기 때문이다. 작업의 쉬는 지점에 맞춘 예약은 결과가 다를 것으로 봐야 한다. L3770 [Claude]

### 5.3 VoI의 약점과 두 결정 분리

- 5-5. VoI 방식의 약점: 세 값(틀릴 확률, 틀렸을 때의 손실, 묻는 비용)을 정확히 추정해야 한다. 특히 "묻는 비용"은 고정값이 아니라 그때 사람이 무엇을 하고 있는지에 따라 달라진다. L3774 [Claude]
- 5-6. "물을까 말까"를 두 결정으로 나눈다. L3778–3781 [Claude]

```text
결정 1. 질문이 있는가        → 낮은 문턱. 불확실하면 일단 질문을 기록한다 (비용이 거의 없음)
결정 2. 언제, 어떻게 전달하나 → 네 방식 중 하나를 고른다
```

- 5-7. 이렇게 나누면 세 값을 정확히 추정해야 하는 경우는 즉시를 고를 때뿐이다. 나머지 세 방식은 추정이 틀려도 견딘다. L3783 [Claude]
- 5-8. 방식별 의미. L3785–3787 [Claude]
  - 협상: "지금 볼 가치가 있나"를 사람이 직접 판단한다. 에이전트가 가장 추정하기 어려운 조건 3을 사람에게 넘기는 셈이다.
  - 중재: 작업 에이전트가 아닌 별도 중재자가 사람의 상태를 보고 판단한다. "Ask or Assume?" 연구의 의도 감시 에이전트가 이 자리다. (브리프 용어집 "중재자": 질문 전달 시점과 묶음을 정하는 에이전트)
  - 예약: 시간이 아니라 Helm의 작업 경계에 모아서 전달한다. 라운드 끝, 루프 전환, 복귀 요약 같은 지점.
- 5-9. [브리프 결정 12와 같음: 기록과 전달 분리, 전달 방식(즉시·협상·중재·예약)]

### 5.4 질문 레코드

- 5-10. 질문 레코드 필드. L3793–3801 [Claude]

```text
question:
  내용           무엇을 묻는가
  임시 가정      답을 받기 전까지 에이전트가 따르는 기본값
  막힘 여부      답이 없으면 작업이 멈추는가
  가정 만료점    이 지점을 넘기면 답이 바뀌었을 때 되돌리는 비용이 커짐
  전달 방식      즉시 / 협상 / 중재 / 예약
  상태           대기 → 전달됨 → 답함 | 가정 확정 | 만료
```

  - 상태 기계 초안: `대기 → 전달됨 → (답함 | 가정 확정 | 만료)`. 정확한 전이 조건은 대화에 없다.
- 5-11. 핵심은 가정 만료점이다. L3803 [Claude]
  - 협상이나 예약으로 둔 질문이 답 없이 만료점에 가까워지면 즉시로 올라간다. "지금 묻는 가치"가 고정 판정이 아니라 시간에 따라 커지는 값이 된다.
  - 만료점까지 답이 없으면 임시 가정을 확정하고, 혼자 정한 결정으로 기록해 나중에 이의를 걸 수 있게 둔다.
  - [브리프 결정 12 "질문 레코드와 가정 만료점"과 같음]

## 6. 취향형 작업의 기원과 "2~3개 고르기" 거부, 원함 탐구

### 6.1 사용자 진술 (L3741 [사용자], 원문)

> 너가 잘 말해준 것 중 하나가 나는 helm의 첫 스타트 포인트가 취향이 정답인 작업에 대해 발산론적 방법을 기반으로 사용자가 실제로 텍스트로 표현하는 요구와 실제 사용자가 가지고 있는 요구가 자기도 모르는 상태로 다르게 표현될 수 있다는 걸 가정하고, 레퍼런스나 여러 자료를 바탕으로 자극이 입력되고 여러개를 비교해보고 나서야 비로소 아 내가 이걸 원하는 걸 알 수 있네? 라는 과정을 위한 에이전트 방법론으로 생각하긴 했어. 그렇다고 현재의 방향성이 잘못됐다는게 아니라, 발산의 동기가 이거고, 어 이런식으로 하면 생각지도 못한 전혀 다른 분야에서 내 분야와 문제에 대한 사고방식 응용이나 접근이 가능하네? 적용해서 문제해결할 수 있을 것 같아! 도 되고 여튼 내 생각을 두서없이 표현해봄. 비판 4도 같은 맥락인데 이걸 단순히 비교 가능한 대안을 겨우 2~3개 던져주고 선택하라는거 자체가 말이안되는거같음. 애초에 이럴거면 그냥 llm 쓰지.

- 6-1. Helm의 출발점: 취향이 정답인 작업. 글로 표현한 요구와 실제 요구가 본인도 모르게 다를 수 있다. 레퍼런스와 자료로 자극을 받고 여러 개를 비교한 뒤에야 원하는 것을 안다. 발산은 이 동기를 위한 방법이다. 현재 방향이 틀렸다는 뜻은 아니다. L3741 [사용자] [브리프 결정 1의 출처]
- 6-2. 발산의 다른 효과: 생각지도 못한 다른 분야의 사고방식을 내 문제에 응용하는 것(Method Transfer와 연결). L3741 [사용자]
- 6-3. "2~3개 던져주고 선택하라는 것"은 말이 안 된다. "애초에 이럴거면 그냥 llm 쓰지." L3741 [사용자] [브리프 결정 18의 출처]

### 6.2 Claude의 정리와 뒷받침 연구

- 6-4. 동기 정리. L3819 [Claude]
- 6-5. 뒷받침 연구. L3821–3823 [Claude] [확인 수준: 기존 지식, L3916]
  - 행동경제학의 선호 구성(constructed preference, Lichtenstein & Slovic 등): 선호는 미리 있다가 꺼내지는 것이 아니라 선택지를 마주하는 순간에 만들어진다.
  - Dow 등(2010): 시안을 하나씩 순서대로 만들 때보다 여러 개를 동시에 만들어 비교할 때 결과가 더 좋았다.
  - Tohidi 등(2006): 시안 하나만 보여주면 칭찬 위주로 반응하고, 여러 개를 보여줘야 비판적 의견이 나온다.

### 6.3 "2~3개 고르기" 거부와 Helm이 해야 하는 것

- 6-6. [정정] 동의. 대안 2~3개를 주고 고르게 하는 것은 LLM 하나로도 할 수 있다. Helm이 달라야 하는 부분은 개수가 아니라 구조다. L3827 [Claude] ([123] 비판 4 보강안(4-19)을 철회)
- 6-7. 일반 LLM과 Helm의 차이. L3829–3835 [Claude]

| 단계 | 일반 LLM | Helm이 해야 하는 것 |
|---|---|---|
| 자극의 폭 | 같은 분야 안의 변형 | 다른 분야 레퍼런스까지 (방법 전이와 연결) |
| 반응의 단위 | 하나 고르기 | 요소 단위 반응 ("이 부분은 좋고 저 부분은 아님"), 이유를 못 대는 반응도 받음 |
| 기준 찾기 | 없음 | 반응에서 숨은 기준을 찾아냄 |
| 다음 자극 | 다시 평균값 근처 | 가장 불확실한 기준을 확인할 수 있는 자극을 고름 |
| 결과물 | 고른 하나 | 선호 모델: 기준, 무게, 좋았던 예와 싫었던 예 |

- 6-8. 기준 찾기 방법 둘. L3837–3840 [Claude]
  - 레퍼토리 그리드(Kelly): 세 가지를 보여주고 "둘은 비슷하고 하나는 다른데, 무엇 때문인가"를 묻는다. 말로 못 하던 기준이 나온다.
  - 비평 기반 추천(critiquing recommender): 사용자가 "이것과 비슷한데 더 단순하게"처럼 예시를 고쳐 말하는 방식으로 선호를 드러낸다.
  - 주의(발췌자 메모): 레퍼토리 그리드는 세 개를 보여주지만 "고르기"가 아니라 "차이의 이유"를 묻는 것이다. 브리프 결정 18은 "고르게 하는 상호작용"을 거부한 것이므로 이 방식과 충돌하지 않는다.
- 6-9. 선호 모델(결과물)은 N 칸(Goal, 완료 기준)에 들어간다. 다음 Concern에서 다시 쓰이고 계속 다듬어진다. 사용자가 말한 "Concern 사이클을 거치며 진화하는 Goal"이 실제로 만들어지는 과정이 이것이다. L3842 [Claude] (브리프 용어집 "선호 모델": 원함 탐구에서 쌓이는 기준 후보와 반응 기록)

### 6.4 사실 탐구(E)와 원함 탐구(N)

- 6-10. 지금까지의 I 루프는 E를 위한 탐구(무엇이 사실인가)였다. 사용자의 동기는 N을 위한 탐구(무엇을 원하는가)다. 둘은 생김새가 같다. L3846–3853 [Claude]

| | 사실 탐구 (E) | 원함 탐구 (N) |
|---|---|---|
| 가설 | 원인 후보 | 선호 후보 ("단순함을 원하는 것 같다") |
| 구분 확인 | 결과가 원인에 따라 달라지는 관찰 | 반응이 선호에 따라 달라지는 자극 |
| 근거 | 도구 실행 결과 | 사용자의 반응 |
| 결과 | 판단 | 선호 모델, 완료 기준 |

  - 구분 확인(discriminating check)이 원함 탐구에도 쓰인다: "반응이 선호에 따라 달라지는 자극"을 고른다(6-7의 "다음 자극"과 같은 원리).
- 6-11. I 루프를 두 종류(사실 탐구, 원함 탐구)로 나누자고 제안. 사용자의 "루프 종류가 범용 작업을 덮기에 너무 적다"는 지적에 대한 답 중 하나. L3855 [Claude] [사용자 동의 L3921] ([127]에서 네 종류로 확장, 10장)
- 6-12. 원함 탐구 기록 원칙: 모델이 초안·자극을 내고 사람은 반응한다. 브리프 결정 18의 "모델이 초안을 쓰고 사람은 반응·수정한다(recognition over recall)"는 이 구간보다 앞(발췌 1 범위, 옛 저장소 분석)에서 나온 표현이다. 이 구간에서는 "요소 단위 반응, 이유를 못 대는 반응도 받음"(L3832)이 그 구체화다.

## 7. Cynefin

### 7.1 [123]의 첫 소개 (네 상황)

- 7-1. Cynefin은 상황을 넷으로 나누고 상황마다 순서가 다르다고 본다. 명확: 감지 → 분류 → 대응 / 복잡: 감지 → 분석 → 대응 / 복합: 탐침 → 감지 → 대응(먼저 작게 해 봄) / 혼돈: 행동 → 감지 → 대응. L3617–3624 [Claude]
- 7-2. 사용자: "cynefin 상황 4가지는 조금 더 설명해줘". L3743 [사용자]

### 7.2 [125]의 상세 설명 (다섯 상황)

- 7-3. Snowden의 틀. 원인과 결과의 관계에 따라 상황을 나누고, 상황 종류마다 맞는 대응 순서가 다르다. Snowden & Boone(2007)과 이후 Snowden의 설명을 기억으로 정리했다. L3859 [Claude] [확인 수준: 기존 지식]
- 7-4. 표. L3861–3866 [Claude]

| 상황 | 원인과 결과 | 대응 순서 | 쓰는 방법 | 빠지기 쉬운 함정 | 예 |
|---|---|---|---|---|---|
| 명확 (Clear) | 누구나 보면 앎 | 감지 → 분류 → 대응 | 정해진 모범 사례 | 익숙해서 방심하다가 갑자기 혼돈으로 떨어짐 | 린트 오류 수정, 회의록 서식 맞추기 |
| 복잡 (Complicated) | 있지만 분석이나 전문가가 필요함 | 감지 → 분석 → 대응 | 여러 좋은 방법 중 전문가가 고름 | 분석 마비, 전문가가 자기 방식만 고집 | 성능 버그 원인 찾기, 세금 계산 |
| 복합 (Complex) | 지나고 나서야 보임 | 탐침 → 감지 → 대응 | 작게, 실패해도 괜찮은 실험을 여러 개 동시에 하고 잘되는 쪽을 키움 | 미리 분석해서 정답을 찾으려 함 | 제품 방향, 글의 톤, 팀에 새 도구 도입 |
| 혼돈 (Chaotic) | 찾을 시간이 없음 | 행동 → 감지 → 대응 | 우선 안정시키고 나서 봄 | 상황이 안정됐는데도 계속 비상 대응을 함 | 프로덕션 장애 (먼저 롤백) |

- 7-5. 다섯 번째 혼란(Disorder): 지금이 어느 상황인지 모르는 상태. 사람은 자기에게 익숙한 방식으로 대응하는 경향이 있다(예: 분석에 익숙한 개발자는 복합 상황도 분석으로 풀려고 함). L3868 [Claude]
- 7-6. Helm과의 연결. L3870–3872 [Claude]
  - OICA의 기본 순서(O → I → C → A)는 복잡 상황에 맞춰져 있다.
  - 취향형 작업은 대표적인 복합 상황이다. 원하는 것은 미리 분석해서 찾을 수 없고 자극을 던져 보고 반응을 봐야 나온다. 여러 자극을 동시에 보여주는 것이 Cynefin의 "실패해도 괜찮은 탐침 여러 개"와 같다. 원함 탐구는 Cynefin 관점에서도 맞는 방법이다.
- 7-7. 상황 유형은 바뀐다(혼돈 → 복합 → 복잡 → 명확). 상황 유형은 Concern에 한 번 붙이고 끝나는 값이 아니라 재진입 규칙을 가진 상태여야 한다. L3989–3990 [Claude]. 사용자: "상황유형이 바뀌는것에 대해 매우 동의". L4020 [사용자 동의] [브리프 결정 6과 같음. HANDOFF §2.2-3 (d) Cynefin 도입 결정]
- 7-8. 상황별 기본 조합과 점검은 9장에서 다룬다.

## 8. 외부 응답과 기대 레코드

- 8-1. 사용자 제안: "비판 5. 사람과 에이전트 둘만 있다고 가정한다. -> 외부 응답을 inquiry 과정에서 발견된 새로운 사실 중 하나 정도의 개념으로 하면 문제가 되려나?" L3745 [사용자]
- 8-2. 대부분 문제없다. 외부 응답은 출처가 외부 행위자인 관찰로 기록한다. 보완 둘. L3876 [Claude] [브리프 결정 9와 같음]
- 8-3. 보완 1: 응답이 없는 것은 관찰되지 않는다. 메일을 보냈는데 답이 오지 않으면 기록에 아무것도 남지 않는다. 그래서 요청을 보낼 때 "기대" 레코드를 남긴다. 필드: 누구에게, 무엇을, 언제까지 받을 것으로 기대하는지. 기한이 지나면 타이머가 "응답 없음" 관찰을 만든다. 응답이 오지 않은 것도 관찰이 되어 "외부 응답 = 관찰"이 그대로 성립한다. L3878–3879 [Claude] (브리프 용어집 "기대 레코드", ID 접두사 `ex`. HANDOFF §2.2-3 (e) "기대 레코드 제안")
- 8-4. 보완 2: 외부에서 온 말은 내용이 아니라 "그렇게 말했다"는 것이 관찰이다. 고객이 "다음 주까지 됩니다"라고 했다면 관찰은 "고객이 다음 주까지 된다고 말했다"이고 "다음 주까지 된다"는 아직 추측이다. L3881–3882 [Claude]
- 8-5. 이 두 가지만 있으면 별도 루프는 필요 없다. 외부 행위자와의 조정은 기대 레코드 + 응답 없음 관찰로 처리하므로 별도 루프로 만들지 않는다. L3884, L3909 [Claude] [사용자 동의 L3921] [정정: [123] 비판 5 보강안 "대기를 정식 상태로"(4-20)를 대체]
- 8-6. 설계 함의(발췌자 메모): 기대 레코드는 타이머(스케줄러)를 필요로 한다. 행위자 표기 `external:<name>`(브리프 §3.3)과 연결된다.

### 9.2 [125]의 조합 구조

### 9.3 [127]의 상황별 점검

- 9-8. 충분하지 않다. 명확과 복잡은 거의 충분하고 나머지 셋에는 OICA에 없는 것이 필요하다. L3966 [Claude]
- 9-9. 명확: O → C → A로 거의 충분. 빠진 것: Cynefin에서 명확 상황의 위험은 방심이다. A의 자동 검증에서 예상과 다른 결과가 나오면 상황을 다시 판정하게 해야 한다. L3970–3971 [Claude]
- 9-10. 복잡: O → 사실 탐구 → C → A로 충분. 선택에 부작용이 걸려 있으면 결과 탐구를 넣는다. L3973–3974 [Claude]
- 9-11. 복합: 부족. 없는 것 둘. L3976–3978 [Claude]
  - 탐침으로서의 C: Snowden은 복합 상황에서 실패해도 괜찮은 실험을 여러 개 동시에 하고, 시작 전에 키울 조건과 접을 조건을 정해 두라고 한다. 지금의 C는 "결정한 것을 실행하는 약속" 하나뿐이다. 결과를 모르는 상태에서 여러 개를 시도하는 C가 따로 필요하다.
  - 지속 관찰로서의 A: 복합 상황에는 미리 정한 완료 기준이 없다. 받아들이거나 거절하는 A가 아니라 내보낸 뒤에도 계속 보면서 잘되는 쪽을 키우고 안 되는 쪽을 접는 A가 필요하다.
- 9-12. 혼돈: 부족. 의존 규칙과 충돌한다. "write를 하려면 C가 필요하다"인데 혼돈에는 합의할 시간이 없다. 그래서 미리 맺어 둔 합의(비상 합의)가 필요하다. 예: 프로덕션 장애가 나면 롤백까지는 묻지 않고 해도 된다. 안정된 뒤에는 바로 끝나지 않고 복합이나 복잡으로 넘어가며, A는 사후 검토(Reflect)가 큰 비중. L3980–3981 [Claude]
- 9-13. 혼란: 부족. 지금의 O에는 상황 유형 판단 단계가 없다. 필요한 것 둘. L3983–3985 [Claude]
  - 상황 판정: 모델이 근거와 함께 유형을 제안하고 기록한다. 판정도 혼자 정한 결정으로 다루므로 이의를 걸 수 있다. 사람이든 모델이든 익숙한 방식으로 기우는 경향이 있으니 판정 근거를 남기는 것이 중요하다. (브리프 ID: 상황 판정 `sa`)
  - 분해: Snowden은 혼란 상황에서 문제를 쪼개 부분마다 다른 유형에 배정하라고 한다. Concern 하나를 유형이 다른 하위 Concern 여러 개로 나누는 단계가 필요하다. (→ [128]~[142]에서 S 루프로 발전, 11장)
- 9-14. 모든 상황에 걸쳐 빠진 것 둘. L3987–3993 [Claude]
  - 상황 유형은 바뀐다(7-7).
  - 돌아보기(Reflect)가 다음 명확 상황을 만든다. 복잡 상황을 여러 번 풀면 정해진 절차가 생기고 그 일은 명확 상황이 된다. 대화 초반의 관찰 에이전트 C가 여기에 들어간다. 세션 로그에서 반복 패턴을 찾아 스크립트나 스킬로 만드는 일이 Cynefin으로 보면 복잡을 명확으로 옮기는 일이다. (브리프 §3.5 관찰 에이전트 → P10(16))
- 9-15. 고친 기본 조합(2차안). L3997–4004 [Claude]

| 상황 | 기본 조합 | 새로 필요한 것 |
|---|---|---|
| 명확 | O → C → A(자동 검증) | 예상 밖 결과가 나오면 상황 재판정 |
| 복잡 | O → 사실 탐구 → (결과 탐구) → C → A | 없음 |
| 복합 | O → 원함·가능성 탐구 ⇄ 탐침 C 여러 개 → 지속 관찰 A → 키우기·접기 | 탐침 C, 지속 관찰 A |
| 혼돈 | 비상 합의로 C(안정화) → O → 복합이나 복잡으로 재판정 → Reflect | 미리 맺어 둔 합의 |
| 혼란 | O(상황 판정 + 분해) → 하위 Concern마다 위 조합 | 상황 판정 단계, Concern 분해 |
| 모든 상황 | 상황 유형은 바뀔 수 있는 상태, Reflect는 반복을 명확 절차로 만듦 | 재판정 규칙, Reflect → P와 스킬 |

- 9-16. 정리: OICA 네 루프는 그대로 두고 변형 세 가지와 단계 두 가지를 더한다. L4006–4011 [Claude]
  - C의 변형: 약속형 C와 탐침형 C
  - A의 변형: 확인형 A와 지속 관찰형 A
  - 미리 맺어 두는 비상 합의
  - O의 단계: 상황 판정
  - O의 단계: Concern 분해 ([128]~[142]에서 S 루프로 옮김)
  - 브리프 용어집 루프 식별자: I.fact, I.want, I.possibility, I.outcome, C.commit, C.probe, C.emergency, A.confirm, A.watch, A.reflect, S.*. 이 변형들이 식별자의 출처다.
- 9-17. Cynefin 세부(구분 조건, 키울 조건과 접을 조건), 사전 부검, 형태 분석, TRIZ는 기존 지식으로 정리했다. L4013 [Claude] [확인 수준: 기존 지식]

### 9.4 [128]의 사용자 요구와 [142]의 반영

## 10. 탐구 종류 추가: 가능성 탐구와 결과 탐구 ([126]~[127])

- 10-1. 사용자 질문: "사실탐구, 원함 탐구 외에 또다른 탐구 방법론에 대한 디벨롭이 필요할까?" L3921 [사용자]
- 10-2. 나누는 기준: 탐구 종류를 따로 두려면 "무엇을 근거로 삼는가"와 "언제 멈추는가"가 달라야 한다. 둘이 같으면 같은 탐구의 변형이고, 다르면 다른 방법론이 필요하다. 사실 탐구와 원함 탐구는 근거(관찰 vs 반응)와 멈춤 조건("1순위 원인이 안정됨" vs "선호 모델이 안정됨")이 다르다. 무엇을 추가할지는 기준을 정해 놓고 골라야 늘어나기만 하지 않는다. L3924, L3928–3930 [Claude]
- 10-3. 탐구 네 종류 표. L3934–3939 [Claude]

| 탐구 | 묻는 것 | 근거 | 멈추는 조건 | 참고할 방법 |
|---|---|---|---|---|
| 사실 탐구 | 무엇이 그런가 | 관찰 | 1순위 원인이 두 라운드 연속 유지됨 | 경쟁 가설 분석, 구분 확인 |
| 원함 탐구 | 무엇을 원하는가 | 사용자의 반응 | 선호 모델의 기준과 무게가 더 바뀌지 않음 | 레퍼토리 그리드, 비평 기반 추천 |
| 가능성 탐구 | 무엇이 될 수 있는가 | 다른 분야 사례, 작은 실현 가능성 확인 | 발산 표의 빈 칸이 닫히고, 실현 가능한 후보가 하나 이상 있음 | 방법 전이, 형태 분석(Zwicky box), TRIZ |
| 결과 탐구 | 하면 무엇이 일어나는가 | 시뮬레이션, 비슷한 사례, 사전 부검 | 주요 실패 경로마다 대응이나 감시 조건이 붙음 | 사전 부검(Klein), 시나리오 계획, STPA |

  - [브리프 결정 7과 같음]
- 10-4. 가능성 탐구를 따로 두는 이유: 사실 탐구는 이미 있는 것을 찾고 가능성 탐구는 아직 없는 것을 만든다. 관찰할 대상이 아직 없으니 다른 분야 사례와 작은 시도가 근거가 된다. 사용자의 "생각지도 못한 다른 분야의 사고방식을 내 문제에 적용하기"가 이 탐구의 중심 방법이다. 지금까지는 사실 탐구의 발산 단계에 섞여 있었다. L3941 [Claude] (Method Transfer의 위치, 브리프 결정 13)
- 10-5. 결과 탐구를 따로 두는 이유: 미래는 지금 관찰할 수 없어 근거가 예측이고, 예측은 나중에 실제 결과로 확인해야 한다. 산출물은 판단이 아니라 "이런 일이 일어날 것이다, 이 날짜에 확인한다"는 예측 레코드다. 이 레코드가 다시 볼 조건이 되고 OPD+C의 Predictability와 연결된다. Klein의 사전 부검은 "이 일이 실패했다고 가정하고 왜 실패했는지 써 보라"는 방식이며 낙관 편향을 줄이는 데 효과가 있다고 알려져 있다. L3943 [Claude] (브리프 ID: 예측 `pr`. 예측 레코드는 확인 날짜 = 타이머를 가진다)
- 10-6. 따로 두지 않아도 되는 것. L3945–3948 [Claude]
  - 관점 탐구("이건 어떤 종류의 문제인가"): 모든 탐구의 앞에 오는 일이라 O의 Frame 단계에 둔다. 상황 판정이 여기에 해당한다.
  - 정당성 탐구("해도 되는가, 누가 영향을 받는가"): 범용 작업에서는 필요하지만 권리와 위험 판별을 권한 레이어로 넘기기로 했다. 사용자 본인의 가치 판단이라면 원함 탐구로 처리된다.
- 10-7. 네 탐구도 루프처럼 조합해서 쓴다. L3950–3962 [Claude]
  - 취향형 작업: `원함 탐구 → 가능성 탐구 → 결과 탐구 → 선택`
  - 성능 문제: `사실 탐구 → 가능성 탐구 → 결과 탐구 → 선택`
- 10-8. 사용자: "추가 탐구들은 좋음". L4020 [사용자 동의]

- 11-1. 사용자 제안: "또 하나 concern을 여러개로 나누는 것 조차 하나의 루프로 보고 다른 상황이나 루프 상황에서도 판단에 따라 수행가능하도록 하는 방안은 어떤지도 묻고싶음". L4020 [사용자]

- 11-4. 나눌 때의 규칙. L4081–4084 [Claude]
  - 하위 Concern도 상위와 Goal에 연결된 상태를 유지한다.

  - 나눈 부분 사이에 걸치는 것을 경계 항목으로 기록한다.
  - 하위 Concern의 개수와 깊이에 상한을 둔다. (숫자는 대화에 없음)
- 11-5. v0.2에서 "거시 루프"라고 부르던 것도 S 루프를 Goal 수준에서 돌리는 것으로 정리된다. L4086 [Claude]

## 14. pi-durable과 pi coding agent의 관계 정정 ([149]~[150])

- 14-1. 사용자 질문: "pi durable이랑 pi coding agent중 하나밖에 못쓰는게 사실임? 사실이라면 뭐가 더 나음? pi ai랑 pi coding agent는 다른역할임?" L4165 [사용자]
- 14-2. [정정] "둘 중 하나만 쓸 수 있다"는 정확한 표현이 아니다. 정확히는 "대화 하나를 돌리는 루프는 둘 중 하나여야 한다". 지난 답의 "주 경로에 둘 다 넣으면 런타임이 둘이 된다"도 이 뜻이었다. L4168 [Claude]
- 14-3. pi 패키지의 층(설치된 패키지의 의존성 목록 기준). L4172–4179 [Claude] [확인 수준: 설치된 의존성 확인]

```text
pi coding agent (완성된 앱: CLI/TUI, 확장 API)     pi-durable (하네스 라이브러리)
  └─ pi-agent-core (에이전트 루프)                   └─ 자체 루프 + 저장소 + task
        └─ pi-ai ─────────────────────────────────────────┘
           (모델 공급자 연결)
```

- 14-4. 각 패키지. L4181–4185 [Claude]
  - pi-ai: 모델을 부르는 라이브러리. OpenAI, Anthropic 등 여러 공급자를 같은 형식으로 호출하고 스트리밍과 도구 호출 형식을 맞춘다. 루프는 없다. 테스트에 쓴 faux 공급자도 여기에 있다.
  - pi coding agent: pi-ai와 pi-agent-core 위에 만든 완성된 앱. 터미널 UI, 기본 도구, 세션, 확장 API.
  - pi-durable: pi-ai 위에 만든 또 다른 하네스 라이브러리. pi-agent-core를 쓰지 않고 자기 루프를 가진다(설치된 의존성에 pi-agent-core가 없음).
  - pi-ai는 부품, pi coding agent는 그 부품으로 만든 완성품. pi coding agent와 pi-durable은 같은 부품(pi-ai)을 쓰는 두 개의 다른 루프.
- 14-5. 한 대화 안에서 두 루프를 섞을 수 없다(세션 저장 방식도 확장 API도 다르다). 역할을 나누면 같이 쓸 수 있다. L4189–4195 [Claude]

|---|---|---|

## 17. 프로세스 배치 A/B/C ([156]~[157])

- 17-1. 사용자: "현재구조상 별도 헬름서버가 켜지는걸로 보이는데 여기 안에 pi 런타임이 들어가는건가? 아키텍쳐 및 기획 고도화작업이 선행되어야할듯함". L4347 [사용자]
- 17-2. 14번 구조에서는 pi가 Helm 서버 안에서 돈다. pi coding agent를 터미널 앱으로 실행하는 것이 아니라 SDK(`createAgentSession`)로 불러 쓰는 라이브러리로 쓴다. 사용자가 켜는 것은 Helm 서버 하나와 브라우저이고, Concern이나 WorkUnit이 생길 때마다 서버가 그 안에서 pi 세션을 만든다. 그래서 v0.3 14 §3.4에 적은 대로 이 배치에서는 평소 쓰는 pi 터미널 UI로 Helm 세션을 열 수 없다. L4350 [Claude]
- 17-3. 이 부분은 구현보다 먼저 정할 기획 문제다. 프로세스 배치에 따라 사용 경험이 크게 달라지는데 지금까지는 기술 검토를 먼저 하느라 이 결정을 건너뛰었다. L4352 [Claude] [사용자 진술 L4347에 동의]
- 17-4. 배치 세 가지. L4356–4371 [Claude]

```text
A. Helm 서버가 pi를 품는다 (14번 구조)
[브라우저] ⇄ [Helm 서버: 커널 · 저장소 · 스케줄러 · pi 세션들(SDK)]

B. pi가 Helm을 품는다
[pi 터미널 + Helm 확장: 커널 · 저장소] ⇄ (확장이 여는 로컬 화면)

C. Helm 데몬이 상태를 맡고, 런타임은 붙었다 떨어지는 실행기
[pi 터미널 + Helm 어댑터 확장] ─┐
[Claude Code + Helm 훅 어댑터] ─┼→ [Helm 데몬: 커널 · 저장소 · 스케줄러] ⇄ [브라우저]
[데몬이 직접 띄운 pi (SDK/RPC)] ─┘
```

- 17-5. 비교표. L4373–4380 [Claude]

| 기준 | A | B | C |
|---|---|---|---|
| 사용자가 실행하는 것 | Helm 서버, 브라우저 | pi 터미널 | Helm 데몬(상시), 평소처럼 pi 터미널, 필요할 때 브라우저 |
| 평소 쓰던 pi 터미널 | Helm 작업에는 못 씀 | 그대로 씀 | 그대로 씀 |
| 터미널을 닫아도 계속 실행 | 됨 | 안 됨 (pi를 닫으면 Helm도 멈춤) | 됨 (데몬이 헤드리스 pi를 띄움) |
| 다른 런타임 연결 | 세션 호스트를 새로 만들어야 함 | 어려움 | 어댑터만 추가 |
| 처음 목표(벤더 중립)와의 거리 | 중간 | 멂 | 가장 가까움 |
| 복잡도 | 중간 | 낮음 | 높음 (데몬과 어댑터 사이 통신, 데몬이 꺼졌을 때의 처리) |

- 17-6. Claude 판단: C가 원래 목표에 가장 가깝다. pi 터미널을 계속 쓰면서 Helm이 뒤에서 상태를 관리하고, 나중에 Claude Code나 Codex도 같은 데몬에 붙일 수 있다. L4382 [Claude]
- 17-7. C의 대가: 도구를 호출할 때마다 확장이 데몬에 차단 여부를 물어야 한다. 데몬이 꺼져 있으면 어떻게 할지(변경 도구를 막을지, 기록만 쌓아 두고 나중에 보낼지)를 정해야 한다. L4382 [Claude] [미결]
- 17-8. [이후 변경: 브리프 결정 22·23·34 / HANDOFF §2.2-5·7·8] 최종 구조는 상주 데몬(진행 중 작업은 클라이언트 없이 계속) + 데몬 안의 자체 런타임(pi 패키지 포크) + 데스크톱 앱 클라이언트. A(서버가 런타임을 품음)에 가깝고, C의 벤더 중립 요소는 "런타임 어댑터 인터페이스를 지금 정의, 1차 구현은 자체 런타임 하나, Claude Code·Codex·pi CLI(RPC)·ACP 어댑터는 이후 단계"로 남았다. 감사(HANDOFF §2.2-2)에서 "프로세스 배치 A/B/C"가 빠진 덩어리로 지적됐다. 브리프 §3.4에서 P3(06)가 프로세스 배치를 맡는다. 17-7의 "데몬이 꺼졌을 때 외부 어댑터의 처리"는 어댑터 설계(13)의 미결 사항이다.

## 18. 선행 기획·아키텍처 작업 7항목, ADR 형식, 세 질문 ([157])

- 18-1. 순서: 기획은 사용 장면부터 정하고, 거기서 아키텍처 결정을 끌어낸다. L4386 [Claude]
- 18-2. 7항목. L4388–4394 [Claude]
  1. 사용 장면 4~5개: 아침에 돌아와 상황 파악, 작업 중 질문 받기, 취향 탐구, 자리를 비운 동안 계속 돌아가는 작업, 다른 런타임에서 이어 하기. 장면마다 어떤 화면과 어떤 프로세스가 필요한지 정리한다.
  2. 진입점 결정: 터미널인지, 웹인지, 둘 다인지
  3. 프로세스 배치 결정: A, B, C 중 무엇인지
  4. 저장소 소유와 기록 경계: 누가 정본을 쓰고 런타임 쪽 기록은 어떻게 다룰지
  5. 런타임 어댑터 계약: pi, Claude Code, Codex에 공통으로 요구할 것
  6. MVP 범위: 어느 루프와 어느 화면부터 만들지
  7. 비기능 요구: 재시작, 데몬이 꺼졌을 때, 로컬 전용 보안
  - [이후 변경] "사용 장면"은 [158]에서 "유즈케이스" 또는 "시나리오"로 바뀌었다(브리프 결정 25). 2번은 데스크톱 앱 먼저, 이후 SSH TUI(결정 19·33). 3번은 상주 데몬 + 자체 런타임(결정 22·23). 4번은 Helm 이벤트 로그가 기준 원본(결정 29). 5번은 어댑터 인터페이스를 지금 설계(결정 34). 7번의 "로컬 전용 보안"은 외부 접속 요구(결정 21)로 바뀌어 Tailscale 기반 원격 접속(결정 26)이 됐다. 브리프 §3.5는 이 7항목을 "기획 선행 작업(유즈케이스, 진입점, 배치, 저장소 경계, 어댑터 계약, MVP, 비기능 요구)"으로 P1·P3에 배정했다.
- 18-3. ADR 형식: 각 결정은 결정 기록(ADR) 형식으로 남기고, 사용 장면과 MVP는 기획 문서 하나로 묶는다. L4396 [Claude] (브리프 §3.4 문서 24 `24-adr.md`, 문서 01·02)
- 18-4. 사용자에게 물은 세 질문(답에 따라 배치와 MVP가 정해짐). L4398–4404 [Claude]
  1. 평소 진입점: pi 터미널은 그대로 쓰고 Helm 화면을 옆에 띄우는 쪽인가, Helm 웹 화면 안에서 대화까지 하는 쪽인가
  2. 사람이 없을 때의 실행: 터미널과 브라우저를 모두 닫아도 Helm이 계속 돌아야 하나(밤새 탐구, 타이머가 다시 볼 조건을 확인하는 경우)
  3. 다른 런타임 연결 시기: Claude Code나 Codex를 가까운 시일 안에 붙일 계획이 있나, 당분간 pi만으로 충분한가
  - 답의 처리: 1번은 [158]에서 답함(19-1). 2번은 [158]에 없고 이후 "진행 중인 작업은 클라이언트가 없어도 계속한다"로 정해졌다(HANDOFF §2.2-3, 브리프 결정 22). 3번은 대화와 HANDOFF에 사용자 답이 없다. 브리프 결정 34(어댑터 인터페이스는 지금, 1차 구현은 자체 런타임 하나)는 조정자가 정한 기본값이다.
- 18-5. 답을 받으면 사용 장면 문서와 배치·저장소·어댑터 결정 기록부터 작성하겠다고 했다. L4406 [Claude]
