# Helm v0.3 개정 메모

> 상태: 개정 후보 (candidate)
> 작성일: 2026-10-11
> 기준 문서: `docs/foundations/` (v0.1), `docs/foundations/10-refinement-candidate.md` (v0.2), `docs/architecture/helm-kernel-v0.2-candidate.md`
> 방식: 기존 문서를 수정하지 않는다. 이 폴더의 문서가 v0.2에서 무엇을 바꾸고, 무엇을 더하고, 무엇을 뺐는지 기록한다.

## 1. 이 개정이 필요한 이유

v0.2까지의 Helm은 코드 작업을 대표 유즈케이스로 삼아 다듬어졌다. v0.3 논의에서 다음 네 가지를 확인했다.

1. **출발 동기가 문서에 제대로 적혀 있지 않았다.** Helm의 원래 출발점은 "사용자가 글로 표현한 요구와 실제로 가진 요구가 다를 수 있고, 자극을 비교해 본 뒤에야 원하는 것을 알게 된다"는 가정이었다. v0.2 문서는 이 동기보다 위임·확인·통합 쪽을 더 자세히 다뤘다.
2. **범용 에이전트 작업에 적용하기에 루프와 탐구의 종류가 부족했다.** 탐구는 사실을 찾는 방식 하나뿐이었고, 루프는 고정 순서처럼 읽혔다.
3. **선택 요청 기준이 질적이고 애매했다.** 세 조건을 판정하는 방법과 "언제, 어떻게 묻는가"가 정해져 있지 않았다.
4. **일부 개념의 정의와 이름이 맞지 않았다.** Goal, Concern의 정의를 다시 세웠다. v0.2 문서는 "Projection"을 두 가지 뜻으로 썼다. 하나는 정본 기록을 읽어 만든 selector 같은 화면(ContextProjection)이고, 다른 하나는 Endsley식 상황 인식에서 앞으로의 상태를 예측하는 단계다. 또 v0.3 논의에서 제품 소유자는 다른 분야의 방법과 사고방식을 지금 문제에 적용하는 개념을 "Projection(투영)"이라고 불렀다. 이 개념은 Helm 자료에 Method Transfer라는 이름으로 이미 있었으므로 그 이름을 쓴다([02 §10](02-core-concepts.md)).

### 2.2 다시 정의한 것

| 개념 | v0.2 | v0.3 |
|---|---|---|
| Goal | versioned normative entity (C7에서 방향만 제시) | 프로젝트 단위의 궁극 목표. 고정되지 않고 Concern 사이클을 거치며 계속 정제되는 기반 |
| Concern | 사람과 agent의 주의와 판단이 필요한 중요한 상황 | 10단계 과정을 돌릴 후보가 되는 상황 그 자체 (문제, 기회, 위험, 불확실성, 취향 결정 등) |
| A 평면 | observe, propose, decide within scope 등 7개 능력 | 원시 행동 층과 기록 능력 층으로 분리 |
| 선택 요청 | 세 조건이 모두 참일 때 Gate 생성 | 권리 게이트 + 정보 게이트 + 전달 방식 |
| I 루프 | 사실(E)을 위한 탐구 | 네 종류의 탐구 (E를 위한 것 둘, N을 위한 것 하나, 아직 없는 것을 위한 것 하나) |
| 루프 순서 | 순차 pipeline이 아니라고 적었지만 10단계 사이클이 순서로 읽힘 | 순서는 상황 유형별 기본값일 뿐이며 언제든 전환 가능 |

### 2.3 범위에서 뺀 것

| 항목 | 이유 | 넘어간 곳 |
|---|---|---|
| Effect class (R0~R4) | 제품 소유자가 든 이유: 최근 모델은 되돌리기 어려운지를 스스로 판별할 수 있고, 이것은 Helm 연구가 다룰 문제가 아니라 에이전트 권한 설계의 문제다. Claude가 덧붙인 근거: 되돌리기 어려운지는 상황에 따라 달라진다 ([01 §4.1](01-scope-and-motivation.md)) | 에이전트 권한 레이어 |
| 행동의 위험·가역성 판별 | 위와 같음 | 에이전트 권한 레이어 |
| 권리 게이트의 대상 판별 일부 | 돈, 외부 발송, 대리 발언 같은 대상 분류는 권한 레이어가 한다. Helm은 그 결과를 받아 선택 요청을 연다 | 권한 레이어 (판별) / Helm (요청과 기록) |

### 2.4 유지한 것 (문구 일부 조정)

v0.2의 불변조건은 v0.3에서도 어느 모드, 어느 다이얼 값에서도 바뀌지 않는다. 2번은 v0.2의 "관찰, 해석, 가능성, 판단, 선택"을 "추측"이라는 묶음 이름으로 줄여 적었으며, 레코드 종류로는 해석과 가능성을 계속 구분한다([02 §2](02-core-concepts.md)).

1. 기록과 진실은 다르다.
2. 관찰, 추측(해석과 가능성), 판단, 선택은 다르다.
3. 투영은 정본을 쓰지 않는다.
4. 권한은 범위를 가진다. (v0.2의 "effect class를 가진다"는 권한 레이어로 넘어감)
5. 완료 주장, 결과 확인, 전체 반영은 다르다.
6. 모르는 것, 이견, 낡은 상태는 숨기지 않는다.

v0.3에서 하나를 더한다.

7. **에이전트가 혼자 정한 결정도 기록되며, 사람은 언제든 이의를 걸 수 있다.**

## 4. 표기 규칙

- **제안**: v0.3 논의에서 나왔고 아직 검증되지 않은 설계.
- **결정**: 제품 소유자(사용자)가 명시적으로 동의한 것.
- 자료의 확인 수준은 다섯 가지로 표시한다. 자세한 목록은 [11](11-references.md)에 있다.
  - **원문 확인**: 이번 개정 작업 중 원문을 읽고 확인함. 설치한 패키지의 README와 타입 정의를 읽고 확인한 것도 원문 확인으로 적는다
  - **초록 확인**: 초록이나 요약 페이지를 읽고 확인함
  - **출처 위치 확인**: 출처의 위치는 확인했으나 내용은 기존 지식에 기반함
  - **기존 지식**: 원문을 다시 확인하지 않음. 인용 전 확인이 필요함
  - **Helm 내부 자료**: Helm 저장소의 자료(방법 카드, Method Transfer 지도 등)에 수록되어 있음

각 문서의 절 제목 옆에 `[결정]`, `[제안]`을 붙여 구분한다. 한 절 안에 둘이 섞이면 `[결정: 도입 / 제안: 세부 절차]`처럼 나눠 적거나, 표의 행마다 표시한다.

12~14에는 절마다 표시를 붙이지 않았다. 12~14의 항목은 모두 [제안]으로 본다.

용어 규칙:

- 제품의 사용 사례는 "유즈케이스"라고 부른다.
- "시나리오"는 결과 탐구의 시나리오([04 §5](04-inquiry-types.md))와 테스트 시나리오에만 쓴다.

## 5. v0.3에서 결정된 것

다음은 v0.3 논의에서 제품 소유자가 명시적으로 동의한 사항이다.

1. Helm의 출발 동기는 원함 발견이며, 발산은 그 동기를 위한 방법이다.
2. Effect class와 가역성 판별은 Helm 범위에서 뺀다.
3. 모드는 페르소나와 다르다. 루프를 중심으로 루프 계획 기본값, 능력 부분집합, 다이얼 값을 정한 설정이다.
4. 능력은 도메인 동작("코드 변경")이 아니라 원시 행동으로 정의한다.
5. 루프는 한 작업 안에서 필요에 따라 여러 개를 조합하며, 기본 조합은 언제든 다른 루프로 전환할 수 있다.
6. 상황 유형은 바뀔 수 있는 상태다.
7. 탐구 네 종류(사실, 원함, 가능성, 결과)를 둔다.
8. 혼자 정한 결정을 기록하고 나중에 확인할 수 있어야 한다.
9. 외부 응답은 탐구 중 발견된 관찰로 다룬다.
10. OPD+C를 위한 장기 관찰·제어 공간은 클라이언트 UX의 주요 구현 대상이다.
11. Goal은 프로젝트 단위의 궁극 목표이며, Concern 사이클을 거치며 계속 정제된다([02 §3](02-core-concepts.md)).
12. Concern은 10단계 과정을 돌릴 후보가 되는 상황 그 자체다([02 §4](02-core-concepts.md)).
13. 묻기를 재설계한다. 질문의 기록과 전달을 나누고, 권리 게이트와 정보 게이트를 구분하고, 전달 방식(즉시·협상·중재·예약)을 두고, 질문 레코드에 가정 만료점을 둔다([06 §3](06-asking-and-interruption.md)). 다이얼 수치는 [제안]으로 남는다.
14. 다른 분야의 방법과 사고방식을 지금 문제에 적용하는 개념의 이름은 Method Transfer로 한다. "투영"은 정본을 읽어 만든 화면이라는 뜻(불변조건 3)으로만 쓴다([02 §10](02-core-concepts.md)).
15. 커널 원칙: 모델은 제안하고, 커널이 상태를 바꾼다([08 §1](08-runtime-architecture.md)).
16. 상황 유형에는 Cynefin의 유형을 쓴다([05](05-situation-types.md)).
17. 클라이언트는 웹이 아니다. 데스크톱 앱을 먼저 만들고, 이후 SSH + pi + 커스텀 TUI 경로를 더한다.
18. Helm은 제품 소유자의 개인 WSL 서버에서 실행한다.
19. 클라이언트는 외부(원격)에서 접속할 수 있어야 한다.
20. 클라이언트가 연결되어 있지 않아도 진행 중인 작업은 계속된다.
21. 구현보다 기획·아키텍처 결정을 먼저 한다.
22. 제품의 사용 사례는 "유즈케이스"라고 부른다(§4 용어 규칙).
