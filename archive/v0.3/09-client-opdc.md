# 09. 클라이언트와 OPD+C

## 1. 왜 클라이언트가 핵심인가 [결정]

OPD+C(Observability, Predictability, Directability, Contestability)는 v0.1부터 공동행위의 평가 기준이었다. 하지만 기준만 있고, 사람이 이를 실제로 누릴 공간이 정의되지 않았다.

v0.3은 다음을 결정한다.

> 사람이 에이전트의 작업을 오랜 기간에 걸쳐 관찰하고, 예상하고, 방향을 바꾸고, 이의를 걸 수 있는 공간이 있어야 한다. 이 공간은 에이전트 UI 클라이언트에서 UX로 구현해야 할 주요 대상이다.

## 2. 대화 중심과 상태 중심

opencode 앱 같은 일반 에이전트 UI는 대화 기록이 중심이다. Helm 클라이언트는 상태가 중심이어야 한다.

| 항목 | 대화 중심 UI | Helm 클라이언트 |
|---|---|---|
| 기본 화면 | 시간순으로 쌓이는 대화와 도구 호출 | 열린 Goal과 Concern, 각각의 상태 |
| 사람이 하는 일 | 대화를 따라 읽음 | 상태를 보고, 필요한 곳에만 들어감 |
| 시간 범위 | 세션 하나 | 며칠, 몇 주 |
| 에이전트가 정한 것 | 대화 속에 흩어짐 | 따로 모여 있고 이의를 걸 수 있음 |
| 질문 | 대화 흐름을 멈추고 끼어듦 | 질문함에 쌓이고 전달 방식에 따라 전달됨 |
| 근거 | 위로 스크롤해서 찾음 | 판단마다 근거 체인을 바로 열 수 있음 |
| 방향 수정 | 새 메시지로 다시 설명 | 목표, 기준, 다이얼을 직접 고침 |
| 대화 | 전부 | 상태 화면의 각 객체에서 열 수 있는 보조 수단 |

## 4. 화면 구성 [제안]

### 4.1 홈

- **Goal 목록**: 각 Goal의 현재 버전, 연결된 선호 모델 요약
- **Concern 트리**: Concern마다 상황 유형, 현재 루프, 모드, 상태(진행 중, 대기, 결과 확인 대기). 트리는 기본으로 접혀 있고, 대기 중이거나 사람이 필요한 것만 펼쳐 보인다.
- **복귀 요약**: 자리를 비운 사이 바뀐 것, 선택 필요, 확인하면 좋은 것, 에이전트가 정한 것(개수)

### 4.2 Concern 상세

- **루프 이력**: 어떤 루프를 거쳤고 언제 왜 전환했는지 (루프 전환 레코드)
- **지금 하는 일**: 현재 루프, 현재 WorkUnit, 그 일을 하는 이유
- **다음 예정**: 다음 행동, 멈출 조건
- **사용 중인 가정**: 답을 받지 않고 진행 중인 임시 가정과 각각의 만료점
- **하위 Concern**: 구조 루프가 나눈 부분과 경계 항목

### 4.3 질문함

- 질문 레코드 목록. 각 질문의 전달 방식, 임시 가정, 만료점, 추천, 대안
- 비슷한 시점의 질문은 묶어서 한 번에 답할 수 있음
- 답하지 않고 "가정대로 진행"을 고를 수 있음

### 4.4 에이전트가 정한 것

- 종류별로 접힌 목록 (루프 전환, 상황 판정, 분해, 가정 확정, 라우팅, 일반 선택)
- 항목마다: 무엇을 정했나, 대안, 이유, 묻지 않은 이유
- 이의 버튼: 누르면 해당 선택이 contested가 되고 관련 Concern이 다시 열림

### 4.5 탐구 화면

| 탐구 | 보여주는 것 |
|---|---|
| 사실 | 관점별 예측과 반박 조건, 후보별 지지·반대 근거, 다음 구분 확인 |
| 원함 | 자극판, 기준 후보와 확신도, 말한 기준과 실제 반응의 차이 |
| 가능성 | 발산 표 (채워진 칸, 빈 칸, 해당 없음과 이유), 렌즈별 가능성, 근거 유무 |
| 결과 | 예측 목록, 실패 경로와 대응, 확인 날짜 |

모든 탐구 화면에서 **대비 압축**을 적용한다. 결과를 바꾸는 차이가 있는 것을 앞에 보이고 나머지는 접는다. 대비 압축은 보여 주는 순서만 정한다. 선택지를 2~3개로 줄이지 않으며, 접힌 항목도 펼쳐 반응할 수 있다. 단, 반대 근거와 이견은 접지 않는다(A9).

### 4.6 원함 탐구의 자극판

원함 탐구는 반응의 해상도가 결과를 좌우하므로 반응 UI에 별도 요구가 있다.

| 요구 | 설명 |
|---|---|
| 요소 단위 반응 | 자극의 특정 부분을 골라 그 부분에만 반응을 달 수 있음 |
| 강도 | 아주 좋음부터 아주 싫음까지 |
| 이유 없음 | "이유는 모르겠지만 이건 아님"을 한 번에 남길 수 있음 |
| 세 개 비교 | "둘은 비슷하고 하나는 다른데 무엇 때문인가" 질문 UI |
| 고쳐 말하기 | "이것과 비슷한데 더 ~하게" 입력 |
| 하나 고르기만 있는 UI 금지 | 고르기는 가능하되, 고르기만으로 라운드가 끝나지 않음 |

### 4.7 근거 체인

판단, 선택, 결과 확인 어디서든 근거를 따라 내려갈 수 있다.

```text
판단 FD-1 "첫 화면 지연의 주원인은 순차 요청"
  ├─ 근거 O-2  "첫 렌더 전 API 4개 순차 호출"  → 도구 실행 기록
  ├─ 근거 O-8  "3번째 요청 제거 시 LCP 4.1s → 2.9s" → 실행 기록, 측정 시점 커밋
  └─ 반대 근거 검토 CE-1 "데스크톱도 1.9s인데 불만 적음" → 열린 질문으로 남음
```

### 4.8 Goal 이력

- 버전별 변경 내용
- 어떤 Concern의 어떤 관찰이나 반응이 변경의 계기였는지
- 변경으로 다시 확인 대상이 된 작업 합의 목록

### 4.9 다이얼 패널

- 현재 Concern의 모드와 다이얼 값
- 값을 바꾸면 다음 턴 경계에서 반영되고, 바뀐 사실이 기록됨
- 설정 층([07 §6](07-modes-and-capabilities.md)) 중 어느 층의 값인지 표시

## 5. OPD+C 대응과 지표

| 기준 | 화면 요소 | 지표 | 목표 |
|---|---|---|---|
| Observability | 홈, Concern 상세, 에이전트가 정한 것, 근거 체인 | 의도나 합의에 연결되지 않은 M 변경 수 | 0 |
| Predictability | 다음 예정, 사용 중인 가정, 예측 목록 | 예정했던 다음 행동과 실제 행동의 차이 | 차이가 나면 관찰로 기록됨 |
| Directability | 다이얼 패널, Goal·기준 직접 수정, 질문함 | 명령부터 행동 변화까지의 턴 수, 기준 하나를 바꾸는 데 필요한 조작 수 | 다음 턴 경계 |
| Contestability | 이의 버튼 (선택, 판단, 상황 판정, 분해, 기준 후보) | 처리되지 않고 사라진 이의 수 | 0 |

A12(자동화가 사람의 이해를 낮추면 실패)를 위한 지표도 함께 본다.

| 지표 | 해석 |
|---|---|
| 복귀 후 다시 작업에 참여하기까지 걸린 시간 | 길어지면 복귀 요약이 제 역할을 못함 |
| 사람이 직접 바꾼 기준, 재정의, 이의의 비율 | 0에 가까워지면 사람이 수동적인 승인자가 되어 감 |

## 6. 하지 말아야 할 것

| 하지 말 것 | 이유 |
|---|---|
| 승인과 취소 버튼만 나열 | 사람을 승인자로 만듦 (A15 위반) |
| 모든 도구 호출을 시간순으로 나열 | 상태가 아니라 로그를 읽게 만듦 |
| 짧게 만들려고 반대 근거와 이견을 지움 | A9 위반 |
| 에이전트를 사람처럼 꾸미기 | 신뢰를 부풀림. Helm 쉬운 말 문서의 "Helm이 아닌 것"과 같음 |
| 같은 미해결 결정에 알림 반복 | v0.2 kernel의 Gate rule. 선택 요청과 알림은 별개 |
| 하나 고르기만 있는 원함 탐구 UI | 원함 탐구의 목적과 맞지 않음 |
