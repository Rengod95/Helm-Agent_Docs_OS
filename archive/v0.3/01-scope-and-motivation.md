# 01. 범위와 동기

## 1. Helm의 출발 동기 [결정]

### 1.1 출발 가정

Helm의 첫 출발점은 정답이 사용자의 취향에 달린 작업이었다. 글의 톤, 기획의 방향, 디자인 같은 작업이다. 제품 소유자의 원래 진단은 다음과 같다. 지금의 에이전트 루프는 사용자의 지시에서 출발한다. 그래서 에이전트가 내리는 결정 하나하나가 사용자 자신의 지식 수준을 넘지 못한다.

Helm은 다음 가정에서 출발한다.

> 사용자가 글로 표현한 요구와 사용자가 실제로 가진 요구는, 사용자 자신도 모르는 사이에 다를 수 있다.

예를 들어 "블로그 글을 짧게 써 줘"라고 쓴 사용자가 여러 도입부를 읽어 본 뒤 계속 고른 것이 긴 글 중 장면 묘사로 시작하는 글일 수 있다([04 §3.4](04-inquiry-types.md)의 `stated_vs_revealed`). 요청대로 짧게 쓰면 요청은 처리됐지만 원하는 것은 이뤄지지 않는다.

취향형이 아닌 작업에서도 같은 일이 생긴다. "첫 화면을 빠르게 해 줘"라고 쓴 사용자가 실제로 원한 것은 "첫 화면에서 불만이 줄어드는 것"일 수 있다. 측정값이 빨라져도 불만이 그대로라면 요청은 처리됐지만 원하는 것은 이뤄지지 않았다.

사용자는 이 차이를 처음부터 알지 못한다. 레퍼런스와 자료를 보고, 서로 다른 접근과 그 원인, 부작용을 비교해 본 뒤에야 "아, 내가 원한 게 이거구나"를 알게 된다.

### 1.2 그래서 Helm이 하는 일

Helm은 사용자의 지시를 그대로 수행하는 도구가 아니라, 다음 과정을 돕는 에이전트 방법론이다.

1. 사용자가 표현한 요구를 출발점으로 삼되 확정된 정의로 취급하지 않는다.
2. 서로 다른 관점, 다른 분야의 사고방식, 레퍼런스를 자극으로 제시한다.
3. 사용자의 반응을 근거로 실제 요구를 찾는다.
4. 찾은 요구를 Goal과 완료 기준에 반영하고, 이후 작업에서 계속 다듬는다.

발산은 이 동기를 위한 방법이다. 발산의 목적은 선택지를 많이 만드는 것 자체가 아니라, 사용자가 비교를 통해 원하는 것을 알게 되는 것이다.

### 1.3 발산이 주는 두 번째 가치

발산하다 보면 전혀 다른 분야에서 비슷한 문제를 다룬 방식이 나온다. 그 방식을 지금 문제에 옮겨 쓰면 사용자가 생각하지 못한 해법이나 관점이 생긴다. 이것을 **Method Transfer**라고 부르며, [04](04-inquiry-types.md)의 가능성 탐구에서 다룬다.

정리하면 발산의 가치는 두 가지다.

| 가치 | 무엇이 생기는가 | 다루는 탐구 |
|---|---|---|
| 원함 발견 | 사용자가 실제로 원하는 것 | 원함 탐구 |
| 관점 확장 | 다른 분야의 사고방식을 옮긴 해법과 관점 | 가능성 탐구 |

### 1.4 외부 근거 [기존 지식]

- **선호 구성 (constructed preference)**: 행동경제학과 의사결정 연구(Lichtenstein & Slovic 등)는 선호가 미리 머릿속에 있다가 꺼내지는 것이 아니라, 선택지를 마주하는 순간에 만들어진다고 본다.
- **병렬 프로토타이핑**: Dow 등(2010)은 시안을 하나씩 순서대로 만들 때보다 여러 개를 동시에 만들고 비교할 때 결과물의 질과 다양성이 높았다고 보고했다.
- **여러 시안 제시**: Tohidi 등(2006)은 사용자에게 시안을 하나만 보여주면 칭찬 위주로 반응하고, 여러 개를 보여주면 더 비판적이고 구체적인 의견이 나온다고 보고했다.

### 1.5 일반 LLM과 무엇이 다른가

대안 2~3개를 주고 고르게 하는 것은 LLM 하나로도 할 수 있다. Helm이 달라야 하는 부분은 자극을 만들고 반응을 처리하는 구조이며, 차이는 다음 표와 같다.

| 항목 | 일반 LLM | Helm |
|---|---|---|
| 자극의 범위 | 같은 분야 안의 변형 | 다른 분야의 레퍼런스까지 |
| 반응을 받는 단위 | 하나 고르기 | 요소 단위 반응, 이유를 못 대는 반응도 받음 |
| 반응의 처리 | 다음 응답에 반영하고 잊음 | 숨은 기준을 찾아 선호 모델로 기록 |
| 다음 자극 | 평균값 근처의 새 변형 | 가장 불확실한 기준을 확인할 수 있는 자극 |
| 결과물 | 고른 하나 | 기준, 무게, 좋은 예와 싫은 예를 담은 선호 모델 |
| 지속성 | 대화가 끝나면 사라짐 | Goal과 완료 기준에 남아 다음 Concern에서 다시 쓰임 |

자세한 절차는 [04 §3 원함 탐구](04-inquiry-types.md)에 있다.

## 2. 사용 전제 [결정]

- Helm은 **개인용**이다. 일반 사용자를 위한 제품이 아니라, 한 사람이 자기 작업을 위해 쓰는 에이전트 방법론과 런타임이다.
- 특정 에이전트 런타임(pi, Claude Code, Codex 등)에 종속되지 않는다. 구현 원칙은 [08](08-runtime-architecture.md)에 있다.
- 코드 작업만이 아니라 글쓰기, 조사, 계획, 의사결정 같은 범용 에이전트 작업을 대상으로 한다.

## 3. 적용 범주 [제안]

### 3.1 모든 작업에 적용하지 않는다

Helm은 라운드, 질문, 기록, 확인이라는 비용을 낸다. 이 비용은 문제 정의가 불확실하거나, 사용자가 원하는 것을 아직 모르거나, 작업이 여러 날과 여러 작업에 걸칠 때 회수된다. 모든 작업에 적용하면 마찰이 커지고, 사용자는 Helm이 필요한 작업에서도 그것을 건너뛰는 습관이 생긴다. 이는 공리 A12(자동화가 사람의 이해와 주도성을 낮추면 실패)에 해당한다.

### 3.2 범주는 업무 분야가 아니라 문제의 모양으로 정한다

"프론트엔드 성능" 같은 분야로 범주를 정하지 않는다. 같은 분야 안에도 정답이 명확한 작업과 불확실한 작업이 섞여 있기 때문이다.

### 3.3 진입 조건

다음 중 두 개 이상이 참이면 Helm으로 진입한다.

| 조건 | 확인하는 질문 |
|---|---|
| 목표가 흐림 | 완료 기준을 한 문장으로 쓸 수 없는가 |
| 관점이나 해법이 나뉨 | 원인이나 해법 후보가 둘 이상인데 아직 어느 쪽인지 모르는가 |
| 원하는 것이 취향에 달림 | 정답이 사용자의 취향이나 가치 판단에 달려 있는가 |
| 오래 걸림 | 여러 세션이나 여러 날에 걸치는가 |
| 다른 것과 얽힘 | 다른 결정, 다른 작업, 다른 사람의 일에 영향을 주는가 |

v0.2 논의의 "되돌리기 비쌈" 조건은 [§4](#4-범위에서-뺀-것-결정)에 따라 진입 조건에서 뺀다. 그 자리에 "원하는 것이 취향에 달림"을 넣는다. 이 조건이 Helm의 출발 동기와 직접 연결되기 때문이다.

### 3.4 제외 조건

그냥 해 보고 결과를 보는 비용이 탐구 비용보다 작으면 Helm으로 진입하지 않는다.

### 3.5 범주에 들어오는 요청의 예

**원인이 불분명한 증상**
- "첫 화면이 느리다는 얘기가 계속 나온다"
- "가끔 상태가 꼬이는데 재현이 안 된다"
- "요즘 글을 써도 반응이 예전 같지 않다"
- "에이전트가 이 저장소에서 자꾸 같은 실수를 한다"

**여러 방향 중 골라야 하는 것**
- "상태 관리 구조를 바꿔야 할까"
- "개인 하네스를 어느 런타임 위에 만들까"
- "이번 분기에 어떤 공부에 시간을 쓸까"

**원하는 것이 취향에 달린 것**
- "블로그 글의 방향을 잡고 싶다"
- "개인 프로젝트의 디자인 톤을 정하고 싶다"
- "발표 자료의 이야기 흐름을 정하고 싶다"

**목표 자체가 흐린 것**
- "에이전트를 더 잘 쓰고 싶다"
- "어떤 런타임에서도 같은 환경을 쓰고 싶다"
- "작업 기록을 더 쓸모 있게 만들고 싶다"

**오래 걸리고 얽히는 것**
- 빌드 도구나 프레임워크 마이그레이션
- 여러 저장소에 공통 설정 도입
- 여러 날에 걸친 학습 계획

**반복되는 마찰**
- "PR마다 같은 지적이 나온다"
- "매번 같은 설정을 다시 한다"
- 관찰 에이전트가 세션 로그에서 찾아낸 반복 패턴

### 3.6 범주 밖에 두는 것

- 원인이 이미 확인된 버그 (스택 트레이스가 원인을 가리킴)
- 스펙이나 디자인이 정해진 구현
- 이름 바꾸기, 타입 수정, 테스트 추가, 오타 수정

### 3.7 승격과 강등

일반 작업으로 시작했어도 다음 신호가 보이면 Helm 진입을 제안한다.

- 같은 확인이 세 번 실패한다.
- 모델이 서로 다른 해법을 두 개 이상 꺼낸다.
- 작업 범위가 예상보다 커진다.
- 사용자가 "잘 모르겠는데", "이게 맞나" 같은 말을 한다.
- 사용자가 결과에 대해 이유를 설명하지 못한 채 "뭔가 아니다"라고 반응한다.

반대로 Helm 안에서 문제가 단순하다고 확인되면 증명 부담 다이얼을 낮추거나(v0.2의 Quick에 해당) 일반 작업으로 내린다. 승격과 강등도 혼자 정한 결정으로 기록한다([06](06-asking-and-interruption.md)).

### 3.8 범주가 맞는지 확인하는 지표

2~4주 사용 후 두 값을 본다.

| 지표 | 해석 |
|---|---|
| Helm으로 진입한 작업 중 실제로 Goal, 완료 기준, 문제 관점이 바뀐 비율 | 거의 0이면 범주가 너무 넓다. 이미 정의가 명확한 작업까지 들어오고 있다 |
| 일반 작업으로 처리했다가 나중에 방향을 다시 잡은 비율 | 높으면 범주가 너무 좁거나 승격 신호가 약하다 |

## 4. 범위에서 뺀 것 [결정]

### 4.1 Effect class와 가역성 판별

v0.2 kernel 문서는 행동을 R0~R4 다섯 등급으로 나눴다.

```text
R0 read-only local
R1 reversible local mutation
R2 shared or externally visible reversible action
R3 costly, sensitive, or low-recoverability action
R4 irreversible or prohibited-by-default action
```

v0.3에서는 이 분류를 Helm 범위에서 뺀다. 제품 소유자가 든 이유는 두 가지다.

1. **최근 모델은 행동을 되돌릴 수 있는지 스스로 판별할 수 있다.**
2. **이것은 Helm 연구가 다룰 문제가 아니라 에이전트 권한 레이어의 설계 원칙에 속한다.**

Claude가 덧붙인 근거: 되돌리기 어려운지는 행동마다 고정된 성질로 정해지지 않고 그때의 상황에 따라 달라진다. feature flag와 빠른 롤백이 있는 배포는 쉽게 되돌릴 수 있고, git이 추적하지 않는 파일의 수정은 되돌릴 수 없다.

이 결정에 따르는 위험(고정된 정의가 없어 매번 판정해야 함)과 대응은 [10 §2](10-critique-and-open-questions.md)에 적는다.

참고로 v0.1 공리 A7은 권한이 "가역성, 파급 범위, 관측 가능성에 따라" 달라진다고 썼고, v0.2 kernel 문서는 이를 고정 목록으로 적었다. 두 문서는 원래부터 서로 맞지 않았다.

### 4.2 Helm에 남는 것

- "무엇을 왜, 어디까지 맡겼는가"라는 **작업 합의** 자체
- 권한 레이어가 "이 행동은 사람의 허락이 필요하다"고 판정했을 때, 그것을 **선택 요청으로 열고 기록하는 일**
- 선택 요청을 열지 정할 때 필요한 위험 정보는 권한 레이어나 모델이 제공하는 값을 입력으로 받는다

### 4.3 공리 A7의 해석 변경

A7 "자율성은 이진값이 아니라 위험 적응적 권한 범위다"는 유지하되, 위험의 판별은 Helm 바깥에서 하고 Helm은 그 결과를 작업 합의와 선택 요청에 반영한다.
