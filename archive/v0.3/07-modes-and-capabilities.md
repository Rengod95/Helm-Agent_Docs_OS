# 07. 모드와 능력

## 1. 모드의 정의 [결정]

v0.3 논의에서 "작업 유형에 따라 Helm 개념을 다르게 적용하는 모드"가 필요하다는 요구가 나왔다. v0.3은 모드를 다음과 같이 정의한다.

> 모드 = 루프 계획 기본값 + 능력 부분집합 + 다이얼 값

모드는 이 세 가지를 묶은 설정이다. "꼼꼼한 검토자", "창의적인 기획자" 같은 성격 설정(페르소나)과 다르며, 어떤 루프를 중심으로 어떤 능력을 쓰고 얼마나 묻고 얼마나 넓게 탐구할지를 정한다.

[제안] v0.2의 Quick / Guided / Assured는 모드의 다이얼 하나(형식과 증명 부담의 양)에 해당한다고 보고, 이를 여러 다이얼로 나눈 뒤 그 값을 모드로 미리 만들어 두는 방안을 검토한다. Quick / Guided / Assured라는 이름을 유지할지는 열린 질문이다([10 §4.1-4](10-critique-and-open-questions.md)).

## 2. 능력 두 층 [결정]

### 2.1 왜 두 층인가

v0.2의 A 평면은 observe, propose, decide within scope, execute action classes, attest evidence, accept result, integrate baseline의 일곱 능력을 하나의 목록으로 두었다. v0.3 논의 중 "코드 변경" 같은 도메인 동작을 능력으로 적으면 범용 작업에 맞지 않는다는 지적이 나왔다.

v0.3은 능력을 성격이 다른 두 층으로 나눈다.

| 층 | 질문 | 수행하는 곳 |
|---|---|---|
| 원시 행동 | 세상에 대해 무엇을 할 수 있나 | 런타임의 도구 (tool calling, REPL 등 방식 무관) |
| 기록 능력 | Helm 기록에 무엇을 쓸 수 있나 | Helm 커널 |

### 2.2 원시 행동

| 행동 | 뜻 | 예 |
|---|---|---|
| read | 상태를 바꾸지 않고 읽음 | 파일 읽기, 검색, 웹 페이지 읽기, 메일함 조회 |
| write | 작업 대상의 상태를 바꿈 | 파일 수정, 문서 편집, 일정 생성 |
| execute | 프로그램이나 절차를 실행 | 테스트 실행, 스크립트 실행, 빌드 |
| send | 작업 공간 밖으로 무언가를 내보냄 | 메일 발송, 메시지 게시, 외부 API에 쓰기, push |
| spawn | 하위 실행을 만듦 | 하위 에이전트, 하위 호출, REPL의 `llm_query` |
| ask | 사람에게 질문함 | 질문 레코드를 거쳐 전달 ([06](06-asking-and-interruption.md)) |

- execute는 읽기처럼 동작할 수도, 쓰기처럼 동작할 수도 있다. 어느 쪽인지, 위험한지의 판정은 권한 레이어가 한다([01 §4](01-scope-and-motivation.md)).
- send는 정보가 밖으로 나가는 모든 행동이다. 밖으로 나간 정보는 되돌릴 수 없으므로, 권한 레이어가 권리 게이트 대상으로 분류할 가능성이 높다.
- 이 여섯 행동을 어떤 도구로 구현하는지는 런타임마다 다르다. 예를 들어 pi의 기본 도구 read, write, edit, bash는 각각 read, write, write, execute에 대응한다.

### 2.3 기록 능력

| 능력 | 뜻 | 예 |
|---|---|---|
| observe | 행동 결과를 관찰로 남김 | 도구 실행 결과가 관찰 레코드가 됨. 실제 생성은 런타임이 하며, 행위자는 출처가 됨 |
| propose | 후보를 제출함 | 추측, 가능성, 질문, 합의 초안, 루프 계획, 분해 제안, Goal 수정 제안 |
| attest | 근거가 맞다고 증언함 | 검증 에이전트가 "이 테스트 결과는 C1을 충족한다"고 기록 |
| accept | 확정함 | 결과 확인, Goal 수정 확정, 선호 기준 확정, 판단 확인 |
| integrate | 반영 완료를 표시함 | 반영 항목을 닫음 |

v0.2의 "decide within scope"는 별도 능력으로 두지 않는다. 맡긴 범위 안에서 에이전트가 정하는 것은 propose의 결과가 P(합의 범위)를 통과해 혼자 정한 결정으로 기록되는 것으로 처리한다.

### 2.4 행위자별 능력표 (A)

| 행위자 | read | write | execute | send | spawn | ask | observe | propose | attest | accept | integrate |
|---|---|---|---|---|---|---|---|---|---|---|---|
| 사람 | O | O | O | O | O | - | O | O | O | O | O |
| 작업 에이전트 | O | O | O | O | O | O | O | O | X | X | X |
| 검증 에이전트 | O | X | O | X | O | O | O | 반대 근거만 | O | X | X |
| 중재자 | O (질문·사용자 상태만) | X | X | X | X | 전달만 | O | 전달 시점 | X | X | X |
| 관찰 에이전트 | O (기록만) | X | X | X | O | X | O | P 수정안, 절차 후보 | X | X | X |
| 라우터 | O (입력·기록) | X | X | X | X | X | O | 모드 | X | X | X |

이 표는 상황과 무관하게 고정된 A다. 실제로 허용되는지는 P가 상황에 따라 추가로 조건을 붙인다. 예를 들어 작업 에이전트의 write는 합의 범위 안에서만, send는 권리 게이트를 통과한 경우에만 허용된다.

## 3. 다이얼

이 표를 다이얼의 정본 목록으로 둔다. 다른 문서의 다이얼 표는 이 표의 일부를 자세히 적은 것이다. 다이얼은 모두 열네 개다.

| 다이얼 | 조절하는 것 | 자세한 곳 |
|---|---|---|
| 질문 조건 문턱 | 질문 조건 1~3마다 적게 묻기 / 보통 / 많이 묻기 [제안] | [06 §2.1, §5](06-asking-and-interruption.md) |
| 기본 전달 방식 | 질문을 즉시 / 협상 / 중재 / 예약 중 어떻게 전달할지 | [06 §5](06-asking-and-interruption.md) |
| 즉시 승격 문턱 | 언제 즉시로 올릴지 | [06 §5](06-asking-and-interruption.md) |
| 만료 여유 | 가정 만료점 얼마 전에 올릴지 | [06 §5](06-asking-and-interruption.md) |
| 종류별 예외 | 특정 종류의 결정은 항상 묻기, 또는 절대 묻지 않기 | [06 §5](06-asking-and-interruption.md) |
| 루프별 설정 | 위 질문 다이얼 값을 O, I, C, A, S마다 다르게 | [06 §5](06-asking-and-interruption.md) |
| 관점 폭 | 발산 표의 크기, 렌즈 수 | [04 §7](04-inquiry-types.md) |
| 탐구 깊이 | 라운드 수 | [04 §7](04-inquiry-types.md) |
| 근거 범위 | 작업 대상만 / 문서까지 / 웹까지 | [04 §7](04-inquiry-types.md) |
| 자율 정도 | 묻지 않고 몇 라운드까지 진행할지 | [04 §7](04-inquiry-types.md) |
| 예산 | 하위 호출 수, 시간 | [04 §7](04-inquiry-types.md) |
| 자극 수 | 원함 탐구의 라운드당 자극 수 상한 | [04 §7](04-inquiry-types.md) |
| 증명 부담 | 결과 확인에 필요한 근거의 양 (v0.2의 Quick / Guided / Assured) | v0.2 |
| 독립 검증 | 결과 확인 전에 검증 에이전트를 거칠지 | [08](08-runtime-architecture.md) |

**질문 빈도**는 질문 조건 문턱 세 개의 값을 한 번에 정하는 미리 만든 조합이며, 별도 다이얼로 세지 않는다. 예를 들어 질문 빈도 "적게"는 세 조건의 문턱을 모두 "적게 묻기"로 둔다. [제안]

## 4. 모드 예 [제안]

모드 이름은 [제안]이다. 탐구 이름(사실 탐구, 원함 탐구)과 겹치지 않게 지었다.

| 모드 | 중심 루프 | 원시 행동 | 기록 능력 | 다이얼 기본값 | 맞는 상황 |
|---|---|---|---|---|---|
| 복귀 안내 | O | read | observe, propose(요약) | 질문 없음 | 며칠 만에 돌아옴 |
| 원인 조사 | O, I.fact | read, execute(읽기 목적), spawn | observe, propose | 협상, 깊이 깊게, 근거 범위 문서까지 | 원인 불명 증상 |
| 취향 탐색 | O, I.want, I.possibility, C.probe | read, write(초안·시안), spawn, ask | observe, propose | 라운드 경계에 예약, 폭 넓게, 근거 범위 웹까지 | 취향형 작업, 흐린 목표 |
| 실행 | C.commit, A.confirm | read, write, execute | observe, propose | 협상, 범위 이탈 시 즉시 | 정해진 일 |
| 검증 | A.confirm | read, execute | observe, propose(반대 근거), attest | 결과 확인 때만 | 리뷰, 사실 확인 |
| 구조 정리 | S | read | observe, propose(분해·병합) | 예약 | Concern이 엉켜 있음 |
| 비상 | C.emergency, O | read, write, execute (비상 합의 범위 안) | observe, propose | 비상 합의 범위 안은 묻지 않음 | 혼돈 |

모드는 루프 계획의 기본값을 정할 뿐이다. 작업 중 루프 전환이 일어나면 모드도 함께 바뀔 수 있다([03](03-loops-and-transitions.md)). 루프 식별자는 [03 §2.1](03-loops-and-transitions.md)을 따른다.

## 5. 라우팅 [제안]

### 5.1 방식

v0.3 논의에서 두 방식이 나왔다.

1. 사용자가 설정 화면에서 다이얼을 직접 조정한다.
2. 작업 유형별 모드를 미리 만들어 두고, 사용자의 입력에 따라 어떤 모드를 쓸지 라우팅한다.

둘 다 쓴다. 라우팅이 기본 모드를 고르고, 사용자 설정은 그 위에 덮어쓰는 층이 된다.

### 5.2 라우터가 보는 신호

| 신호 | 예 |
|---|---|
| 상황 판정 | 복합이면 취향 탐색 모드 |
| 진입 조건 | 진입 조건이 두 개 이상 참이면 Helm으로 진입하고, 두 개 미만이면 Helm 밖의 일반 작업 ([01 §3.3](01-scope-and-motivation.md)) |
| 입력의 형태 | "~ 리뷰해줘"면 검증 모드, "어디까지 했지"면 복귀 안내 모드 |
| 사용자의 명시 | `/mode taste` 같은 직접 지정 |
| 기록 | 같은 종류의 Concern에서 과거에 쓰인 모드와 그 결과 |

### 5.3 라우터의 결정도 기록한다

라우터가 모드를 고른 것 자체가 에이전트가 혼자 정한 결정이다. 따라서 선택 레코드로 남기고, 사용자가 이의를 걸 수 있다. 이의가 걸린 라우팅 기록은 라우팅 규칙 수정의 자료가 된다.

## 6. 설정의 우선순위

여러 층의 설정이 겹칠 때 아래쪽이 위쪽을 덮어쓴다.

```text
1. 시스템 기본값
2. 상황 유형별 기본값 (05)
3. 라우팅으로 고른 모드
4. 사용자의 저장된 설정
5. 현재 Concern에서 사용자가 바꾼 값
6. 지금 이 지시
```

## 7. 다이얼이 건드리지 못하는 것

어떤 모드, 어떤 다이얼 값에서도 다음은 바뀌지 않는다([00 §2.4](00-README.md)).

1. 기록과 진실은 다르다.
2. 관찰, 추측(해석과 가능성), 판단, 선택은 다르다.
3. 투영은 정본을 쓰지 않는다.
4. 권한은 범위를 가진다.
5. 완료 주장, 결과 확인, 전체 반영은 다르다.
6. 모르는 것, 이견, 낡은 상태는 숨기지 않는다.
7. 혼자 정한 결정도 기록되며 이의를 걸 수 있다.

예를 들어 질문 빈도를 "적게"(세 질문 조건의 문턱을 모두 "적게 묻기")로 설정해도 작업 에이전트가 결과를 확인(accept)할 수는 없다. 다이얼은 얼마나 묻고 얼마나 증명할지만 조절한다.
