# 08. 런타임 구조

이 문서는 특정 에이전트 런타임과 무관하게 Helm을 구현하는 원칙을 적는다. 특정 런타임(pi 등)에 대한 내용은 §11에 참고로만 둔다.

## 1. 기본 원칙: 모델은 제안하고, 커널이 바꾼다 [결정]

Helm 공리의 대부분은 "모델이 무엇을 혼자 하면 안 되는가"에 관한 것이다. 추측을 판단으로 올리면 안 되고, 범위를 넘으면 안 되고, 자기 결과를 스스로 확인하면 안 된다. 이런 규칙은 프롬프트만으로는 지켜지지 않는다. 상태 변경을 모델 바깥의 코드만 할 수 있을 때 지켜진다.

그래서 구조는 다음과 같다.

- LLM 에이전트 루프는 **제안만 하는 하위 실행**이다.
- 그 바깥에 Helm의 규칙을 집행하는 **커널**이 있다.
- 모델이 상태를 바꾸려면 반드시 타입이 정해진 제안(action)을 커널에 보내야 한다.

React 개발자에게 익숙한 비유로는 Redux와 같다.

| Redux | Helm |
|---|---|
| 컴포넌트가 dispatch하는 action | 모델의 제안, 사람의 명령, 런타임의 도구 결과 |
| middleware | 형식 검사, 권한 검사 |
| reducer (순수 함수) | 커널의 상태 전이 |
| store의 state | N, E, M 레코드 |
| action 기록과 시간 여행 | 이벤트 로그, 특정 시점 상태 조회 |
| selector | 투영 (복귀 요약, 모델에게 주는 컨텍스트) |

v0.3 논의 중 작성한 장난감 커널 `helm.mjs`(이 문서 묶음과 별도로 전달됨)는 이 구조를 reducer 하나로 보여준다. 21번의 시도 중 8번이 거부되고, 거부된 시도도 기록에 남는다.

## 2. 모든 변화가 지나는 경로

```text
입력 (모델 제안 / 사람 명령 / 도구 결과 / 타이머)
  → 1. 형식 검사      스키마, 참조 id가 실재하는가, 어느 칸의 레코드인가
  → 2. 권한 검사      A(능력표)와 P(상황 조건). 권한 레이어의 판정 결과를 입력으로 받음
  → 3. 이벤트 기록    누가, 언제, 무엇을, 무엇을 근거로
  → 4. 세계 모델 갱신 N, E, M 레코드와 품질 상태
  → 5. 규칙 평가      루프 전환, 질문 전달, 재진입, 상황 재판정, 구조 루프 호출
  → 6. 투영과 감시    복귀 요약, 클라이언트 화면, OPD+C 지표
  → 7. 다음 단계 구성 다음 루프에 줄 도구, 지시, 컨텍스트
  → 내부 에이전트 루프의 다음 턴
```

1이나 2에서 실패하면 거부되고, 이유가 제안한 쪽에 돌아간다. 거부된 시도도 기록에 남는다(A14).

## 3. 구성요소

| 구성요소 | 하는 일 | 위치 |
|---|---|---|
| 정본 저장소 | 이벤트 로그. 레코드의 현재 상태는 로그를 재생해서 얻음 | 런타임 바깥 |
| 커널 | 위 경로의 1~7 | 순수 모듈 (런타임 import 없음) |
| 런타임 어댑터 | 커널의 "다음 단계 구성"을 특정 런타임의 설정으로 바꾸고, 도구 결과를 커널 입력으로 바꿈 | 런타임별 |
| 클라이언트 | 투영을 보여주고 사람의 명령을 받음 | [09](09-client-opdc.md) |
| 보조 행위자 | 검증 에이전트, 중재자, 관찰 에이전트, 라우터 | 각자 별도 컨텍스트 |

### 3.1 커널 모듈

| 모듈 | 내용 |
|---|---|
| schema | 레코드와 이벤트 타입 ([02 §8](02-core-concepts.md)) |
| ledger | append-only 기록, 해시 체인 (커널을 거치지 않은 변경 감지) |
| concern | Concern 상태 기계: 상황 유형, 루프 계획, 현재 루프, 상위·하위 연결 |
| loops | 루프 계약 (§7)과 전환 규칙 ([03 §5, §6](03-loops-and-transitions.md)) |
| promote | 추측 → 판단 승격 규칙, 기준 후보 → 선호 기준 승격 규칙 |
| policy | P 규칙 평가. 권한 레이어의 판정을 입력으로 받음 |
| questions | 질문 레코드, 전달 방식 결정, 가정 만료점 감시 ([06](06-asking-and-interruption.md)) |
| timers | 기대 기한, 예측 확인일, 가정 만료점, 다시 볼 조건 |
| projection | 대상과 시점별 읽기 전용 화면 |
| inquiry | 발산 표의 빈 칸 계산, 확인 순서 계산, 다음 자극 선택, 멈춤 판정 ([04 §8](04-inquiry-types.md)) |

## 4. 결정 주체 분류 [결정: 원칙 / 제안: 표]

Helm의 결정을 하나씩 꺼내 네 가지 중 하나로 표시한다.

| 분류 | 뜻 |
|---|---|
| 코드 | 커널이 규칙으로 정함 |
| 모델 선언 + 코드 계산 | 모델이 구조화된 값을 선언하고, 결정은 코드가 계산함 |
| 사람 | 사람이 정함 |
| 측정 | 정하지 않고 지표로만 봄 |

원칙 [결정]: **모델이 구조화된 값을 선언할 수 있으면 결정 자체는 코드로 내린다.**

아래 표의 결정별 분류는 [제안]이다.

| 결정 | 분류 |
|---|---|
| 관찰 생성 | 코드 (도구 결과에서 자동) |
| 추측 → 판단 승격 | 코드 (규칙) + 사람 (결정에 쓰이는 경우) |
| 발산할 곳 (빈 칸) | 코드 |
| 확인 순서 | 모델 선언(예측, 비용) + 코드 계산 |
| 다음 자극 (원함 탐구) | 모델 선언(기준 후보) + 코드 계산 |
| 물을 질문 선택 | 모델 선언(후보) + 코드 계산 |
| 질문 전달 방식과 시점 | 코드 (규칙) + 중재자 (중재 방식일 때) |
| 탐구 멈춤 | 코드 |
| 상황 유형 | 모델 선언(판정 질문의 답과 근거) + 코드 기록, 사람 이의 가능 |
| 루프 전환 | 모델 제안 + 코드 (의존 규칙 검사) |
| 구조 루프의 분해·병합 | 모델 제안 + 코드 (상한 검사), 사람 이의 가능 |
| 결과 확인 | 사람 |
| Goal 변경 | 사람 |
| 선호 기준 확정 | 사람 |
| 선택의 질, 관점의 다양성, 예측의 정확도 | 측정 |

## 5. 공리별 네 항목

공리마다 불변조건, 집행 지점, 위반 테스트, 운영 지표를 적는다. 예:

| 공리 | 불변조건 | 집행 지점 | 위반 테스트 | 운영 지표 |
|---|---|---|---|---|
| A5 상태 구분 | 관찰은 실제 실행 결과를 참조해야 함 | 형식 검사 | 모델이 지어낸 id로 근거를 연결하면 거부되는가 | 근거 없는 추측의 비율 |
| A6 제안과 약속 | 결과 확인은 accept 능력이 있는 행위자만 | 권한 검사 | 작업 에이전트가 accept를 보내면 거부되는가 | - |
| A10 제출·확인·반영 | 반영 항목이 남으면 완료 불가 | 규칙 평가 | 반영 항목이 남은 Concern을 닫으면 거부되는가 | 열린 반영 항목 수 |
| A13 낡음 | 참조한 M이 바뀌면 근거가 stale | 세계 모델 갱신 | 파일 해시가 바뀐 뒤 근거 상태가 stale인가 | stale 근거로 내려진 선택 수 |
| 불변조건 7 | 혼자 정한 결정은 why_not_asked와 함께 기록 | 형식 검사 | autonomous 선택에 why_not_asked가 없으면 거부되는가 | 종류별 이의 비율 |
| 구조 루프 규칙 2 | 하위가 모두 반영돼야 상위가 닫힘 | 규칙 평가 | 하위가 열린 상위를 닫으면 거부되는가 | 재조합 생략 건수 |

## 6. 커널 테스트와 모델 평가를 나눈다

| 대상 | 방법 | 보장하는 것 |
|---|---|---|
| 커널 | 정해진 제안 순서를 내는 가짜 모델로 시나리오 재생. 같은 입력이면 같은 이벤트 로그가 나와야 함 | 잘못된 승격, 범위 밖 실행, 확인 없는 완료가 일어나지 않음 |
| 커널 불변조건 | 무작위 제안 순서를 넣는 속성 기반 테스트 | 어떤 순서로도 불변조건이 깨지지 않음 |
| 모델 품질 | 별도 평가 | 관점 다양성, 예측 정확도(예측 레코드의 result), 선호 모델 안정성, 혼자 정한 결정의 이의 비율 |

커널이 보장하는 것과 모델 성능에 달린 것을 섞지 않는다.

## 7. 루프 계약은 데이터로 둔다 [제안]

루프와 모드는 코드가 아니라 데이터로 정의하고, 커널이 읽어 동작한다. 이론이 바뀌면 데이터가 바뀌고, 테스트가 그 변화를 잡는다.

```yaml
loop_contract:
  id: I.want
  entry:
    - situation == complex          # 혼란(disorder)은 먼저 S.split으로 분해한다 (05 §2.5)
    - or: user_request_kind == taste
  exit:
    - preference_model.stable_rounds >= 2
    - or: budget.exhausted
  allowed_proposals: [stimulus, reaction_interpretation, criterion_candidate, question]
  primitives: [read, write(draft), spawn, ask]
  record_caps: [observe, propose]
  context_projection:
    include: [goal, preference_model, recent_reactions, open_questions]
    exclude: [unrelated_concerns]
  human_touchpoints: [criterion_confirm]
  opdc:
    observability: "현재 기준 후보와 확신도 표시"
    contestability: "기준 후보마다 이의 명령"
  budget: { rounds: 4, subcalls: 24 }
```

## 8. 런타임 계약 (벤더 중립)

커널이 하위 에이전트 런타임에 요구하는 능력은 다섯 개다.

| 능력 | 없을 때 |
|---|---|
| 주어진 지시, 도구, 컨텍스트로 루프를 실행 | 사용 불가 |
| 도구 호출을 실행 전에 가로챔 | 격리된 작업 공간에서 실행하고 끝난 뒤 diff로 범위 검사. 보장 수준을 낮추고 사용자에게 표시 |
| 도구 결과를 id와 함께 돌려줌 | 어댑터가 id를 부여. 출처 신뢰도를 낮게 표시 |
| 턴 경계에서 멈추거나 계속하게 함 | 실행 단위를 작게 쪼개서 매번 새로 실행 |
| 새 컨텍스트를 만듦 (검증자, 분기) | 별도 프로세스로 실행 |

원시 행동([07 §2.2](07-modes-and-capabilities.md))은 각 런타임의 도구에 대응시킨다. 도구 호출 방식이든 REPL 방식이든 커널 입장에서는 같다. 커널은 원시 행동 단위로 권한을 검사하고, 결과를 관찰로 받는다.

## 9. 하위 실행의 독립성

| 용도 | 방식 | 이유 |
|---|---|---|
| 발산 표의 빈 칸 | 같은 시점의 기록에서 시작한 분기들. 서로의 결과를 보지 못함 | 관점의 독립성을 구조로 보장 |
| 원함 탐구의 자극 생성 | 분기 | 같은 이유 |
| 검증 | 분기가 아닌 새 컨텍스트. 합의, 기준, 근거 id만 받음. 가능하면 다른 모델 | 분기는 작업자의 추론을 그대로 보므로 독립성이 깨짐 |
| 중재 | 새 컨텍스트 | 작업을 계속하려는 쪽으로 기울지 않게 |
| 탐구의 REPL 실행 | REPL 변수는 작업 메모. 기록은 dispatch로만 | [04 §9](04-inquiry-types.md) |

## 10. 시간

Helm에는 시간에 따라 일어나는 일이 많다.

- 기대 기한이 지나면 "응답 없음" 관찰
- 예측 확인일이 오면 A 루프
- 가정 만료점이 가까워지면 질문 승격
- 다시 볼 조건 감시
- 지속 관찰형 A의 관찰 기간

그래서 프로세스가 재시작돼도 살아남는 타이머가 필요하다. 사람이 없을 때도 돌아야 하므로, 대화 세션 안이 아니라 커널 쪽 스케줄러가 소유한다.

## 11. 참고: 현재 후보 런타임 [제안]

v0.3 논의 중 검토한 구현 경로이며, Helm 이론과 독립적이다.

| 경로 | 장점 | 한계 |
|---|---|---|
| pi coding agent 확장 | TUI가 있음. `tool_call` 차단, `tool_result` 기록, `agent_before_settle`, `session_before_compact` 등 개입 지점이 많음 | 상태가 세션 단위. 원자적 기록, 지속 타이머, 소유 구조가 없음 |
| pi-durable 하네스 | 항목·문서·task의 원자적 commit, phase 기반 task 상태 기계, 첫 기록 우선 memo, 분기, 소유 트리와 취소 전파, 재시작 후 재개 | 실험 단계. UI를 직접 만들어야 함. 저장소 하나에 프로세스 하나 |

어느 경로든 커널은 순수 모듈로 두고 어댑터만 바꾼다.

## 12. 다음 실험

1. 장난감 커널에 질문 레코드와 전달 방식 규칙을 붙이고, 기본 전달 방식만 바꿔 같은 시나리오를 돌려 본다.
2. 루프 계획, 루프 전환, 상황 판정 레코드를 붙이고, 의존 규칙 위반이 거부되는지 본다.
3. 구조 루프의 분해·재조합과 "하위가 열린 상위는 닫을 수 없음" 규칙을 재현한다.
4. 원함 탐구 한 라운드를 가짜 반응으로 돌려, 기준 후보 → 다음 자극 선택 → 선호 모델 승격 흐름을 확인한다.
