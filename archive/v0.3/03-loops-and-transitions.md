# 03. 루프와 전환

## 1. 원칙: 루프는 순서가 아니라 조합이다 [결정]

v0.1 운영 이론은 "네 루프는 순차 pipeline이 아니다"라고 적었다. 하지만 10단계 사이클(Sense → Frame → Diverge → Investigate → Deliberate → Commit → Execute → Assure → Integrate → Reflect)이 순서로 읽히면서, 실제 설계는 O → I → C → A를 차례로 지나는 형태가 되었다.

v0.3은 다음을 원칙으로 둔다.

1. **한 작업에 필요한 루프를 필요한 만큼 조합한다.** O + I만 쓰는 작업, O + C + A만 쓰는 작업, A만 쓰는 작업이 모두 정상이다.
2. **기본 조합은 계획일 뿐이다.** 상황 유형([05](05-situation-types.md))에 따라 기본 조합을 제안하지만, 어느 루프에서든 다른 어느 루프로든 전환할 수 있다.
3. **전환은 기록된다.** 어디서 어디로, 왜 옮겼는지를 루프 전환 레코드로 남긴다. 모델이 정해서 옮긴 것은 혼자 정한 결정으로 다루며 사람이 이의를 걸 수 있다.
4. **코드가 막는 것은 의존 규칙뿐이다.** 조합과 전환은 자유롭되, [§5](#5-의존-규칙)의 몇 가지 의존 관계만 커널이 강제한다.

## 2. 다섯 루프

v0.3은 v0.2의 네 루프(O, I, C, A)에 구조 루프(S)를 더한다.

| 루프 | 목표 | 다루는 대상 | 주로 쓰는 칸 |
|---|---|---|---|
| O 상황 파악 | 지금 무슨 일이 있는지, 어떤 종류의 상황인지 안다 | Concern의 현재 상태 | 세 칸을 읽음, 상황 판정을 씀 |
| I 탐구 | 사실, 원하는 것, 가능성, 결과를 밝힌다 | Concern의 내용 | E에 씀, N에 제안 |
| C 약속과 실행 | 정한 것을 실행하거나, 모르는 것을 작게 시도한다 | WorkUnit | N에 합의, M을 바꿈 |
| A 확인과 반영 | 결과를 확인하고, 전체와 맞추고, 돌아본다 | 결과 | M을 N과 비교, E 갱신, P 수정 제안 |
| S 구조 [제안] | Concern을 나누고, 합치고, 다시 배치한다 | Concern 트리 | N의 구조 |

O, I, C, A는 **Concern 하나의 안쪽**에서 일하고, S는 **Concern들의 구조**에서 일한다.

## 3. 루프별 상세

### 3.1 O: 상황 파악

**하는 일**

- 무엇이 변했는지, 왜 중요한지, 개입하지 않으면 무엇이 일어나는지 파악한다.
- 사람이 돌아왔을 때 복귀 요약을 만든다.
- **상황 판정** [제안]: 이 Concern이 명확, 복잡, 복합, 혼돈, 혼란 중 어디에 해당하는지 판정하고 근거와 함께 기록한다([05](05-situation-types.md)).
- 문제를 정의하는 Frame 단계는 O와 I의 경계에 있다.

**입력**: 기록(ledger), 외부 상태, 사람의 새 요청

**산출**: 복귀 요약(투영), 상황 판정 레코드, 루프 계획 제안

**종료 조건**: 상황 유형이 판정되고, 다음 루프가 정해짐

**10단계 대응**: Sense, Frame

### 3.2 I: 탐구

**하는 일**: 네 종류의 탐구 중 필요한 것을 수행한다. 자세한 내용은 [04](04-inquiry-types.md)에 있다.

| 탐구 | 묻는 것 |
|---|---|
| 사실 탐구 | 무엇이 그런가 |
| 원함 탐구 | 무엇을 원하는가 |
| 가능성 탐구 | 무엇이 될 수 있는가 |
| 결과 탐구 | 하면 무엇이 일어나는가 |

**입력**: Concern, 관련 관찰, Goal과 선호 모델

**산출**: 판단, 선호 모델, 가능성 목록, 예측, 문제 정의 패킷, 질문

**종료 조건**: 탐구 종류별 멈춤 조건([04](04-inquiry-types.md)) 또는 예산 소진. 예산이 먼저 소진되면 열린 질문을 그대로 넘긴다.

**10단계 대응**: Diverge, Investigate, Deliberate

### 3.3 C: 약속과 실행

v0.3에서 C는 두 가지 변형을 가진다.

#### 약속형 C (v0.2의 C)

정한 것을 실행한다.

- 작업 합의: 무엇을 왜, 어디까지, 어떤 근거와 함께 제출하는지, 언제 멈추는지
- 합의 안에서 WorkUnit 실행
- 범위를 벗어나면 멈추고 선택 요청이나 탐구로 돌아감

**종료 조건**: 결과 제출

#### 탐침형 C [제안]

결과를 모르는 상태에서 작게 시도한다. 복합 상황([05](05-situation-types.md))에서 주로 쓴다. Snowden은 복합 상황에서 실패해도 괜찮은 실험을 여러 개 동시에 하고, 시작하기 전에 키울 조건과 접을 조건을 정해 두라고 한다.

- 탐침 레코드: 확인하려는 가설, 키울 조건, 접을 조건, 예산
- 여러 탐침을 동시에 실행할 수 있음
- 결과는 판단이 아니라 관찰로 기록되고, 다시 I나 A로 넘어감

**종료 조건**: 키울 조건이나 접을 조건 충족, 또는 예산 소진

약속형과 탐침형의 차이는 다음과 같다.

| 항목 | 약속형 C | 탐침형 C |
|---|---|---|
| 시작 시점 | 무엇을 할지 정한 뒤 | 무엇이 될지 모르는 상태 |
| 개수 | 보통 하나 | 여러 개 동시에 |
| 실패의 의미 | 문제가 생긴 것 | 정보를 얻은 것 |
| 다음 단계 | A의 결과 확인 | I로 돌아가거나, 잘된 탐침을 약속형 C로 키움 |

#### 비상 합의 [제안]

혼돈 상황에서는 합의를 맺을 시간이 없다. 그래서 **미리 맺어 둔 합의**를 둔다. 예를 들어 "프로덕션 장애가 나면 직전 배포로 롤백하는 것까지는 묻지 않고 해도 된다" 같은 것이다.

- 비상 합의는 평상시에 사람이 확정해 둔다.
- 비상 합의에 따른 실행도 기록되며, 안정된 뒤 사후 검토 대상이 된다.
- 비상 합의 범위를 넘는 행동은 여전히 선택 요청 대상이다.

**10단계 대응**: Commit, Execute

### 3.4 A: 확인과 반영

v0.3에서 A도 두 가지 변형을 가진다.

#### 확인형 A (v0.2의 A)

- 결과 제출 → 결과 확인 → 전체 반영 → 돌아보기
- 결과 확인은 사람만 할 수 있다 (A6). 제품 소유자가 든 이유는 두 가지다.
  1. 결과를 받아들이는 것은 그 결과에 책임을 지는 일이고, 책임을 지는 주체는 사람이다.
  2. 작업한 모델이 자기 결과를 확인하면 같은 실수를 같은 방식으로 반복한다. 검증 에이전트를 새 컨텍스트에서, 가능하면 다른 모델로 돌리는 것도 같은 이유다([08 §9](08-runtime-architecture.md)).
- 결과 확인과 전체 반영은 보는 것이 다르다. 결과 확인은 "명세대로 만들었는가"를 본다. 전체 반영은 "다른 관점, 다른 화면, 다른 사람의 작업에서도 맞는가", 즉 올바른 것을 만들었는가를 본다.
- 근거는 실제 관찰을 참조해야 한다.
- 반영 항목이 남아 있으면 "결과 확인됨"이고 "완료"가 아니다 (A10).

#### 지속 관찰형 A [제안]

복합 상황에는 미리 정한 완료 기준이 없다. 결과를 받아들이거나 거절하는 대신, 내보낸 뒤에도 계속 지켜보면서 잘되는 쪽을 키우고 안 되는 쪽을 접는다.

- 관찰할 신호와 기간을 정함
- 기간 동안 관찰을 모음
- 키우기(약속형 C로), 접기, 계속 관찰 중 하나를 고름

#### 취향형 작업의 확인 [제안]

취향이 정답인 작업은 근거로 확인할 정답이 없다. 이때 확인은 선호 모델과의 일치 여부를 사용자가 판정하는 것이며, 불일치가 나오면 원함 탐구로 돌아간다. "대안 2~3개 중 고르기"로 확인을 대신하지 않는다([04 §3](04-inquiry-types.md)).

#### 돌아보기 (Reflect)

- 다음에 무엇을 다르게 할지 한 줄 남김
- 반복해서 같은 방식으로 풀린 작업은 절차나 스크립트로 바꿀 후보가 된다. 이렇게 복잡 상황이 명확 상황으로 옮겨진다([05 §5](05-situation-types.md)).
- 관찰 에이전트가 기록을 모아 정책(P) 수정안을 제안한다.

**10단계 대응**: Assure, Integrate, Reflect

## 4. S: 구조 루프 [제안]

### 4.1 왜 따로 루프로 두는가

Concern을 나누는 일은 v0.3 논의에서 처음에 "혼란 상황의 O 단계"로 제안되었다. 하지만 실제로는 어느 루프에서든 필요해진다.

| 어디서 | 예 |
|---|---|
| O | 혼란 상황에서 문제가 여러 유형의 부분으로 섞여 있음 |
| I | 탐구해 보니 문제가 사실 서로 다른 두 문제였음 ("느리다"와 "찾기 어렵다") |
| C | 실행 중 범위가 커져서 하나의 합의로 감당하기 어려움 |
| A | 반영하다가 새로운 문제를 발견함 |
| 거시 | 여러 Concern이 사실 같은 문제임 |

그리고 이 일은 다른 루프와 같은 성질을 가진다.

- 자기 입력이 있다: Concern과 그 내용
- 자기 산출이 있다: 하위 Concern, 합쳐진 Concern, 그 사이의 연결
- 자기 종료 조건이 있다: 각 부분이 독립적으로 다룰 수 있는 크기와 유형이 됨
- 되돌리는 동작이 필요하다: 나눈 것은 나중에 다시 합쳐서 상위에 반영해야 함

그래서 하나의 단계가 아니라 **어느 루프에서든 호출할 수 있는 별도 루프**로 둔다. O, I, C, A는 Concern 하나의 안쪽을 다루고, S는 Concern들의 구조를 다룬다.

### 4.2 S가 하는 동작

| 동작 | 뜻 | 예 |
|---|---|---|
| 분해 | 하나의 Concern을 여러 하위 Concern으로 나눔 | "첫 화면 문제" → "요청 순서 문제" + "찾기 어려움 문제" |
| 병합 | 여러 Concern을 하나로 합침 | 두 Concern이 같은 원인임을 발견 |
| 독립 | 하위 Concern을 상위에서 떼어 독립 Concern으로 만듦 | 하위 문제가 원래 목표와 무관하게 중요해짐 |
| 재배치 | Concern을 다른 Goal 아래로 옮김 | 다른 프로젝트의 문제였음 |
| 재조합 | 하위 Concern들의 결과를 모아 상위에 반영 | 나눈 문제들이 모두 풀린 뒤 전체 확인 |
| 보류·닫기 | 지금 다루지 않기로 하거나 종료 | 우선순위에서 밀림 |

### 4.3 규칙

1. **상위 연결을 잃지 않는다.** 모든 하위 Concern은 상위 Concern과 Goal에 대한 연결을 가진다 (A1).
2. **하위가 모두 반영돼야 상위가 끝난다.** 분해한 Concern은 하위 결과를 재조합해서 확인하기 전까지 완료되지 않는다 (A10).
3. **하위의 상황 유형은 따로 판정한다.** 분해의 주된 목적 중 하나가 유형이 다른 부분을 나누는 것이다.
4. **경계를 기록한다.** 나눌 때 부분 사이에 걸치는 것(공유 전제, 서로 영향을 주는 결정)을 경계 항목으로 남긴다. 나누면 경계 사이의 문제가 누락되기 쉽기 때문이다. 시스템 공학의 인터페이스 관리와 같은 원리다.
5. **분해와 병합은 혼자 정한 결정으로 기록한다.** 사람이 이의를 걸 수 있다.
6. **깊이와 개수에 상한을 둔다.** 한 Concern 아래 하위 Concern 수와 트리 깊이에 기본 상한을 두고, 넘으면 선택 요청을 연다. 재난 대응 체계(ICS)의 관리 가능 범위(span of control) 원리를 참고한다.

### 4.4 실패 유형과 대응

| 실패 | 증상 | 대응 |
|---|---|---|
| 과분해 | 조각이 너무 많아 전체가 안 보임 | 개수 상한, 복귀 요약에서 트리를 접어서 보여줌 |
| 맥락 소실 | 하위에서 상위의 목적을 잊음 | 하위 Concern의 투영에 상위 Goal과 경계 항목을 항상 포함 |
| 경계 누락 | 나눈 부분 사이에서 생기는 문제를 아무도 다루지 않음 | 경계 항목 기록, 재조합 단계의 확인 |
| 재조합 생략 | 하위가 끝났는데 상위를 확인하지 않음 | 상위 완료 조건에 재조합 확인 포함 |

### 4.5 거시 루프와의 관계

v0.2에서 "거시 루프"라고 부른 것(여러 Concern 사이의 주의 배분, 복귀 요약, 다시 볼 조건 감시)은 S 루프의 Goal 수준 실행과 주의 배분 스케줄러를 합친 것으로 볼 수 있다.

### 4.6 참고한 방법 [Helm 내부 자료: Method Transfer 지도]

- Viable System Model (지도 #32): 자율적인 하위 단위가 재귀적으로 같은 구조를 가지면서 전체 응집성을 유지함
- Incident Command System (#18): 관리 가능한 범위, 목표 단위 조직
- NASA Systems Engineering (#23): 논리적 분해, 요구 추적, 인터페이스 관리, 통합

## 5. 의존 규칙

조합과 전환은 자유롭다. 커널이 강제하는 것은 다음 의존 관계뿐이다. 표시는 행마다 붙인다.

| 규칙 | 뜻 | 예외 | 표시 |
|---|---|---|---|
| write나 send를 하려면 C가 있어야 한다 | 실제를 바꾸거나 밖으로 보내려면 작업 합의가 필요 | C는 짧게 압축될 수 있음. 혼돈 상황의 비상 합의 | [결정] |
| "완료"라고 하려면 A를 거쳐야 한다 | 완료 주장, 확인, 반영의 구분 | 없음 | [결정] |
| 판단으로 올리려면 I의 근거가 있어야 한다 | 추측이 저절로 사실이 되지 않음 | 없음 | [결정] |
| 하위 Concern이 있는 Concern은 재조합 확인 후에 닫힌다 | 구조 루프의 규칙 | 사람이 명시적으로 닫는 경우 | [제안] |
| Goal을 바꾸려면 사람이 확인해야 한다 | 방향의 저자는 사람 | 없음 | [제안] |

Goal은 Concern 사이클을 거치며 정제되므로([02 §3](02-core-concepts.md)), 작은 정제까지 매번 사람 확인을 요구하는 5행은 너무 엄격할 수 있다.

어느 루프에서든 다음 계기가 생기면 다른 루프로 전환할 수 있다. v0.2 운영 이론 §5의 재진입 규칙 여섯 개를 포함한다.

| 계기 | 보통의 전환 | 출처 |
|---|---|---|
| 새로운 놀라운 관찰 | O → I | v0.2 |
| 탐구 중 목적 충돌 발견 | I → N 재개방 (Goal 수정 제안) | v0.2 |
| 실행 중 권한 밖 문제 | C → I 또는 선택 요청 | v0.2 |
| 확인 중 근거 부족 | A → I (탐구 WorkUnit) | v0.2 |
| 반영 중 공유 전제 충돌 | A → 관련 결정과 컨텍스트 무효화 | v0.2 |
| 돌아보기 결과 | A → P 수정 제안 | v0.2 |
| 상황 유형 변경 | 어디서든 → O (재판정) | v0.3 |
| 명확 상황에서 예상 밖 결과 | A → O (재판정) | v0.3 |
| 결과 확인에서 해결되지 않았다고 판정됨 | A → I (문제 정의 다시 보기) | v0.3 |
| 결과 확인에서 수정 요청 | A → C (합의를 유지한 채 진행 중으로) | v0.3 |
| 탐침이 키울 조건 충족 | 탐침형 C → 약속형 C | v0.3 |
| 탐침이 접을 조건 충족 | 탐침형 C → I | v0.3 |
| 문제가 둘 이상으로 나뉨 | 어디서든 → S (분해) | v0.3 |
| 여러 Concern이 같은 문제 | 어디서든 → S (병합) | v0.3 |
| 기대 기한 초과 (응답 없음 관찰) | 대기 → O 또는 I | v0.3 |
| 선호 모델 변경 | 어디서든 → A (기존 결과 재확인) 또는 I | v0.3 |

| 사용자의 직접 지시 | 지시한 루프로 | v0.3 |

## 7. 외부 행위자와 대기

### 7.1 외부 응답은 관찰이다 [결정]

메일 답장, 회의 결정, 다른 사람의 리뷰 같은 외부 응답은 별도 루프 없이 **출처가 외부 행위자인 관찰**로 기록한다. 탐구 중에 발견된 새로운 사실과 같은 방식으로 처리된다. 내용은 관찰이 아니라 "그 사람이 그렇게 말했다"가 관찰이다([02 §2.3](02-core-concepts.md)).

### 7.2 응답이 없는 것은 관찰되지 않는다 [제안]

요청을 보냈는데 답이 오지 않으면 아무 일도 일어나지 않고, 기록에도 아무것도 남지 않는다. 그래서 외부에 요청할 때 **기대 레코드**를 남긴다.

```yaml
expectation:
  id: EXP-4
  to: "디자인 리뷰어"
  what: "필터 화면 시안에 대한 의견"
  sent_at: 2026-10-11T10:00
  due: 2026-10-13T18:00
  on_timeout: observation("응답 없음")
  linked_concern: F-07
```

기한이 지나면 타이머가 "응답 없음"이라는 관찰을 만든다. 이렇게 하면 응답이 오지 않은 것도 관찰이 되어, 외부 응답을 관찰로 다루는 원칙이 그대로 유지된다.

## 8. 루프 계획과 전환의 기록

### 8.1 루프 계획

```yaml
loop_plan:
  concern: F-12
  situation: complex
  default_combo: [O, I.want, C.probe, A.watch, C.commit, A.confirm]
  reason: "블로그 방향은 취향이 정답이고 미리 분석할 수 없음"
  proposed_by: agent
  autonomous: true      # 사람에게 묻지 않고 정함 → 이의 가능
```

### 8.2 루프 전환

```yaml
loop_transition:
  concern: F-12
  from: C.probe
  to: S.split
  reason: "탐침 결과, '글 주제'와 '글 형식'이 서로 다른 선호 기준을 가짐"
  trigger: OBS-31
  autonomous: true
```

## 9. 예시 흐름

### 9.1 취향형 작업: 블로그 글 방향 잡기

```text
O        상황 판정: 복합 (취향이 정답, 미리 분석 불가)
I.want   서로 다른 방향의 글 도입부 6개를 자극으로 제시 (다른 분야 레퍼런스 포함)
         요소 단위 반응 수집 → 선호 기준 후보 3개
C.probe  기준을 확인할 짧은 초안 3개를 동시에 작성 (키울 조건: 사용자가 이어 쓰고 싶다고 함)
S.split  반응을 보니 '주제'와 '형식'의 선호가 따로 움직임 → 하위 Concern 둘로 분해
I.want   각각 원함 탐구 계속 → 선호 모델 안정
C.commit 선호 모델을 완료 기준으로 한 작업 합의, 본문 작성
A.confirm 사용자가 선호 모델과의 일치를 확인
S.recombine 두 하위 Concern의 결과를 합쳐 상위 확인
A.reflect 선호 모델을 Goal에 연결 → 다음 글에서 재사용
```

### 9.2 혼돈에서 시작하는 작업: 배포 후 장애

```text
C.emergency            직전 배포로 롤백 (비상 합의)
O                      상황 재판정: 혼돈 → 복잡 (안정됨, 원인 분석 가능)
I.fact                 원인 탐구
I.outcome              재배포 계획의 결과 탐구 (사전 부검)
C.commit               수정 후 재배포
A.confirm              확인
A.reflect              비상 합의와 배포 절차 수정 제안 → 다음엔 명확 상황으로 처리 가능
```
