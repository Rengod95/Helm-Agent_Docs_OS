# 02. 핵심 개념

이 문서는 v0.3에서 쓰는 개념을 정의한다. v0.2와 같은 개념은 짧게 적고, 바뀌거나 새로 생긴 개념을 자세히 적는다.

## 1. 세 의미 세계: N, E, M

일하면서 적는 모든 기록은 세 칸 중 하나에 들어간다.

| 칸 | 이름 | 뜻 | 예 |
|---|---|---|---|
| N | 방향 (Normative) | 하기로 한 것, 지켜야 할 것, 원하는 것 | Goal, 완료 기준, 선택, 작업 합의, 선호 모델 |
| E | 이해 (Epistemic) | 안다고 생각하는 것과 모르는 것 | 관찰, 추측, 판단, 근거, 예측, 열린 질문 |
| M | 실제 (Material) | 실제로 존재하거나 바뀐 것 | 파일, 실행 기록, 보낸 메일, 배포된 상태 |

### 1.1 관찰은 M이 아니라 E다

자주 헷갈리는 지점이다. "네트워크 탭을 보니 API 응답이 평균 2초였다"는 M이 아니라 E다.

- M은 세상 그 자체다. API 서버가 실제로 응답하는 데 걸리는 시간이 M이다.
- E는 그것에 대해 내가 알게 된 것이다. "내가 본 바로는 2초였다"는 기록이 E다.

둘은 어긋날 수 있다. 2초는 측정한 컴퓨터의 네트워크 탓이었을 수 있다. 코드를 고쳐서 M이 바뀌면 "2초"라는 E는 낡은 정보가 된다.

### 1.2 세 칸의 관계 (v0.2 유지)

```text
E justifies N    근거와 판단이 선택을 정당화한다
N authorizes M   선택과 작업 합의가 변경을 허가한다
M updates E      실행 결과가 믿음과 가설을 바꾼다
M fulfills N     결과가 목표와 약속을 충족한다
```

v0.3에서 하나를 더한다.

```text
E reveals N      자극에 대한 반응(관찰)에서 원하는 것(방향)을 알아낸다
```

원함 탐구([04 §3](04-inquiry-types.md))가 이 관계를 다룬다. 사용자의 반응은 E에 관찰로 기록되고, 그 관찰에서 추론한 선호가 N의 선호 모델과 완료 기준으로 올라간다.

## 2. 이해의 단계: 관찰 → 추측 → 판단

E 칸 안에서 기록은 단계를 가진다.

| 단계 | 뜻 | 누가 만드는가 |
|---|---|---|
| 관찰 | 직접 보거나 도구로 확인한 것 | 런타임(도구 실행 결과), 사람의 발화, 외부 행위자의 응답 |
| 추측 | 관찰을 해석하거나 설명하는 것. v0.2의 해석(Interpretation)과 가능성(Possibility)을 묶은 말 | 모델, 사람 |
| 판단 | 현재 근거 안에서 참으로 받아들인 것 | 승격 규칙을 통과했을 때만 |

- "추측"은 설명을 위해 묶어 부르는 이름이다. 레코드 종류로는 해석(Interpretation)과 가능성(Possibility)을 계속 구분한다([§8.1](#81-기존-레코드-v02-유지)).
- 이 문서 묶음에서 "판단"은 Finding만 가리킨다. 일반적인 뜻으로는 "판정"이나 "결정"을 쓴다.
- 선택은 판단에서 자동으로 나오지 않는다. 추천도 선택이 아니며, 사람이 고르거나 맡긴 범위 안의 정책이 적용될 때만 선택이 된다.

### 2.1 핵심 규칙: 추측은 저절로 판단이 되지 않는다

에이전트는 자기가 쓴 추측을 다음 턴에 사실처럼 읽는 경향이 있다. 그래서 추측이 판단으로 올라가려면 다음 조건을 모두 만족해야 한다.

1. 근거가 있다. 근거는 모델이 쓴 문장이 아니라 실제 관찰(도구 실행 결과 등)이다.
2. 근거 중 적어도 하나는 구분 확인이다. 구분 확인은 경쟁하는 추측이 맞았다면 다른 결과가 나왔을 관찰이다([§2.2](#22-구분-확인)).
3. 반대 근거를 찾아봤다. "찾아보지 않아서 없는 것"과 "찾아봤는데 없는 것"은 다르다.
4. 찾아본 결과 추측과 맞지 않는 관찰이 없다.
5. 결정에 쓰이는 판단이라면 사람이 확인한다.

### 2.2 구분 확인

추측을 확인할 때는 **결과가 추측에 따라 달라지는 관찰**을 고른다. "캐시가 없어서 느리다"는 추측을 확인하려고 "캐시 코드가 없다"를 관찰해도, 원인이 DB 쿼리여도 캐시 코드는 똑같이 없다. 이런 관찰은 추측을 구분해 주지 못한다. 반면 "응답 2초 중 DB 쿼리가 1.8초"는 원인에 따라 결과가 달라지므로 쓸모 있는 확인이다.

### 2.3 외부에서 온 말

외부 행위자의 말은 내용이 아니라 "그렇게 말했다"는 것이 관찰이다. 고객이 "다음 주까지 됩니다"라고 했다면 관찰은 "고객이 다음 주까지 된다고 말했다"이고, "다음 주까지 된다"는 추측이다.

## 3. Goal [결정]

### 3.1 정의

Goal은 **프로젝트 단위의 궁극 목표**다. 한 번 정하고 끝나는 값이 아니라, 반복되는 Concern 사이클을 거치며 계속 다듬어지는 프로젝트의 기반이다.

v0.2 정제 문서의 C7 항목은 Purpose가 초기화할 때 한 번 저장되고 바뀌지 않는 것을 모순으로 지적했고, "Goal은 versioned normative entity"라는 방향만 제시했다. v0.3은 이 방향을 받아 Goal이 어떻게 다듬어지는지를 정한다.

### 3.2 Goal이 가지는 것

| 항목 | 설명 |
|---|---|
| 서술 | 이루려는 것을 한두 문장으로 |
| 성공 조건 | 무엇이 되면 이뤄졌다고 볼 것인가 |
| 보존 제약 | 이루는 과정에서 잃으면 안 되는 것 |
| 선호 모델 연결 | 원함 탐구로 찾은 기준과 무게 ([§8.2](#82-새-레코드-v03)) |
| 상위·하위 Goal | 큰 Goal 아래 작은 Goal |
| 버전 이력 | 언제, 어떤 Concern에서, 무엇이, 왜 바뀌었는가 |

### 3.3 Goal이 다듬어지는 경로

```text
Concern에서 탐구 → 원하는 것이나 사실을 새로 알게 됨
  → Goal 수정 제안 (goal.revise.proposed)
  → 사람이 확인 (goal.revised) 또는 거절
  → 새 버전의 Goal이 이후 Concern과 작업 합의의 기준이 됨
  → 이전 버전에 기대던 작업 합의와 컨텍스트는 다시 확인 대상이 됨
```

Goal의 변경은 항상 사람이 확인한다. 모델은 수정을 제안만 한다. 이 규칙은 [03 §5](03-loops-and-transitions.md)의 의존 규칙 5행이며 [제안] 상태다.

### 3.4 Goal 이벤트

| 이벤트 | 뜻 |
|---|---|
| goal.proposed | 새 Goal 제안 |
| goal.revise.proposed | 수정 제안. 근거가 된 Concern과 관찰을 참조 |
| goal.revised | 사람이 수정을 확인함. 새 버전 생성 |
| goal.split | 하나의 Goal을 여러 하위 Goal로 나눔 (구조 루프) |
| goal.paused | 잠시 멈춤 |
| goal.superseded | 다른 Goal로 대체됨 |
| goal.achieved.claimed | 이뤄졌다는 주장 |
| goal.achieved.accepted | 사람이 이뤄졌음을 확인함 |

## 4. Concern [결정]

### 4.1 정의

Concern은 **10단계 과정(Sense → Frame → … → Reflect)을 돌릴 후보가 되는 상황 그 자체**다. 문제만이 아니라 다양한 상황이 Concern이 될 수 있다.

| 종류 | 예 |
|---|---|
| 문제 | "첫 화면이 느리다는 얘기가 계속 나온다" |
| 기회 | "새 런타임 기능을 쓰면 하네스를 단순하게 만들 수 있을 것 같다" |
| 위험 | "이 의존성이 곧 지원 종료된다" |
| 불확실성 | "이 방향이 맞는지 모르겠다" |
| 취향 결정 | "블로그 글의 방향을 잡고 싶다" |
| 반복 마찰 | "매번 같은 설정을 다시 한다" |
| 외부 요청 | 다른 사람이 맡긴 일 |

v0.2 정의("사람과 agent의 주의와 판단이 필요한 중요한 상황")를 바꾼 이유: "주의가 필요하다"는 Concern이 생기는 이유이고, Concern의 정의가 아니다. v0.3은 Concern을 과정이 적용되는 대상으로 정의한다.

### 4.2 Concern이 가지는 것

| 항목 | 설명 |
|---|---|
| 서술 | 어떤 상황인가 |
| 연결된 Goal | 어느 Goal 아래에 있는가 (A1) |
| 상황 유형 | 명확, 복잡, 복합, 혼돈, 혼란 중 하나. 바뀔 수 있음 ([05](05-situation-types.md)) |
| 루프 계획 | 기본 조합과 현재 위치 ([03](03-loops-and-transitions.md)) |
| 상위·하위 Concern | 구조 루프가 만든 트리 |
| 상태 | 열림, 진행 중, 대기, 결과 확인 대기, 결과 확인됨, 반영 완료, 닫힘, 다시 열림 |

### 4.3 Concern 트리

Concern은 나뉘고 합쳐질 수 있다. 나누고 합치는 일 자체를 **구조 루프(S)**로 다룬다([03 §4](03-loops-and-transitions.md)). 하위 Concern은 상위 Concern과 Goal에 대한 연결을 잃지 않는다.

## 5. WorkUnit

WorkUnit은 **작업 합의 하나 아래에서 실행되는 구체적인 작업**이다. 런타임에서는 내부 에이전트 루프의 실행 1회(또는 그 묶음)에 해당한다.

| 종류 | 하는 일 | 주로 쓰는 루프 |
|---|---|---|
| 탐구 WorkUnit | 조사, 측정, 자료 수집, 자극 생성 | I |
| 탐침 WorkUnit | 결과를 모르는 상태에서 작게 시도 | 탐침형 C |
| 변경 WorkUnit | 결정한 것을 실행 | 약속형 C |
| 반영 WorkUnit | 결과를 다른 작업과 맞추기 | A |

Concern 하나 아래에 여러 WorkUnit이 생길 수 있고, WorkUnit 하나가 여러 Concern에 영향을 줄 수 있다.

## 6. A: 참여자와 능력

### 6.1 A는 능력표다

A는 행위자마다 **어떤 종류의 일을 할 수 있는지**를 정한 고정된 표다. 행위자의 신원("사람인가 아닌가")이 아니라 능력으로 정의한다. 작업 에이전트와 검증 에이전트는 둘 다 사람이 아니지만 할 수 있는 일이 다르기 때문이다.

### 6.2 능력 두 층 [결정]

| 층 | 무엇을 정하는가 | 항목 |
|---|---|---|
| 원시 행동 | 세상에 대해 무엇을 할 수 있나 | read, write, execute, send, spawn, ask |
| 기록 능력 | 기록에 무엇을 쓸 수 있나 | observe, propose, attest, accept, integrate |

자세한 정의와 모드 구성은 [07](07-modes-and-capabilities.md)에 있다.

## 7. P: 상황에 따른 조건

### 7.1 A와 P를 나누는 기준

> 일하는 도중에 상황이 바뀌면 답도 바뀌는가? 바뀌면 P, 언제나 같으면 A다.

| 규칙 | 구분 | 이유 |
|---|---|---|
| 작업 에이전트는 결과를 확인할 수 없다 | A | 어떤 작업이든 항상 같음 |
| 검증 에이전트는 파일을 쓸 수 없다 | A | 금지 문장이어도 항상 같으면 A |
| 작업 에이전트는 합의된 범위 안에서만 쓸 수 있다 | P | 합의가 바뀌면 범위도 바뀜 |
| 결과를 만든 행위자는 그 결과를 증언할 수 없다 | P | 이번 결과를 누가 만들었는지에 따라 달라짐 |

### 7.2 P에 들어가는 규칙 종류

| 종류 | 예 |
|---|---|
| 합의 범위 | 이번 작업 합의가 허용한 대상, 예산, 기한, 멈출 조건 |
| 근거 부담 | 판단으로 올리거나 결과를 확인할 때 필요한 근거의 양 |
| 독립성 | 결과를 만든 행위자는 그 결과를 증언하거나 확인할 수 없음 |
| 질문 전달 | 기본 전달 방식, 즉시로 올리는 문턱 ([06](06-asking-and-interruption.md)) |
| 신선도와 무효화 | 참조한 M이 바뀌면 근거가 낡음 |
| 동시성 | 같은 대상을 두 WorkUnit이 동시에 바꾸지 않음 |
| 비상 합의 | 혼돈 상황에서 미리 허용해 둔 행동 ([03 §3.3](03-loops-and-transitions.md)) |

권한 레이어가 판정하는 위험과 가역성은 P의 입력값으로 들어오지만, 그 판정 자체는 Helm 범위 밖이다([01 §4](01-scope-and-motivation.md)).

| Expectation (기대) | N | 외부에 요청하고 응답을 기다리는 것 | 대상, 내용, 기한, 기한이 지나면 만들 관찰 | [03](03-loops-and-transitions.md) |
| Prediction (예측) | E | 하면 무엇이 일어날지에 대한 예상 | 내용, 근거, 확인할 날짜나 조건, 확인 결과 | [04](04-inquiry-types.md) |
| LoopPlan (루프 계획) | N | 이 Concern에서 쓸 루프 조합 | 기본 조합, 이유, 상황 유형 | [03](03-loops-and-transitions.md) |
| LoopTransition (루프 전환) | E | 한 루프에서 다른 루프로 옮긴 기록 | 출발, 도착, 이유, 계기가 된 관찰 | [03](03-loops-and-transitions.md) |
| SituationAssessment (상황 판정) | E | Concern의 상황 유형 판정 | 유형, 근거, 확신도, 판정 주체 | [05](05-situation-types.md) |
| Probe (탐침) | N | 결과를 모르는 상태의 작은 시도 | 가설, 키울 조건, 접을 조건, 예산 | [03](03-loops-and-transitions.md) |

새 레코드는 위 8종이다. 에이전트가 묻지 않고 정한 선택은 별도 레코드를 두지 않는다. Choice에 `autonomous`, `why_not_asked`, `contestable` 필드를 추가해 표시한다([06 §4](06-asking-and-interruption.md)).

## 9. 품질 상태와 다시 볼 조건 (v0.2 유지, 범위 확장)

### 9.1 품질 상태

```text
absent(없음) → captured(적힘) → structural(형식 갖춤) → qualified(근거 갖춤) → accepted(받아들여짐)
```

옆길 상태가 셋 있다.

- contested: 이의가 걸림
- stale: 참조한 사실이나 실제가 바뀌어 낡음
- superseded: 다른 것으로 대체됨

### 9.2 다시 볼 조건

모든 선택에는 "이게 바뀌면 다시 본다"는 조건을 붙인다(A13). v0.3에서는 다음에도 붙인다.

- 에이전트가 혼자 정한 선택
- 선호 모델의 각 기준 (같은 종류의 작업에서 반대 반응이 나오면 다시 봄)
- 예측 (확인 날짜가 오면 실제 결과와 비교)
- 상황 판정 (예상 밖 결과가 나오면 다시 판정)

### 9.3 자동으로 낡는 경우

근거가 M을 참조할 때 파일 해시나 커밋을 함께 기록한다. 참조한 대상이 바뀌면 그 근거는 자동으로 stale이 된다.

## 10. 이름 정리: Projection과 Method Transfer [결정]

v0.2 문서는 "Projection"을 두 가지 뜻으로 썼다. 그리고 v0.3 논의에서 제품 소유자는 다른 분야의 방법과 사고방식을 지금 문제에 적용하는 개념을 "Projection(투영)"이라고 불렀다. 이 개념은 Helm 자료에 Method Transfer라는 이름으로 이미 있었으므로 그 이름을 쓴다. 세 개념의 이름은 다음과 같다.

| 쓰인 곳 | 뜻 | v0.3 이름 |
|---|---|---|
| v0.2 kernel·아키텍처 문서의 ContextProjection, Projection Runtime | 정본 기록에서 보는 대상과 시점에 맞게 뽑아낸 읽기 전용 화면. Redux의 selector에 해당 | **투영** (그대로 유지, 불변조건 3) |
| v0.2 문서의 상황 인식(Endsley) 3단계 Projection, 복귀 요약의 Changes–Assessment–Projection | 앞으로의 상태에 대한 예상 | **예측(Prediction)**. 결과 탐구의 예측 레코드와 같은 이름 ([04 §5](04-inquiry-types.md)) |
| v0.3 논의에서 제품 소유자가 "Projection(투영)"이라고 부른 개념. Helm 자료의 Method Transfer Map, Method Card (`docs/research/`) | 다른 분야의 방법과 사고방식을 원리 수준에서 뽑아 지금 문제에 적용하는 것 | **Method Transfer** |

"투영"은 첫째 뜻(selector에 해당하는 읽기 전용 화면)으로만 쓴다.

Method Transfer는 v0.2까지 Helm 자체를 설계하기 위한 연구 방법으로만 쓰였다. v0.3에서는 이를 런타임의 가능성 탐구 안에서 사용자의 문제에 적용하는 동작으로 옮긴다([04 §4](04-inquiry-types.md)).
