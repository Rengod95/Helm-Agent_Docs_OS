# Helm v0.3 문서 전수조사 결과

- 조사일: 2026-10-11
- 대상 문서: `helm-v0.3/` 00~14
- 기준: 대화 원문 전체(메시지 [1]~[158])와 2026-10-11 마지막 결정
  - 클라이언트는 웹이 아니다. 자체 데스크톱 앱 또는 SSH + pi + 커스텀 TUI.
  - 외부(원격)에서 연결할 수 있어야 한다.
  - 제품 사용 사례는 "유즈케이스" 또는 "시나리오"로 부른다.
- 방법: 대화를 다섯 구간으로 나눠 구간마다 문서와 대조하고, 별도로 문서끼리의 일관성을 조사했다. 여섯 조사를 병렬로 진행했다.
- 분류: 반영 / 부분 반영 / 누락 / 충돌 / 범위 밖
- 문서는 아직 수정하지 않았다.

## 0. 요약

1. **최신 결정과 충돌하는 곳이 12, 13, 14, 10, 09에 걸쳐 있다.** 웹 클라이언트 전제, 원격 접속을 범위 밖에 둔 것, 14의 프로세스 배치(서버가 pi를 품는 구조)가 해당한다.
2. **사용자가 직접 말하거나 동의한 내용 중 빠지거나 다르게 적힌 것이 있다.** "C와 A를 가장 많이 건너뛴다"는 답, "pi 안에서 Helm을 구현" 질문, 질문 조건을 AND/OR 중 고르게 하자는 제안, 관찰 에이전트 C, "기획이 먼저" 판단, "취향이 정답인 작업에서 출발"이 해당한다.
3. **대화에서 길게 설계했지만 문서에 옮기지 않은 덩어리가 여럿 있다.** 발산 서브시스템, 관찰 에이전트 C, 공리 A1~A15 전체 대응표, 벤더 중립 원칙, pi 안의 Helm 구조, 프로세스 배치 A/B/C가 대표적이다.
4. **기술 전제가 틀린 곳이 있다.** codemode 변수는 스크립트 한 번이 끝나면 사라지고 채팅 모델 하위 호출이 없다. bash로 파일을 바꾸면 합의 범위 검사를 지나친다.
5. **표시·숫자·참조·용어가 맞지 않는 곳이 많다.** 사용자가 정하지 않은 [결정] 표시, 레코드와 다이얼 개수, 끊긴 참조 6건, 루프 식별자 표 부재가 해당한다.
6. 금지 표현('축', '박다', '가른다', '닿다', "사용 장면")은 문서에 없다. 가벼운 의인화가 7곳 남아 있다.

## 1. 최신 결정과 충돌하는 곳 (먼저 고칠 것)

### 1.1 웹 클라이언트 전제

| 문서 | 위치 | 내용 |
|---|---|---|
| 12 | 머리말 스택, §1.1, §2 구조도, §3 `apps/helm-web`, §11, §13 Playwright, §14 M3, §15-1 | helm-web(Vite + React 18 CSR)을 전제로 한다. M3 완료 기준이 "브라우저에서 흐름 수행, 새로고침 후 복원"이고, §15-1은 웹 우선을 제안한다 |
| 13 | §1, §2.4, §3.3, §4, §5-3 | assistant-ui를 클라이언트로 전제한다 |
| 14 | §1, §2 구조도, §5 전체, §5.1 "Vite + React 18 CSR", §7, §8 마지막 행 | 구조도 맨 위가 helm-web이다 |
| 10 | §4.3-12 | "TUI로 먼저인가, 웹으로 먼저인가"를 아직 열린 질문으로 둔다 |
| 09 | §4 전체 | 버튼, 패널, "자극의 특정 부분을 골라 반응" 같은 GUI 서술만 있고, TUI에서 어떻게 할지는 없다 |

수정 방향:
- 클라이언트 서술을 "데스크톱 앱 또는 SSH + pi + 커스텀 TUI"로 바꾼다.
- assistant-ui는 데스크톱 앱을 웹뷰로 만들 때만 다시 쓸 수 있고, TUI 경로에서는 쓸 수 없다고 적는다.
- 09에 클라이언트 형태별 메모를 둔다. 예: TUI에서 요소 단위 반응은 줄 번호나 구간을 지정하는 명령으로 받는다.

### 1.2 원격 접속

- 12 §1.2는 "원격 배포, 인증"을 범위 밖에 둔다. 12 §2는 로컬 단일 프로세스와 `~/.helm`을 전제로 한다.
- 대화 [157]의 비기능 요구 초안도 "로컬 전용 보안"이었다.
- 수정 방향: 원격 접속과 인증을 범위 안으로 옮긴다. 접속 경로(SSH로 원격 호스트의 pi + TUI 실행, 데스크톱 앱이 원격 Helm 데몬에 인증된 암호화 연결로 접속)와 인증 방식은 기획 문서에서 정한다. 여러 사용자는 개인용 전제대로 범위 밖에 둔다.

### 1.3 프로세스 배치와 "기획 먼저"

- 14의 구조는 대화 [157]의 배치 A(Helm 서버가 pi SDK 세션을 품음)에 해당한다.
- 14 §3.4는 "pi 터미널 UI로 같은 세션을 열 수 없다"를 남는 한계로 적는다. SSH + pi + TUI 경로에서는 이것이 바로 막히는 지점이다.
- 14 §3.2 (b) 메모리 세션 방식은 pi 세션 파일을 남기지 않는다. pi를 사용자가 직접 실행하는 경로, 그리고 pi 세션 파일을 읽는 관찰 에이전트와 맞지 않는다.
- README §3은 14를 "현재 권고 경로"라고 적는다. 대화 마지막에서는 배치 C(Helm 데몬 + 붙었다 떨어지는 런타임)가 원래 목표에 더 가깝다고 보았고, 사용자는 기획·아키텍처를 먼저 하자고 했다.
- 다음 내용은 문서 어디에도 없다.
  - 배치 A/B/C 비교와 기준 여섯 가지
  - 배치 C의 대가(도구 호출마다 데몬에 묻기, 데몬이 꺼졌을 때의 정책)
  - 선행 작업 7개(유즈케이스, 진입점, 프로세스 배치, 저장소 소유와 기록 경계, 런타임 어댑터 계약, MVP 범위, 비기능 요구)와 ADR 형식
  - 사용자에게 물은 질문 3개(진입점, 사람이 없을 때 실행, 다른 런타임 연결 시기)
- 00 §6, 10 §5, 12 §14, 14 §8은 다음 단계를 구현이나 스파이크로 적는다.

수정 방향: 새 기획 문서(15)에 위 내용을 옮기고, 00 §6 첫 항목을 "구현 전에 기획·아키텍처 결정을 먼저 확정한다"로 바꾼다. README의 "현재 권고 경로" 표기는 배치 결정 전까지 보류로 바꾼다.

### 1.4 "pi 안의 Helm" 설계 누락

사용자가 "helm을 별도 엔진으로 두지 않고 pi 런타임 내에서 구현할 수 있나"를 물었고, 대화에서 다음을 설계했다. 최신 결정(SSH + pi + 커스텀 TUI)에 가장 가까운 구조인데 문서에는 08 §11에 한 줄만 있다.

- 프로세스는 하나, 코드는 둘(순수 core 모듈 + pi 확장 어댑터). 정본은 `.helm/ledger.jsonl`
- Helm 기능과 pi 확장 지점 대응표: `tool_result`, `input`, `before_agent_start`, `setActiveTools`, `registerTool`, `tool_call`, `agent_before_settle`, `ctx.ui`, `setWidget`, `registerCommand`(/focus /brief /agree /accept /reopen), `session_start`, `session_before_compact`, `ctx.newSession`
- 이점: 컴팩션을 Helm 투영으로 대체, 분기마다 branch id를 붙이고 채택된 분기만 판단으로 승격
- 한계: 세션이 열려 있어야 동작, bash로 ledger를 고칠 수 있음(해시 체인 필요), 파일 락, API 변화. 별도 프로세스가 필요한 경우 두 가지
- 구현 순서: core → C/A 어댑터 → 최소 터미널 클라이언트 → O, I, 거시
- pi-durable에는 TUI가 없으므로 pi-tui + watchEvents + viewState로 터미널 클라이언트를 만드는 경로(예제 26, 27, 28)

수정 방향: 14 또는 15에 "배치 B: pi 확장 안의 Helm" 절로 넣고, 배치 C와 비교한다.

### 1.5 12와 13의 갱신 표시

- 12 머리말에 "14와 2026-10-11 결정으로 갱신됨" 표시가 없다.
- 13의 갱신 표시는 §2.4와 §5만 가리킨다. §1의 pi coding agent 행("주 경로로 부적합")과 §2.2도 14와 맞지 않는다.
- 12 §14 M8은 pi coding agent를 두 번째 어댑터로 두고, 14 §7은 반대로 pi-durable을 두 번째로 둔다. 14 §7 변경표에 M3, M8 행과 helm-permission, helm-protocol 패키지가 없다.
- 08 §11 후보 런타임 표에 14 경로가 없다.

## 3. 대화에서 설계했지만 문서에 없는 덩어리

### 3.1 발산 서브시스템 ([46]~[49])

대화에서는 하나의 서브시스템으로 설계했는데, 문서에서는 04의 탐구 네 종류로 흩어지면서 다음이 빠졌다.

- 개입 게이트 뒤의 단계: 앵커링(확실한 것, 모호한 것, 암묵 가정 분리) → 다섯 방향 발산 → 대비 압축 → 반응을 N 평면 전이로 기록 → 정지 규칙
- 다섯 방향 중 위로(목적 사다리: "이게 이뤄지면 무엇이 좋아지나?"), 뒤집기("무엇이 실패·후회하게 만드나")를 발산 자극으로 쓰는 것
- 대비 압축 형식: 결과가 갈리는 프레임 2~3개를 "X를 원하면 A를 얻고 B를 잃는다"로 보여 주고, 정보 가치가 가장 큰 질문 하나만 묻는다. 트리가 아니라 대비로 보여 주는 이유("이쪽은 이걸 잃는데 괜찮으세요?"에는 바로 반응할 수 있음)
- 정지 규칙: "내 답이 계획을 더 바꾸지 않으면 C로". 03 §6 전환 표에도 행이 없다
- 반응 기록: goal.revise / concern.reframe / choice.commit 전이. `concern.reframe` 이벤트가 없다
- 같은 모델 발산의 메아리를 막는 대책 세 가지 중 근거 필수만 있다. 그마저 약해져 04 §4.4는 근거 없는 가지에 "추측" 표시만 붙여 보여 준다. 가지마다 다른 모델 쓰기, 개인의 선택·기각 이력을 다음 발산에 넣기가 빠졌다(04 §3.4 선호 모델은 Goal 단위만 다룬다)
- 발산 가지에 대한 적대적 검증(별도 컨텍스트의 반대 검토)
- 진입 계기 세 번째: 관찰 에이전트가 감지한 잦은 정정. 정정 발화("아니, 그게 아니라")를 모아 문제 정의 오류를 집계하고 진입 기준과 평가 지표로 쓰는 것
- 설계 우선순위: "발산은 쉽고 어려운 것은 수렴과 평가"
- RLM 유비의 한계: RLM은 정답과 합치기 방식이 정해져 있지만 문제 정의에는 없다. 합치기는 대비 압축 기준과 사람의 반응으로 대신한다
- 루트는 원래 의도와 압축된 가지 요약만 들고, 가지가 repo와 기록을 변수처럼 탐색한다
- Claude가 "목표 공간은 사용자만 안다"는 주장을 정정한 사실과 근거(공진화, Dorst & Cross; 선호 구성; Dewey)
- 이론적 위치: A3, A4, 법칙 2 인용. "Loop I를 생성형 엔진으로 만드는 일"이라는 정리. 수렴 기준의 내부 출처 M4("Alternatives must disagree consequentially")
- 커널을 더 만들기 전에 발산 ①~③을 스크립트로 만들어 막연한 작업 5개로 먼저 시험하는 단계(보기 전·후 목표 비교, 피로 기록, 반나절)

수정 방향: 04에 "발산 서브시스템" 절을 두고 위 내용을 모은 뒤, 기존 탐구 네 종류와 연결한다. 사전 시험은 10 §5 맨 앞에 0단계로 넣는다.

### 3.2 관찰 에이전트 C ([12]~[18])

문서는 산출물을 "P 수정안, 절차 후보"로 좁혀 적었고(05 §5, 07 §2.4), 대화에서 정한 설계 대부분이 없다.

- 런타임 밖 별도 프로세스, 읽기 전용, 더 싼 모델. 12 §2 원칙 2("같은 프로세스 안의 task")와 충돌한다
- 처리 단계: 정규화 → 결정적 마이닝 → 후보만 LLM 판단 → 제안함(세션 id, 빈도, 추정 절감 토큰) → 사람 승인 후 반영 → 효과 측정(채택 후 같은 패턴이 줄었는지 다시 마이닝, 줄지 않으면 절차를 내림)
- 후보 분류: 스킬(판단 필요) / CLI(완전 결정적) / 훅(반드시 지켜야 함) / 우연
- 로그는 신뢰할 수 없는 데이터: 로그 원문의 지시를 제안 초안에 옮기지 않음, 자동 설치 금지, 비밀 값 마스킹
- 자기 세션 제외, 증분 읽기(오프셋), 결과를 Concern 대화에 넣지 않고 제안함과 복귀 요약으로만 전달
- 기각한 후보는 패턴 서명과 함께 남겨 다시 올리지 않음. 같은 의도의 다른 명령은 경로·인자를 추상화한 뒤 묶음
- 출력은 고정 JSON 스키마. 수치는 코드가 채우고 모델은 요약·판단만
- 실행 시점은 코드가 정함(세션 종료, 마지막 변경 후 일정 시간, 정해진 시각, 누락 대비 주기 스캔). 모델에게 스폰을 맡기면 비결정적이라는 이유
- 로그 집계는 REPL 방식이 가장 잘 맞는 자리
- Prime Agent 사례의 교훈: 자동 개선이 해로운 행동을 보존할 수 있으므로 최소 권한, 독립 검증, 버전과 근거를 남긴 되돌리기

열린 질문으로 둘 것: 관찰 범위가 Helm 기록만인지, Helm을 거치지 않은 pi·Claude Code·Codex 세션 로그도 포함하는지.

수정 방향: 관찰 에이전트를 별도 문서(16)나 08의 독립 절로 둔다.

### 3.3 "모델이 초안을 쓰고 사람은 반응·수정만 한다"

### 3.5 세계 모델과 변경 경로

- 관계 네 개를 쓰기 시점 참조 제약으로 바꾸는 규칙: Choice는 Finding이나 Possibility를 참조, M 변경은 Agreement를 참조, Observation은 실행 기록을 참조, Acceptance는 기준과 Outcome을 참조. "E reveals N" 제약도 포함.
- OICA는 흐름, NEMAP는 상태, OPD+C는 평가를 다룬다는 구분과 각각이 변경 경로의 어느 단계에 걸리는지.
- 07 모드 정의에서 "우선 보장할 OPD+C 기준"이 빠진 이유. 09 §5 Predictability에 "현재 모드 표시" 연결.
- 승격 조건에 구분 확인(경쟁 추측이 맞았다면 다른 결과가 나왔을 관찰)이 빠졌다(02 §2.1).
- Claim 스키마에 evidence, counterEvidence, counterChecked 필드가 없다(12 §4.3). 반증 탐색도 실행 기록으로 남아야 한다.
- 거부의 세 갈래: 내용(근거와 상태) / 자격(보낸 행위자) / 경로(커널 우회). 08 §2는 "1이나 2에서 실패하면 거부"라고 하지만 5단계 규칙 평가에서도 거부가 난다.
- helm.mjs의 거부 8건을 커널 테스트의 첫 대본으로 쓰기. helm.mjs 자체가 산출물 폴더에 없다(08 §1은 "별도로 전달됨"이라고 적음).
- "문서를 상태로 쓰지 않는다", "온톨로지를 먼저 완성하지 않는다", "그 단계에서 쓰면 안 되는 도구는 차단하지 않고 아예 주지 않는다".
- 계층 상태 기계(상위 OICA, 하위 10단계), 명세를 데이터로 두는 다섯 대상(스키마, 능력 행렬, 정책, 모드 계약, 재진입 규칙표), 레코드별 상태 전이.

### 3.9 pi-durable과 pi coding agent의 관계 ([149]~[150])

- Claude의 정정: "둘 중 하나만"이 아니라 "대화 하나를 돌리는 루프가 둘 중 하나"이다
- 패키지 층: pi-ai(모델 호출 부품) / pi-agent-core / pi coding agent(완성된 앱) / pi-durable(pi-agent-core를 쓰지 않는 별도 하네스)
- 결합 방식: pi-durable이 지휘하고 pi coding agent가 WorkUnit을 RPC·SDK로 실행. WorkUnit 안쪽은 재개 보장 없음, 범위 검사는 pi 확장이 맡음
- "pi coding agent는 일상 도구로 계속 쓴다"는 전제

### 3.10 06 묻기와 끼어들기 보완

- Horvitz의 "불확실할수록 범위를 좁힌다": 초안까지만 만들고 멈추는 중간 선택지
- 가정하고 진행할 때 되돌릴 지점(`rollback_point`) 필드
- 질문 상태 초안의 "만료"가 assumed로 옮겨졌다는 설명
- 자동으로 검증할 수 있는 선택은 에이전트가 정하고 검증 결과를 관찰로 남긴다(판정 연습 c)
- approval theater 용어

| bash로 범위 검사 우회 | 12 §8, 07 §2.2 | 합의 범위 검사가 write·edit에만 걸린다. bash로 파일을 바꾸면 지나친다(대화의 u1f992 사례) | execute 전후 작업 공간 diff를 떠서 범위 밖이면 거부 관찰과 선택 요청을 만들거나, bash 도구를 감싸 정책 검사를 거치게 함 |
| pi coding agent의 codemode | 14 §4 | pi coding agent의 codemode 안 도구 호출은 `ctx.executeTool`을 거쳐 훅이 적용된다(pi-durable에서는 우회). 14의 장점인데 빠졌다 | 14 §4 표에 추가(스파이크로 확인 필요) |

pi 세션에서 다루지 않은 것(14 경로 공통):
- 세션은 트리다. 항목의 parent id를 저장하고, 복원은 활성 경로만 하고, 버린 분기는 관찰 입력으로만 쓴다
- context_edit: 원본 기록과 모델이 본 것이 다를 수 있다
- `agent_settled.aborted`로 중단과 정상 종료를 구분하고, `durationMs`를 관찰에 넣는다. OSC 7501은 TUI에서 여러 세션 상태 표시 후보
- RPC의 message_update는 0.84부터 델타만 보낸다
- 루프마다 도구 목록을 바꾸면 프롬프트 캐시가 깨진다. 도구 목록 교체와 `tool_call` 차단 방식을 비교해야 한다. helm_* 도구별 노출 등급
- helm_* 도구에 outputSchema 선언
- `context` 이벤트로 투영을 대체할 때 세션 기록과 캐시 영향, `agent_before_settle` 무한 반복 방지(미검증)
- 패치 버전에도 breaking change가 있으므로 버전 고정과 changelog 확인
- pi 확장에서는 프로세스·타이머를 시작하지 않는다. 스케줄러와 관찰 에이전트는 별도 프로세스

## 6. 사용자 확인이 필요한 항목

문서를 고치기 전에 정해야 하는 것들이다.

1. **사용자가 "투영"이라 부른 개념의 이름.** 후보: 방법 전이 / 렌즈 / 투영 유지. "투영"을 쓰면 불변조건 3의 투영(정본을 읽어 만든 화면·컨텍스트)과 겹친다.
2. **질문 조건 조합.** (a) AND를 유지하고 조건별 문턱 다이얼(적게/보통/많이)로 조절, (b) 사용자가 AND/OR을 직접 고르는 옵션. OR이면 정책이 없는 사소한 선택까지 묻게 된다.
3. **[결정]으로 둘지.** 08 §1 커널 원칙, 08 §4 결정 주체 분류, 03 §5 의존 규칙 다섯 개, 05 §1 Cynefin 도입, 03 §7.2 기대 레코드.
4. **프로세스 배치와 클라이언트 순서.** 배치 A/B/C 중 무엇으로 갈지, 데스크톱 앱과 SSH + TUI 중 무엇을 먼저 만들지, 원격 접속 방식, 클라이언트가 꺼져 있어도 Helm이 돌아야 하는지, Claude Code·Codex를 언제 붙일지.
5. **관찰 에이전트의 입력 범위.** Helm 기록만인지, Helm을 거치지 않은 세션 로그도 포함하는지.
