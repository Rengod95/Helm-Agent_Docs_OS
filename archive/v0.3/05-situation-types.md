# 05. 상황 유형

## 1. 왜 필요한가 [결정]

v0.2의 기본 순서(O → I → C → A)는 원인과 결과를 분석으로 찾을 수 있는 상황을 전제로 한다. 범용 에이전트 작업에는 이 전제가 맞지 않는 경우가 많다.

- 정답이 뻔해서 탐구가 필요 없는 작업
- 미리 분석해서는 답이 나오지 않고 해 봐야 아는 작업 (취향, 사람, 시장 반응)
- 분석할 시간 없이 먼저 행동해야 하는 작업 (장애)

v0.3은 Snowden의 Cynefin 틀을 빌려 Concern마다 **상황 유형**을 붙인다. 유형에 따라 기본 루프 조합과 다이얼 기본값이 달라진다.

이 문서의 Cynefin 설명은 Snowden & Boone(2007)과 이후 Snowden의 설명을 기존 지식으로 정리한 것이다. [기존 지식]

## 2. 다섯 유형

### 2.1 명확 (Clear)

| 항목 | 내용 |
|---|---|
| 원인과 결과 | 누구나 보면 안다 |
| 제약 | 고정된 제약. 정해진 절차가 있다 |
| 대응 순서 | 감지 → 분류 → 대응 |
| 쓰는 방법 | 정해진 모범 사례 |
| 함정 | 익숙해서 방심하다가, 상황이 바뀐 것을 놓치고 갑자기 혼돈으로 떨어진다 |
| 범용 작업 예 | 회의록 서식 맞추기, 정해진 양식의 보고서 채우기 |
| 개발 작업 예 | 린트 오류 수정, 의존성 패치 버전 올리기 |

**판정 질문**: 이 작업을 전에 같은 방식으로 여러 번 했는가? 정해진 절차나 스크립트가 있는가?

### 2.2 복잡 (Complicated)

| 항목 | 내용 |
|---|---|
| 원인과 결과 | 있지만, 분석하거나 전문 지식이 있어야 보인다 |
| 제약 | 지배적 제약. 전문 영역의 규칙이 있다 |
| 대응 순서 | 감지 → 분석 → 대응 |
| 쓰는 방법 | 여러 좋은 방법 중 전문가가 고른다 |
| 함정 | 분석이 끝나지 않음, 전문가가 자기 방식만 고집함 |
| 범용 작업 예 | 세금 계산, 계약서 검토, 여행 일정의 제약 맞추기 |
| 개발 작업 예 | 성능 문제의 원인 찾기, 재현되는 버그 디버깅 |

**판정 질문**: 시간을 들여 분석하면 정답에 가까운 답이 나오는가? 이 분야의 전문가라면 답을 알 것인가?

### 2.3 복합 (Complex)

| 항목 | 내용 |
|---|---|
| 원인과 결과 | 지나고 나서야 보인다. 미리 분석해도 답이 나오지 않는다 |
| 제약 | 가능하게 하는 제약. 결과는 상호작용 속에서 생긴다 |
| 대응 순서 | 탐침 → 감지 → 대응 |
| 쓰는 방법 | 작고 실패해도 괜찮은 실험을 여러 개 동시에 하고, 잘되는 쪽을 키우고 안 되는 쪽을 접는다 |
| 함정 | 미리 분석해서 정답을 찾으려 함 |
| 범용 작업 예 | 글의 방향과 톤, 개인 프로젝트의 디자인, 팀에 새 도구 도입, 공부 방향 |
| 개발 작업 예 | 제품 기능의 방향, 사용자가 좋아할 UX, 개발자 경험 개선 |

**판정 질문**: 정답이 사용자의 취향이나 다른 사람의 반응에 달려 있는가? 해 보기 전에는 결과를 예상할 수 없는가?

Helm의 출발 동기인 취향형 작업([01](01-scope-and-motivation.md))은 대표적인 복합 상황이다. 원하는 것은 미리 분석해서 찾을 수 없고, 자극을 던져 보고 반응을 봐야 나온다. 원함 탐구에서 여러 자극을 동시에 보여주는 것이 Cynefin의 "실패해도 괜찮은 탐침 여러 개"에 해당한다.

### 2.4 혼돈 (Chaotic)

| 항목 | 내용 |
|---|---|
| 원인과 결과 | 찾을 시간이 없다 |
| 제약 | 효과 있는 제약이 없다 |
| 대응 순서 | 행동 → 감지 → 대응 |
| 쓰는 방법 | 먼저 안정시키고 나서 본다 |
| 함정 | 상황이 안정됐는데도 계속 비상 대응을 함 |
| 범용 작업 예 | 마감 직전 자료 유실, 잘못 보낸 메일의 수습 |
| 개발 작업 예 | 프로덕션 장애 (먼저 롤백) |

**판정 질문**: 지금 당장 무언가를 하지 않으면 피해가 커지는가? 원인을 찾을 시간이 있는가?

### 2.5 혼란 (Disorder / Confused)

지금이 어느 유형인지 모르는 상태다. 이 상태에서 사람은 자기에게 익숙한 방식으로 대응하는 경향이 있다. 분석에 익숙한 개발자는 복합 상황도 분석으로 풀려고 한다. 모델도 같은 경향을 가질 수 있다.

**대응**: 문제를 쪼개서 부분마다 다른 유형에 배정한다. Helm에서는 구조 루프(S)의 분해가 이 일을 한다([03 §4](03-loops-and-transitions.md)).

## 3. 상황 판정 [제안]

### 3.1 판정 레코드

```yaml
situation_assessment:
  concern: F-12
  type: complex
  confidence: 0.7
  answers:
    - q: "정답이 취향이나 반응에 달려 있는가"
      a: yes
      evidence: [OBS-3]      # 사용자가 "어떤 느낌이 좋을지 모르겠다"고 말함
    - q: "분석하면 정답에 가까운 답이 나오는가"
      a: no
  alternative: complicated
  assessed_by: agent
  autonomous: true           # 사람에게 묻지 않고 정함 → 이의 가능
```

### 3.2 규칙

1. 판정은 O 루프에서 한다. 판정 질문에 대한 답과 근거를 함께 남긴다.
2. 판정은 혼자 정한 결정으로 기록되며 사람이 이의를 걸 수 있다.
3. 두 유형 사이에서 확신이 낮으면 대안 유형도 함께 적는다.
4. 판정할 수 없으면 혼란으로 두고 구조 루프로 분해한다.
5. 익숙한 유형으로 기우는 경향을 줄이기 위해, 판정 근거가 판정 질문에 대한 답으로 남아 있어야 한다. 근거 없는 판정은 기록되지 않는다.

## 4. 유형은 바뀐다 [결정]

상황 유형은 Concern에 한 번 붙이고 끝나는 값이 아니라 **바뀔 수 있는 상태**다. 유형이 바뀌면 루프 조합도 바뀐다. 이것이 [03](03-loops-and-transitions.md)의 "기본 조합은 언제든 다른 루프로 전환 가능하다"는 원칙의 근거 중 하나다.

### 4.1 흔한 전이

| 전이 | 계기 | 예 |
|---|---|---|
| 혼돈 → 복합 | 안정화됨. 하지만 원인은 아직 모름 | 롤백 후 장애가 멈춤 |
| 복합 → 복잡 | 탐침 결과로 패턴이 보임 | 몇 가지 시도 후 어떤 방향이 통하는지 보임 |
| 복잡 → 명확 | 같은 문제를 같은 방식으로 여러 번 풀어 절차가 생김 | 비슷한 성능 문제를 세 번 같은 방법으로 해결 |
| 명확 → 혼돈 | 방심. 바뀐 상황을 놓침 | 늘 하던 배포가 바뀐 환경에서 장애를 냄 |
| 복잡 → 복합 | 전문적 분석이 계속 틀림. 사람이나 반응이 변수였음 | 기술적 원인을 고쳤는데 사용자 불만이 그대로 |
| 혼란 → 각 유형 | 분해 후 부분마다 판정 | |

### 4.2 전이 감지 신호

| 신호 | 의심할 전이 |
|---|---|
| 명확 상황에서 자동 검증이 예상 밖 결과를 냄 | 명확 → 다른 유형 |
| 사실 탐구가 예산을 다 써도 1순위가 안정되지 않음 | 복잡 → 복합 |
| 사용자의 반응이 분석 결과와 계속 어긋남 | 복잡 → 복합 |
| 탐침이 일관된 패턴을 보임 | 복합 → 복잡 |
| 비상 조치 후 상태가 안정됨 | 혼돈 → 복합이나 복잡 |

신호가 나오면 O 루프로 전환해 다시 판정한다.

## 5. 돌아보기로 명확 절차 만들기 [제안]

복잡 상황을 여러 번 풀다 보면 정해진 절차가 생기고, 그 일은 명확 상황이 된다. 이 전이를 의도적으로 만드는 것이 A 루프의 돌아보기와 관찰 에이전트의 일이다.

```text
같은 종류의 Concern이 같은 루프 조합과 같은 방식으로 여러 번 해결됨
  → 관찰 에이전트가 기록에서 패턴을 찾음
  → 절차, 스크립트, 스킬로 만들 후보를 제안
  → 사람이 확인
  → 이후 같은 종류의 Concern은 명확 유형으로 판정되고 그 절차를 씀
```

절차로 만들 후보의 기준(제안):
- 같은 종류의 Concern이 세 번 이상
- 루프 조합이 같고
- 사람이 결과에 이의를 걸지 않았음

반대 방향도 기록한다. 절차를 쓴 작업에서 예상 밖 결과가 나오면 그 절차의 신뢰도를 낮추고, 반복되면 절차를 내리고 다시 복잡 유형으로 다룬다.

## 6. 유형별 기본 조합

| 유형 | 기본 조합 | 쓰는 탐구 | 쓰는 루프 변형 | 다이얼 기본값 |
|---|---|---|---|---|
| 명확 | O → C.commit → A.confirm | 없음 | 약속형 C, 확인형 A (자동 검증) | 질문 적게, 탐구 없음 |
| 복잡 | O → I → C.commit → A.confirm | 사실, 필요하면 결과 | 약속형 C, 확인형 A | 질문 보통, 탐구 깊게 |
| 복합 | O → I ⇄ C.probe → A.watch → C.commit → A.confirm | 원함, 가능성, 결과 | 탐침형 C, 지속 관찰형 A | 탐구 넓게, 질문은 라운드 경계에 예약 |
| 혼돈 | C.emergency → O → 재판정 → … → A.reflect | 안정 후 사실, 결과 | 비상 합의 | 비상 합의 범위 안은 묻지 않음 |
| 혼란 | O(판정) → S.split → 하위 Concern마다 위 조합 | 하위에 따름 | 구조 루프 | 판정 근거 필수 |

루프 식별자는 [03 §2.1](03-loops-and-transitions.md)을 따른다.

모든 유형에서 공통으로:

- 기본 조합은 계획이며 언제든 다른 루프로 전환할 수 있다.
- 유형은 바뀔 수 있다.
- 돌아보기는 반복되는 일을 명확 절차로 만든다.
