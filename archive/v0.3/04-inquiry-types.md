# 04. 탐구 네 종류

## 1. 탐구를 나누는 기준 [결정]

v0.2의 I 루프는 사실을 찾는 탐구 하나였다. v0.3은 탐구를 네 종류로 나눈다.

탐구 종류를 따로 두려면 두 가지가 달라야 한다.

1. **무엇을 근거로 삼는가**
2. **언제 멈추는가**

둘이 같으면 같은 탐구의 변형이고, 다르면 다른 방법론이 필요하다.

| 탐구 | 묻는 것 | 근거 | 멈추는 조건 | 결과물 | 쓰는 칸 |
|---|---|---|---|---|---|
| 사실 탐구 | 무엇이 그런가 | 관찰 | 1순위 설명이 두 라운드 연속 유지되고, 남은 질문이 결과를 바꾸지 않음 | 판단, 문제 정의 | E |
| 원함 탐구 | 무엇을 원하는가 | 사용자의 반응 | 선호 모델의 기준과 무게가 두 라운드 동안 바뀌지 않음 | 선호 모델, 완료 기준 | E → N |
| 가능성 탐구 | 무엇이 될 수 있는가 | 다른 분야 사례, 작은 실현 가능성 확인 | 발산 표의 빈 칸이 닫히고 실현 가능한 후보가 하나 이상 있음 | 가능성 목록 | E |
| 결과 탐구 | 하면 무엇이 일어나는가 | 시뮬레이션, 유사 사례, 사전 부검 | 주요 실패 경로마다 대응이나 감시 조건이 붙음 | 예측 레코드 | E |

위 표에서 "멈추는 조건" 열과 "결과물" 열은 [제안]이다.

모든 탐구에는 예산(라운드 수, 하위 호출 수, 시간)이 있고, 예산이 먼저 소진되면 그 시점의 상태와 열린 질문을 그대로 넘긴다.

### 1.1 따로 두지 않은 것

| 후보 | 따로 두지 않은 이유 | 다루는 곳 |
|---|---|---|
| 관점 탐구 ("이건 어떤 종류의 문제인가") | 모든 탐구 앞에 오는 일 | O 루프의 Frame 단계와 상황 판정 |
| 정당성 탐구 ("해도 되는가, 누가 영향을 받나") | 권리와 위험 판별은 권한 레이어로 넘김. 사용자 본인의 가치 판단이면 원함 탐구 | 권한 레이어, 원함 탐구 |

## 2. 사실 탐구

### 2.1 목적

관찰된 증상의 원인이나 현재 상태를 근거로 밝힌다.

### 2.2 절차

1. **관점 세우기**: 문제를 보는 관점을 여러 개 세운다. 관점마다 "이 관점이 맞다면 무엇이 관찰되어야 하는가(예측)"와 "무엇이 관찰되면 틀린 것인가(반박 조건)"를 적는다. 예측이 겹치는 관점은 묶거나 구분 확인을 만든다.
2. **원인 후보 만들기 (추측)**: 관점마다 원인 후보를 만든다. 원인 후보는 추측이다.
3. **구분 확인 고르기**: 결과가 원인 후보에 따라 달라지는 확인을 고른다. 순서는 "구분되는 후보 수 ÷ 비용"으로 정한다. 모델은 각 후보가 확인 결과를 어떻게 예측하는지와 비용만 선언하고, 순서는 코드가 계산한다.
4. **확인 실행**: 결과는 관찰로 기록된다.
5. **지지·약화 갱신**: 관찰에 따라 각 후보의 근거와 반대 근거를 갱신한다. 갱신은 커널이 한다.
6. **반대 근거 찾기**: 1순위 후보에 대해 일부러 반대 근거를 찾는다.
7. **승격**: 승격 규칙([02 §2.1](02-core-concepts.md))을 통과하면 판단이 된다.

### 2.3 멈춤

- 1순위 후보가 두 라운드 연속 유지되고
- 남은 질문의 답이 1순위를 바꾸지 않을 때

또는 예산이 소진됐을 때.

### 2.4 실패 유형

| 실패 | 대응 |
|---|---|
| 첫 그럴듯한 설명에 빨리 수렴 | 관점을 최소 두 개 이상 세우게 함 |
| 확증 편향 | 반대 근거 탐색을 승격 조건에 넣음 |
| 구분하지 못하는 확인 | 확인마다 후보별 예측을 선언하게 해서, 모든 후보가 같은 결과를 예측하면 그 확인을 쓰지 않음 |

### 2.5 참고 방법 [기존 지식, Helm 내부 자료: 방법 카드]

Dewey의 Inquiry, Peirce의 Abduction, 경쟁 가설 분석(Analysis of Competing Hypotheses)

## 3. 원함 탐구 [결정: 도입 / 제안: 세부 절차]

### 3.1 목적

사용자가 실제로 원하는 것을 찾는다. Helm의 출발 동기([01 §1](01-scope-and-motivation.md))를 직접 다루는 탐구다.

사실 탐구와 생김새가 같다. 다만 대상이 E가 아니라 N이다.

| | 사실 탐구 | 원함 탐구 |
|---|---|---|
| 가설 | 원인 후보 | 선호 후보 ("단순함을 원하는 것 같다") |
| 구분 확인 | 결과가 원인에 따라 달라지는 관찰 | 반응이 선호에 따라 달라지는 자극 |
| 근거 | 도구 실행 결과 | 사용자의 반응 |
| 결과 | 판단 | 선호 모델, 완료 기준 |

### 3.2 절차

#### 1단계: 표현된 요구를 기록한다

사용자가 쓴 요청을 관찰로 기록한다. 이 요청은 출발점이며 확정된 정의가 아니다.

#### 2단계: 자극을 만든다

자극은 사용자가 반응할 수 있는 구체적인 것이다. 시안, 초안 일부, 레퍼런스, 사례, 비유가 될 수 있다.

- **범위**: 같은 분야 안의 변형만이 아니라 다른 분야의 레퍼런스를 포함한다. 일부러 극단적인 자극도 넣는다. 극단에 대한 반응을 보면 기준의 경계를 알 수 있기 때문이다.
- **개수**: 고정하지 않는다. 처음에는 넓게(예: 6~12개), 기준이 좁혀질수록 적게.
- **순서**: 첫 자극에 평가가 끌려가는 것을 줄이기 위해 순서를 섞는다.

#### 3단계: 반응을 받는다

하나를 고르게 하지 않는다. 다음 형태의 반응을 모두 받는다.

| 반응 형태 | 예 |
|---|---|
| 요소 단위 | "이 도입부의 톤은 좋은데 길이는 별로" |
| 비교 | "A가 B보다 낫다" |
| 강도 | 아주 좋음 / 좋음 / 상관없음 / 싫음 / 아주 싫음 |
| 이유 없는 반응 | "이유는 모르겠는데 이건 아니다" |
| 고쳐 말하기 | "이것과 비슷한데 더 짧게" |

반응은 관찰로 기록된다. 이유를 대지 못하는 반응도 근거로 쓴다. 원함 탐구가 다루는 것이 바로 말로 표현되지 않은 요구이기 때문이다.

#### 4단계: 숨은 기준을 찾는다

반응에서 기준 후보를 추론한다. 기준 후보는 추측(E)이다.

- **세 개 비교 (레퍼토리 그리드)**: 세 자극을 보여주고 "둘은 비슷하고 하나는 다른데, 무엇 때문인가"를 묻는다. 사용자가 말로 하지 못하던 기준이 나온다.
- **고쳐 말하기 분석 (비평 기반 추천)**: "더 짧게", "덜 딱딱하게" 같은 수정 요청에서 기준과 방향을 뽑는다.
- **반응 패턴**: 좋았던 자극들의 공통점과 싫었던 자극들의 공통점을 비교한다.

#### 5단계: 다음 자극을 고른다

가장 불확실한 기준을 확인할 수 있는 자극을 고른다. 사실 탐구의 구분 확인과 같은 원리다. 예를 들어 "길이"와 "톤" 중 어느 쪽이 반응을 좌우하는지 모르면, 길이만 다르고 톤이 같은 자극 쌍을 보여준다.

#### 6단계: 선호 모델로 올린다

기준 후보가 여러 자극에서 일관되게 확인되면 사용자에게 보여주고 확인받는다. 확인되면 선호 모델(N)의 기준이 된다.

### 3.3 멈춤

- 선호 모델의 기준과 무게가 두 라운드 동안 바뀌지 않거나
- 사용자가 "이거다"라고 하고 그 이유를 기준으로 설명할 수 있을 때

또는 예산이 소진됐을 때.

### 3.4 선호 모델 레코드

```yaml
preference_model:
  id: PM-3
  goal: G-2            # 이 선호가 속한 Goal
  concern: F-12
  criteria:
    - name: "도입부는 구체적인 장면으로 시작"
      weight: high
      confidence: 0.8
      evidence: [OBS-21, OBS-24, OBS-27]   # 반응 관찰
      counter: []
    - name: "길이보다 톤이 중요"
      weight: medium
      confidence: 0.6
      evidence: [OBS-25]
      counter: [OBS-29]
  liked_examples: [STIM-4, STIM-9]
  disliked_examples: [STIM-2]
  stated_vs_revealed:
    - stated: "짧은 글을 원함"
      revealed: "긴 글 중 장면 묘사가 있는 것을 계속 고름"
  status: qualified
  review_trigger: "같은 종류 작업에서 반대 반응이 두 번 이상 나오면 다시 봄"
```

`stated_vs_revealed`는 사용자가 말한 기준과 실제 반응이 다를 때 그 차이를 숨기지 않고 남기는 칸이다. 이 차이가 Helm의 출발 가정이 실제로 일어난 사례다.

### 3.5 결과가 쓰이는 곳

- 작업 합의의 완료 기준
- 취향형 작업의 결과 확인 기준 ([03 §3.4](03-loops-and-transitions.md))
- Goal의 선호 모델 연결. 다음 Concern에서 다시 쓰고 계속 다듬는다.

### 3.6 실패 유형

| 실패 | 대응 |
|---|---|
| 자극이 평균값 근처에 모임 | 다른 분야 레퍼런스와 극단 자극을 필수로 포함 |
| 사용자가 지침 | 질문 전달 방식([06](06-asking-and-interruption.md))으로 묶어서 받고, 라운드당 자극 수 상한 |
| 말한 기준과 실제 반응이 다름 | 반응을 우선하되 차이를 기록하고 사용자에게 보여줌 |
| 첫 자극에 끌림 | 자극 순서를 섞고, 같은 자극을 다른 맥락에서 다시 보여줌 |
| 대안 몇 개 중 고르기로 축소됨 | 하나 고르기 형태의 반응만 받는 라운드를 금지 |

### 3.7 참고 방법 [기존 지식]

선호 구성(Lichtenstein & Slovic), 병렬 프로토타이핑(Dow 등 2010), 여러 시안 제시(Tohidi 등 2006), 레퍼토리 그리드(Kelly), 비평 기반 추천(critiquing-based recommender), 컨조인트 분석(선택에서 기준의 무게를 추정)

## 4. 가능성 탐구 [결정: 도입 / 제안: 세부 절차]

### 4.1 목적

아직 없는 해법이나 관점을 만든다. 사실 탐구가 이미 있는 것을 찾는다면, 가능성 탐구는 아직 없는 것을 만든다. 관찰할 대상이 없으므로 근거는 다른 분야의 사례와 작은 실현 가능성 확인이다.

v0.2까지는 이 일이 사실 탐구의 발산 단계에 섞여 있었다.

### 4.2 발산 표

가능성을 어디로 넓힐지는 **코드가 정한다.** "관점 × 바꾸는 대상" 표를 만들고 빈 칸을 찾는다.

| | 방법 | 도구 | 구조 | 사람·절차 | 목표·제약 | 시점·순서 |
|---|---|---|---|---|---|---|
| 관점 1 | ● | · | ○ | · | ○ | · |
| 관점 2 | ○ | ● | ● | · | · | ○ |
| 관점 3 | · | · | ○ | ● | ○ | · |

관점 × 바꾸는 대상 표는 Zwicky의 형태 분석(morphological analysis)을 따르고, 모순을 푸는 관점은 TRIZ를 참고한다. [기존 지식]

- ● 채워짐, ○ 빈 칸, · 해당 없음(이유를 적어야 닫힘)
- 관점 행 중 최소 하나는 Method Transfer 렌즈(§4.3)로 만든다.
- 빈 칸마다 하위 호출을 하나 만든다. 하위 호출들은 모두 같은 시점의 기록에서 시작하며 서로의 결과를 보지 못한다. 독립성을 구조로 보장하기 위해서다.
- 열(바꾸는 대상)의 범주는 작업 종류에 따라 바꿀 수 있다. 위 표는 범용 작업용 기본값이다. 범주를 고정하면 그 자체가 편향이 되므로, 관찰 에이전트가 범주 수정안을 제안할 수 있게 한다.
- "목표·제약" 열은 일부러 둔다. 문제를 푸는 대신 목표나 제약을 바꾸는 가능성을 빠뜨리지 않기 위해서다.

### 4.3 Method Transfer 렌즈 [결정: 개념 / 제안: 절차]

Method Transfer는 다른 분야의 방법을 원리 수준에서 뽑아 지금 문제에 옮기는 것이다. v0.2까지는 `docs/research/`에서 Helm 자체를 설계하는 연구 방법으로만 쓰였다. v0.3에서는 이를 가능성 탐구 안의 동작으로 옮긴다.

#### 연구용 절차 (기존, `docs/research/README.md`)

```text
원래 분야와 그 분야의 실패
  → 환경 가정
  → 분야와 무관한 메커니즘
  → 복사하면 안 되는 것
  → Helm 요소
  → 반증 가능한 가설
  → 프로토타입과 지표
```

#### 런타임용 절차 (v0.3)

```text
1. 지금 문제의 구조를 분야 용어 없이 서술한다
2. 같은 구조의 실패를 겪은 다른 분야를 찾는다
3. 그 분야의 환경 가정을 적는다
4. 환경과 무관하게 유지되는 원리를 뽑는다
5. 복사하면 안 되는 것을 적는다
6. 지금 문제로 번역한 가능성을 만든다
7. 반증 조건과 작은 확인 방법을 붙인다
```

1단계가 가장 중요하다. 분야 용어가 남아 있으면 같은 분야의 해법만 찾게 된다.

#### 예

```text
문제: 개인 하네스의 여러 세션에서 무엇이 진행 중인지 놓친다

1. 구조: "제한된 주의를 가진 한 사람이, 동시에 진행되는 여러 흐름의 상태를 놓치지 않아야 한다"
2. 같은 구조의 분야: 병원 교대 인수인계, 항공 관제, 식당 주방의 주문 관리
3. 환경 가정 (주방): 주문이 짧은 주기로 끝나고, 모든 사람이 같은 공간에서 화면 하나를 봄
4. 원리: 진행 중인 것을 한곳에 물리적으로 늘어놓고, 끝나면 치운다 (주문표 레일)
5. 복사하면 안 되는 것: 실시간 소리치기, 짧은 주기 가정
6. 번역: 진행 중인 Concern을 한 줄씩 늘어놓는 상태 화면, 끝나면 사라지고 대기 중인 것만 강조
7. 반증 조건: 일주일 사용 후 복귀 시 "무엇이 진행 중인지 다시 찾는 시간"이 줄지 않으면 틀림
```

#### 렌즈 라이브러리

- 초기값: `docs/research/method-transfer-map.md`의 35개 방법과 20개 방법 카드
- 사용자가 렌즈를 추가할 수 있다.
- 렌즈를 쓴 가능성이 채택되거나 거절되면 그 기록이 렌즈별로 쌓인다. 어떤 렌즈가 이 사용자에게 쓸모 있었는지 나중에 볼 수 있다.

### 4.4 근거 규칙

가능성마다 근거를 붙인다. 근거는 다음 중 하나다.

- 저장소나 작업 대상에 대한 관찰 id
- 문서나 웹 자료를 실제로 읽은 도구 실행 결과 id
- 다른 분야 사례의 출처

근거가 없으면 "근거 없음"으로 표시하고, 비교 화면에서 근거 있는 가능성과 구분해서 보여준다.

### 4.5 작은 실현 가능성 확인

유망한 가능성은 탐침형 C([03 §3.3](03-loops-and-transitions.md))로 작게 시도해 본다. 결과는 관찰로 돌아온다.

### 4.6 멈춤

- 발산 표의 모든 빈 칸이 닫히고 (채워지거나, 해당 없음과 이유가 적힘)
- 실현 가능하다고 확인된 후보가 하나 이상 있을 때

또는 예산이 소진됐을 때.

### 4.7 실패 유형

| 실패 | 대응 |
|---|---|
| 같은 분야의 평균값 근처 가능성만 나옴 | 발산 표의 빈 칸을 코드가 찾고, Method Transfer 렌즈로 만든 관점 행을 최소 하나 넣음 |
| 겉모습만 비슷한 전이 | 1단계에서 분야 용어를 빼게 하고, 5단계(복사하면 안 되는 것)를 필수로 둠 |
| 가능성이 너무 많아 비교 불가 | 대비 압축: 결과를 바꾸는 차이가 있는 2~3개 관점을 앞에 보여주고 나머지는 접어 둠. 대비 압축은 보여 주는 순서만 정한다. 선택지를 2~3개로 줄이지 않으며, 접힌 항목도 펼쳐 반응할 수 있다 |

## 5. 결과 탐구 [결정: 도입 / 제안: 세부 절차]

### 5.1 목적

어떤 선택을 하면 무엇이 일어날지 예상한다. 미래는 지금 관찰할 수 없으므로 근거는 예측이며, 예측은 나중에 실제 결과로 확인해야 한다.

### 5.2 절차

1. **사전 부검**: "이 선택이 실패했다고 가정하고, 왜 실패했는지 쓴다." Klein이 제안한 방법으로, 낙관 편향을 줄이는 데 쓰인다.
2. **시나리오**: 잘 풀린 경우, 나쁘게 풀린 경우, 예상 밖으로 풀린 경우를 각각 짧게 쓴다.
3. **유사 사례**: 비슷한 선택을 한 사례에서 무슨 일이 있었는지 찾는다.
4. **다음 효과**: "그 다음에는 무엇이 일어나는가"를 한 단계 더 따라간다.
5. **영향 범위**: 이 선택이 다른 Concern, 다른 사람, 다른 결정에 주는 영향을 적는다.
6. **예측 기록**: 각 예측에 확인할 날짜나 조건을 붙인다.

### 5.3 예측 레코드

```yaml
prediction:
  id: PRED-7
  concern: F-03
  choice: CH-1
  statement: "SWR 방식을 쓰면 첫 화면 불만이 2주 안에 절반 이하로 줄어든다"
  basis: [OBS-8, OBS-9, CASE-3]
  failure_paths:
    - path: "오래된 가격이 보여 새로운 불만이 생김"
      mitigation: "가격 영역만 즉시 갱신"
      watch_signal: "가격 관련 피드백 수"
  check_at: 2026-10-25
  check_method: "피드백 분류 재실행"
  result: null          # 확인 날짜에 A 루프가 채움
```

### 5.4 멈춤

주요 실패 경로마다 대응이나 감시 신호가 붙었을 때. 또는 예산이 소진됐을 때.

### 5.5 확인

확인 날짜가 오면 A 루프가 예측과 실제 결과를 비교하고 `result`를 채운다. 예측이 맞았는지의 기록은 모델 품질을 평가하는 자료가 된다([08 §6](08-runtime-architecture.md)).

### 5.6 실패 유형

| 실패 | 대응 |
|---|---|
| 낙관 편향 | 사전 부검을 필수 단계로 둠 |
| 시나리오가 끝없이 늘어남 | 예산, 그리고 실패 경로마다 대응이 붙으면 멈춤 |
| 확인할 수 없는 예측 | 확인 날짜와 방법이 없는 예측은 기록 거부 |

### 5.7 참고 방법 [기존 지식]

사전 부검(Klein, 2007), 시나리오 계획, STPA(Helm 방법 카드 수록)

## 6. 탐구의 조합

탐구도 루프처럼 필요한 만큼 조합한다.

| 작업 | 조합 |
|---|---|
| 취향형 (글 방향, 디자인 톤) | 원함 → 가능성 → (원함) → 결과 → 선택 |
| 원인 불명 증상 (성능 문제) | 사실 → 가능성 → 결과 → 선택 |
| 기술 선택 (런타임 고르기) | 원함(무엇을 중요하게 보나) → 가능성 → 사실(각 후보 확인) → 결과 → 선택 |
| 흐린 목표 ("에이전트를 더 잘 쓰고 싶다") | 원함 → 사실(현재 사용 기록) → 가능성 → 원함(다시) |

## 7. 탐구 다이얼

| 다이얼 | 조절하는 것 |
|---|---|
| 관점 폭 | 발산 표의 행(관점) 수와 열(바꾸는 대상) 수, 렌즈 수 |
| 깊이 | 라운드 수 |
| 근거 범위 | 작업 대상만 / 문서까지 / 웹까지 |
| 자율 정도 | 사람에게 묻지 않고 몇 라운드까지 진행할지 |
| 예산 | 하위 호출 수, 시간 |
| 자극 수 (원함 탐구) | 라운드당 자극 수 상한 |

다이얼 값은 모드([07](07-modes-and-capabilities.md))에 기본값으로 들어가고, 사용자가 덮어쓸 수 있다. 다이얼의 정본 목록은 [07 §3](07-modes-and-capabilities.md)에 있다.

## 8. 무엇을 코드가 정하고 무엇을 모델이 하는가

| 결정 | 주체 | 방법 |
|---|---|---|
| 어디로 넓힐지 | 코드 | 발산 표의 빈 칸 |
| 어떤 확인을 먼저 할지 | 코드 | 모델이 선언한 예측과 비용으로 계산 |
| 어떤 자극을 다음에 보여줄지 (원함) | 코드 | 기준별 불확실성으로 계산 |
| 무엇을 물을지 | 코드 | 모델의 질문 후보 중 "답에 따라 1순위가 바뀌는가"로 선택 |
| 언제 멈출지 | 코드 | 탐구별 멈춤 조건, 예산 |
| 칸의 내용, 자극, 기준 후보, 예측 문장 | 모델 | 제안으로 들어오고 커널 검사를 거침 |
| 선호 기준 확정, 판단 확인, Goal 수정 | 사람 | |

모델이 선언한 예측과 비용이 틀리면 계산도 틀린다. 다만 선언 내용이 기록에 남기 때문에 나중에 어디서 틀렸는지 추적할 수 있다.

## 9. REPL로 탐구하기 [제안]

탐구 과정은 REPL 구조(RLM 방식)로 수행할 수 있다.

- 관점, 가능성, 반응, 기준 후보를 REPL 변수에 둔다.
- 모델은 코드로 발산 표를 만들고, 빈 칸마다 하위 호출(`llm_query`)을 돌린다.
- 탐구 과정이 코드로 남기 때문에 다시 실행하고 검토할 수 있다.

지켜야 할 규칙: **REPL 변수는 작업 메모이고 정본이 아니다.** REPL 안에서 만든 가능성, 기준, 판단은 커널의 dispatch를 거쳐야만 기록이 된다. 비유하면 REPL은 컴포넌트의 로컬 state이고, 기록은 store다.
