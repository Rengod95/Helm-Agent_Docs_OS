# 06. 묻기와 끼어들기

## 1. v0.2 규칙과 그 한계

### 1.1 v0.2 규칙

`helm-kernel-v0.2-candidate.md`의 Gate rule은 다음 세 조건이 **모두** 참일 때 사람에게 묻는다.

1. 정책이 자동으로 처리할 수 없다.
2. 사람의 결정이 결과를 실질적으로 바꾼다.
3. 지금 묻는 가치가 주의 비용보다 크다.

또한 "Gate Event와 UI notification을 구분한다"는 규칙이 있다. 선택 요청이 생긴 것과 사람에게 알리는 것은 별개라는 뜻이다.

### 1.2 한계

| 한계 | 설명 |
|---|---|
| 판정 방법이 없다 | 세 조건이 질적으로 적혀 있어 무엇을 기준으로 참·거짓을 정하는지 없다 |
| 취향형 작업에서 판정 불가 | 정답이 취향이면 "결과가 바뀌는가"(조건 2)를 미리 알 수 없다 |
| 이분법 | "묻는다 / 혼자 정한다" 둘뿐이고, 범위를 줄여 진행하거나 가정하고 진행하는 선택지가 없다 |
| 시점과 방식이 없다 | 조건 3은 "지금"을 말하지만, 언제 어떤 방식으로 묻는지는 정하지 않는다 |
| 묻는 이유가 섞여 있다 | 몰라서 묻는 것과, 원래 사람이 정할 권리라서 묻는 것이 구분되지 않는다 |
| 묻지 않은 것의 사후 확인이 없다 | 혼자 정한 결정을 나중에 어떻게 보여줄지 정해져 있지 않다 |

## 2. 다른 분야의 틀

### 2.1 정보 가치 (Value of Information) [기존 지식]

결정 이론에서는 "물어서 얻는 기대 개선 > 묻는 비용"일 때 묻는다(Howard, 1966). v0.2의 세 조건은 이것을 말로 풀어 쓴 형태로 볼 수 있다.

| v0.2 조건 | 정보 가치의 항 |
|---|---|
| 조건 1: 정책이 처리할 수 없다 | 에이전트의 기본 선택이 틀릴 확률 |
| 조건 2: 결과가 실질적으로 바뀐다 | 틀렸을 때의 손실 차이 |
| 조건 3: 묻는 가치 > 주의 비용 | 묻는 비용 |

세 항은 곱셈 관계라서 하나라도 0이면 물어서 얻는 기대 개선도 0이 된다. 이 구조로 보면 세 조건을 모두 만족할 때 묻는 규칙(AND)이 자연스럽다. 하나만 만족해도 묻게 하면(OR) 결과에 영향이 없는 변수 이름 같은 것까지 묻게 된다.

v0.3 논의에서 제품 소유자는 사용자가 "세 조건 모두 / 하나만" 중에서 고를 수 있게 하자고 제안했다. v0.3은 이 제안을 다음처럼 반영한다. [제안]

- 기본값은 AND로 둔다.
- 조건마다 문턱 다이얼(적게 묻기 / 보통 / 많이 묻기)을 둔다. 어떤 조건의 문턱을 "많이 묻기"로 두면 그 조건이 참으로 판정되는 범위가 넓어져 질문이 늘어난다([§5](#5-다이얼-제안)).
- AND와 OR를 사용자가 직접 고르는 옵션을 둘지는 실제로 써 본 뒤 정한다. 그때 볼 값은 Concern당 질문 수와, 에이전트가 혼자 정한 결정에 이의가 걸린 비율이다([§7](#7-측정)).

### 2.2 Horvitz의 mixed-initiative 원칙 (1999) [출처 위치 확인]

시스템은 "실행 / 확인 질문 / 아무것도 안 함" 중 기대 효용이 가장 큰 것을 고른다. 이 논문은 다음도 강조한다.

- 사용자의 목표에 대한 불확실성을 고려한다.
- 사용자의 주의 상태를 보고 타이밍을 정한다.
- 잘못 추측했을 때의 비용을 줄인다.
- 불확실할수록 서비스의 범위를 좁힌다.
- 사용자를 관찰하며 계속 배운다.

Helm에 없던 것은 "범위를 좁혀서 진행"이라는 중간 선택지다.

### 2.3 Parasuraman, Sheridan, Wickens의 자동화 유형과 수준 (2000) [출처 위치 확인]

자동화를 네 기능(정보 수집, 정보 분석, 결정 선택, 실행)으로 나누고, 기능마다 자동화 수준을 따로 정한다. 질문 빈도도 하나의 값이 아니라 기능(루프)별로 다르게 둘 수 있다는 근거가 된다.

### 2.4 McFarlane의 끼어드는 방식 네 가지 (2002) [원문 확인]

36명이 참여한 실험실 이중 과제 실험이다.

| 방식 | 정의 | 결과 |
|---|---|---|
| 즉시 | 생기는 즉시 전달하고, 사람은 하던 일을 멈추고 답해야 함 | 응답은 가장 빨랐지만 입력 오류가 가장 많고 원래 작업 정확도가 나빴음. 참여자가 "가장 방해받았다"고 느낌 |
| 협상 | 질문이 왔다는 것만 알리고, 언제 볼지(볼지 말지)는 사람이 정함 | 종합적으로 가장 좋았음. 원래 작업 정확도가 높고 오류가 적었으며 가장 많이 선호됨(36명 중 17명이 1순위). 대신 답이 가장 늦었음 |
| 중재 | 대리자가 받아 두고 사람의 작업 부하를 보고 전달 시점을 정함 | 대부분 중간. 원래 작업의 효율은 좋았음 |
| 예약 | 정해진 시간표에 맞춰 전달 (실험에서는 25초마다) | 작업 전환은 가장 적고 예측하기 쉬웠지만, 원래 작업 정확도와 응답 속도가 가장 나빴음 |

논문의 권고:

1. 응답 속도가 결정적인 경우가 아니면 협상을 기본으로 한다.
2. 사람마다 선호가 크게 다르므로(약 4분의 1은 협상을 싫어했음) 방식을 고를 수 있게 한다.
3. 작업이 잠시 쉬는 지점에 전달하면 두 작업 모두 좋아진다.

예약 방식이 나빴던 것은 시간표가 작업 흐름과 무관하게 고정되어 있었기 때문이다. Helm에서는 시간이 아니라 작업 경계에 맞춰 예약한다.

논문 스스로 밝힌 한계: 실험실의 추상화된 과제라 외부 타당성이 제한적이며, 특히 하위 작업이 서로 얽힌 경우에는 그렇다.

### 2.5 작업 경계 연구 [기존 지식]

Iqbal과 Bailey 등의 연구는 작업의 큰 경계(하위 작업 하나가 끝난 지점)에서 끼어들면 재개 비용과 불쾌감이 작다고 보고했다.

### 2.6 LLM 에이전트 연구 [초록 확인]

- **Ask-when-Needed (2024)**: 도구 호출 전마다 지시가 충분한지 확인하고, 부족하면 묻고, 도구로 할 수 없는 일은 거절한다. 빠진 정보가 있는 경우에 맞는 질문을 하는 비율이 크게 올랐다(gpt-4o 기준 0.52 → 0.90). 일부 모델은 불필요한 질문도 늘었다.
- **Ask or Assume? (2026)**: 작업 에이전트와 별도로 의도 감시 에이전트를 두고, 빠진 맥락을 감지하면 작업 에이전트가 사용자에게 묻게 했다. 일부러 덜 명세한 SWE-bench Verified 500개 과제에서 해결률이 단일 에이전트 61.2%에서 69.4%로 올랐다. 완전히 명세한 경우는 70.8%였다. 저자들은 질문이 개선의 원인이라고 단정하지 않는다.

두 연구 모두 물을지 정하는 단계를 작업 흐름에 명시적으로 넣었고, 두 번째 연구는 그 결정을 별도 에이전트에게 맡겼다. Helm의 중재 방식과 같은 방향이다.

## 3. 재설계 [결정]

구조(기록과 전달의 분리, 두 게이트, 네 전달 방식, 질문 레코드와 가정 만료점)는 [결정]이다. 다이얼의 수치와 기본값은 [제안]이다([§5](#5-다이얼-제안)).

### 3.1 묻기를 두 결정으로 나눈다

```text
결정 1. 질문이 있는가          → 낮은 문턱. 불확실하면 일단 질문을 기록한다
결정 2. 언제, 어떻게 전달하나   → 네 방식 중 하나를 고른다
```

질문을 기록하는 데는 비용이 거의 들지 않는다. 비용이 드는 것은 사람의 주의를 쓰는 전달이다. 이렇게 나누면 정보 가치의 세 항을 정확히 추정해야 하는 경우는 **즉시** 전달을 고를 때뿐이다. 나머지 방식은 추정이 틀려도 견딘다.

| 방식 | 정보 가치 계산의 어느 부분을 대신하는가 |
|---|---|
| 협상 | "지금 볼 가치가 있나"를 사람이 직접 정한다. 에이전트가 가장 추정하기 어려운 조건 3을 사람에게 넘긴다 |
| 중재 | 작업 에이전트가 아닌 별도 중재자가 사람의 상태를 보고 정한다 |
| 예약 | 작업 경계(라운드 끝, 루프 전환, 복귀 요약)에 모아서 전달한다. 묻는 비용을 경계에서 한 번만 낸다 |
| 즉시 | 세 항을 모두 추정해야 한다. 그래서 문턱을 높게 둔다 |

### 3.2 두 게이트

질문이 생기는 이유는 두 가지이며, 구분해서 다룬다.

| 게이트 | 묻는 이유 | 판정 | 전달 |
|---|---|---|---|
| 권리 게이트 | 원래 사람이 정할 권리가 있는 결정이다 (돈을 씀, 사용자 대신 말함, 다른 사람에게 영향을 줌, Goal 변경) | 대상 분류는 권한 레이어. Goal 변경과 결과 확인은 Helm이 직접 | 즉시. 정보 가치가 0이어도 묻는다 |
| 정보 게이트 | 몰라서 묻는다 | 기본 선택이 틀릴 수 있고, 틀리면 결과가 달라짐 | 3.3의 규칙 |

### 3.3 전달 방식 규칙

| 상황 | 전달 방식 |
|---|---|
| 권리 게이트 | 즉시 |
| 답 없이는 작업이 멈추고, 기다리는 비용이 큼 | 즉시 |
| 가정하고 진행할 수 있음 | 사용자 기본값 (보통 협상) |
| 여러 질문이 비슷한 시점에 생김 | 다음 작업 경계에 예약 |
| 사용자가 자리에 없음 | 예약 (다음 복귀 요약) |
| 가정 만료점이 가까워짐 | 즉시로 승격 |

### 3.4 질문 레코드

```yaml
question:
  id: Q-14
  concern: F-12
  loop: I.want
  gate: information              # rights | information
  kind: criterion_confirm        # 기준 후보를 선호 모델에 올려도 되는지 확인
  text: "기준 후보 '도입부는 구체적인 장면으로 시작'을 선호 모델에 넣어도 될까요? 근거는 도입부 자극 세 개에 대한 반응입니다."
  evidence: [OBS-21, OBS-24]
  assumption: "이 기준을 임시로 적용해 다음 자극과 초안을 만든다"   # 답을 받기 전까지 따르는 임시 가정
  blocking: false                # 답이 없으면 작업이 멈추는가
  assumption_expires: "본문 2절 작성 시작 전"   # 넘기면 답이 바뀌었을 때 되돌리는 비용이 커짐
  delivery: negotiated           # immediate | negotiated | mediated | scheduled
  status: pending                # pending → delivered → answered | assumed | expired | withdrawn
  answer: null
```

질문 문장은 v0.2 쉬운 말 문서의 "선택 요청" 항목을 따른다. 지금 정할 것, 왜 지금인지, 선택지와 추천, 가장 강한 다른 선택, 아직 모르는 점, 미뤘을 때의 영향, 다시 볼 조건.

원함 탐구에서는 대안 몇 개를 주고 하나를 고르게 하는 질문을 만들지 않는다([04 §3.2](04-inquiry-types.md)). 원함 탐구의 질문은 위 예처럼 기준 후보를 확인하거나, 참고 자료 범위처럼 사실을 묻는 정보 게이트 질문이다.

### 3.5 질문의 상태

```text
pending (기록됨)
  → delivered (전달됨)
      → answered (답함)            → 답에 따라 진행, 임시 가정과 다르면 해당 작업 수정
      → assumed (가정 확정)        → 만료점까지 답이 없어 임시 가정을 확정. 혼자 정한 결정으로 기록
  → withdrawn (철회)              → 진행 중 질문이 필요 없어짐
  → expired (만료)                → 질문이 의미를 잃음 (Concern 종료 등)
```

### 3.6 가정 만료점과 승격

**가정 만료점**은 이 지점을 넘기면 답이 바뀌었을 때 되돌리는 비용이 커지는 지점이다.

- 협상이나 예약으로 둔 질문이 답 없이 만료점에 가까워지면 즉시로 올라간다.
- 그래서 "지금 묻는 가치"는 고정된 판정이 아니라 시간에 따라 커지는 값이 된다.
- 만료점까지 답이 없으면 임시 가정을 확정하고, 혼자 정한 결정으로 기록해 나중에 이의를 걸 수 있게 둔다.

### 3.7 중재자

중재 방식은 작업 에이전트와 분리된 별도 행위자가 맡는다.

- 입력: 열린 질문 목록, 사용자의 현재 상태(활동 중인지, 마지막 응답 시각, 현재 보고 있는 Concern), 각 질문의 만료점
- 출력: 질문별 전달 시점과 묶음
- 중재자의 결정도 기록된다.

작업 에이전트가 스스로 "지금 물어도 되나"를 정하면, 작업을 계속하고 싶은 쪽으로 기울 수 있다. 분리하는 이유다.

## 4. 혼자 정한 결정의 기록 [결정]

### 4.1 원칙

공리 A8은 "결정은 가장 낮은 유능한 수준에서 하고 예외만 위로 올린다"고 한다. 그러면 사람에게 묻지 않고 에이전트가 정하는 일이 많아진다. v0.3은 이것을 사후에 확인할 수 있어야 한다는 것을 불변조건으로 둔다.

> 불변조건 7: 에이전트가 혼자 정한 결정도 기록되며, 사람은 언제든 이의를 걸 수 있다.

### 4.2 무엇을 기록하는가

에이전트가 혼자 정한 것은 선택(Choice) 레코드로 남기고 다음을 함께 적는다.

```yaml
choice:
  id: CH-22
  concern: F-05
  decided_by: agent
  autonomous: true
  decision: "변수명은 items로 통일"
  alternatives: ["data", "list"]
  reason: "기존 코드의 다른 목록 변수와 일관"
  why_not_asked: "정보 게이트: 결과에 실질적 차이 없음 (조건 2 거짓)"
  from_question: null            # 가정 확정에서 나온 경우 질문 id
  review_trigger: null
  contestable: true
```

`why_not_asked`는 반드시 남긴다. 묻지 않은 이유가 있어야 나중에 묻지 않기로 한 결정이 맞았는지 볼 수 있다.

혼자 정한 결정에 포함되는 것:
- 정보 게이트를 통과하지 못해 묻지 않고 정한 것
- 질문의 가정 확정
- 루프 계획과 루프 전환
- 상황 판정
- 구조 루프의 분해와 병합
- 모드 라우팅

### 4.3 어떻게 보여주는가

- 복귀 요약에 "에이전트가 정한 것 n건"을 묶어서 보여준다. 기본은 접힌 상태이며, 종류별로 개수만 보인다.
- 각 항목에 이의 버튼이 있다. 이의를 걸면 그 선택은 contested가 되고, 관련 Concern이 다시 열린다.
- 클라이언트 요구는 [09](09-client-opdc.md)에 있다.

### 4.4 기록이 다이얼을 조정한다

이의가 걸린 기록은 묻기 정책을 조정하는 자료가 된다.

| 관찰 | 해석 | 조정 제안 |
|---|---|---|
| 특정 종류의 혼자 정한 결정에 이의가 자주 걸림 | 그 종류는 더 물어야 함 | 그 종류를 즉시나 협상으로 올림 |
| 답한 질문 중 답이 임시 가정과 같았던 비율이 높음 | 덜 물어도 됨 | 그 종류의 질문은 가정하고 진행 |
| 가정 확정 후 이의가 걸린 비율이 높음 | 만료점이 너무 이름 | 만료 여유를 늘리거나 즉시 승격 문턱을 낮춤 |

조정은 제안으로 올라가고 사람이 확인한다. Horvitz의 "사용자를 관찰하며 계속 배운다" 원칙과 같은 방향이다.

## 5. 다이얼 [제안]

| 다이얼 | 값 | 기본값 |
|---|---|---|
| 기본 전달 방식 | 즉시 / 협상 / 중재 / 예약 | 협상 (McFarlane 권고). 사용자마다 다르게 둠 |
| 질문 조건 문턱 | 조건 1~3마다 적게 묻기 / 보통 / 많이 묻기 (§2.1) | 세 조건 모두 보통 |
| 즉시 승격 문턱 | 높음 / 보통 / 낮음 | 보통 |
| 만료 여유 | 만료점 얼마 전에 즉시로 올릴지 | 작업 경계 하나 전 |
| 종류별 예외 | 특정 종류의 결정은 항상 묻기, 또는 절대 묻지 않기 | 없음 |
| 루프별 설정 | O, I, C, A, S마다 위 값을 다르게 | 아래 표 |

루프별 기본값 (Parasuraman 등의 기능별 자동화 수준을 따름):

| 루프 | 기본 전달 방식 | 이유 |
|---|---|---|
| O | 예약 (복귀 요약) | 상황 파악은 사용자가 돌아왔을 때 보면 됨 |
| I | 예약 (라운드 경계). 작업이 막히는 질문만 협상 | 탐구는 가정하고 계속 진행할 수 있음 |
| C | 협상, 범위 이탈 시 즉시 | 실행 중에는 범위 이탈만 급함 |
| A | 즉시 (결과 확인) | 결과 확인은 사람의 권리 |
| S | 예약 | 구조 변경은 다음 경계에서 확인해도 됨 |

## 6. 예시

밤 11시, 사용자는 퇴근했다. 블로그 글 방향 Concern에서 원함 탐구가 진행 중이다.

```text
23:02 Q-14 기록 (정보 게이트, 막힘 아님, 만료점 "본문 2절 작성 전")
      내용: 기준 후보 "도입부는 구체적인 장면으로 시작"을 선호 모델에 넣어도 되는가
      전달 방식: 사용자 부재 → 예약 (다음 복귀 요약)
      임시 가정 "이 기준을 임시로 적용"으로 계속 진행
23:40 Q-15 기록 (권리 게이트: 초안을 외부 리뷰어에게 보내도 되는가)
      권리 게이트 → 즉시. 하지만 사용자 부재 → 전송은 하지 않고 대기
      관련 작업만 멈추고 나머지 계속
다음 날 09:10 복귀 요약
      선택 필요 1 (Q-15)
      확인하면 좋은 것 1 (Q-14, 임시 가정으로 진행 중)
      에이전트가 정한 것 4 (접힘)
09:12 사용자: Q-14 확정 → 임시 가정과 같음 → 기준을 선호 모델에 올리고 그대로 진행
09:13 사용자: Q-15 허락 → 기대 레코드 생성 후 전송
```

## 7. 측정

| 지표 | 해석 |
|---|---|
| Concern당 전달된 질문 수 | 많으면 사용자가 Helm을 건너뛰게 됨 (A12) |
| 즉시 전달 비율 | 높으면 즉시 문턱이 너무 낮음 |
| 답이 임시 가정과 같았던 비율 | 높으면 덜 물어도 됨 |
| 가정 확정 후 이의 비율 | 높으면 더 물어야 하거나 만료점이 너무 이름 |
| 혼자 정한 결정 중 이의 비율 (종류별) | 종류별 정책 조정의 근거 |
