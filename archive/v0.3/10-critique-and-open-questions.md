# 10. 비판과 열린 질문

## 1. v0.2에 대한 반대 측 비판과 v0.3의 반영

v0.3 논의에서 O, I, C, A 네 루프(OICA)가 코드 작업이 아닌 범용 에이전트 작업에도 쓸모 있는지를 반대 입장에서 검토했다.

| 비판 | 내용 | v0.3 반영 | 상태 |
|---|---|---|---|
| 1. 숙련자는 탐구하지 않는다 | Boyd의 OODA에는 Orient에서 Act로 바로 가는 경로가 있다. Klein의 Recognition-Primed Decision 연구에서 현장 전문가는 대안을 비교하지 않고 처음 떠오른 안을 머릿속 시뮬레이션으로 확인한 뒤 실행한다 | 루프 조합 자유. I를 건너뛰는 것을 정상 경로로 인정하고 기록만 남김 ([03 §1](03-loops-and-transitions.md)) | 반영됨 |
| 2. 순서는 상황 종류에 따라 다르다 | Cynefin은 상황마다 대응 순서가 다르다고 본다. OICA는 "복잡" 상황을 전제로 한 순서다 | 상황 유형과 유형별 기본 조합 ([05](05-situation-types.md)) | 반영됨 |
| 3. C 루프는 "실행"에 치우쳐 있다 | 범용 작업의 다수는 산출물(글, 보고, 계획)을 만드는 일이라 C와 A가 겹친다. 실행 없이 I로 끝나는 작업도 많다 | 탐침형 C, 루프 조합 자유, I만 쓰는 작업 인정 | 부분 반영. 산출물형 작업에서 C와 A가 겹칠 때의 의존 규칙 표현이 남음 ([§4.1-1](#41-개념)) |
| 4. A 루프의 확인 기준이 없는 작업이 있다 | 창작이나 전략은 근거로 받아들일 정답이 없다 | 취향형 작업은 선호 모델과의 일치로 확인. 지속 관찰형 A | 반영됨 |
| 5. 사람과 에이전트 둘만 있다고 가정한다 | 범용 작업에는 메일 수신자, 회의 참석자 같은 제3자가 있다 | 외부 응답은 관찰. 기대 레코드와 "응답 없음" 관찰 ([03 §7](03-loops-and-transitions.md)) | 반영됨 |

### 1.1 뒷받침하는 증거

Parasuraman, Sheridan, Wickens(2000)는 자동화를 네 기능(정보 수집, 정보 분석, 결정 선택, 실행)으로 나눴다. O, I, C, A와 거의 같은 분할이다. 자동화 연구에서도 비슷한 네 단계 구분을 쓴다. OICA의 분할이 임의로 정한 것이 아니라는 근거 중 하나다. 동시에 그 모델은 네 기능을 순환이 아니라 기능별로 따로 자동화하는 대상으로 다룬다. v0.3이 루프를 순서가 아닌 조합으로 바꾼 것과 일치한다.

## 2. v0.3 자체에 대한 비판

v0.3은 개념을 많이 더했다. 그 대가로 생기는 위험을 적는다.

| 위험 | 내용 | 대응 |
|---|---|---|
| 개념이 너무 많아짐 | 루프 다섯 개와 변형, 탐구 네 종류, 상황 유형 다섯 개, 다이얼 열네 개([07 §3](07-modes-and-capabilities.md)), 새 레코드 여덟 종류와 Choice의 autonomous 표시. v0.2 정제 문서가 지적한 과잉 모델링이 반복될 수 있다 | 레코드와 루프는 실제로 쓰는 것만 구현. 사용자에게는 기본값으로 숨기고 필요할 때만 보임 |
| 상황 판정이 모델에 의존 | 판정이 틀리면 기본 조합이 틀림 | 판정 근거 필수, 이의 가능, 전이 감지 신호로 재판정 |
| 원함 탐구가 사용자를 지치게 함 | 반응을 자주, 자세히 요구함 | 질문 전달 방식으로 묶기, 라운드당 자극 수 상한, 피로 측정 |
| 혼자 정한 결정이 너무 많아 무시됨 | "에이전트가 정한 것" 목록을 아무도 안 봄 | 종류별 접기, 이의 비율로 정책 조정 |
| 구조 루프의 과분해 | 조각이 너무 많아짐 | 개수와 깊이 상한, 재조합 확인 |
| 코드의 계산이 모델 선언의 질에 묶임 | 확인 순서와 다음 자극 선택이 모델이 선언한 예측에 의존 | 선언을 기록해 사후 추적. 예측 정확도를 모델 평가로 측정 |
| 가정 만료점 추정이 어려움 | 언제 되돌리기 비싸지는지 모델이 잘못 추정할 수 있음 | 기본값을 "다음 작업 경계"로 두고, 가정 확정 후 이의 비율로 조정 |
| Method Transfer가 겉모양만 닮음 | 분야 용어만 바꾼 피상적 전이 | 런타임 절차 1단계(분야 용어 빼기)와 5단계(복사하면 안 되는 것) 필수 |
| Effect class 제외로 생기는 판정 불확실성 | 고정된 정의가 없으면 모델이나 권한 레이어가 행동을 되돌릴 수 있는지 매번 판정한다. 제품 소유자가 A 루프에 대해 지적한 것과 같은 종류의 불확실성이다 ([01 §4.1](01-scope-and-motivation.md)) | 권한 레이어의 판정 결과와 이유를 관찰로 기록한다. send는 기본값으로 항상 사람의 허락을 받는다 |

## 3. 반증 조건

v0.3의 주요 가설과, 무엇이 관찰되면 그 가설이 틀렸다고 볼지 적는다.

| 가설 | 반증 관찰 | 측정 |
|---|---|---|
| H1. 원함 탐구가 대안 몇 개 중 고르기보다 실제 요구를 더 잘 찾아낸다 | 선호 모델을 기준으로 만든 결과와 고르기로 만든 결과 사이에 만족도나 이후 수정 횟수 차이가 없음 | 같은 종류의 취향형 작업 두 방식 비교 |
| H2. 질문 기록과 전달을 나누면 방해는 줄고 결과 품질은 유지된다 | 가정 확정 후 이의 비율이 높고 재작업이 늘어남 | [06 §7](06-asking-and-interruption.md) 지표 |
| H3. 상황 유형별 기본 조합이 고정 순서보다 낫다 | 대부분의 Concern에서 시작하자마자 재판정이나 전환이 일어남 (기본 조합이 의미 없음) | 첫 전환까지의 시간, 재판정 비율 |
| H4. 구조 루프가 엉킨 Concern 관리를 돕는다 | 분해 후 재조합 생략이나 경계 누락이 자주 일어남 | 재조합 생략 건수, 경계 항목에서 나중에 생긴 문제 수 |
| H5. 혼자 정한 결정 기록이 사람의 이해를 유지한다 | "에이전트가 정한 것" 목록을 거의 보지 않고, 이의도 0인데, 나중에 사람이 결과에 놀람 | 목록 열람 비율, 이의 비율, "예상 못 했다"는 반응 수 |
| H6. Method Transfer가 쓸모 있는 가능성을 만든다 | 렌즈에서 나온 가능성의 채택률이 0에 가까움 | 렌즈별 채택률 |
| H7. 진입 조건이 Helm이 필요한 작업을 맞게 고른다 | [01 §3.8](01-scope-and-motivation.md)의 두 지표 | 진입한 작업 중 정의가 바뀐 비율, 일반 작업 중 나중에 방향을 다시 잡은 비율 |

## 4. 열린 질문

### 4.1 개념

1. 산출물형 작업(글, 보고서)에서 C와 A가 겹칠 때, "write를 하려면 C가 필요하다"와 "완료라고 하려면 A가 필요하다"를 어떻게 적용하는가. 초안 하나하나를 WorkUnit으로 볼 것인가.
2. 선호 모델은 프로젝트(Goal) 단위인가, 사용자 단위인가. 사용자 단위의 일반 선호와 프로젝트 단위의 선호를 나눠야 하는가.
3. 상황 유형을 하나의 값으로 둘 것인가, 여러 유형에 대한 확신도 분포로 둘 것인가.
4. v0.2의 Quick / Guided / Assured를 이름으로 유지할 것인가, 다이얼(증명 부담)로 흡수할 것인가.
5. 권리 게이트 대상 중 Helm이 직접 판별하는 것(Goal 변경, 결과 확인)과 권한 레이어가 판별하는 것(돈, 외부 발송)의 경계를 어디에 둘 것인가.

### 4.2 운영

6. 루프 계획을 작업 에이전트가 정할 것인가, 라우터가 정할 것인가.
7. 다이얼 조정 제안을 사람이 매번 확인할 것인가, 일부는 자동 적용할 것인가.
8. 관찰 에이전트가 만든 절차(명확 상황용)의 신뢰도를 어떻게 관리하고 언제 내릴 것인가.
9. 탐구 예산의 기본값은 얼마인가. 상황 유형별로 다르게 둘 것인가.
10. 외부 행위자가 여러 명일 때 기대 레코드와 응답 관찰을 어떻게 묶을 것인가.
11. 사용자의 피로를 무엇으로 측정할 것인가.

### 4.3 구현

12. 클라이언트 형태. 클라이언트는 웹이 아니다 [결정]. 데스크톱 앱을 먼저 만들고, 이후 SSH + pi + 커스텀 TUI 경로를 더한다 [결정]. 남은 질문은 두 가지다. 프로세스 배치(Helm 데몬, 에이전트 런타임, 클라이언트를 어떻게 나눌지), 그리고 TUI에서 시안이나 레퍼런스 같은 시각 자극을 어떻게 보여 줄지([09 §4.6](09-client-opdc.md)).
13. 지속 타이머와 사람이 없을 때의 실행을 어떤 런타임 기능으로 구현할 것인가.
14. REPL 방식 탐구와 도구 호출 방식 탐구를 둘 다 지원할 것인가.
