# 신뢰, 통제, 결과 확인

## 1. Agent를 믿는 대신 맡긴 범위를 안다

Helm은 “이 agent는 자율성이 높다”라고 말하지 않는다. 각 진행 작업마다 **맡긴 범위**를 보여준다.

- **대상:** 어떤 초점, 파일, 서비스, 환경에서 일하는가?
- **가능한 행동:** 읽기, 제안, 로컬 변경, 외부 메시지, 배포 중 무엇이 가능한가?
- **금지된 행동:** 무엇은 절대 하지 않는가?
- **되돌리기:** 변경을 얼마나 쉽게 원래대로 돌릴 수 있는가?
- **영향 범위:** 다른 사용자와 시스템에 어디까지 영향을 주는가?
- **확인 방법:** 성공과 실패를 자동으로 확인할 수 있는가?
- **아직 모르는 점:** 환경과 결과를 얼마나 알고 있는가?
- **유효 기간:** 이 범위는 언제까지 유효한가?

Prompt에 “알아서 해”라고 적는 것과 실제 권한을 넓히는 것은 별개다.

## 2. 선택 요청의 깊이

### 가볍게 확인

작고 되돌리기 쉽고 자동 확인 가능한 작업에 사용한다.

- 무엇을 할지
- 예상 결과
- 되돌리는 방법

### 일반적인 선택

방향이나 결과 품질에 의미 있는 차이가 있을 때 사용한다.

- 지금 정할 것과 왜 지금인지
- 추천과 다른 선택
- 기준과 핵심 근거
- 아직 모르는 점
- 다시 볼 조건

### 깊은 검토

큰 비용, 외부 영향, 낮은 복구 가능성, 가치 충돌이 있을 때 사용한다.

- 경쟁하는 선택과 현상 유지
- 지지·반대 근거
- 실패 방식과 영향 범위
- 이해관계자와 결정 권한
- 복구 방법과 명시적 수락

위험하다는 이유만으로 모든 정보를 보여주지 않는다. 사용자의 판단을 바꿀 수 있는 차이를 우선한다.

## 3. 근거를 이해하는 법

근거의 수보다 다음 질문이 중요하다.

- 누가 어떤 방법으로 만들었는가?
- 어느 판단과 실제로 관련되는가?
- 직접 확인한 것인가, 여러 해석을 거친 것인가?
- 지금도 최신인가?
- 판단 전체를 확인하는가, 일부만 확인하는가?
- 다른 근거와 독립적인가?
- 어떤 결과가 이 판단을 틀렸다고 만들 수 있는가?

따라서 Helm은 근거 다섯 개를 근거 하나보다 자동으로 강하다고 표시하지 않는다.

## 4. 결과 확인

Agent가 일을 끝냈다고 제출하면 다음을 본다.

```text
완료 기준
  ├─ 확인된 기준과 연결된 근거
  ├─ 확인하지 못한 범위
  ├─ 남은 전제와 아직 모르는 점
  ├─ 반대 근거와 알려진 제한
  └─ 결과가 무효가 되는 조건
```

사용자는 다음 중 하나를 선택할 수 있다.

- **수정 요청:** 기준을 충족하지 못했거나 근거가 부족함
- **조건부 확인:** 범위와 제한을 명시하고 일부만 받아들임
- **결과 확인:** 현재 범위에서 받아들임
- **다시 조사:** 문제 관점이나 핵심 가능성을 다시 엶

## 5. 전체 반영

결과 확인은 끝이 아니다. 다음을 확인해야 한다.

- 목표와 이전 선택에 맞는가?
- 다른 진행 작업의 전제를 깨뜨렸는가?
- 관련 문서, 규칙, 테스트, 외부 상태도 갱신했는가?
- 지역적인 개선이 전체 품질을 낮추지 않는가?
- 실패하면 어떻게 되돌리거나 복구하는가?

이 과정이 끝나야 사용자 화면에서 작업을 `완료`로 표시한다.

## 6. 시간이 지나면 다시 확인한다

판단과 근거는 영원히 유효하지 않다.

다음 상황에서 `재확인 필요` 또는 `다시 열림`으로 바뀐다.

- 핵심 전제가 틀린 것으로 확인됨
- 더 직접적인 반대 근거가 생김
- 적용 환경이나 결과물이 바뀜
- 목표 또는 완료 기준이 바뀜
- 정한 유효 기간이 끝남
- 전체 반영 중 예상하지 못한 충돌이 발견됨

## 7. 실패와 복구

실패한 진행 작업은 처음부터 다시 시작하게 하지 않는다.

- 마지막으로 확인된 지점
- 실패한 행동과 실제 영향
- 다시 실행해도 안전한지
- 이미 실행된 외부 행동
- 가능한 수정, 이전 지점부터 재개, 다른 agent로 이관, 되돌리기

복구 뒤에는 다음 작업 합의나 자동화 규칙이 실제로 달라져야 한다.
