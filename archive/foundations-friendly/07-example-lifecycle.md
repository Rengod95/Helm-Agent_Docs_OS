# 예시로 보는 Helm 전체 Lifecycle

> Scenario: 한 팀이 기존 고객을 보호하면서 새로운 결제 흐름을 출시하려 한다.

## 1. 사용자가 목표를 말한다

사용자:

> 다음 달까지 새 결제 흐름을 출시하고 싶어. 기존 고객이 결제하지 못하는 일은 없어야 해.

Helm이 정리한다.

- **목표:** 다음 달까지 새 결제 흐름을 안전하게 출시
- **초점:** 기존 고객의 결제 호환성
- **완료 기준:** 기존 결제 성공률 유지, 복구 경로 확인, 되돌리기 가능
- **지켜야 할 것:** 기존 고객 데이터와 결제 연속성
- **하지 않을 것:** 사용자 동의 없는 결제 정보 변경

사용자는 중요한 차이만 수정하고 목표를 확정한다.

## 2. 가능성을 비교한다

Agent들이 조사한 결과:

| 가능성 | 지지 근거 | 반대 근거 | 다음 확인 |
|---|---|---|---|
| 새 API가 구버전 앱과 맞지 않음 | staging에서 구버전 요청 실패 | 운영 traffic의 일부만 구버전 | 구버전별 재현 테스트 |
| 데이터 이전 순서가 문제 | 실패가 이전된 계정에 집중 | 모든 실패가 이전 계정은 아님 | 계정 cohort 비교 |
| 캐시된 설정이 문제 | 설정 초기화 뒤 일부 회복 | 모바일에서 재현 안 됨 | 모바일 cold-start 테스트 |

Helm은 한 가지 결론으로 합치지 않고 경로를 실제로 바꿀 차이를 보존한다.

## 3. 중요한 선택을 요청한다

```text
지금 정할 것
호환 모드를 한 달 유지할까요?

왜 지금인가
데이터 이전을 시작한 뒤에는 되돌리는 비용이 크게 늘어납니다.

추천
한 달 유지하고 구버전 사용자가 5% 아래로 내려가면 종료합니다.

다른 선택
즉시 전환하면 구현은 단순하지만 구버전 실패 위험이 커집니다.

아직 모르는 점
모바일 cold-start 환경의 복구 경로를 확인하지 못했습니다.
```

사용자는 추천을 그대로 승인하는 대신 종료 기준을 3%로 바꾸고 선택한다.

## 4. 작업을 합의하고 맡긴다

```text
진행 작업: 모바일 복구 경로 확인
사람 책임자: 제품 책임자
Agent 담당: 모바일 검증 agent

완료 기준
- 세 구버전에서 실패 재현
- 복구 뒤 결제 성공 확인
- 자동 회귀 테스트 추가

맡긴 범위
- 코드와 로그 읽기
- 로컬 테스트와 로컬 변경
- 운영 배포와 고객 연락은 금지

도움 요청 조건
- 운영 로그가 필요함
- 결제 데이터 변경이 필요함
- 예상과 다른 실패 유형 발견
```

## 5. 사용자가 자리를 비운 동안 진행된다

Agent는 여러 테스트를 수행한다. Helm은 모든 command 대신 의미 있는 변화를 기록한다.

- 모바일 cold-start에서만 실패가 재현됨
- 캐시 가능성이 강화됨
- 구버전 API 불일치 가능성은 약화됨
- 로컬 수정과 회귀 테스트가 준비됨
- 운영 배포 전 선택이 필요해 멈춤

## 6. 사용자가 돌아온다

복귀 요약:

```text
돌아온 뒤 달라진 점
모바일 cold-start 실패를 재현했고 캐시된 설정이 원인이라는 판단이 강해졌습니다.

왜 중요한가
호환 모드만으로는 모바일 실패를 막지 못합니다.

그대로 두면
Agent는 로컬 검증을 마친 상태로 멈춰 있습니다. 운영에는 변화가 없습니다.

지금 할 일
캐시 초기화 변경을 canary 환경에 배포할지 선택하세요.
```

사용자는 raw log를 처음부터 읽지 않고도 다음 판단을 할 수 있다.

## 7. 결과를 확인한다

Agent의 결과 제출:

- 세 구버전 재현: 확인됨
- 복구 뒤 결제 성공: 확인됨
- 회귀 테스트: 확인됨
- 실제 운영 traffic: 아직 확인하지 못함
- 알려진 제한: canary에서만 확인 가능

사용자는 `canary 범위에서 조건부 확인`을 선택한다.

## 8. 전체에 반영한다

Helm이 영향 범위를 확인한다.

- 배포 계획에 canary 단계 추가
- 호환 모드 종료 선택의 다시 볼 조건 유지
- 모바일 운영 문서 갱신
- 다른 agent의 “호환 모드만으로 충분하다”는 전제 무효화
- 실패 시 설정 rollback 경로 기록

canary 관찰까지 끝나면 결과를 전체에 반영하고 작업을 완료한다.

## 9. 다음 작업이 더 나아진다

돌아보기에서 다음 기본 규칙을 추가한다.

- 모바일 설정 변경에는 cold-start 테스트를 기본 완료 기준으로 포함
- 운영 배포는 canary 결과가 없으면 자동으로 선택 요청 생성
- 같은 유형의 복구 작업에는 검증된 작업 합의를 재사용

Helm의 장기 가치는 기록을 많이 남기는 것이 아니라, 다음 Context와 작업 합의와 자동화 규칙이 실제로 좋아지는 데 있다.
