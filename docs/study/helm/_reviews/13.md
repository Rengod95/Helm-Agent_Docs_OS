## 1. 기술 문제

높음 2건, 중간 5건, 낮음 6건.

### T1. 높음 / 과도한 일반화와 생략: "인증 실패 응답은 사유를 구분하지 않는다"
- 인용: "형식이 틀리거나 없거나 해시가 맞지 않으면 모두 같은 '인증 실패'를 돌려줘서, 어떤 기기가 존재하는지 알려 주지 않습니다." / 점검 목록 "인증 실패 응답이 사유를 구분하지 않는가."
- 1차 자료: 18 §3.6.1 `helloDeviceAuth`와 §3.4.5 `verifyDevice`, 19 오류 코드 표(439~443행). 형식 틀림·해시 조회 실패·해시 불일치만 모두 `1004`다. 폐기와 만료는 `1005`이고 `details.reason`이 `revoked`, `expired_absolute`, `expired_idle`로 갈린다. 기기 ID·노드·방식·전달 수단 불일치는 `1008`이고 `reason`이 `device_mismatch`, `node_mismatch`, `method_not_allowed`, `carrier_mismatch`로 갈린다. 업그레이드 단계에서 토큰이 없거나 형식이 틀리면 HTTP 401이고, `cookieAuth` 실패 401 응답도 `reason`(`revoked`, `expired`, `node_mismatch`, `carrier_mismatch`)을 싣는다. 페어링 코드 실패(1009)만 사유를 전혀 구분하지 않는다.
- 문제: 글은 앞 문장에서 폐기·만료·기기 ID·전달 수단·노드 묶기 검사를 나열한 바로 뒤에 "모두 같은 인증 실패"라고 쓴다. 독자는 폐기나 노드 불일치도 같은 응답이라고 읽는다. 마지막 점검 항목은 그대로 구현 리뷰 기준이 되므로, 올바르게 `1005`·`1008` 사유를 돌려주는 코드를 위반으로 판정하게 만든다. 반대로 "기기가 있는지 알려 주지 않는다"는 목적이 `1004` 하나에만 걸린다는 점은 전해지지 않는다. 폐기·만료·불일치는 토큰 해시가 맞은 뒤에만 나오므로 그 단계의 사유 노출은 설계 의도다.
- 수정 제안: "토큰 형식이 틀리거나 해시를 찾지 못하거나 해시가 맞지 않으면 사유를 나누지 않고 같은 `1004`를 돌려줍니다. 해시가 맞은 뒤의 실패(폐기, 만료, 기기 ID·노드·전달 수단 불일치)는 클라이언트가 다음 행동을 정해야 하므로 사유를 싣습니다"로 고친다. 점검 항목도 "`1004` 세 경우가 구분되지 않는가. 해시가 맞은 뒤의 실패 사유는 정의된 코드와 일치하는가"로 바꾼다.

### T2. 높음 / 생략과 의미 변경: 복원 뒤 "기기 목록을 직접 확인해야 한다"
- 인용: "복원 뒤 기기 권한을 확인하라는 화면 안내는 2단계로 미뤄져 있어서(결정 62), 그 전까지는 복원 직후 사용자가 기기 목록을 직접 확인해야 합니다."
- 1차 자료: 18 §3.16 복원 조건 4번. 현재 DB를 열 수 없으면 복원본의 모든 기기 토큰을 `restore_without_revocation_list`로 무효로 하고 모든 기기를 다시 페어링한다. 그다음 문장이 "Grant·합의는 복원본 상태를 그대로 둔다. '복원 지점 이후 권한 변경을 확인할 수 없음' 주의 항목은 2단계로 미룬다 [결정 62]. MVP는 화면·질문 종류를 두지 않는다"이다. 18 §3.2의 T-R1 남는 위험도 "Grant·합의 범위 좁힘은 되살아날 수 있다"이다.
- 문제: 2단계로 미룬 것은 Grant와 합의 범위의 변경 주의 항목이고, 대상이 기기가 아니다. 이 항목이 필요한 경우(현재 DB를 열 수 없는 경우)에는 기기 토큰이 이미 모두 무효라서 기기 목록은 확인할 거리가 없다. 현재 DB를 열 수 있는 경우는 폐기 목록이 재적용되므로 기기 목록 확인이 필요 없다. 설계 문서에 "사용자가 복원 직후 기기 목록을 직접 확인한다"는 절차도 없다. 글이 만든 절차이고, 실제 남는 위험(복원 지점 뒤에 좁힌 Grant·합의가 되살아남)을 사용자가 확인해야 한다는 점은 빠졌다. 위협 표의 "일부 권한이 되살아날 수 있음"과 본문이 서로 다른 대상을 가리킨다.
- 수정 제안: "현재 DB를 열 수 없으면 기기 토큰은 모두 무효가 되어 다시 페어링하지만, 백업 뒤에 좁히거나 거둔 Grant와 합의 범위는 복원본 상태로 돌아옵니다. 이것을 알려 주는 주의 항목은 2단계로 미뤄졌고(결정 62), MVP에는 그 화면이 없습니다. 그래서 이 경우 사용자가 직접 Grant와 합의를 다시 점검해야 합니다"로 바꾼다.

### T3. 중간 / 과도한 단정: 체크포인트가 "기록의 변조를 찾는다"
- 인용: "이벤트 로그의 해시 체인과 서버 키로 서명한 체크포인트(4번 노드)가 기록의 변조를 찾고, 이 키(`HELM_LEDGER_HMAC_KEY`)가 없으면 데몬은 시작하지 않습니다."
- 1차 자료: 18 §3.10.5 "지키는 범위" 행. "같은 uid는 age 키로 원본을 복호화할 수 있으므로 같은 uid의 위조는 막지 못한다(T-H2). 이 키가 막는 것은 샌드박스 안 도구가 DB를 고치고 체인을 다시 계산하는 위조다." 18 §3.13.3: 같은 uid의 재작성은 오프사이트 매니페스트와의 비교로만 잡히고, H-2 반영 전에는 그 비교가 없다.
- 문제: 같은 글의 경계 A 절이 "같은 uid는 DB 파일을 직접 고칠 수 있다"고 세웠는데, 비밀 절은 변조 탐지를 범위 없이 쓴다. 독자는 HMAC 키가 같은 uid 위조까지 잡는다고 읽을 수 있다. 키 원본(SOPS)을 같은 uid가 복호화할 수 있으므로 그렇지 않다. 글 안의 모순이다.
- 수정 제안: "서명한 체크포인트는 샌드박스 안 도구가 DB를 고치고 체인을 다시 계산하는 위조를 찾습니다. 같은 uid는 키를 복호화할 수 있어 이 장치로 막지 못하고, 백업 매니페스트를 오프사이트 사본과 비교해야 잡습니다(H-2 뒤)"로 범위를 쓴다.

### T4. 중간 / 문서 간 불일치를 한 문장에 합침: 인증 실패의 "지연과 일시 차단"
- 인용: "인증 전 메시지 크기, 연결 수, 인증 실패 속도에도 상한이 있어서, 반복 실패는 지연과 일시 차단으로 이어집니다."
- 1차 자료: 18 §3.14 인증 실패 행. 19 기본값은 "1분 5회 → 60초 차단"인데 18 상한은 "차단 대신 지연: 1분 5회를 넘으면 다음 실패 응답마다 2초씩 늘린 지연(최대 30초). 토큰이 맞는 연결은 지연·실패 묶음과 무관하게 통과한다." 18 §3.4.2도 "X-Forwarded-For 기준으로 차단하지 않는다"이다. 19 §3.4.5(614행, 711행)는 "인증 실패에는 지연을 준다", 상한을 "1분 5회(60초), 10분 20회(10분)"로 쓰고 상한에 이르면 `1011 rateLimited` + `retryAfterMs`로 답한다.
- 문제: 두 문서가 달라서(18은 지연뿐이고 최대 30초, 19는 지연 뒤 60초·10분 상한에서 `1011`) 글은 양쪽을 "지연과 일시 차단"으로 합쳤다. 어느 쪽도 정확하지 않다. 정리 중인 부분을 글이 한쪽으로 확정하지도, 미정이라고 쓰지도 않았다. 더 중요한 빠진 조건은 두 문서가 일치하는 부분이다. 맞는 토큰을 가진 연결은 실패 묶음과 무관하게 통과하고, 위조한 X-Forwarded-For로 소유자를 막지 못한다. 이것이 지연 방식을 고른 이유이고, 구현 리뷰에서 확인할 항목이다.
- 수정 제안: "반복 실패에는 지연을 주고, 지연이 상한에 이르면 `1011`과 `retryAfterMs`로 답합니다. 맞는 토큰을 가진 연결은 이 지연의 영향을 받지 않고, 실패는 X-Forwarded-For가 아니라 확인된 tailnet 노드 단위로 셉니다. 지연 상한 값은 18과 19가 아직 다릅니다(18은 최대 30초, 19는 60초와 10분)"처럼 일치하는 부분을 단정하고 다른 값은 미정으로 쓴다. 점검 목록에도 "맞는 토큰의 연결이 실패 지연과 무관하게 통과하는가"를 더한다.

### T5. 중간 / 문서 내부 불일치를 한쪽으로 단정: 검사 순서 Host → Origin → 신원 → 토큰
- 인용: "Host 헤더가 허용 목록과 다르면 바로 403입니다. ... 다음으로 Origin을 봅니다. ... 그다음은 Tailscale 신원입니다." / 점검 목록 "Host 검사가 가장 먼저 실행되는가."
- 1차 자료: 18 §3.4.3 첫 문단은 "Host 검사 → Origin 검사 → 신원 검사 → 자격 검사 순서다"라고 쓰지만, 같은 절의 `preflight` 의사 코드는 `tailnet`에서 Host 403 → `tailscaleIngress` 실패 401 → 경로별 Origin 검사 순이다(`/pair`, `/rpc` 업그레이드의 Origin 거부는 `upgradeAuth`와 경로 분기 안에 있다). 정적 `/m/` 경로는 신원 검사만 거치고 Origin은 보지 않는다.
- 문제: Host가 먼저라는 점은 두 서술이 같다. Origin과 신원의 앞뒤는 설계 문서 안에서 다르다. 글은 산문 쪽을 확정했다. 이 순서는 응답 코드(403 대 401)가 달라지는 지점이어서, 시험이 한쪽을 기대하면 구현 리뷰에서 충돌한다. 또 모든 경로가 Origin을 보는 것처럼 읽히지만 `/healthz`와 `/m/` 정적 경로, GET `/m/whoami`(`originGetRule`), `/files/*` 등은 규칙이 다르다.
- 수정 제안: Host가 가장 먼저이고 나머지 검사의 앞뒤는 18 안에서 산문과 의사 코드가 다르다는 점을 쓰거나, 순서 대신 "각 검사가 어떤 응답 코드를 내는가"(Host·Origin 403, 신원·토큰 없음 401, 한도 429)를 쓴다. 점검 항목은 "Host 검사가 가장 먼저이고, Origin이 있는 헤더 갈래 요청이 403인가"로 줄인다.

### T6. 중간 / 조건 누락: 사람 결정에 "확인 문자열"이 필요한 경우
- 인용: "그중에서도 사람 결정(질문 답, 결과 확인, 안전 모드 해제)은 TUI나 터미널에서 확인 문자열을 입력한 경우만 받습니다."
- 1차 자료: 18 §3.5 규칙 6, 19 278행·730행·447행. 사람 결정은 `tui`(화면의 결정 버튼이 확인 단계) 또는 `tty_cli`에서만 받는다. 확인 문자열(데몬이 발급한 4자, 2분 유효, 1회)을 싣는 것은 `tty_cli`뿐이고, 없거나 다르면 `1012 confirm.required`다. TUI는 문자열을 쓰지 않는다. 비대화 `localAdmin`은 `decide` scope가 없다.
- 문제: "TUI나 터미널에서 확인 문자열을 입력"은 두 경로 모두 문자열을 입력한다는 뜻으로 읽힌다. 리뷰어가 TUI 코드에서 확인 문자열을 찾게 되고, 정상 구현을 결함으로 볼 수 있다. 앞 문단의 설명("비대화로 실행된 관리 CLI는 사람 결정을 내릴 수 없습니다")과도 이어지지 않는다.
- 수정 제안: "TUI는 화면의 결정 버튼이 확인 단계이고, 터미널 CLI는 표준 입출력이 모두 터미널일 때만 결정을 받으며 명령마다 데몬이 낸 확인 문자열(2분, 1회)을 입력해야 합니다. 비대화 실행은 받지 않습니다"로 고친다.

### T7. 중간 / 생략으로 생긴 오해: 노드 묶기와 `loopback` 리스너의 검사 범위
- 인용: "`loopback` 리스너(SSH 터널)는 Tailscale 헤더를 보지 않고 기기 토큰만 봅니다." / "Tailscale 콘솔에서 노드를 제거하고(노드 묶기 때문에 토큰만으로는 통과하지 못함)" / 위협 표 "토큰을 tailnet 노드에 묶음"
- 1차 자료: 18 §3.4.1 정책 표. `loopback`은 Host·Origin 검사를 하고, 노드 묶기는 "검사하지 않음(sshd 연결은 출처 노드를 알 수 없다)"이다. §3.7.2: 코드 페어링 성공 때 whois의 `Node.StableID`로 묶는다. §3.7.3: SSH 발급 기기는 가능하면 `SSH_CONNECTION` IP로 미리 묶고, 실패하면 첫 WSS 접속 때 묶는다. §3.6.1 `bindTailnetNode` 설정이 꺼져 있으면 검사하지 않는다. §3.6.2: SSH 키를 가진 자는 서버 셸을 얻는다.
- 문제: 글은 노드 묶기가 무엇인지, 언제 묶이는지, 어느 리스너에서만 검사하는지 쓰지 않았다. "토큰만으로는 통과하지 못함"은 `tailnet` 리스너에만 해당한다. 도난 노트북의 앱은 `loopback`(SSH) 경로로도 붙으므로 SSH 키를 지우는 단계가 따로 필요한 이유가 이 차이에서 나오는데, 글은 이유를 주지 않는다. `loopback`이 Host·Origin을 검사한다는 점도 빠졌다(점검 항목 2번이 TCP 리스너 전체에 걸리므로 구현 리뷰에서 필요).
- 수정 제안: 노드 묶기를 "토큰이 처음 발급될 때 그 요청의 tailnet 노드에 붙여 두고 `tailnet` 리스너에서만 대조하는 조건"으로 한 문장 정의한다. 도난 절차에는 "SSH 경로는 노드 묶기를 검사하지 않으므로 SSH 키를 따로 지웁니다"를 덧붙인다. `loopback` 문장은 "Host·Origin 검사와 기기 토큰만"으로 고친다.

### T8. 낮음 / 조건 누락: 고정 기준선이 "끌 수 없다"
- 인용: "(보호 경로 쓰기 거부, 발송은 승인, 웹 읽기는 허용, 권한 상승 명령 거부, Windows 실행 파일 거부 등)은 8번 노드에서 보았고, 모드나 다이얼로 끌 수 없습니다."
- 1차 자료: 18 §3.11.6. 보호 경로 쓰기·권한 상승·Windows 실행은 합의로도 바뀌지 않는다. 발송은 합의가 없으면 `deny`, 있으면 `ask`다. 보호 경로 읽기와 네트워크 실행은 합의가 경로·명령·네트워크를 명시하면 `allow`로 바뀐다. `disclose_data`가 "다이얼과 무관한 권리 게이트"라는 문장은 있으나, 같은 표의 네트워크 행은 `net:` 부여가 있으면 `allow`다.
- 문제: 모드와 다이얼로 끌 수 없다는 말은 맞지만, 합의로 바뀌는 항목과 바뀌지 않는 항목이 섞인 목록을 "끌 수 없다" 하나로 묶었다. 발송은 "승인"만 쓰고 합의 없을 때의 `deny`가 빠졌다. 08번 노드가 이미 다룬 내용이라 영향은 작다.
- 수정 제안: "모드나 다이얼로는 끌 수 없습니다. 이 가운데 보호 경로 쓰기, 권한 상승, Windows 실행은 합의로도 바뀌지 않습니다"로 쓰거나 8번 노드 참조만 남기고 반복을 줄인다.

### T9. 낮음 / 과도한 일반화: 비밀이 "도구 ... 에는 넘어가지 않는다"
- 인용: "도구, 관찰 에이전트, 브라우저 프로세스에는 비밀이 넘어가지 않고"
- 1차 자료: 18 §3.10.1 MCP 서버 자격 행. 운영자 설정에 이름을 적은 키가 그 MCP 서버 프로세스의 환경이나 HTTP 헤더로 넘어간다(R-2 예외). §3.10.2: 사용자 작업이 `.env`를 쓰는 경우 `.env*` 읽기와 `secrets run`은 `ask`이고 합의에 명시하면 허용된다.
- 문제: 샌드박스 도구 실행 환경에 대한 규칙(R-2)을 모든 도구와 프로세스로 일반화했다. MCP 서버 프로세스와 합의로 허용한 `.env` 경로가 예외다.
- 수정 제안: "샌드박스 안 도구와 관찰 자식, 브라우저 프로세스에는 비밀이 넘어가지 않습니다. 예외는 운영자가 이름을 적은 MCP 서버 자격과 사람이 합의에 명시한 `.env` 경로입니다"로 한정한다.

### T10. 낮음 / 오해 소지: 쿠키를 정적 경로에서 "붙이지도" 않는다
- 인용: "쿠키는 특정 경로(...)에서만 읽고, 정적 파일 경로에서는 읽지도 붙이지도 않습니다."
- 1차 자료: 18 §3.4.6 마지막 행. 쿠키 `__Host-helm_dt`는 `Path=/`라서 정적 요청에도 브라우저가 실어 보낸다. 정적 응답은 그 값을 쓰지 않고 `Set-Cookie`도 붙이지 않는다.
- 문제: "붙이지도"가 서버의 `Set-Cookie`를 가리키는지 브라우저 전송을 가리키는지 모호하고, 브라우저 전송으로 읽으면 틀린다. 서버가 읽지 않는 것이 방어이고 전송은 막지 못한다는 점이 요점이다.
- 수정 제안: "정적 경로 요청에도 브라우저는 쿠키를 실어 보내지만(`Path=/`), 서버는 그 값을 읽지 않고 `Set-Cookie`도 붙이지 않습니다"로 쓴다.

### T11. 낮음 / 단정: 하위 프로토콜 토큰이 "프록시 로그에 남기 때문"
- 인용: "스크립트가 토큰을 들고 있어야 해서 XSS 하나로 유출되고, 프록시 로그에 남기 때문입니다."
- 1차 자료: 18 §3.4.4와 19 227행. 이유 (2)는 "프록시·진단 로그에 그대로 남을 수 있다"이다. 또 가짜 데몬과 시험 빌드의 브라우저 전송에는 남겨 둔다.
- 문제: "남을 수 있다"를 "남는다"로 바꿨다. 점검 항목 "하위 프로토콜 토큰을 받지 않는가"도 정식 데몬 한정이라는 조건이 빠졌다.
- 수정 제안: "남을 수 있기 때문"으로 고치고 점검 항목에 "정식 데몬"을 넣는다.

### T12. 낮음 / 생략: 위협 표의 "스냅숏에 비밀 값 없음"과 XSS·CSRF 행의 SameSite
- 인용: "restic 암호화(H-2 뒤), 스냅숏에 비밀 값 없음" / "HttpOnly 쿠키, 응답 보안 헤더, SameSite, Origin 정확 일치"
- 1차 자료: 18 §3.16. 스냅샷에는 API 키와 VAPID 키가 없지만 기기 토큰 해시, 페어링 코드 해시, `push_tokens`의 Web Push 구독 원문이 있다(유출되어도 VAPID 키 없이는 서명할 수 없다). 18 §3.18.1 T-W4와 26 X-16: 같은 호스트의 다른 포트는 same-site라 `SameSite=Strict`가 막지 않고, 막는 것은 Origin 정확 일치(포트 포함)다.
- 문제: 앞의 문장은 18 표의 표현을 그대로 옮겼으나 해시가 들어 있다는 점이 빠져 읽는 이가 "스냅샷은 인증에 쓸 값이 전혀 없다"고 이해할 수 있다. 뒤의 행은 SameSite가 어떤 공격을 막고 어떤 공격(같은 호스트 다른 포트)을 못 막는지 구분하지 않는다. 쿠키 절에서 포트를 구분하지 않는다는 한계는 썼으므로 모델은 맞지만 두 곳이 연결되지 않는다.
- 수정 제안: "스냅숏에 키는 없고 토큰 해시만 있음"으로 쓰고, 표의 SameSite 칸은 "다른 사이트의 요청을 막음. 같은 호스트의 다른 포트는 Origin 일치가 막음"으로 적는다.

### 1차 자료와 대조해 맞는 것으로 확인한 주장(참고)
자산 아홉 가지, 경계 A·B·C 설명과 S0 `critical`, 신뢰 등급 표, 위협 표의 대부분 행, tailnet 검사 순서의 Host 403·헤더 갈래 Origin 거부·쿠키 갈래 Origin 정확 일치, Funnel·태그 노드·whois 대조·fail closed, 헤더가 같은 호스트에서 흉내 낼 수 있다는 한계, 페어링 코드 규칙(60비트 12자, 10분, 1회, 5회, 해시), SSH 발급의 표준 입력 JSON, 토큰 형식·수명(365일·90일·30일 전 경고), 키체인·쿠키 저장 위치, 폐기의 즉시 효과 목록과 연쇄 폐기, 도난 절차 5단계, 모바일 scope 제한, 쿠키 이름과 속성, X-16 한계와 전용 호스트 이름 미결, `untrusted` 표식과 엔티티 치환, `taint.web`, 지침 파일 해시와 2단계 보류(결정 62), `/m/*`·`/files/*` 헤더, 인라인 허용 형식, HMAC 키 필수, 공급망 항목, 복원 재적용 순서(리스너를 열기 전)와 승인 만료.

티켓 경로는 18(`/files/<티켓>/…`)과 19(`/files/t/<ticket>`)가 다르지만 글은 경로를 단정하지 않아 해당 없다. 폐기 때 티켓이 무효가 된다는 문장만 있고 이는 18 §3.8.4와 맞다.

## 2. 지침 위반

### W51 의인화와 인지 동사
- "설계가 이 위험을 숨기지 않고 적어 두었다는 점이 중요합니다." 주어 "설계"는 추상 개념이고 동사 "숨기다·적어 두다"는 의도를 가진 행위다. 사용자가 명시한 금지 표현("설계가 ~한다")에 해당한다. 수정: "마지막 열의 위험은 설계 문서에 남는 위험으로 적혀 있습니다"처럼 사실만 쓰거나 문장을 뺀다.
- "승인 화면은 커널이 아는 구조 값(경로, 명령, 네트워크 여부)을 먼저 보이고" 인지 동사 "알다". 수정: "커널이 가진 구조 값".
- "웹 페이지가 표식을 닫고 Helm의 상태 메시지인 척하지 못하게" 웹 페이지(데이터)가 주어이고 "척하다"는 의도 동사다. 수정: "웹 페이지 본문이 표식을 닫고 Helm의 상태 메시지처럼 해석되는 일을 막습니다".
- "체크포인트가 기록의 변조를 찾고" 데이터가 주어다. 수정: "체크포인트와 대조하면 기록의 변조가 드러나고".
- "어떤 기기가 존재하는지 알려 주지 않습니다" 응답이 주어이고 "알려 주다"는 발화 동사. 수정: "응답으로는 기기가 존재하는지 확인할 수 없습니다"(또는 기기 존재 여부가 응답에서 드러나지 않습니다).
- "쿠키는 포트를 구분하지 않아서" 쿠키가 주어이고 "구분하다"는 인지 동사. 수정: "쿠키는 포트별로 나뉘지 않아서"(쿠키의 범위가 포트를 포함하지 않아서).
- "실패 응답은 이유를 구분하지 않습니다" 같은 이유. 수정: "실패 응답에는 이유별 차이가 없습니다".
- 허용으로 판정한 것: "샌드박스가 ... 가립니다"(실행 주체가 샌드박스 구성, 동작 가리기=마운트 차단), "Host 헤더가 ... 다르면", "스크립트가 토큰을 들고 있어야"(실행 중인 스크립트), "승인 화면에는 ... 표시됩니다". "Helm은 경계를 셋으로 나눕니다"는 제품이 주어이지만 설계 분류를 서술하는 문장이라 허용 범위로 보았다.

### W52와 사용자 금지 표현
- '축', '박다', '가른다', '닿다'는 쓰이지 않았다. "권한 축소 이벤트", "합의 축소"의 '축소'는 일반 명사이므로 위반이 아니다. "걸러 내는 것은 불가능하다", "원격 공격자를 거르는 겹"은 '가른다' 계열이 아니며 허용한다. 합니다체는 일관된다.
- "A가 아니라 B" 구호: 본문에는 없다. 단 절 제목 "문장은 막지 못하고 권한은 구조로 막는다"는 대비 구호 형태다. 수정: "프롬프트 주입에는 권한 구조로 대응한다"처럼 대비를 걷어 낸 제목.

### W4, W23 도입과 개요
- "이 노드의 범위" 절이 본문 전체(위협 모델, 외부 접속, 기기 인증, 프롬프트 주입, 웹 화면, 복원)를 나열하는 개요 문단이다. W23은 글 머리의 전체 요약 개요를 금지하고, W4는 상황-문제-질문-답으로 시작하라고 한다. 첫 절은 "왜 보안 모델이 따로 필요한가"(1인 서버, 에이전트 시스템, 사람 결정의 위조 위험)로 바로 들어가는 편이 낫다. 수정: 첫 문장은 02·08과의 연결로 두고 나열 문장은 삭제.

### W2 정의 없이 쓴 용어
- "노드 묶기"(T7 참고), "주체"(principal 개념, 02가 이름만 썼음), "taint.web"(7번 노드가 정의했으므로 허용), "권리 게이트"와 "disclose_data"(5·6번 노드가 다룸, 용어 연결 한 문장 필요), "Funnel"(Tailscale 용어, 독자가 아는 범위로 추정되어 낮음), "hop", "상수 시간 비교". 우선순위는 "노드 묶기".

### W20, W22 표상
- 위협 표 도입 문장 "각 대응이 위 경계 가운데 어디에 해당하는지 보입니다"가 표에서 실현되지 않는다. 표에 경계 A/B/C 열이 없다. 수정: 열을 하나 더하거나 문장을 "경로별 대응과 남는 위험"으로 고친다.
- 외부 접속 절의 검사 순서와 리스너별 차이(세 리스너 × 검사 항목)를 4개 문단의 산문으로 서술한다. 순서가 있는 단계는 W27(번호 붙은 단계)이고, 세 리스너의 비교는 표가 정보를 덜 잃는다. 18 §3.4.1 표가 그대로 쓸 수 있는 구조(행: 받는 출처, 검사, 받는 주체, 토큰 전달, 노드 묶기)이다. 수정: 표 하나로 옮기고 본문은 표에 없는 이유(왜 헤더가 토큰을 대신하지 못하는가)만 쓴다.
- 그림 직전 문장 "화살표는 '이 경계를 넘으려면 이것이 필요하다'는 뜻입니다"는 4절에 쓴 이유로 그림과 맞지 않는다. 그림 뒤 문단은 그림의 라벨(경계 B 기기 토큰, 경계 C 도구 샌드박스, 경계 A 같은 uid)을 문단마다 다시 나열한다(W22의 반복).

### W26 단락당 새 개념, W3, W14, W9 예시
- "마지막이 기기 토큰입니다" 문단 한 개에 검사 여덟 가지와 하위 프로토콜 거부 이유가 들어 있다. "기기 등록과 토큰" 첫 문단도 코드 규칙 다섯 가지, SSH 발급, 셸 해석, 알림을 한 문단에 담는다. W26(새 개념 한두 개)에 맞게 나누거나 표로 옮긴다.
- 구체적 예에서 규칙으로 가는 구성(W9, W14)이 없다. 예를 들어 "휴대폰 분실부터 폐기까지" 또는 "웹 페이지 안의 주입 문장이 발송으로 이어지려다 막히는 과정"을 단계별로 따라가는 예가 글에 한 번도 없다. 모든 절이 규칙 나열이다.

### W32, W34 연결과 주제어
- "프롬프트 주입" 절 둘째 문단은 "첫째 ... 다섯째"로 장치를 나열하지만 각 장치가 어떤 공격을 막는지의 연결어가 약하다. "첫째, 모델에게 권한을 바꾸는 도구가 없습니다"에서 "그러면 주입된 문장이 권한 변경을 시도해도 호출할 도구가 없다"는 인과를 한 문장 더 쓰면 W35(생략된 추론)를 채운다.

## 3. 독자 흐름 문제와 학습 적합성

### 독자 정보와 목표 대비
인덱스 기준 독자는 Helm 이론과 제품 결정, 홈랩 환경(Tailscale, systemd, SOPS)을 아는 제품 소유자이고, 목표는 구현이 끝난 코드를 리뷰하며 설계의 구조·동작·불변조건이 지켜지는지 스스로 판단하는 것이다. 노드 13의 이유는 "외부 접속, 기기 토큰, 도구 격리, 비밀 관리의 경계를 확인한다"이고 선수 노드는 2와 8이다. 글은 이 목표에 맞게 마지막에 점검 목록을 두었고, 점검 항목 대부분이 설계의 검사 가능한 불변조건이라 구성은 적합하다. 다만 아래 문제로 점검 목록의 신뢰도가 떨어진다.

1. 점검 목록의 정확성: T1(사유 구분), T5(검사 순서), T6(확인 문자열), T7(Host·Origin의 `loopback` 적용), T11(정식 데몬 한정)이 점검 항목의 판정 기준과 설계 사이에서 어긋난다. 이 글의 가치가 점검 목록에 있으므로 우선 고쳐야 한다. 빠진 점검 항목은 다음과 같다. (a) 맞는 토큰의 연결이 실패 지연과 무관하게 통과하는가, (b) 실패 지연이 X-Forwarded-For 기준이 아니라 확인된 노드 단위인가, (c) 토큰이 다른 전달 수단(헤더 기기의 쿠키)이면 `carrier_mismatch`인가, (d) 만료(절대, 유휴)가 hello에서 이벤트 없이 거부되는가, (e) 1차에서는 토큰 회전이 없는가, (f) 복원 뒤 Grant·합의 상태가 복원본 그대로라는 점(T2).
2. 같은 서버에서 도는 다른 에이전트: 경계 A 절은 "의도적 공격은 막을 수 없다"고 쓰지만 18 §3.5 규칙 7의 운영 권고(이 서버에서 같은 uid로 상시 도는 Claude Code·Codex에게 `helm` CLI를 쓰지 말라는 사용자 지침)를 쓰지 않았다. 독자가 정확히 그런 환경에서 일하므로(CLAUDE.md의 에이전트 구성), 경계 A가 현실에서 의미하는 바와 사람이 해야 할 일이 이 글에서 가장 직접적인 학습 가치다. 같은 이유로 규칙 7의 우회 경로(비대화 `localAdmin`으로 기기를 발급받아 `loopback`으로 붙으면 기기 주체가 됨)도 한 문장 필요하다. 글의 "비대화로 실행된 관리 CLI는 사람 결정을 내릴 수 없습니다"만 읽으면 이 우회가 막혀 있다고 오해하기 쉽다.
3. 2번과 8번 노드와의 중복:
   - 02는 리스너 셋, "루프백은 격리 경계가 아니다" 오해, 신원 헤더 + whois + 토큰 "셋 모두 필요", 같은 기기 프로세스가 헤더를 흉내 낼 수 있어 마지막 방어는 기기 토큰이라는 점, S0 예외까지 이미 설명한다. 13의 "외부 접속" 둘째·셋째 문단 첫 문장과 `loopback`·`local` 설명 일부가 02와 같은 말이다. 13이 더하는 새 내용(Host → Origin 순서와 응답 코드, whois 캐시와 fail closed, 전달 수단 불일치, 사유 비구분, 하위 프로토콜 미수용)에 집중하고, 02에서 이미 한 설명은 연결 한 문장으로 줄여야 한다(W1, W3 중 "같은 말의 반복").
   - 08은 S0·S1b·S1, 고정 기준선, 네트워크 차단, `taint.web`, 네트워크 차단 대역을 이미 다룬다. 13의 위협 표 "모델이 실행하는 bash"와 "네트워크 도구로 홈랩 내부 서비스 접근" 행, 경계 C 문단의 소켓·정본 디렉터리 가림, "프롬프트 주입" 절의 기준선 문단은 08의 재서술이다. 05·07도 `taint.web`과 발송 게이트를 이미 설명한다. 13에서 새로운 것은 신뢰 경계로 묶는 관점, `<untrusted>` 표식의 무작위 id와 엔티티 치환, 지침 파일 해시, 승인 화면의 구조 값 우선이다. 나머지는 "8번 노드에서 본 것"으로 위치만 짚고 줄이는 편이 낫다.
   - 12는 비밀 로드(자식 로더)와 복원 절차(위험 변경 재적용, 리스너 열기 전, 승인 만료, 안전 모드)를 이미 설명한다. 13의 "복원과 권한" 절은 12의 복원 문단과 네 가지 단계가 겹친다. 13에서 새로운 부분은 "왜 보안 문제인가"(폐기·회수 되살아남)와 "현재 DB를 열 수 없을 때의 전체 토큰 무효와 Grant·합의 잔존 위험"이다. 04는 HMAC 체크포인트와 키 필수를 설명한다(글의 해당 문장은 04 참조로 줄일 수 있고, T3의 범위 한정만 더하면 된다).
4. 수준: 지침상 독자는 이론과 결정을 아는 사람이라 기본 설명은 충분하다. 반면 홈랩 전문 용어(Funnel, tailnet 태그 노드, 마지막 hop)는 독자가 아는 범위로 보이나, 구현 리뷰 맥락의 용어("노드 묶기", "전달 수단", "주체")는 18의 정의가 필요하다.
5. 분량과 밀도: 한 글이 위협 모델 전체, 외부 접속, 등록·토큰, 프롬프트 주입, 웹 헤더, 비밀·감사·공급망, 복원을 모두 담는다(약 1.7만 자). 인덱스 노드 하나로는 많다. 중복 제거(위 3번)로 줄이고, 줄인 분량을 예시 하나(휴대폰 분실 시나리오, W9·W14)와 표 하나(리스너별 검사)에 쓰는 것이 학습에 유리하다. 비밀·감사·공급망 절은 사실 나열에 가깝고 리뷰 목표와의 연결이 약하다(점검 목록에 비밀·공급망 항목이 없다). 점검 목록에 최소한 "비밀이 도구 환경과 로그에 없는가", "HMAC 키가 없으면 시작을 거부하는가", "새 빌드 스크립트가 있으면 설치가 실패하는가"를 더하거나 절을 줄인다.
6. 논리 비약:
   - "경계 B ... 같은 호스트의 다른 OS 사용자가 이 경계 밖에 있습니다"는 18의 T-H4(다른 uid·root는 범위 밖)와 방향이 다르다. 18 §3.3은 경계 B가 "같은 호스트의 다른 OS 사용자 공간에서 오는 연결"에 대한 경계라고 쓰지만 T-H4는 다른 uid·root 자체를 범위 밖으로 둔다. 글은 앞의 서술만 썼고, 위협 표에 T-H4 행이 없는 이유가 설명되지 않는다.
   - 위협 표에서 "도난 노트북"의 대응이 "OS 키체인, 노드 묶기, 원격 폐기"인데 "노드 묶기"는 이 표 앞에서 정의되지 않았다(T7).
   - "복원과 권한" 절은 "복원은 보안 문제이기도 합니다"로 시작하며 12번 노드와 연결하지 않아, 독자가 12의 복원 단계를 기억한다고 가정하고 새로 요약한다(W6: 짧은 연결 문장이면 충분).

## 4. 표상 문제

- 렌더링: mermaid 11.4 `parse`가 `flowchart-v2`로 성공했다. 정적 `pre.mermaid`로 쓸 때는 라벨 안의 괄호와 쉼표가 모두 따옴표 안이라 문제가 없다.
- 구조 불일치: 그림 앞 문장은 "화살표는 '이 경계를 넘으려면 이것이 필요하다'는 뜻"이라고 하는데, 세 화살표의 의미가 다르다. B는 "넘으려면 기기 토큰이 필요하다"이지만 C는 "샌드박스가 있으면 넘지 못한다"(막는 장치이지 넘기 위한 조건이 아니다)이고 A는 "같은 uid면 모든 것이 가능하다"(넘는 데 필요한 것이 없다)이다. C의 화살표 `M → U`는 모델 코드가 샌드박스를 거쳐 일반 공간으로 갈 수 있다는 인상을 준다. 설계는 정반대로, 경계 C가 `M`이 `U`에 들어오지 못하게 막는다. 글 본문도 "들어오지 못하게 합니다"라고 쓴다.
- 누락: 18 §3.3 그림이 보여 주는 핵심(각 경계를 통과하는 입구: `tailnet`·`loopback` 리스너는 B, `local` 소켓은 A의 파일 권한, 도구는 C)과 `local` 리스너가 없다. 글은 본문에서 경계 A를 "같은 uid"로, 경계 B를 토큰으로 설명하는데 그림에는 `local` 소켓이 보이지 않아 "경계 A 안에 소켓이 있고 도구 샌드박스가 소켓을 가린다"는 가장 중요한 구조가 전해지지 않는다. 8번 노드와 중복 없이 이 노드의 위치를 보이려면 소켓(`rpc.sock`)과 샌드박스의 가림 관계를 그림에 넣어야 한다.
- 지식 구조: 경계 안팎의 포함 관계와 통과 조건이라 지식 구조는 "계층"과 "조건 조합"이다. 현재 그림은 선형 흐름도 3줄이라 계층을 담지 못한다. 포함 관계(helmd ⊂ 같은 uid ⊂ 호스트 ⊂ tailnet)를 `subgraph` 중첩으로 그리고 경계마다 "무엇이 막는가"(토큰, 샌드박스, 파일 권한)를 라벨로 붙이는 편이 맞다.
- 문장 연결: 그림 뒤 세 문단이 그림의 라벨을 그대로 다시 말한다(W22). 그림이 보여 주는 값(경계 이름과 통과 조건)은 글에서 가리킴만 하고, 글에는 그림에 없는 것(이유, 한계, 예: 경계 A를 지키지 않는 근거, S0에서 전제가 깨지는 이유)을 써야 한다.
- 위협 표(14행, 3열)는 표상으로 적합하나 경계 열이 없다(2절 W20·W22).

## 5. 지침 부작용

- W16(출처·근거 수준 표시 금지)과 W17(확인한 사실만 단정): 설계 문서 안에 [제안], [결정], [실험], [가정] 표시가 있고 값이 아직 확정되지 않은 곳이 많다(속도 상한, 인증 실패 지연 값, 검사 순서의 의사 코드, 기기 키 서명 1차 꺼짐 등). 지침을 지키면 글에서는 상태 표시가 사라져서 독자는 "확정된 규칙"과 "제안 단계의 값"을 구분하지 못한다. 이 글에서 T4, T5가 그 예다. 관련 규칙: W16, W17. 빈도: 이 글에서 3곳 이상. 제안: W17의 "사실 자체가 정해져 있지 않은 경우는 그 상태를 내용으로 쓴다"를 확장해, 설계 문서가 확정하지 않았거나 문서끼리 다른 값은 "아직 18과 19가 다릅니다" 식으로 본문에 쓰도록 예시를 지침에 넣는다.
- W23(글 머리 개요 금지)와 시리즈 글: 학습 인덱스 노드는 선수·후속과 이어지는 시리즈라 앞 노드와의 위치를 알리는 짧은 연결이 필요한데, 지침은 개요 문단을 금지하고 "절 사이 위치를 알리는 표현"을 조건부로 허용한다. 글은 이 사이에서 "이 노드의 범위"라는 개요 절을 만들었다. 관련 규칙: W6, W23. 빈도: 1곳. 제안: 시리즈 글의 첫머리에는 "앞 노드 의존 한두 문장"을 허용하고, 본문 전체의 나열은 금지한다고 구분해 쓴다.
- W31(능동 과제와 점검 질문 금지)와 구현 리뷰 점검 목록: 인덱스 목표가 "리뷰 기준을 갖는다"라서 글마다 점검 목록이 필요한데, 지침은 이해 점검 질문을 본문에 넣지 말라고만 한다. 글은 이 둘을 구분해 점검 목록을 썼다. 관련 규칙: W30, W31. 빈도: 1곳(그리고 08에도 있음). 제안: "구현 검토 기준(이해 점검 질문이 아님)은 시리즈 목표가 요구하면 마지막 절에 둔다"를 W31에 예외로 명시한다.
- W51(의인화 금지)로 고치다가 문장이 길어지는 경향: "설계가 ~한다" 대신 피동이나 명사형으로 옮기면 행위자가 흐려진다(예: "적혀 있습니다"). 지침이 제시하는 순서(실행 주체 → 상태 → 순서)를 보안 문서에서 "설계 문서가 정한 규칙은 ~입니다"처럼 쓰는 방법이 있는지 예시를 더하면 좋다. 관련 규칙: W51. 빈도: 이 글 1~2곳. 제안: "설계 문서"는 기록물로서 "정의합니다/적혀 있습니다"는 허용 동사로 W51 허용 목록에 둔다.

## 6. 전체 평가

구조와 목적은 적합하다. 신뢰 경계를 위협 표와 점검 목록으로 연결해 구현 리뷰에 쓰게 한 점, 사람 결정 권한을 핵심 자산으로 세운 점, 대부분의 사실(토큰 형식·수명, 페어링 코드, 쿠키 속성, 응답 헤더, 폐기 효과, 주입 대응, 복원 순서)이 18·19·26 원문과 맞는다. 다이어그램 문법도 통과한다.

고칠 것은 세 가지로 모인다. (1) 점검 목록이 설계와 어긋난 곳(인증 실패 사유 구분, 확인 문자열, 검사 순서, `loopback`과 노드 묶기)과 복원 뒤 확인 대상이 틀린 곳이 리뷰 판정을 흐린다. (2) 18과 19가 다른 지연·차단 서술과 18 내부의 검사 순서 불일치를 글이 한쪽으로 단정하거나 합쳤다. (3) 02·08·12와의 중복이 크고 예시와 표 같은 표상이 부족하다. 그림은 화살표 의미가 경계마다 달라서(C는 막는 장치) 본문과 어긋나고, `local` 소켓이 빠졌다.

의인화 위반은 "설계가 ~"(사용자 금지) 1곳과 인지 동사 몇 곳이다. '축', '박다', '가른다', '닿다'와 "A가 아니라 B" 구호는 본문에 없다.
