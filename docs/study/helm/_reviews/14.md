## 1. 기술 문제

높음 2건, 중간 8건, 낮음 4건. 메시지 형식, 핸드셰이크 순서, seq와 `(from, to]` 계약, `replay.outOfRange` 네 사유와 캐시 처리, 송신 큐 우선순위와 8/16 MiB·10초, 휘발 스트림의 번호 체계, 무효화 정확성 규칙, 파일 한도와 티켓, 버전 협상, 연결 상태 여덟 가지, 닫는 코드 값은 원문과 맞는다. 문제는 두 곳에 몰려 있다. 하나는 "무엇이 같고 무엇이 다른가"를 한 문장으로 줄이다가 리뷰 기준이 틀어진 곳(T1, T2)이고, 다른 하나는 구현 리뷰 체크리스트가 기대는 규칙의 조건이 빠진 곳(T3~T10)이다.

### T1. 높음 / 과도한 일반화 + 생략으로 생긴 오해 + 앞 노드와 모순: "경로마다 다른 것은 받는 인증 방식뿐"
- 인용: "**세 경로 모두 같은 HTTP + WebSocket 코드를 쓰고, 경로마다 다른 것은 받는 인증 방식뿐입니다.**"(§세 경로, 하나의 대화), 체크리스트 "세 리스너가 같은 처리기를 쓰고, 리스너별 차이가 인증 방식 허용뿐인가."
- 1차 자료: 19 P-01은 "같은 HTTP + WebSocket 스택을 쓰고 **전송 조건과** 받는 인증 방식만 다르다"이다(§2.3). §3.2.1 표는 리스너마다 전송 조건이 다르다고 적는다. `tailnet`은 Tailscale 신원 헤더 확인(`tailscale whois` 대조), Host 검사, 갈래별 Origin 검사이고, `loopback`은 Host·Origin 허용 목록만 보고 Tailscale 헤더를 요구하지 않으며, `local`은 소켓 파일 권한(0600/0700)이다. 쿠키는 `tailnet`에서만 읽는다. §3.2.5 표는 받는 HTTP 경로도 리스너마다 다르다고 적는다(`/m/*`, `POST /m/pair`, `/m/cmd`, `POST /pair`는 `tailnet`만, `loopback`에서 `/m/*`와 `/pair`는 404). 받는 인증 방식도 `tailnet`은 `deviceToken`, `local`은 `deviceToken`·`localAdmin`·`runtimeAdapter`다(§3.2.1, §3.4.2). 노드 2의 표와 노드 13의 tailnet 검사 순서도 "Tailscale 신원 + whois + 기기 토큰", "SSH 키 + 기기 토큰", "소켓 권한"으로 인증 조건 자체가 리스너마다 다르다고 적는다.
- 문제: 원문의 "전송 조건과"가 빠져 "인증 방식 허용 외에는 동작이 같다"로 읽힌다. 이 문장이 굵은 글씨의 결론이고 체크리스트 항목이기도 해서, 리뷰어가 Host/Origin/Tailscale 신원 검사의 리스너별 차이나 `/m/*` 경로의 `tailnet` 전용 처리를 버그로 지적하는 방향으로 틀어진다. "같은 처리기"가 어디까지인지도 흐려진다(공유하는 것은 HTTP/WebSocket 스택, 메서드 디스패치, 메시지 열이고 연결을 받기 전의 검사는 리스너별로 따로 있다).
- 수정 제안: "같은 HTTP + WebSocket 코드와 같은 메서드 집합을 쓰고, 리스너마다 다른 것은 연결을 받기 전 전송 조건(Host·Origin·Tailscale 신원·소켓 권한), 받는 HTTP 경로, 받는 인증 방식이다"로 바꾼다. 체크리스트도 "공통 처리기 위에서 리스너별 차이가 이 세 가지로 한정되는가. 같은 적합성 시험이 세 리스너와 ssh -W에서 통과하는가"로 맞춘다.

### T2. 높음 / 오기 + 생략으로 생긴 오해: 재연결 순서의 대조 대상과 저장소 교체 처리
- 인용: "`hello`가 성공하면 동기화 상태로 들어가 저장된 서버 ID와 기기 ID를 대조하고, 저장된 위치로 구독을 복원하고, 모든 구독이 따라잡으면 준비 상태로 가서 낡은 열린 뷰를 다시 받습니다. 진행 중이던 명령의 재전송은 구독이 복원된 뒤에 시작하고"(§생존 확인과 재연결)
- 1차 자료: 19 §3.10.2 상태 기계와 §3.4.2. 서버 ID 대조는 `hello` 전, `handshaking` 상태에서 `hello.challenge`를 받았을 때 한다(불일치면 `hello`를 보내지 않고 `needsUser`, kind `server.mismatch`). `hello` 성공 뒤 `syncing`에 들어가며 대조하는 것은 `hello.log.storeId`와 `hello.connection.deviceId`를 진행 중 명령함 항목의 `storeId`·`deviceId`와 맞춰 보는 일이다. `storeId`가 다르면 `clearServer(serverId, "all")`을 먼저 부르고 그 항목을 자동 재전송에서 뺀다. 20 §3.9.6 단계 1도 같다("hello.challenge → serverId 비교 → hello → syncing, 코어가 hello.log.storeId를 저장 위치의 storeId와 비교하고 다르면 먼저 clearServer"). 적합성 시험 CT-08은 "진행 중 명령의 재전송이 `2001`보다 먼저 나가지 않고 `hello.log.storeId`가 다르면 재전송 전에 캐시를 비운다"를 요구한다.
- 문제: 글은 서버 ID 확인 시점을 `hello` 뒤로 옮겼고, 기기 ID와 `storeId`를 무엇과 대조하는지 쓰지 않았다. 이 단계가 복원된 저장소에 옛 명령이 다시 적용되지 않게 하는 핵심 안전장치(19 F-42)인데, 글에서는 `storeId` 변경이 `replay.outOfRange`(구독 단계)로만 보인다. 리뷰어가 "구독 복원 전 `hello.log.storeId` 대조와 보류 처리"를 점검 항목으로 갖지 못한다.
- 수정 제안: 순서를 "챌린지의 서버 ID 확인(불일치면 멈춤) → `hello` → 동기화 상태 진입 시 `hello.log.storeId`·기기 ID를 진행 중 명령함 항목과 대조(다르면 그 항목은 자동 재전송에서 빠지고 `storeId`가 다르면 캐시 폐기) → 구독 복원 → …"로 고친다. 체크리스트 마지막 항목에 "`storeId`가 달라진 진행 중 명령이 재전송되지 않는가"를 더한다.

### T3. 중간 / 글 안의 모순 + 생략: `dependsOn`이 레코드 ID 목록뿐이라는 서술
- 인용: "이 뷰를 만들 때 읽은 레코드 ID 목록(`dependsOn`)", "이벤트마다 커밋 때 계산된 `invalidates`(영향받은 레코드 ID와 집계 이름)가 붙어 오고, 이 집합이 열린 뷰의 `dependsOn`과 겹치면"(§화면 데이터)
- 1차 자료: 19 §3.6.3. `dependsOn: Type.Array(InvalidationTag)`이고 태그는 "레코드 ID 또는 집계 이름(`@` 접두)"이다. "뷰 처리기는 뷰를 만들 때 읽은 레코드 ID와 집계 이름을 `dependsOn`에 넣는다." 홈, 질문함 같은 뷰는 기본 집계 태그(`@home`, `@inbox` 등)로 동작한다(§3.7.4 표). 태그 수가 상한(이벤트당 64, 뷰당 512)을 넘으면 집계 이름 하나로 대체한다.
- 문제: 글의 정의대로면 `dependsOn`에는 집계 이름이 없어서 집계 이름 태그는 어느 뷰와도 겹칠 수 없다. 글 안의 두 서술이 맞지 않고, 독자는 모든 뷰가 읽은 레코드 ID를 전부 나열한다고 이해한다. 상한 초과 때 집계 이름으로 넓히는 규칙("넓게 다시 받는 쪽으로 틀리는 것은 괜찮다")의 구체 사례도 빠졌다.
- 수정 제안: "읽은 레코드 ID와 집계 이름(`@inbox` 같은 이름)의 목록"으로 쓰고, 태그가 상한을 넘으면 집계 이름 하나로 줄인다는 한 문장을 정확성 규칙 문단에 더한다.

### T4. 중간 / 생략으로 생긴 오해: 멱등 결과는 일부만 저장되고, 거부 뒤에는 새 키를 쓴다
- 인용: "서버는 같은 키와 같은 지문이면 저장된 결과를 `duplicate: true`로 돌려주고, 같은 키에 다른 내용이면 거부합니다.", "응답을 못 받았거나 재연결했거나 다른 경로로 바꿔서 다시 보낼 때는 같은 키와 같은 내용을 보냅니다."(§명령 보내기)
- 1차 자료: 19 §3.9.2와 09 §3.9.2. 저장되는 결과는 accepted, needs_gate, 거부(내용·자격·경로), conflict(버전 불일치·이미 해결됨·대체됨)다. 같은 키로 다시 보내면 같은 거부가 다시 오고, "상황이 바뀐 뒤 다시 하려면 새 키가 필요하다(사람이 '다시 보내기'를 누르면 앱이 새 키를 만든다)". 저장되지 않는 결과(1단계 검증 오류, 3006, 5001~5004, 커널 내부 오류, 일시 실패)는 같은 키로 다시 보내면 처음부터 다시 처리한다.
- 문제: 글은 "재전송은 같은 키"만 말해서, 충돌(3004·3008·3009) 뒤에 같은 키를 다시 쓰는 코드가 맞는 것처럼 읽힌다. 실제로는 같은 키가 같은 충돌을 되돌려 줄 뿐이라, 앱이 초안을 되살려 사람이 다시 판단한 뒤 새 키를 만들어야 한다. 글의 충돌 문단은 초안 되살리기까지만 쓰고 새 키는 쓰지 않는다. 구현 리뷰에서 "충돌 뒤 새 키를 만드는가"와 "저장되지 않는 오류에서는 같은 키 재전송이 안전한가"를 점검할 근거가 없다.
- 수정 제안: 멱등 문단에 "거부·충돌도 저장되므로 같은 키로 다시 보내면 같은 거부가 온다. 사람이 판단을 바꿔 다시 보낼 때는 새 키를 만든다"와 "검증 오류, 일시 실패, 내부 오류는 저장되지 않아 같은 키로 다시 보내도 된다"를 더한다. 체크리스트에 "충돌·거부 뒤 사람이 다시 보낼 때 새 키를 만드는가"를 추가한다.

### T5. 중간 / 생략으로 생긴 오해: 멱등 범위와 지문에는 행위자와 출처(기기)가 들어간다
- 인용: "지문에는 연결 ID, 리스너, `basisSeq`가 들어가지 않으므로, 화면이 다시 그려져 `basisSeq`가 바뀌어도 같은 명령으로 인식됩니다(4번 노드)."
- 1차 자료: 09 §3.9.1. 범위 키는 `channel|actor|viaKey(via)|idempotencyKey`이고 지문은 `{type, actor, viaKey(via), payload − 생성 ID}`의 해시다. 사람 명령의 `viaKey`는 `device:<deviceId>` 또는 `local_cli:<uid>`다. 19 §3.9.1 (3)과 F-06은 "다시 페어링해 `deviceId`가 바뀌면 멱등 범위가 바뀐다"고 적고 그런 항목은 자동 재전송에서 뺀다. 노드 4(§멱등 키와 지문)는 "명령 종류, 행위자, 출처, 내용의 해시"라고 이미 적었다.
- 문제: 빠진 값만 나열해 무엇이 지문에 있는지는 글에서 알 수 없다. 독자는 "경로가 달라도 키와 내용이 같으면 중복"으로만 이해하고, 다른 기기나 재페어링 뒤에는 같은 키가 중복이 아니라는 조건(체크리스트 "재전송이 같은 키와 같은 내용이고"가 놓치는 부분)을 모른다.
- 수정 제안: "같은 기기·행위자가 같은 키와 같은 내용을 어느 연결·리스너·경로로 보내도 같은 명령이고, 기기가 바뀌면(재페어링 포함) 범위가 달라진다"를 한 문장으로 넣는다. 노드 4와 겹치는 지문 정의는 줄이고 노드 4를 가리킨다.

### T6. 중간 / 생략으로 생긴 오해: 자동 재전송에서 빠지는 명령
- 인용: "진행 중이던 명령의 재전송은 구독이 복원된 뒤에 시작하고, 동기화 중에는 사람 결정 명령을 보내지 않습니다.", "등록 표의 해시(`schemaHash`)가 같으면 양쪽 스키마가 같다는 뜻이고, 재연결 때 저장된 명령을 다시 보낼지 판단하는 데도 씁니다."(§생존 확인과 재연결, §버전)
- 1차 자료: 19 §3.9.1. 자동 재전송에서 빠져 "보내지 못한 조작"이 되는 경우는 (1) `pendingCommandMaxAgeMs`(기본 24시간) 초과, (2) `storeId` 불일치, (3) `deviceId` 불일치, (4) 프로토콜 버전·`schemaHash`가 바뀌었고 params가 새 스키마를 통과하지 못함, (5) 저장되지 않는 영구 오류(-32600, -32601, -32602, 5007), (6) `5003 readOnly`다. 이 항목은 앱이 입력을 초안으로 되살리고, 사람이 다시 보내기 전에 `command.lookup { idempotencyKey }`로 이미 커밋됐는지 먼저 확인한다(그래서 24시간이 지난 명령도 두 번 적용되지 않는다). `schemaHash`는 다르다는 것만으로 제외하지 않고 새 스키마 통과 여부로 가른다.
- 문제: 글에서는 재전송 대상이 "진행 중이던 명령"이라는 한 덩어리이고, 24시간 한도, `command.lookup`, 제외 사유가 없다. "동기화 중에는 사람 결정 명령을 보내지 않는다"와 "구독이 복원된 뒤(동기화 중) 진행 중 명령을 재전송한다"가 나란히 있어 독자가 충돌로 읽을 수 있다(전자는 새 사람 결정, 후자는 이미 보낸 명령의 같은 키 재전송이라는 구분이 없다). `schemaHash` 설명은 "해시가 다르면 재전송 안 함"으로 읽힌다.
- 수정 제안: 재전송 문단에 위 제외 사유를 요약(여섯 항목은 짧은 나열 허용)하고, 제외된 항목은 초안으로 되살아나며 다시 보내기 전에 `command.lookup`을 부른다고 쓴다. "동기화 중 사람 결정 명령 금지"는 "새 결정은 막고, 이미 보낸 명령은 같은 키로 다시 보낸다"로 구분한다. `schemaHash`는 "스키마가 달라졌을 때 저장된 params가 새 스키마를 통과하는지 판단하는 데 쓴다"로 고친다.

### T7. 중간 / 과도한 일반화: "명령 응답 전에 결과 이벤트가 도착한다"의 조건
- 인용: "그래서 명령을 보낸 연결은 응답을 받을 때 그 응답의 `lastSeq`까지의 이벤트를 이미 받은 상태입니다(재전송 중인 구독은 예외)."(§이벤트 구독과 재전송)
- 1차 자료: 19 §3.5.9. "요청한 연결의 실시간 구독(필터에 맞는 경우)에서는 응답의 `lastSeq`까지의 이벤트가 응답보다 먼저 도착한다. 재생 중인 구독은 이 보장이 없다. 클라이언트는 응답의 `lastSeq`와 자기 구독 위치를 비교해 '반영됨'을 판단한다." `POST /m/cmd`(HTTP)는 WebSocket 구독과 별개 경로라 같은 보장이 성립하지 않는다(§3.9.4). `CommandResult.lastSeq`는 이벤트가 없으면 null이다.
- 문제: 예외가 재전송 중 하나뿐인 것처럼 쓰였다. 필터가 결과 이벤트를 걸러 내는 구독, 이벤트 구독이 없는 연결, `/m/cmd` 경로는 같은 보장이 없다. 글은 클라이언트가 `lastSeq`와 자기 위치를 비교해 반영 여부를 판단한다는 사실도 쓰지 않아서, 체크리스트 "커밋 뒤 결과 이벤트가 명령 응답보다 먼저 큐에 들어가는가"만 서버 쪽 시험으로 남고 클라이언트 쪽 점검이 빠진다.
- 수정 제안: 보장 범위를 "응답을 보낸 연결의 실시간 이벤트 구독 중 필터에 맞는 것"으로 좁히고, 클라이언트는 `lastSeq`와 구독 위치를 비교해 반영 여부를 판단한다는 문장과 `/m/cmd`는 이 보장 밖이라는 한 줄을 더한다.

### T8. 중간 / 글 안의 모순 + 의미 변경: 휘발 상태를 언제 지우는가
- 인용: "영속 이벤트(메시지 완성, 도구 결과)가 오면 같은 메시지의 휘발 상태를 버리는데, 마지막 조각이 영속 커밋 순번을 싣고 오므로 클라이언트는 그 순번을 받을 때까지 휘발 상태를 지우지 않습니다."(§이벤트 구독과 재전송, 마지막 문단)
- 1차 자료: 19 §3.6.4. 영속 이벤트(메시지 완성, 도구 결과, run 종료)를 받으면 해당 `messageId`·`toolCallId`의 휘발 상태를 버린다. 별도 규칙으로 `end` 조각은 run을 끝내는 영속 이벤트가 커밋된 뒤 보내고 `finalSeq`를 싣는다. "클라이언트는 이벤트 구독이 `finalSeq`를 받기 전까지 휘발 상태를 지우지 않는다(화면이 잠깐 비는 것을 막는다)." 20 §3.9.6도 같다. 또 `afterSeq`가 클라이언트 위치보다 크면 조각 적용을 미룰 수 있다.
- 문제: 같은 문장에서 "영속 이벤트가 오면 버린다"와 "그 순번을 받을 때까지 지우지 않는다"가 이어져 서로 부딪힌다. `finalSeq`는 메시지마다가 아니라 run 종료 `end` 조각의 값이고, 지우는 시점의 기준은 구독이 받은 위치(`finalSeq`를 넘었는지)다. 체크리스트에는 이 항목이 없다.
- 수정 제안: 두 규칙을 나눠 쓴다. "메시지 완성 이벤트가 오면 그 메시지의 휘발 텍스트를 버린다. run이 끝날 때 오는 `end` 조각에는 run 종료 이벤트의 순번(`finalSeq`)이 있고, 이벤트 구독이 그 순번에 이를 때까지 해당 run의 휘발 상태를 지우지 않는다. 그래야 영속 내용이 화면에 오기 전에 텍스트가 사라지지 않는다."

### T9. 중간 / 부분적으로 틀림: 휘발 스트림 구독 단위
- 인용: "휘발 스트림은 run 단위로 구독하고(`stream.subscribe`), 조각마다 run 안의 번호가 붙어 빠진 조각을 알 수 있습니다."
- 1차 자료: 19 §3.6.4 `StreamScope`는 `{concernId}`, `{runId}`, `{workUnitId}`, `{all: true}` 넷이다. §3.6.1 표는 "실행 중 휘발 조각: `stream.subscribe({scope})`, 대화 패널·진행 작업 카드"로 쓴다. 조각 번호 `n`은 run 안에서 1씩 오른다(버린 조각도 번호 소비). 구독 응답의 `active`가 범위 안의 현재 run 상태를 준다.
- 문제: 구독 단위(Concern·run·작업·전체)와 번호 단위(run)가 한 문장에서 섞였다. 리뷰어가 `stream.subscribe`의 범위를 run으로 한정하는 구현을 맞다고 볼 수 있다.
- 수정 제안: "구독 범위는 Concern, run, 작업 단위, 전체 중 하나이고, 조각 번호는 run마다 1부터 센다"로 고친다. 재접속 때 `active`로 현재 상태를 받고 `run.partial`로 유실을 복원한다는 한 문장도 더하면 체크리스트의 휘발 항목과 이어진다.

### T10. 중간 / 비슷한 용어의 기준 혼동: 오류 코드 범위와 닫는 코드의 이름 공간
- 인용: "1xxx는 핸드셰이크·인증·권한 범위·속도, 2xxx는 구독·재전송·뷰, 3xxx는 명령 결과, 4xxx는 파일, 5xxx는 데몬 상태·취소·시한입니다.", "WebSocket 닫는 코드도 Helm이 쓰는 것이 정해져 있습니다. 4000은 클라이언트의 생존 감시 시간 초과, 4001은 핸드셰이크 시한, 4008은 느린 소비자, 4009는 기기 폐기·만료나 기기당 연결 초과입니다."(§오류 코드)
- 1차 자료: 19 §3.3.4와 §3.2.6, J-344. "오류 코드와 WebSocket 닫는 코드는 다른 이름 공간이며 이미 1008, 1001, 1011, 4001이 겹친다." 오류 코드 4001은 `blob.tooLarge`, 4008은 `web.tooLarge`, 4009는 `web.unsupportedType`이고, 닫는 코드 4001·4008·4009는 위 의미다. 3010 `browser.staleRef`, 3011 `edit.staleSnapshot`은 명령 결과가 아니라 도구 결과로 온다(J-344). 4008~4010, 5008도 모델용 웹 도구 오류다. 오류 코드 1008(`auth.methodNotAllowed`)과 닫는 코드 1008(정책 위반)도 다른 것이다.
- 문제: 두 번호 체계가 한 절에 이어져 있어 "4008"이 파일 오류인지 느린 소비자인지 글만으로 구분되지 않는다. 범위 설명도 "3xxx는 명령 결과, 4xxx는 파일"로 일반화돼 3010·3011과 4008~4010(웹 도구)이 설명되지 않는다. 구현 리뷰에서 번호만 보고 판정하는 실수를 부를 수 있다.
- 수정 제안: "닫는 코드(WebSocket 프레임)와 오류 코드(JSON-RPC 응답의 `error.code`)는 이름 공간이 다르고 1008, 4001처럼 숫자가 겹친다"를 명시하고, 범위 설명에 "3xxx는 명령 결과와 일부 도구 결과, 4xxx는 파일과 웹 도구"를 반영한다. 닫는 코드는 표로 분리하는 편이 낫다(§4 R2).

### T11. 낮음 / 조건 생략: 정책 기본값을 고정 사실처럼 씀
- 인용: "서버는 15초마다 WebSocket ping과 함께 `tick`", "35초 동안 아무것도 오지 않으면", "송신 큐가 8MiB를 넘으면", "파일 하나는 64MiB까지입니다", "결과는 365일 보관", "5분 유효"

- 수정 제안: 처음 나오는 곳에 "기본값"이라고 쓰고, 정책에서 읽는 값은 "기본 15초"처럼 적는다.

### T12. 낮음 / 과도한 일반화: TUI와 인증 수단
- 인용: "WebSocket 업그레이드 요청의 헤더(`Authorization: Bearer`, 데스크톱·TUI)", "서버 안의 TUI와 관리 CLI는 Unix 소켓(`local` 리스너)으로 붙습니다."
- 1차 자료: 19 P-03은 "데스크톱·TUI는 Authorization: Bearer 헤더"라고 쓰지만, §3.2.4는 `local` 리스너의 TUI·관리 CLI는 기본이 `localAdmin`(소켓 접근 자체가 근거, TUI는 `interactive: "tui"`, CLI는 표준 입출력이 모두 터미널일 때 `tty_cli`와 `localConfirm`)이고 TUI를 기기로 페어링하면 `deviceToken`도 쓸 수 있다고 한다. `runtimeAdapter`는 외부 런타임 브리지의 run 단위 토큰이다. 19 문서 안에서도 P-03과 §3.2.4의 서술이 어긋난다.
- 문제: 글은 TUI를 헤더 토큰 기기로만 쓰고 `localAdmin`·`runtimeAdapter`는 한 번도 말하지 않는다. 로컬 경로의 기본 인증이 토큰이 아니라는 사실이 빠진다(범위 문제는 §3 L6에 따로 쓴다).
- 수정 제안: "TUI와 관리 CLI는 기본이 `localAdmin`이고 기기로 페어링하면 토큰도 쓸 수 있다"로 쓰고, 문서 간 불일치는 사용자 확인 항목으로 알린다.

### T13. 낮음 / 표현 부정확: "메서드 하나에 커널 명령 하나"

## 2. 지침 위반

### 사용자 문체 요구 / W52 / W38
- 금지어 검색: 글에는 '축', '박다', '가른다', '닿다'가 없다. 합니다체는 전체에서 지켜진다. 구호형 "A가 아니라 B다"는 한 곳이다. "질문으로 바뀐 경우는 오류가 아니라 `gated` 성공 응답입니다."(§오류 코드). 사실 대비라서 W38의 "대비를 보이는 부정"으로 허용되지만, 사용자 요구를 엄격히 적용하면 "질문으로 바뀐 경우는 `gated` 상태의 성공 응답으로 돌아옵니다"로 바꿀 수 있다.
- 단순 부정: "빠뜨리거나 명령을 두 번 보내지 않는가", "배치 요청은 받지 않습니다", "프로토콜은 순번을 새로 매기지 않고"는 대비 없는 부정이다. 각각 "빠짐없이 받고 한 번만 보내는가", "배치 요청은 오류로 응답합니다", "프로토콜의 위치 값은 정본 로그의 seq 그대로입니다"처럼 긍정문으로 바꿀 수 있다. 기각한 방식을 서술하는 "쓰지 않습니다"(JSON Patch)는 대비를 보이는 부정이어서 허용한다.

### W51 의인화
판정 기준: 주어가 실제 실행 주체(서버, 클라이언트, 데몬, 앱, 커널, 처리기)이고 동사가 실행 동작이면 허용한다. 주어가 데이터·규칙·프로토콜·알림·응답 필드이고 행위 동사나 발화·인지 동사를 쓰면 위반이다.
- "앱이 할 수 있는 일은 이 프로토콜이 허용하는 것뿐입니다"(§왜 이 계약이 중요한가): 프로토콜(명세)이 주어이고 "허용하다". 수정: "앱이 보낼 수 있는 요청은 프로토콜에 정의된 메서드뿐입니다".
- "이 메서드가 허용한 것 이상을 하지 않는가"(같은 절): 메서드가 주어. 수정: "데몬이 메서드의 권한 범위를 넘어 동작하지 않는가".
- "알림 하나는 그 구간에서 필터에 맞는 이벤트를 … 담고, … 빈 알림으로 위치를 넘겨 줍니다"(§이벤트 구독과 재전송): 알림(데이터)이 주어, "담다", "넘겨 주다". 수정: "서버가 보내는 알림 하나에는 그 구간에서 필터에 맞는 이벤트가 … 들어 있고, … 서버가 빈 알림을 보내 위치를 앞으로 옮깁니다".
- "프로토콜은 순번을 새로 매기지 않고 정본 로그의 seq를 그대로 씁니다"(굵은 문장): 프로토콜이 주어이고 "매기다", "쓰다". 수정: "프로토콜의 위치 값은 정본 로그의 seq 그대로이고, 프로토콜 계층에서 따로 순번을 만들지 않습니다".
- "화면 응답의 `asOfSeq`가 그 데이터에 이미 반영된 순번을 알려 주므로": 필드가 주어이고 "알려 주다". 수정: "화면 응답의 `asOfSeq`는 그 데이터에 반영된 마지막 순번이므로".
- "마지막 조각이 영속 커밋 순번을 싣고 오므로": 조각이 주어. 수정: "마지막 조각에 영속 커밋 순번이 들어 있으므로".
- "규칙은 한 방향만 보장합니다"(§화면 데이터): 규칙이 주어. 수정: "이 규칙이 요구하는 것은 한 방향뿐입니다".
- "프로토콜은 이를 오류 코드로 돌려줍니다"(§명령 보내기): 수정: "서버가 이를 오류 코드로 돌려줍니다".
- "서버가 알려 준 재시도 시간을 하한으로 지킵니다"(§생존 확인과 재연결): "알려 주다"는 발화 동사. 수정: "응답에 담긴 재시도 대기 시간(`retryAfterMs`)을 하한으로 씁니다".
- "서버가 이전 값을 기억했다가 변경분을 보내는 방식"(§화면 데이터): "기억하다"는 인지 동사. 수정: "서버가 이전 값을 저장해 두었다가".
- 허용으로 판정한 것: "서버는 … 처리합니다", "클라이언트는 … 저장하고", "데몬은 … 큐에 넣고", "앱은 … 되살리고"는 실행 주체의 동작이다. "응답에는 … 들어 있습니다", "오류 객체에는 … 들어갑니다"는 상태 서술이다.

### W32 연결어 없는 나열
- §메시지 형식 첫 단락(요청, 응답, 알림, `id`, `params`, 배치, 서버→클라이언트 요청, 클라이언트→서버 알림): 여덟 가지 규칙이 연결어 없이 이어진다. 그대로 나열이 맞는 병렬 규칙이므로 목록(W30 허용)이나 짧은 표가 낫다.
- §오류 코드 첫 단락, §큰 데이터 첫 단락, §버전 단락: 앞 사실이 뒤 사실의 이유인 관계가 문장에 없다. 특히 "WebSocket 메시지에는 파일 바이트를 싣지 않습니다"의 이유(메시지 상한과 재전송 범위, base64 첨부가 프레임 한도를 넘은 사례)가 없다. 19 §3.11.1이 이유를 적고 있다.

### W26 한 단락의 새 개념 수
- §연결에서 첫 화면까지 마지막 단락("`hello` 응답에는 연결 정책(…)이 들어 있습니다 …"): 연결 정책 여덟 항목, 저장소 정보, 복귀 요약 확인 위치를 한 단락에 넣었다.
- §이벤트 구독과 재전송 "재전송할 수 없는 경우도 있습니다" 단락: 네 사유, 두 갈래 캐시 처리, gap까지 새 개념이 다섯 이상이다. 표(사유와 클라이언트 처리)가 필요하다(§4 R2).
- §명령 보내기 "서버는 명령을 이렇게 처리합니다" 단락: 검사 다섯 가지와 변환·제출·응답 상태 세 가지.
- §생존 확인과 재연결 두 번째 단락: 상태 여덟 가지 이름과 백오프 규칙과 자동 재연결 중단 조건.

### W2 정의 없이 쓴 용어
- "터미널 확인 문자열"(§명령 보내기): 관리 CLI가 사람 결정 명령마다 받는 4자 코드(`localConfirm`)인데 정의도 이유도 없다. 앞 노드에도 없다(13에 `localConfirm` 없음).
- `decide`, `decideMobile`, `devices`, `admin`(§명령 보내기): 권한 범위 이름만 나열하고 무엇이 어떤 주체에 주어지는지 없다(휴대폰은 `decideMobile`, 비대화 `localAdmin`은 `decide`를 받지 않음). 체크리스트에서 쓰는 개념인데 설명이 없다.
- "스냅숏 경로"(체크리스트 `replay.outOfRange`로 스냅숏 경로를 타는가): 본문에는 "현재 위치(`head`)부터 구독하고 열린 화면을 다시 받습니다"만 있고 "스냅숏 경로"라는 말은 처음 나온다. 설계 원문 표기 "스냅샷"과도 다르다.
- "지수 백오프에 무작위 지연을 더하고"(§생존 확인과 재연결): 값의 모양(0.5초부터 두 배씩, 최대 30초, 절반 지터)이 없다. W45와도 이어진다. "디바운스"는 React 개발자 수준에서 허용한다.
- "gap", "느린 소비자", "`BlobRef`"는 문장 안에서 뜻이 드러나 허용한다.

### W43 용어 불일치
- "스냅숏"(체크리스트)과 설계의 "스냅샷". 노드 4·12의 표기를 확인해 맞출 것.
- "권한 범위(scope)"와 "scope 부여"(§연결에서 첫 화면까지)가 한 단락에서 둘 다 나온다. 한 가지로 정한다.
- "화면 캐시", "열린 화면", "열린 뷰"가 체크리스트와 본문에서 섞인다. §화면 데이터에서 "화면 데이터는 … 뷰"로 정의했으므로 "뷰"로 모은다.

### W16 출처 표기
- 본문에 출처 번호나 링크는 없다. "(1번 노드)", "(4번 노드)", "(5번 노드)", "(13번 노드)"는 노드 간 연결 표기로 W6의 "먼저 짚기"에 해당해 허용한다.

### W48 같은 말의 반복
- "구독을 먼저 열고 화면 데이터를 나중에 받는다"가 그림 앞 안내문과 굵은 문장 단락에 반복된다. 두 곳은 같은 말이다.
- "서버가 영속 이벤트를 버리지 않는다"가 §이벤트 구독, 송신 큐 단락, gap 설명, 체크리스트에 4번 나온다. 각각 맥락이 다르나 gap 문장("서버가 영속 이벤트를 버리지 않으므로 정상 동작에서는 생기지 않습니다")은 앞 설명의 되풀이다.

### W31 본문 속 질문
- 체크리스트 16개 항목이 모두 "~하는가"로 끝난다. 학습 점검 질문이 아니라 구현 리뷰 기준이어서 인덱스의 노드 14 목적과 다른 노드 글의 관례에 맞는다. 위반으로 보지 않는다. T1~T9가 고쳐지면 항목 문구도 함께 고쳐야 한다.

### W29 굵은 글씨
- 굵은 문장 다섯 개는 모두 결론 문장이고 한 단락에 한 번이어서 허용한다. 첫 번째(T1)는 결론이 틀렸으므로 고쳐야 한다.

### W23 반복 문형
- 새 절의 도입은 대부분 사실로 바로 시작하고 같은 마무리 문형의 반복은 없다. "이 노드의 기준으로 구현을 볼 때" 절은 다른 노드와 같은 이름의 고정 절이다.

### W22 표상과 글
- 그림 앞 문장("클라이언트가 구독(5번)을 먼저 하고 …을 따라가 보면 됩니다")은 무엇을 따라갈지 알려 준다. 그림 뒤 단락이 그림 값을 다시 나열하지 않는 점은 잘 지켰다.
- 라벨 불일치: 그림 "HelloResult(버전, server, connection, policy, features, log)"는 글에서 "`hello` 응답"이다. 그림 "ViewResult"는 글에서 "화면 응답"이다. 그림의 "events 알림"은 글의 "이벤트 알림"과 `events.subscribe`로 섞인다. 한 이름으로 맞춘다.

## 3. 독자 흐름 문제

독자는 이벤트 소싱·투영·멱등 키·펜싱·bwrap 격리 개념(노드 4, 4.1, 5, 7.1, 13)을 앞서 읽었고 React CSR을 안다. JSON-RPC는 "들어 봤지만 설계 수준으로는 모를 수 있는 것"이다.

L1. 글이 사실을 모형에 붙이지 않고 설계 절 순서대로 간다(W5, W12). 이 노드가 답할 질문은 "연결이 끊기고 다시 붙는 환경(휴대폰, SSH, 슬립)에서 화면과 명령이 어긋나지 않게 하는 방법"이고, 답은 세 가지 보장(위치로 이어받기, 무효화로 화면 갱신, 멱등 키로 한 번만 적용)이다. 글에는 이 세 개를 묶는 문단이 없다. 도입은 "양쪽 코드를 리뷰할 때 기준"이라고 쓰는 데 그치고 곧바로 메시지 형식으로 간다. 독자가 앞 절의 사실이 어느 보장에 속하는지 알 수 없다. 제안: 도입에 "끊김이 일상인 환경에서 필요한 세 가지 보장"을 제시하고, 각 절이 어느 보장을 구성하는지 첫 문장에서 짚는다.

L2. §이벤트 구독과 재전송에서 "구독을 먼저 열고 화면 데이터를 나중에 읽는다"의 이유는 한 문장이다("그 사이에 커밋된 이벤트를 놓칠 수 있기 때문입니다"). 따라갈 구체 예가 없다. 예: 화면 데이터를 seq 100 시점에 읽고 구독을 seq 105 시점에 열면 101~104가 사라진다. 반대로 구독을 먼저 열면 겹치는 이벤트는 `seq ≤ asOfSeq`로 걸러진다. W9/W14의 단계별 예가 빠진 가장 중요한 곳이다. 그림의 5→7 순서가 이를 보여 주지만 숫자 예는 없다.

L3. 논리 비약: §명령 보내기에서 "화면이 낡았으면 커널이 충돌로 거부하고"로 넘어가는데, 낡음 판정의 기준(`basisSeq`와 `revisionSeq`)은 노드 4에 있다. W6에 따라 한 문장으로 다시 짚어야 한다. 같은 절 첫 단락은 "범용 '실행' 메서드는 없다"는 결정을 말하지만 이유(권한 범위와 검사, 도메인 동작별 변환 함수, 등록 표 한 곳)와 연결하는 문장이 없다.

L4. 아직 설명하지 않은 개념에 의존: "인증 방식 허용"(T1 문장), "터미널 확인 문자열", `decideMobile` 등 범위 이름(W2에 정리). §연결에서 첫 화면까지의 판정 순서 문장은 "방식별 인증"을 쓰면서 어떤 방식이 있는지(`deviceToken`, `localAdmin`, `runtimeAdapter`) 말하지 않는다.

L5. 독자가 이미 아는 내용을 길게 다시 설명한 곳: §세 경로의 두 번째 단락(헤더·쿠키·거부·검사 시점)은 노드 13의 "마지막이 기기 토큰입니다…" 단락과 같은 내용이다. 지문 정의는 노드 4와 겹친다(T5). 둘 다 "13번 노드", "4번 노드"를 가리키고 요점만 남기면 된다. 반대로 이 노드에서만 새로운 "토큰이 JSON 메시지에 실리지 않는다"는 체크리스트에만 있다.

L6. 구현 리뷰 목표와의 연결: 체크리스트 16개 항목은 대체로 구현에서 확인 가능한 형태로 쓰였다. 빠진 점검은 T2(저장소가 바뀐 뒤 옛 명령), T4(거부 뒤 새 키), T6(24시간·초안), T7(`lastSeq` 비교), T8(`finalSeq` 전 휘발 삭제 금지), 그리고 로컬 경로의 `localAdmin`·`localConfirm`과 에이전트의 도구 프로세스가 `local` 소켓을 열 수 없어야 한다는 전제(결정 14 연결, 19 §3.2.4)다. 마지막은 이 노드가 맡을지 노드 13·8이 맡을지 정해야 한다. 현재 02, 08, 13 어디에도 `localAdmin`이 없다.

## 4. 표상 문제

R1. 시퀀스 다이어그램(연결에서 첫 화면까지). 렌더링: mermaid 11.4.1 parse 통과. 구조: 시간 순서와 두 참여자라서 sequenceDiagram은 알맞다.
- 제목은 "연결에서 첫 화면까지"이고 설명도 "첫 화면을 그리기까지의 순서"인데 그림은 9~10번에서 명령 결과 이벤트와 명령 응답을 보여 준다. 첫 화면 이후의 다른 이야기가 섞였다. 9~10번 앞에 명령 요청이 없어서 "명령 응답"이 무엇에 대한 응답인지 그림만으로 알 수 없다. 글은 "명령 응답(10번)보다 그 결과 이벤트(9번)가 먼저 온다"를 따라가라고 하는데, 요청 화살표(`C->>D: 명령(ik_…, basisSeq)`)가 있어야 순서 보장이 보인다.
- 캡션이 없다. 이 그림은 타이머(5초 챌린지, 10초 `hello` 시한), 권한 범위 부여, `view.get`의 `minSeq` 대기를 생략한 개략 그림인데 단순화 사실이 밝혀지지 않았다(W22 캡션).
- 5~6번(구독과 재전송)과 7~8번(화면 읽기)이 순서대로 놓여 "구독 먼저"를 보여 준다. 그러나 재전송이 끝나기(`caughtUp`) 전에 `view.get`을 보내는지 끝난 뒤인지는 그림에서 알 수 없다. 원문(§3.10.2)은 `syncing`에서 모든 구독이 `caughtUp`이 된 뒤 `ready`에서 낡은 열린 뷰를 다시 받는다고 적는다. 첫 접속과 재접속의 차이를 한 줄로 밝힌다.
- 수정 제안: 7~8번 뒤에 명령 요청 화살표를 추가하고, 제목을 "연결, 구독, 화면 읽기, 명령 한 번"처럼 고치거나 9~10번을 별도 그림으로 나눈다. 캡션에 "개략도: 타이머와 권한 범위 부여는 생략"을 쓴다.

R2. 표나 그림이 필요한데 문장으로만 쓴 곳(W20). 동시에 유지해야 할 관계가 셋 이상이다.
- 리스너 x 받는 경로 x 전송 조건 x 받는 인증 방식(T1): 3x4 비교표. 노드 2에 비슷한 표가 있으므로 "무엇이 다른가" 열을 중심으로 한 표를 둔다.
- 오류 코드 영역(1xxx~5xxx)과 닫는 코드(1000번대 표준, 4000번대 Helm)를 두 표로 나눠 이름 공간이 다름을 보이는 표(T10).
- `replay.outOfRange` 네 사유에 대해 클라이언트가 버리는 것(위치, 이벤트 캐시, 투영 캐시)을 보이는 4x3 표(W26).
- 송신 큐 단계: 임계 8 MiB에서 휘발 스트림 폐기, 10초 초과나 16 MiB에서 연결 닫기(4008), 버리지 않는 것(영속 이벤트, 응답).
- 연결 상태 여덟 가지와 전이: 시간순 흐름과 분기가 있어 W20 대상이다. 글은 상태 이름 나열과 재연결 순서를 섞는다. 상태 다이어그램 하나(idle, connecting, handshaking, syncing, ready, backoff, needsUser, closed)가 있으면 글은 전이 조건과 이유만 설명하면 된다. 노드 15가 화면 표시를 다루므로 중복을 피하려면 상태 이름과 전이 조건 표만 둔다.

R3. 표상이 불필요한 곳은 없다. 오류 코드 전체 표를 넣으라는 뜻은 아니다. 노드 범위상 영역 설명 한 줄과 3001~3009 중 자주 필요한 것만 쓰는 지금 방식이 알맞다.

## 5. 지침 부작용

S1. W16(출처 표기 금지)과 W17(확인한 사실만 단정)의 상호작용: 원문의 [제안] 표시(제안 상태인 설계 결정)와 설계 문서끼리의 불일치가 글에서 모두 사라져 단정형이 되었다. 19는 대부분이 [제안]이고 구현이 끝난 뒤 리뷰에서 설계와 구현의 불일치가 나올 수 있다. 사실 자체가 정해지지 않은 곳은 W42에 따라 이유와 함께 한 번 쓸 수 있으나 이 글은 한 번도 쓰지 않았다. 예: TUI의 기본 인증(T12). 지침 개선 제안: 설계 문서 학습 글에서는 "설계 문서끼리 어긋난 곳"을 W17의 "사실 자체가 정해져 있지 않은 경우"로 보아 내용으로 쓰라고 명시한다. 빈도: 이 글 전체, 특히 T12.

S2. W3(분량보다 깊이)와 설계 문서 요약의 긴장: 글이 20KB에 이르고 설계 §3.2~3.14를 거의 모두 요약해 깊이보다 폭으로 간다(L1). 관련 규칙: W3, W5, W12. 나타난 위치: 전체. 지침 개선 제안: 설계 문서를 요약하는 학습 글에는 "문서 절 순서를 따르지 말고 모형에서 시작"을 W5에 덧붙이고, 체크리스트와 이해용 설명을 나누는 분량 기준을 W28에 둔다.

S3. W45(추상 명사는 수치로)와 정책 값: 수치를 구체로 쓰라는 지침이 설정으로 바뀌는 기본값을 고정 사실처럼 쓰게 했다(T11). 지침 개선 제안: W45에 "설정으로 바뀌는 값은 '기본값'을 표시한다"를 추가한다.

## 6. 전체 평가

기술 정확성은 대체로 높다. 메시지 형식, 핸드셰이크 순서, seq와 `(from, to]` 계약, 범위 밖 처리, 느린 소비자 규칙, 파일 한도, 버전 협상, 닫는 코드 값은 원문과 맞는다. 문제는 대비하려고 줄인 문장(T1)과 시간 순서를 풀어 쓴 문장(T2)에 집중되어 있고, 이 둘은 굵은 결론이거나 체크리스트에 그대로 들어가 리뷰 기준을 틀어 놓는다. 높음 2건을 먼저 고치고, 중간 T3~T10은 조건 한두 문장을 더하면 해결된다.

학습 적합성 면에서 이 글의 약점은 오류보다 구조다. 이 노드의 핵심은 세 가지 보장(위치 이어받기, 무효화, 멱등)이 맞물리는 방식인데, 글은 설계 절 순서대로 사실을 쌓고 작동 모형과 숫자 예가 없다(L1, L2). 노드 2·4·13과의 중복(리스너 표, 지문 정의, 토큰 운반 방식)은 요약해 가리키면 줄어들고, 줄인 분량을 모형 도입, "구독 먼저" 예, 재연결 순서의 단계별 예(저장된 위치 120, head 150, 재전송, `view.get`, 같은 키 재전송)에 쓰는 편이 구현 리뷰 목표에 더 맞는다. 로컬 경로의 `localAdmin`·`localConfirm`은 이 노드가 맡을지 정해야 한다. 의인화 위반은 10곳이고 모두 프로토콜·알림·규칙·필드를 주어로 쓴 형태라 주어를 실행 주체로 바꾸면 해결된다. 금지어('축', '박다', '가른다', '닿다')는 없다. Mermaid 블록은 문법 오류가 없으나 명령 요청 화살표와 캡션이 없다(R1).
