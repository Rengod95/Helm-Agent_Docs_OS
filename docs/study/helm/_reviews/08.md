### T1. 높음 / 사실 오류: 해시라인의 태그를 "줄마다 붙는 태그"로 설명
- 인용: "`hashline`은 파일을 읽을 때 줄마다 짧은 태그를 붙여 보여 주고, 모델은 '이 태그의 줄부터 저 태그의 줄까지를 이렇게 바꿔라' 같은 연산으로 편집합니다. 태그는 충돌할 수 있는 4자리 별칭이라 일치 판정에는 쓰지 않고, 실제 보호는 파일 전체의 sha256 해시가 합니다."
- 1차 자료: 13 §3.3.7(488행 부근). 입력은 `[PATH#TAG]` 섹션과 줄 번호 연산(`PUT N.=M:`, `PUT <N:`, `PUT >N:`, `CUT N.=M`)이고, "줄 번호는 태그 시점의 원본 기준"이다. 태그는 "파일 내용에서 만든 4자리 16진 별칭(xxh32 하위 16비트)"이고, 데몬은 태그를 (경로, sha256, 본 줄 집합)으로 매핑해 runId 범위로 보관한다. `read`·`grep` 출력은 `[path#TAG]` 헤더와 `줄:내용` 줄이다. research-ohmypi.md §1 3번과 §3.1은 "해시라인은 줄마다 해시가 아니다. 파일 단위 4자리 스냅샷 태그와 원본 줄 번호"라고 명시한다(줄별 해시는 2026-02 초기 형식).
- 문제: 글의 모형에서는 줄마다 태그가 있고 태그로 줄 범위를 지정한다. 실제로는 파일(스냅샷) 하나에 태그 하나가 있고, 줄은 번호로 지정한다. 태그 충돌의 의미도 달라진다(글의 모형에서는 줄 단위 충돌, 실제는 스냅샷 단위 충돌). 구현 리뷰에서 "줄 태그" 기준으로 코드를 보면 정상 구현을 오류로 판정한다. 같은 오류가 implementation-readiness.md A-3 배경 문단("줄마다 짧은 해시 표식")에도 있어서, 글이 그것을 옮겼을 가능성이 크다. 설계 정본(13)과 점검표가 다르므로 점검표 쪽을 고쳐야 한다.
- 수정 제안: "파일을 읽으면 `[경로#태그]` 헤더와 `줄번호:내용` 줄이 나옵니다. 태그는 읽은 시점의 파일 내용에서 만든 4자리 별칭이고, 모델은 이 태그와 줄 번호 범위(`N~M줄을 이 본문으로 교체`)로 편집합니다"로 고친다. 태그가 줄이 아니라 읽은 스냅샷을 가리킨다는 점, 데몬이 태그를 (경로, sha256, 본 줄 집합)으로 기억해 두었다가 해시를 대조한다는 점을 한 문장씩 더한다.

### T2. 높음 / 글 안의 모순과 과도한 일반화: "어떤 합의로도 열리지 않는 보호 경로"
- 인용: "어떤 합의로도 열리지 않는 경로가 있습니다. 정본 DB가 있는 `/srv/volumes/helm/data`, 데몬 소켓, 설정 디렉터리, 작업 공간 안의 `.env`와 `secrets/` 같은 보호 파일입니다." / 점검 목록 "보호 경로(`/srv/volumes/helm/data`, 소켓, 설정, `.env`, `secrets/`, git 설정)가 어떤 합의로도 열리지 않는가" / 기준선 문단 "보호 경로 쓰기는 거부, 보호 경로 읽기는 질문".
- 1차 자료: 18 §3.11.6 첫 줄 "보호 경로 읽기: `ask`(`disclose_data`)", 같은 절 끝 "보호 경로 쓰기, 권한 상승, Windows 실행은 합의로도 바뀌지 않는다", 18 §3.11.5 머리말 "줄이려면 합의의 경로별 허용". 13 §3.4.3 예외 항목: "`/srv/volumes/helm/data`는 어떤 합의로도 열지 않는다"(같은 절 `draft_only` 초안 영역 `/srv/volumes/helm/drafts/<concernId>/**`와 검증 작업 트리는 합의가 명시하면 rw로 연다). `.git/config` 등 git 설정은 18 §3.11.5에서 "합의·부여로도 열리지 않는다"고 따로 적었다. 13 §3.10: 읽기 `ask` 행은 "사람이 합의로 연 경로에만 해당".
- 문제: "어떤 합의로도 열리지 않는다"가 맞는 것은 (a) 모든 보호 경로의 쓰기, (b) `/srv/volumes/helm/data`, (c) git 설정·훅의 쓰기다. `.env`, `secrets/`, 소켓, 설정 디렉터리의 읽기는 기본 거부이지만 합의가 경로를 명시하면 열리고, 열린 뒤에도 모델 문맥으로 가져가는 읽기는 권리 게이트 질문이다. 글은 바로 뒤 기준선 문단에서 "읽기는 질문"이라고 적어 앞 문단과 스스로 어긋난다. 점검 목록이 이 일반화를 구현 리뷰 기준으로 못 박기 때문에, 18 기준으로 올바르게 구현된 "합의로 연 경로의 읽기 질문"을 위반으로 볼 수 있다. 샌드박스 쪽은 합의와 무관하게 가림 목록을 읽기 불가로 덮으므로, 데몬 파일 도구(realpath 검사)와 샌드박스의 차이도 글에 없다.
- 수정 제안: 두 층으로 나눠 쓴다. "쓰기는 어떤 합의로도 열리지 않는 목록(정본 데이터, 보호 경로 쓰기, git 설정·훅)"과 "읽기는 기본 거부이고 합의가 경로를 명시하면 질문을 거쳐 열 수 있는 목록"이다. 점검 목록도 "보호 경로 쓰기가 합의로 열리는 경로가 있는가", "`/srv/volumes/helm/data`와 git 설정이 어떤 경우에도 열리는가" 두 항목으로 나눈다.

### T3. 중간 / 과도한 단정: "`/srv/volumes`는 아예 마운트하지 않습니다"
- 인용: "`/srv/volumes`는 아예 마운트하지 않습니다."
- 1차 자료: 13 §3.6.2 `SandboxSpec` 주석: S1의 `home`은 `/srv/volumes/helm/sandbox/<workspaceId>/home`(작업 공간별 영속 캐시 홈, `--bind`로 rw). bwrap 인자의 마스크 주석은 "`/srv/volumes` 자체는 바인드하지 않는다". 13 §3.4.3 예외와 18 R-3·R-14: `draft_only` 합의가 경로를 명시하면 `/srv/volumes/helm/drafts/<concernId>/**`와 `/srv/volumes/helm/worktrees/<runId>/**`를 rw로 바인드한다(S1만).
- 문제: 정확한 사실은 "`/srv/volumes` 전체를 바인드하지 않고, 그 아래에서 샌드박스 홈과 (합의가 명시한) 초안·검증 작업 트리만 바인드한다"이다. 글의 단정은 "`/srv/volumes` 아래 어떤 마운트도 있으면 위반"이라는 점검으로 이어진다. 18 R-3의 "`/srv/volumes` 숨김"과 R-14 예외, 샌드박스 홈이 바로 이 지점이다. 샌드박스 홈의 위치는 문서끼리 정리 중인 홈 디렉터리 정책과 닿는 부분이라, 글은 홈 위치를 특정하지 않는 쪽이 안전하다.
- 수정 제안: "`/srv/volumes` 전체는 마운트하지 않고, 정본 `helm/data`는 어떤 경우에도 보이지 않습니다. 샌드박스의 `HOME`과 합의가 명시한 초안·검증 작업 트리만 그 아래에서 예외로 붙습니다"로 고친다.

### T4. 중간 / 조건 누락: 공개 인터넷 "기본 허용"의 적용 범위
- 인용: "그래서 공개 인터넷 읽기(`net:public`)는 합의 없이 기본 허용이고, 루프백, 사설 대역, ... 어떤 부여로도 열리지 않습니다." / "네트워크가 필요한 실행(패키지 설치, git fetch 등)은 언제나 프록시를 거칩니다." / 기준선 문단의 "공개 인터넷 읽기는 허용".
- 1차 자료: 18 R-6, §3.11.6 "네트워크가 있는 실행" 행: "합의에 `net:` 부여(`net:public` 포함)가 있으면 `allow`, 없으면 `ask`"(`network.ungranted`, 권리 범주 `disclose_data`). 합의 없는 샌드박스 실행은 `network: 'none'`(13 §3.5.3 `effectiveScope`, "합의가 없으면 bash는 쓰기 가능 루트 없이, 네트워크 없이 돈다"). 기본 허용은 `web_fetch`, `web_search`, 브라우저 GET·HEAD(데몬과 browserd가 직접 하는 읽기)에만 해당한다(18 R-6 마지막 문장, J-205).
- 문제: 글은 기본 허용을 먼저 일반 규칙으로 쓰고, 샌드박스 실행의 프록시를 다음 문단에서 설명하면서 "부여가 없으면 `ask`"를 적지 않는다. 독자는 `npm install`이 합의 없이 공개 인터넷에 나간다고 읽을 수 있다. 기준선 요약에서도 이 행이 빠졌다. 구현 리뷰에서 가장 자주 부딪칠 경로(bash의 네트워크)의 기본 동작이 틀리게 남는다.
- 수정 제안: 두 경로를 나눠 쓴다. "웹 읽기 도구는 합의 없이 공개 인터넷을 읽습니다. 샌드박스 안 실행은 합의에 `net:` 부여가 없으면 네트워크 자체가 없고(`network: 'none'`), 부여 없이 네트워크가 필요한 명령은 질문이 됩니다." 기준선 문단에도 네트워크 실행 행을 더한다.

### T5. 중간 / 생략으로 생긴 오해: S1b를 S1과 사실상 같은 수준으로 서술
- 인용: 표 "S1b | `systemd-run --user` 일회성 단위의 경로 차단 | bwrap이 없을 때 2순위. 일부 작업 제외".
- 1차 자료: 13 §3.6.1 S1b 행: 읽기 범위는 허용 목록, "같은 uid 프로세스에 신호는 보낼 수 있음", "허용 목록 방식과 바인드한 하위 경로의 `InaccessiblePaths`가 [실험]으로 확인되지 않은 동안은 `pre_read_exposed`(쓰기는 막지만 읽기가 넓다)로 표시하고 `sandbox` 점검은 critical". 13 §3.6.4·§3.6.5: 작업 공간 안 `.env`·`secrets/` 가림이 S1b에서 실제로 동작하는지는 [가정]이다. 18 §3.11.2 표: S1b는 "격리 수준 낮음" 배지, 상태 degraded. 초안·검증 작업 트리 실행은 S1에서만(R-14).
- 문제: "일부 작업 제외"만으로는 S1b가 (a) pid 분리가 없고 (b) 작업 공간 안 비밀 가림이 검증 전이라 읽기가 넓을 수 있으며 (c) 화면에 낮은 수준으로 표시된다는 점이 안 전해진다. 이 서버는 bwrap이 설치되어 있지 않은 상태에서 시작한다(18 §3.11.2 순서 1, [실험 7]). 구현 직후 처음 리뷰하는 환경이 바로 S1b일 수 있어서 영향이 크다.
- 수정 제안: 표의 S1b 칸이나 표 아래 한 문단에 위 세 가지(pid 분리 없음, 가림 검증 전이라 `pre_read_exposed`, 초안·검증 작업 트리 불가)를 쓴다. 점검 목록에 "S1b에서 `sandbox` 점검이 critical/degraded로 보이는가"를 더하는 것도 좋다.

### T6. 중간 / 과도한 일반화: "모르면 되돌릴 수 없는 것으로 다룹니다"
- 인용: "되돌릴 수 있는지(`reversibility`)는 권한 레이어가 값을 정하고 Helm은 읽기만 하며, 모르면 되돌릴 수 없는 것으로 다룹니다."
- 1차 자료: 13 §3.10 마지막에서 두 번째 항목: "`unknown`은 외부 효과가 있는 호출(`externalEffect`)이면 `hard`와 같이 다룬다". 같은 절 표: write·edit는 git이 추적하는 깨끗한 파일이면 `reversible`, 아니면 `unknown`(`externalEffect: false`). bash(네트워크 없음)도 `unknown`, `externalEffect: false`.
- 문제: `unknown`을 항상 `hard`로 다루면 로컬 파일 쓰기 대부분이 되돌릴 수 없는 행동이 되어 5·6번 노드의 묻기 기준과 맞지 않는다. 실제 규칙은 "모르는데 외부 효과까지 있으면 `hard`"다.
- 수정 제안: "모르는 값(`unknown`)은 외부 효과가 있는 호출일 때만 되돌릴 수 없는 것과 같이 다룹니다. 작업 공간 안 쓰기는 모르는 값이어도 이 규칙에 걸리지 않습니다"로 한정한다.

### T7. 중간 / 조건 누락: "원시 행동은 도구마다 하나"
- 인용: "원시 행동(`primitive`): read, write, execute, send, spawn, ask 가운데 하나. 도구마다 하나입니다." / 점검 목록 1번째 항목.
- 1차 자료: 13 §3.2.5 `browser_*` 계약: "읽기 멤버 `read`. 상호작용 멤버는 `read`이고 요청마다 `send`가 붙는다. `javascript_exec`는 `execute` + `send`, `file_upload`는 `send`". §3.3.3 표: 브라우저 상호작용 멤버는 "read (요청마다 send 판정)". §3.10 표: 브라우저 상호작용 멤버의 `externalEffect`는 `uncertain`.
- 문제: 명세의 `primitive` 필드는 하나이지만, 브라우저 상호작용 멤버는 호출 때마다 요청 판정으로 `send`가 더해지고(필드는 `read`), `javascript_exec`는 두 행동이 붙는다. 글의 브라우저 절은 이 "요청마다 send로 올림"을 따로 설명하므로 앞 절과 어긋나 보인다. 점검 항목이 "도구 하나에 행동 하나"만 확인하게 한다.
- 수정 제안: "명세에는 원시 행동이 하나 선언됩니다. 브라우저 상호작용처럼 효과가 호출 때 정해지는 도구는 선언은 `read`이고, 요청이 만들어질 때 `send`가 더해집니다"로 쓴다.

### T8. 중간 / 글이 넘긴 사실 중 확인 가능한 것: 해시라인 기본값의 이유와 켜는 조건
- 인용: "기본값을 `replace`로 둔 이유와 `hashline`을 켤 조건은 구현 착수 점검표의 결정 항목에 있습니다."
- 1차 자료: 13 §3.3.7 마지막 항목: "기본은 `replace`다. 해시라인은 23의 A/B 시험 뒤 모델별로 켠다(§7 O-13-17, 판정 J-190 (7)). oh-my-pi의 저자 벤치는 Helm의 주 모델(Claude 계열)에 대한 근거가 아니다." implementation-readiness.md A-3의 추천: 구현 뒤 고정 과제 세트로 SP-23을 재고, 성공률이 더 높고 `stale_snapshot` 실패가 늘지 않는 계열에서만 `ai.editMode`를 `hashline`으로 켠다.
- 문제: W17은 확인할 수 있는 사실을 미루지 말라고 한다. 이유(근거가 저자 자체 벤치뿐이고 Claude 계열 근거가 없음)와 조건(A/B 시험 뒤 모델별)은 두 문장이면 쓸 수 있고, 구현 리뷰에서 "기본값이 `replace`인가, 설정 키로 모델별로 고를 수 있는가"를 볼 때 필요하다. 본문이 점검표를 가리키는 형태도 독자를 문서 밖으로 보낸다(W16과 비슷한 문제).
- 수정 제안: 이유와 조건을 본문에 직접 쓰고 마지막 문장을 지운다.

### T9. 중간 / 생략으로 생긴 오해: 합의가 없을 때 bash의 동작
- 인용: "샌드박스 안에서는 합의가 허용한 쓰기 가능 루트만 쓰기로 마운트되고 나머지는 읽기 전용이거나 아예 보이지 않습니다."
- 1차 자료: 13 §3.5.3: 합의가 없으면 `writableRoots: []`, `network: 'none'`이고 `targets: []`, `targetsKnown: true`여서 bash는 읽기 전용으로 실행된다("합의 없는 실행은 작업 대상을 바꾸지 않는다"를 샌드박스로 보장). 파일 단위·중간 글롭 부여는 bash 쓰기 루트가 되지 않고 `<D>/**` 꼴의 하위 트리 부여만 루트가 된다(`write`와 `execute` 둘 다 있을 때). 쓰기 루트가 필요한데 파일 단위 부여뿐이면 `gate.scope_expansion_required` 질문이 된다.
- 문제: "합의가 허용한 루트"가 어떤 부여에서 어떻게 계산되는지, 합의가 없을 때 bash가 막히는 것이 아니라 읽기 전용으로 돈다는 점이 없다. 구현 리뷰의 가장 직접적인 질문("합의 없이 bash를 부르면?")에 글이 답하지 못한다.
- 수정 제안: 샌드박스 문단 앞이나 뒤에 세 문장을 더한다. (1) 합의가 없으면 bash는 쓰기 루트도 네트워크도 없이 읽기 전용으로 돈다. (2) 쓰기 루트는 합의의 하위 트리 전체 부여(`<디렉터리>/**`)에서만 계산된다. (3) 파일 단위 부여는 `write`·`edit`로만 쓸 수 있다.

### T10. 낮음 / 근거: 네트워크 실행의 결과 불명 조건
- 인용: "네트워크를 쓰는 실행이 시간 초과로 끝나면 결과 불명으로 기록합니다."
- 1차 자료: 12 §3.4.6 `afterToolCall`: 외부 효과가 있을 수 있는 호출이 "타임아웃, 신호 종료, 전송 끊김, 취소, MCP 서버 크래시"로 끝나면 `outcome: 'uncertain'`. 13 §3.3.5 `endedBy = exit | timeout | signal | cancel`, exit 밖이면 결과 불명.
- 문제: 시간 초과만 쓰면 취소·신호 종료는 해당하지 않는 것처럼 읽힌다. 모형은 맞다.
- 수정 제안: "정상 종료(exit)가 아닌 모든 끝(시간 초과, 신호, 취소)"으로 바꾼다.

### T11. 낮음 / 수치 기준: "호출당 비용은 약 16ms"
- 인용: "호출당 비용은 약 16ms입니다. 여기에 실행 전후의 파일 상태를 비교하는 변경 감지를 더해".
- 1차 자료: 13 §3.6.6: bwrap 시작이 약 16ms이고, 변경 감지(`git ls-files` 기반 또는 최대 50,000 항목 walk)와 실행 전 보호 파일 탐색이 "도구 호출당 수십~수백 ms"를 더한다. S1b 단위 기동은 약 70ms(§3.6.5). ADR-13-01은 "호출당 약 16ms"라고 쓰지만 같은 문서 §3.6.6이 정정한다.
- 문제: 뒤 문장이 변경 감지를 "더해"라고 해서 대체로 맞게 읽히지만, "호출당 비용 16ms"는 bwrap 시작만의 값이다.
- 수정 제안: "bwrap 시작 자체는 약 16ms이고, 변경 감지와 보호 파일 탐색이 호출마다 수십~수백 ms를 더합니다"로 쓴다.

### T12. 낮음 / 부정확한 수식: "사용자·프로세스·네트워크 네임스페이스를 모두 분리"
- 인용: "사용자·프로세스·네트워크 네임스페이스를 모두 분리하고".
- 1차 자료: 13 §3.6.2 `--unshare-all`(user, ipc, pid, net, uts, cgroup), 마운트 격리는 바인드 구성으로 한다.
- 문제: 세 가지로 한정하는 듯 읽히는 "모두"다. S1b는 pid를 분리하지 않는다(T5).
- 수정 제안: "bwrap의 `--unshare-all`로 사용자, pid, 네트워크 등 네임스페이스를 분리하고"로 쓰고, pid 분리가 S1에만 있다는 점은 T5와 함께 다룬다.

### T13. 낮음 / 근거 수준이 낮은 사실의 단정: 브라우저 도구 개수
- 인용: "`browser_*`: 1단계 읽기 12개(이동, 페이지 읽기, 찾기, 스크린샷, 탭 관리 등), 2단계 상호작용 6개(클릭, 입력, 폼 채우기 등)".
- 1차 자료: 13 §3.2.5와 §7 O-13-18: 멤버 이름과 목록은 [검색] 수준이라 구현 전에 공식 문서로 확인한다.
- 문제: 멤버 수가 확정이 아닌데 숫자로 단정한다. 사실 자체가 정해져 있지 않은 상태이므로 W17은 그 상태를 내용으로 쓰라고 한다.
- 수정 제안: "읽기 단계와 상호작용 단계로 나뉘고, 멤버 목록은 구현 전에 제공자 문서로 확정합니다"로 바꾸거나 개수를 뺀다.

### T14. 낮음 / 설계 문서 간 차이를 한쪽으로 단정: 명령 문자열 검사
- 인용: "설계는 bash 명령 문자열 분석을 '거짓 안심을 준다'는 이유로 기각했습니다." / "문자열 검사는 질문을 늘리는 방향으로만 쓰고, 허용하는 근거로는 쓰지 않습니다."
- 1차 자료: 13 §3.5.2 (b): "기각. 보조 신호로도 쓰지 않음(거짓 안심)". 13 §3.10 표와 18 §3.11.6은 `git push`·`curl -X POST` 등이 보이면 `speak_for_user`를 더하고, `sudo`·`systemctl`·`crontab` 등은 명령 문자열로 `deny`한다.
- 문제: 13 안에서 §3.5.2는 "보조 신호로도 쓰지 않음"이고 §3.10은 보조 신호로 쓴다. 글은 기각과 사용을 "질문을 늘리는 방향으로만"으로 화해시키지만, 거부(`deny`)를 더하는 쪽도 쓴다는 점이 빠졌다.
- 수정 제안: "질문이나 거부를 더하는 방향으로만 쓰고"로 고친다. 문서 간 불일치는 글 밖 보고 대상이다(아래 문서 간 차이 목록).

### T15. 낮음 / 설계 문서 간 차이: 샌드박스를 쓸 수 없을 때 남는 도구
- 인용: "S1과 S1b 둘 다 쓸 수 없으면 bash를 빼고, 샌드박스가 필요한 grep과 find도 빼고, 읽기와 Helm 도구만 남깁니다."
- 1차 자료: 13 §3.6.1 수준 판정 표 마지막 행은 "`read`·`ls`·Helm 도구만". 반면 §3.2.2의 묶음 계산은 `write`·`edit`를 샌드박스 조건 없이 두고, 웹·브라우저 도구는 S0이거나 `read`가 없을 때만 뺀다고 쓴다. S1·S1b 둘 다 불가일 때의 웹 읽기 도구는 어느 표에도 직접 쓰여 있지 않다.
- 문제: 글은 §3.6.1 한 행을 따랐다. `write`·`edit`·웹 읽기 도구가 이 상태에서 남는지는 13이 한 곳에서 정하지 않았다.
- 수정 제안: 글은 "읽기와 Helm 도구만"을 유지하되, 13에서 `write`·`edit`·웹 도구의 처리를 확정해 달라는 이슈를 올린다.

### T16. 낮음 / 근거 표시: "실험에서 ... 표지 파일을 하나도 만들지 않았고"
- 인용: "실험에서 악성 설정이 걸린 저장소에 허용 명령들은 표지 파일을 하나도 만들지 않았고, `git status`와 `git archive`는 필터를 실행했습니다."
- 1차 자료: 13 §3.5.7 1·2번: 같은 내용이다(`exp-git-harden.out.txt`). 단 `git diff`도 금지 명령이고(필터 경로가 있음), 글의 금지 목록 `status`, `add`, `checkout`, `archive`에는 `diff`가 없다.
- 문제: 사실은 맞다. 그러나 "실험에서"는 근거 수준 표시에 가깝다(W16). 금지 목록에서 `diff`와 `worktree add`(18 R-13)가 빠진 것은 낮은 수준의 누락이다.
- 수정 제안: "악성 설정이 걸린 저장소에서 허용 명령은 아무것도 실행하지 않았고 `git status`와 `git archive`는 필터를 실행하는 것이 확인되었습니다" 정도로 쓰고, 금지 목록에 `diff`를 추가한다.

### 문서 간 차이 중 글이 한쪽을 단정했거나 정리 대상으로 남을 부분 (정리 중인 다른 에이전트에게 전달)
1. 보호 경로 읽기: 13 §3.4.3 표는 읽기를 "거부"로 쓰고, 13 §3.10과 18 §3.11.6은 `ask`로 쓴다. 글은 둘을 모두 적었다(T2).
2. 샌드박스 `HOME`: 18 R-2는 "S1은 작업 공간별 영속 캐시 홈, S1b는 실행별 임시 홈". 18 R-4는 홈을 빈 tmpfs로 덮는다. 13 §3.6.2는 S1 홈을 `/srv/volumes/helm/sandbox/<workspaceId>/home`에 둔다. 글은 홈 위치를 쓰지 않았지만 `/srv/volumes` 비마운트를 단정해 부딪쳤다(T3). 정리 결과에 맞춰 한 번 더 보아야 한다.
3. `systemctl`: 18 §3.11.6은 `systemctl` 전체를 거부하고 13 §3.10 표는 `systemctl --user`만 쓴다. 글은 "`sudo`·`systemctl`·`crontab`"으로 18을 따랐다. 근거는 맞지만 13과 같은 문구가 아니다.
4. `web_fetch` 크기: 13은 기본 2 MiB, 최대 10 MiB, 18 §3.11.8은 "크기 상한 10 MiB". 글은 13의 기본값을 썼다. 모순은 아니다.
5. 변환 대상 미디어 타입: 13 §3.2.4 (6)은 HTML·텍스트·JSON, 18 §3.11.8 5번은 HTML·텍스트·JSON·XML·PDF. 글은 "받은 HTML은"이라고만 써서 어느 쪽도 단정하지 않았다. 정리 뒤에도 유지하면 된다.
6. 변경 감지: 18 R-13은 "변경 감지는 해시 스캔으로 한다"이고 13 §3.5.4는 git 방식(`ls-files`)을 쓰되 설정 해시가 바뀌면 스캔으로 바꾼다. 글은 13을 따랐다(옳다). 18을 정리할 때 13 쪽이 정본임을 확인해야 한다.
7. 명령 문자열 검사: T14.
8. 해시라인: 점검표 A-3과 13이 다르다(T1).

## 2. 지침 위반

### W51 의인화와 금지 동사
- "웹 페이지가 무엇을 시키는지는 커널이 문자열로 알 수 없습니다." 두 가지 문제가 있다. (a) "웹 페이지가 시킨다"는 데이터를 주어로 둔 의도 동사다. (b) "커널이 알 수 없다"는 인지 동사 "알다"이고, W51은 실행 주체가 주어여도 쓰지 않는다. 제안: "bash 명령이 내부에서 어떤 파일을 수정하는지, 웹 페이지 본문에 어떤 지시가 적혀 있는지는 커널이 도구 호출의 문자열로 판별할 수 없습니다" (판별하다는 검사 단계에 대응하는 동작이다).
- "스크립트 파일을 만들어 실행하거나 변수로 경로를 조립하면 문자열 검사로는 어떤 파일을 건드릴지 알 수 없습니다." 같은 "알 수 없다". 제안: "문자열 검사에서 대상 파일이 나타나지 않습니다".
- "설계는 bash 명령 문자열 분석을 '거짓 안심을 준다'는 이유로 기각했습니다." 사용자가 명시한 "설계가 ~한다" 형태이고, "분석이 안심을 준다"도 사물 의인화다. 제안: "bash 명령 문자열 분석은 검사에 걸리지 않는 명령을 통과시키므로 쓰지 않기로 했습니다(ADR 결정)" 또는 "문자열 분석은 우회가 쉬워서 채택하지 않았습니다".
- "사용자 결정 55는 에이전트의 외부 자율 탐색을 필수로 하되, 내부망으로 들어가는 요청만 막도록 정했습니다." 결정을 주어로 "정했다"를 쓴 형태다. 제안: "사용자는 결정 55에서 외부 자율 탐색을 필수로 하고 내부망으로 들어가는 요청만 막기로 했습니다".
- "(7번 노드의 프롬프트 캐시를 지키려는 것입니다)", "(이름 확인과 연결 사이에 주소가 바뀌는 공격을 막으려는 것입니다)", "(...)막으려는 것입니다"(browser, 네트워크 절 포함 3곳 정도). 주어 없는 의도 표현이라 사실상 "설계가 의도한다"는 뜻이다. 제안: "...를 막습니다" 또는 "캐시가 유지됩니다"처럼 효과로 쓴다.
- "단위/마운트가 ... 읽기 전용이거나 아예 보이지 않습니다"는 상태 서술이라 허용한다. "대신 운영체제가 막게 합니다"의 "운영체제가 막다"는 커널이 실제 실행하는 동작(EROFS)이라 허용한다.

### W52 / 사용자 금지어
'축', '박다', '가른다', '닿다'는 본문에서 찾지 못했다. 합니다체는 일관된다.

### W16 출처·근거 표시
- 결정 번호 괄호가 본문에 다섯 번 나온다: "사용자 결정 55에 따라", "(결정 2)", "(결정 61)", "(결정 63)", "(결정 55)" 계열. 1~7a 글에는 거의 없다(06에 3번, 07a에 1번). 독자가 결정 19~64를 안다고 정리했지만, 출처 표기처럼 읽히는 괄호가 연속된다. 제안: 결정 번호는 처음 나올 때 한 번만 쓰고, 나머지는 내용(예: "스크린샷 원본을 보관하지 않기로 한 결정")으로 푼다. 반영하지 않으려면 사유를 기록한다.

- "구현 착수 점검표의 결정 항목에 있습니다" 문서 지시. T8 참조.

### W2 정의 없는 용어
- `tmpfs`, `realpath`, `rename`/`fsync`, `네임스페이스`, `CONNECT 프록시`, `EROFS` 대응어("읽기 전용 파일 시스템" 오류는 풀어 썼다), `CDP`(CDP 파이프), `playwright-core`, `Syncthing`, `ChangeSet`. 인덱스는 bwrap 격리를 "들어 봤지만 설계 수준으로는 모를 수 있는 것"으로 적었다. 샌드박스 절은 `tmpfs`, 읽기 전용 바인드, 네임스페이스를 풀지 않고 쓴다. 제안: 샌드박스 절 도입에서 마운트 격리의 모형(아래 3번 항목)을 한 문단 세운다. `CDP`는 "브라우저를 제어하는 프로토콜"을 한 구절로 푼다.
- `taint.web`을 쓰지 않고 "웹 내용을 본 뒤의 발송"으로 풀어 썼다. 07이 정의했으므로 맞게 연결된다. 다만 기준선 문단은 "웹 내용을 본 뒤"가 run 단위 표식이며 다음 run과 하위 run에 이어진다는 점을 07에 의존한다. 한 구절 연결이 있으면 좋다.

### W43 용어 일관성
- "발송"(기준선, 브라우저 절)과 원시 행동 "send"(명세 절, 점검 목록)가 섞인다. "발송은 합의가 없으면 거부", "업로드는 발송으로 보아". 같은 개념이므로 처음 한 번 "발송(`send`)"으로 묶고 이후 하나로 쓴다.
- "샌드박스 수준"(표)과 "격리"(절 제목), "자가 시험"과 "격리 상태 확인". 개념은 같고 절 제목에서만 다르므로 낮은 문제다.
- "작업자 프로세스"(web_fetch)와 `helm-browserd`("별도 프로세스")는 다른 것이지만 "프로세스"만 반복되어 헷갈릴 수 있다.

### W20·W22 표상 관련은 4번 항목.

### W23 도입·마무리
- 글 머리 문단 마지막 문장 "이 노드는 그 빈틈을 무엇으로 채우는지, 즉 도구를 어떻게 정의하고 실행하고 격리하는지를 다룹니다."는 글 전체를 요약하는 개요 문장이다. 앞 문장들이 이미 문제를 설정하므로 지워도 흐름이 유지된다. 낮음.

굵은 글씨는 "운영체제가 막게 합니다." 한 곳이다. 정의되는 용어가 아니라 결론 문장이고, 이 글의 핵심 문장이라 W29의 "결론 문장" 예외로 볼 수 있다. 목록은 명세 성질 6개(나란한 항목)와 점검 목록 13개로 한정되어 있다. 점검 목록 13개 모두 "~가?"로 끝나는 질문형인데 구현 리뷰 기준이라 W31의 이해 점검 질문이 아니라 기준 목록이다. 이전 노드(07 등)와 같은 형태다.

## 3. 독자 흐름 문제와 학습 적합성

### 3.1 흐름 문제
- 구체적인 예 없이 규칙이 이어진다(W9, W14). 글 전체에 도구 호출 하나를 따라가는 예가 없다. `bash`로 `echo x > ../outside`나 `npm install`을 부를 때 준비(범위 계산, 샌드박스 사양), 마운트 구성, 실행, 후처리(변경 감지, 마스킹)가 어떻게 일어나는지 한 번 따라가면 경로, 격리, 네트워크, 출력 절이 한 흐름으로 묶인다. 지금은 절마다 규칙 목록으로 읽혀서 "bash 한 호출에서 무엇이 어느 순서로 막히는가"를 독자가 직접 조립해야 한다. 이것이 구현 리뷰(코드 한 경로를 따라 점검)에 직접 필요한 모형이다.
- "격리" 절의 S1 문단("S1 샌드박스 안의 모습은 이렇습니다")은 한 문단에 마운트 6종(읽기 전용, 쓰기 가능, 읽기 전용 덧씌움, 빈 파일, 빈 tmpfs, 미마운트)과 네임스페이스, 환경 변수가 연달아 나온다. 새 개념이 한 단락에 여덟 개 이상이다(W26). 표나 그림으로 옮기거나 단락을 나누는 편이 낫다.
- 경로 절 첫 문단과 쓰기 도구 문단 사이의 접속이 약하다. "링크를 따라간 뒤에 판정한다"라는 제목 아래 보호 경로, 쓰기 절차가 모두 들어 있다. 제목은 앞 문단만 예고한다(W24). 쓰기 절차는 "원자적 쓰기" 소제목으로 나누는 편이 맞다.
- "권한 레이어" 절은 기준선 목록으로 8~9개 규칙을 한 문장에 나열한다. 한 문장에 규칙이 아홉 개라 훑어 읽기 어렵고, 각 규칙이 왜 그렇게 정해졌는지(W12) 이유가 없다. 표로 옮기는 것을 권한다.
- "웹 읽기와 검색", "브라우저" 절은 모두 방어 항목의 나열이다. 어떤 공격을 어느 항목이 막는지(예: 이름 확인과 연결 사이 주소 변경 = DNS rebinding, 리디렉션 우회, 페이지 안 지시문 주입)가 이름 없이 괄호 설명으로만 나온다. 독자가 보안 리뷰어가 되려면 위협 이름과 방어의 대응이 필요하다.

### 3.2 학습 적합성: 범위
- 도구 모델, 단계, 경로, 격리, safeGit, 네트워크, 권한 레이어, 웹, 브라우저, 출력·관찰, 해시라인으로 13의 거의 모든 절을 한 글에 담았다(약 1.8만 자). 인덱스 노드 8은 "모델이 실제로 세상에 영향을 주는 경로라 보안 리뷰의 중심"인데, 정작 이 글이 설명하지 않는 부분이 리뷰에 중요하다.
  - Helm 제안 도구의 생성 규칙(13 §3.7, ADR-13-02). "커널 명령마다 도구 하나를 명령 스키마에서 생성하고, 제출과 결과를 한 트랜잭션으로 실행한다"가 5번 노드의 "모델은 제안하고 커널이 바꾼다"가 코드에서 이어지는 지점이다. 글은 "제안 도구"를 명세 성질(원시 행동 null, 순차, 원자적 취소)에서만 언급하고 정의하지 않는다. 03·07a는 이미 제안 도구를 쓰지만 이 노드가 정의할 자리다.
  - 합의가 없을 때의 동작(T9)과 쓰기 루트가 합의에서 계산되는 규칙(13 §3.5.3). 샌드박스가 합의 범위를 강제하는 연결점이라 5번 노드와 이어지는 핵심이다.
  - MCP 도구(13 §3.9)는 MVP 표에도 없다. 기본 도구가 아니라서 빼는 선택은 타당하지만 한 줄도 없다.
- 반대로 상세한 쪽: 브라우저 요청 가로채기, 스크린샷 규칙, 해시라인 태그는 MVP 후반·선택 기능이다. 구현 직후 첫 리뷰 대상은 MVP 도구(bash 격리, 파일 도구, web_fetch, safeGit)이므로 비중을 줄이고 심화로 옮기는 것이 W28에 맞다. 해시라인 절(T1 포함)은 기본값이 `replace`이고 시험 뒤에 켜는 기능이라 짧게 줄여도 된다.

### 3.3 학습 적합성: 수준과 구현 리뷰 목표 연결
- 독자는 bwrap을 들어 본 수준이다(인덱스 머리말). 글은 네임스페이스와 바인드 마운트의 모형을 세우지 않은 채 S1을 설명한다(W5, W8). "왜 쓰기 가능 루트만 rw로 붙이면 `rm -rf`나 스크립트도 막히는가"를 한 문단으로 먼저 세워야 이후 규칙(작업 공간은 읽기 전용, 보호 파일은 빈 파일로 덮음)이 한 모형에 붙는다.
- 구현 리뷰 목표와의 연결은 마지막 점검 목록이 맡는다. 13개 항목은 대부분 코드에서 확인할 수 있는 형태다. 부족한 점은 (a) 항목이 설계 규칙의 반복이라 "코드의 어디를 보면 되는가"가 없다(예: 모든 데몬 git 호출이 `safeGit` 하나를 거치는지는 호출 지점 검색으로 확인한다), (b) T2·T4·T7의 오류를 그대로 담고 있고, (c) 합의 없는 bash, S1b 표시, 네트워크 기본값(합의 없으면 `ask`)이 빠졌다는 것이다. 22의 시험 번호(SG-01~06 등, 13 §3.5.7이 언급)와 연결하면 점검 항목을 "이 시험이 있고 통과하는가"로 바꿀 수 있다.
- 앞 노드와의 연결은 좋다. 1번(결과 확인 도구가 목록에 없음), 2번(데몬 환경에 비밀 없음), 7번(`beforeToolCall`·`afterToolCall`, 프롬프트 캐시), 7.1번(`replay`, 해시 검사) 언급이 모두 앞 글과 일치한다. 5번과 6번(권리 게이트·`taint.web`·발송 항상 질문)은 기준선 문단이 반복한다.

### 3.4 13번 보안 노드와의 겹침
- 겹침이 크다. 인덱스 노드 13은 "외부 접속, 기기 토큰, 도구 격리, 비밀 관리의 경계"이고 주 원천이 18인데, 이 글의 약 40%가 18 §3.11 내용이다. 겹치는 부분: 보호 경로 목록과 `.env` 가림, 환경 변수 허용 목록과 금지 패턴, 마스킹기, 격리 자가 시험, 네트워크 차단 대역과 프록시, 권한 레이어 기준선 표, 웹·브라우저의 신뢰 불가 처리와 `taint.web`.
- 권고: 이 글은 "도구가 어떻게 정의되고 한 호출이 어떤 경로로 실행되는가"(명세, `prepare`·`execute`·`postprocess`, 경로 정규화, 쓰기 절차, 샌드박스 사양, 출력·관찰, 변경 감지)를 중심으로 남긴다. 보호 경로 목록 전체, 환경 변수 금지 패턴, 권한 레이어 기준선 표, 자가 시험 목록은 한두 문장으로 줄이고 "13번 노드에서 다룹니다"로 연결한다. 5번 노드가 이미 발송 항상 질문과 `taint.web`을 설명하므로 기준선 문단의 해당 항목도 중복이다. 네트워크 프록시와 `safeGit`은 도구 실행 메커니즘이라 이 글에 두는 것이 맞다. 이렇게 줄이면 위에서 지적한 예 한 개와 마운트 모형을 넣을 분량이 확보된다. 13번 글의 범위가 아직 쓰이지 않았으므로, 어느 쪽에 둘지는 두 글이 쓰일 때 한 번 더 조정해야 한다.

## 4. 표상 문제
- 글에 다이어그램이 없다. W20 기준으로 표상이 필요한 곳이 두 군데 있다.
  1. S1 샌드박스의 마운트 구성: 시스템·도구 체인(읽기 전용), 작업 공간(읽기 전용), 쓰기 가능 루트(rw), 읽기 전용 덧씌움(`.git` 설정), 가림 파일(빈 파일), 가림 디렉터리(빈 tmpfs), 마운트 안 된 `/srv/volumes`, 네임스페이스 분리가 한꺼번에 관계된다. 관계가 셋 이상이고 "무엇이 어디에 겹쳐 올라가는가"가 층 구조라서 문장으로는 정보가 줄어든다. 표(경로 / 마운트 방식 / 샌드박스 안에서 일어나는 일)나 층 그림을 권한다.
  2. 네트워크 경로: 샌드박스 안 `127.0.0.1:3128`의 `helm-netshim`, Unix 소켓, 데몬의 `helm-egress-proxy`, 인터넷, 그리고 데몬이 직접 하는 `web_fetch`와 browserd 경로가 서로 다른 프로세스·경계 위에 있다. 프로세스 경계와 방향이 있는 구조이므로 다이어그램이 필요하다. 현재 문단은 한 문장에 프로세스 이름이 네 개 나온다.
- 기존 표 2개는 앞 문장이 안내 역할을 한다. 도구 단계 표 앞은 "도구는 단계별로 들어옵니다"로 연결되고, 샌드박스 수준 표 앞은 "샌드박스 수준은 네 가지입니다"로 연결되어 안내는 충분하다. 표의 값(S1·S1b·S0·S2의 조건)을 본문이 다시 쓰는 곳이 있다. "S1과 S1b 둘 다 쓸 수 없으면...", "합의에 어떤 값을 넣어도 S0을 켤 수는 없습니다"는 표에 없는 정보라서 문제없다. "bwrap이 없을 때 2순위"와 본문의 "S1" 정의가 겹치는 곳은 없다.
- 라벨 일치: 표의 `S1`, `S1b`, `S0`, `S2`와 본문이 일치한다. "자가 시험"은 본문에서 쓰이고 표는 없다.

## 5. 지침 부작용
- W51(의인화 금지)과 W32·W33의 충돌: "커널이 문자열로 알 수 없다"를 고칠 때 행위자를 지우면 피동("알 수 없습니다" → "판별되지 않습니다")이 되어 W39와 부딪친다. 이 글에서 3곳 정도다. 지침을 고쳐 "판별하다, 검사하다는 검사 단계에 대응하는 동작이라 허용"이라는 예를 더하면 이런 충돌이 줄어든다.
- W16(출처 표시 금지)과 학습 자료성: "구현 착수 점검표의 결정 항목에 있습니다"처럼 문서 지시를 지우면 독자가 확인 경로를 잃는다. 이 글에서 1곳이다. 근거 메모를 독자용 "참고 위치 부록"으로 따로 줄 수 있다는 규칙이 있으면 본문에서 뺀 출처를 되살릴 수 있다.
- W20(표상 최소화)과 W26(단락당 개념 1~2개): 표상을 요청하지 않은 상태에서 W26을 지키려고 단락을 나누면 글이 길어진다. 이 글에서는 S1 문단이 그렇다. 지침에 "한 단락에 개념이 셋 이상이고 관계가 층 구조이면 표상을 먼저 검토한다"를 더하면 판단이 쉬워진다.

## 6. 전체 평가
- 설계 내용을 구조적으로 거의 정확히 옮긴 글이다. 13·18에서 대조한 사실 주장 수십 개 중 대부분(취소 방식, 쓰기 절차, 잘림 상한, `safeGit` 허용 명령과 금지 명령, 프록시 포트, 자가 시험 항목, 환경 변수 금지 패턴, 브라우저 요청 판정 표, 스크린샷 규칙, 서버 측 검색 도구 기각)이 원문과 일치한다.
- 학습 목표(구현 리뷰)에 직접 영향을 주는 오류는 두 군데다. 해시라인 태그 모형(T1)과 보호 경로 "어떤 합의로도" 일반화(T2)다. 두 번째는 점검 목록에도 들어가 있어서 먼저 고쳐야 한다. 중간 문제 가운데 T4(네트워크 기본값), T5(S1b), T9(합의 없는 bash)는 구현 직후 첫 리뷰 환경(bwrap 미설치 서버)에서 곧바로 부딪칠 내용이다.
- 흐름과 범위: 규칙 목록이 길고 예가 없다. 13번 보안 노드와 겹치는 비중이 커서, 겹치는 항목을 줄이고 그 분량으로 bash 호출 하나를 따라가는 예와 샌드박스 마운트 표, 네트워크 경로 그림을 넣기를 권한다.
- 문체: 사용자 금지어는 없고 합니다체가 일관된다. 의인화는 "설계는 ~기각했습니다", "웹 페이지가 무엇을 시키는지", "커널이 ... 알 수 없습니다", "결정 55는 ... 정했습니다"와 "~하려는 것입니다" 3곳이 남아 있다.
- 높음 기술 문제(T1, T2)를 고치면 W9 규칙에 따라 고친 부분만 한 번 더 검토받아야 한다.
