# 02-architecture.md 리뷰 (V8 형식)

대조 자료: 06 §3.2~§3.8, §3.9, 17 §3.4.2·§3.4.5·§3.8·§3.7, 18 §3.4.1·§3.4.2·ADR-18-01·02, 24 ADR-06-02·06-04. 글은 수정하지 않았다. Mermaid 2개는 mermaid 11.4.0과 headless Chrome으로 렌더링했고 문법 오류는 없었다.

## 1. 기술 문제

### 높음

T1. Windows 호스트 변경 절차가 설계와 다르다.
- 인용: "Windows 호스트 쪽 변경(방화벽, `tailscale serve` 설정)은 에이전트가 하지 않습니다. 검토할 수 있는 PowerShell 스크립트를 만들어 두면 사람이 관리자 권한으로 실행합니다."
- 유형: 사실 오류, 근거 메모 요약 오역.
- 1차 자료: 17 D17-14와 §3.7.1(17-daemon-and-operations.md 155, 1005행). "Windows 호스트 쪽 변경은 없다. 필요한 것은 홈랩 `serve.table` 한 줄과 `just serve-apply`(관리자 권한 불필요)뿐이다. 방화벽 규칙은 더하지 않는다. 확인용 `.ps1`(읽기 전용, 관리자 권한 불필요)만 둔다." 관리자 권한으로 실행할 Helm 전용 스크립트는 없다. 06 §3.8.1(1144행)도 serve 설정은 homelab `tailscale/serve.table` 한 줄과 `just serve-apply`이고 homelab 저장소 변경이라 사람이 한다고 적는다.
- 수정 제안: "serve 설정은 homelab 저장소의 `serve.table` 한 줄과 `just serve-apply`이며 사람이 합니다. Helm이 더하는 방화벽 규칙은 없고, Windows용 `.ps1`은 상태를 읽기만 하는 확인 스크립트입니다."로 바꾼다.

### 중간

T2. 단일 변경 경로의 5단계 중 "알림 대기열"이 트랜잭션 안의 대기열처럼 읽힌다.
- 인용: "하나의 동기 SQLite 트랜잭션 안에서 다음 순서로 실행됩니다. … 5. 알림 대기열: 커밋 뒤 구독 중인 클라이언트에 보낼 이벤트를 쌓습니다."
- 유형: 생략으로 생긴 오해, 글 안의 모순(트랜잭션 안인데 "커밋 뒤").
- 1차 자료: 06 §3.4.5(526행) "outbox 테이블은 없다. 커밋 뒤 알림(`onCommitted`)은 커밋한 JS 턴 안에서 동기로 부르고, 놓친 구독자는 `readEvents(afterSeq)`로 따라잡는다." 06 §3.7.5(a)의 트랜잭션 내용은 "멱등 확인 → basisSeq 낡음 검사·kernel.decide → 이벤트 append → 투영 갱신 → commands 행에 결과 저장"이고 알림은 그 뒤 `onCommitted`다. "알림 대기열"은 06 §3.3.2(394행)의 표현이다. 같은 06 안에서도 §3.4.5와 §3.7.5가 대기열을 두지 않는 쪽이라 §3.3.2의 표현이 더 느슨하다.
- 수정 제안: 트랜잭션 단계는 4개(멱등 확인, 판정, append, 투영 갱신과 결과 저장)로 쓴다. 알림은 "커밋 직후 같은 JS 턴에서 `onCommitted`가 동기로 구독자에게 보내며, 별도 outbox는 없고 놓친 구독자는 seq 이후를 다시 읽는다"로 따로 쓴다. 구현 리뷰에서 outbox를 찾는 오해를 막는다.

T3. 트랜잭션 안 `await`·I/O 금지의 이유가 틀렸다.
- 인용: "트랜잭션이 짧고 동기여야 쓰기 프로세스가 하나뿐인 SQLite에서 다른 요청이 오래 막히지 않고, 중간에 예외가 나면 … 되돌려지기 때문입니다."
- 유형: 근거 혼동, 핵심 메커니즘 생략.
- 1차 자료: 06 §3.6.5(970~972행). `await`가 없어야 JavaScript 이벤트 루프 안에서 두 쓰기가 섞이지 않으며 이것이 단일 writer 직렬화(DR-4)의 구현이다. 트랜잭션 안 I/O 금지는 "트랜잭션이 길어지면 모든 클라이언트와 런타임이 멈추기 때문"이다(데몬이 Node 프로세스 하나, 이벤트 루프 하나). 목표는 명령 하나의 트랜잭션 p99 10 ms 이하다.
- 수정 제안: "`await`가 있으면 그 사이에 다른 제출이 끼어들어 직렬화가 깨지고, 트랜잭션이 길어지면 같은 이벤트 루프에서 도는 모든 클라이언트 처리가 멈추기 때문"으로 바꾼다. "SQLite 쓰기 프로세스가 하나"라는 이유는 근거가 아니다.

T4. "~/projects 밖" 절의 시작 조건과 "리스너는 복구 뒤"의 예외 누락.
- 인용: "**리스너는 복구가 끝난 뒤에만 열립니다.**" 그리고 체크리스트 "리스너를 여는 시점이 복구 뒤인가".
- 유형: 과도한 단정.
- 1차 자료: 17 §3.4.2 "읽기 전용 시작"(572행). 무결성 의심이나 복구 실패(`integrity_suspect`, `recovery_failed`)면 8~14단계 중 남은 것을 건너뛰고 15단계 리스너만 연다. 이때 모드는 `read_only`이고 이벤트를 하나도 쓰지 않는다. 안전 모드(`safe_mode`)도 리스너를 연다. 복구가 완료되지 않은 채 리스너가 열리는 정상 경로가 있다.
- 수정 제안: "정상 시작에서는 복구가 끝난 뒤에 열고, 복구가 실패하면 상태 변경을 모두 거절하는 읽기 전용 모드로만 엽니다"를 덧붙인다. 체크리스트도 "복구 전에 상태 변경 명령을 받는 경로가 있는가"로 바꾸는 편이 정확하다.

T5. `execute` 능력을 끄는 조건에 예외가 빠졌다.
- 인용: "샌드박스를 쓸 수 없으면 `execute` 능력 자체를 끕니다."
- 유형: 과도한 단정.
- 1차 자료: 06 §3.7.4 4번(1068행). 격리 수단을 모두 쓸 수 없으면 `execute`를 끄는 것은 맞다. 단 운영자 설정 `tools.sandbox="off"`(S0)로는 격리 없이 실행할 수 있고, 그때 감사 기록과 상태 경고를 남기며 능력 목록에 `advisory`로 적는다. 18 §3.5 규칙 7과 709행은 S0에서 bash가 `rpc.sock`으로 로컬 관리자 명령을 보낼 수 있다고 쓴다.
- 수정 제안: S0 예외를 한 문장으로 쓴다. 구현 리뷰 항목에는 "`tools.sandbox=off`가 아닌데 격리 없이 `execute`가 켜지는 경로가 있는가"를 넣는다.

T6. "모델 제공자를 호출하는 것은 데몬뿐"이 글 안의 다른 절과 맞지 않는다.
- 인용: "모델 제공자를 호출하는 것은 데몬뿐입니다. 클라이언트는 모델을 직접 부르지 않고, 모델 API 키도 클라이언트에 없습니다."
- 유형: 과도한 일반화, 글 안의 모순.
- 1차 자료: 06 §3.6.3(938행) "`helmd`가 모델 API를 직접 부르는 **유일한 상주 프로세스**다." 외부 런타임(Claude Code, Codex, pi RPC)은 자기 모델 호출을 하며, 글의 "다른 런타임을 위한 자리" 절이 이를 전제한다. 1차 구현(자체 런타임) 범위에서만 맞다. 관찰 에이전트는 모델 호출을 데몬에 맡긴다는 점은 맞다.
- 수정 제안: "1차 구현에서 모델 제공자를 호출하는 상주 프로세스는 데몬뿐이고, 클라이언트와 관찰 에이전트는 직접 부르지 않습니다. 이후 외부 런타임은 자기 호출을 합니다."

T7. 층 규칙을 "아래층이면 모두 의존 가능"으로 읽게 쓴다.
- 인용: "패키지는 층(레이어)에 속하고, 위층이 아래층에 의존할 뿐 아래층이 위층을 import하지 않습니다."
- 유형: 생략으로 생긴 오해.
- 1차 자료: 06 §3.2.1(304행)과 §3.4.1 허용 표. 방향 규칙은 필요조건이고 허용 표가 부분집합으로 더 좁힌다. 예: `daemon`은 `kernel`을 직접 import하지 않는다. `observer`(L4)는 `engine`, `kernel`, `runtime`, `protocol`을 import하지 않는다. `runtime`은 `store`를 import하지 않고 `engine`이 구현한 `RuntimeStorePort`를 쓴다(§3.4.6). L6c는 L5~L1을 건너뛰고 L0만 본다. 글은 `scripts/architecture-rules.ts`의 허용 표가 원본이라고 쓰지만, 이런 금지 의존을 본문에서 한 건도 예시하지 않는다(근거 메모 C7에는 있다).
- 수정 제안: 금지 의존 예 2~3개(daemon→kernel, observer→engine, runtime→store)를 층 설명 뒤에 쓴다. 구현 리뷰에서 가장 자주 쓰일 판단이다.

T8. 로그 흐름 안내가 노드 번호를 잘못 가리킨다.
- 인용: "실험 측정(16번 노드의 지표)"
- 유형: 기준 혼동(설계 문서 번호와 학습 노드 번호).
- 1차 자료: 00-index.md. 지표는 노드 11(관찰 에이전트와 지표, 주 원천 설계 16)이고 노드 16은 구현 리뷰 가이드다. 같은 글의 "4번과 5번", "7.1번과 12번", "8번", "13번"은 노드 번호와 맞는다. 1번 글 쪽도 "테스트 전략(16번 노드)"이 있어 노드 16은 시험을 다루므로 그 참조는 맞다.
- 수정 제안: "11번 노드"로 고친다.

T9. 인증 표의 tailnet 행이 헤더·whois의 역할을 과하게 읽히게 한다.
- 인용: "Tailscale 신원 헤더 + whois 대조 + 기기 토큰, 셋 모두 필요"
- 유형: 생략으로 생긴 오해.
- 1차 자료: 18 §3.4.2(240행)와 ADR-18-01 결과. 헤더와 `X-Forwarded-For`는 같은 호스트 프로세스가 위조할 수 있고 whois·노드 묶기도 통과할 수 있다. 같은 호스트의 프로세스에 남는 방어는 기기 토큰뿐이다. 헤더·whois는 원격 공격자를 거르는 겹이다. 또 ADR-18-01은 토큰의 tailnet 노드 묶기까지 4가지를 요구한다.
- 수정 제안: 루프백 오해 절에서 "헤더는 로컬 프로세스가 흉내 낼 수 있으므로 같은 기기 안에서는 기기 토큰이 마지막 방어"임을 한 문장 추가한다. 이 문장이 "127.0.0.1은 안전하다" 오해를 바로잡는 핵심 근거다.

### 낮음

T10. "셋 모두 `127.0.0.1`에만 바인딩하고": 세 번째는 Unix 소켓이라 해당하지 않는다(17 §3.5, 06 §3.7.1). 주소 검증은 TCP 둘에만 적용된다(설정 검증기는 `::1`도 허용). "TCP 리스너 둘은 127.0.0.1에만 바인딩하고 `local`은 Unix 소켓"으로 쓴다.

T11. 데이터 위치 검사: "`~/projects` 아래이거나 Windows 디스크(`/mnt/c`)". 09 §3.6.2는 `~/projects`, `/mnt/*`, 9p·drvfs, tmpfs 거부이고 시작 단계 2에서 종료 코드 2다(17 §3.2.3). `/mnt/c`만 쓰면 범위가 좁다. 종료 코드를 같이 쓰면 12번 노드와 이어진다.

T12. 종료 순서: "새 요청을 거절하고". 17 §3.4.3은 새 연결을 받지 않고 상태 변경 요청만 5001로 거절하며 읽기 요청은 받는다. "새 연결과 상태 변경 요청을 거절"로 쓴다.

T13. 판정 상태 목록: 4개(허용, 거부, 사람 확인 필요, 충돌)만 쓴다. 06 §3.4.6 `SubmitResult`에는 `key_reused`(같은 멱등 키에 다른 내용, 이벤트와 commands 행을 만들지 않음)와 `error`(저장하지 않고 롤백)가 더 있다. 5번 노드로 미루더라도 "거부도 기록됩니다"는 `rejected`와 `conflict`에 해당하고 `key_reused`·`error`는 기록되지 않는다고 구분하는 편이 정확하다.

T14. 사실 점검 통과 항목(참고): 세 배치안 비교와 C안 선택 근거, 포트·인증 표(경로 ①②, 7840/7841/rpc.sock), 시작 순서의 큰 흐름, 종료 코드 1~5와 재시작 정책, `OnFailure` 알림, `ExecStartPost=helm ops wait-ready`, 관찰 에이전트의 fork·읽기 전용 리더·IPC·`agent:observer` 고정, `secrets run` 자식 로더와 `ExecStart`로 감싸지 않는 이유(sops가 SIGTERM을 전달하지 않음), 백업(데몬 스냅샷을 restic이 가져감), 능력 목록 `enforced`/`detected`/`advisory`, 도구 격리 시 mirrored 설명.

## 2. 지침 위반

W52, W51 (사용자 문체 요구)
- "이 규칙들은 사람이 지키는 관례가 아니라 검사 도구가 지킵니다." "A가 아니라 B" 구호이고 "검사 도구가 지킵니다"는 의인화 소지가 있다. 판정: 검사기는 실행 주체이고 "검사하다"는 허용되지만 "지키다"는 의도 동사에 가깝다. 수정: "이 규칙은 `just verify`에서 검사 스크립트가 위반을 찾아 실패시킵니다."
- "그래서 설계는 네 가지를 함께 겁니다." "설계"(추상 개념)가 주어인 행위 동사. 수정: "그래서 다음 네 가지 장치를 함께 둡니다."
- "설계는 이 두 요구로 세 배치안을 비교했습니다." 같은 문제. 수정: "설계 문서는 …를 비교합니다" 대신 "세 배치안을 두 요구로 비교하면 다음과 같습니다."
- "모델 쪽 코드가 실수로라도 이벤트를 직접 쓸 수 없습니다"는 허용(코드가 쓰는 동작). "모델은 제안하고 커널이 상태를 바꾼다는 원칙을 리뷰로 지키는 대신 import 규칙으로 지키는 셈입니다"는 "원칙이 지켜진다"의 피동 처리로 고치는 편이 좋다.
- "관찰 에이전트에게 쓰기 권한이 없다는 원칙은 이렇게 프로세스 경계로 지켜집니다", "1번 노드의 불변조건 3 … 구조로 지켜집니다"는 피동이라 행위자가 없다. 허용 범위지만 같은 문형이 3곳에 반복된다(W48).
- "축", "박다", "가른다", "닿다"는 글에서 발견되지 않았다.

W16: 본문에 출처·추론 표시 없음. 통과.

W29, W30: 굵은 글씨 3곳(C안 선택 문장, "루프백 바인딩은 격리 경계가 아닙니다", "리스너는 복구가 끝난 뒤에만 열립니다")은 단락당 한 번 이하이고 결론 문장이다. 통과. 단 마지막 점검 목록 10개 항목은 나란한 항목이라 허용되나, 항목이 의문문 형태라 W31(능동 과제·이해 점검 질문)과 경계에 있다. 독자가 요청한 "구현을 볼 때" 기준이라면 유지해도 된다.

## 4. 표상 문제

R1. 렌더링: 두 Mermaid 블록 모두 mermaid 11.4.0에서 오류 없이 렌더링된다. 서브그래프 사이 간선(`L6 --> L6c`, `D --> DB`, `D -- "HTTPS" --> Model`), 세미콜론으로 한 줄에 여러 노드를 선언한 `desktop[...]; mobile[...]`, 큰따옴표 안의 `'`, `·`, `①`, `<br/>`, 괄호는 모두 통과했다. 위험 요소: 예약어 `end`, `click`, `style`, `class`를 id로 쓰지 않았다. 세미콜론 한 줄 선언은 다른 렌더러(예: 정적 변환기, 구버전)에서 깨질 수 있으므로 한 줄에 하나씩 쓰는 편이 안전하다. 출력 대상이 정적 `pre.mermaid`라면 `<`, `>`, `&`는 이스케이프해야 한다(`<br/>`가 이 때문에 깨질 수 있으니 HTML 변환 때 확인).

R2. 그림 2(층 구조)가 글의 설명과 시각적으로 맞지 않는다. 글은 "층을 위에서 아래로 쌓은 것"이라고 하지만 렌더링 결과는 다음과 같다. `daemon`(L5)이 맨 위, L6 앱은 오른쪽 중간, `ai`·`agent`·`tools`(L3')가 `engine`(L3)과 같은 행, `store`(L2)·`kernel`(L1)·`protocol`(L0)이 같은 맨 아래 행에 놓인다. 서브그래프 선언 순서가 아니라 간선으로 정해지는 배치이기 때문이다. 층 번호와 위치가 대응하지 않아 "쌓였다"는 문장이 틀린 인상을 준다. 수정 제안: 보이지 않는 간선으로 순서를 강제하거나, 문장을 "화살표 방향이 의존 방향입니다"로 바꾸고 "쌓은 것"이라는 말을 뺀다.

R3. 그림 2에 허용 의존의 많은 간선이 빠져 있다(`daemon`→`store`·`protocol`·`ai`, `runtime`→`kernel`·`domain`, `observer`→`store/read`, `cli`→`store/admin`, 앱→`client`). `observer`는 간선이 하나도 없는 고립 노드로 그려져 "observer는 어디에 의존하는가"를 알 수 없다. 캡션이 개략도라는 사실과 허용 표가 원본이라는 점을 그림 바로 옆에서 밝히지 않는다(W22 캡션 요건). 또 본문의 "`engine`과 실행 부품이 서로 화살표로 이어지지 않는다는 점"은 맞게 보이지만, 간선 생략 때문에 "화살표가 없다 = 금지"로 오독된다. 이 그림에서 생략한 간선은 "허용되지만 그리지 않음"과 "금지"를 구별하지 못한다.

R4. 그림 1의 `D --> DB`, `D --> Tools`, `D --> Obs`가 렌더링에서 `helmd` 박스 아래 한 점에서 세 갈래로 나가 DB → 도구 → 관찰 에이전트가 일렬로 이어진 것처럼 보인다. 또한 관찰 에이전트가 DB를 읽기 전용으로 읽는 관계(`Obs --> DB`)가 없고 "읽기 전용 fork"라는 라벨만 있어 읽기와 spawn이 한 노드에 섞여 있다. 수정 제안: `Obs -. 읽기 전용 .-> DB` 간선을 추가하고 `D --> Tools`, `D -- fork --> Obs`로 간선 라벨을 분리한다.

R5. 그림 1의 클라이언트 서브그래프에 "Windows 앱"이 있으나 글 첫 문단은 Windows PC가 서버 호스트 자체라고 설명한다. 같은 기기에서 ①(serve 경유)과 ②를 쓰는 경우라는 점이 그림에 보이지 않는다(06 §3.1 300행). 작은 문제이지만 "클라이언트 기기"와 "Windows 호스트 server"가 분리되어 보이므로 한 문장이 필요하다.

R6. 그림 앞 안내는 두 번 모두 "~따라가 보면 됩니다", "~눈여겨보면 됩니다"로 같은 문형이다(W22). 표의 앞 문장 "비교해 보면 … 보입니다"까지 세 번이 비슷하다. 표 값(주소, 인증)을 본문이 다시 나열하지는 않아 W22의 값 반복은 지켰다.

R7. 표(리스너 3행)는 적절하다(비교 지식 구조). 그러나 `local` 행에 "기기 토큰도 받는다"와 "로컬 관리자 주체를 허용한다"가 빠져 있다(18 §3.4.1). 이것이 T9, T5와 이어지는 중요한 구분(`localAdmin`은 `local`에서만)이므로 표에 한 열(받는 주체)이 있으면 좋다.

R8. 표상이 필요한데 문장뿐인 곳: 시작 순서(9개 단계)와 종료 코드 5종 매핑이 줄글이다. 순서가 있는 목록이므로 W27상 번호 목록이나 표가 낫다. 단 F1에서 분량을 줄이면 필요 없다.

## 6. 전체 평가

글의 뼈대는 좋다. 첫 절이 배치안 비교로 "왜 데몬 하나인가"를 W4대로 풀고, 루프백 오해 바로잡기(W13)와 구현 점검 목록이 학습 목표(구현 리뷰)에 직접 쓰인다. 사실 대부분은 06·17·18과 일치하고 Mermaid도 문법 오류 없이 렌더링된다.

고칠 것은 세 군데다. Windows 호스트 절차가 설계와 반대로 적혔고(T1), 단일 변경 경로의 알림 단계와 트랜잭션 제약의 이유가 틀려 구현 리뷰에서 잘못된 것을 찾게 만든다(T2, T3). 그리고 층 규칙이 허용 표보다 느슨하게 읽히는데 금지 의존 예가 없다(T7). 기술 문제는 높음 1건, 중간 8건(T2~T9), 낮음 4건이다. 범위는 노드 12·13·11의 내용이 많이 들어와 있어 줄이는 편이 노드 2 질문에 맞고, 그림 2는 층이 쌓인 모양으로 렌더링되지 않아 설명을 바꾸거나 배치를 고쳐야 한다. 사용자 문체 요구 위반은 "A가 아니라 B" 구호 1건과 "설계가 ~합니다" 의인화 2건이다.
