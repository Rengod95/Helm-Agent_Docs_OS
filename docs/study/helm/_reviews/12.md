## 1. 기술 문제

높음 1건, 중간 10건, 낮음 7건.

### T1. 높음 / 사실 오류: 모델 키가 없어도 데몬은 시작한다
- 인용: "필요한 비밀(모델 키, `HELM_LEDGER_HMAC_KEY` 등)이 없으면 데몬은 시작하지 않습니다."
- 1차 자료: 17 §3.3.2 `required` 주석 "없으면 시작 거부(종료 코드 2). 기본 `["HELM_LEDGER_HMAC_KEY"]`. 모델 키와 웹 검색 키는 넣지 않는다(없어도 데몬은 뜨고, 제공자와 `web_search`만 사용 불가, 02 UC-11 E3, 판정 J-190)". 17 §3.8 4번 "`required`에 없는 키가 비어 있으면 그 기능만 저하로 표시한다". §3.11.2 `secrets`는 값이 없는 키를 `degraded`로, `required` 키 없음만 `critical`(시작 거부)로 둔다. 04번 글도 시작을 거부하는 비밀로 HMAC 키만 든다.
- 문제: 모델 키 부재를 시작 거부 사유로 쓰고 있다. 마지막 점검 목록의 "필수 비밀이 없으면 시작을 거부하는가"는 `required`(기본 HMAC 키 하나)로 읽어야 맞는데, 본문 때문에 리뷰어가 "모델 키 없이 뜨는 정상 구현"을 위반으로 볼 수 있다.
- 수정 제안: "시작을 거부하는 비밀은 설정의 `required`에 든 키이고 기본값은 `HELM_LEDGER_HMAC_KEY` 하나입니다. 모델 키가 없으면 데몬은 뜨고 해당 제공자만 쓸 수 없는 저하 상태가 됩니다"로 고친다. 점검 목록에도 이 구분을 반영한다.

### T2. 중간 / 생략으로 생긴 오해: 크래시 루프 차단기와 systemd 한도가 맞물리는 범위
- 인용: "systemd 쪽에도 10분에 5번 시작하면 포기하고 경보 단위를 실행하는 한도가 있는데, 데몬의 안전 모드가 먼저 걸리도록 숫자를 맞춰 두었습니다. 같은 문제로 반복해서 죽는 데몬이 그때마다 같은 run을 재개해 같은 외부 행동을 반복하는 일을 막는 장치입니다."
- 1차 자료: 12 §3.7.6 첫 항목 "시작 순서의 10단계(`daemon.booted`) 전에 죽은 부팅은 `boots` 행이 없으므로 이 계산에 넣지 않는다. 그런 부팅의 반복은 systemd 쪽 시작 한도가 막는다(판정 J-269)". 17 §3.4.6 둘째 항목 "systemd 쪽 한도는 데몬이 아예 시작 단계를 못 넘기는 경우(종료 코드 1이 반복)를 막는다". 17 §3.6.5 "순서상 데몬 안전 모드가 먼저 걸린다"는 10단계를 넘긴 재시작을 전제로 한다.
- 문제: 두 장치는 순서만 다른 것이 아니라 담당 구간이 다르다. 10단계 이전(설정, 잠금, DB 열기, 마이그레이션 등)에서 죽는 부팅은 데몬 쪽에서 세지 않고 systemd 한도만 막는다. 글은 안전 모드가 항상 먼저 걸린다고 읽히게 쓰고 있어서, 구현 리뷰 때 "시작 단계 실패 반복이 안전 모드로 이어지는가"를 잘못 기대하게 만든다. 점검 목록의 "10분 창, 3회, 마지막 해제 이후, 읽기 전용 시작도 센다"에는 이 경계가 빠져 있다.
- 수정 제안: "`daemon.booted`를 쓰기 전(10단계 앞)에 죽는 부팅은 데몬이 세지 못하므로 systemd 한도가 맡고, 그 뒤에 죽는 부팅은 안전 모드가 먼저 걸립니다"를 한두 문장으로 넣는다.

### T3. 중간 / 순서 오류: 복원 뒤 첫 부팅의 처리 순서
- 인용: 본문 "데몬이 다음에 시작하면 이 표시를 보고 `store.restored`를 기록하고, 리스너를 열기 전에 적어 둔 위험한 변경을 다시 적용하고, 쓰지 않은 발송 승인을 모두 만료시키고, 안전 모드로 들어갑니다." 점검 목록 "새 `storeId`, 위험 변경 재적용, 발송 승인 만료, 안전 모드 진입이 순서대로 일어나는가".
- 1차 자료: 17 §3.9.4 7단계 "`daemon.booted` → `daemon.safe_mode_entered { reason: "restored" }` → `store.restored` … 리스너를 열기 전에: restore-carry 재적용, 미소진 승인 `approval.expired`". 09 §3.8.2 10단계는 `daemon.booted`와 `daemon.safe_mode_entered`를 같은 `BEGIN IMMEDIATE` 트랜잭션에 넣고, 09 §3.14.2 7단계도 같은 순서다. 새 `storeId`는 데몬 시작 전에 CLI가 붙인다(§3.9.4 5~6단계).
- 문제: 안전 모드 진입은 마지막이 아니라 `store.restored`보다 먼저, 부팅 이벤트와 같은 트랜잭션에 기록된다. 점검 목록은 이 순서를 검사 기준으로 삼으므로 올바른 구현을 틀렸다고 볼 수 있다. 본문 서술도 같은 순서를 암시한다.
- 수정 제안: "`daemon.booted`, `daemon.safe_mode_entered(restored)`, `store.restored` 순으로 기록하고, 리스너를 열기 전에 위험 변경 재적용과 승인 만료를 마칩니다. 새 `storeId`는 복원 CLI가 데몬 시작 전에 붙입니다"로 바꾼다. 같은 이유로 4번 글의 설명과 맞춘다.

### T4. 중간 / 생략으로 생긴 오해: 종료 때 끊긴 도구 호출을 모두 "중단됨"으로 기록한다는 서술
- 인용: "끝나지 않은 도구 호출을 '중단됨'으로 기록하고, 마지막 이벤트와 체크포인트를 쓰고, `daemon.stopped`를 기록한 뒤 잠금을 풉니다."
- 1차 자료: 12 §3.7.7 표 4행 "끊긴 도구 호출은 `toolcall.report_unknown{reason: 'daemon_shutdown'}`, run은 `run.end{outcome: interrupted, code: 'daemon_shutdown'}`". 12 §3.5 상태 표(379행)와 09 §3.8.2 11단계: 외부 효과가 있는 호출은 `toolcall.outcome_uncertain`이 되고 run은 `awaiting_recovery`로 가며 `run.end`를 내지 않는다. 외부 효과가 없으면 `toolcall.interrupted`다. 17 §3.4.3 4단계도 "커널이 run을 이미 `awaiting_recovery`로 옮겼으면 `run.end`를 내지 않는다".
- 문제: 외부 효과(발송, push 등)가 있는 호출은 "중단됨"이 아니라 "결과 불명"으로 닫히고 사람에게 복구 질문이 간다. 7.1번 노드의 핵심 구분이 종료 절차 서술에서 사라진다. 02번 글에도 같은 문장이 있어 시리즈 전체에 번진다.
- 수정 제안: "외부 효과가 없는 호출은 중단됨, 외부 효과가 있을 수 있는 호출은 결과 불명으로 닫습니다. 결과 불명이 생긴 run은 복구 대기 상태로 남습니다"로 쓴다.

### T5. 중간 / 순서 오류와 용어 충돌: "마지막 이벤트와 체크포인트"
- 인용: "마지막 이벤트와 체크포인트를 쓰고, `daemon.stopped`를 기록한 뒤 잠금을 풉니다."
- 1차 자료: 17 §3.4.3 6단계 "`daemon.stopped { … }` append. `PRAGMA wal_checkpoint(TRUNCATE)`. DB 닫기." 7단계 "`helmd.owner.json`에 `state: "stopped"`. 잠금 해제."
- 문제: (a) 체크포인트는 SQLite WAL 체크포인트이고 `daemon.stopped` 뒤에 실행된다. 글은 앞에 둔다. (b) "마지막 이벤트"는 종료 순서에 별도 단계가 없다. (c) 이 시리즈에서 "체크포인트"는 4번 글의 HMAC 체크포인트와 7.1의 run 체크포인트를 가리키므로, 설명 없이 쓰면 다른 개념으로 읽힌다.
- 수정 제안: "`daemon.stopped`를 기록하고, WAL 체크포인트(`wal_checkpoint(TRUNCATE)`)를 실행한 뒤 DB를 닫고 잠금을 풉니다"로 고친다.

### T6. 중간 / 생략으로 생긴 오해: 업그레이드 되돌리기가 링크 교체만으로 끝난다고 읽힘
- 인용: "작업 트리에서 바로 실행하지 않는 이유는 … 되돌리기를 링크 교체 하나로 만들기 위해서입니다." / "새 릴리스가 시작에 실패하면 자동으로 이전 릴리스로 되돌립니다. DB 마이그레이션은 앞으로만 가므로(4번 노드), 옛 릴리스가 새 스키마 DB를 열면 종료 코드 4로 거부합니다."
- 1차 자료: 17 §3.10.4 3단계 "DB 스키마 버전 > previous 릴리스의 `schema.max`이면 가장 최근 pre-upgrade 스냅샷을 §3.9.4 절차로 복구한다. 그 사이에 쌓인 이벤트는 quarantine에 남은 DB에만 있다." 같은 절 끝 "스냅샷 복원을 했으면 복원 뒤 첫 부팅이 안전 모드(`restored`)로 시작한다". §3.10.2 7~8단계: 실패 판정은 시작 실패만이 아니라 `releaseId` 불일치, `mode`가 `ready`가 아님, `health = critical`도 포함한다.
- 문제: 마이그레이션이 이미 적용된 뒤의 자동 되돌리기는 링크 교체가 아니라 스냅샷 복원이고, 그 사이 이벤트를 잃으며 안전 모드로 시작한다. 글은 "자동 되돌림"과 "옛 릴리스는 새 스키마를 거부"를 나란히 놓고 둘의 관계(그래서 스냅샷 복원이 필요하다)를 적지 않아 독자가 스스로 이어야 한다.
- 수정 제안: 스키마가 바뀌지 않은 업그레이드는 링크 교체로 되돌리고, 마이그레이션을 거친 뒤에는 pre-upgrade 스냅샷을 복원하며 이때 안전 모드가 된다는 점, 실패 판정이 시작 실패 외에 준비 상태 확인을 포함한다는 점을 쓴다.

### T7. 중간 / 오해를 낳는 서술: 예비 파일(`.reserve`)의 용도
- 인용: "이를 위해 예비 파일(`.reserve`)을 미리 잡아 두어, 공간이 바닥나도 운영 이벤트를 쓸 여지를 남깁니다."
- 1차 자료: 17 §3.2.2(331행) "`.reserve` 64 MiB 예약 파일. 디스크가 가득 차면 지워 마지막 쓰기 자리를 만든다". §4 F-05: `SQLITE_FULL`로 외부 효과 도구의 완료 커밋이 실패하면 12가 결과를 `state/pending-results/<tcId>.json`에 쓰고, 데몬이 `.reserve`를 지워 자리를 만든 뒤 그 pending 결과를 먼저 커밋하고 현재 epoch의 남은 run을 부팅 복구와 같은 규칙으로 정리한다. 여유가 2 GiB로 돌아오면 예약 파일을 다시 만든다. 12 §3.7.7도 같다.
- 문제: 예비 파일의 목적은 이미 일어난 외부 효과의 결과를 잃지 않고 커밋하는 것이다. "운영 이벤트를 쓸 여지"로 쓰면 목적이 바뀐다. 구현 리뷰에서 `disk-reserve` 코드가 pending 결과 커밋과 이어지는지 볼 근거가 사라진다. 또 "5GiB 경고, 1GiB 읽기 전용, 2GiB 해제" 점검 목록에 예비 파일 사용 시점과 재생성이 없다.
- 수정 제안: "예비 파일은 디스크가 가득 찬 순간 이미 끝난 도구 호출의 결과를 커밋할 자리를 만들기 위해 지우는 파일입니다. 여유가 2GiB로 돌아오면 다시 만듭니다"로 쓴다.

### T8. 중간 / 과도한 일반화와 근거 오귀속: 읽기 전용 모드에서 이벤트를 쓰는 조건
- 인용: "디스크 부족과 운영자 지정이면 운영 이벤트는 계속 쓰지만, 무결성 의심, 복구 실패, 투영 실패면 아무것도 쓰지 않습니다. 데이터를 더 손상시킬 수 있는 상황에서는 기록조차 멈추는 것입니다."
- 1차 자료: 17 §3.4.1 부수 효과 `read_only` "사유가 `disk_critical`·`operator`뿐이면 데몬 자신의 운영 이벤트(`daemon.*`, `backup.*`)는 디스크가 허락하면 쓴다. `integrity_suspect`·`recovery_failed`·`projection_fault`면 아무것도 쓰지 않는다." `projection_fault`의 이유는 "쓰기가 투영 갱신을 거치므로" 쓰기 자체가 계속 실패한다는 것이고, 손상 확대가 아니다.
- 문제: (a) 사유는 집합으로 관리되므로 "뿐이면" 조건이 핵심이다. 디스크 부족과 무결성 의심이 함께 있으면 쓰지 않는다. (b) 디스크 부족일 때는 "디스크가 허락하면"이라는 조건이 붙는다. (c) 이유 문장이 투영 실패에는 맞지 않는다. (d) 읽기 전용에서 스케줄러가 멈추고 진행 중 run이 다음 턴 경계에서 멈춘다는 점이 빠졌다.
- 수정 제안: 사유별 동작을 사유, 이벤트 기록 여부, 이유, 해제 조건으로 나눈 표(6절 제안 3)로 옮긴다.

### T9. 중간 / 생략으로 생긴 오해: 읽기 전용 시작의 진입 조건
- 인용: "무결성 검사(7단계)나 투영 따라잡기·복구(9·12단계)가 결정적으로 실패하면, 남은 쓰기 단계를 건너뛰고 리스너만 엽니다."
- 1차 자료: 17 §3.4.2 8단계 "이미 적용된 마이그레이션의 체크섬이 다르면 적용하지 않고 읽기 전용 시작(`integrity_suspect`)". 같은 절 읽기 전용 시작 문단 "(7·8단계의 `integrity_suspect`, 9·12단계의 `recovery_failed`)". 09 §3.10.5도 마이그레이션 체크섬 불일치를 든다.
- 문제: 8단계 조건이 빠졌다. 구현 리뷰에서 체크섬 불일치를 종료 코드로 끝내는 코드를 정상으로 볼 수 있다.
- 수정 제안: "7단계와 8단계(적용된 마이그레이션 체크섬 불일치)의 무결성 문제, 9단계와 12단계의 복구 실패"로 쓴다.

### T10. 중간 / 생략으로 생긴 오해: WSL이 부팅되려면 Windows 로그온이 필요함
- 인용: "linger가 켜져 있어서 로그인하지 않아도 WSL이 부팅되면 올라옵니다." / "WSL 자체가 꺼지지 않게 하는 장치(Windows 로그온 때 WSL을 띄워 두는 작업, `.wslconfig`의 유휴 종료 끄기)는 이미 dotfiles에 있고"
- 1차 자료: 17 §3.6.6 Windows Update 재부팅 행 "재부팅 뒤 사용자가 Windows에 로그온해야 `WSL-Autostart` 작업이 배포판을 띄우고 `helmd`가 시작한다. 로그온 전까지 데몬은 꺼져 있다". §2.3 "로그인 전 자동 시작은 확실한 방법이 없다". 미결 Q17-01(추천: 그대로 둔다).
- 문제: 글은 서버가 재부팅되는 상황을 도입에서 전제하면서, Windows 재부팅 뒤 로그온 전까지 데몬이 꺼져 있다는 결과를 쓰지 않는다. "WSL이 부팅되면"으로 끝나서 자동 시작이 무조건인 것처럼 읽힌다. `.wslconfig`가 dotfiles 소관이라는 서술도 17 §2.2 실험 11·13은 `WSL-Autostart` 작업만 dotfiles 출처로 밝힌다(`.wslconfig`는 읽어서 확인한 값). 낮은 수준의 불확실성이다.
- 수정 제안: "Windows 재부팅 뒤에는 사용자가 로그온해야 WSL이 올라오므로 그 전까지 데몬은 꺼져 있고, 이 구간은 복귀 요약에 '데몬 꺼짐 구간'으로 보입니다"를 추가한다. 이 사실은 미결(Q17-01)이므로 "현재 방법이 없다"로 쓴다.

## 2. 지침 위반

### W51 의인화 (사용자 요구 포함)
금지어(축, 박다, 가른다, 닿다)와 "A가 아니라 B다" 구호는 글에서 발견되지 않았다. "설계가 ~한다" 형태도 없다. 아래는 W51 판정 기준(주어가 실행 주체인가, 동사가 실행 동작인가, 의도·역할 동사가 아닌가)으로 본 결과다.
- 의도를 가진 주체로 쓴 문장(설계 의도가 주어 없이 "~하려는 것입니다"로 반복됨):
  - "정상 종료 절차는 기록을 깔끔하게 남기려는 최선의 노력일 뿐" — 절차(추상 개념)가 의도와 노력을 가진다. "정상 종료 절차가 끝까지 실행되면 기록이 깔끔하게 남지만, 실행되지 않아도 다음 시작의 복구가 같은 상태를 만듭니다"로 상태와 인과를 쓴다.
  - "클라이언트가 복구 전 상태를 보고 명령을 보내지 않게 하려는 것입니다" — 의도. "복구 전에 리스너를 열면 클라이언트는 아직 정리되지 않은 '실행 중' 상태를 보고 명령을 보낼 수 있습니다. 그래서 리스너는 복구 뒤에 엽니다"로 인과를 쓴다.
  - "사람이 원격에서 상태를 보고 복원이나 재구성을 결정할 수 있게 하려는 것입니다" — 같은 문형. "리스너가 열려 있으면 사람이 원격에서 상태를 보고 복원이나 재구성을 결정할 수 있습니다"로 고친다.
  - "변경이 실행 중인 코드에 섞이지 않게 하고 되돌리기를 링크 교체 하나로 만들기 위해서입니다" — 같은 문형.
  - "분기에 한 번은 사람이 restic에서 꺼낸 파일로 같은 훈련을 하도록 권합니다" — 설계가 "권한다". 미결 항목(Q17-05)의 추천값이므로 "분기에 한 번 사람이 restic에서 꺼낸 파일로 같은 훈련을 하는 방식을 쓸 예정입니다"처럼 사실 상태로 쓰되, 확정이 아님을 이유와 함께 한 번 적는다(W42).
- 자원이 행위 동사의 주어인 문장: "D:는 같은 물리 디스크라 디스크 고장을 막지 못하고" — D:(자원)에 "막다"를 붙였다. "D:는 같은 물리 디스크라 디스크가 고장 나면 사본도 함께 잃고"로 쓴다.
- 경계 사례: "스스로를 제한하는 방식"(데몬은 실행 주체이고 "제한하다"는 동작이므로 허용하나 "스스로"가 의지를 암시), 제목 "데몬이 지켜야 할 것"(실제 내용은 의무가 아니라 전제 조건 한 개이므로 제목과 어긋남, W24). "새 릴리스가 시작에 실패하면"(릴리스는 데이터이므로 "새 릴리스로 시작한 데몬이 준비 상태가 되지 못하면"). "이 표시를 보고"(데몬이 `meta.restored_pending`을 읽는 동작이므로 "읽고"가 더 정확).
- 허용으로 판정한 예: "데몬이 잠금을 얻지 못하고 종료 코드 3으로 끝납니다", "운영체제가 잠금을 풉니다", "복구가 만듭니다"(복구는 시작 순서의 단계), "자식은 필요한 키만 골라 … 쓰고 끝납니다"(프로세스의 동작), "`SecretStore`는 … 막혀 있으며"(상태 서술).

- "~하지 않게 하려는", "아무것도 덧쓰지 않으면서", "가져가지 않는다" 등은 대비가 있어 유지 가능하다. "시작하지 않습니다"(필수 비밀 문장)는 T1 수정 때 "시작을 거부합니다"로 긍정화한다.

### 합니다체
- 마지막 절 점검 목록 항목이 "~하는가"로 끝난다. 시리즈 다른 노드(04, 07a)도 같은 형식이라 일관성은 있으나, 사용자 요구가 합니다체이므로 확인이 필요하다. 해당 형식을 유지한다면 근거(시리즈 관례)를 기록한다.

## 3. 독자 흐름 문제

### F1. 안전 모드와 읽기 전용 모드의 관계가 빠졌다
안전 모드와 읽기 전용 시작·모드는 서로 다른 절에서 따로 설명되고, 둘이 어떻게 다른지(리스너를 연다는 점은 같다, 안전 모드는 쓰기를 받고 자동 실행만 멈춘다, 읽기 전용은 상태 변경 명령을 거절한다)와 겹칠 수 있다는 점(`read_only`가 되어도 안전 모드 표시를 유지하고, 읽기 전용이 풀리면 표시가 있을 때 `safe_mode`로 돌아간다)이 없다. 17 §3.4.1 상태표의 가장 헷갈리는 부분이다. 구현 리뷰에서 가장 많이 틀릴 곳이다. 상태 기계 표상(6절 제안 2)과 비교 표(제안 3)로 해결한다.

### F2. 읽기 전용 모드에서 어떻게 나오는지가 없다
65~69행은 디스크 사유의 해제(2GiB)만 쓴다. 무결성 의심, 복구 실패, 투영 실패는 자동으로 풀리지 않고 사람이 복원, `rebuild-projections`, 고친 릴리스 뒤 재시작해야 푼다는 점이 빠졌다(17 §3.4.1). 4번 글(150행)도 "세부 동작은 12번 노드가 설명합니다"라며 주간 전체 검사 실패의 처리(실패 지점 기록, 백업 회전 정지, 읽기 전용으로 바꿀지 사람에게 질문, 자동으로 읽기 전용이 되지 않음)를 12번에 넘긴다. 글은 주간 검사를 타이머 목록에서 이름만 쓰고 이 처리를 쓰지 않았다. 노드 간 약속이 지켜지지 않았다.

### F3. 시작 순서의 실패 분기가 없다
25~31행은 단계를 다섯 덩어리로 묶었지만, 구현 리뷰에서 가장 필요한 정보인 "어느 단계가 실패하면 종료 코드 몇인가, 어느 단계가 실패하면 읽기 전용 시작인가, 어디까지 이벤트를 쓰지 않는가(10단계 이전)"는 앞 절의 종료 코드 문단과 읽기 전용 시작 문단에 흩어져 있다. 독자는 두 곳을 오가며 매핑을 만들어야 한다. 표 한 장으로 해결된다(6절 제안 1).

### F4. 도입의 전제가 본문에서 충분히 쓰이지 않는다
도입은 "언제든 비정상 종료될 수 있다"는 전제와 서버 재부팅, WSL 종료, 디스크 부족을 든다. 이후 절에서 이 사건들이 각각 어떤 동작으로 이어지는지 쓰는 곳은 디스크뿐이다. Windows 재부팅(로그온 필요, T10), `wsl --shutdown`, 절전 복귀, 정전은 17 §3.6.6 표에 정리되어 있는데 하나도 옮기지 않았다. 인덱스의 노드 12 목적("데몬이 죽고 살아날 때의 동작을 리뷰한다")에 가장 가까운 내용이 빠졌다. 사건별 한두 문장 표(사건, 데몬이 겪는 일, 다음 시작에서 보이는 것)가 맞다.

### F5. 구체적 예가 없다
글 전체가 설명과 사실 나열이고 W9, W14가 요구하는 단계별 해설 예가 없다. 크래시 루프(10분 안에 세 번 죽으면 어떻게 되는가)나 복원 뒤 첫 부팅이 가장 적합하다. 예: "03:50, 03:54, 03:58에 연속으로 비정상 종료가 일어나면 세 번째 시작에서 안전 모드가 되고, 그 상태에서 재시작해도 해제 이벤트가 없으면 계속 안전 모드로 시작한다."

### F6. 설계 문서끼리 번호가 다른 점이 글에 없다
글은 "0~16단계"만 쓴다. 독자가 코드를 보면 09 `openStore` 주석은 1~13번이고, 12 `RuntimeLifecycle` 문서에는 다른 번호가 남아 있을 수 있다. "이 글의 번호는 17의 시작 순서표 기준이고 저장소 모듈 안에서는 번호가 다르다"를 한 문장으로 적는다.

### F7. 앞 노드와의 중복
- 02번 글 "시작과 종료" 문단과 12번 글 31~33행·51~53행: 리스너가 복구 뒤에 열린다는 이유, 종료 코드 1~5의 재시작 정책, 종료 절차 목록, 비밀 로더와 `secrets run ... -- helmd`를 감싸지 않는 이유(02번 130행 부근과 12번 35행)가 거의 같은 문장이다. 12번이 "(2번 노드)"로 참조하면서 같은 내용을 다시 설명한다.
- 04번 글 "백업과 복원" 문단과 12번 57~61행: 온라인 백업 API, 사본 전체 검사, restic이 DB 파일을 가져가지 않음, 새 `storeId`, 복원 뒤 안전 모드가 거의 반복된다. 04번 글의 "세 겹" 문단도 12번 13행의 마지막 문장과 겹친다.
- 07a번 글 "안전 모드"와 "정상 종료는 어떻게 다른가" 문단: 크래시 루프 정의, 안전 모드에서 멈추는 4가지, 해제 주체, 종료 절차(20초, SIGTERM 5초 SIGKILL)가 12번 41~51행과 거의 같다.
- 제안: 12번 글에서 이 내용은 한두 문장 연결로 줄이고, 앞 글이 다루지 않은 것으로 채운다. 앞 글에 없는 것: 시작 순서의 실패 분기(F3), 읽기 전용 모드의 사유와 해제(F2), 두 모드의 관계(F1), Windows·WSL 사건별 동작(F4), 업그레이드와 되돌리기에서 스키마가 걸리는 경우(T6), 크래시 루프가 세지 못하는 구간(T2), 종료의 시간 예산(27초 합계 대 45초 한도), 헬스 수준과 `/healthz`의 정보 최소화(아래 T18), 관리 CLI 종료 코드 5(`gated`).

### T18(추가, 중간). `/healthz`와 `OpsStatus` 노출 범위
- 인용: "클라이언트에는 `/healthz`와 프로토콜 메서드로 노출되고, 서버 안에서는 `helm status --json`으로 볼 수 있습니다."
- 1차 자료: 17 §3.11.3 `/healthz`는 인증 없이 응답하고 본문은 `{"status": …}` 한 필드뿐이며 버전, 기기, 점검 상세를 넣지 않는다. HTTP 코드는 `ok`·`degraded` 200, 나머지 503. 읽기 전용 모드는 `degraded`로 보인다. 상세는 인증된 연결의 `daemon.status`(줄인 모양)와 로컬 관리자의 `admin.status`(`OpsStatus` 그대로)다.
- 문제: `OpsStatus` 전체가 클라이언트에 노출되는 것으로 읽힌다. 실제로는 기기는 줄인 `DaemonStatus`만 받고, `/healthz`는 상태 문자열 하나뿐이다. 보안 리뷰(13번 노드) 관점에서 중요한 경계다. 심각도는 중간이다(1절 집계에 포함: T2~T10, T18).
- 수정 제안: "상세 상태(`OpsStatus`)는 로컬 관리자만 보고, 인증된 기기는 줄인 `daemon.status`를 받으며, 인증 없는 `/healthz`는 상태 문자열 하나만 돌려줍니다"로 쓴다.

## 4. 표상 문제

현재 글에는 표상이 없다. W20 기준으로 표상이 필요한데 문장으로만 쓴 곳이 셋이다.
1. 시작 순서(25~31행): 17개 단계, 단계별 실패 결과(종료 코드 2, 3, 5, 4, 읽기 전용 시작, 1), 쓰기 시작선(10단계 이후), 리스너 열기(15단계)를 동시에 유지해야 한다. 다섯 덩어리 목록은 분기를 담지 못한다.
2. 데몬 모드 상태 기계(41, 69, 73행에 흩어짐): 상태 7개, 사건 8종, 복합 규칙(읽기 전용 사유 집합, 안전 모드 표시 유지)이 있어 문장 순서로 옮기기 어렵다.
3. 읽기 전용 사유 다섯 가지의 진입 조건, 이벤트 기록 여부, 해제 조건(69행): 5행 × 3열 비교.
시간 길이 구조(종료 예산)는 문장으로 가능하나 숫자가 여러 개 흩어지므로 낮은 우선순위의 표상 후보다.

## 5. 지침 부작용

- S1. W16(출처 표기 금지)과 W3(깊이 우선) 사이: 설계 문서끼리 번호나 용어가 다른 곳(F6)을 독자에게 알리려면 출처 번호가 필요한데, 출처 표기를 금지하는 규칙 때문에 "17의 시작 순서표 기준"이라는 한 문장도 쓰기 어렵다. 나타난 위치: 시작 순서, 복원 절차. 제안: W16에 "독자가 코드나 다른 문서와 대조할 때 필요한 번호 체계의 기준 문서는 이름만 허용한다"를 예외로 둔다.
- S2. W51(의인화 금지)과 W4(왜 존재하는가에서 시작): 설계 이유를 쓰려면 "~하려고"가 자연스러운데 이 문형이 의도 서술로 분류되어, 글에서 "~하려는 것입니다"가 4번 반복되었다. 인과문("복구 전에 열면 …할 수 있다. 그래서 …")으로 바꾸면 해소되지만 지침에 이 대체 문형이 예시로 없다. 제안: W51에 "설계 이유는 '문제 상황, 그래서 이 선택' 인과문으로 쓴다"를 예시로 추가한다.
- S3. W52/W38 제약 하의 대비 서술: 이 노드는 "A가 아니라 B" 구조가 자연스러운 곳이 많다(장치 대비: 살아 있는 DB가 아니라 검증된 사본). 사용자 요구로 쓰지 못해 두 문장으로 나누는 결과가 되었다. 의도된 효과이므로 지침 개선 대상은 아니다.

## 6. 표상 제안

### 제안 1: 시작 순서 표 (표 + 두 개의 경계선)
[표상 요청서]
- 보여 줄 내용: 단계 0~16, 각 단계의 한 줄 요약, 실패했을 때의 결과(종료 코드 또는 읽기 전용 시작과 사유), 소유 문서 노드
- 지식 구조: 순서, 분기(실패 결과), 조건 조합
- 맡길 정보: 단계별 실패 결과의 대응(글에서 문장으로 옮기면 17줄 반복), 쓰기 시작선(단계 10에서 `daemon.booted`, 이전 단계는 이벤트를 쓰지 못함)과 리스너 열기(15단계)의 위치, 크래시 루프 집계 범위(10단계 이전에는 세지 못함, T2)
- 독자 수준: 이벤트 소싱, `bootEpoch`, 투영, 읽기 전용 개념을 4, 4.1, 7.1에서 배웠다. 단계 번호와 실패 결과는 모른다
- 쓸 이름: 글의 식별자(`daemon.booted`, `bootEpoch`, `helmd.lock`, `SecretStore`, 읽기 전용 시작, 안전 모드, 종료 코드 2, 3, 4, 5, 1)
- 출력 대상: HTML 아티팩트(표, 접근성 있는 색 대비, 모바일에서 가로 스크롤 없이 접히는 레이아웃)
- 앞뒤 문단 요지: 앞은 "시작 순서가 운영의 기준이다"(25행), 뒤는 "리스너는 복구 뒤에 열린다"(33행)와 비밀 로드 설명
- 표 구성 제안: 열 = 단계 | 하는 일 | 실패 시. 같은 열을 쓰는 행은 5덩어리(준비, 저장소, 이번 부팅 시작, 정리와 복구, 실행 시작)로 묶어 구분선을 둔다. 10단계 행 앞에 "여기부터 이벤트를 쓴다", 15단계 행 앞에 "여기서 리스너가 열린다"를 표시한다. 글은 표의 값을 다시 나열하지 않고, 표가 보여 주지 않는 것(왜 이 순서인가: 무결성, 마이그레이션, 투영, `daemon.booted`, 복구, 오케스트레이터, 스케줄러, 리스너)만 쓴다.

### 제안 2: 데몬 모드 상태 기계 (상태 다이어그램)
[표상 요청서]
- 보여 줄 내용: 내부 모드 7개(starting, recovering, ready, safe_mode, read_only, draining, stopped), 클라이언트 모드 이름 대응(normal, safeMode, readOnly, draining), 전이를 일으키는 사건(시작 단계 성공, 복구 끝, 안전 모드 조건, 안전 모드 해제, 읽기 전용 조건, 읽기 전용 해제, 종료 신호, 시작 단계 실패)
- 지식 구조: 상태 전이(복합 상태 포함)
- 맡길 정보: (1) `read_only`는 사유 집합이고 안전 모드 표시를 유지한다는 점, 읽기 전용이 풀리면 표시 유무에 따라 `ready` 또는 `safe_mode`로 가는 점, (2) 읽기 전용 시작은 starting과 recovering에서 곧바로 `read_only`로 가는 경로이며 이 경로에서는 이벤트를 쓰지 않는다는 점, (3) `starting`·`recovering`은 클라이언트 모드가 없고(리스너가 닫혀 있음), `draining` 중에는 모든 모드 사건을 무시한다는 점
- 독자 수준: 안전 모드와 읽기 전용 시작을 글에서 이미 읽었다
- 쓸 이름: starting, recovering, ready, safe_mode, read_only, draining, stopped, 클라이언트 이름 4개, 사유 이름(`crash_loop`, `restored`, `disk_critical`, `integrity_suspect`, `recovery_failed`, `projection_fault`, `operator`)
- 출력 대상: HTML 아티팩트(인라인 SVG, 어두운/밝은 테마)
- 앞뒤 문단 요지: 앞은 안전 모드와 읽기 전용 시작의 정의, 뒤는 안전 모드 차단기의 판정과 해제 주체
- 구성 제안: 가운데 `ready`를 두고 `safe_mode`, `read_only`가 양쪽에 오게 배치한다. `read_only`는 사유 칩을 그 안에 그린다. 종료 신호는 모든 상태에서 `draining`으로 이어지므로 선을 모두 그리지 않고 "어느 상태에서나 SIGTERM이면 draining" 한 줄 범례로 처리해 선 폭주를 막는다. 안전 모드와 읽기 전용의 차이는 글에서 문장으로 쓴다.

### 제안 3: 읽기 전용 사유 비교 표와 안전 모드 대비 (표)
- 보여 줄 내용: 사유 5개(`disk_critical`, `integrity_suspect`, `recovery_failed`, `projection_fault`, `operator`)별 진입 조건, 이벤트 기록 가능 여부, 해제 방법
- 지식 구조: 비교, 조건 조합
- 맡길 정보: "뿐이면" 규칙(T8)을 표 아래 한 문장으로, 해제가 자동(디스크 2GiB 복귀)인지 사람 조치(복원, `rebuild-projections`, 고친 릴리스, `admin.setMode normal`)인지(F2)
- 쓸 이름: 위 사유 이름, 이벤트 이름 `daemon.*`, `backup.*`
- 출력 대상: HTML 아티팩트
- 선택: 마지막에 안전 모드와 읽기 전용 모드를 비교하는 2열 표를 붙이면 F1이 해소된다(리스너, 상태 변경 명령, 자동 재개, 이벤트 기록, 해제 주체).

### 제안 4(낮은 우선순위): 종료 시간 예산 타임라인
- 단계 1~3(최대 20초), 단계 4(최대 6초), 단계 5~7(보통 1초 이하), 합계 약 27초, systemd 한도 45초. 가로 막대 타임라인이 한 번에 비교를 보여 준다. 종료 순서 목록(T4, T5, T11 수정 후 번호 목록)에 붙일 수 있다.

## 7. 학습 적합성

범위: 인덱스의 노드 12 목적("1인 서버에서 데몬이 죽고 살아날 때의 동작을 리뷰한다")에 비해 글이 설치, 업그레이드, 타이머, 비밀, 백업·복원, 디스크, 상태 확인, 관리 CLI, 시험 장치를 모두 한 장에서 다룬다. 분량이 약 1.5만 자인데 사실 나열형 문단이 많고, 구조를 세우는 도입(1절)과 점검 목록(마지막 절)만 목적과 직접 이어진다. 다음처럼 가지치기를 제안한다.
- 줄이기: 02, 04, 07a와 겹치는 문단(F7), 시험 종료 지점과 고장 주입(77행, 구현 리뷰 16번 노드가 더 적합), `OpsStatus` 문단의 필드 나열(73행), 관리 CLI 종류 설명(75행).
- 넓히기: 시작 순서의 실패 분기(F3), 두 모드의 관계와 상태 기계(F1), 읽기 전용 해제(F2), Windows·WSL 사건별 동작(F4), 업그레이드 되돌리기에서 스키마가 걸리는 경우(T6), 크래시 루프의 집계 경계(T2).

수준: 독자는 Helm 이론, systemd, SOPS를 알고 4, 4.1, 7.1을 읽은 상태다. 글이 이 수준에 맞게 systemd 기본 설명을 짧게 쓴 것은 적절하다. 반면 전제로 삼은 4번 글의 "펜싱 세 겹"과 7.1의 부팅 복구를 연결 문장 한 줄로만 참조하고 본문에서 다시 설명하는 곳이 여럿이어서 중복이 된다(F7).

구현 리뷰 목표 연결: 마지막 절 점검 목록은 목적에 잘 맞는 형식이다. 다만 목록 12개 항목 중 T1, T3, T13이 틀렸거나 부정확한 기준을 담고 있어 수정이 우선이다. 보태면 좋은 항목: `Restart=on-failure`와 `RestartPreventExitStatus=2 3 4 5`, `TimeoutStopSec=45s`(종료 시간 예산이 45초 안에 들어오는가), `.reserve` 사용 시점과 pending 결과 커밋, 읽기 전용 모드가 풀리는 조건, `/healthz` 응답이 상태 문자열 하나뿐인가, 업그레이드가 빌드, 자체 시험, 백업, 링크 교체, 확인 순서를 따르고 실패 시 스키마 비교로 스냅샷 복원 분기가 있는가.

노드 간 중복과 약속: 02, 04, 07a가 12번에 넘긴 약속(04의 주간 전체 검사 실패 처리, 02의 크래시와 복구 세부, 07a의 안전 모드 운영 측면)은 F2에서 보듯 일부만 이행되었다. 반대로 12번이 앞 글 내용을 되풀이하는 분량은 F7에서 열거했다.

## 8. 전체 평가

근거 메모와 17번 설계 문서의 대부분 수치(타이머 시각, 임계값, 종료 코드, 시작 단계 번호와 분류)는 원문과 일치한다. 사실 오류는 하나(모델 키를 필수 비밀로 쓴 문장)이고, 그보다 중요한 문제는 구현 리뷰 기준으로 쓰이는 문장 몇 개가 원문과 순서나 범위가 어긋난 점(복원 순서, 종료 때 도구 호출 기록, 크래시 루프 집계 범위, 예비 파일 목적, 읽기 전용에서 이벤트 기록 조건)이다. 문체는 금지어와 "A가 아니라 B" 구호가 없고 합니다체를 지키며, 의인화는 "~하려는 것입니다" 형태의 설계 의도 서술과 몇 곳의 자원 주어 문장에 한정된다. 학습 면에서는 앞 노드 02, 04, 07a와 겹치는 설명이 길고 이 노드만의 내용(시작 순서의 실패 분기, 모드 상태 기계, Windows·WSL 사건별 동작)이 표상 없이 얕게 쓰여 있다. 표 두 개(시작 순서, 읽기 전용 사유)와 상태 다이어그램 하나를 넣고, 중복 문단을 줄이는 방향의 수정을 권한다.
