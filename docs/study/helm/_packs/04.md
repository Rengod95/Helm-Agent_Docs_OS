# 노드 04 학습 원천 묶음: 정본, 레코드·ID, 이벤트 로그, 투영, 재구성·복원

- 주 문서: `docs/design/08-domain-model.md`(08), `docs/design/09-event-store.md`(09)
- 이름 정본 확인용: 10(명령), 12(복구), 17(운영·백업), 18(HMAC·기기), 19(재전송), 22(시험 ID), 25(용어)
- 표기: 출처는 `문서 §절`. 줄 번호는 적지 않는다(설계 문서가 수정 중이다). 08·09는 "1단계 초안"이며 `[제안]` 표시는 본문에 그대로 남겼다.

## 1. 이 노드가 답할 질문

> "Helm의 정본은 무엇이고, 어떤 레코드(Goal, Concern, Thread, Run, ToolCall, Question, Agreement 등)와 ID 접두사로 이루어지는가? 이벤트 로그(SQLite, WAL)는 어떻게 쓰이고(트랜잭션, 시퀀스, 멱등 지문, 펜싱/epoch), 투영(projection)·읽기 모델은 어떻게 만들어지며, 재구성·마이그레이션·복원은 어떻게 되는가?"

- Q1 정본은 무엇인가 (08 §2.1, 09 §3.1)
- Q2 레코드 종류, 평면, 접두사, 만드는 이벤트 (08 §3.2.2, §3.20.1)
- Q3 레코드끼리 무엇을 참조하고 쓰기 때 무엇을 검사하는가 (08 §3.20.2~3)
- Q4 `store.transaction(fn)`의 단계, seq, 해시, 멱등, 동시성 (09 §3.2, §3.8.4, §3.9, §3.16.2)
- Q5 단일 쓰기와 펜싱 (09 §3.8.1, §3.8.3; 08 R-42·R-43)
- Q6 투영, 재구성, 마이그레이션, 백업, 복원 (09 §3.11~§3.14)

## 2. 핵심 개념

### 2.1 정본은 이벤트 로그다

| 개념 | 뜻 | 저장 | 해시 체인 |
|---|---|---|---|
| 명령 (command) | 상태를 바꾸려는 의도. 아직 일어난 일이 아니다 | `commands` (inbox, 결과 포함) | 아니오 |
| 영속 이벤트 | 커널이 명령·관찰·타이머를 평가해 기록한 불변 전이 | `events` | 예 |
| 휘발 이벤트 | 화면 갱신용 흐름 (토큰 스트림, 도구 출력 진행) | 저장 안 함 | 아니오 |
| 투영 (read model) | 이벤트를 접은 테이블. 커널 판단의 입력이자 조회 대상 | `p_*` | 아니오 (재구성 가능) |
| 운영 상태 | 재구성이 필요 없는 값 (기기 접속, 소비자 커서) | 운영 테이블 | 아니오 |
| blob | 큰 내용. envelope에는 내용 해시만 든다 | `blobs` + 파일 | 해시만 |
| trace | 모델 요청, 압축, 실행 단계 같은 실행 기록. 도메인 상태 밖 | `trace` | 아니오 (D09-11) |

- `State(seq_n) = fold(apply, State0, Events[1..n])` (09 §3.1, 08 §3.1.1). 운영 상태, 휘발 이벤트, trace는 State에 들지 않는다.
- 레코드 테이블을 정본으로 두지 않는다. 레코드를 직접 쓰는 API는 없다. 레코드는 이벤트를 접은 결과의 모양이다 (08 §3.1.4, §2.1 "기준 원본은 이벤트 로그" [제안: 결정 29 기본값]).
- 모델은 제안만 하고 커널이 상태를 바꾼다 (결정 14). 관찰은 런타임·사람·외부·타이머만 만든다 (08 R-06).

### 2.2 다섯 평면 (08 §3.1.1)

| 평면 | 뜻 | 대표 레코드 | 누가 바꾸는가 |
|---|---|---|---|
| N | 하기로 한 것, 지킬 것 | Project, Goal, Concern, Choice, Agreement, Question | 사람, 확인된 제안, 맡긴 범위의 정책 |
| E | 안다고 주장하는 것과 모르는 것 | Observation, Assumption, Interpretation, Possibility, Finding | 모델은 제안만, 관찰은 런타임·사람·외부·타이머, 승격은 커널 |
| M | 실제로 바뀐 것 | 저장하지 않음. `MaterialRef`로 참조만. WorkUnit, Run, ToolCall은 실행 기록 | 도구 실행 |
| A | 참여자와 능력 (고정 표) | 행위자 문법, 능력표, Device | 코드, 기기는 사람이 등록 |
| P | 지금 해도 되는가 | Grant, 합의 범위, PolicyProposal, Procedure | 사람 (관찰 에이전트는 수정안만) |

판별 질문: "일하는 도중에 상황이 바뀌면 답도 바뀌는가?" 바뀌면 P, 같으면 A (08 §3.1.1).

### 2.3 레코드 종류와 ID 접두사

- ID 형식: `<prefix>_<ULID>`. 접두사는 소문자 두 글자, ULID는 Crockford base32 26자이며 첫 글자는 0~7이다. 예: `cn_01JA2Z7Q8M3XK4V9TB6N0PRWES` (08 §3.2.1).
- ID는 바뀌지 않는다. 시각 부분은 힌트일 뿐이고 순서는 `seq`로만 판단한다 (08 §3.2.1).
- 커널은 ID를 만들지 않는다. 쓰기 경로가 `IdFactory`를 주입한다 (08 §3.2.1).
- 접두사는 60개다. 브리프의 24개와 이 문서가 더한 36개다 (08 §3.2.2).
- blob은 `sha256:<hex>`로 가리키고, 행 식별자는 `bl_<ULID>`다 (09 §3.12).

### 2.4 레코드 공통 메타, 품질, 자율성 (08 §3.4)

- `RecordMeta`: `id`, `plane`, `projectId`, `createdSeq/At/By/Via`, `revisionSeq`, `revision`, `lastSeq`, `updatedAt`, `textOverflow` (08 §3.4.2).
- `revisionSeq`는 사람 판단에 영향을 준 마지막 변경의 seq로 낙관적 동시성 기준이다. `lastSeq`는 모든 변경의 seq다. `revision`은 바뀐 횟수 + 1로 화면용이며 비교에 쓰지 않는다 (D08-12).
- 품질 단계: `captured` → `structural` → `qualified` → `accepted`. 옆길 플래그는 `contested`, `stale`, `superseded`로 단계와 독립이다 (08 §3.4.3, D08-3).
- `Autonomy`: `HumanDecision` 또는 `AutonomousDecision`(`whyNotAsked` 필수, `decisionKind`, `decisionPointKey`). `whyNotAsked`는 `info_gate`, `within_grant`, `emergency`, `assumption_expired`, `auto_verifiable`, `delegated_by_human`, `rule` 일곱 가지다. 권리 게이트 결정은 autonomous가 될 수 없다 (08 §3.4.5, R-15).
- 자율 결정 레코드는 ch, lp, lt, sa, sc, md 여섯 종류이고 레코드 안의 결정 블록도 이의 대상이다. `contestable` 필드는 없다 (08 D08-13, §3.24.1 불변조건 7).
- 텍스트 상한을 넘은 입력은 거부하지 않고 앞부분만 남기며 원문은 blob에 둔다 (08 E-29).

### 2.5 레코드별 요점

- **Project (`pj`)**: 작업 루트(`rootPaths`), 외부 세션 관찰 여부. 데몬 하나가 여러 프로젝트를 한 DB에 담는다 (D08-7). 생성 때 자리표시 Goal과 `light_work` Concern이 함께 생긴다 (09 §3.4.1).
- **Goal (`gl`)**: 프로젝트 단위 궁극 목표. `goalVersion`을 가지며 상태는 proposed, active, paused, achievement_claimed, achieved, superseded, retired다. 확정과 개정은 사람만 한다 (결정 11, R-35).
- **Concern (`cn`)**: 다룰 가치가 있는 상황 한 덩이. 상태는 open, active, held, completed, closed, merged다. `completed`는 결과 확인과 전체 반영까지 끝난 상태이고 `closed`는 완료하지 않고 끝낸 상태다 (08 §2.3 "완료" 행, §3.22.2).
- **WorkUnit (`wu`)**: Concern 안의 일 한 단위. `workKind`는 inquiry, probe, change, integration이다. `plannedPrimitives`에 write나 send가 있으면 합의가 필요하다 (R-05, §3.7).
- **Observation (`ob`)**: "누가 무엇을 보았다"는 E 기록이며 참이라는 뜻이 아니다. `obsKind`는 tool_result, tool_interrupted, utterance, reaction, external_response, no_response, derived, material_change 여덟 가지다. 반응도 관찰이다 (D08-5, §3.8).
- **Assumption (`as`), OpenQuestion (`oq`)**: 전제와 모델의 열린 질문. 사람에게 묻는 Question (`qs`)과 구분한다 (§3.25).
- **Interpretation (`in`), Possibility (`ps`)**: 해석과 가능성. `in`은 관찰이 없으면 전제로 강등된다 (R-07). `ps`의 `possibilityKind`는 cause, perspective, solution, preference_criterion, failure_path이며 cause와 perspective는 `ifTrue`, `falsifier`, `nextCheck`가 필수다 (R-08).
- **DiscriminatingCheck (`dc`)**: 관찰 전에 결과 라벨과 후보별 예측을 선언한다. 예측이 두 개 이상이고 서로 달라야 한다 (R-12, E-06). 관찰 뒤에 선언하면 `posthoc`으로 표시하고 승격에 세지 않는다 (E-08, D08-2).
- **Finding (`fd`)**: 승격 때 새로 생긴 판단. `promotionBasis`(supports, checks, counterSearchCount, atSeq)에 승격 근거를 고정하고, 원래 추측은 `promoted`로 남는다. 신뢰도는 숫자가 아니다 (D08-1, D08-10, R-13).
- **Choice (`ch`)**: 결정. `alternatives`와 `basis`(E 레코드)가 각각 한 개 이상이고, `goal`은 결정 시점 버전을 가리킨다. `committed`에서 시작해 `superseded`, `revoked`로만 간다 (08 §2.3, §3.22.12, R-15).
- **Objection (`ct`)**: `contests` 링크로 대상을 가리킨다. 대상은 결정 레코드와 근거 레코드를 포함한다. 이유 없는 이의도 받는다 (R-16, J-20).
- **Agreement (`ag`)**: 작업 합의. `purpose`, `criteria`(한 개 이상), `scope`, `forbidden`, `forbiddenResources`, `stopConditions`(한 개 이상), `preserve`, `nonGoals`, `checkpoint`를 가진다. 상태는 proposed → active → fulfilled, released, declined, expired, superseded다 (08 §3.11, §3.22.4).
- **Criterion (`cr`)**: 완료 기준. 결과 제출의 기준 id 집합은 현재 개정판과 같아야 한다 (R-17).
- **Grant (`gr`)**: 맡겨 둔 권한. `scope`와 `expiresAt`을 가지며 상태는 active, revoked, expired, exhausted다 (R-41, §3.22.15).
- **ResultSubmission (`rs`)**: 완료 주장. `criteriaResults`, `materialChanges`(M 참조), `limitations`, `integrationCandidates`를 담는다. 근거가 없는 기준은 `unverified`로 강등된다 (E-05).
- **Attestation (`at`)**: 검증 증언. 검증 실행의 루트가 생산 실행 루트와 같으면 `denied.producer_cannot_attest`로 거부된다 (R-18, E-32).
- **Acceptance (`ac`)**: 결과 확인. `decidedBy`는 `human` 리터럴로 고정된다. 결정값은 accepted, conditional, revision_requested, rejected, criteria_wrong이다. 만든 뒤 바뀌지 않는다 (08 §3.12, §3.24.1 불변조건 5).
- **Integration (`ig`), Obligation (`io`)**: 전체 반영과 반영 항목. 결과 확인 뒤 열리고, 모든 항목이 닫히거나 넘겨지거나 미뤄지면 `integration.completed`다 (R-20, R-22, §3.22.6).
- **Question (`qs`)**: 사람에게 묻는 질문. 게이트는 rights(임시 가정 금지)와 information이다. information은 `blocks`가 action, workunit, concern이면 막히고, nothing이면 막히지 않으며 가정과 만료점이 필수다. 상태는 pending, delivered, answered, assumed, withdrawn, expired, delegated다 (결정 12, §3.13, §3.22.7).
- **Expectation (`ex`)**: 보낸 것에 대한 기대. 보낸 도구 호출이 완료된 뒤에만 만들고 기한이 지나면 `no_response` 관찰이 생긴다 (R-26).
- **Prediction (`pr`)**: 확인일이나 트리거가 있는 예측. `basis`가 필요하고 트리거가 `manual`이면 안 된다 (R-27).
- **LoopPlan, LoopTransition, SituationAssessment, ModeAssignment (`lp`, `lt`, `sa`, `md`)**: 루프(O, I, C, A, S) 계획, 전환, 상황 판정, 모드 배정. 모두 Autonomy를 가진다. 루프 위치는 Concern 상태 기계와 따로 둔다 (결정 5). 계산은 14 소유다.
- **Probe (`pb`), Watch (`wt`)**: 탐침과 지속 관찰 (R-39, R-50).
- **Inquiry (`iq`), Stimulus (`st`), PreferenceModel (`pm`), Lens (`ln`)**: 탐구 실행, 자극, 선호 모델, 렌즈. 자극은 탐구가 열려 있을 때만 만든다 (R-37). 선호 기준은 지지 반응 관찰이 있어야 확인된다 (R-36, `E reveals N`).
- **Run (`rn`)**: 에이전트 실행 한 번. `runKind`는 work, verifier, mediator, branch, subrun, inquiry다. 연결은 `threadId`, `parentRunId`, `rootRunId`, `goalId`, `concernId`, `workUnitId`, `inquiryId`다. 펜싱 필드는 `ownerEpoch`와 `attempt`다. 진행 단계는 trace에 둔다 (08 §3.18.1, D08-14).
- **ToolCall (`tc`)**: 도구 호출 한 번. `runId`, `requestId`(mr), `messageId`(ms), `primitive`, `modelArgs`(blob), `replay`(기본 never), `purpose`를 가진다. `started`는 실행 전에 커밋한다 (write-ahead, 08 §3.18.2).
- **Thread (`th`)**: 실행 대화 흐름. `activeRunId`, `forkedFrom`, `status`(open, closed)를 가진다. 대기 실행은 같은 thread에서 새 실행이 이어받는다 (J-38, §3.22.13).
- **RollbackPoint (`rb`)**: 가정하고 진행할 때 되돌릴 지점. `mechanism`은 git_ref, snapshot_blob, manual이다 (08 §3.18.3).
- **Device (`dv`), PairingCode (`pc`), PolicyProposal (`pp`), Procedure (`pd`)**: 기기와 페어링(18), 관찰 에이전트의 수정안(정본은 16 §3.15.3), 채택된 절차. 신뢰를 올리는 것은 사람만 한다 (R-52, R-40).
- **Link**: `from`, `to`, `rel`, `createdSeq`, `createdBy`, `note`. 이벤트가 아니라 투영기가 payload에서 만든다 (08 §3.4.8, §3.20.3). `rel` 종류는 supports, challenges, qualifies, invalidates, supersedes, reopens, derived_from, belongs_to, child_of, split_from, merged_into, justifies, authorizes, fulfills, reveals, depends_on, answers, contests다.

| 필드 | 뜻 |

## 3. 동작 흐름

### 3.1 `store.transaction(fn)` (09 §3.8.4, §3.16.2)

`transaction(fn)`이 쓰기 트랜잭션 하나다 (J-148). `commit`(명령 하나)과 `commitBatch`(여러 개)는 그 위의 편의 함수다. fn 안의 뒤 제출은 앞 제출이 같은 트랜잭션에 쓴 투영과 덧씌운 KernelState를 본다.

```text
transaction(fn):
  0. (트랜잭션 밖) envelope 스키마 검사, scopeKey·fingerprint 계산, 큰 본문은 putBlob
  1. BEGIN IMMEDIATE
  2. fence: meta.current_boot_epoch == myEpoch 아니면 ROLLBACK, throw (path.fenced)
  3. fn(tx) 안에서 tx.commitOne(input)마다:
     a. 멱등 조회 SELECT commands WHERE scope_key
          같은 fingerprint → 저장된 result에 replayed: true
          다른 fingerprint → key_reused (행 없음)
     b. decision = input.decide(view, ctx)   // 10의 순수 함수, expect·basisSeq 검사 포함
          status = error → 전체 ROLLBACK
     c. drafts = decision.events  (거부·충돌·게이트면 command.rejected 포함)
     d. 각 draft: seq = head+1, id = ids.next('ev'), recordedAt = max(clock, last_recorded_at)
          payload 검사 (실패 = 커널 버그), canonicalJson ≤ 256 KiB
          hash = sha256(prevHash + "\n" + canonical)
          INSERT events, INSERT event_refs
          projectors.apply(db, envelope)   // 오류면 전체 롤백 (D09-5)
          prevHash = hash; head = seq
     e. INSERT commands(scope_key, command_id, type, fingerprint, status, result, first_seq, last_seq, ...)
  4. INSERT trace (after_seq = head)
  5. UPDATE meta head_seq, head_hash, last_recorded_at
  6. head가 1,000의 배수를 지나면 integrity_checkpoints에 HMAC 행
  7. COMMIT
  8. 같은 JS 턴에서 동기로 onCommitted(StoredEvent[]) (구독자 예외는 로그만)
```

- fn 안에서 await, 네트워크, 파일 쓰기를 하지 않는다. fn이 던지면 전체 롤백이고 KernelState 사본도 버린다 (09 §3.16.2).
- 고장 주입 지점: `after_fence`, `after_decide`, `after_event_insert:<n>`, `after_projection:<n>`, `before_command_insert`, `before_trace_insert`, `before_commit`. 커밋 전에 어느 지점에서 예외가 나도 events, commands, p_*, trace에 흔적이 남지 않아야 한다 (09 §3.8.4).

### 3.2 처리 결과별 저장 (09 §3.9.2, D09-3)

| 결과 | commands 저장 | 이벤트 | 같은 키 재시도 |
|---|---|---|---|
| accepted | 예 | 커널 이벤트 | 저장된 결과 재생, `replayed: true` |
| needs_gate | 예 | `command.rejected`(gateQuestionId) + `question.recorded` | 같음 |
| rejected | 예 | `command.rejected` 하나 | 같음 (다시 계산하지 않음) |
| conflict | 예 | `command.rejected`(conflict) 하나 | 같음. 새 버전은 새 키 |
| key_reused | 아니오 | 없음 | `{status: "key_reused", original}` |
| error, 일시 실패 (fenced, BUSY, 디스크 가득, 투영기 예외) | 아니오 | 없음 (롤백) | 처음부터 다시 처리 |

거부를 저장하는 이유: 저장하지 않으면 그사이 상태가 바뀌어 같은 키 재시도가 통과할 수 있고, 클라이언트가 어느 시도가 반영됐는지 알 수 없기 때문이다 (09 §3.9.2, A09-2).

### 3.3 멱등 키와 지문 (09 §3.9.1, §3.9.3)

```text
scopeKey    = <channel>|<actor>|<viaKey>|<idempotencyKey>      // channel: H M X R S A
viaKey      = device:<dv> | local_cli:<uid> | run:<rn> | process:<name> | system
fingerprint = sha256(canonicalJson({type, actor, via: viaKey, payload에서 생성 id 필드 제외}))
```

- 지문에서 빼는 것: commandId, expect, basisSeq, 연결 id, 리스너, attempt, pid, 제출자 생성 id. 다른 연결이나 리스너로 재전송해도 같은 지문이어야 한다 (22/FI-25).
- 내부 쓰기 키: 도구 결과 `tc:<tcId>:result`, 스케줄러 `timer:<timerId>:<dueAt>`, 부팅 복구 `recover:<runId>:<attempt>`와 `recover:<tcId>:<epoch>`, 외부 관찰 `ext:<channel>:<actor>:<externalId>`, 이어받기 `handoff:<awaitingRunId>`.

### 3.4 낙관적 동시성 (09 §3.9.4, D09-4)

- 사람 명령은 `basisSeq`(화면이 본 seq)를 싣는다. 커널은 `revisionSeq > basisSeq`면 충돌로 본다. 레코드 지정 비교는 `expect: [{id, version}]`로 한다. 비교는 `decide` 안에서 한다 (10 V-VER-01).
- 에이전트 제안은 기본적으로 `expect`를 넣지 않고 상태 기계 검사에 맡긴다. 전역 커서 `expectedCursor`는 쓰지 않는다. commit 결과에 `headSeq`를 돌려준다.

### 3.5 단일 쓰기, 펜싱, epoch (09 §3.8.1, §3.8.3)

| 겹 | 방법 | 막는 것 |
|---|---|---|
| 1 | systemd 단위 하나 (17) | 같은 기계에서 데몬 두 개 |
| 2 | `data/helmd.lock`에 `BEGIN EXCLUSIVE` 유지, 실패하면 종료 코드 3 | 수동 실행, 오프라인 CLI와의 충돌 |
| 3 | 모든 쓰기 트랜잭션이 `BEGIN IMMEDIATE` 직후 `meta.current_boot_epoch`를 대조, 다르면 롤백하고 `path.fenced` | 두 프로세스가 같은 DB를 쓰는 경우 |

- Node에는 기본 `flock`이 없어서 잠금을 SQLite 배타 트랜잭션으로 구현한다. epoch는 ULID다. 정수 카운터는 복원 때 되돌아갈 수 있다 (D09-7, D09-10).
- 실행의 명령은 `runId`를 싣고, 커널은 `ownerEpoch ≠ 현재 epoch`이거나 실행이 running·stopping이 아니면 `path.stale_epoch`로 거부하고 거부를 기록한다 (08 R-43, 09 F-15).
- 두 코드의 차이: `path.fenced`는 커밋 시점 대조 실패로 프로세스를 끝내고, `path.stale_epoch`는 옛 실행의 명령 거부다.
- 부팅 복구(`internal:recovery`)만 이 검사를 받지 않는다. 대신 키가 `recover:` 형식이어야 한다.

### 3.6 부팅 순서 (09 §3.8.2)

1. 위치 검사, 2. 인스턴스 잠금, 3. HMAC 키 확인 (없으면 시작 안 함), 4. DB 열기와 `application_id`, 5. `user_version` (앱보다 높으면 거부), 6. 무결성 tail 검사 (실패하면 `read_only`), 7. 마이그레이션 (pre-migrate 백업 뒤), 8. 이벤트 타입과 버전 확인 (모르면 거부), 9. 투영 버전과 `last_seq = head_seq` 확인 (어긋나면 재구성), 10. `BEGIN IMMEDIATE`로 새 epoch, `boots` 행, `daemon.booted` 기록 (복원 뒤 첫 부팅이면 `daemon.safe_mode_entered{restored}`), 11. 런타임 복구 (12 §3.7.3), 12. 타이머 따라잡기 (`occurredAt = due_at`), 13. 쓰기 받기.

- 11번의 복구: ownerEpoch가 현재와 다른 queued·running·stopping run은 `interrupted`로, started·replaying 호출은 `interrupted` 또는 `outcome_uncertain`으로 정리한다. 결과 불명 외부 호출이 있는 run은 `awaiting_recovery`가 되고 `run.ended`를 내지 않는다 (09 §3.8.2).

### 3.7 투영 갱신과 조회 (09 §3.11.1, §3.11.5, §3.16.4)

- 투영기 `core` 하나가 모든 `p_*`를 갱신한다. 처리 순서: `upcast` → 생성 이벤트면 `*Core`로 레코드 INSERT와 링크 생성 → 전이 이벤트면 `machines/*.ts`로 다음 상태 계산 → `last_seq = seq`, `bumpsRevision`이면 `revision_seq = seq` → 파생 테이블(`p_timers`, `p_attention`, `p_goal_versions`, `p_agreement_revisions`, `p_budget`, `p_dials`, `p_search`) → `event_invalidations`.
- 지표 투영(16)은 커밋 뒤 소비자 `metrics`가 채운다. 커서는 `consumer_cursors`에 둔다.
- 투영이 실패하면 명령 전체가 롤백된다 (D09-5, F-05). 같은 투영기 예외가 반복되면 `read_only`로 바꾼다.
- `p_attention`(주의 항목)은 복귀 요약의 재료다. 예: `question.rights`(심각도 4), `question.info`(2, 막힘이면 3), `result.awaiting_review`(3), `objection.open`(3), `toolcall.outcome_uncertain`(3) (09 §3.11.4).
- `readEvents(EventQuery)`는 `afterSeq`, `limit`(최대 5,000), 여러 필터, `scanLimit`(기본 50,000), `redact`(기본 true)를 받고 `events`, `headSeq`, `nextAfterSeq`, `scannedUntilSeq`를 돌려준다. 필터를 쓰면 seq에 빈칸이 생기므로 클라이언트는 `nextAfterSeq`를 따라간다 (19).
- 모든 조회는 한 읽기 트랜잭션에서 실행하고 응답에 `headSeq`를 붙인다. 읽기 연결은 `query_only`로 열며 WAL이라 쓰기와 동시에 읽을 수 있다 (09 §3.6.3).
- 커널 상태는 시작 때 `kernel_snapshots`에서 읽고(규칙 버전과 해시가 맞을 때만) 그 뒤 이벤트를 `apply`로 접는다. 스냅숏은 1만 이벤트마다와 정상 종료 직전에 쓴다 (F-29).

### 3.8 재구성 (09 §3.11.2)

1. `BEGIN IMMEDIATE` (쓰기를 받기 전에만). 2. 각 `p_*`마다 새 테이블 `p_x__new`를 같은 DDL로 만든다. 3. `events`를 `seq` 순서로 5,000건씩 읽어 `apply(upcast(...))`. 4. 테이블을 교체하고 인덱스를 다시 만든다. 5. `p_checkpoint = {version, last_seq = head, rebuilt_at}`. 6. `COMMIT`.

- 결정성 검사: 새 DB에서 재구성한 결과와 운영 DB의 `p_*`를 정렬해 digest로 비교한다 (`projectionDigest`, `helm ops verify --projections`). 다르면 투영기 버그다.
- 부분 재구성은 두지 않는다. 재구성이 결정적으로 실패하면 17의 `read_only`(recovery_failed)로 시작한다 (09 §3.11.2).

### 3.9 마이그레이션 (09 §3.13)

- 스키마 버전은 `PRAGMA user_version`이다. 선형 정수이고 down은 없다. `schema_migrations`에 `checksum = sha256(판 번호 + SQL)`을 남긴다.
- 흐름: `user_version > LATEST`면 거부(다운그레이드 금지, F-08). 적용된 마이그레이션의 체크섬이 다르면 `read_only`(F-09). 새 버전이 있으면 pre-migrate 백업을 뜨고, 각 마이그레이션을 `BEGIN IMMEDIATE`로 적용하며 `user_version`도 같은 트랜잭션에서 올린다. 부팅 10단계에서 `store.migrated`를 남긴다.
- `events` 열 변경은 트리거 때문에 행을 다시 쓸 수 없으므로 `ADD COLUMN`으로 한다. 해시 대상이 `envelope` 열뿐이라 체인은 영향이 없다.
- 투영 스키마가 바뀌면 `PROJECTOR_VERSION`을 올리고 재구성한다. 투영 스키마와 이벤트 스키마는 따로 버전을 가진다 (09 §3.13.2).
- payload 버전: `typeVersion`과 순수 함수 업캐스터 `UPCASTERS[type][n]`으로 변환한다. 저장된 행을 고쳐 쓰지 않는다. 데이터 정정은 업캐스터가 아니라 새 이벤트(예: `record.revalidated`)로 한다 (09 §3.13.3).

### 3.10 무결성 검사 (09 §3.10)

```text
prevHash(1) = "0" × 64
hash(n)     = SHA-256( prevHash(n) + "\n" + canonicalJson(envelope(n)) )
checkpoint  = HMAC-SHA256(key, "helm-checkpoint:" + n + ":" + hash(n))   // 1,000건마다, 종료·백업 직전
```

- 체인은 우발 손상과 SQL 직접 편집을 찾는다. HMAC는 체인 전체를 다시 계산한 위조를 찾는다. 기록의 내용이 참이라는 것은 보장하지 않는다 (불변조건 1).
- 검사 모드: `tail`(부팅)과 `full`(주간, 백업 직후). 실패 코드는 `gap`, `chain_broken`, `hash_mismatch`, `not_canonical`, `column_mismatch`, `head_mismatch`, `checkpoint_hash`, `checkpoint_hmac`, `checkpoint_key_unavailable`이다 (09 §3.10.4).
- 실패하면 `read_only`로 들어가 이벤트를 남기지 않는다. 손상된 꼬리는 자동으로 자르지 않는다 (09 §3.10.5, F-06).

### 3.11 백업 (09 §3.14.1)

흐름: head 체크포인트 → `db.backup(dest)`(온라인 백업 API, 쓰기를 멈추지 않음) → 사본의 `integrity_check`와 full 검사 → `manifest.json` (storeId, upToSeq, headHash, hmacHead, dbSha256 등) → `.tmp`에서 최종 경로로 rename → `backup.created`. blob은 복사하지 않는다. restic은 `backups/`만 가져가고 `helm.sqlite*`는 넣지 않는다 (17 D17-10, U-07).

### 3.12 복원 (09 §3.14.2)

1. 백업 검증 (dbSha256, integrity_check, full 검사, hmacHead).
2. 현재 상태를 pre-restore 백업으로 남길 수 있으면 남긴다.
3. 백업 뒤의 위험 이벤트(device.revoked, grant.revoked, agreement.released, dial.set 하향, blob.redacted, 키 교체 등)를 `restore-carry.json`에 적는다.
4. 현재 DB를 `quarantine/<UTC>/`로 옮긴다. 지우지 않는다.
5. 백업 DB를 `helm.sqlite`로 복사하고 새 `storeId`를 만든다 (lineage에 이전 값을 덧붙인다).
6. 데몬 시작 → 부팅 10단계: `daemon.safe_mode_entered{restored}`, `store.restored`. 리스너를 열기 전에 위험 이벤트를 `internal:recovery`로 다시 적용하고, 미소진 send 승인은 모두 `approval.expired{restored}`로 닫는다.
7. 안전 모드에서는 run 자동 재개, 에이전트 타이머, 관찰 에이전트, 새 실행을 멈춘다. 사람이 `helm ops safe-mode off`로 끝낸다 (`daemon.safe_mode_exited`).

- `storeId`를 바꾸는 이유: 같은 seq가 다른 이벤트를 가리키게 되므로 클라이언트가 캐시를 버리게 하기 위해서다 (19, F-25). epoch가 ULID라 복원 전 쓰기와 겹치지 않는다 (D09-10).
- 내보내기(`helm export --jsonl`)는 읽기 연결로 하며 정규화 envelope, `prevHash`, `hash`를 적는다 (09 §3.14.3).

### 3.13 상태 기계 요약 (08 §3.22)

표에 없는 (상태, 이벤트) 조합은 `conflict.invalid_transition`이다 (08 §3.22 머리).

- **Concern**: open → active (`concern.activated`) ⇄ held (`structure.changed` hold) → completed (R-34) 또는 closed, merged. completed·closed는 `concern.reopened`로 active에 돌아갈 수 있다.
- **WorkUnit**: proposed → negotiating → delegated → in_progress → submitted → accepted → integrated. in_progress → scope_exceeded, submitted → rejected. 종료: integrated, concluded, rejected, cancelled, superseded.
- **Agreement**: proposed → active (확인, grant, 선택 범위, rule 활성화) → fulfilled (결과 accepted), released, declined, expired, superseded. active → active (renegotiated, 개정판 + 1).
- **Run**: queued → running (`run.started`, attempt) → stopping, 또는 awaiting_human·awaiting_recovery → ended. 부팅 복구는 interrupted로 바꾸고, 재개는 같은 runId의 새 attempt다 (J-38, J-39).
- **ToolCall**: requested → started (실행 전 커밋, R-05·R-43) → completed, interrupted, outcome_uncertain → recovered. requested → awaiting_approval → approved(다시 검사) 또는 denied. 종료: blocked, denied, not_executed, completed, recovered.
- **Question**: pending → delivered → answered (R-24). pending·delivered → pending (deferred). 정보 게이트에 한해 delegated, assumed(비막힘). 종료: answered, withdrawn, expired, delegated, assumed.

## 7. 구현 리뷰 체크포인트 후보

### 7.1 이벤트 로그

- 이벤트는 UPDATE와 DELETE를 트리거로 막는다 (09 §3.7).
- seq는 1부터 빈칸 없이 증가하고 `head + 1`로만 부여된다 (D09-2).
- 해시는 DB의 `envelope` 열 바이트를 덮는다. 정규화가 깨진 행도 검사가 찾는다 (09 §3.10.2).
- envelope는 256 KiB 이하다. 저장본의 `redactions`는 항상 빈 배열이다 (09 §3.2 규칙 6, 10).
- 상태를 바꾸는 이벤트는 `authority`가 한 개 이상이다. 커널과 스케줄러 이벤트는 `causationId`가 필수다 (09 §3.2 규칙 4·5).
- payload는 `EventPayloads`로 검사하고, 실패는 커널 버그로 본다 (09 §3.8.4 3d).

### 7.2 쓰기와 멱등

- 같은 키와 같은 지문이면 저장된 결과를 재생하고 이벤트를 늘리지 않는다. 같은 키와 다른 지문이면 `key_reused`이고 저장하지 않는다 (09 §6.2 `commit.ts` 1·2).
- 거부·충돌·게이트도 `commands`에 저장하고 `command.rejected`를 남긴다 (A09-2, 22/AX-14).
- 지문에서 연결, 리스너, attempt, commandId, expect, basisSeq를 뺀다 (09 §3.9.1, 22/FI-25).
- 투영기 예외가 나면 명령 전체가 롤백된다 (09 §3.8.4).
- 모든 쓰기는 `transaction(fn)` 안에서 일어난다. `commit`과 `commitBatch`는 편의 함수다 (09 §3.16.2).

### 7.3 펜싱과 epoch

- 모든 쓰기 트랜잭션은 `BEGIN IMMEDIATE` 직후 epoch를 대조한다. 나중 인스턴스가 부팅한 뒤 이전 인스턴스의 commit은 `Fenced`로 실패한다 (09 §6.2 `boot.ts`).
- 실행 명령은 `ownerEpoch`와 `attempt`가 현재 값이고 running 또는 stopping일 때만 받는다 (08 R-42·R-43).
- 복원 뒤의 epoch는 옛 epoch와 겹치지 않는다 (D09-10).

### 7.4 투영과 재구성

- 투영은 쓰기 트랜잭션 안에서 갱신되고 outbox가 없다 (A09-4, D09-5).
- 투영은 정본이 아니다. `projection.` 이름이 없고 투영 값은 레코드 id 형식이 아니다 (08 §3.24.1 불변조건 3).
- 재구성 뒤 `p_checkpoint.last_seq = head_seq`이고 재구성 중에는 쓰기를 받지 않는다 (09 §6.2 `rebuild.ts`).
- 모든 `EventType`에 처리 함수가 있다. 망라성 테스트가 있다 (09 §6.2 `projectors/core/*.ts`).

### 7.5 무결성, 백업, 복원

- HMAC 키가 없으면 시작하지 않는다 (09 §3.8.2, U-03).
- 행 삭제는 `gap`, 편집은 `hash_mismatch`, 키 없는 체인 재계산은 `checkpoint_hmac`이다 (09 §6.2 `integrity.ts`, 22/FI-17, FI-18).
- 쓰기 중에 백업한 사본이 full 검사를 통과한다 (09 §6.2 `backup.ts`).
- 복원하면 `storeId`가 바뀌고 `store.restored`가 남는다. 복원 뒤에는 자동 재개가 없다 (09 §3.14.2, 22/FI-20, FI-26, FI-29).
- 근거 체인에 든 관찰의 blob은 가지치기에서 빠진다 (09 §6.2 `retention.ts`).

## 8. 헷갈리기 쉬운 점

| 헷갈리는 쌍 | 구분 |
|---|---|
| `seq`, `headSeq`, `lastSeq`, `revisionSeq`, `basisSeq` | 전역 순서 / 저장소의 마지막 seq / 레코드의 마지막 변경 seq / 사람 판단에 영향을 준 마지막 seq / 화면이 본 seq |
| `revision` vs `revisionSeq` | `revision`은 바뀐 횟수(표시용), 비교는 `revisionSeq` (08 D08-12) |
| `bootEpoch`(이벤트), `ownerEpoch`(run), `storeId` | 부팅 ULID / 실행을 시작한 epoch / 저장소 계보 (복원하면 새로 만듦) |
| `bootEpoch` 패턴 vs 레코드 id 패턴 | epoch는 `^[0-9A-HJKMNP-TV-Z]{26}$`로 첫 글자 0~7 제약이 없다. 레코드 id는 있다 (09 §3.2, 08 §3.2.1) |
| `path.fenced` vs `path.stale_epoch` | 커밋 시 대조 실패(프로세스 종료) vs 옛 실행의 명령 거부 기록 (09 §3.8.1, §3.8.3) |
| `occurredAt` vs `recordedAt` | 효력 시각 vs 데몬 기록 시각. 늦게 온 관찰은 과거 `occurredAt`만 가진다 |
| `commandId` (cm) vs `idempotencyKey` (ik) vs `scope_key` | 명령 id / 클라이언트 키 (1~128자) / 행 키 (`channel|actor|viaKey|key`) |
| `toolcall.requested` vs `toolcall.started` | 차단과 승인 필요 여부를 기록하는 첫 단계 vs 실행 전에 커밋한 실행 의도. 합칠지는 U-13 |
| `interrupted` vs `outcome_uncertain` vs `not_executed` | 재실행하지 않는 종료 / 외부 효과가 있을 수 있는 불확실 / 실행되지 않았음이 확실한 종료 |
| 결과 상태와 확인 결정 | 결과 상태는 `conditionally_accepted`, 확인 결정은 `conditional`이다. §3.22.5 표는 두 이름을 섞어 쓴다 (08 §3.12) |
| `submitted` | WorkUnit 상태와 결과 상태에 같은 이름이 있다 (08 §3.22.3, §3.12) |
| 완료 | 완료 = WorkUnit `integrated`, Concern `completed`. `closed`는 완료가 아니다 (08 §2.3) |
| Thread vs Run | Thread는 대화 흐름과 `activeRunId`, Run은 실행 한 번과 `threadId`. 재개는 같은 runId의 새 attempt (08 §3.18) |
| 원전·Product 이름 | Claim(원전)은 없다 (in·ps·fd로 나뉨). Decision→Choice, DecisionGate→Question, CompletionClaim→ResultSubmission, Focus→Concern, WorkAgreement→Agreement, Evidence는 독립 엔티티가 아니다 (08 §3.25) |
| 품질과 상태 | 품질 단계와 옆길 플래그(contested, stale, superseded)는 상태 열과 따로 있다 (08 D08-3) |
| 투영, 운영 상태, trace | 투영은 이벤트로 다시 만든다. 운영 상태는 재구성 대상이 아니다. trace는 실행 기록이며 보존 기간이 짧다 (09 §3.1) |
| Concern 표시 상태 계산 위치 | 08 §3.22.2는 "09 §3.11.4의 `v_concern_display`"라고 쓰고 08 §2.5 주변도 뷰라고 부른다. 09 §3.7 DDL에는 뷰가 없고, 09는 `views/concern-display.ts`의 함수로 계산한다고 쓴다. 표현이 다르다 |
| 성능 수치 | 09 §3.15.2 목표는 p99 ≤ 25 ms이고 22/PF-01도 같다. 09 §6.2 벤치는 "p99 100 ms를 넘으면 실패(초기 기준)"라고 쓴다. 목표와 실패 기준이 다르다 |
