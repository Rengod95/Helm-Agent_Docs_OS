## 2. 핵심 개념 목록

### 2.1 envelope: JSON-RPC 2.0

- **정의**: 모든 메시지는 `"jsonrpc": "2.0"`을 갖는다. 요청 `{jsonrpc, id, method, params}`, 응답 `{jsonrpc, id, result}` 또는 `{jsonrpc, id, error}`, 알림 `{jsonrpc, method, params}`(id 없음). WebSocket 텍스트 메시지 하나가 JSON-RPC 메시지 하나다.
- **왜 있는지**: 결정 31(JSON-RPC 2.0 over WebSocket)의 기본값을 따르고 세부는 이 문서가 정했다. 조정자 기본값 표시는 `[제안: 결정 31 기본값]`이다.
- **규칙**: `id`는 문자열, 1~64자, `[A-Za-z0-9._:-]`. 숫자나 null id는 -32600. `params`와 `result`는 항상 객체다(원시값·배열 금지). 배치(배열 메시지)는 받지 않고 -32600 응답 하나(`id: null`)를 보낸다. 서버는 클라이언트에 요청을 보내지 않는다(서버 → 클라이언트는 응답과 알림뿐). 클라이언트 → 서버 알림은 `$/cancelRequest`와 `presence.report` 둘이다. 출처 §3.3.1, §3.8.2, P-04.
- **한도**: 중첩 깊이 64, 배열 길이 10,000을 넘으면 -32600. strict JSON(NaN·Infinity 없음). 시각은 ISO 8601 UTC 문자열. 출처 §3.3.1.
- **스키마 도구**: TypeBox 상수로 정의하고 타입은 `Static`으로 얻는다. envelope 검사는 `additionalProperties: false`. 출처 §3.3.1 코드, §3.4.2.
- **id와 멱등 키는 다르다**: JSON-RPC `id`는 연결 안에서 응답을 짝짓는 값일 뿐이고 멱등 키로 쓰지 않는다. 출처 §3.9.2 끝.

### 2.2 데몬 리스너 셋과 세 경로

- **리스너**: `tailnet`(127.0.0.1:7840 TCP, Tailscale serve가 넘기는 곳만), `loopback`(127.0.0.1:7841 TCP, SSH 경로용), `local`(Unix 소켓 `/run/user/<uid>/helm/rpc.sock`, 파일 0600). 세 리스너는 같은 HTTP + WebSocket 코드를 쓰고 받는 인증 방식만 다르다. 출처 §3.2.1, P-01.
- **경로 (a) WSS**: 클라이언트 → tailnet → Windows `tailscale serve`(TLS 종료) → 데몬 평문. 주소 `wss://<서버 MagicDNS 이름>:<serve 포트>/rpc`. TLS는 serve가 끝낸다. 출처 §3.2.2.
- **경로 (b) SSH**: 클라이언트가 `ssh -W 127.0.0.1:7841`로 표준 입출력을 loopback에 잇고, 그 위에 같은 HTTP + WebSocket을 쓴다. 별도 프레임 형식은 없다. 출처 §3.2.3, P-02, 결정 38.
- **경로 (c) 로컬**: WSL 안의 TUI·관리 CLI가 `local` 소켓(`ws+unix`)에 붙는다. 출처 §3.2.4.
- **전송 조건**: 리스너는 전송 조건(Tailscale 신원 헤더, Host·Origin 검사, 소켓 권한)을 통과한 연결만 연결 처리기에 넘긴다. 연결 처리기 아래는 리스너 종류를 모르고, 리스너 종류는 인증 방식 허용과 감사 기록에만 쓰인다. 출처 §3.1.
- **불변 성질**: 세 경로의 메시지와 재전송 의미는 같다(결정 38). 멱등 범위와 지문에는 연결 ID, 리스너, 시도 번호가 들어가지 않는다. 출처 §3.1 끝, §3.9.2.

### 2.3 연결 인증: 기기 토큰의 운반 방식

- **운반 방식 두 가지**: `header`는 `Authorization: Bearer <토큰>`을 싣고 데스크톱·TUI가 쓴다. 허용 리스너는 tailnet, loopback, local이다. `cookie`는 `__Host-helm_dt` HttpOnly 쿠키이고 모바일 PWA가 쓴다. 허용 리스너는 tailnet만이며 Origin이 `auth.allowedOrigins`와 정확히 같아야 한다. 출처 §3.2.2 표, P-03.
- **기기마다 고정**: 기기의 운반 방식은 하나로 정해진다(08 Device `credentialCarrier`). 다르면 `hello`에서 1008 `carrier_mismatch`다. 출처 §3.2.2, F-47.
- **토큰은 JSON에 싣지 않는다**: `hello` params의 `HelloAuth`는 토큰 값을 갖지 않는다. 토큰은 업그레이드 요청의 헤더나 쿠키로만 온다. 웹뷰 메모리를 거치지 않게 하려는 선택이다. 출처 §3.4.3, 19-A2.
- **형식 검사는 업그레이드 단계**: `helm_dt_` + base64url 43자가 틀리면 업그레이드에서 401로 끝난다. 해시 조회, 폐기, 만료 판정은 `hello`에서 한다. 출처 §3.2.2.
- **`helm-bearer.<토큰>` 하위 프로토콜은 받지 않는다**: 정식 데몬은 무시하고 헤더·쿠키 없으면 401이다. 시험용 가짜 데몬에만 남겼다. 출처 §3.2.2, Q-16.
- **`localAdmin`**: `local` 리스너에서만 받는다. 근거는 소켓 파일 권한이다. `interactive`는 `tui`, `tty_cli`, null 중 하나다. `tty_cli`는 사람 결정 명령마다 `localConfirm`이 필요하다. 출처 §3.4.3, §3.2.4, §3.4.6.
- **`runtimeAdapter`**: `local` 리스너에서만, run 단위 단기 토큰을 헤더로 받는다. 외부 런타임 MCP 설정에는 기기 토큰을 넣지 않는다. 출처 §3.4.3, §3.4.6.
- **증명**: 기기 키 서명(`DeviceProof`, Ed25519 또는 ES256)은 필드만 있고 1차에는 `proofRequired: false`로 끈다. 출처 §3.4.3, Q-02.

### 2.4 핸드셰이크

- **순서**: 업그레이드 101 → 서버가 첫 메시지로 `hello.challenge` 알림을 보낸다 → 클라이언트가 `hello` 요청을 보낸다 → 서버가 `hello` 응답을 보낸다. 클라이언트는 챌린지를 받기 전에 `hello`를 보내지 않는다. 출처 §3.4.1.
- **`hello.challenge`**: `nonce`(32바이트 base64url, 이 연결에서만 유효), `serverTime`, `serverId`(프로필 값과 비교), `protocols`, `authMethods`, `proofRequired`. 출처 §3.4.2.
- **`hello` params**: `protocol {min, max}`, `client`(`kind`: desktop·mobile·tui·cli·test, `version`, `platform`: macos·windows·linux·ios, `instanceId`), `auth`(세 방식 중 하나), 선택값 `resume`, `capabilities`, `locale`(기본 ko-KR), `timeZone`. 출처 §3.4.3.
- **서버 판정 순서**: (1) 상태가 `awaitingHello`인지(아니면 1002) → (2) 스키마(-32602) → (3) 버전 고르기(`chosen = min(client.max, server.max)`, 공통 범위가 없으면 1003) → (4) 인증 방식이 이 리스너에서 허용되는지(1008) → (5) 방식별 판정 → (6) scope 부여 후 `ready`. 출처 §3.4.3.
- **`hello` 응답(`HelloResult`)**: `protocol`, `server {id, version, bootEpoch, startedAt, mode, modeReasons}`, `connection {id, listener, authMethod, carrier, deviceId, interactive, scopes, tailscaleLogin?}`, `policy`, `features {methods, notifications, views, capabilities, schemaHash}`, `log {storeId, headSeq, oldestReplayableSeq, resume}`, `human {briefAckSeq}`, `serverTime`. 출처 §3.4.4.
- **정책 값은 응답으로만 안다**: `ConnectionPolicy`(메시지 상한, tick 주기, 동시 요청, 명령 속도, 구독 수, 재생 상한, 송신 큐 상한, 멱등 보관 기간, 대기 명령의 최대 나이, 파일 한도)는 클라이언트에 하드코딩하지 않고 재접속할 때마다 다시 읽는다. 기본값은 `DEFAULT_POLICY`에 있다. 출처 §3.4.4.
- **인증 전 제한**: `hello` 전 메시지는 16 KiB까지다. `hello` 외 요청이 오면 1001 후 1008로 닫는다. 응답 대기 요청은 1개다. 업그레이드 뒤 10초 안에 `hello` 응답이 없으면 4001이다. 출처별 인증 전 연결은 8개다. 인증 실패는 지연을 준다(1분 5회 → 60초, 10분 20회 → 10분, 넘으면 1011 `rateLimited`). 출처 §3.4.5.
- **서버 연결 상태**: `awaitingHello` → `ready` → `draining`(데몬 종료 시작) → `closing` → `closed`. 소켓이 닫히면 그 연결의 구독, 응답 대기 요청, 다운로드 티켓은 모두 사라진다. 남는 것은 영속 이벤트, 멱등 결과, 기기 상태뿐이다. 출처 §3.4.7.
- **같은 기기의 연결 수**: 동시 연결이 8개를 넘으면 가장 오래된 연결에 `connection.closing{kind: "replaced"}`를 보내고 4009로 닫는다. 전체 연결이 64개면 새 업그레이드를 503으로 거절한다. 출처 §3.4.3, §18 §3.14(19 인용).

### 2.5 메서드 분류: METHOD_SPECS

- **원천 한 곳**: `METHOD_SPECS`(`packages/protocol/src/registry.ts`)가 등록 표의 원천이다. TS 타입, JSON Schema, 참조 문서, 서버 디스패처 표, 적합성 테스트가 모두 여기서 나온다. 출처 §2.3 P-15, §3.13.2. 근거는 OpenClaw `CORE_GATEWAY_METHOD_SPECS`다(S4 openclaw-gateway §1.4).
- **항목 필드**: `name`, `kind`(`ctl`·`read`·`cmd`·`adm`), `scopes`(null이면 인증 전), `since`(도입 버전), `params`, `result`, `errors`(낼 수 있는 Helm 오류 코드 목록), `kernelCommand`(cmd만, 10의 명령 이름), `mobileLimit`(휴대폰 값 제한), `basisChecked`, `compat`, `summary`. 출처 §3.13.2.
- **종류 `kind`**: `ctl` 연결 제어(`hello`), `read` 조회·구독, `cmd` 사람 명령(멱등 키와 `basisSeq` 필수), `adm` 관리. 출처 §3.7.1 머리말.
- **조회·구독(read/ctl)**: `hello`, `ping`, `events.subscribe`·`events.unsubscribe`, `events.read`, `view.get`, `record.locate`, `search.query`, `command.lookup`, `stream.subscribe`·`stream.unsubscribe`, `run.partial`, `composer.preview`, `localConfirm.request`, `blob.downloadTicket`, `daemon.status`, `device.pushConfig`, `protocol.describe`. 알림으로 가는 `presence.report`가 있다. 출처 §3.7.1 첫 표.
- **사람 명령(cmd, scope `decide`)**: 질문(`question.*`), 이의·확인(`objection.*`, `decision.confirm`, `autonomous.markSeen`), 선택(`choice.*`, `finding.*`, `criterion.*`), 탐구(`inquiry.*`, `reaction.*`, `stimulusRound.close`, `possibility.*`), 합의(`agreement.*`), 권한(`grant.*`), 결과 확인(`result.accept`), 할 일(`obligation.*`), Goal·Concern·루프·모드·다이얼·설정(`goal.*`, `concern.*`, `loop.requestTransition`, `loopPlan.revise`, `mode.set`, `dial.set`·`dial.unset`, `settings.update`), 실행(`work.*`, `thread.compact`, `composer.submit`), 브리프·복구(`brief.*`, `recovery.resolve`), 측정(`surprise.report`, `resumptionCheck.*`, `selfReport.submit`), 관찰 제안(`observerProposal.*`). 출처 §3.7.1 둘째 표.
- **기기·관리**: `device.*`(list·rename·revoke·expireTokens·rebind·createPairingCode·registerPush 등), `connection.list`·`connection.close`, `daemon.exitSafeMode`, `admin.*`(status·issueDevice·drain·setMode·backupNow·verify·maintain·reloadConfig·reloadSecrets). 출처 §3.7.1 셋째 표, §3.7.7, §3.7.8.
- **scope가 메서드를 막는다**: `read`, `decide`, `decideMobile`, `devices`, `devicesLimited`, `admin`, `modelTool` 일곱 개다. 같은 메서드도 값에 따라 막힌다(예: 휴대폰은 `question.answer`의 `approve_edited`와 `result.accept`의 `reject`를 못 쓴다). 위반은 1010 `scope.forbidden`이다. 출처 §3.4.6.
- **목록에 없는 것**: 페어링 코드를 쓰는 JSON-RPC 메서드(코드 사용은 HTTP `POST /pair`·`/m/pair`이고, 코드 만들기는 `device.createPairingCode` 명령이다), 토큰 교체 결과를 JSON으로 돌려주는 메서드(HTTP `POST /devices/self/rotate`), 파일 업로드·다운로드 자체, 클라이언트가 도구 결과를 채우는 메서드(결정 14), 관찰 에이전트의 모델 호출(16 IPC), `admin.safeMode`(판정 J-165). 출처 §3.7.1 아래 항목들.
- **명령은 domain action별**: generic `execute`가 없다. 명령 메서드는 04의 명령 의도 이름을 따른다. 메서드 이름의 정본은 19, 명령 이름의 정본은 10 §3.11.11(2)이다. 두 표가 다르면 10 표를 고치게 한다. 출처 §2.3 P-09, §3.7.1 머리말, 19-A6.
- **이름 규칙**: `<영역>.<동사>`, 소문자 낙타 표기. `$/` 접두는 프로토콜 제어용으로 예약. 출처 §3.3.1.

### 2.6 구독과 이벤트 스트림

- **두 종류**: 영속 이벤트는 09 정본 로그에 커밋된 이벤트다. seq가 있고 재전송 대상이며 버리지 않는다. 휘발 스트림은 텍스트 조각 같은 실시간 델타다. seq가 없고 `stream.chunk`로 보내며 버려도 된다. 출처 §3.5.2, P-08.
- **seq**: 09의 전역 seq를 그대로 쓴다. 정수, 1부터, 커밋 순서대로 빈칸 없이 증가하고, 한 번 부여된 이벤트는 바뀌지 않으며, 재시작 뒤에도 이어진다. 프로토콜은 seq를 새로 매기지 않고 연결별 카운터나 메모리 버퍼를 두지 않는다. 출처 §3.5.1, 19-A3, 09 D09-2.
- **`storeId`**: 저장소의 정체(ULID). 저장소를 새로 만들거나 백업에서 복원하면 바뀌고, 복원 뒤 `store.restored`가 남는다. 출처 §3.5.1, 09 §3.14.2.
- **`bootEpoch`**: 데몬 프로세스가 시작할 때마다 바뀐다. 재전송 판정에는 쓰지 않고 "데몬이 재시작됨" 표시와 진단에만 쓴다. 출처 §3.5.1.
- **위치(position)**: 클라이언트는 위치를 항상 `{storeId, seq}` 쌍으로 저장한다. "여기까지 빠짐없이 받았다"는 뜻이다. 출처 §1.4, §3.5.1.
- **구독 호출**: `events.subscribe {from: {storeId, seq} | "head", filter?}`의 응답은 `{sub, start, headSeq, storeId, mode: replaying | live}`다. 이후 `events` 알림이 `{sub, from, to, events, caughtUp}`로 온다. 출처 §3.5.3.
- **구간 계약**: 알림 하나는 `(from, to]` 구간에서 필터에 맞는 영속 이벤트를 빠짐없이, 중복 없이, seq 오름차순으로 담는다. 빈 구간도 `events: []`로 위치를 넘길 수 있다. 실시간 구독은 tick마다 위치가 headSeq보다 뒤면 빈 알림을 보낸다. 출처 §3.5.3. Chord `ReplicatedStateSource`의 커서 계약을 구간형으로 바꾼 것이다(P-06).
- **필터(`EventFilter`)**: `goalIds`, `concernIds`(+`includeDescendants`, 기본 true), `typePrefixes`, `excludeTypePrefixes`, `payload`(`full` 또는 `none`). 조건 사이는 AND, 배열 안은 OR다. 출처 §3.6.2.
- **이벤트 와이어(`EventWire`)**: 09 공개 사본(`redact: true`)에서 만든다. 바뀌는 것은 ms 시각의 ISO 변환, 해시 필드 제외, `invalidates` 추가 셋이다. 가린 필드 이름은 `redactions`에 남고, 빠진 payload는 `payloadOmitted`(`tooLarge` 또는 `filtered`)로 표시한다. 출처 §3.5.2.
- **재생 알고리즘(서버)**: (1) 필터 검사 → (2) 구독 수 검사 → (3) head를 읽고 위치 검사 후 구독 등록 → (4) 응답 큐잉 → (5) 재생 묶음을 송신 큐가 1 MiB 아래일 때만 읽어 보내고, 재생 중 쌓인 커밋은 보류분으로 필터해 뒤에 보낸다 → live. 출처 §3.5.4.
- **구독 먼저, 스냅샷 나중**: 클라이언트는 변경 통로를 먼저 열고 상태(뷰, 이력)를 나중에 읽는다. 상태 응답의 `asOfSeq`가 이미 반영한 seq를 알려 준다. 출처 §3.5.6.
- **gap 감지(클라이언트)**: 알림의 `from`이 자기 위치와 다르면 구독을 다시 맞춘다. 1분에 3번이면 1000으로 닫고 재접속한다. 서버가 영속 이벤트를 버리지 않으므로 정상 동작에서는 gap이 생기지 않는다. 출처 §3.5.7.
- **범위 밖**: 재생할 수 없으면 2001 `replay.outOfRange`와 `reason`(`storeMismatch`, `aheadOfHead`, `beforeOldest`, `tooFar`)을 준다. 출처 §3.3.4, §3.5.4.
- **스냅샷 경로**: 저장소가 다르거나 위치가 앞서면 모든 캐시를 버린다. `beforeOldest`나 `tooFar`면 투영 캐시는 "낡음"으로 남긴다. 그 뒤 `from: "head"`로 구독하고, 열린 뷰를 `minSeq: H0`로 다시 받는다. 타임라인은 `events.read`로 최근 이력을 거꾸로 채운다. 출처 §3.5.5.
- **느린 소비자**: 송신 큐가 8 MiB(`sendQueueHighWaterBytes`)를 넘으면 `stream.chunk`부터 버린다. 10초 넘게 상한 위에 있거나 16 MiB를 넘으면 `connection.closing{kind: "slowConsumer"}` 후 4008로 닫는다. 영속 이벤트와 응답은 버리지 않는다. 출처 §3.5.8, P-11.
- **송신 우선순위**: 응답과 오류 > tick, `server.shutdown`, `connection.closing` > `events` > `stream.chunk`. 출처 §3.5.8.
- **응답과 이벤트의 순서**: 커밋 → 같은 턴에 모든 연결의 실시간 구독에 결과 이벤트 알림을 큐잉 → 명령 응답을 큐잉. 그래서 요청 연결의 실시간 구독에서는 응답의 `lastSeq`까지의 이벤트가 응답보다 먼저 온다. 재생 중인 구독은 이 보장이 없다. 출처 §3.5.9.
- **휘발 스트림**: `stream.subscribe {scope, parts?}` → `{sub, active: RunPartial[]}`. 조각 알림 `stream.chunk {sub, runId, concernId, n, afterSeq, part}`. `n`은 실행별 조각 번호이고 버린 조각도 번호를 쓴다. `part`는 `text`, `thinking`(기본으로 보내지 않음), `toolArgs`, `toolOutput`, `toolPhase`, `status`, `end`다. 출처 §3.6.4.
- **텍스트 조각 규칙**: `offset`이 현재 길이와 같으면 덧붙이고, 이미 가진 범위면 버리고, 겹치면 새 꼬리만 덧붙이고, 앞이 비면 gap으로 보고 `run.partial`로 맞춘다. 출처 §3.6.4.
- **휘발 상태의 소멸**: 영속 이벤트(메시지 완성, 도구 결과, run 종료)를 받으면 같은 `messageId`·`toolCallId`의 휘발 상태를 버린다. `end` 조각은 영속 커밋 뒤에 보내고 `finalSeq`를 싣는다. 클라이언트는 `finalSeq`를 받을 때까지 휘발 상태를 지우지 않는다. 출처 §3.6.4.
- **구독 해제**: `events.unsubscribe`, `stream.unsubscribe`는 `{}`를 준다. 해제 응답 뒤에는 알림이 오지 않는다. 해제 전에 큐에 들어간 알림은 올 수 있으므로 클라이언트는 모르는 `sub`의 알림을 버린다. 출처 §3.6.5.
- **구독 종류**: 전체 스트림(데스크톱 기본 구독 하나, 모든 뷰의 무효화를 받는다), Concern 단위(관리 CLI `helm tail`), 뷰 단위(`view.get` + 태그), 휘발 스트림. 출처 §3.6.1.

### 2.7 뷰 투영과 무효화 태그

- **정의**: 데몬이 정본을 읽어 만든 화면 데이터다. 클라이언트는 `view.get`으로 받아 캐시하고, 이벤트의 무효화 태그로 낡은 것을 다시 받는다. 출처 §1.4, P-07.
- **요청과 응답**: `view.get {view, params, minSeq?, waitMs?, page?}` → `ViewResult {view, key, asOfSeq, generatedAt, freshness, staleReason?, omitted?, dependsOn, page?, data}`. `freshness`는 `current`, `stale`, `rebuilding`, `failed`다. `failed`는 정상 응답의 한 값이다. 출처 §3.6.3.
- **뷰 카탈로그**: 26개다. `home`, `brief`, `inbox`, `question`, `autonomous`, `concernTree`, `concern`, `inquiry`, `stimulusRound`, `work`, `agreement`, `review`, `loopTimeline`, `thread`, `evidenceChain`, `goals`, `goal`, `dials`, `observerProposals`, `devices`, `recovery`, `records`, `tray`, `settings`, `metrics`, `evaluation`. 각 뷰의 params 스키마, 화면 ID, 키 형식, 기본 태그가 표로 있다. 출처 §3.7.4.
- **뷰 키**: 응답의 `key`가 정본이다. 클라이언트가 직접 만들지 않는다(파라미터 정규화를 서버 한 곳에 둔다). 출처 §3.7.4.
- **무효화 태그**: 이벤트의 `invalidates`는 커밋 때 투영기가 계산해 09 `event_invalidations`에 저장한 값이다. 재전송된 옛 이벤트도 같은 값을 받는다. 뷰의 `dependsOn`은 뷰를 만들 때 읽은 레코드 ID와 집계 이름(`@` 접두, 예 `@inbox`)이다. 두 집합이 겹치면 그 뷰는 낡은 것이다. 출처 §3.6.3, 12 §3.5.8 규칙 2.
- **태그 상한**: 이벤트당 64개, 뷰당 512개다. 넘으면 집계 이름 하나(예 `@concernTree`)로 대신하며 넓게 무효화하는 쪽으로 간다. 출처 §3.6.3.
- **정확성 규칙**: 이벤트를 반영해 다시 만든 뷰의 `data`가 달라지면 그 이벤트의 `invalidates`와 뷰의 `dependsOn`은 반드시 겹친다. 반대 방향은 허용된다. 속성 테스트 VIEW-01로 확인한다. 출처 §3.6.3, §6.2.
- **클라이언트 처리**: 낡은 뷰 중 열린 것만 `view.get({…, minSeq: e.seq})`로 다시 받는다. 키마다 150ms 디바운스, 동시에 하나다. 재생 중(`caughtUp` 전)에는 미루고 `caughtUp` 뒤 한 번만 받는다. 닫힌 뷰는 낡음 표시만 하고 화면에 다시 열릴 때 받는다. 출처 §3.6.3.
- **대기**: `minSeq`를 받은 서버는 투영이 따라올 때까지 `waitMs`(기본 2,000, 최대 10,000)만큼 기다린다. 넘으면 2006 `view.notReady`(재시도 가능)다. 출처 §3.5.6, §3.3.4.
- **기각한 대안**: 스냅샷 + JSON Patch 방식은 서버가 연결·뷰마다 이전 값을 들고 있어야 하고 패치 순서 오류에 대비한 재동기화가 또 필요해서 기각했다. 19-A4, Q-03.
- **데이터 타입의 소유**: 뷰 모델 `data`의 타입은 04가 정하고, 정본에서 만드는 규칙은 12가 정한다. 이름, params, 키, 태그는 19가 정한다. 출처 §3.7.4 머리말.

### 2.8 명령 제출

- **params 형태**: 모든 사람 명령은 `Cmd({...})`다. `CommandBase`(`idempotencyKey`, `basisSeq`, 선택 `expect`, 선택 `clientTime`, 선택 `localConfirm`)와 메서드별 필드를 합친 닫힌 객체다. 출처 §3.7.2, §3.7.5.
- **`basisSeq`**: 사람이 결정을 내릴 때 본 화면 뷰의 `asOfSeq`다. 화면 밖 동작은 그 시점의 구독 위치를 쓴다. 커널은 대상 레코드의 `revisionSeq`가 `basisSeq`보다 크면 충돌로 본다. 출처 §3.9.3, P-09.
- **`expect`**: 화면이 특정 레코드의 판(`revisionSeq`)을 직접 알 때만 싣는다. 출처 §3.9.3.
- **클라이언트가 보내지 않는 것**: 행위자, 채널, provenance. 서버가 채운다. 사람 명령은 `channel: "human_client"`, `actor: "human"`, `provenance.adapterId: "client:<client.kind>"`, `provenance.externalRunId: <connection.id>`다. 새 레코드 ID(예 `objectionId`, `acceptanceId`)도 데몬이 만든다. 출처 §3.7.5 공통 규칙, 10 §3.3.2.
- **입력 마스킹**: 사람이 쓴 자유 텍스트(`note`, `reason`, `text`, `edits`의 문자열)는 10 payload로 바꾸기 전에 18의 입력 단계 마스킹을 거친다. 비밀 형태는 가린 값으로 바꾸고 원문을 남기지 않는다(판정 J-147). 출처 §3.7.5.
- **서버 처리 단계**: (1) 스키마(-32602), scope·값(1010), `tty_cli`면 `localConfirm`(1012), 명령 속도(1011), 데몬 모드(readOnly면 5003, draining이면 5001) → (2) 변환 `toCommand_<메서드 점을 밑줄로>`가 `{type, payload}`를 만든다 → (3) `EngineInput` 생성(채널, 행위자, via, provenance, basisSeq, expect, idempotencyKey) → (4) `engine.submit`: 커널 decide를 store 트랜잭션 안에서 실행 → (5) 결과를 `CommandResult` 또는 오류로 바꾼다 → (6) 커밋이 있었으면 이벤트 알림을 먼저, 응답을 나중에 보낸다. 출처 §3.9.2, §3.15.
- **`via`**: 기기 명령은 `{kind: "device", deviceId, listener, connectionId}`, 로컬 CLI는 `{kind: "local_cli", uid, interactive}`다. 출처 §3.9.2.
- **`CommandResult`**: `status`(`applied`, `accepted`, `gated`), `commandId`, `duplicate`, `reduced?`, `headSeq`, `firstSeq`, `lastSeq`, `events[]`, `created?`, `notices?`, `jobId?`, `runId?`, `questionId?`, `impact?`. `gated`는 커널이 자격 부족을 질문으로 바꾼 것이고 명령은 적용되지 않았다. 출처 §3.7.2.
- **명령 조회**: `command.lookup {idempotencyKey}`는 `found: false`, `found: true, result`, `found: true, error` 중 하나를 준다. 범위는 이 연결의 멱등 범위(채널, 행위자, viaKey)다. 출처 §3.7.3.
- **변환 메타데이터**: 메서드마다 10 `type`과 필드 대응을 적는다. 예: `result.accept` → `result.accept`(`acceptanceId` 서버 발급, `core` 조립), `question.answer` → 그대로, `dial.set` → `{layer, scopeId}`로 변환. 출처 §3.7.9. `check-registry.ts`가 등록 표와 변환 함수 목록을 대조한다(§3.13.2).

### 2.9 멱등 키와 지문

- **키 형식**: `ik_` + ULID 26자, 정규식 `^ik_[0-7][0-9A-HJKMNP-TV-Z]{25}$`. 사용자 의도 하나에 하나를 만든다(버튼 한 번, 보내기 한 번). 같은 의도를 다시 보낼 때(응답 유실, 재접속, 시간 초과, 경로 바꿈)는 같은 키와 같은 params를 보낸다. 다른 의도에 키를 다시 쓰지 않는다. 출처 §3.9.1, §3.4.2, 20 APP-D09.
- **범위 키(09)**: `channel | actor | viaKey(via) | idempotencyKey`. `viaKey`는 기기 명령이면 `device:<deviceId>`, 로컬 CLI면 `local_cli:<uid>`다. 연결 ID, 리스너, 실행 시도 번호는 들어가지 않는다. 출처 09 §3.9.1(`scopeKey`, `viaKey`).
- **지문(09)**: `sha256(canonicalJson({type, actor, viaKey(via), payload에서 제출자 생성 ID 필드를 뺀 것}))`. `commandId`, `expect`, `basisSeq`, `localConfirm`은 지문에 없다. 그래서 화면이 다시 그려져 `basisSeq`가 달라져도 같은 명령이다. 출처 19 §3.9.2, 09 §3.9.1(`fingerprint`, `generatedIdFields`).
- **같은 키 처리 결과**: 같은 키와 같은 지문이면 저장된 결과를 `duplicate: true`로 돌려준다. 같은 키와 다른 지문이면 3006 `idempotency.keyReused`이고 이 시도는 저장하지 않는다. 출처 §3.9.2, §3.3.4.
- **결과 저장 규칙(09)**: `accepted`, `needs_gate`, 커널 거부(내용·자격·경로), `conflict`는 저장하고 같은 키로 재시도하면 같은 결과가 온다. `key_reused`, 커널 내부 오류, 일시 실패(쓰기 소유권 상실, SQLite 바쁨, 디스크 가득 참)는 저장하지 않는다. 출처 09 §3.9.2 표, 19 §3.9.2 끝.
- **처리 중인 같은 키**: 뒤에 온 요청은 앞의 결과를 기다려 `duplicate: true`로 받는다. 10초를 넘으면 3007 `command.inProgress`(`retryAfterMs` 1000)다. 출처 §3.9.2.
- **보관**: 09 `commands` 행은 지우지 않는다. 365일(`idempotencyWindowMs` 기본값)이 지나면 `result`를 줄이고 `scope_key`, `fingerprint`, `status`만 남긴다. 줄인 행에 같은 키와 같은 지문이 오면 `{status, commandId, duplicate: true, reduced: true}`를 준다. 출처 §3.9.2, 09 §3.15.3, §3.4.4.
- **화면을 끄기 직전의 명령**: 휴대폰은 `visibilitychange → hidden`에서 진행 중 명령을 `POST /m/cmd`(keepalive)로 같은 키로 보낸다. 인증은 쿠키 판정이고 `hello`가 없다. `connectionId`는 요청마다 새 `cx_`다. 출처 §3.9.4, 26 §3.3.5.
- **JSON-RPC id는 멱등 키가 아니다**: happy-agent의 반향용 `mutationId`와 섞은 혼동을 피한 결정이다. 출처 §3.9.2 끝.

### 2.10 낡음 검사와 결과 대응

- **검사 위치**: 커널이 decide 안에서 한다(판정 J-79, 09 §3.9.4). 기준은 대상 레코드의 `revisionSeq`다. `revisionSeq`는 사람이 판단할 때 의미 있는 변경에서만 오르고, 근거 링크 추가 같은 운영 변경에서는 오르지 않는다. 출처 §3.9.3, 09 D09-4.
- **대상이 여럿일 때**: `subjects()`(10 §3.11.12)가 돌려준 대상마다 비교하고, 우선순위는 10이 정한다. 출처 §3.9.3.
- **충돌 결과**: 3004 `command.revisionConflict`(현재 요약 `rebase` 포함), 3008 `command.alreadyResolved`(`outcome`: answered, assumed, withdrawn, expired, accepted), 3009 `command.superseded`(새 판을 가리킴). 출처 §3.3.4, §3.3.5.
- **가정 확정 뒤의 답**: 3008에 `outcome: "assumed"`, `assumedValue`, 다음 행동 `objection.file`을 싣는다. 화면은 쓰던 답을 이의 초안으로 넘긴다. 판정 J-120. 출처 §3.3.5, F-48.

### 2.11 오류 코드 체계

- **JSON-RPC 표준 다섯 개**: -32700 `jsonrpc.parseError`, -32600 `jsonrpc.invalidRequest`, -32601 `jsonrpc.methodNotFound`, -32602 `jsonrpc.invalidParams`, -32603 `internal`. 내부 오류는 `message`를 `"Internal error"`로 바꾸고 원인은 데몬 로그에만 남긴다(`traceId`로 연결). 출처 §3.3.4, §3.3.3.
- **Helm 코드 범위**: 1000~5999의 양의 정수를 영역별로 나눈다. 1xxx는 핸드셰이크·인증·scope·속도·확인, 2xxx는 구독·재생·뷰·실행, 3xxx는 명령 결과, 4xxx는 파일, 5xxx는 데몬 상태·취소·시한·런타임이다. 출처 §3.3.4.
- **오류 객체**: `code`, `message`(개발자용 영어 한 줄, 화면에 그대로 쓰지 않음), `data {kind, retryable, retryAfterMs?, details?, traceId?}`. `kind`는 점 이름이다(예 `command.rejected.content`). 출처 §3.3.1 `HelmErrorData`, §3.3.3.
- **`details` 공통 필드**: `reason`(10 거부 코드 등 하위 이유), `ruleId`(10 규칙 또는 08 R-xx), `nextActions`(최대 8개, `{action, label?, params?}`). 화면 문구는 `kind`, `reason`, `ruleId`, `nextActions`로 05·21이 만든다. 출처 §3.3.3.
- **10 거부 코드 → 프로토콜 결과**: 내용 거부 → 3001(명령 대상 레코드 없음이면 3005), 자격 거부(`denied.*`) → 3002, 경로 거부 → 3003(`path.fenced`는 5001, `path.store_read_only`는 5003), 버전 불일치 → 3004, 이미 해결됨 → 3008, 대체됨 → 3009, 같은 키 다른 지문 → 3006, 커널·저장소 버그 → -32603, 일시 실패 → 5002, 질문으로 바뀜(`gate.*`, `policy.structure_cap_exceeded`) → 성공 응답 `status: "gated"`. 출처 §3.3.5.
- **거부 기록**: 거부된 명령은 10 §3.4.5에 따라 `command.rejected` 이벤트로 남고, `details.rejectionEventSeq`에 그 seq를 싣는다. 10의 `Rejection.message`(모델용 문장)는 `details.kernelMessage`에 넣고 JSON-RPC `message`에는 넣지 않는다. 출처 §3.3.5.
- **취소**: `$/cancelRequest`는 커밋 전이면 5004 `request.cancelled`(명령은 적용되지 않음)이고, 커밋 뒤면 취소하지 않고 정상 결과를 보낸다. 출처 §3.8.2, F-32.
- **WebSocket 닫는 코드**: 1000, 1001, 1002, 1003, 1006, 1008, 1009, 1011, 1012는 WebSocket 표준 뜻이다. Helm이 쓰는 것은 4000(클라이언트의 tick 감시 시간 초과), 4001(핸드셰이크 시한), 4008(느린 소비자), 4009(연결 강제 종료: 기기 폐기·만료, 기기당 연결 초과)다. 출처 §3.2.6.

### 2.12 큰 데이터: 파일 바이트와 티켓

- **원칙**: WebSocket 메시지에 파일 바이트(base64 포함)를 싣지 않는다. 이벤트와 뷰에는 `BlobRef`만 싣는다. 출처 §3.11.1, P-13, 19-A7.
- **`BlobRef`**: `blobId`(`bl_`), `hash`(`sha256:<소문자 hex 64자>`), `bytes`, `mediaType`, `preview?`를 갖는다. 뷰 데이터에서는 `name`, `image`, `variants`(thumb·display, 긴 변 512px·1,600px)를 더한다. 출처 §3.11.1 코드.
- **내용 주소**: 파일은 SHA-256 내용 주소로 저장한다. 같은 내용은 같은 `blobId`다. 한 번 정해진 `blobId`의 내용은 바뀌지 않으므로 클라이언트는 `blobId`를 키로 영구 캐시해도 된다. 출처 §3.11.1.
- **한도(기본값)**: 파일 하나 64 MiB(`policy.files.maxBlobBytes`), 한 번에 올리기 8 MiB 이하, 청크 4 MiB, 기기당 대기 업로드 합계 512 MiB, 기기당 동시 업로드 세션 4, 업로드 세션은 마지막 청크 뒤 1시간, 참조되지 않은 업로드는 24시간 뒤 정리, 이벤트 하나 256 KiB, `composer.submit` 본문 32 KiB. 출처 §3.11.1 표, §3.4.4.
- **업로드 한 번에**: `POST /files/u`에 `Authorization: Bearer`(또는 쿠키와 Origin 정확 일치), `Content-Type`, `Content-Length`, `X-Helm-Sha256`(필수), 원시 바이트를 보낸다. `201 {blob, stagedUntil}`. 해시 불일치는 422와 4005, 크기 초과는 413과 4001, 대기 합계나 세션 수 초과는 429와 1011이다. 출처 §3.11.3.
- **업로드 청크**: (1) `POST /files/u`에 `Upload-Length`와 `X-Helm-Sha256`을 보내 `201 {uploadId, chunkBytes, expiresAt}`을 받는다. (2) `PATCH /files/u/<uploadId>`에 `Upload-Offset`과 `application/offset+octet-stream` 본문을 보낸다. 성공은 204와 새 `Upload-Offset`이고, 위치가 틀리면 409다. 마지막 청크의 해시가 맞으면 `201 {blob}`이다. (3) 끊기면 `HEAD`로 위치를 받아 이어 올린다. 이 방식은 tus 1.0 헤더 이름을 빌린 단순형이다. 출처 §3.11.3.
- **업로드 후 상태**: 파일은 "대기(staged)" 상태다. 명령이 `BlobRef`를 참조하면 커널이 참조를 기록하고 보관 상태가 된다. 24시간 안에 참조되지 않으면 17의 정리 작업이 지운다. 출처 §3.11.3, F-24.
- **다운로드**: `GET /files/b/<blobId>`는 Bearer 헤더, 쿠키(휴대폰), 또는 티켓 경로로 받는다. 응답은 200 또는 206이며 `Accept-Ranges`, `Content-Range`, `ETag: "sha256:<hex>"`(원래 바이트의 해시), `Repr-Digest`를 준다. 범위 오류 416, 없음 404, 내용 없음(가지치기·가림) 410 `blob.gone`, 토큰 오류 401이다. 출처 §3.11.2.
- **티켓**: `blob.downloadTicket {blobId, variant?}`가 `{path: "/files/t/<ticket>", expiresAt}`를 준다. 헤더를 붙일 수 없는 곳(웹뷰가 직접 여는 링크, 외부 프로그램)에서 쓴다. 티켓은 32바이트 무작위 base64url이고, 수명 5분(`downloadTicketTtlMs` 기본 300,000), 발급한 WebSocket 연결에 묶여 연결이 닫히면 무효, 발급 때 지정한 blob 하나만 받으며, 수명 안에서는 Range 요청에 여러 번 쓸 수 있다. 기기 토큰은 URL에 넣지 않는다. 출처 §3.11.2, P-13.
- **티켓 로그**: 접근 로그에는 `/files/t/***`로 가리고 `Authorization`·`Cookie` 헤더를 남기지 않는다. 출처 §3.2.5.
- **격리 헤더**: 모든 `/files/*` 응답에 `Content-Security-Policy: sandbox; default-src 'none'`, `X-Content-Type-Options: nosniff`, `Cross-Origin-Resource-Policy: same-origin`을 붙인다. 인라인 표시는 `image/png`, `image/jpeg`, `image/webp`, `image/gif`, `text/plain; charset=utf-8`만 허용하고, 그 밖의 형식은 `application/octet-stream`과 `Content-Disposition: attachment`로 보낸다. 출처 §3.11.2, F-51, CT-41.
- **캐시 헤더**: `/files/*`는 `private, no-store`다. 정본은 18 §3.4.6이다(판정 J-252). 출처 §3.11.2.
- **가림**: 09 `blob.redacted` 이벤트의 `invalidates`에 `blobId`가 들어간다. 클라이언트는 이 이벤트를 받으면(재전송 포함) 그 `blobId`의 캐시를 지운다. 가린 blob은 `ETag`를 보내지 않는다. 출처 §3.11.1, 판정 J-147.
- **이미지 판**: `variants`의 `blobId`나 원본 `?variant=thumb|display`로 받는다. 판이 없으면 원본을 주고 `X-Helm-Variant: original`을 붙인다. 출처 §3.11.2.
- **SSH 경로**: 파일 요청마다 `ssh -W`를 하나 띄워 HTTP/1.1 요청 하나를 보낸다. 출처 §3.2.3, §3.11.3.

### 2.13 생존 확인과 재접속

- **서버 쪽**: WebSocket ping을 15초마다 보내고, 무수신(pong 포함 모든 프레임) 45초면 소켓을 파기한다. `tick` 알림은 `tickIntervalMs`(기본 15,000 ms)마다 보내며 송신 큐가 차 있어도 우선 보낸다. `tick`은 `{serverTime, headSeq, mode}`다. 출처 §3.10.1, §3.8.1, §3.4.4.
- **클라이언트 쪽**: 어떤 메시지든 받으면 감시 타이머를 다시 시작한다. `clientTimeoutMs`(기본 35,000 ms, 2 × tick + 5,000) 안에 아무것도 안 오면 4000으로 닫고 재접속한다. 앱 수준 ping은 보내지 않는다. 웹뷰 JavaScript는 WebSocket ping을 볼 수 없으므로 감시는 `tick`으로 한다. 출처 §3.10.1, P-12.
- **SSH 쪽**: `ServerAliveInterval=15`, `ServerAliveCountMax=3`이다. 45초 무응답이면 ssh가 끝나고 전송이 끝난다. 출처 §3.10.1.
- **클라이언트 상태 기계**: `idle`, `connecting`, `handshaking`, `syncing`, `ready`, `backoff`, `needsUser`, `closed` 여덟 상태다. `HelmClient`가 구현한다. 출처 §3.10.2, §3.14.
- **백오프 공식**: `d = min(30,000, 500 × 2^attempt)`, `delay = d/2 + random() × d/2`(반 지터), 그다음 `retryAfterMs`와 `restartExpectedMs`를 하한으로 적용한다. 직전 닫힘이 4008이면 첫 대기가 0이다. `ready` 상태가 30초 이상 유지되면 `attempt`를 0으로 돌린다. 출처 §3.10.3.
- **자동 재접속을 멈추는 실패**: 전송 `blocked`, HTTP 401·403, `protocol.unsupported`, `auth.failed`, `auth.revoked`, `auth.methodNotAllowed`, `pairing.invalidCode`, `serverId` 불일치다. 사람이 고쳐야 풀리는 실패다. 그 밖의 실패는 30초 간격으로 계속 시도한다. 출처 §3.10.3, §3.10.2.
- **즉시 재시도**: `retryNow()`는 백오프를 끝내되 `retryAfterMs` 하한을 지킨다. `needsUser`면 아무것도 하지 않는다. 네트워크 복구, OS 깨어남, 창 포커스, 화면 표시 때 부른다. 출처 §3.10.2, §3.14.
- **재접속 순서**: `hello` 성공 → `syncing`(저장된 `storeId`·`deviceId`를 대조해 다르면 `clearServer` 후 보류) → 저장된 위치로 이벤트 구독 복원 → `2001`이면 스냅샷 경로 → 모든 구독이 `caughtUp`이면 `ready`와 낡은 열린 뷰 다시 받기. 진행 중 명령 재전송은 구독 응답 뒤에 시작한다. `syncing` 중에는 사람 결정 명령을 보내지 않는다. 출처 §3.10.2.
- **경로 바꾸기**: WSS와 SSH 사이 전환은 네트워크 계열 실패에서만 하고, 연결된 동안에는 바꾸지 않는다. 위치와 진행 중 명령함은 같은 `serverId` 아래에서 그대로 쓴다. 출처 §3.10.3, 20 §3.8.10.
- **자격 상실**: `connection.closing{kind: "auth.revoked"}`나 4009 뒤 `credentialLost{reason}`을 내고 `needsUser`로 간다. `revoked`면 이 서버의 뷰 캐시, 진행 중 명령함, blob 캐시를 지우고 초안만 남긴다. `expired_absolute`나 `expired_idle`이면 캐시와 초안을 남기고 재페어링을 안내한다. 출처 §3.14, F-06, F-45.
- **데몬 재시작**: 연결이 1001로 닫힌다. 재접속 때 `bootEpoch`가 바뀌었음을 보이고, seq는 이어진다. 재생 중이었다면 마지막으로 받은 `to`부터 다시 구독한다. 출처 F-07, CT-27.

### 2.14 버전 협상

- **정수 하나**: `PROTOCOL_VERSION = 1`, `MIN_PROTOCOL_VERSION = 1`. 버전 2부터 서버는 현재와 직전 버전을 받는다. 출처 §3.12.
- **고르기**: `chosen = min(client.max, server.max)`다. `chosen < max(client.min, server.min)`이면 1003 `protocol.unsupported`이고 `details`에 `serverMin`, `serverMax`, `serverVersion`을 싣는다. 출처 §3.4.3, §3.3.4.
- **버전을 올리지 않는 변경**: 새 메서드, 새 알림, 새 뷰, 선택 params 추가, 결과·알림의 새 필드, 새 이벤트 종류, 기존 kind 아래의 새 오류 코드, 결과 열거형의 새 값. 추가형 변경은 `features`(메서드, 알림, 뷰, `capabilities`)로 알린다. 출처 §3.12, P-14.
- **버전을 올리는 변경**: 메서드나 필드의 삭제·이름 변경, 기존 필드의 뜻 변경, 선택 params를 필수로 바꾸기, 재전송·순서 계약(§3.5) 변경, 오류 코드의 뜻 변경. 출처 §3.12.
- **기능 이름**: `<영역>.<기능>.v<n>` 형식이다(예 `files.chunkedUpload.v1`). 양쪽이 광고하고 교집합만 쓴다. 출처 §3.12, §3.4.4.
- **읽기 규칙**: 서버는 요청 params를 엄격히 검사한다(모르는 필드는 -32602). 클라이언트는 결과와 알림을 관대하게 읽는다. 모르는 필드는 무시하고, 모르는 열거형 값은 "알 수 없음"으로 보이고, 모르는 이벤트 종류는 무시하거나 일반 행으로 보이고, 모르는 오류 코드는 `kind`의 앞부분과 `retryable`로 처리한다. 출처 §3.12, F-27, CT-25.
- **스키마 해시**: `features.schemaHash`는 등록 표의 해시(64자 hex)다. 같으면 클라이언트와 서버의 스키마가 같다. 재접속 때 저장된 명령의 `schemaHash`와 비교해 재전송 대상을 고른다. 출처 §3.4.4, §3.14.
- **이벤트 payload 버전**: `EventWire.v`(09 관리)는 프로토콜 버전과 별개다. payload가 바뀌어도 프로토콜 버전은 올리지 않는다. 출처 §3.12.
- **앱 쪽 판정**: `protocol.unsupported`를 받으면 `serverMin`, `serverMax`와 자기 범위를 비교해 "앱 업데이트 필요" 또는 "서버 업데이트 필요"를 보인다. 출처 §3.12, 20 APP-D14.
- **휴대폰 PWA**: 데몬이 같은 릴리스 묶음을 서빙하므로 보통 버전이 같다. 옛 서비스 워커가 옛 묶음을 들고 있으면 `protocol.unsupported`를 받고 새 묶음을 받아 다시 연다. 출처 §3.12, 26 §3.6.
- **조회**: `protocol.describe`는 이 연결의 버전, 지원 범위, `schemaHash`, 메서드 목록(kind, scopes, since)을 준다. `includeSchemas: true`를 주면 JSON Schema도 준다. 출처 §3.13.2.

### 2.15 클라이언트 코어와 앱 쪽 연결 모델

- **코어 `@helm/client`**: `HelmClient` 하나를 데스크톱(웹뷰 TS), 모바일 PWA(26), TUI가 같이 쓴다. 화면 프레임워크를 모른다. 코어가 맡는 것은 연결 상태 기계, 백오프, `hello`, 구독 복원, 뷰 무효화 판정, 휘발 스트림, 진행 중 명령 재전송이다. 출처 §3.14.
- **전송 인터페이스 `Transport`**: `open(handlers)`는 업그레이드 101까지 기다린다. 실패는 `TransportFailure`로 reject한다. `send(text)`와 `close(code, reason)`가 있다. `TransportFailure`는 `network`, `httpStatus`(status), `daemonUnreachable`, `blocked`(reason), `other`다. 출처 §3.14.
- **진입점**: `@helm/client`(브라우저 안전, 전송 구현 없음), `@helm/client/node`(`NodeWsTransport`, TCP와 `ws+unix`), `@helm/client/browser`(브라우저 WebSocket, 쿠키 토큰, `/m/whoami` 판정, `navigator.locks` 리더 잠금). 출처 §3.13.1.
- **데스크톱 전송 소유**: Rust가 전송을 소유하고 웹뷰는 텍스트 프레임만 받는다(ADR-20-01). Rust가 `Authorization` 헤더를 붙이고, `Origin`은 보내지 않는다. 출처 20 §3.2, §3.8.4, §3.8.5(20 ADR-20-01은 20 쪽 후보).
- **앱 쪽 세 가지 추가**: (1) 경로 선택기 `MultiRouteTransport`(순서대로 시도, 연결 뒤에는 경로를 안 바꿈, 3라운드 연속 네트워크 실패면 30분 뒤로 미룸) (2) 앱만 아는 실패(SSH, 키체인, `serverId`)를 `TransportFailure`로 바꾸기 (3) 사용자용 연결 상태 계산. 출처 20 §3.8.8, §3.8.10.
- **연결 프로필**: 서버 하나당 프로필 하나이고 경로가 1개 이상이다. 배열 순서가 시도 순서다. 토큰은 프로필 파일에 없고 키체인에 있다. 기본 템플릿 "Tailscale (권장)"은 `wss` 하나 뒤 `ssh` 하나다. 출처 20 §1.4, §3.8.1.
- **앱 저장소**: IndexedDB 데이터베이스 `helm-desktop`이고 모든 키에 `serverId`가 있다. `positions` 저장소는 키 `[serverId, subKey]`다(데스크톱은 `subKey` `main` 하나). `meta` 저장소에 `lastBootEpoch`, `schemaHash`, `recentDeliveryIds`를 둔다. `IdbClientStateStorage`가 19의 `ClientStateStorage`를 구현한다. 출처 20 §3.9.5.
- **명령 결과 처리(앱)**: `applied`와 `duplicate`는 "연결이 끊긴 동안 보낸 조작이 처리됐습니다"로 보인다. 3004·3009는 쓰던 내용을 초안으로 되살린다. 3008은 "다른 곳에서 먼저 처리했습니다"이다. 5003은 초안으로 되살리고 자동으로 보내지 않는다. 자동 재전송 제외 행은 "보내지 못한 조작"에 보이고 `command.lookup`으로 먼저 원래 키의 결과를 확인한다. 출처 20 §3.9.7.
- **낙관적 갱신 금지**: 화면은 "보내는 중"만 보이고 결과는 응답과 뒤따르는 뷰 무효화로 받는다. 사람 결정은 도구 결과 경로가 아니라 명령 메서드로만 들어온다(assistant-ui 도구 카드 버튼 포함). 출처 §3.5.9, §3.7.5, 발췌4 20-9·20-10(19 §2.4 인용), 20 §3.9.7.

### 2.16 SSH 경로 (결정 38)

- **결정 38**: 데스크톱 앱은 WSS와 SSH 두 경로로 접속한다. 두 경로에서 메시지와 재전송 의미가 같아야 한다. SSH의 구체 방식은 19가 방식을 정하고 ADR 후보 19-A1로 남긴다. 출처 §2.1 표(결정 38).
- **채택한 방식 B3**: `ssh -W 127.0.0.1:<loopback 포트>`. 비교 대상은 B1(`ssh -L` → 데몬 TCP), B2(`ssh -L` → 데몬 Unix 소켓), B4(`ssh <서버> helm bridge` exec stdio → 소켓), B5(exec stdio + 길이 접두 프레임, pi-env식)다. 근거 네 가지는 (1) HTTP 서버 코드, 프레이밍, 파일 전송이 경로와 무관하게 같다 (2) 원격 명령을 실행하지 않아 셸 시작 파일 출력이 섞이지 않는다 (3) 클라이언트 쪽에 열린 포트가 없다 (4) 데몬 쪽 추가는 리스너 하나다. 출처 §3.2.3, 19-A1, 20 APP-D03·ADR-20-02.
- **`ssh -W`의 제약**: `host:port`만 받으므로 Unix 소켓을 직접 가리킬 수 없다. 그래서 TCP 리스너가 하나 더 필요하다. 출처 §3.2.3(`man ssh` 인용).
- **프레이밍**: 별도 길이 접두 프레임이 없다. 바이트 스트림 위의 HTTP/1.1(RFC 9112)과 WebSocket(RFC 6455)이다. 텍스트 메시지 하나가 JSON-RPC 메시지 하나(UTF-8, BOM 없음)다. 바이너리 메시지는 1003으로 닫는다. 조각난 메시지의 합계가 `maxInboundMessageBytes`를 넘으면 1009다. 클라이언트 프레임은 마스킹해야 하며 생략하면 서버가 1002로 닫는다. `permessage-deflate`는 협상하지 않는다. 출처 §3.2.3.
- **업그레이드의 `Host`**: `127.0.0.1:<HELM_LOOPBACK_PORT>`로 보낸다. loopback의 허용 목록은 `127.0.0.1:<포트>`와 `localhost:<포트>`다. 출처 §3.2.3, §3.2.1.
- **클라이언트 절차**: (1) `ssh -T -o BatchMode=yes -o ServerAliveInterval=15 -o ServerAliveCountMax=3 -W 127.0.0.1:<포트> <별칭>`을 띄운다(`-W`는 `-N -T ExitOnForwardFailure`를 포함한다고 원문 인용). 호스트 키 정책은 20과 18이 정한다. (2) 표준 입출력 위에서 `GET /rpc` 업그레이드를 보낸다. 이후는 WSS 경로와 같다. (3) 파일 요청은 요청마다 ssh 프로세스를 하나 더 띄운다. (4) ssh 프로세스가 끝나면 WebSocket도 끝난 것이다. 재접속은 1단계부터 다시 한다. 출처 §3.2.3, 20 §3.8.3.
- **loopback의 인증**: Tailscale 신원을 확인하지 않고(있으면 무시), Host와 Origin 허용 목록만 본다. 받는 인증은 `deviceToken`뿐이다. 같은 호스트의 다른 프로세스가 붙어도 토큰이 없으면 `hello`가 실패하고 그 밖의 요청은 처리하지 않는다. 출처 §3.2.1, F-29.
- **예비 경로 B4**: 서버 쪽 sshd가 TCP 포워딩을 막으면 `helm bridge`를 쓴다. 브리지는 stdout에 `HELM-BRIDGE/1 <nonce>\n` 동기화 줄을 먼저 쓰고, 클라이언트는 그 앞 바이트를 버린다. 이 경로는 `local` 리스너로 들어가므로 `deviceToken`을 받는다. 출처 §3.2.3, Q-01.
- **동등성 시험**: 같은 적합성 스위트를 리스너마다 돌린다(CF-01). `ssh -W localhost`로 붙은 실제 경로에도 돌린다(CF-02, `just test-conformance-ssh`). 두 방식의 JSON-RPC 메시지 열(요청 id, 시각, nonce, 연결 ID를 정규화)이 같아야 한다. 출처 §6.3, 22 §3.10.

### 2.17 HTTP 경로 목록

- **구분**: 리스너마다 받는 경로가 다르다. 검사 순서는 Host → Origin → 신원 → 자격이다(18 §3.4.3 `preflight`). 
- **주요 경로**: `GET /rpc`(WebSocket, 셋 다), `GET /healthz`(셋 다, 본문 `{"status": …}`만), `GET /m/*`(정적 PWA, tailnet), `POST /m/pair`(모바일 페어링, tailnet, Set-Cookie), `GET /m/whoami`(쿠키 확인, tailnet), `POST /m/logout`(tailnet), `POST /pair`(데스크톱 페어링, tailnet, Origin이 있으면 403), `POST /devices/self/rotate`(토큰 교체, tailnet·loopback), `POST /m/cmd`(진행 중 명령 HTTP 전송, tailnet), `POST /files/u`·`HEAD`·`PATCH /files/u/<uploadId>`(업로드, 셋 다), `GET /files/b/<blobId>`(다운로드, 셋 다), `GET /files/t/<ticket>`(티켓 다운로드, 셋 다). 출처 §3.2.5 표.
- **페어링 응답의 토큰**: `POST /m/pair`는 토큰을 본문에 싣지 않고 `Set-Cookie: __Host-helm_dt=…`로만 준다. `POST /pair`는 본문에 토큰을 싣고 `Origin`이 있으면 403이다. 브라우저에서 오는 페어링은 `/m/pair`만 받는다. 출처 §3.2.5, 18 §3.4.3 규칙 4.
- **목록에 없는 경로**: 404다. 기능 플래그 `clients.mobile`이 꺼져 있으면 `/m/*`와 휴대폰 페어링은 모두 404다. `loopback`에서 `/m/*`와 `/pair`는 404다. 출처 §3.2.5.
- **공통 헤더**: 모든 HTTP 응답에 `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`를 붙인다. 파일 내용이 아닌 응답은 `Cache-Control: no-store`다. 접근 로그에는 `Authorization`과 `Cookie`를 남기지 않는다. 출처 §3.2.5.
- **Origin 정확 일치**: 스킴, 호스트, 포트까지 같아야 한다. 같은 호스트의 다른 포트(8443~8447)에서 온 요청도 403이다. 출처 §3.2.5, 26 §3.3.3 X-16.
- **데스크톱 앱의 CORS**: 데스크톱 앱은 데몬과 같은 출처가 아니고 Rust가 요청을 보내므로 CORS 응답 헤더를 두지 않는다. 출처 §3.2.5, 20 §3.1.

### 3.3 구독 재생 알고리즘 (서버)

  2. 구독 수 검사 → 초과면 2003

### 3.6 SSH 경로의 바이트 흐름

```text
Rust/클라이언트
  └ ssh -T -o BatchMode=yes -o ServerAliveInterval=15 -o ServerAliveCountMax=3
        -W 127.0.0.1:7841 <별칭>        ← 로컬 포트를 열지 않는다
        표준 입출력 = TCP 바이트 스트림
        └ HTTP 업그레이드 GET /rpc (Host: 127.0.0.1:7841)
        └ WebSocket 텍스트 메시지 = JSON-RPC 하나 (마스킹됨)
파일 요청마다 같은 명령으로 ssh를 하나 더 띄워 HTTP/1.1 요청 하나
```

출처 §3.2.3, §3.16.4. 1단계(업그레이드)만 WSS와 다르고, 2단계 이후의 메시지, 위치, 재전송, 멱등 처리는 바이트 단위로 같다. `loopback` 리스너는 Tailscale 신원 헤더를 요구하지 않는다.

### 3.7 파일 업로드와 다운로드 절차

- **업로드(한 번에)**: `POST /files/u` → `201 {blob}` → 명령의 `attachments`에 `BlobRef` 참조 → 커널이 참조를 기록하고 보관. (§3.11.3, §3.16.5)
- **업로드(청크)**: `POST /files/u`(Upload-Length, X-Helm-Sha256) → `201 {uploadId}` → `PATCH /files/u/<uploadId>`(Upload-Offset) 반복 → 마지막 청크에서 해시 검사 후 `201 {blob}`. 끊기면 `HEAD`로 위치를 받아 이어 올린다. (§3.11.3)
- **다운로드(헤더 가능)**: `GET /files/b/<blobId>` + `Authorization: Bearer`. (§3.11.2)
- **다운로드(헤더 불가)**: `blob.downloadTicket` → `/files/t/<ticket>`(5분, 연결에 묶임). 티켓 만료나 연결 종료 뒤 401이면 새 티켓을 받아 `Range`로 이어 받는다. (§3.11.2, F-25, CT-22)

## 6. 다른 노드와의 연결

- **10 명령 채널**: 사람 결정은 `human_client` 채널과 `human` 행위자로만 들어간다. 허용 via는 `device`와 `local_cli`다. 프로토콜의 `EngineInput`이 이 값을 서버에서 채운다. 비대화 `localAdmin`이나 `runtimeAdapter` 출처의 사람 결정은 `denied.channel`이다(10 §3.3.2). 명령 envelope의 `clientKind`는 인증된 연결의 기기 종류로 채운다(10 §3.3.1, 19 §3.3.1). 이 pack의 §2.8이 프로토콜 쪽 처리 단계다.
- **09 멱등과 이벤트**: 09 §3.9.1이 범위 키와 지문을 계산하고, 프로토콜은 그 값을 그대로 쓴다. 09 §3.9.2가 결과 저장 규칙을 정한다. 09가 seq, `storeId`, `invalidates`(`event_invalidations`)를 제공한다. 09 `EventQuery`의 `untilSeq`, `scanLimit`, `scannedUntilSeq`가 재생에 쓰인다(19 §3.5.4).
- **08 레코드**: `RecordRef`, `RecordKind`, `Device.credentialCarrier`, `Via`, `ActorRef` 문자열, `RevisionRef`(`{id, revisionSeq}`)를 08에서 가져온다. 레코드 필드 타입은 08 값이고 프로토콜이 다시 정의하지 않는다(19 §3.7.4, §3.7.2).
- **12 투영과 태그**: 12 §3.5.8이 집계 태그 이름과 이벤트 종류별 대응의 정본이다. 뷰 `dependsOn` 계산과 속성 테스트 VIEW-01이 여기에 기댄다(19 §3.6.3).
- **04·05·21 화면**: 뷰 `data`의 타입은 04가 정한다. 오류 kind와 reason에 대응하는 문구는 05가 키로 만든다. 화면 ID(`SCR-*`)는 03이 정한다. 20·21이 `basisSeq`를 쓴다(19 §3.7.2, 20 §3.9.7).
- **17 데몬 운영**: 리스너 주소와 포트, 소켓 경로, `serve.table`, 데몬 모드 전이(normal·safeMode·readOnly·draining), `admin.*`의 의미, 대기 파일 정리, 종료 예산은 17이 정한다. 프로토콜은 메서드 이름과 scope만 정한다(19 §3.7.8).
- **18 보안**: Tailscale 신원 확인, 기기 토큰 형식과 해시 저장, 페어링 정책, 서명 키, 전송 조건(preflight), 쿠키 판정, 입력 마스킹, `/files/*` 격리 헤더의 보안 시험(18 §3.17)은 18이 정한다. 프로토콜은 판정 함수의 입력과 결과 코드만 정한다(19 §3.4.3).
- **20 앱**: 연결 상태 기계 소유(`HelmClient`), 경로 선택기, 프로필, IndexedDB 저장소, 명령 흐름, OS 알림 규칙(`question.delivered`를 받았을 때만)을 20이 맞춘다. 데스크톱 전송의 `ssh -W`는 20 ADR-20-02다.
- **26 모바일**: 같은 프로토콜과 같은 `@helm/client`를 쓴다. 쿠키 운반, `/m/*` 정적 서빙, `/m/whoami`, `/m/cmd` keepalive, 푸시(Web Push, `interrupt`·`notice`)는 26과 19 §3.17이 나눈다.
- **22 시험**: 적합성 시나리오 CT-01~CT-50을 세 리스너와 `ssh -W` 경로에 돌린다(CF-01~03). 시험 흐름은 AC-04-05(재접속 뒤 위치 다음부터), AC-04-06(오프라인 초안, 끊긴 명령 한 번만 적용), AC-10-06, AC-11-03, AC-11-05, AC-07-13, FI-07~FI-10, FI-17, FI-24, FI-29, PF-02~PF-04에 걸린다.
- **13 어댑터**: 런타임 어댑터 프로토콜은 클라이언트 계약과 분리한다(canon C8). 관찰 에이전트와 데몬 사이 IPC는 16 §3.2.3이 정한다. 이 프로토콜에는 도구 결과를 채우는 메서드가 없다.

## 7. 구현 리뷰 체크포인트 후보

### 7.1 불변조건 (설계가 "반드시"로 정한 것)

- 서버는 `hello` 성공 전에 `hello` 외의 요청을 처리하지 않는다. 다른 요청은 1001 응답 뒤 1008로 닫는다(§3.4.5, §3.4.7).
- 업그레이드 뒤 서버의 첫 메시지는 `hello.challenge`다(§3.4.1).
- 토큰 경로의 실패는 언제나 1004다. 1006(`auth.unknownDevice`)은 토큰 경로에서 쓰지 않는다. 기기 존재를 알려 주지 않으려고 세부를 나누지 않는다(§3.4.3, §3.3.4).
- TCP 리스너(`tailnet`, `loopback`)는 기기 토큰 없이 아무것도 허용하지 않는다(§3.2.1).
- `localAdmin`은 `local` 리스너에서만 받는다(§3.4.3).
- 쿠키는 `tailnet` 리스너에서만 읽고, Origin은 정확히 일치해야 한다(§3.2.2, §3.2.5).
- `helm-bearer.` 하위 프로토콜은 정식 데몬이 받지 않는다(§3.2.2).
- 기기의 운반 방식은 고정이다. 어긋나면 1008(`carrier_mismatch`)이다(§3.2.2, §3.4.3).
- 클라이언트는 provenance와 actor, channel을 자기 값으로 보내지 않는다. 서버가 채운다. 스키마에 해당 필드가 없다(§3.7.5).
- 모든 `cmd` 메서드는 `idempotencyKey`와 `basisSeq`를 가진다(§2.3 P-09, §3.7.5).
- 같은 키·같은 지문이면 저장된 결과를 주고, 같은 키·다른 지문이면 3006이며 저장하지 않는다(§3.9.2).
- 멱등 범위와 지문에 연결 ID, 리스너, 시도 번호를 넣지 않는다(§3.9.2, 09 §3.9.1).
- 지문에 `commandId`, `expect`, `basisSeq`, `localConfirm`을 넣지 않는다(§3.9.2).
- 발급 ID 필드(예 `objectionId`)는 지문에서 뺀다(09 `generatedIdFields`, §3.9.2).
- 커밋 이벤트 알림은 명령 응답보다 먼저 큐에 들어간다(§3.5.9).
- 재생 중 연결의 `from`은 직전 알림의 `to`와 같아야 한다. 아니면 gap으로 보고 다시 구독한다(§3.5.3, §3.5.7).
- 구독 등록은 head 읽기와 같은 이벤트 루프 턴에서 한다(§3.5.4).
- 영속 이벤트는 버리지 않는다. 버릴 수 있는 것은 휘발 조각뿐이다(§3.5.8, P-11).
- `invalidate` 처리는 같은 구간의 위치 저장보다 먼저 일어난다(§6.3 CT-35).
- 데이터가 바뀐 뷰의 `invalidates`와 `dependsOn`은 반드시 겹친다(§3.6.3, VIEW-01).
- 휘발 상태는 `finalSeq`를 받을 때까지 지우지 않는다(§3.6.4).
- `syncing` 중에는 사람 결정 명령을 보내지 않는다(§3.10.2).
- 1003, 1004, 1005, 1008, 4009(auth.revoked)에서는 자동 재접속을 멈춘다(§3.10.3).
- 클라이언트 설정값(정책)은 하드코딩하지 않고 `hello` 응답에서 다시 읽는다(§3.4.4).
- `5003`을 받은 명령은 자동 재전송하지 않는다(§3.9.1 (6), F-17).
- 자동 재전송 대상은 `storeId`, `deviceId`, `protocol`, `schemaHash`가 현재 값과 같아야 한다(§3.14, §3.9.1).
- WebSocket 텍스트 메시지 하나는 JSON-RPC 메시지 하나다. 바이너리 메시지는 1003으로 닫는다(§3.2.3).
- `ssh -W` 경로의 클라이언트 프레임은 마스킹한다(§3.2.3).
- `permessage-deflate`는 협상하지 않는다(§3.2.3).
- 기기 토큰을 URL에 넣지 않는다. 티켓은 발급한 연결에 묶인다(§3.11.2, P-13).
- `/files/*` 응답은 격리 헤더를 항상 붙이고, 허용 목록 밖의 형식은 `attachment`로 보낸다(§3.11.2, CT-41).
- `/files/t/<ticket>` 값은 접근 로그에서 가린다(§3.2.5).
- 가린 blob은 `ETag`를 보내지 않는다(§3.11.1).
- 같은 내용의 파일은 같은 `blobId`다(§3.11.1).
- 파일 바이트를 WebSocket 메시지에 싣지 않는다(§3.11.1, 19-A7).
- `protocol.unsupported`에서 클라이언트는 자동 재접속을 멈춘다(§3.10.3, F-05).
- `features.methods`에 없는 메서드를 부르지 않는다. 서버는 -32601로 답한다(§3.4.4).

## 8. 헷갈리기 쉬운 점

- **WebSocket 닫는 코드 1008과 오류 코드 1008은 다른 것이다.** 닫는 코드 1008은 WebSocket 표준의 "정책 위반"이고, 오류 코드 1008은 `auth.methodNotAllowed`다. 4001도 같다. 닫는 코드 4001은 핸드셰이크 시한이고, 오류 코드 4001은 `blob.tooLarge`다. 1001도 닫는 코드(going away)와 오류 코드(`handshake.required`)가 다르다. 1011은 닫는 코드(내부 오류)와 오류 코드(`rateLimited`)가 다르다. 출처 §3.2.6, §3.3.4.
- **`lastSeq`와 위치.** 설계 본문은 재전송 위치를 `{storeId, seq}`로 부르고 `lastSeq`는 쓰지 않는다(§1.4). `lastSeq`는 결정 31 원문, `CommandResult.lastSeq`(이 명령이 커밋한 이벤트 seq 범위의 끝), §3.5.9 설명에 남아 있다. 명령 결과의 `lastSeq`는 "재전송 위치"가 아니다. 출처 §1.4, §3.7.2, §3.5.9, 20 §1.4.
- **중복 응답의 이름.** 19는 같은 키 재요청의 응답 필드를 `duplicate: true`로 쓴다. 09 §3.9.2 표와 `06 SubmitResult`는 `replayed`라고 쓴다. 19는 "06 SubmitResult.replayed"를 `duplicate`로 옮긴다고 적었다. 출처 §3.7.2 `duplicate` 주석, 09 §3.9.2.
- **멱등 키 형식.** 19는 `ik_` + ULID 26자를 정규식으로 강제한다(`^ik_[0-7]…$`). 09 §3.9.1은 `idempotencyKey`를 "1~128자, 클라이언트가 정함, 보통 commandId와 같은 ULID"라고 적는다. 형식 강제는 19(메서드 params 스키마)에서만 본다. 출처 §3.4.2, 09 §3.9.1.
- **멱등 보관 기간 7일과 365일.** 20 §3.9.7은 "보존 idempotencyWindowMs 7일, 19 §3.9.2"라고 적는다. 19 §3.4.4 정책 주석과 §3.9.2는 365일(09 §3.15.3)이다. 19가 정본이다. 20의 값은 맞춰야 한다. 출처 20 §3.9.7, 19 §3.4.4, §3.9.2.
- **영구 오류 목록의 `retryable`.** 19 §3.9.1은 "저장되지 않는 영구 오류(`retryable: false`인 -32600·-32601·-32602·5007)"라고 적는다. 5007(`feature.disabled`)은 `retryable: false`이고 저장하지 않는다(표 §3.3.4). 목록은 맞다. 다만 `-32603`은 `retryable: true`다. 출처 §3.3.4, §3.9.1.
- **`redacted`와 `redactions`.** F-12 표는 `redacted: [""]`라고 적는다. 와이어 스키마 `EventWire`의 필드 이름은 `redactions`다(§3.5.2). 구현은 스키마 이름을 따른다. 출처 §4 F-12, §3.5.2.
- **`ping`과 `tick`.** `ping`은 진단용 왕복 측정 메서드다. 생존 확인은 `tick` 알림이 한다. 클라이언트는 `ping`을 주기적으로 보내지 않는다. 출처 §3.7.2 끝.
- **`from`과 `resume`.** `events.subscribe`의 `from`은 구독 시작 위치다. `hello`의 `resume`은 응답 `log.resume`의 판정 미리보기에만 쓴다. 실제 재전송은 `from`으로 한다. 출처 §3.4.3 주석, §3.5.3.
- **`duplicate`와 `reduced`.** `reduced`는 보관 기간이 지나 결과를 줄인 행에만 `true`다. 이때 `events`와 `created`는 비어 있다. 출처 §3.7.2, §3.9.2.
- **`applied`와 `accepted`.** `applied`는 결과 이벤트가 커밋된 것이다. `accepted`는 오래 걸리는 일을 접수한 것이고 결과는 이벤트로 온다. 10 거부 결과 `needs_gate`는 프로토콜에서 `status: "gated"`(성공 응답)이다. 오류가 아니다. 출처 §3.3.5, §3.7.2.
- **`basisSeq`와 `asOfSeq`.** `basisSeq`는 사람이 결정할 때 본 화면의 `asOfSeq`다(19 §3.9.3). `expect`는 특정 레코드의 `revisionSeq`를 직접 주는 것이다. 두 값을 같은 것으로 보면 안 된다. 출처 §3.9.3.
- **`revisionSeq`와 `seq`.** `revisionSeq`는 레코드의 판 번호(사람이 의미 있는 변경에서만 오름)다. `seq`는 이벤트 로그 순번이다. 운영성 변경(근거 링크 추가 등)은 seq는 오르고 revisionSeq는 안 오른다. 출처 §3.9.3, 09 D09-4.
- **`device.pair`는 JSON-RPC 메서드가 아니다.** 등록 표에 같은 이름이 없다. 코드를 쓰는 페어링은 HTTP `POST /pair`(데스크톱)와 `POST /m/pair`(휴대폰)로 한다. 토큰을 웹뷰에 보이지 않으려는 이유다. 코드를 만드는 쪽은 `device.createPairingCode`(cmd)다. 출처 §3.7.1 아래 항목, §3.7.7.
- **`stream.chunk`의 `n`과 `afterSeq`.** `n`은 실행별 조각 번호(버린 조각도 소비)다. `afterSeq`는 조각을 낼 때의 마지막 영속 seq다. 둘은 다른 값이다. 출처 §3.6.4.
- **`minSeq`와 `waitMs`.** `minSeq`는 "이 seq 이상 반영한 투영만 받겠다"는 조건이다. `waitMs`는 그 조건을 기다리는 시간(기본 2,000 ms)이다. 기다려도 못 맞추면 2006이다. 출처 §3.6.3, §3.5.6.
- **`bootEpoch`와 `storeId`.** `bootEpoch`는 프로세스 시작마다 바뀌고 재전송 판정에 안 쓴다. `storeId`는 저장소가 바뀔 때만 바뀌고 재전송 판정에 쓴다. 출처 §3.5.1.
