## 1. 이 노드가 답할 질문

> "Helm은 누구의 어떤 문제를 풀고, 제품으로서 무엇을 하며 무엇을 하지 않는가? 핵심 개념(원함 발견, Goal·Concern, 루프 O/I/C/A/S, 능력, 모드·다이얼, 불변조건 1~7, recognition over recall)과 대표 유즈케이스 흐름은 무엇인가?"

- 누구: 제품 소유자 한 사람이 쓰는 혼자 쓰는 앱. 여러 사용자, 팀, SaaS, 조직 정책은 범위 밖이다 [결정 24; 01 §2.3; NS-02].
- 어떤 문제: 지시에서 출발하는 에이전트가 원하는 것을 찾지 못하는 문제(PB-1~3), 사람 입력이 병목이 되어 형식이 우회되는 문제(PB-4), C와 A를 건너뛰는 문제(PB-5), 돌아왔을 때 복원 비용이 드는 문제(PB-6), 묻지 않은 결정이 흩어지는 문제(PB-7), 묻는 횟수가 늘어 우회 습관이 생기는 문제(PB-8), 기기가 꺼지면 멈추는 문제(PB-9). 01 §3.2.
- 무엇을 하는가: 원함 탐구, 작업 합의(C)와 결과 확인(A), 질문의 기록과 전달, 혼자 정한 결정의 기록과 이의, 자리를 비운 동안 데몬의 진행, 돌아왔을 때의 복귀 요약 [01 §3.1.4].
- 무엇을 하지 않는가: 모든 작업에 Concern 절차를 강제하지 않는다(NG-01). 모델이 결과를 승인하거나 Goal을 확정하지 않는다(PR-07). 승인 버튼만 주는 확인을 만들지 않는다(X-05). 대화 중심 화면, 대안 2~3개를 고르게 하는 원함 탐구, 페르소나를 만들지 않는다(NG-12, PR-13). 전체는 §2.17.

## 2. 핵심 개념

### 2.1 제품 정의와 구성

- 한 문장 [제안] (01 §3.1.1): "Helm은 한 사람이 에이전트와 함께 일할 때, 자신이 실제로 원하는 것을 자극과 반응으로 찾고, 무엇을 어디까지 맡겼고 결과를 무엇으로 확인했는지 남기며, 자리를 비워도 일이 이어지고 돌아왔을 때 바로 다시 판단할 수 있게 하는 개인용 에이전트 작업 시스템이다."
- 구성 (01 §3.1.2 [결정 19~23, 33, 38, 41] [제안: 결정 26·27·28·29 기본값]):
  - 데스크톱 앱(Tauri v2 + React 19). 얇은 클라이언트이고 Helm 로직이 없다. 접속은 (a) Tailscale serve 경유 WSS, (b) SSH 경유.
  - 홈 서버 WSL2 Ubuntu 24.04의 상주 데몬 `helmd`(systemd). 안에 커널(검증·상태 전이·정책, 모델은 제안만), 이벤트 로그(SQLite WAL, 기준 원본, `/srv/volumes/helm`), 자체 런타임(pi-agent-core 포크 루프, pi-ai 모델 계층, coding-agent 도구와 Helm 제안 도구), 탐구 엔진, 스케줄러가 있다.
  - 이후 단계: 관찰 에이전트(쓰기 권한 없음), SSH로 들어가는 Helm TUI(pi-tui), 관리 CLI `helm`(페어링, 상태, 백업, 복구).
- 사용자가 직접 실행하는 것은 앱 하나다. 앱을 닫아도 진행 중인 작업은 계속된다 [결정 22]. pi와 Claude Code는 Helm 밖에서 그대로 쓰며, 허용된 폴더의 외부 세션 로그는 관찰 입력으로만 읽는다 [결정 35].
- Helm이 하는 일 (01 §3.1.4): 1 요구를 확정 정의로 취급하지 않는다. 2 다른 관점과 분야, 레퍼런스를 자극으로 제시한다. 3 반응으로 실제 요구를 찾는다. 4 찾은 요구를 Goal과 완료 기준에 반영한다. 5 정한 일을 작업 합의로 맡긴다(C). 6 완료 주장을 근거와 함께 받고 사람이 확인해 전체에 반영한다(A). 7 사람 없이 진행하고 돌아온 사람에게 바뀐 것과 판단할 것을 보인다(O).
- 일반 에이전트 하네스와 대비 (01 §3.1.5): 출발점은 지시문과 반응(Helm), 사람은 승인과 수정(하네스)과 달리 초안에 반응하고 맡길 범위를 확정하며, 기본 화면은 대화가 아니라 Goal·Concern 상태, 질문함, 에이전트가 정한 것이다. 완료는 제출, 확인, 반영으로 나뉘고, 기록의 기준은 이벤트 로그다.

### 2.2 문제와 근거 (01 §3.2, §3.4)

- PB-1: 지시에서 출발하면 세부 결정이 사용자 지식 수준을 넘지 못한다. PB-2: 글로 쓴 요구와 실제 요구가 다르고, 자극을 비교해야 원하는 것을 안다 [결정 1]. PB-3: 대안 2~3개를 고르게 하는 방식은 원하는 것을 찾지 못한다 [결정 18].
- PB-4: 사람이 의미를 직접 써넣게 하면 병목이 되고 형식이 우회된다. PB-5: 사용자는 C와 A를 가장 많이 건너뛴다 [대화 L2019]. PB-6: 실행 속도가 이해 속도보다 빨라 복귀 때 원본 로그를 다시 읽어야 한다 [canon §3.2]. PB-7: 묻지 않은 결정이 흩어진다 [결정 8]. PB-8: 묻는 횟수가 늘면 습관이 번진다 [공리 A12]. PB-9: 기기가 잠들거나 오프라인이면 멈춘다 [결정 21·22].
- v0.2 실사용 증거 (founder dogfood 001·002, 01 §3.4.1): EV-1 Git만으로 모은 네 영역 중 셋이 `unknown`이었다. EV-2 의미는 사람 입력 7개에서 나왔다. EV-4 템플릿 질문 약 197개를 사용자는 폼을 고치지 않고 한 문장으로 답했다. EV-5 `summary: ㅇ`, `rationale: ㅁㄴㅇ`인 결정이 필수 필드만 채워져 최신 결정으로 표시되었다. EV-6 짧은 자연어 개입 한 번이 범위와 로드맵을 바꿨다. EV-7 자동 Brief는 파일 56개를 56행으로, 수동 Brief는 3그룹으로 보였다. dogfood 002는 파일 89개를 5그룹으로 줄였다. EV-8 24시간 복귀 실험은 결과 없이 구현으로 넘어갔다. EV-9 가장 많이 건너뛴 루프는 C와 A다.
- 01 §3.4.2는 이 증거를 다음 제약으로 옮긴다: 의미 입력은 짧은 자연어 반응과 선택으로 받고, 자동 수집한 변화에서 목적과 결정을 추론해 확정하지 않는다(PR-01). 지표는 `decision_changed_outcome`, 바뀐 합의, 취소된 작업 중심이다(§3.10).

### 2.3 사용자가 다루는 단위 (01 §3.1.3)

- Goal: 프로젝트 단위 궁극 목표. Concern을 거치며 다듬어진다 [결정 11].
- Concern: 10단계 과정을 돌릴 후보가 되는 상황(문제, 기회, 위험, 불확실성, 취향 결정, 반복 마찰) [결정 11].
- WorkUnit: Concern 안의 실행 단위(탐구, 탐침, 변경, 반영) [브리프 §6].
- 작업 합의: 목적, 완료 기준, 범위, 금지 행동, 제출할 근거, 멈출 조건.
- 결과 확인: 제출된 결과를 사람이 받아들이거나 고치게 하는 일 [결정 15(2)].
- 질문: 기록과 전달이 나뉜다 [결정 12]. 에이전트가 정한 것: 묻지 않고 정한 결정으로, 이의를 걸 수 있다 [결정 8].
- 선호 모델: 원함 탐구에서 쌓인 기준, 무게, 좋은 예와 싫은 예 [결정 1·15].
- 사용자에게 N/E/M, A/P, OPD+C, 루프 식별자 같은 내부 용어를 외우게 하지 않는다 [제안].

### 2.4 원함 발견과 원함 탐구

- 원함 발견(동기): 사람이 글로 쓴 요구와 실제 요구가 다를 수 있고, 자극을 비교해 본 뒤에야 원하는 것을 안다는 전제다 [결정 1; 25 §3.1]. 첫 출발점은 취향이 정답인 작업(글의 톤, 기획 방향, 디자인)이다 [결정 1].
- 원함 탐구(`I.want`): 자극에 대한 반응으로 숨은 기준을 찾는 루프다 [25 §3.4; 15 §3.6]. 발산은 원함 발견을 위한 방법이고, 발산 서브시스템은 일곱 단계다 [25 §3.1].
- 탐구 네 종류: 사실, 원함, 가능성, 결과 [결정 7].
- 반응 형태: 요소 단위(문장 구간이나 이미지 영역), 강도, 이유 없는 반응, 고쳐 말하기. 각각 `observation.recorded`(kind `reaction`)로 기록한다 [02 AC-01-05].
- 하나 고르기 금지: 한 라운드가 "하나 고르기"만으로 끝날 수 있으면 위반이다 [PR-02; X-10; 02 AC-01-06, AC-01-16]. 사용자가 "그냥 하나 골라 줘"라고 직접 지시하면 지시로 기록하고 따른다 [FX-07].
- 기준 후보는 반응 관찰 id를 하나 이상 참조해야 하며, 기준 확정은 사람 명령으로만 생긴다 [02 AC-01-07, AC-01-08]. 말한 기준과 반응이 다르면 `stated_vs_revealed`로 남기고 두 값을 함께 보인다 [FX-06].
- 정지 규칙 `planStable`: 사람 입력이 있었던 라운드만 세어 지문이 두 번 연이어 같거나 한 번 같고 가장 좋은 남은 질문의 점수가 0이면 참이다. 예산이 다 되면 정지가 아니라 `budget_exhausted`다 [02 AC-01-10, UC-01 A4].
- 예산: 첫 라운드 자극 8개, 묶음 최소 4개(판정 J-06), 근거 범위 "웹까지(읽기)", 전달은 라운드 경계 예약이 기본이다 [02 UC-01 모드 행, AC-01-03].

### 2.5 Goal과 Concern

- Goal: 프로젝트 단위 궁극 목표. Concern 사이클을 거치며 정제되고 버전을 가진다 [결정 11; 25 §3.2 `goalVersion`]. 확정 Goal이 없으면 자리표시 Goal "이름 없는 Goal"에 연결해 진행하고 요청을 거부하지 않는다 [FX-13]. Goal 수정 확정은 사람이 한다(의존 규칙 5 [제안]). 수정 제안은 `goal.revision_proposed`다 [25 §3.2].
- Goal 상태: `proposed`, `active`, `paused`, `achievement_claimed`, `achieved`, `superseded`, `retired` [25 §3.3].
- Concern 종류 `ConcernKind` 여덟: `problem`, `opportunity`, `risk`, `uncertainty`, `taste`, `friction`, `external_request`, `light_work` [25 §3.1].
- 보관 Concern: 프로젝트마다 하나, `kind: light_work`. 가벼운 작업이 그 아래 WorkUnit으로 들어간다 [01 §3.6.4].
- 여러 프로젝트는 한 홈에 두고 프로젝트 필터를 쓴다 [OQ-11].

### 2.6 루프 O, I, C, A, S

- 결정 5: 루프는 한 작업 안에서 조합하고 언제든 전환한다. 커널이 강제하는 것은 의존 규칙뿐이다. 결정 6: 상황 유형 `clear`(명확), `complicated`(복잡), `complex`(복합), `chaotic`(혼돈), `disorder`(혼란)는 바뀔 수 있는 상태다 [25 §3.1; 08 §3.15].
- `LoopId` 18개 [25 §3.4; 08 §3.15 `LOOP_IDS`]: O(상황 파악) / I.fact, I.want, I.possibility, I.outcome / C.commit(약속), C.probe(탐침), C.emergency(비상) / A.confirm(확인), A.watch(지속 관찰), A.reflect(돌아보기) / S.split, S.merge, S.detach, S.relocate, S.recombine, S.hold, S.close.
- 상황 판정 `SituationAssessment`(`sa`)는 판정 질문 아홉 개의 답에서 결정표로 계산한다 [25 §3.2; 14 §3.7].
- 루프 계획 예 (02 표): UC-01은 O → I.want → C.commit → A.confirm → A.reflect. UC-07은 O → C.commit → A.confirm → A.reflect(I를 건너뛰고 이유를 계획에 남김). UC-02는 O → I.fact → (선택) → C.commit → A.confirm.
- 루프 계획 방식 [결정 53; 02 §2.1]: 기본은 모델이 계획 표시(`PlanFlags`)를 선언하고 코드가 계산하는 혼합 방식이다. 방식은 다이얼 `planAuthoring`(`computed`, `hybrid`, `model`, 기본 `hybrid`)으로 고른다. 계획은 권고이며 벗어나는 전환이 허용된다 [25 §3.2].
- 전환 명령은 `loop.transition`(10), 전환 기록은 `loop.transitioned`(09)다. 10 §3.8: 전환 자체는 막지 않고 `from`이 현재 루프인지만 본다.
- C/A 우선 (01 §3.5.1): 사용자 진술 "C와 A"(대화 L2019)가 근거다. 이유 네 가지: O와 I는 판단이 많아 강제하기 어렵고 C와 A는 기록과 검사라 강제하기 쉽다. 채팅에서는 지시가 합의 역할을 하고 "완료했습니다"가 제출, 확인, 반영을 한꺼번에 끝낸 것처럼 된다. C를 건너뛰면 A의 기준이 없다. A6, A7, A10, A13은 코드로 검사할 수 있다. A는 사람만 한다 [결정 15(2); 공리 A6; 대화 L3069].
- 사람 조작 상한 R-OP-1 (01 §3.5.2 [제안]): 정상 경로(변경 WorkUnit 하나의 C와 A)에서 결정 조작은 두 번 이하다. 합의 확정 1회, 결과 확인 1회.
  - R-OP-2: 합의 확정 질문을 하지 않는 경우는 두 가지다. (a) 사람이 이미 고른 선택지(`scope: Scope`)나 맡겨 둔 권한(Grant) 범위 안에 새 합의가 들어 있음을 커널이 증명할 때 [판정 J-133, J-90]. (b) 명확한 직접 지시의 echo. 미리보기(`composer.preview`)를 보이고, 그 지시를 보내는 것이 확정을 겸한다 [10 §3.6.7]. 자연어를 범위로 옮긴 것은 모델 제안이므로 확정 질문을 한다.
  - R-OP-3: 반영 항목 처리 방침은 결과 확인 한 번 안에서 전역 두 값으로 고른다. "에이전트가 모두 진행"(기본)과 "남는 제한은 미루고 나머지 진행"이다 [04 §3.12].
  - R-OP-4: 정상 경로 밖 결정 조작은 상한에 넣지 않고 사유와 함께 센다. 사유 일곱: `scope_expansion`, `rights_gate`, `correction_cycle`, `reinquiry`, `goal_change`, `contest`, `promotion`.
  - R-OP-5: 돌아보기 한 줄은 조작으로 세지 않는다. R-OP-6: 상한은 C/A에만 적용하고 원함 탐구 반응은 입력(I)으로 따로 센다.
  - 셈법: 질문 여러 개를 한 화면에서 답하면 질문 수만큼 센다. 결과 확인에 묶인 질문은 결과 확인 1회다. 초안을 고쳐 한 번 제출하면 1회다. 화면 경로와 보기는 세지 않는다. 정상 경로 여부는 저장하지 않고 이벤트 종류로 계산한다 [판정 J-76]. 계산 값은 `normalPath`, `opReason`, `editedDraft`다 [01 §3.5.2].
- 지표 CA-1~CA-7 (01 §3.5.3, 정본 `ca.*`는 16): CA-1 합의 우회·취소율 30% 초과면 C가 무겁다. CA-2 WorkUnit당 범위 초과 차단 중앙값 1 초과. CA-3 제출당 근거 없는 기준 평균 1 초과. CA-4 결과 확인까지 걸린 시간 중앙값 24시간 초과. CA-5 7일 넘게 열린 반영 항목. CA-6 정상 경로 조작 3 이상이 하나라도 있으면 설계 위반. CA-7 사유별 건수(기준 없음). 첫 14일 뒤 숫자를 조정한다 [OQ-03].

### 2.7 작업 합의(C)와 결과 확인(A)

- 작업 합의 `Agreement`(`ag`): 목적, 완료 기준, 범위, 금지 행동, 제출할 근거, 멈출 조건 [25 §3.2]. "계약", "Commitment"라 부르지 않는다. 합의 상태: `proposed`, `active`, `fulfilled`, `released`, `declined`, `expired`, `superseded` [25 §3.3]. 활성 뒤 첫 쓰기 전에 되돌릴 지점(커밋)을 만든다 [02 UC-07 단계 6; 13 §3.7.8].
- 결과 제출 `result.submitted`: 기준별 근거(관찰 id)와 함께 낸다. 근거 id가 실재하지 않으면 제출은 받고 그 기준을 "확인 못함"으로 강등한다 [02 UC-07 E2].
- 결과 확인 `Acceptance`(`ac`) [25 §3.2]: 기록 값 `accepted`, `conditional`, `revision_requested`, `rejected`, `criteria_wrong`. 명령 값(10 `result.accept`) `accept`, `accept_with_conditions`, `request_changes`, `reject`, `criteria_wrong`, 그리고 `reopenTo`.
- 화면 라벨: "결과 확인", "조건 붙여 확인", "수정 요청", "거절(해결 안 됨)", "기준이 틀림". "승인"과 단독 "거절" 버튼은 금지다 [25 §3.18; 25 §4.1 N-25].
- 결과 확인 대기는 "반영 완료"가 아니다. 반영 항목(`obligation`)이 모두 닫히거나 미뤄진 뒤에야 Concern을 닫는다 [02 AC-01-14]. 반영 항목의 닫힘은 근거 관찰로 커널이 하고, 전제 무효화는 사람만 닫는다 [02 UC-07 단계 10]. `integration.completed`는 남은 항목이 0일 때만 [V-INV-05].
- 조건부 확인의 조건은 같은 트랜잭션에서 미룬 반영 항목(다시 볼 조건 = 조건 문장)이 된다 [판정 J-125].

### 2.8 의존 규칙 (결정 15)

- (1) write·send에는 활성 작업 합의가 필요하다. (2) "완료"에는 결과 확인이 필요하다. (3) 판단 승격에는 I의 근거가 필요하다. 셋은 [결정 15]. (4) 하위 Concern을 재조합한 뒤 닫는다. (5) Goal 변경 때 사람 확인이 필요하다. 둘은 [제안] [25 §3.1].
- 가벼운 작업에도 (1)(2)가 적용되고, 줄인 형태(echo 합의, 한 화면 확인)로 지킨다 [판정 J-01].

### 2.9 능력과 행위자

- 원시 행동 여섯(`read`, `write`, `execute`, `send`, `spawn`, `ask`)과 기록 능력 다섯(`observe`, `propose`, `attest`, `accept`, `integrate`) [결정 4; 25 §3.1].
- 능력표 `CAPABILITY_TABLE`(08 §3.3.4)은 행위자별 능력을 고정한 표다. 커널의 자격 거부 판정 입력이다. 모드의 능력은 이 목록의 부분집합이다 [25 §3.1; 14 §3.10].
- A/P 판별: "일하는 도중 상황이 바뀌면 답도 바뀌는가?" 바뀌면 P(정책), 언제나 같으면 A(능력) [25 §3.1].
- 권한 레이어: effect class와 가역성 판별은 Helm 밖이다 [결정 2]. "되돌릴 수 있음"은 출처를 붙여 표시한다 [PR-12, X-09].
- 행위자 [02 §2.2]: `human`, `agent:work`, `agent:router`, `agent:verifier`, `agent:mediator`, `agent:observer`(뒤의 셋은 2단계), `runtime`, `kernel`, `scheduler`, `external:<name>`(2단계).
- 모델은 사람 결정을 만들 수 없다. 모델 도구 목록에 결과 확인 계열이 없다 [02 UC-07 E3; NFR-S-8; 결정 14].

### 2.10 모드와 다이얼 (결정 3, 17)

- 모드 = 루프 계획 기본값 + 능력 부분집합 + 다이얼 값. 페르소나가 아니다 [결정 3]. 에이전트에게 성격 문장을 주지 않는다 [25 §3.4].
- `ModeId` 여덟 [25 §3.4; 14 §3.10.2]: `orient`(복귀 안내), `investigate`(원인 조사), `deliberate`(선택 검토), `taste`(취향 탐색), `execute`(실행), `verify`(검증), `restructure`(구조 정리), `emergency`(비상).
- 모드는 Concern에 붙고 WorkUnit이 물려받는다. 라우터는 `mode.route`, 사람은 `mode.set`으로 고르고 기록은 `mode.assigned`다 [25 §3.4; 10 §3.11.11].
- 다이얼 `DIAL_KEYS`는 스무 개다. 저장 층은 `user`, `concern`, `instruction`이다. 층 1~3(시스템, 상황 유형, 모드)은 저장하지 않는다 [25 §3.4]. 키 형식은 `<묶음>.<이름>`이고 예외는 `planAuthoring`과 `assumptionDeferOnDowntime`이다 [25 §3.14].
- 예: `assurance.proof_burden`(`light`, `standard` 기본, `heavy`; 화면 "가볍게/보통/엄격"; Quick/Guided/Assured 이름은 보이지 않음) [OQ-12, 판정 J-12]. `inquiry.depth`(라운드 1~8). `question.threshold.c1`~`c3`(프리셋 `few`, `normal`, `many`는 다이얼 목록 밖). `inquiry.budget`(하위 호출, 시간, 비용 상한) [25 §3.4, §3.6].
- 다이얼은 불변조건을 끌 수 없다 [결정 17; 10 §3.6.4]. 알림 설정(`notifications.resultReview`: `none` 기본, `daily_digest`, `immediate`; `notifications.dndException`)은 의미 설정으로 다이얼과 구분한다 [결정 56, 59; 25 §3.10].

### 2.11 질문: 기록, 전달, 게이트, 혼자 정한 결정

- 기록과 전달을 나눈다. 질문 `Question`(`qs`)은 기록이고, 전달 방식은 별도다 [결정 12]. 방식은 즉시, 협상(기본), 중재, 예약이다 [결정 12; PR-06].
- 권리 게이트: 사람의 허락이 필요하다(send, 결과 확인, Goal 수정 등). 막는 것은 즉시 전달한다. 막지 않는 것은 기록은 즉시, 전달은 다음 작업 경계나 검토 창에 한다 [01 §3.7; 판정 J-132]. 만료가 임박하면 `interrupt`로 올린다 [결정 64].
- 정보 게이트: 임시 가정과 만료점을 가진다. 만료 때 가정이 확정되어 "에이전트가 정한 것"으로 남는다. 가정 확정은 기준을 확정하지 않는다 [02 UC-01 E4; 15 §3.6.7].
- 질문 조건은 AND가 기본이다 [결정 16]: c1 정책이 처리하지 못함, c2 결과가 실질적으로 바뀜, c3 지금 묻는 가치가 주의 비용보다 큼 [25 §3.5].
- 질문 사유 `QuestionReason` 일곱: `value_conflict`, `high_uncertainty`, `authority_boundary`, `disagreement`, `acceptance`, `integration`, `missing_context` [25 §3.5]. 질문 문장은 `text`, `whyNow`, `options`, `recommendation`, `strongestAlternative`, `unknowns`, `delayImpact`, `reviewTrigger`로 짠다 [25 §3.5].
- 같은 미해결 질문은 반복해 알리지 않는다. 같은 질문은 `dedupeKey`로 합친다 [X-11; 11 §3.5.5].
- 혼자 정한 결정 (결정 8, 불변조건 7): 모두 기록되고 이의를 걸 수 있다. 자율 결정에 `whyNotAsked`가 없으면 거부한다(`invalid.why_not_asked`) [10 §3.11.5]. 이의 뒤 자율 재결정은 하지 않는다 [V-AUT-02]. 이의는 명령 `decision.contest`, 이벤트 `objection.filed`다. 화면 이름은 "에이전트가 정한 것"(`SCR-AUTO`)이고 종류별로 접는다 [FX-08]. 진입 판정도 같은 방식으로 기록되고 `why_not_asked`는 "진입 판정은 정책으로 처리"다 [01 §3.6.3].
- 주의 예산 [01 §3.7 제안]: 기본 화면의 일상 도구 활동은 절반 이하다. 질문은 기본 3개를 펼치고, 권리 게이트는 접어도 개수를 보인다 [canon-3 §7.1 C3].

### 2.13 제품 원칙과 recognition over recall

- recognition over recall: 결정 18 본문에 나오는 문구다. "대안 2~3개를 던지고 고르게 하는 상호작용은 거부되었다... '모델이 초안을 쓰고 사람은 반응·수정한다'(recognition over recall)가 핵심 원칙이다." 25 §3.1은 "초안·반응 원칙"으로 부른다. 01 본문은 영문 문구 없이 PR-01·PR-02로 적는다.
- PR-01 원칙: 사람에게 빈칸을 채우게 하지 않는다. Goal, 작업 합의, 기준 후보, 질문 문장, 복귀 요약은 모델(또는 커널 투영)이 초안을 만들고 사람은 고치거나 확정한다. 승인 버튼만 주는 확인과 다르다 [25 §3.1; X-05, X-13].

## 3. 동작 흐름

### 3.1 진입 (01 §3.6)

- 범주는 문제의 모양으로 정하고 업무 분야로 정하지 않는다 [01 §3.6.1].
- E1 시작 시 진입 판정(화면 `RGN-COMPOSER`). E2 작업 중 승격 제안: 승격 신호가 나오면 "Concern으로 열까요?"를 정보 게이트 질문으로 협상 전달한다. E3 직접 지정: 조건과 무관하게 진입한다(`concern.opened`, origin `human_designated`). 강등: 단순하다고 확인되면 가벼운 작업으로 내린다. 강등도 혼자 정한 결정이다 [01 §3.6.2].
- 조건 EC-1 `goal_vague` 목표가 흐림, EC-2 `paths_diverge` 해법이 나뉨, EC-3 `taste_dependent` 취향에 달림, EC-4 `long_running` 오래 걸림, EC-5 `entangled` 얽힘 [01 §3.6.3; 14 신호 id].
- 규칙: 근거(`evidenceRefs`)가 있는 참 신호가 두 개 이상이면 진입한다. 근거 없는 참 신호와 "모름"은 세지 않는다. 제외 규칙(해 보고 결과를 보는 비용이 더 작음)은 진입 규칙보다 우선하되 EC-3이 참이면 무시한다. 직접 지정은 조건과 무관하다. 문턱 "두 개"는 고정이다 [OQ-04]. 판정은 `entry.evaluated`(`enter`, `suggest`, `skip`)로 기록한다.
- 가벼운 작업 [01 §3.6.4, 판정 J-01]: 보관 Concern 아래 WorkUnit. 상황 판정, 루프 계획, 탐구는 하지 않는다. write와 send는 직접 지시 echo로 합의를 충족하고, 완료는 한 화면 확인이다. 정책으로 결과 확인을 닫는 것은 MVP에서 쓰지 않는다 [OQ-15]. 예: "README 오타 고쳐 줘".
- 승격 신호 PS-1 같은 확인이 세 번 실패, PS-2 해법이 두 개 이상, PS-3 범위가 예상보다 커짐, PS-4 "잘 모르겠는데", PS-5 이유 없이 "뭔가 아니다" [01 §3.6.5]. 거절하면 같은 작업에서 다시 제안하지 않는다 [X-11, PR-06].

### 3.2 한 Concern의 정상 흐름 (01, 02 공통 골격)

1. 진입: E1 또는 E3로 Concern이 열린다. 판정과 지정이 기록된다.
2. O: 상황 판정(아홉 질문), 상황 유형, 루프 계획, 모드(`mode.assigned`)를 정한다. 방향이 정해졌으면 I를 건너뛰고 그 이유를 남긴다.
3. I(필요할 때): 탐구한다. 반응과 관찰을 쌓아 기준 후보를 만들고 기준 확인 질문을 정보 게이트로 보낸다.
4. C.commit: 합의 초안을 낸다. 사람이 `agreement.confirm`(고친 내용 `edits` 포함)으로 확정하면 WorkUnit이 시작된다. 확정 전 쓰기는 `toolcall.blocked`(`denied.agreement_required`)로 막힌다.
5. 실행: 합의 범위 안에서만 도구를 쓴다. 범위 밖이면 `workunit.scope_exceeded`로 선택 요청을 만든다.
6. 제출: 마무리 검사로 제출을 한 번 더 요청하고(최대 두 번, 그 뒤 `workunit.paused`), `result.submitted`로 기준별 근거를 낸다.
7. A.confirm: 사람이 `result.accept` 계열로 결과를 받아들이거나, 조건을 붙이거나, 수정을 요청하거나, 거절하거나, 기준이 틀렸다고 한다. 반영 방침(R-OP-3)을 함께 고른다.
8. 반영: 반영 항목을 처리한다. 남은 항목이 0이면 `integration.completed`.
9. A.reflect(선택): 돌아보기 한 줄. 조작으로 세지 않는다.
10. 닫힘: `concern.completed`. 미룬 항목은 다음 복귀 요약 맨 위로 올라간다.

### 3.6 UC-06 복귀 요약 (02 §3.9)

- 목표: 하루 이상 비운 뒤 5분 안에 목표, 바뀐 것, 위험, 지금 판단할 것을 원본 로그 없이 파악한다.

- 흐름: 열면 `SCR-BRIEF`가 열린다. 결정적 부분을 먼저 보내고 모델 문장은 나중에 채운다. 항목은 근거 참조를 갖고 `SCR-EVIDENCE`로 내려간다. "여기까지 봤음"으로 cursor를 옮긴다(`brief.acknowledged`). 열기만으로는 옮기지 않는다.
- 예외: 모델 문장 실패는 결정적 부분만 보이고 실패를 표시한다. 항목이 너무 많으면 접되 반대 근거와 이견은 접지 않는다.
- 수용 기준 요지: cursor는 사람 단위로 하나(AC-06-01). 이벤트 1,000개에서 결정적 부분 1초 이내(NFR-P-5). 권리 게이트가 맨 위(AC-06-06). qualified가 아닌 선택은 기준선으로 보이지 않는다(AC-06-07).

- FX-01 진입 판정이 틀림: 기록된 판정에 이의를 걸면 반대 경로로 바뀐다(14, 16).

- FX-03 결과 확인을 오래 미룸: 가정 확정으로 넘기지 않는다. "결과 확인 대기"로 남고, 이 결과에 기대는 작업은 대기하거나 임시 가정으로 진행한다. 복귀 요약 상단에만 보인다(11, 14).
- FX-04 일주일 이상 부재: 합의 범위 안에서만 진행. 정보 게이트는 만료점에서 가정 확정, 권리 게이트는 대기(11, 12).
- FX-05 원함 탐구 중 "오늘은 여기까지": 열린 기준 후보를 그대로 두고 멈춘다(15, 05).
- FX-06 말과 반응이 다름: `stated_vs_revealed`로 남기고 보여 준다. FX-07 "그냥 골라 줘": 사용자 지시로 기록하고 따른다.
- FX-08 정한 것이 너무 많음: 종류별로 접고 개수만 보인다(11, 16).
- FX-09 모델 비용 소진: 새 실행을 시작하지 않고 진행 중 WorkUnit은 현재 단계까지 간다(12).
- FX-10 데몬이 내려감: 아무것도 진행하지 않는다. 앱은 오프라인 표시와 읽기 전용 캐시를 쓰고, 재기동 뒤 크래시 복구와 중단 기간을 보인다(17, 12).
- FX-11 두 기기가 같은 질문에 답함: 먼저 받은 답만 받아들이고 나중 답은 `이미 답함`으로 거부한다(10, 19).
- FX-12 Helm 밖에서 파일을 고침: 실제 변경을 관찰로 남기고 그 파일에 기댄 판단은 낡음으로 표시한다. 사용자를 막지 않는다(12, 16).
- FX-13 Goal 없는 프로젝트: Goal 초안 카드(`이 Goal로 시작`, `고쳐서 시작`, `나중에`). 거부하지 않고 자리표시 Goal에 연결해 진행한다(08 E-02, 14, 04).
- FX-14 취향 작업에서 탐구를 건너뛰라고 함: 지시를 따르고, 결과 확인 기준에 선호 모델이 없음을 표시한다.
- FX-15 권한 레이어가 허락을 요구: 권리 게이트 질문을 연다. 합의가 권한 판정을 덮지 않는다(11, 13).
- FX-16 앱과 데몬의 프로토콜 버전이 다름: 연결하지 않고, 캐시된 투영을 읽기 전용으로 보이며 갱신을 안내한다(19, 20).
- FX-17 Mac이 잠든 중 즉시 전달 질문: 데몬은 기록하고 대기한다. 깨면 알린다(11, 20).
- FX-18 외부 효과가 불확실한 도구 실행 중 데몬 사망: 다시 실행하지 않는다. send나 네트워크면 확인 조회 후 판단 불가이면 권리 게이트. 효과가 없으면 실제 상태를 관찰로 남긴다(12, 13; 판정 J-05).
- FX-19 모델의 루프 계획이 의존 규칙을 어김: 한 번 돌려주고, 다시 어기면 코드가 계산한 계획을 쓰고 기록한다. 사람은 이의를 걸 수 있다(14, 10, 16).

### 5.2 유즈케이스 공통과 시나리오 (02 §4, §3.13, §3.10 E)

- CX-01 오래된 질문 카드에 답함: 답에 `basisSeq`가 있고, 바뀌었으면 `conflict.version_mismatch`로 거부, 이미 답했으면 `conflict.already_resolved`.
- CX-02 `ㅇ` 같은 무의미 입력: 확정과 거절은 받고, 무의미한 자유 입력은 비운 것으로 다룬다. 필수 의미(조건 등)가 비면 받지 않는다.
- CX-03 같은 시각에 질문 여럿: 질문함에 묶고 권리 게이트를 위로 올린다. CX-06 두 기기에서 같은 합의 카드를 고침: 먼저 받은 개정만 남고 다른 쪽은 충돌로 거부된다.
- CX-07 WorkUnit 상한(기본 3) 초과: 대기열에 들어가고 "대기 중(앞에 n개)"이 보인다.
- UC-10 변형: B1 데몬 비정상 종료는 진행 중 WorkUnit을 "중단됨"으로 정리하고 재개한다(확인된 이벤트 손실 0). B3 외부 행동이 불확실하면 다시 실행하지 않고 확인 조회 또는 권리 게이트(J-05). B4 모델 장애는 run을 `model_unreachable`로 끝내고 질문을 만들지 않는다.
- NFR-O-2 오프라인 중 사람 입력: 결정 입력은 보내지 않고 기기에 초안으로 보존한다. 자동 전송하지 않는다.
- UC-07 E5: 범위 밖 파일 변경은 관찰로 남기고 선택 요청을 만든다. 자동 되돌림은 13이 정한다.

### 5.3 비기능 요구 (01 §3.11, 제안, 실사용 14일 뒤 재검토)

- 응답: 사람 명령의 결과 표시 서버 p95 300ms 이하(NFR-P-1), 이벤트 도착 p95 500ms(P-2), 홈 2초(P-3), 이벤트 1,000개 재접속 3초(P-4), 복귀 요약 결정적 부분 1초(P-5), 즉시 질문 알림 5초(P-6).
- 가용성: 비정상 종료 뒤 첫 재시작 5초 이내, 연속이면 최대 60초, 30초 안에 복구(A-1). 호스트 재부팅 뒤 로그온 후 2분(A-3). 고가용성은 요구하지 않는다(A-5).
- 데이터: 수락한 명령과 이벤트는 손실 0(D-1). 서버 데이터는 마지막 백업까지, 백업 하루 1회 이상(D-3).
- 비용: 월 상한은 설치 때 묻고, 없으면 USD 50(가정, J-22). 80%에 알림, 100%에 새 실행 중지(C-1). 데몬 상시 대기 CPU 2% 이하, 메모리 1GB 이하(C-4).
- 보안: 데몬은 127.0.0.1에만 바인딩하고 공개 인터넷에 노출하지 않는다. 모든 리스너가 자격 증명을 요구한다([판정 46], S-2). 기기 토큰은 폐기하면 즉시 끊긴다(S-3). 비밀은 로그, 투영, 모델 컨텍스트, 앱에 들어가지 않는다(S-4). 도구의 쓰기는 허용 폴더 안이다(S-5). 웹과 도구 출력은 신뢰하지 않는 데이터다(S-6). send는 항상 권리 게이트다(S-7). 사람 결정은 앱 명령 경로로만 온다(S-8).
- 사용성: 동시 Concern 50개(U-1), 동시 WorkUnit 기본 3개(U-2), 알림에서 답까지 결정 조작 1회(U-7).

## 8. 헷갈리기 쉬운 점

### 8.1 비슷한 이름, 다른 대상

1. 원함 발견(동기, 결정 1), 원함 탐구(`I.want`, 루프), 원함(사용자의 말)은 다르다 [25 §3.1, §3.4].
2. 탐구 네 종류 `InquiryKind`(fact, want, possibility, outcome)와 루프 식별자 `I.fact`, `I.want`, `I.possibility`, `I.outcome`은 같은 네 이름이다. 종류는 탐구, 식별자는 루프다 [25 §3.4, §3.6].
3. "A"의 세 뜻: 공리 A1~A15, 루프 `A.confirm`·`A.watch`·`A.reflect`, 평면 능력 A(Authority). 25 §3.1은 "평면 A"로 구분한다.
4. "V"의 여러 뜻: 가설 V1~V9(01 §3.10.1), 사후 검사 V-INV-nn과 V-AUT, V-POL, V-PLAN, V-DEP, V-PRO(10·22). 가설 V1과 검사 V-INV-01은 다르다.
5. "H": 가설 H1~H10(foundations/08), 엔진 가설 H-I1~H-I4와 H-R1(15, "H·V와 겹치지 않는다" 25 §3.11), 06의 데몬 책임 라벨 H1~H8(25 N-32는 접두어를 바꾸라고 함).
6. 불변조건 번호는 v0.3 1~7(INV1~7), 원전 I1~I12, F01 1~8이 각각 다르다.
7. 결정 번호: 1~25는 2026-10-11 이전 결정이다(v0.3 이론과 구조). 26~37은 조정자 기본값이며 33·35는 사용자 확인 결정이다. 38 이후는 사용자 결정과 판정이다. `[판정 n]`(44~46)과 `[판정 J-nn]`(rulings)은 결정 번호가 아니다.
8. CA-n은 01과 16의 별칭이고 정본은 `ca.*`다. CT-n은 `entry.*`의 별칭이다.
9. "혼자 정한 결정"(결정 8, 08 `Autonomy`) = "에이전트가 정한 것"(화면 `SCR-AUTO`) = "자율 결정"(10, 11, 22 등). 화면에는 "자율 결정"을 쓰지 않는다 [25 §4.1 N-45].
10. "결과 확인"(A 루프, 레코드 `Acceptance`, 화면 `SCR-REVIEW`), "결과 제출"(작업 측 `result.submitted`), "완료 주장"(모델의 말), "반영 완료"(Concern 표시)는 다르다. 단독 "완료"는 전체 반영 뒤에만 쓴다 [25 §3.18].
11. 결과 확인 값 이름: 명령 `accept_with_conditions`, 기록 `conditional`, 화면 "조건 붙여 확인". "조건부 확인"은 옛 표기다 [25 §4.1 N-25; 03 §3.3.1].
12. "거절": 커널 거부(`rejected`, `command.rejected`)와 결과 확인의 "거절(해결 안 됨)"은 다르다. 단독 "거절" 버튼은 금지다.
13. "권리 게이트"에는 막는 것과 막지 않는 것이 있다. 결과 확인과 Goal 수정은 막지 않는다. send는 막는다 [01 §3.7; 02 UC-07 A4].
14. "정보 게이트"의 가정 확정은 기준을 확정하지 않는다 [15 §3.6.7].
15. 질문 상태 `delegated`(맡김)는 사람이 명시적으로 고를 때만 쓴다. 03과 05 목록에는 아직 없다 [25 §4.1 N-12; 판정 J-131].
16. "가벼운 작업"(light work), "일반 세션"(14 §3.14.2, 01이 같은 대상으로 명시), Quick·Guided·Assured(v0.2 이름, 화면에 보이지 않음).
17. 증명 부담 값 `light`, `standard`, `heavy`의 화면 이름은 "가볍게", "보통", "엄격"이다. 기본은 보통이다.
18. 상황 유형(`SituationType`, 다섯 값), 상황 판정(`SituationAssessment`, 레코드), Concern 종류(`ConcernKind`, 여덟 값)는 다르다.
19. "복잡"(`complicated`)과 "복합"(`complex`)을 바꿔 쓰지 않는다 [25 §3.1].
20. 모드 `execute`("실행")와 루프 `C.commit`("약속 실행")은 다르다. 모드는 페르소나가 아니다. "역할", "프로필"이라 쓰지 않는다 [25 §3.4].
21. 발산과 수렴(원전 Double Diamond)은 모드가 아니다 [25 §3.4].
22. 다이얼(`DIAL_KEYS`), 질문 빈도 프리셋(`few`, `normal`, `many`, 입력 편의), 알림 설정(`notifications.*`, 의미 설정)은 구분한다 [25 §3.4, §3.10].
23. Concern 상태 집합 세 개(저장, 표시, 오케스트레이션 `ConcernView`)는 이름이 일부 겹치지만 다른 집합이다 [25 §3.3].
24. WorkUnit 종류 `workKind`(inquiry, probe, change, integration)와 WorkUnit 목적 `WorkUnitPurpose`(18)는 다르다. 루프 식별자도 18개여서 숫자만 같다.
25. 이벤트 `loop.transitioned`(09)와 명령 `loop.transition`(10). 명령 `mode.set`(사람)과 `mode.route`(라우터), 기록은 `mode.assigned`다.
26. 명령 `decision.contest`(10), 이벤트 `objection.filed`(09), 메서드 `objection.file`(19). 옛 이름 `contest.file`은 쓰지 않는다 [25 §4.1 N-34].
27. 알림 강도 세 값은 `interrupt`, `notice`, `digest`다. 옛 이름 `notify`는 쓰지 않는다 [25 §4.1 N-17]. "digest"는 알림 강도, 판정 갈래, 관찰 통합 보고로 세 뜻이다 [25 §3.18].
28. "범위"는 맡긴 범위, 근거 범위, 연결 범위, 이벤트 소속이 있다. "예산"은 탐구 예산, 주의 예산, 관찰 비용 예산, 월 비용 상한이 있다. 앞말을 붙인다 [25 §3.18].
29. "경계"는 작업 경계(`boundary.reached`)와 경계 항목(`bd`)이 다르다 [25 §3.18].
30. "작업 합의"는 "계약"이라 쓰지 않는다. Goal에 "목표", "목적", "Purpose"를 쓰지 않는다. 합의의 `purpose`와 Goal은 다르다 [25 §3.2].
31. 01 §3.1.6의 "최상위 목적"은 원전 foundations/00 §1의 목적이며 Goal이 아니다.
32. "판단"은 Finding만 가리킨다. 에이전트 문구는 "정했습니다", "추천합니다"다 [25 §3.18].
33. "선택"은 사람이 정했거나 정책이 적용된 Choice만 가리킨다. 추천은 선택이 아니다 [25 §3.18].
34. "이의"는 사람만 건다. 검증 에이전트는 반대 근거와 증언을 낸다 [25 §3.18].
35. "확인"은 여러 곳에 쓴다(결과 확인, 합의 확인, 혼자 정한 결정 확인, 기준 확인, 복귀 점검). 단독 "확인" 버튼은 쓰지 않는다 [25 §3.18].
36. "투영"은 정본을 읽어 만든 화면이나 컨텍스트에만 쓴다. Method Transfer와 예측에는 쓰지 않는다 [결정 13; 25 §3.18].
37. "정본"과 "기준 원본"은 같다. Helm 이벤트 로그다. pi 세션 파일과 pi-durable은 정본이 아니다 [결정 29].

## 9. 미결과 이후 단계로 미룬 것

### 9.1 미결 사항 (01 §7)

- OQ-01 원함 탐구를 MVP에 넣음(추천 적용). OQ-02 2회 상한은 정상 경로에만 적용(추천). OQ-03 CA 숫자는 첫 14일 뒤 조정. OQ-04 진입 문턱은 고정, CT 지표를 본 뒤 재검토.
- OQ-05(해소, J-01) 가벼운 작업은 보관 Concern 아래 WorkUnit. OQ-06 월 비용 상한은 사용자가 정하고, 답이 없으면 USD 50(가정, J-22). OQ-07 MVP의 send는 git push만, 항상 권리 게이트.
- OQ-08(해소, J-11) 한 번에 구현하고 2단계 기능은 G1 기록 전까지 기본값을 끈다. OQ-09 V1 비교는 G0 비교 조건이 첫 자료다.
- OQ-10(해소, 결정 42, 47~49) 모바일은 2단계 PWA, Web Push, `interrupt`·`notice`만 푸시, iOS 26 이상. OQ-11 한 홈에 프로젝트 필터. OQ-12(해소, J-12) 증명 부담 다이얼.
- OQ-13 이미지 자극은 MVP에서 사용자 파일과 웹 레퍼런스다. 이미지 생성은 2단계 후보(pi-ai 지원은 07이 확인).
- OQ-14(해소, J-01) 가벼운 작업에도 (1)(2)를 줄여 적용. OQ-15(해소, J-89) 정책으로 결과 확인을 닫는 것은 2단계 이후 검토. OQ-16(해소, 결정 54) 하네스 동기화는 범위 밖. OQ-17(해소, 결정 55, J-190(1)) 웹 도구는 MVP에 넣는다.

### 9.2 단계와 증거 관문 (01 §3.8)

- MVP: 데몬, 데스크톱 앱(macOS, Windows, Tailscale과 SSH), 자체 런타임, 커널, C/A, 복귀 요약, 사실 탐구, 원함 탐구, 질문함, 에이전트가 정한 것, Goal 정제, 루프 계획 혼합, 웹 읽기와 검색, `grep` 확장, 해시라인 편집, 브라우저(후반), 지표 리포트.
- 2단계: 휴대폰(PWA), 결과 확인 알림 설정, 가능성 탐구(Method Transfer), 결과 탐구, 탐침형 C, 지속 관찰형 A, 발산 서브시스템 전체, 관찰 에이전트, 검증 에이전트, 중재자, 기대 레코드, 다이얼 전체 노출.
- 3단계: 구조 루프(S), 비상 합의, 혼란 분해, Helm TUI(SSH와 pi-tui). 이후: 외부 런타임 어댑터, Tailscale 없는 기기 접속, 컴퓨터 사용과 구조 검색·편집 도구, LSP.
- G0(원함 탐구를 커널에 연결하기 전): 실제 흐린 작업 다섯 개(취향형 둘 이상)로 `just eval-inquiry`를 돌리고, 보기 전과 본 뒤의 목표와 완료 기준, 변화, 피로를 기록한다. 변화가 1건 이하면 발산 설계를 다시 본다(15 소유).
- G1(MVP 실사용 14일 뒤): G1-1 24시간 이상 부재 뒤 복귀 3회, 원본 로그 없이 네 질문에 답하고 정정은 복귀당 2건 이하. G1-2 CA-6 위반 0, CA-1 30% 이하. G1-3 취향형 작업 1건 이상, 선호 모델이 완료 기준으로 쓰이고 사용자 평가가 남음. G1-4 고친 기록 1건 이상, 처음부터 쓴 기록이 더 적음. G1-5 "다음에도 쓰겠는가"와 16 §3.27.4 자기보고. 모두 통과하면 2단계, 일부 미통과면 범위 조정, 원함 탐구나 C/A가 쓰이지 않으면 제품 정의를 다시 본다.
- G2(2단계 14일 뒤): V6 채택률, 관찰 에이전트 제안 채택률, 질문 지표, 피로 평가(16 소유).
- 관문 기록은 "Helm 사용 평가" Concern으로 남긴다 [제안]. 긴장: 브리프 §1은 한 번에 구현이고, 관문은 기능 켜는 순서로 지킨다 [제안]. 01 §3.8.4가 이 긴장을 최종 보고의 "브리프에 대한 이의"에 적었다고 하나, 그 최종 보고는 이 pack이 읽지 않았다.
