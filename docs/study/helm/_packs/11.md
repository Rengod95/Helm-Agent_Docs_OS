## 1. 이 노드가 답할 질문

> 관찰 에이전트는 무엇을 입력으로 받아(Helm 기록, 허용된 외부 세션 로그, 결정 35) 무엇을 만들고(제안, 이의, 지표), 언제 돌며(observer_cycle 타이머), 결과가 어떻게 사용자에게 보이는가? 지표 정의와 계산 방식, 혼자 정한 결정의 확인·이의(objection.filed 등), 장기 관찰·제어 공간(결정 10)과의 관계, 제한·예산은?

질문 전제를 원문 기준으로 바로잡는다.

- **관찰 에이전트는 이의를 만들지 않는다.** `objection.filed`의 행위자는 `human`뿐이다(09 카탈로그, `objection.filed` 행). 관찰 에이전트의 능력은 read·spawn·observe·propose이고 이의 명령이 없다(§3.4.1). 관찰 에이전트가 이의와 관련해 하는 일은 두 가지다. 이의 이벤트를 지표 원천으로 읽는 것(§3.22.3, §3.23.2·§3.23.5), 이의율이 높은 종류에 묻기 정책 수정안(D10)을 내는 것(§3.10.1).
- **타이머 이름은 `observer.cycle`이다.** 12의 `runtime_timers`에 있고 DB 종류 값은 `observer_cycle`이다(12 매핑 표). 기본 cron은 `0 18 * * *`, 사용자 시간대, single-flight다(§3.3.1 T3).
- **"제안"은 관찰 에이전트가 쓰는 정본 레코드 이름이 `PolicyProposal`(`pp_`)이다.** 제안 종류는 13가지다(§3.12.1).

## 2. 핵심 개념

### 2.1 주체와 경계

- **관찰 에이전트(`@helm/observer`)**: Helm 기록과 허용 폴더의 외부 세션 로그를 읽어 반복 패턴을 찾고 수정안을 제안하는 별도 프로세스. 쓰기 권한이 없고, 제안은 커널 명령으로만 제출한다. 근거: [결정 14] 커널 원칙(모델은 제안하고 커널이 상태를 바꾼다), [결정 4] 능력 표. 출처 §1.1, §2.1, §3.1.3.
- **일회성 자식 프로세스 (OB-1, OBS-ADR-1)**: 데몬이 트리거마다 띄우고 작업 하나를 끝내면 내려간다. 상주하지 않는다. 기본은 `child_process.fork()`와 Node IPC이고, 격리 실행을 켜면 일회성 `systemd-run --user` 서비스다. 배치 A(데몬 안 비동기 task)는 큰 로그 파싱이 데몬 메모리와 비밀을 공유하므로 기각했고, 배치 C(별도 상주 서비스)는 제출 경로가 결국 데몬을 거치므로 기각했다. 출처 §3.2.1, §3.2.2.
- **관찰 실행(observer run, `or_`)**: 프로세스가 떠서 작업 하나(`scan`·`analyze`·`effect`·`digest`·`evaluate`·`rebuild`)를 끝내고 내려가는 단위. `runKey`로 식별하며 `or` 접두사는 08에 있다(판정 J-113). 실행 수명은 `observer_run.started`·`.completed`·`.failed`로 남는다. 출처 §1.5, §3.3.2, 08 §3.2.2 표.
- **감독기(`observer-supervisor`)**: 데몬 안의 구성 요소(06 DR-8). 트리거 판정, fork, 대기열, 시간 초과, IPC 처리, 2차 마스킹, 커널 제출 대행을 맡는다. 출처 §3.2.1, §3.4.2.
- **능력 (결정 4)**: `read`(기록만), `spawn`(데몬 경유 하위 모델 호출만), `observe`(보고 제출), `propose`(P 수정안, 절차 후보, 관찰 주석). `write`·`execute`·`send`·`ask`·`attest`·`accept`·`integrate`는 없고 커널이 자격 거부한다. 출처 §3.4.1.
- **관찰 보고는 E 관찰이 아니다**: 관찰 에이전트의 집계는 기록을 다시 읽어 만든 파생 값이다. 작업 에이전트가 이를 근거로 판단을 승격하지 못하도록 별도 종류 `observer_report`로 둔다. 출처 §3.4.1.
- **모델 호출 경로 (OB-3, OBS-ADR-2)**: 관찰 프로세스는 비밀 값을 갖지 않는다. 모델 호출은 `llm.complete` IPC로 데몬을 거치고, 데몬이 예산 계정 `observer`를 집행하고 2차 마스킹을 한다. 모델은 도구가 없고 출력은 고정 스키마 JSON 하나다. 출처 §3.2.4, §3.12.3.

### 2.2 입력

- **Helm 기록**: 정본 이벤트 전체와 투영. 읽기 전용 SQLite 연결(`openReader`, `query_only`)로 읽는다. 패턴 탐지 입력에서는 관찰 에이전트 자신의 이벤트, `policy_proposal.*`, `observer_run.*`, 범주 `measurement` 이벤트를 뺀다(자기 재귀 방지). 지표 계산에는 포함한다. 출처 §3.5.1, §3.6.2, OB-T20.
- **외부 세션 로그 (결정 35, 입력 단계 I1)**: pi·Claude Code·Codex 세션 파일 가운데 세션 cwd가 허용 폴더 아래인 것. 허용 폴더는 `observeExternalSessions = true`인 프로젝트의 `rootPaths`이고, 기본은 꺼짐이며 사람이 프로젝트 설정에서 켠다. 경로 비교는 양쪽 `realpath` 후 접두사와 구분자로 한다(`/a/b`는 `/a/bc`의 상위가 아니다). 판정 J-08. 출처 §1.5, §3.5.1, OB-T09.
- **Mac 세션은 보이지 않는다 (AS-3)**: `~/projects`만 동기화되므로 Mac에서 연 세션은 대상 밖이다. 평가 보고에 "서버 밖 작업은 관찰되지 않음"을 항상 적는다. 출처 §3.5.1, §4.2.
- **소스별 상태**: pi는 `v1.1.0` 기준 형식을 확인했다(판정 44). Claude Code는 2026-10-11에 파일 목록과 줄별 최상위 키만 확인했고 본문은 읽지 않았으며, 형식은 가정이다(AS-1). Codex는 이 서버에 세션이 없어 확인하지 못했고, 픽스처 적합성 테스트를 통과하기 전까지 꺼 둔다(AS-2, OQ-16-09). 출처 §3.6.3~§3.6.5.
- **확장 단계 I2~I4 (§3.5.2)**: I2 Git 상태와 `justfile` 실행 로그(읽기 전용), I3 Mac 수집기(마스킹 후 전송), I4 셸 히스토리(사용자 명시 요청 때만). 각 단계는 앞 단계 채택률과 효과가 확인된 뒤 사람이 켠다. 관찰 에이전트는 다음 단계를 켜자는 제안을 하지 않는다(§3.12.4). 입력 단계 번호 I1~I4는 01의 제품 단계와 다른 번호다.
- **설정의 출처 (§3.5.3)**: 운영 설정은 `helmd.toml`의 `[observer]` 절(다음 회차부터 반영, 06 §3.10). 허용 폴더는 Project 레코드에서 온다. 바꾸는 주체는 사람이고 바뀐 키는 `setting.changed`로 남는다.
- **입력에서 빼는 것**: 허용 폴더 밖 cwd의 줄, 기본 `excludedGlobs`(`**/.helm/private/**`, `**/secrets/**`) 경로를 대상으로 한 도구 결과는 본문 없이 바이트 수만 남긴다(§3.5.3, §4.2).

### 2.3 마스킹, 신뢰, 탐지, 분류

- **마스킹 2단계 (§3.8.1)**: 1차는 관찰 프로세스가 정규화 직후, 캐시에 쓰기 전에 규칙(MK-01~MK-13)과 엔트로피 검사로 한다. 2차는 데몬이 `llm.complete`와 `kernel.submit` 요청을 받을 때 SecretStore에 등록된 값을 완전 일치로 가린다(판정 45). 2차 적중이 0보다 크면 1차 규칙 누락이므로 경고하고 그 후보는 이번에 제출하지 않는다.
- **마스킹 토큰 (§3.8.4)**: `[REDACTED:<kind>:<h8>]`. 관찰 입력의 `h8`은 `HMAC-SHA256(salt, 원래 값)`의 앞 8자다. 같은 값은 같은 토큰이 되어 반복 패턴은 찾되 값은 알 수 없다.
- **출처 등급 (§3.9.2)**: `human`(사용자 메시지, 발췌 400자까지), `agent`(어시스턴트 텍스트, 400자까지), `tool_output`(도구 결과와 웹 내용. 모델 입력에 넣지 않고 오류 서명과 바이트 수만), `derived`(코드가 만든 템플릿·서명·수치).
- **신뢰할 수 없는 로그 (§3.9.1, §3.9.3)**: 로그 내용은 데이터로만 다룬다. 로그 속 지시문 패턴이 있으면 `suspiciousInstruction`으로 표시하고 발췌 후보에서 뺀다. 제안에는 `flags.injectionSuspect`를 남긴다. 제안은 적용 전에 반드시 사람이 본다.
- **패턴 탐지기 D1~D13 (§3.10.1)**: 모두 결정적 코드다(같은 입력이면 같은 출력). 주요 탐지기는 다음과 같다. D1 반복 도구 순서(길이 2~6 n-gram, 지지도는 세션 수), D2 반복 셸 명령(`commandTemplate`), D3 같은 파일 반복 읽기, D4 실패 후 재시도 고리, D5 사용자 정정, D6 토큰 과다 턴, D7 버린 분기, D8 같은 방식으로 풀린 Concern(3개 이상), D9 Helm 밖 변경, D10 묻기 정책 신호, D11 합의·확인 마찰, D12 학습 신호(near miss, 설명되지 않은 관찰, 지역 적응), D13 렌즈 사용.
- **문턱 (§3.10.2, [제안])**: 세션 3 이상, 서로 다른 날 2 이상, 28일 창, 절감 추정 2만 토큰 또는 사람 조작 3 이상, 실행당 후보 12. 미달하면 `below_threshold`로 캐시에만 둔다.
- **서명과 패밀리 (§3.11)**: 서명은 `sha256:` + 정규화 JSON(detector, kind, core)의 해시다. `core`는 경로·숫자·비밀을 치환한 템플릿이고 `scope`는 서명에 넣지 않는다. 규칙 버전 `v`가 다르면 기각 기억을 적용하지 않는다. 패밀리는 core의 자카드 유사도 0.8 이상이고 탐지기가 같을 때 묶인다. 모델의 `sameIntentAs`는 화면 참고용이고 억제에 쓰지 않는다.
- **제안 종류 13가지 (§3.12.1)**: `procedure`, `skill`, `script`, `tool_promotion`, `guard`, `policy`, `agreement_template`, `context`, `routing`, `entry_criteria`, `divergence_category`, `lens`, `demotion`. 질문은 두 가지다. 무엇을 바꾸는가(Context, 작업 합의, 정책 P, 절차·도구)와 어떤 형태로 굳히는가(판단이 필요하면 스킬, 결정적이면 스크립트, 지켜야 하면 정책 검사).
- **탐지기별 허용 판정 (§3.12.2)**: 모델은 탐지기에 허용된 `verdict`만 고를 수 있다. 예를 들어 D1은 `skill`·`script`·`procedure`·`coincidence`, D10은 `policy`만 허용되고 방향은 코드가 정한다. `coincidence`(우연)는 제출하지 않고 캐시에만 남긴다.
- **모델 판정 (§3.12.3)**: 후보마다 독립 호출한다(서로의 결과를 보지 않는다). `temperature 0`, 입력 해시 캐시(`cacheKey`), 실행당 동시 호출 4개. 출력 스키마가 틀리면 재요청하고, 그래도 실패하면 `draft_failed`다. 재요청 횟수는 16이 1회, 12 §3.14.6이 2회라고 적어 서로 다르다(§8 참고). 모델이 쓴 수치는 버린다(§3.9.1 원칙 3).
- **관찰 에이전트가 내지 않는 제안 (§3.12.4)**: 자기 입력 범위·능력·예산·탐지 문턱·정정 어휘, 불변조건 1~7이나 의존 규칙(결정 15)을 약하게 하는 변경, 권리 게이트를 줄이는 변경, 다른 행위자의 능력표 변경. 커널도 이런 `policy` 패치를 자격 거부한다(V-POL-01).
- **초안 lint L1~L7 (§3.9.5)**: 제출 전에 코드로 검사한다. 비밀 재검사, URL 호스트가 후보 특징에 있는지, 위험 명령(`curl … | sh`, `rm -rf`, `sudo`, `chmod 777`, `ssh`, 네트워크 업로드)은 항상 실패, 작업 루트 밖 경로, `tool_output` 원문과 40자 이상 겹치기, 길이 상한(제목 80자, 요약 400자, 본문 4,000자), 형식별 필수 절. 하나라도 걸리면 `draft_rejected`로 보고에 남긴다.
- **절감 추정 (§3.13.3)**: 코드 식으로 계산하고 화면에 "추정"과 계산식을 함께 보인다. `script`는 창 안 토큰 합 × 0.7 [가정]에 재시도 고리 토큰을 더한다. `skill`·`procedure`는 정정·질문 수를 쓴다. `policy`는 질문 전달 수 × 임시 가정 비율 또는 이의 수다.

### 2.4 제안과 사람의 결정

- **제안 레코드 (§3.15.2)**: `PolicyProposal`(`pp_`, 08 §3.19.2). 정본 이벤트 `policy_proposal.submitted`의 payload는 `PolicyProposalCore`다. 초안은 마스킹한 JSON blob(`application/vnd.helm.proposal-draft+json`)으로 두고 `preview`는 `title`이다. 근거 `refs`는 최대 20개이고 나머지는 개수만 센다.
- **기각 기억 (OB-5, §3.14.1)**: 사람의 결정은 정본 이벤트에 있다. 관찰 실행은 투영 `observer_proposal`에서 서명·패밀리별 최신 결정을 얻는다. 관찰 캐시를 지워도 같은 결과가 나와야 한다(OB-T16).
- **재제출 규칙 (§3.14.2)**: 기각 사유 `coincidence`는 같은 패밀리를 90일 억제한다. 일반 기각은 근거가 기각 때의 2배 이상이고 30일이 지났을 때만 다시 올린다(이전 기각 id를 화면에 표시). `family_forever`는 영구 억제이고 설정에서 풀 수 있다. 커널이 거부한 제안은 같은 서명을 7일 뒤에야 다시 낸다.
- **근거 갱신 (§3.14.3)**: 열린 제안에 근거가 더 쌓이면 새 제안을 만들지 않고 `evidence_updated`로 근거 수와 최근 참조만 갱신한다. 사람에게 다시 알리지 않는다.
- **상태 기계 (§3.15.3)**: `open` → `accepted`·`dismissed`·`deferred`. `accepted` → `applied`(설정 종류) 또는 `applying`(파일 종류, 적용 Concern 열림) → `applied`(효과 측정 중) → `reverted`(사람). `withdrawn`(근거 소실·대체·대상 없음)과 `expired`(60일 결정 없음)도 끝 상태다. 채택·기각·나중에는 사람만 할 수 있다.
- **채택 후 적용 경로 (§3.16)**: `policy`(다이얼, 라우팅, 진입, 정책 규칙)는 채택과 같은 트랜잭션에서 커널이 적용한다. 커널은 패치의 `from`이 현재 값과 같은지 먼저 확인하고, 다르면 "제안 이후 설정이 바뀜"으로 거부한다. `agreement` 템플릿도 같은 경로다. `procedure`는 `procedure.adopted`(초기 `trust: trial`)로 등록한다. 렌즈·발산 범주는 15 데이터를 바꾼다. 스킬·도구·컨텍스트 제안은 **적용 Concern**을 연다. 그 안에서 작업 에이전트가 작업 합의(C)를 거쳐 파일을 바꾸고 사람이 결과 확인(A)을 한다. 관찰 에이전트는 어느 경로에서도 파일을 쓰지 않는다(OB-6).
- **채택 명령 자체가 사람의 결정이다 (판정 J-74)**: 제안마다 권리 질문을 따로 만들지 않는다. 제안은 `SCR-OBSERVER`와 복귀 요약의 "관찰 에이전트" 절로만 전달한다.

### 2.5 효과 측정과 결과 전달

- **효과 측정 (§3.17.1~§3.17.3)**: 적용 시각 `t0`부터 7·14·28일에 체크포인트를 잰다(부족하면 56일까지 연장). 기준선은 제출 전 28일이다. 활동량 차이는 활동 시간당과 세션당으로 나눠 보정한다. 판정 규칙은 다음과 같다. 두 표본 합이 6 미만이면 `inconclusive`, 품질 보조 지표가 0.2 이상 나빠지면 `harmful`, 주 지표 상대 변화가 −0.2 이하이고 품질 악화가 0.1 미만이면 `effective`, 그 밖은 `ineffective`다.
- **효과 뒤 동작**: `ineffective`나 `harmful`이면 다음 `analyze`가 `demotion` 제안을 만든다. `harmful`은 제안 화면 맨 위에 둔다. 절차는 `trial` → (효과 `effective` + 사람 확인) → `trusted`로 바뀌고 `procedure.trust_changed`로 남는다.
- **통합 보고(다이제스트, §3.18.1)**: 세션별 상태(`blockedOn`은 코드 판정: `question`·`error_loop`·`scope_block`·`user_absent`), 외부 변경 수(D9), 새 제안 수, 관찰 실행 자신의 비용을 담는다. `oneLine` 요약만 모델이 쓰고 끌 수 있다. 요약은 외부 세션의 사람·어시스턴트 발췌로만 만든다.
- **사용자에게 보이는 경로 (§3.18.2, 04 §3.18, §3.24.2)**: (1) 복귀 요약의 "관찰 제안 n" 절(기본 접힘). (2) 제안함 `SCR-OBSERVER`(내비게이션 6번, Mod+6, `G O`). 목록에는 종류, 제목, 추정 절감과 식, 근거 수, 주입 의심 경고가 보이고, 동작은 적용·고쳐서 적용·기각(사유 선택, "다시 보지 않기")·미루기다. (3) 홈 경고 띠: 연결되지 않은 변경 > 0, 사라진 이의 > 0, 정상 경로 조작 위반, 해로움 판정 > 0일 때만. (4) 평가 화면 `SCR-METRICS`와 복귀 요약 맨 아래 "2주 평가 준비됨" 카드. (5) `harmful` 판정 제안은 다음 복귀 요약의 "확인하면 좋은 것"에 올린다.
- **보이지 않는 곳**: 작업 중인 Concern의 대화와 컨텍스트에는 넣지 않는다(E1-088). 작업 에이전트의 투영에도 넣지 않는다(OB-8). 질문 레코드로 만들지 않아 묻기 다이얼의 대상이 아니다. 관찰 결과는 알림을 만들지 않는다(결정 48의 푸시 대상이 아님, §2.1 표).

### 2.6 지표

- **지표(metric)와 ID (§1.5, §3.21, §3.23 머리)**: 정본 이벤트에서 코드로 계산하는 결정적 투영이다. 커널 판정, 런타임 루프, 다이얼에 자동으로 들어가지 않는다(OB-7). ID 형식은 `<묶음 접두사>.<이름>`이다(예 `ca.agreement_bypass_rate`). 01이 붙인 별칭(예 `CA-1`)은 따로 적는다. OPD+C 지표는 `opdc.o/p/d/c.*`이고, 14 루프 계약의 의무 ID는 `opdc:<기준>.<이름>`(콜론, 판정 J-149)이라 겹치지 않는다.
- **묶음 접두사 (§2.6 `MetricDef.group`)**: `opdc`, `a12`, `ca`, `q`, `ad`, `entry`, `inq`, `out`, `int`, `stale`, `ctx`, `sit`, `s`, `want`, `draft`, `exp`, `obs`, `proc`, `cost`, `ext`, `rt`, `push`, `device`.
- **지표 사실(metric fact) (§3.22.2)**: 이벤트 하나에서 뽑은 측정 단위 값. 필드는 `kind`, `sub`, `at`, `value`(기본 1, 기간이면 ms), `dims`, `sourceEventSeq`, `stream`이다. `id`는 `${sourceEventId}:${kind}:${n}`로 멱등이다(같은 이벤트를 두 번 넣어도 중복이 없다, OB-T21).
- **지표 값(MetricValue) (§3.22.2)**: `value`(표본 부족이면 null), `numerator`·`denominator`, `n`, `breakdown`, `evidence`(원천 seq 최대 50개).
- **지표 정의(MetricDef) (§3.22.2)**: `id`, `aliases`, `group`, `title`, `unit`(`count`·`ratio`·`ms`·`turns`·`tokens`·`usd`·`score`·`per_hour`), `direction`(`lower_better`·`higher_better`·`target_zero`·`informational`), `window`(`1d`·`7d`·`14d`·`28d`·`per_return`·`cumulative`), `minSample`, `reviewSignal`, `pairedWith`, `hypotheses`, `defVersion`, `compute(facts, window)`.
- **표본과 검토 신호 (§3.21 원칙 5·7, §3.23 머리)**: 비율 지표의 기본 `minSample`은 5, 중앙값 지표는 3이다. 표본이 모자라면 값 대신 "표본 부족(n/필요 수)"을 보인다. 검토 신호는 [제안] 초기 가설값이고 성공·실패 판정이 아니다. 첫 14일 기준선 뒤 사람이 고친다(OB-12).
- **쌍으로 보기 (§3.21 원칙 4)**: 한 방향만 좋아지는 지표는 짝 지표와 함께 본다. 예: 질문 수 감소는 가정 확정 후 이의율과, 결과 확인 시간 감소는 확인 후 재작업률과 함께 본다. 지표 고착(Goodhart)을 줄이기 위한 규칙이다.
- **활동량 보정 (§3.21 원칙 9)**: 횟수 지표는 활동 시간당이나 Concern당으로 병기한다.
- **공통 정의: 활동·부재·복귀 (§3.23.1)**: 활동 구간은 어느 기기든 `presence.changed`가 `active`인 구간의 합집합이다(데스크톱 5분, 휴대폰 2분 문턱은 14 §3.13.8 파생 함수를 따른다). 부재는 활동 사이 빈틈이 4시간 이상인 것이다. 복귀 에피소드는 부재 뒤 첫 활동 시작이고, 장기 복귀는 부재 24시간 이상이다(H1 측정 대상). 첫 유효 행동은 복귀 뒤 처음 받아들여진 `human_op`(보기는 제외)이다.
- **계산 흐름 (§3.22.1, §3.22.4)**: 정본 이벤트 → 데몬의 커밋 뒤 소비자 `metrics`(09 §3.11.1 6번, 커서 `consumer_cursors.metrics`) → `extractFacts(event, lookup)`(순수 함수, `@helm/observer/metrics`) → `metric_fact`. 화면 요청 시 `aggregate(metricDef, window)`를 계산해 19 `metrics` 뷰로 주고 5분 캐시한다. 매일 04:00 T4에 `metric_snapshot`(1d·7d·14d·28d)을 만든다. 14일마다 T6 `evaluate`가 평가 보고를 `observer_report.recorded { form: "evaluation" }`로 남기며 그 시점 값으로 동결한다.
- **관찰 프로세스는 지표 테이블을 쓰지 않는다 (§3.22.1)**: 외부 세션에서만 얻을 수 있는 값(D9 `outside_changes`, 채팅 기준선 `baseline`)은 관찰 프로세스가 `observer_report.recorded`로 제출하고, 소비자가 그것을 사실로 바꾼다. 쓰기 트랜잭션 안의 core 투영기는 지표 테이블을 건드리지 않는다. 쓰기를 늦추지 않기 위해서다.
- **지연 상한 (OQ-16-17)**: 커밋 알림마다 처리하되 한 번에 500건까지다. 밀리면 다음 틱으로 넘기고, 화면은 `asOfSeq`로 늦음을 보인다.
- **재구성 (§3.22.1, OB-T26)**: 투영을 재구성하면 지표 테이블도 비우고 `metrics` 커서를 0으로 돌려 처음부터 다시 만든다.
- **정의 버전 (§3.21 원칙 6, §3.22.4)**: 정의를 바꾸면 `defVersion`을 올린다. 다른 버전의 스냅샷은 같은 추세선에 잇지 않는다. 2주 평가 보고는 그 시점 값으로 동결되어 정의가 바뀌어도 과거 보고는 그대로다.
- **지표 원칙 (§3.21)**: (1) 결정적 투영, 모델은 지표 계산에 쓰지 않는다. (2) 변경 경로 밖. 지표가 동작을 바꾸는 길은 관찰 제안과 사람 채택 하나다. (3) 작업 에이전트에게 숨긴다(OB-8). (4) 쌍으로 본다. (5) 표본을 표시한다. (6) 정의 버전. (7) 임계값은 검토 신호다. (8) 측정을 위해 작업을 멈추지 않는다(OB-11). (9) 활동량 보정.

## 3. 동작 흐름

### 3.1 파이프라인 (관찰 실행 안)

§3.1.1 구성도 기준이다.

1. 수집: Helm 이벤트(읽기 전용 SQLite)와 외부 세션 파일(읽기만).
2. 정규화: 소스 어댑터가 공통 트레이스 스키마로 바꾼다.
3. 마스킹: 캐시에 쓰기 전에 비밀과 주입 의심 문구를 처리한다.
4. 패턴 탐지: 결정적 탐지기 D1~D13.
5. 분류: 서명과 묶음(코드), 판정과 초안(모델, 묶음 단위).
6. 제안 생성: 초안 검사(lint), 수치는 코드가 채운다.
7. 중복·기각 확인: 정본의 기각 기억과 열린 제안을 비교한다.
8. 제출: IPC → 데몬 → `engine.submit` → 커널 명령.

커서는 정규화 결과와 같은 트랜잭션에서 커밋한다(§4.1). 그래서 실패하면 반쯤 읽은 파일을 처음 오프셋부터 다시 읽는다.

### 3.2 실행 주기와 트리거 (§3.3)

트리거는 모두 코드가 판정한다. 모델이 관찰 실행을 띄우는 일은 없다.

| 트리거 | 조건 | 띄우는 작업 | 비고 |
|---|---|---|---|
| T1 Helm 실행 정착 | `run.ended` 뒤 같은 Concern에 새 실행이 10분 없음 | `scan` | 디바운스 10분, 여러 Concern이면 한 번으로 합친다 |
| T2 외부 세션 확인 | 외부 소스가 하나라도 켜짐 | `scan` (15분마다) | 바뀐 파일이 없으면 `stat`만 한다. inotify에 의존하지 않는다 |
| T3 일일 분석 | `observer.cycle` (cron `0 18 * * *`, 사용자 시간대, single-flight) | `scan` → `analyze` → `digest` | 대화 L310 예시("매일 저녁 6시") |
| T4 지표 스냅샷 | 매일 04:00 | 데몬 안 `runtime`의 지표 소비자 (관찰 실행 아님) | 관찰 실행과 겹치지 않게 다른 시각 |
| T5 효과 측정 | 적용 후 7·14·28일 도래 | `effect` | §3.17 |
| T6 2주 평가 | MVP 완료일부터 14일마다 09:00 | `evaluate` | §3.27.6 |
| T7 누락 대비 | 데몬 시작 시, 마지막 `scan` 성공 뒤 6시간 경과 | `scan` | 이벤트 트리거 누락 대비 |
| T8 수동 | `helm observer run <kind>` 또는 클라이언트 명령 | 지정한 작업 | 예산 검사는 같게 적용 |

규칙 (§3.3.1):

1. `analyze`는 T3와 T8에서만 돈다. 같은 날 최대 2회다.
2. `scan`은 결정적이고 모델을 쓰지 않는다. 직전 `scan` 종료 뒤 5분 안에는 다시 띄우지 않는다.
3. 사용자가 활동 중이어도 T1·T2·T7 `scan`은 돈다. 결과는 사용자에게 알리지 않는다. 제안은 일일 분석 뒤 제안함과 복귀 요약으로만 보인다.
4. 데몬이 꺼져 있던 동안 밀린 T3·T5·T6은 시작 뒤 한 번씩만 따라잡는다.
5. 안전 모드(17 `daemon.safe_mode_entered`)면 관찰 실행을 띄우지 않는다. 읽기 전용 모드에서는 `scan`만 돌고 제출하지 않는다.
6. 일별 집계(`outside_changes`, `baseline`)는 T3에서 마감된 날짜(어제까지)만 제출한다. 멱등 키는 `form + localDate`다.

트리거 레코드 (§3.3.2): `helm_run_settled`, `external_periodic`, `daily_analyze`, `effect_due`, `biweekly_evaluate`, `catch_up`(`daemon_start` 또는 `stale_scan`), `manual`(`requestedBy: "human"`).

타이머 연결 (12 §3.14.7, §2244 매핑): 타이머 `observer.cycle`이 데몬의 관찰 감독기를 깨운다. 실행 중에 같은 종류의 계기가 겹치면 16 규칙대로 합치고 실행이 끝난 뒤 한 번 더 돈다. 시간대는 두 곳에 다르게 적혀 있다. T3는 "사용자 시간대", 다이제스트 발송(§3.23.14)은 "서버 시간대"다(§8 참고).

### 3.3 실행 프로세스 (§3.2.1, §3.2.3)

- 감독기는 대기열 하나를 두고 동시에 한 관찰 실행만 돌린다. 같은 작업 종류의 대기 항목은 하나로 합친다.
- 자식 옵션: `execArgv: ["--max-old-space-size=768"]`, 환경 변수는 허용 목록만(`HOME`, `PATH`, `TZ`, `LANG`, `NODE_ENV`). `HELM_*`와 모델 API 키는 넘기지 않는다(OB-T02). 설정과 데이터 경로는 `job.start` 메시지로 받는다. 우선순위는 `os.setPriority(pid, 10)`으로 낮춘다.
- 격리 실행(판정 J-70, Q17-02): 기본은 fork다. 켜면 `systemd-run --user --unit=helm-observer-<runKey> --slice=helm-tools.slice --property=PartOf=helmd.service --pipe --wait`로 띄우고 IPC를 표준 입출력 JSON 줄로 바꾼다. `--scope`는 쓰지 않는다. 단위 속성은 `MemoryMax=1G`, `Nice=10`, `PrivateNetwork=yes`, `ProtectSystem=strict`, `ProtectHome=read-only`, `ReadWritePaths=/srv/volumes/helm/observer`, `InaccessiblePaths`(WSL 경로, `%t/helm`, `/srv/volumes/helm/private`)다. 격리를 켰는데 `systemd-run`이 실패하면 fork로 돌아가지 않고 실패로 기록한다(§17 §5.2).
- 읽기 전용 층 (§3.2.4): 정본은 `openReader(dataDir)`(`readonly`, `fileMustExist`, `PRAGMA query_only = ON`, `busy_timeout = 5000`)로 연다. 외부 로그는 `fs.open(path, "r")`만 쓴다. `/srv/volumes/helm/private/`와 `.helm/private/`는 열기 전에 감싸개가 거부한다(OB-T32). 격리 모드에서는 `InaccessiblePaths`가 막는다.
- IPC (§3.2.3): JSON 한 개씩이고 `id`로 요청·응답을 짝짓는다. 전송은 `nodeIpcTransport`(process.send)와 `stdioJsonLinesTransport`(줄마다 JSON, 1 MiB 넘는 줄은 `ipc.invalid_message`) 둘이다. 관찰 프로세스는 `@helm/client`·`@helm/protocol`을 쓰지 않는다. 받는 쪽은 스키마 검사를 통과한 메시지만 처리한다(OB-T33).
- 데몬이 죽으면 관찰 자식은 IPC가 끊겨 스스로 끝난다. 다음 부팅 때 짝 없는 `observer_run.started`를 `run_failed(interrupted)`로 닫는다(§4.1).

### 3.4 제출 경로 (§3.4.2)

```text
관찰 프로세스 ── IPC rpc.call kernel.submit ──▶ 데몬(감독기)
  데몬: actor = agent:observer, channel = aux_agent 고정, 2차 마스킹, 크기 상한,
        초안·보고 본문을 blob으로 저장한 뒤 BlobRef를 페이로드에 넣는다
  ──▶ engine.submit (10 §3.2) ──▶ 커널 명령 하나 (form에 따라)
```

| `ObserverSubmission.form` | 10 명령 | 09 이벤트 |
|---|---|---|
| `proposal` (`changes`가 policy 또는 agreement) | `policy.change.propose` | `policy_proposal.submitted` |
| `proposal` (procedure, tooling, context) | `procedure.candidate.propose` | `policy_proposal.submitted` |
| `annotation` (Helm 정정, D5) | `observation.annotate` | `observation.annotated` (`repeated_correction`, `near_miss`) |
| `evidence_update` | `observer.report.submit` | `policy_proposal.evidence_updated` |
| `effect_report` | `observer.report.submit` | `policy_proposal.effect_measured` |
| `withdraw` | `observer.report.submit` | `policy_proposal.withdrawn` |
| `run_started` / `run_finished` / `run_failed` (감독기만) | `observer.report.submit` | `observer_run.started` / `completed` / `failed` |
| `digest`, `evaluation`, `outside_changes`, `baseline`, `correction_signal` | `observer.report.submit` | `observer_report.recorded` (본문은 blob) |

커널 검증 요구 (§3.15.1): (1) 행위자 `agent:observer`이고 형태가 위 목록 중 하나다. (2) `kind`가 13종 목록에 있고 `changes`가 표와 맞다. (3) `patch.key`가 §3.12.4 금지 목록에 없다. (4) Helm 근거 참조가 존재한다(외부 참조는 형식만 본다). (5) 같은 `idempotencyKey`는 한 번만 기록한다. (6) 제안 전체 32 KiB 상한.

실패하면 `command.rejected`가 남고 IPC로 오류가 돌아간다. 거부 갈래는 `content`, `authority`, `path` 셋이다. 관찰 프로세스는 같은 실행 안에서 같은 서명을 다시 내지 않는다.

### 3.5 사용자에게 결과가 도착하는 순서

1. 트리거 → 실행 → 제안이 `policy_proposal.submitted`로 정본에 들어간다(상태 `open`). 제안함 카운트와 복귀 요약 카운트가 1 오른다.
2. 다음 복귀 요약의 "관찰 제안 n" 절(접힘)과 제안함에 나타난다. 알림은 없다.
3. 사람이 `SCR-OBSERVER`에서 채택, 고쳐서 채택, 기각, 미루기 중 하나를 고른다. 채택은 `policy.change.accept`(명령)이고 화면은 `observerProposal.adopt`(19 메서드)를 부른다.
4. 정책·다이얼은 같은 트랜잭션에서 적용된다. 파일 종류는 적용 Concern이 열리고 C·A를 거친다.
5. 적용 뒤 7·14·28일에 효과를 재고, 결과가 `SCR-METRICS`와 제안 화면의 "채택한 제안의 효과"에 나온다.

### 3.7 중복·기각 확인 알고리즘 (§3.14.2 요지)

```text
dedupe(p):
  m = 서명으로 찾은 최신 결정, 없으면 패밀리로 찾음
  없으면                         → SUBMIT
  open, deferred                 → UPDATE_EVIDENCE (열린 제안에 근거 추가)
  accepted, applying, applied, effect_pending → SKIP
  dismissed:
     family_forever              → SKIP
     coincidence이고 90일 안      → SKIP
     근거 2배 이상 + 30일 경과    → SUBMIT (이전 기각 id 표시)
     그 밖                        → SKIP
  kernel_rejected                → 7일 지나면 SUBMIT, 아니면 SKIP
```

### 3.8 OBS-ADR 후보 (상태 모두 "제안")

- OBS-ADR-1: 관찰 에이전트는 데몬이 띄우는 일회성 자식 프로세스로 실행한다.
- OBS-ADR-2: 관찰 에이전트의 모델 호출은 데몬을 거친다.
- OBS-ADR-3: 지표는 결정적 투영이며 동작을 자동으로 바꾸지 않는다. 다이얼 자동 조정은 기각했다(v0.3 10 §4.2 질문 7의 "일부 자동 적용").
- OBS-ADR-4: 반증 측정은 1인 N-of-1이며 채팅 기준선은 외부 세션 로그로 대신한다.

## 5. 경계 사례와 실패

### 5.1 관찰 실행 (§4.1)

| 사례 | 처리 |
|---|---|
| 데몬이 실행 중에 죽음 | 자식은 IPC가 끊겨 스스로 끝난다. 다음 부팅 복구에서 짝 없는 `observer_run.started`를 `run_failed(interrupted)`로 닫는다. 커서는 마지막 커밋 단계에 있어 다음 실행이 이어 읽는다 |
| 예산 소진 (실행 중) | `llm.complete`가 `budget.exhausted`를 낸다. 남은 모델 판정을 멈추고 결정적 제출만 한 뒤 `job.finished { outcome: "partial" }`. 시작 전에 이미 소진이면 `analyze`를 띄우지 않고 `scan`만 띄운다 |
| 자식이 `job.finished` 없이 죽음 | 감독기가 `observer_run.failed(crashed)`를 낸다. 같은 종류가 연속 3회 실패하면 6시간 동안 그 종류를 띄우지 않고 상태 화면에 경고한다 |
| 벽시계 상한 초과 | SIGTERM, 10초 뒤 SIGKILL. 캐시는 단계별 트랜잭션이라 마지막 커밋 단계까지만 반영된다 |
| 데몬 종료 중 | `job.cancel(shutdown)`. 진행 단계는 롤백하고 `outcome: "cancelled"`. 제출 중이던 제안은 멱등 키로 다음 실행에서 중복 없이 다시 보낸다 |
| 정본 스키마 버전 불일치 | 실행을 거부한다(`store_schema_mismatch`). 업그레이드 절차가 관찰 패키지도 함께 올린다 |
| 데몬이 읽기 전용 모드 (17 `read_only`) | `scan`은 계속 읽고 제출은 하지 않는다(`kernel.store_read_only`). 실행은 `partial`로 끝난다 |
| 관찰 캐시 손상 | `observer.db.corrupt-<시각>`으로 옮기고 새로 만든다. 다음 `scan`이 재구성한다 |
| 디스크 부족 | 캐시 쓰기 실패 시 `partial`로 끝내고 경고한다. 상한 정리를 먼저 시도한다 |
| 시계가 뒤로 감 | 트레이스 `ts`는 원천 시각을 그대로 쓰고, 이전 항목보다 이르면 맞추고 이상으로 기록한다 |

### 5.2 외부 로그 (§4.2)

| 사례 | 처리 |
|---|---|
| 마지막 줄이 쓰이는 중(개행 없음) | 그 줄 앞에서 멈추고 다음 실행에 읽는다 |
| JSON 파싱 실패 줄 | `malformed_json`으로 세고 건너뛴다 |
| 1 MiB 넘는 줄 | `oversized_line`. 앞 64 KiB에서 `type`, id, 부모 id만 뽑고 본문은 버린다 |
| 모르는 `type`·형식 버전 | 개수만 센다. 한 파일에서 모르는 `type`이 50%를 넘으면 `format_version_unknown`으로 표시하고 탐지 입력에서 뺀다 |
| 파일이 다시 쓰임(앞부분 해시 변경)·잘림 | 처음부터 다시 읽고 이벤트 id로 멱등 upsert한다. 사라진 항목은 지우지 않고 위치가 없는 것으로 남긴다 |
| 허용 폴더에서 루트가 빠짐 | 다음 `scan`에서 그 루트의 트레이스와 후보를 지운다. 열린 제안은 `withdraw(target_removed)` |
| 세션 cwd가 허용 밖 | 읽지 않는다. 세션 안에서 cwd가 밖으로 바뀐 줄은 버린다 |
| Claude Code 하위 에이전트의 부모가 허용 밖 | 하위 에이전트도 읽지 않는다 |
| Helm이 외부 런타임을 구동한 세션 (`drivenByHelm`) | 패턴 탐지와 C/A 우회 집계에서 뺀다. Helm 쪽 기록만 쓴다 (§3.6.6) |
| Codex 형식 미확인 | 기본 꺼짐. 사람이 켜도 픽스처 적합성 테스트 결과가 없으면 설정 화면이 경고하고 `format_version_unknown`으로 동작한다 |

### 5.3 마스킹과 주입 (§4.3)

| 사례 | 처리 |
|---|---|
| 1차 마스킹 누락을 2차가 잡음 | 데몬이 가리고 `secondaryMaskHits`를 올리고 경고한다. 그 후보는 이번에 제출하지 않고 다음 실행으로 미룬다 |
| PEM 키가 여러 줄에 걸침 | MK-01이 블록 단위로 가린다. 블록 끝이 다음 증분 읽기에 있으면 시작 줄부터 다시 처리한다 |
| 엔트로피 오탐 | 오탐도 가린다. 서명은 `<secret>`으로 묶여 탐지에 영향이 작다 |
| 로그 안 지시문 | `suspiciousInstruction`. 모델 입력에서 뺀다. 남은 발췌로도 이상한 초안이 나오면 lint에서 막힌다 |
| 모델이 스키마 밖 출력 | 1회 재요청 후 `draft_failed` |
| 모델이 수치를 지어냄 | 무시한다. 수치 필드는 스키마에 없다 |
| 초안이 위험 명령을 포함 | L3에서 실패. 같은 서명은 `suppressed`(사유 `unsafe_draft`) |

### 5.4 제안과 사람의 결정 (§4.4)

| 사례 | 처리 |
|---|---|
| 채택했는데 그사이 설정이 바뀜 | 커널이 `from` 불일치로 거부한다. 다음 실행에서 새 `from`으로 갱신하고 이전 것은 `withdraw(superseded)` |
| 같은 대상의 두 정책 제안이 충돌 | 같은 `patch.key`와 범위의 열린 제안은 하나만 둔다. 새 것이 생기면 이전 것을 대체 철회한다 |
| 적용 Concern이 28일 넘게 열림 | 제안 화면에 "적용 중 28일"을 보이고 효과 측정은 시작하지 않는다 |
| 채택된 정책이 불변조건을 끄려 함 | 커널 V-POL-01이 거부한다. 관찰 에이전트는 §3.12.4 목록으로 미리 거른다 |
| 제안이 너무 많음 | 실행당 상한 12. 열린 제안이 20개를 넘으면 새 제출을 멈추고 근거 갱신만 한다 [제안] |
| 사람이 오래 결정하지 않음 | 60일 뒤 `expired`. 근거가 계속 쌓이면 다시 제출할 수 있다 |
| 관찰 에이전트가 자신을 바꾸는 제안 | §3.12.4에서 막고, 커널도 거부한다 |

### 5.5 지표 (§4.5)

| 사례 | 처리 |
|---|---|

### 6.3 장기 관찰·제어 공간 (결정 10)과의 관계

결정 10: "OPD+C를 위한 장기 관찰·제어 공간이 클라이언트 UX의 주요 구현 대상이다. 대화 중심 UI와 다른 상태 중심 UI다" (브리프 결정 10, design 00-README, 03 §3.1.3). 16 문서는 이 공간의 **측정과 제안** 쪽을 맡고, 공간의 화면은 03·04가 맡는다.

| OPD+C 기준 (03 §3.1.3) | 사용자 질문 | 화면 요소 (03·04) | 16의 측정 |
|---|---|---|---|
| Observability | 지금 상태와 이유가 보이는가 | 홈 Concern 트리, Concern 개요, `SCR-AUTO`, `SCR-EVIDENCE`, `SCR-GOAL` | 연결되지 않은 M 변경 수 = 0 (`opdc.o.unlinked_m_changes`) |
| Predictability | 다음 행동과 멈출 조건이 예상되는가 | 진행 작업 카드의 다음 단계와 멈출 조건, 가정과 만료점, 현재 모드 | 예정과 실제 행동의 차이 (`opdc.p.plan_deviation_rate`) |
| Directability | 방향을 낮은 비용으로 바꿀 수 있는가 | Goal·완료 기준 편집, 다이얼 `SCR-DIALS`, 질문함, 멈춤·방향 바꾸기 | 명령부터 행동 변화까지 턴 수, 기준 하나 바꾸는 조작 수 (`opdc.d.*`) |
| Contestability | 이의를 걸고 다시 열 수 있는가 | `OVL-CONTEST`(선택, 판단, 루프 전환, 가정 확정 등) | 처리되지 않고 사라진 이의 = 0 (`opdc.c.orphaned_contests`) |

관계를 정리하면 다음과 같다.

- 관찰 에이전트는 이 공간의 **밖**에 있다. 제안은 `SCR-OBSERVER`와 복귀 요약 절로만 들어오고, 공간의 상태를 직접 바꾸지 않는다(OB-7, OB-8, §3.1.2).
- 지표는 OPD+C를 **재는** 값이다. 커널 판정, 다이얼, 작업 에이전트 투영에는 들어가지 않는다. 지표 값은 `SCR-METRICS`에서 사람이 본다.
- 14의 의무 ID(`opdc:o.autonomous_decisions` 등)는 화면 요소와 연결되고, 16 지표 ID(`opdc.o.*`)는 측정 값과 연결된다. 두 레지스트리는 형식이 다르다(콜론과 점).

## 8. 헷갈리기 쉬운 점

- **관찰(Observation)과 관찰 에이전트의 보고는 다르다.** 관찰(E 레코드)은 실제 실행 기록을 출처로 갖는다. 관찰 에이전트의 집계는 파생 값이라 `observer_report`로 두고 작업 에이전트가 근거로 쓰지 못하게 했다 (§3.4.1). 25 용어집은 `observer`를 에이전트 역할 행에 둔다.
- **전환 규칙 ID와 관찰 트리거 ID가 다르다.** 14 §3.9.2~§3.9.3의 전환 규칙은 `T01`~`T28`이고 테스트 ID는 `T-CR-nn`이다. 16의 관찰 트리거 T1~T8(§3.3.1)은 이것과 별개다 (25 용어집 "전환 규칙" 항목). 관찰 실행 id는 `or_`다.
- **관찰 제안(`pp`, PolicyProposal)과 "인사이트", "추천"은 다르다.** 기각(`dismissed`, 사람)은 커널 거부(`command.rejected`, 내용·자격·경로)와 다르다 (§1.5, 25).
- **사실 키와 이벤트 이름이 같은 모양이다.** `contest/opened`, `contest/orphaned`, `autonomous_choice/recorded`, `plan/adopted`는 지표 계산 안의 사실 키(`kind/sub`)이고 이벤트 이름이 아니다. 이벤트 이름은 `objection.filed`, `objection.resolved`, `loop_plan.adopted`, `choice.committed`다 (§3.22.3 표 머리, 16 §3.23.2·§3.23.5, J-244). 16 본문에 1판 이름(`contest.opened`, `contest.resolved`, `autonomous_choice.recorded`, `result.accepted`, `agreement.cancelled`, `downgraded.interpretation_to_assumption`)은 더 남아 있지 않다. 다만 `round-2` 검증 보고(R2-recheck-b)가 지적한 대로 사실 키 표기는 점 표기 이벤트처럼 보일 수 있다.
- **이의 명령의 이름은 셋이다.** 이벤트 `objection.filed`, 명령 `objection.file`(19 `ObjectionFileParams`, 판정 J-111), 16 본문의 "이의 걸기"(화면 `OVL-CONTEST`). 이벤트는 행위자 human만 낸다.
- **기각 명령과 메서드와 이벤트가 셋이다.** 명령 `policy.change.reject`, 메서드 `observerProposal.decline`(화면이 부르는 이름, 19 §3.7.5), 이벤트 `policy_proposal.dismissed`. 16 §3.24.2는 "19 메서드는 `observerProposal.adopt`·`decline`·`snooze`"라고 적는다. `defer`와 `snooze`도 같은 것이다.
- **제안 기각 사유 값이 두 번 정의된다.** 16 §3.15.2의 열거값(`already_handled`, `coincidence`, `not_wanted`, `will_do_myself`, `too_costly`, `other`)과 이벤트 payload의 `reason`(문자열 32자)이다. 화면 한국어 문구는 04 §3.18 기준이다.
- **`policy_proposal.dismissed`의 기각 범위 값.** `this` 또는 `family_forever`다. 화면 문구 "다시 보지 않기"가 후자에 해당한다.
- **`observer.cycle` 타이머와 `observer_cycle` DB 종류는 같은 것이다.** 16 T3 표가 "`observer.cycle`(cron `0 18 * * *`)"이라 적고, 12 매핑 표가 DB 값 `observer_cycle`을 준다. 다이제스트 발송 타이머 `result_review_digest`(19:00)는 다른 타이머다 (§3.23.14, 26).
- **시간대가 둘이다.** T3 일일 분석은 "사용자 시간대"(§3.3.1), 결과 확인 묶음 발송은 "서버 시간대"(§3.23.14)다.
- **재요청 횟수가 16과 12 사이에서 다르다.** 16 §3.12.3은 출력 스키마 실패 시 1회 재요청이라고 적고 §5.2에서 12 §3.14의 "2회"를 맞추라고 요구한다. 12 §3.14.6은 여전히 "실패 시 2회까지 다시 요청"이라고 적는다. 이 요구의 반영 여부는 이 pack에서 확인하지 못했다.
- **가설 목록 V1~V7과 V1~V9가 섞여 있다.** OB-9와 §1.2는 v0.3 가설을 V1~V7로 부른다고 적고, §3.26.1, §3.27.6, §5.1은 V1~V9를 쓴다. 판정 J-09·J-10은 V1~V9다. 본문이 쓰는 번호는 V1~V9다.
- **`view.opened`의 필드 이름이 문서마다 다르다.** 16 §3.23.1과 09 payload는 `view`, `dwellBucket`, `deviceId`, `refs`, `depth`를 쓴다. 04 §3.27은 `view.opened{surface, depth, subjectRef}`를 쓴다. 04 §3.27은 열람 장소를 다섯 곳으로 적고, 16 §3.23.1은 여섯 번째인 결과 확인 중 `SCR-EVIDENCE`를 더 든다. 16 §5.2의 04 요구 (2)는 04에 이를 반영하라고 한다.
- **`ad.list_view_rate`의 조건 `view.surface = "auto"`도 09 필드명(`view`)과 다르다.** 같은 이유로 09 기준 필드명으로 맞춰야 한다.
- **`opdc.*`(지표)와 `opdc:*`(의무 ID)는 다른 레지스트리다.** 점과 콜론으로 구분한다 (J-149, 25 용어집 "OPD+C 의무 ID" 항목).
- **H1~H10(원전, foundations/08)과 V1~V9(v0.3 10 §3)와 H-I1~H-I4·H-R1(15)는 다른 목록이다.** 같은 번호라도 출처를 붙인다 (OB-9).
- **`CA-1`(01 별칭)과 `ca.agreement_bypass_rate`(16 ID)는 다른 이름이다.** 16 ID가 정본이고 별칭은 01이 붙였다 (§3.23 머리).
- **`normalPath`와 `followedRecommendation`.** 정상 경로 조작 수 지표는 08 `HumanOpMeta`의 "추천을 그대로 따랐는가" 필드를 쓰지 않고 이벤트 종류에서 계산한 `normalPath`(불리언)와 `opReason`(열거값)만 쓴다 (§3.22.3, 판정 J-76). 01 §3.5.2의 옛 이름 `onNormalPath`, `extraReason`도 쓰지 않는다 (§5.2 01 행).
- **`presence` 상태 이름.** 정본 값은 `active`·`idle`·`hidden`·`offline`이다. `locked`는 모바일 전용 값이 없다고 판정되었으므로 쓰지 않는다 (판정 J-119).
- **관찰 자식의 이름이 여럿이다.** 프로세스는 `@helm/observer`(진입점 `dist/main.js`), 격리 단위는 `helm-observer-<runKey>`, 12 본문은 `helm-observer`라고도 쓴다. 감독기는 `observer-supervisor`(06 DR-8, 17 `observer-supervisor`)다.
- **관찰 캐시의 `or` 접두사.** 25 용어집 §3.11 행에는 "`or`은 08 §3.2.2 접두사 목록에 없다(§4 N-20)"라고 적혀 있다. 08 현행 표(L224)와 예약 목록(L240)에는 `or`이 있고 판정 J-113이 반영했다. 25 행은 옛 메모로 보인다.
- **"관찰 제안 n"과 "에이전트가 정한 것 n"은 다른 절이다.** 전자는 복귀 요약 9절과 `SCR-OBSERVER`, 후자는 8절과 `SCR-AUTO`다.
- **제안 제출의 단계 표기가 흐리다.** 16 §2.1은 [판정 J-07]을 "결정적 수집·탐지·지표는 MVP, 모델 판정·제안 제출은 2단계"로 적는다. §3.12.2는 "모델을 끈 상태에서도 D10, 효과 측정 제안은 템플릿 문장으로 제출된다"고 적는다. 제안 제출이 MVP인지 2단계인지는 본문만으로 정해지지 않는다. 04 §3.27은 관찰 에이전트 절을 2단계로 둔다.
- **OB-T34~T37은 `just verify` 포함 목록에 없다.** §6.2 끝 문장은 OB-T01~OB-T33만 적는다. 나머지 네 시험이 빠졌는지는 22 쪽에서 확인해야 한다.
- **`observer_run.completed`의 `proposals`와 `report`.** `proposals`는 제출된 제안 수, `report`는 실행 보고 blob이다. 실행 보고의 수치는 지표 원천 `obs.*`로만 쓰고 기록과 섞지 않는다 (§3.3.2).
- **`obs.*` 지표 묶음과 `observer_*` 테이블.** `obs.*`는 관찰 에이전트의 지표 묶음이고, 테이블 `observer_proposal`·`observer_signal`은 색인이다. 이름이 비슷해도 역할이 다르다.
- **"다음 실행에서 한 번 더"와 "대기열에서 합침".** §3.2.1은 같은 종류의 대기 항목을 합친다고 하고, 12 §3.14.7은 겹친 계기를 실행이 끝난 뒤 한 번 더 돈다고 적는다. 둘은 같은 규칙이지만 표현이 다르다.
- **이 pack이 쓰지 않은 것.** 설계 문서의 `design-gaps.md`는 이 pack 작업이 고치지 않는다(지시: 네 pack 파일만 쓴다). 위 어긋남은 메인 마지막 검토 대상으로 여기에만 적는다.
