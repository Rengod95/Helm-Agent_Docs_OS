## 1. 이 노드가 답할 질문

> Helm은 어떤 프로세스와 패키지로 이루어지고, 어디에 배치되며(WSL2 서버, Windows 호스트, Mac·Windows 데스크톱, iPhone), 각 부분은 어떤 방향으로 의존하는가? 데이터와 요청은 어떤 경로(Tailscale serve, SSH, 루프백)로 흐르는가? 핵심 ADR은 무엇인가?

나눈 질문:

- (가) 프로세스: 상주하는 것과 일회성인 것, 누가 띄우는가.
- (나) 패키지: 이름, 층, 한 줄 책임.
- (다) 배치: 어느 기기·OS에 무엇이 사는가.
- (라) 의존 방향: 패키지 import와 프로세스 통신의 방향.
- (마) 경로: 요청·이벤트·데이터가 지나는 길.
- (바) 핵심 ADR과 한 줄 결정.

## 2. 핵심 개념

### 2.1 시스템 구성

**C1. 배치 C: 상태는 데몬이 갖고, 실행기는 붙었다 떨어진다.**
커널·저장소·스케줄러 같은 상태는 데몬 `helmd`가 소유한다. 실행기(런타임)는 런타임 어댑터 계약을 통해서만 데몬과 대화한다. 1차 구현에서 붙는 실행기는 데몬 프로세스 안의 자체 런타임 하나다. 까닭: 클라이언트가 없어도 작업이 계속되어야 하고(결정 22), 다른 런타임을 나중에 붙일 수 있어야 한다(결정 34). B안(pi 프로세스 안에서 Helm이 돈다)은 결정 22와 충돌해 버렸다. A안(서버 안 런타임, 계약 없음)은 다른 런타임을 붙일 때 세션 호스트를 새로 만들어야 해서 버렸다.
출처: 06 §3.6.1 (ADR-06-01).

**C2. helmd: 상주 단일 프로세스, 단일 writer, 조립 루트.**
Node 프로세스 하나가 정본 DB에 쓰는 유일한 프로세스다. systemd 사용자 단위 `helmd.service`가 띄우고 상주한다. 설정 로드, 잠금, 비밀 로딩, 리스너 셋, JSON-RPC 처리, `engine`·`runtime` 생성, 관찰 감독기를 맡는 조립 루트다. 제품 의미(규칙)는 소유하지 않는다. 의미는 `kernel`과 `engine`이 소유한다.
출처: 06 §3.4.12, §3.6.2 (책임 DR-1~DR-8), ADR-06-02; 17 §3.1.1.

**C3. 정본은 SQLite 이벤트 로그 하나.**
위치는 `/srv/volumes/helm/data/helm.sqlite`(WSL ext4, WAL). 모든 프로젝트가 DB 하나를 쓰고 이벤트 seq는 DB 전체에서 하나다. 투영 테이블, 멱등 입력함, 실행 기록, 측정도 같은 파일에 있지만 정본이 아니거나 별도 범주다(§2.3 C20 참고).
출처: 06 §3.9.1, ADR-06-05, 결정 29(제안 기본값).

**C4. 자체 런타임은 pi 패키지를 재활용한 포크다.**
모델 호출은 `@helm/ai`(pi-ai를 얇은 인터페이스 뒤에 둠), 루프는 `@helm/agent`(pi-agent-core 포크), 도구는 `@helm/tools`(coding-agent 도구 포크)다. 외부 pi 패키지(pi-ai, pi-codemode, pi-mcp, pi-tui)는 정확한 버전 `1.1.0`으로 고정한다. 수정하는 pi 코드는 `vendor/` 아래 비공개 패키지 3개로 둔다. 기준 태그는 `v1.1.0`(커밋 `abe508e1`).
출처: 06 §3.4.7~§3.4.9, §3.4.18, §3.12.1; ADR-00-23, ADR-00-27, ADR-00-28, ADR-00-44.

**C5. 레이어와 의존 방향.**
위 레이어가 아래 레이어에 의존하고 아래에서 위로의 의존은 없다. 같은 레이어 안에서는 §3.4 표에 적힌 것만 허용한다.
- L0 계약: `domain`, `protocol`.
- L1 규칙: `kernel`(순수, I/O 없음, 하위 경로 `orchestration`).
- L2 기록: `store`(SQLite 드라이버는 여기서만).
- L3 변경 경로: `engine`.
- L3' 실행 부품: `ai`, `agent`, `tools`, `browserd`(별도 프로세스, `@helm/*` 미의존).
- L4 실행: `runtime`, `observer`(fork 일회성 자식).
- L5 호스트: `daemon`(조립 루트).
- L6c 클라이언트 공용: `client`, `client-react`, `ui-language`, `ui-tokens`, `ui`.
- L6 앱: `desktop`, `mobile`(2단계), `tui`(이후), `cli`.
- `engine`(L3)과 L3'는 서로 의존하지 않는다. 둘을 함께 쓰는 곳은 L4 `runtime`뿐이다. 그래서 모델 루프 코드가 기록 계층에 직접 쓸 경로가 없다(결정 14, P3).
출처: 06 §3.2.1.

**C6. 패키지 목록과 더한 이유.**
브리프 §3.1 목록을 따르고 패키지를 더했다. 더한 것은 `engine`, `client`, `client-react`, `ui-language`, `ui-tokens`, `ui`, `testkit`, `browserd`, vendor 패키지 3개다. `engine`은 "이벤트 append는 여기서만"을 import 규칙 하나로 강제하려고 두었다. `client`는 데스크톱·모바일·TUI·CLI가 같은 재접속 로직을 쓰게 하려고 `protocol`(와이어 타입)과 나눴다. `browserd`는 `playwright-core`를 도구 패키지에서 떼어 별도 프로세스로 두려고 만들었다. `ui-tokens`와 `ui`는 모바일이 같은 부품을 쓰게 데스크톱 앱 밖에 두었다.
출처: 06 §3.3.1, §3.3.2 (ADR-06-17이 ADR-06-03을 대체), 판정 J-216.

**C7. 허용 의존 표가 원본이다.**
행은 의존하는 쪽, 열은 대상이다. 빈칸은 금지, `O`는 허용, 경로만 적은 칸은 하위 경로만 허용이다. 예: `observer`는 `protocol`, `client`, `ai`, `engine`, `runtime`, `kernel`을 import하지 않는다. `client`는 `protocol`에만 의존하고 `domain`·`kernel` 이상은 import하지 않는다. `daemon`은 `kernel`을 직접 import하지 않는다. 판정은 항상 `engine`을 거친다.
출처: 06 §3.4.1, §3.4.11, §3.4.13.

**C8. 의존 규칙은 도구가 강제한다.**
규칙 R1~R16(06 §3.5.1)의 원본은 `scripts/architecture-rules.ts` 한 파일이다. 검사기는 `scripts/check-architecture.ts`(TypeScript 컴파일러 API만 사용)이고, ESLint 패키지별 금지 import와 전역·구문 금지, pnpm 엄격 해석, `exports` 진입점, `tsc -b` 프로젝트 참조가 함께 돈다. 규칙을 바꾸면 06 §3.4.1과 `architecture-rules.ts`를 같은 커밋에서 고친다. `just verify`(`check-arch`, `lint`)가 실패하면 완료가 아니다.
출처: 06 §3.5.1~§3.5.4; ADR-06-04.

**C9. 단일 변경 경로: 모든 상태 변경은 `engine`을 지난다.**
사람 명령, 모델 제안, 도구 관찰, 타이머, 관찰 제안의 다섯 입력이 모두 "멱등 확인 → 커널 판정 → 이벤트 append → 투영 갱신 → 알림 대기열"을 한 동기 트랜잭션으로 지난다. 트랜잭션 안에서는 `await`와 I/O(모델 호출, 파일 읽기, 네트워크)를 하지 않는다. 같은 트랜잭션 안의 뒤 제출은 앞 제출이 덧씌운 `KernelState` 사본을 본다. 롤백하면 사본도 버린다.
출처: 06 §3.4.6, §3.6.5; ADR-06-21(판정 J-148); R13.

**C10. 커널은 순수하고 시계를 읽지 않는다.**
`kernel`은 `Date.now()`, 인자 없는 `new Date()`, `Math.random`, `crypto`, 타이머, `console`, `process`를 쓰지 않는다. 시각과 ID는 `engine`이 `KernelContext`로 넣는다. 판정 함수는 `decide`, 상태 전이는 `apply`, 반응은 `react`다. 판정의 결과 상태는 `accepted`, `rejected`, `needs_gate`, `conflict`, `error` 중 하나다.
출처: 06 §3.4.4; R4, R5.

**C11. 투영은 정본을 쓰지 않는다.**
화면과 모델 컨텍스트용 읽기 모델은 로그에서 다시 만들 수 있어야 한다. 투영 계산 함수는 `kernel`(순수)에 있고 쓰기 API를 import할 수 없다. 불변조건 3(투영은 정본을 쓰지 않는다)을 구조로 지킨다.
출처: 06 §3.9.2 6번, §2.3(P5); 22/INV-3.

### 2.2 접속과 신뢰

**C12. 리스너 셋.**
- `tailnet`: TCP 127.0.0.1:7840. Windows `tailscale serve`가 넘긴 연결만 받는다. 인증은 Tailscale 신원 헤더와 whois 대조와 기기 토큰이 모두 필요하다(AND).
- `loopback`: TCP 127.0.0.1:7841. 데스크톱 앱의 `ssh -W 127.0.0.1:7841 server`가 sshd를 거쳐 여는 연결만 받는다. 기기 토큰이 필수다. Tailscale 헤더는 보지 않는다. 로컬 관리자 주체는 받지 않는다.
- `local`: Unix 소켓 `rpc.sock`(파일 0600, 디렉터리 0700). 서버 안의 `helm` CLI와 TUI가 쓴다. 같은 OS 사용자 권한이 인증이고 로컬 관리자 주체를 허용한다. 기기 토큰도 받는다.
- 세 리스너 모두 `0.0.0.0`, tailnet 주소, LAN 주소에 바인딩하지 않는다. 설정 검증기는 `host`가 127.0.0.1(또는 ::1)이 아니면 거부한다.
출처: 17 §3.5; 06 §3.7.1; 06 §3.7.4 (1~2번).

**C13. 연결 처리 3층.**
리스너(전송 수락과 리스너별 사전 검사) → 인증층(hello에서 주체를 정함. 실패한 연결은 프로토콜층으로 넘기지 않음) → 프로토콜층(처리기 한 벌, 전송을 모름). 세 리스너는 같은 HTTP + WebSocket 스택과 같은 처리기를 쓴다. 리스너는 출발지 주소 127.0.0.1을 신뢰 근거로 쓰지 않는다. 그래서 TCP 리스너는 기기 토큰 없이 주체가 정해지지 않는다.
출처: 06 §3.7.2; ADR-06-13.

**C14. 세 방향의 흐름.**
- Northbound: 사람 명령과 조회(클라이언트), 관찰 제안, 외부 어댑터의 관찰 후보 → 프로토콜 → `engine.submit`/`query`.
- Southbound: 런타임 안의 일(메시지 완료, 도구 호출 요청·결과, 실행 종료)을 중립 어휘로 바꾼 신호 → `runtime` → 관찰 후보·제안으로 `engine.submit`.
- Control: 커널 판정(허용, 거부, 질문 필요), 컨텍스트 무효화, 중지 요청 → `runtime` → 어댑터. 커밋 뒤 `engine.onCommitted` → 구독 클라이언트.
하나의 채널로 세 방향을 모두 만들지 않는다.
출처: 06 §3.7.3 (canon-2 §1.4).

**C15. 루프백은 격리 경계가 아니다.**
도구 자식 프로세스(bash 등)는 데몬과 같은 OS 사용자로 돈다. `networkingMode=mirrored`에서는 Windows 쪽 프로세스도 127.0.0.1 포트에 붙을 수 있다. 그래서 (1) 모든 리스너가 자격 증명을 요구하고 (2) 로컬 관리자 주체는 소켓 권한에 기대므로 도구가 `rpc.sock`과 데이터·설정 디렉터리를 볼 수 없게 가리고 (3) 사람 권한 토큰은 클라이언트 키체인에만 두고 (4) 격리 수단이 없으면 `execute`를 끈다. 격리 없음(S0)은 운영자 설정 `tools.sandbox="off"`로만 허용하고 그때마다 감사 기록을 남긴다.
출처: 06 §3.7.4; 판정 46; ADR-00-46.

**C16. 프로세스의 상주와 일회성.**
- 상주: `helmd`(데이터 디렉터리마다 하나. 정식과 개발이 따로 돈다), 데몬 안의 워커 스레드(codemode 실행기, 무거운 읽기 작업).
- 일회성 자식: 도구 실행(`bash`, `rg`, `git`), 웹 본문 변환 작업자, `helm-browserd`(브라우저 세션 하나), 관찰 에이전트(fork, 동시에 하나), 비밀 로더(시작 때 한 번).
- 외부: 모델 제공자(HTTPS, 데몬만 호출), 외부 에이전트 pi·Claude Code·Codex(사용자가 직접 실행, 세션 로그만 읽음. 2단계 이후 어댑터).
- 클라이언트(데스크톱, 모바일, TUI, CLI)는 모델을 직접 부르지 않는다.
출처: 06 §3.6.3, §3.6.5; ADR-06-02.

### 2.3 관찰, 비밀, 설정, 관측, 어댑터

**C17. 관찰 에이전트는 데몬과 다른 일회성 프로세스다.**
`@helm/observer`의 진입점 `dist/main.js`를 데몬의 감독기(`daemon/src/observer-supervisor.ts`)가 `child_process.fork`로 띄운다(기본 전송). 정본은 `query_only` 읽기 연결로만 읽고, 제출과 모델 호출은 Node IPC로 데몬에 맡긴다. 데몬은 행위자를 `agent:observer`로, 채널을 `aux_agent`로 고정한다. 관찰 프로세스는 비밀과 클라이언트 프로토콜을 갖지 않는다. 쓰기 권한이 없다는 것은 프로세스 경계와 IPC 채널 고정으로 지킨다.
출처: 06 §3.4.11, §3.6.3, §3.7.1; ADR-06-02; 16 OB-3.

**C18. 비밀은 시작 때 데몬 메모리로만 들어온다.**
원본은 SOPS `~/projects/helm/secrets/<env>.sops.yaml`이다. 데몬 시작 단계에서 `secrets run <scope> -- helm-secret-export <키…>`를 자식으로 실행해 표준 출력 파이프로 받고 메모리의 비밀 저장소에 넣는다. 값은 `process.env`와 `/proc/<pid>/environ`에 남지 않는다. 도구·관찰 프로세스에는 허용 목록의 변수만 넘긴다. 데몬이 `ExecStart`를 `secrets run`으로 감싸지 않는 까닭은 주 PID가 sops가 되어 신호 전달이 꼬이기 때문이다.
출처: 06 §3.9.3; ADR-00-45(판정 45); 17 D17-07.

**C19. 설정은 운영 설정만 담는다.**
TOML 형식이다. 우선순위(낮은 것부터 덮어씀)는 다음과 같다: 코드 기본값 → `$HELM_CONFIG` 또는 `~/.config/helm/helmd.toml`(dotfiles에서 관리) → `helmd.local.toml`(미추적) → 허용된 환경 변수 → 명령행 인자. 데몬은 설정을 읽기만 한다. 다이얼, 모드, 정책처럼 Helm 의미에 속하는 값은 설정이 아니라 도메인 이벤트로 바꾸고 정본에 기록한다. 화면에서 바꾼 값이 설정 파일에 써지는 일은 없다.
출처: 06 §3.10.1~§3.10.2; ADR-06-11; 17 §3.3.1.

**C20. 관측 흐름 네 개를 섞지 않는다.**
도메인 원장(SQLite 이벤트 로그), 운영 로그(pino로 stdout에 JSON 줄, systemd가 journald로 보냄, 내용 미기록), 실험 측정(16이 정함. 정본 흐름이지만 도메인 원장과 섞지 않음), 원시 런타임 trace(SQLite 근거 원천, 판단 근거로 인용하는 것은 관찰 레코드뿐). 서버 오류나 토큰 사용량을 자동으로 도메인 이벤트로 만들지 않는다. 반대로 중요한 산출물 변화를 운영 로그에만 남기지 않는다.
출처: 06 §3.11.1, §3.11.2; ADR-06-12.

**C21. 벤더 중립: 어댑터 계약과 능력 목록.**
런타임별 이름(pi 이벤트, Claude Code 훅, Codex 메서드)은 어댑터 안에서만 쓴다. 도메인과 커널은 중립 어휘만 안다. 어댑터는 능력 목록(`CapabilityManifest`)을 제출하고, 능력이 없으면 멈추지 않고 보장 수준을 낮춰 동작하며 낮아진 사실을 화면과 감사 기록에 보인다. 보장 수준은 `enforced`(실행 전 차단), `detected`(실행 뒤 감지), `advisory`(지시문뿐), `unavailable`로 능력 목록에서 계산한다. 어댑터는 정본 이벤트를 직접 append하지 않고 `KernelGate`를 거쳐 `engine.submit`으로 제출한다. 같은 대본을 어댑터마다 돌리는 적합성 시험이 광고와 실제를 비교한다.
출처: 06 §3.13.1~§3.13.6; ADR-00-34; ADR-06-10(ADR-13-04가 대체).

**C22. 운영 수명주기는 systemd 사용자 단위가 맡는다.**
`linger`가 켜져 있어서 WSL 배포판이 부팅할 때 user manager가 `helmd.service`를 띄운다. 복구가 끝나고 리스너가 열린 뒤에야 `active`로 본다(`ExecStartPost`의 `helm ops wait-ready`). 종료 코드 1(예상하지 못한 오류)이면 재시작한다. 2·3·4·5는 재시작해도 같으므로 재시작하지 않는다. 자세한 내용은 §3.2.
출처: 17 §3.6.3, §3.6.4; 06 §3.6.6.

### 3.3 데이터 경로: 명령, 재연결, 도구 호출, 관찰

출처: 06 §3.7.5(a)~(d). 각 단계의 함수 이름은 06이 쓴 것이다.

(a) 사람이 데스크톱 앱에서 결과를 확인한다.
1. 앱의 `@helm/client`가 명령을 만들고 멱등 키를 붙여 진행 중 명령함에 먼저 저장한다(`client.command("result.accept", {…, basisSeq})`).
2. 요청이 serve를 거쳐 `tailnet` 리스너에 닿는다. 신원 헤더를 확인하고 hello에서 기기 토큰을 검증한다. 주체는 `human`, 기기 ID는 `dv_…`.
3. JSON-RPC 처리기가 `engine.submit({kind:"command", channel:"human_client", actor: human, …})`를 호출한다.
4. 트랜잭션 안에서 멱등 확인 → `basisSeq` 낡음 검사와 `kernel.decide` → 이벤트 append(seq=N) → 투영 갱신 → `commands` 행에 결과 저장.
5. 커밋한 JS 턴 안에서 `engine.onCommitted`가 구독 중인 모든 연결에 seq=N 이벤트를 보낸다. 이벤트 알림이 응답보다 먼저 나간다.
6. 응답 `{status:"accepted", seq:N}`. 커밋 뒤 `engine.onDirective`가 지시를 `runtime`에 넘긴다(예: 통합 작업 시작).

(b) 모델이 쓰기 도구를 부른다(1차 런타임).
1. 에이전트 루프의 이벤트 싱크에서 `message_end`가 오면 `runtime`이 `engine.transact`로 모델 메시지 실행 기록을 남긴다. 도구 실행은 커밋 뒤에 시작한다(결정 28, 판정 J-14).
2. `beforeToolCall`(write)에서 `engine.submit({kind:"proposal", command: toolcall.intend})`. 커널이 활성 작업 합의와 범위를 확인한다. 허용이면 `toolcall.requested`와 실행 의도 이벤트, 거부나 `needs_gate`면 `toolcall.blocked` 또는 `approval_requested`와 사유.
3. 허용이면 `tools.write`를 실행하고 `afterToolCall`에서 `engine.submit({kind:"observation", command: toolcall.complete})`. 거부면 도구 결과를 오류로 모델에 돌려준다.

(c) 앱이 다시 연결된다.
1. 앱이 `hello{…, resume:{storeId, seq:1200}}`로 연결한다. 필드 이름은 19가 정한다.
2. `storeId`가 같고 1201부터 남아 있으면 1201..현재를 구간 알림으로 보내고 실시간으로 이어 간다.
3. `storeId`가 다르거나(복원된 DB) 보존 범위 밖이면 `replay.outOfRange`를 보낸다. 앱은 뷰를 낡음으로 표시하고 head부터 다시 받는다. 복원 때는 저장소 epoch(`storeId`)가 새로 발급된다(06 §4 F15).

(d) 관찰 에이전트 한 회차.
1. 스케줄러가 관찰 트리거를 낸다. 감독기가 `@helm/observer`를 fork한다(허용 환경 변수만, 비밀 없음).
2. 관찰 프로세스가 `job.start`를 받고 `store/read`로 Helm 기록을, 허용한 프로젝트 폴더의 외부 세션 로그를 증분으로 읽는다.
3. 결정적 마이닝 → IPC `llm.complete`(데몬이 모델 호출, 예산 계정 `observer`) → IPC `kernel.submit` × n → `job.finished` → 종료.
4. 데몬의 감독기가 `kernel.submit`을 `engine.submit(actor = agent:observer)`로 넘긴다. 시간 제한을 넘으면 SIGTERM, 10초 뒤 SIGKILL(16 §3.2.1).
5. 관찰 모델 판정과 제안은 2단계 기능이라 `features.flags`로 기본 꺼짐(판정 J-07, ADR-06-18).

### 3.4 접속 경로 세 가지

출처: 06 §3.8, 17 §3.5, ADR-00-38.

| 경로 | 시작점 | 전송 | 리스너 | 인증 | 확정 |
|---|---|---|---|---|---|
| ① Tailscale serve WSS | Mac·Windows 데스크톱 앱(Rust가 바이트 연결) | `wss://<서버>.ts.net:8448` → Windows `tailscale serve`(TLS 종료) → HTTP/WS `127.0.0.1:7840` | `tailnet` | 기기 토큰(`Authorization: Bearer`, 필수) + Tailscale 신원 헤더 + whois 대조 | 17 D17-09, 19, 20 |
| ② SSH | 같은 앱, 두 번째 방식 | 시스템 OpenSSH `ssh -W 127.0.0.1:7841 server` → WSL OpenSSH :22(tailnet에서만, 키 인증, direct-tcpip) → `127.0.0.1:7841` | `loopback` | SSH 키(전송) + 기기 토큰(필수) | 19 P-02, 20 APP-D03 |
| TUI 경로 | WSL 셸(`ssh server`로 들어옴) | TUI가 Unix 소켓 `rpc.sock`에 붙음 | `local` | 소켓 파일 권한 + 로컬 관리자 주체(TUI 또는 TTY에서 확인 문자열) | 결정 33, 39; 19 |
| 관리 CLI | WSL 셸 또는 just 레시피, systemd `ExecStartPost` | `rpc.sock` 또는 오프라인 명령 | `local` | 같은 uid. 오프라인 명령은 잠금을 잡고 DB에 직접 | 17 §3.15 |
| 모바일 PWA (2단계) | iPhone 홈 화면 웹 앱 | serve → `tailnet`과 같은 주소, `GET /m/*`(정적), `POST /m/pair`, `GET /m/whoami`, `wss://…/rpc` | `tailnet` | 쿠키 `__Host-helm_dt`(HttpOnly, Origin 정확 일치) | 26, 18, 결정 47 |

두 경로가 같아야 하는 것(결정 38): JSON-RPC 메시지 형식, 메서드 집합, 서버 이벤트 seq와 재전송 규칙, 오류 코드, 멱등 키 처리, 기기 인증. 달라도 되는 것: 리스너, 리스너별 사전 검사, 큰 데이터 요청의 연결 방식(경로 ②는 요청마다 `ssh -W` 하나, 20 APP-D12).

`loopback`을 `tailnet`과 따로 두는 이유: `tailnet`은 신원 헤더를 요구하는데 SSH로 들어온 연결에는 헤더가 없다. 한 포트에서 "헤더가 없으면 다른 규칙"을 허용하면 헤더 검사를 건너뛰는 길이 생긴다(17 §3.5; 18 §3.4.2). 06 1차 초안의 stdio 프레임 전송은 쓰지 않는다(19 P-02). 예비 경로 B4(`helm bridge`, 19)는 sshd가 TCP 포워딩을 막을 때만 쓴다.

Tailscale이 멈추면 두 경로가 함께 끊긴다(두 경로 모두 tailnet을 지남). serve만 멈췄으면 경로 ②로 붙는다(06 §4 F10).

ADR-00-21의 제목은 "외부(원격) 접속"이고 구체 방식은 06 §3.8이 정한다(결정 26, 38). Tailscale SSH는 쓰지 않는다(브리프 §2.5).

### 3.5 의존 방향 한눈에

- 패키지 import 방향: `apps/*` → `client`, `client-react`, `ui`, `ui-language`, `ui-tokens`, `protocol`, `domain`(타입) → `protocol` → `domain`. `daemon` → `engine`, `runtime`, `ai`, `store/write`·`store/admin`, `protocol`, `observer/ipc`, `observer/metrics`. `runtime` → `engine`, `kernel`(순수 함수), `ai`, `agent`, `tools`, `domain`. `engine` → `kernel`, `store/read`·`store/write`, `domain`. `kernel` → `domain`(그리고 `typebox`). `store` → `domain`, `better-sqlite3`.
- 금지의 대표 예: `apps/desktop`이 `kernel`을 import하면 `check-arch` 실패. `observer`가 `ai`나 `client`를 import하면 실패. `client`가 `domain`을 직접 import하면 실패(06 §6 S2 예). `ai`가 `vendor-pi-tools`를 import하면 실패(R7).
- 프로세스 방향: 클라이언트 → 데몬(연결, 요청). 데몬 → 도구·관찰·변환 작업자·browserd(자식, stdio 또는 IPC). 관찰 → SQLite(읽기만), 관찰 → 데몬(IPC 제출·모델 호출 대행). 데몬 → 모델 제공자(HTTPS). 데몬 → Apple 푸시(Web Push).
- 쓰기 방향: 정본에 쓰는 프로세스는 `helmd` 하나다(06 §3.9.2 5번). CLI의 오프라인 명령(마이그레이션, 복구)은 데몬이 멈췄을 때만 같은 잠금을 잡는다.

### 4.3 엔진, 커널, 저장소, 런타임 이름

- `Engine` 인터페이스(06 §3.4.6): `submit(input): SubmitResult`(동기), `transact(fn)`(동기, 트랜잭션 전체), `store`(`RuntimeStoreReader`), `readAfter(seq, limit)`, `onCommitted(listener)`, `onDirective(listener)`.
- `EngineInput`: `CommandEnvelope`에서 `commandId`(없으면 발급), `actor`, `via`, `channel`을 뺀 것. `channel`은 호출자가 정하지 않는다. 데몬 처리기는 연결 종류에서, runtime은 `runtime`·`model_tool`, 스케줄러는 `scheduler`로 정한다.
- `SubmitResult` 상태: `accepted`, `rejected`, `needs_gate`, `conflict`, `key_reused`(같은 멱등 키·다른 지문, 이벤트와 `commands` 행을 만들지 않음), `error`(저장하지 않고 롤백).
- `KernelContext`: `now`, `cursor`, `newId`, `rules`, `attention`. 정본 정의는 09 §3.16.1. `presence`는 읽기 전용 스냅숏 필드다.
- 커널 함수: `decide(state, cmd, ctx)`, `apply(state, event)`(순수 reducer), `react(before, after, drafts, ctx)`. 조회 함수 `pendingTimers`, `checkSettle`, `allowedCommands`, `mustIncludeRefs`, `impactOf`, `viewAt`, `explain`(10 §3.1.5).
- `RuntimeStorePort` = `RuntimeStoreReader` + `RuntimeStoreWriter`(`@helm/domain/src/runtime-store.ts`). `runtime`은 `store`를 import하지 않고 이 포트로만 정본을 읽는다(ADR-06-19).

## 8. 헷갈리기 쉬운 점

- **`tailnet`의 두 뜻.** 리스너 이름 `tailnet`(TCP 127.0.0.1:7840)과 Tailscale 네트워크 이름 `tailnet`이 같은 말이다. 06 §3.7.1, §3.8.1에서는 문맥으로 구별한다. 리스너 이름으로 쓸 때는 항상 `tailnet` 리스너라고 적는다.
- **25 §4 N-01 표는 낡았다.** 25 표는 Via의 `listener` 값을 `"tailscale" | "ssh" | "local"`로 적고 08 Via와 26을 정본으로 맞추라고 한다. 현재 08의 Via 스키마(`Enum(["tailnet", "loopback", "local"])`, 19 ListenerKind)와 10 §3.3.2(판정 J-102)는 `tailnet | loopback | local`이다. 리스너 이름과 Via 값이 같다. 구현 리뷰에서는 08과 10 쪽을 본다.
- **`loopback`과 `local`은 다르다.** `loopback`은 TCP 7841이고 SSH로 들어온 연결만 받으며 로컬 관리자 주체가 없다. `local`은 Unix 소켓 `rpc.sock`이고 TUI·CLI가 쓰며 로컬 관리자 주체를 허용한다. "127.0.0.1에서 온다"는 사실은 신뢰 근거가 아니다(ADR-06-13).
- **`helm`, `helmd`, `helm-*` 실행 파일 이름.** `helmd`는 데몬, `helm`은 관리 CLI(`apps/cli`), `helm-secret-export`는 비밀 로더, `helm-browserd`는 브라우저 실행기, `helm-netshim`은 샌드박스 안 중계기, `helm-egress-proxy`는 데몬 쪽 CONNECT 프록시다. 같은 "프록시"라도 둘이다(아래 불일치 항목 참고).
- **`engine`, `kernel`, `runtime`, `store`의 역할.** 이벤트 append는 `engine`만 한다. `kernel`은 순수 판정만 한다. `runtime`은 `store`를 직접 import하지 않고 `RuntimeStorePort`로만 정본을 읽는다. 06 §3.4.1의 허용 표가 이것을 보여 준다.
- **`Directive`(지시)와 `Effect`(효과).** v0.3의 `Effect`는 범위 밖으로 뺀 effect class(결정 2)와 단어가 겹쳐서 `Directive`로 바꿨다. 10이 이 이름을 채택했다(06 §3.4.6).
- **`observer`의 세 뜻.** 패키지 `@helm/observer`(프로세스), 관찰 에이전트(역할), `Watch`(지속 관찰, 08 §3.16.2)는 다르다. 25는 "지속 관찰은 관찰 에이전트와 다르다"고 적는다.
- **정본, 투영, trace, 운영 로그, 측정.** 네 흐름을 섞지 않는다(06 §3.11.1). 같은 DB 파일 안에 있어도 정본이 아니거나 별도 범주다. 운영 로그는 journald에 있고 DB에 없다.
- **종료 코드 5.** 데몬에서는 "DB를 열 수 없음"이고, CLI에서는 "사람 결정 필요(gated)"다. 같은 숫자의 두 뜻이다. 1도 데몬은 "예상하지 못한 오류(재시작)", CLI는 "결과 실패"다.
- **읽기 전용 상태의 이름.** 17은 `read_only`, 19는 `readOnly`라고 한다. 25 §4 N-28은 화면 이름을 "읽기 전용"으로 맞추고 "복구"라는 말은 `SCR-RECOVERY` 화면에만 쓰라고 한다. 옛 표기 "복구 모드"·`recovery_mode`가 여러 문서에 남아 있다.
- **저장 결과 타입의 이름.** 06 §3.4.2는 저장되는 명령 결과를 `SubmitResult`라고 하고 09의 `WriteResult`를 이 이름으로 맞추라고 적는다. 그런데 06 §3.4.5의 store 공개 타입 목록에는 `CommitResult`가 있다. 06 안에서도 두 이름이 함께 쓰인다.
- **커널 상태 타입.** `KernelState`(불변 맵)를 쓴다. 09의 메서드형 `KernelView`는 두지 않는다(06 §3.4.2).
- **원칙 이름 체계가 여러 개다.** 06 안에 `P1~P7`(원전 아키텍처 원칙, §2.3), `AP-1~8`(어댑터 원칙, §3.13.1), `DR-1~8`(데몬 책임, §3.6.2), `R1~R16`(의존 규칙, §3.5.1)이 있다. 원전 가설 ID `H`, `V`와도 구별한다(25 §4 N-32).
- **의존 규칙의 개수가 문서마다 다르다.** 06 §3.5.1 표는 R1~R16이고, 24 ADR-06-04 본문은 "규칙 R1~R13", 06 §6 S2와 22의 `check-arch` 행은 "R1~R14"라고 적는다. R15(`observer`의 `fs` 감싸개)와 R16(웹 변환 작업자)은 나중에 더해졌다.
- **데몬 측 CONNECT 프록시의 위치가 문서마다 다르다.** 06 §3.4.9는 `src/sandbox/proxy.ts`(`@helm/tools` 소속)라고 하고, 13 U-TL-16도 `sandbox/proxy.ts`와 `bin/helm-netshim`이다. 17 §3.1.2는 데몬 주 스레드의 `helm-egress-proxy`라고 하고, 18 §3.11.9는 `packages/daemon/src/net/egress-proxy.ts`(18)와 `packages/tools/src/sandbox/proxy.ts`(13)를 둘 다 적는다. 06은 데몬 쪽 CONNECT 프록시를 §3.6.7 그림과 §3.7.4 9번에서 언급하지만, 코드 위치는 §3.4.9의 `tools/src/sandbox/proxy.ts`로만 적고 데몬 패키지 목록에는 넣지 않는다. 이 pack에서는 소유 위치를 정하지 못했다.
- **관찰 에이전트의 전송.** 06 §3.6.3과 ADR-06-02는 `fork`가 기본이고 `systemd-run --user` 일회성 단위는 격리 실행을 켤 때라고 적는다(16 §3.2.1). 17 §3.1.1은 "systemd-run --user 일회성 단위 또는 fork"라고 적는다. 기본값이 같은지는 16이 정한다.
- **쓰기 트랜잭션 시간의 수치가 세 가지다.** 06 §3.6.5는 목표 p99 10 ms(`[가정]`), 06 F13은 100 ms를 넘으면 `warn`(`[제안]`), 17 §3.1.2 규칙 1은 평상시 50 ms를 넘지 않게 나눈다고 적는다.
- **React 판.** ADR-00-32 제목은 React 18이고 `(대체됨 → ADR-00-41)`이다. 06 §3.12.1과 ADR-00-41은 React 19다.
- **로컬 관리자 주체의 이름.** Via는 `local_cli`(08)로 적혀 있는데 `createdBy.kind`는 `local_admin`이다(25 §4 N-50, "맞춘다"로 표시). 19는 `localAdmin` 주체라고 한다.
- **dev와 정식의 포트.** 정식 `loopback`은 7841, 개발 `loopback`은 7851이다. 정식은 `tailnet` 7840을 쓰지만 개발은 `tailnet` 리스너를 끈다. `.env.example`의 `HELM_LISTEN_SSH_PORT`는 개발 기본값 7851이다.
- **브리프 §2.5의 secrets 문장과 06 §3.9.3.** 브리프는 "just 레시피가 `secrets run`으로 자식 프로세스에만 주입"이라고 적는다. 06은 이것이 일회성 레시피에 해당하고 상주 데몬은 시작 때 자식 로더로 받는다고 적는다(판정 45).
- **"Tailscale SSH"와 "WSL OpenSSH".** 브리프 §2.5는 Tailscale SSH를 쓰지 않는다고 한다. 경로 ②는 WSL의 OpenSSH 22번이다. Windows sshd 2222는 WSL이 죽었을 때 쓴다.
- **두 SSH 경로의 이름.** 경로 ②(`ssh -W`, 데스크톱 앱), TUI 경로(`ssh server` 후 셸에서 TUI 실행), 예비 B4(`helm bridge`)는 셋 다 SSH를 쓰지만 리스너와 쓰임이 다르다(19 P-02, 19 B4).
- **"배치 C"와 "배치 A/B".** 06 §3.6.1의 A, B, C는 토폴로지 세 가지이고 C를 골랐다. 1차 구현은 C의 구조에 자체 런타임을 데몬 안에 넣은 것이라서, 실제 프로세스 모양은 A와 같다고 06이 설명한다.
- **`helm-tools.slice`와 `helm-tool-*` 단위.** 17은 도구마다 `helm-tool-<tc_id>.service`를 만든다고 적는다. 06 §3.6.3은 격리 방식을 13·18이 정한다고 적는다. 시험 단위와 실제 단위는 다를 수 있다.

## 9. 미결·이후 단계로 미룬 것

06 §7과 본문의 "제안"에서 모은 것이다.

- O-02: serve 이름 방식. 기본은 포트 `8448`이고 `helm.stackmellow.com`(Caddy) 방식은 17이 검토한다.
- O-03: TypeScript 7로 옮길 시점. 기본은 6.0 유지(typescript-eslint가 7을 지원하면 옮김).
- O-04: `node:sqlite` 전환. 기본은 `better-sqlite3` 유지(재검토 조건은 06 §3.12.3).
- O-05: 개발 실행을 소스 직접 실행으로 할 수 있는지. 06 §6 S1에서 확인(`node --conditions=source …`). 안 되면 대체 방식으로 바꾸고 06을 고친다.
- O-06: 어댑터 계약을 별도 패키지로 꺼낼 시점. 저장소 밖 어댑터가 생길 때.
- O-07: DB가 커질 때 오래된 실행 기록을 보관 파일로 옮길지. 17이 크기 지표와 문턱을 정한다(06 §3.9.2 4번, 17 §7 Q17-08).
- O-08: 갱신형 자격 증명(구독 OAuth 등). 시작은 API 키만. 필요하면 `/srv/volumes/helm/secrets/`(0600, 백업 제외)에 두고 18이 규칙을 정한다.
- O-11: CI. `just verify`는 서버에서만 돈다(비밀과 SOPS 키가 서버에 있음). Windows 앱 빌드만 20의 `app-build-win-ci`를 사람 확인 뒤 수동 실행한다.
- O-12: Renovate 같은 자동 업그레이드는 쓰지 않는다. pi 추적은 사람이 한다(07 §3.18).
- O-13: 진단 span을 외부(OTLP)로 내보내지 않는다. `trace` 수준에서 로그로만 남긴다.
- O-15: 2단계 기능 플래그를 G1 기록 없이 켜는 것을 막을지. 기본은 경고만(§3.10.3). 23이 관문 운영을 정하면 다시 본다.
- O-18: 웹 본문 변환기. 기본은 readability + turndown(위에 `linkedom`). 23 스파이크에서 한글 페이지 품질을 비교하고 나쁘면 바꾼다(06 §3.12.5).
- 06 §6 S1 실행 형태 확인: Node 타입 제거 실행과 `source` 조건이 워크스페이스 패키지에서 되는지. 가정(`[가정]`) 단계다.
- 06 §3.14 항목 6은 `tui`를 골격만 만들고 비워 둔다고 적는다. 모바일 앱(`apps/mobile`)은 2단계이며 26이 정한 뒤 만든다.
- 결정 57: Apple 개발자 프로그램이 지금 없다고 본다. 네이티브 iOS 경로(26의 경로 B, Tauri iOS와 APNs)는 이후에 검토한다. 현재 모바일은 PWA다(ADR-00-47).
- 외부 어댑터(pi RPC, Claude Code, Codex, ACP)는 이후 단계다. 1차는 자체 런타임 하나다(ADR-00-34). 두 번째 런타임 대신 시험용 가짜 어댑터를 둔다(06 §3.13.1 AP-8).
- 컴퓨터 사용 도구(`computer_*`, 실행마다 새 Xvfb)는 MVP 이후 1차 단계다(13 §3.2.6, ADR-13-09). Windows 호스트 데스크톱 조작은 비목표다(06 §2.4 12번).
- 15의 탐구 엔진과 14의 오케스트레이션 세부는 각 문서가 정한다. 06은 순수부가 `@helm/kernel/orchestration`에 있다는 것만 정한다(ADR-06-20).
- 전역 seq와 DB 하나 구조를 바꾸는 일은 06 §3.9.2 4번의 대가를 보고 정한다.
- 06 §1.2와 17 §1.3에 적힌 "다루지 않는 것"의 세부(인증 세부, 프로토콜 메서드 목록, 앱 빌드 경로, 테스트 계층 세부)는 18, 19, 20, 22가 정한다.
