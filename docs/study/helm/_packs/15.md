## 2. 핵심 개념 목록

### 2.A 화면 체계 (03)

**상태 중심 UI** [결정 10]. 대화 중심 UI와 달리 앱을 열면 대화가 아니라 홈(`SCR-HOME`)이 열린다. 마지막 확인 이후 변화가 기준치를 넘으면 복귀 요약(`SCR-BRIEF`)을 먼저 연다. 전역 대화창은 두지 않는다. 대화는 Concern·질문·작업 합의 같은 객체에 딸린 탭이다. 왜: 결정 10은 OPD+C를 위한 장기 관찰·제어 공간이 클라이언트 UX의 주요 구현 대상이며 대화 중심 UI와 다르다고 정했다(00-README 결정 10). 출처: 03 §3.1.1, §3.1.2.

**화면 규칙 8개** [제안, 03 §3.1.2]:
1. 상태가 먼저 보인다. 첫 화면은 객체의 현재 상태이고 로그·대화는 아래나 다른 탭이다.
2. 차이가 먼저 보인다. 목록과 요약은 마지막 확인 이후 차이를 먼저 보이고, 원본 로그는 drill-down으로만 연다.
3. 화면은 정본을 쓰지 않는다. 숫자와 라벨은 데몬 투영에서 온다. 앱은 우선순위·품질·가역성·전달 시점을 계산하지 않는다(결정 2·14·32). 조작은 명령 의도로 보내고, 받아들여진 결과가 돌아온 뒤에만 화면이 바뀐다(21 UI-D03과 같은 규칙).
4. 기준 시점이 보인다. 모든 투영은 seq와 생성 시각을 가지며, 낡으면 그 사실을 표시한다.
5. 구분이 보인다. 관찰·해석·가능성·판단·선택, 결과 제출·결과 확인·전체 반영, 사람 작성·에이전트 작성·정책 적용을 라벨로 나눈다. 색만으로 구분하지 않는다.
6. 모름과 이견은 접지 않는다.
7. 사람 행동 요청은 질문함 하나로만 들어온다(IA-02). 진행 보고는 사람 행동을 요청하지 않는다.
8. 모델 문장은 상태처럼 보이지 않는다. "관찰·선택·작업 합의·결과 제출·결과 확인·전체 반영" 라벨은 커널 레코드에서만 붙인다(03 §3.1.2 8, canon-2 §4.5).

**OPD+C 네 기준** [결정 10, 배치는 제안, 03 §3.1.3]. Observability(지금 상태와 이유), Predictability(다음 행동과 멈출 시점), Directability(방향을 낮은 비용으로 바꿈), Contestability(이의를 걸고 다시 엶). 각 기준은 화면 요소와 지표(16이 측정)에 대응한다. 예: Directability는 `SCR-DIALS`, Goal 제자리 편집, 진행 작업 멈춤 버튼에 대응한다.

**셸 영역** [제안, 03 §3.4.1]. `RGN-TOPBAR`(앱 이름, 위치 경로, 명령 팔레트 입력, 연결 상태, 기준 seq), `RGN-RAIL`(최상위 내비게이션과 배지), `RGN-BANNER`(즉시 전달 질문, 연결 끊김, 복구 필요, 안전 모드, 읽기 전용 등. 모달로 띄우지 않는다), `RGN-STATUSLINE`(Concern 범위 화면에서만: Goal·Concern·모드·지금 하는 일·맡긴 범위·다음 멈춤), `RGN-MAIN`(현재 화면), `RGN-INSPECTOR`(선택 객체의 출처·근거·작성자·기준 시점. 기본으로 닫혀 있다), `RGN-COMPOSER`(범위를 입력창 앞에 표시하는 자연어 입력. 전역 대화창이 아니다), `RGN-RUNS`(진행 중 서랍. Goal ▸ Concern ▸ WorkUnit으로 묶고 run은 한 줄).

**창 폭** [제안, 03 §3.4.2]. 1280px 이상은 다섯 영역 모두. 1024–1279px은 검사 패널을 서랍으로. 760–1023px은 아이콘만 있는 레일. 760px 미만은 지원하지 않으며 최소 창 크기 760×560은 20이 소유한다.

**최상위 내비게이션** [제안, 03 §3.5.2]. 1 홈(`SCR-HOME`), 2 질문함(`SCR-INBOX`, 배지는 전달된 질문 수), 3 에이전트가 정한 것(`SCR-AUTO`, 새 항목이 있으면 점만), 4 Concern(`SCR-CONCERNS`), 5 Goal(`SCR-GOALS`), 6 관찰 제안(`SCR-OBSERVER`, 2단계), 7 설정(`SCR-SETTINGS`). 복구(`SCR-RECOVERY`)는 항목이 있거나 안전 모드일 때만 보인다. MVP는 여섯 항목이고 2단계에 관찰 제안이 더해져 일곱이 된다. 근거(`SCR-EVIDENCE`), 변화 기록(`SCR-RECORD`), 루프 이력(`SCR-LOOPS`), 평가(`SCR-METRICS`)는 최상위가 아니라 drill-down이다.

**질문함 단일화와 화면 종류** [제안, 03 §3.2.4, IA-02]. 사람 행동 요청은 모두 질문 레코드로 질문함에 든다. 질문 레코드의 `kind`(08 `QuestionKind`)를 화면에서 종류별로 묶는다. 선택 요청(권리 게이트, `SCR-QUESTION`, `choice`·`send_approval`·`scope_change` 등), 정보 질문(정보 게이트, "확인하면 좋은 것"), 기준 확인(`SCR-STIM` 기준 패널 또는 질문), 판단 확인(`SCR-EVIDENCE` 머리 구역, `finding_confirm`), 합의 확인(`SCR-AGREE`, `agreement_confirm`), 결과 확인(`SCR-REVIEW`, `result_review`), Goal 확인(`SCR-GOAL`, `goal_revision`), 예산 확인(`budget_extension`), 복구 선택(`SCR-RECOVERY`, `recovery`), 관찰 제안(`SCR-OBSERVER`, `policy_change`).

**사람 행동 요청 질문 게이트** [결정 12]. 권리 게이트는 답이 있을 때까지 작업이 멈춘다. 정보 게이트는 임시 가정으로 계속하고 만료점을 보인다. 막지 않는 권리 게이트(결과 확인, Goal 확인)는 기록은 즉시, 전달은 다음 작업 경계나 검토 창에 한다. 사람이 정한 마감이 임박한 것만 즉시 전달한다(03 §3.2.4 [판정 J-132]).

**상태 라벨** [제안, 03 §3.3]. 라벨은 정본 상태(08)를 옮긴 것이고 앱은 상태를 추론하지 않는다(§3.3.1). 같은 화면에 함께 나오는 상태 집합끼리는 같은 라벨을 쓰지 않는다. 선택 이전은 질문 상태가, 선택 이후는 WorkUnit 상태가 맡는다. WorkUnit(§3.3.2): `proposed` 준비 중, `negotiating` 합의 확인 필요, `in_progress` 진행 중(수정 요청 뒤에는 "수정 중"), `paused`+`pauseKind` 멈춤 계열, `scope_exceeded` 선택 필요(범위 밖), `submitted` 결과 확인 필요, `accepted` 결과 확인됨·반영 n개 남음, `integrated` 완료, `rejected` 거절됨(해결 안 됨). "완료"는 `integrated`에만 쓴다(IA-08). Concern은 "반영 완료"나 "닫힘"을 쓴다. 재시작으로 중단된 run은 WorkUnit 라벨 옆에 "중단됨(재시작)"으로 겹쳐 보이되 사람이 멈춘 것과 섞지 않는다(§3.3.2, 보고).

**표시 번호** [제안, 03 §3.2.6, IA-07]. "질문 14", "Concern 12"처럼 레코드 종류별로 붙는다. 데몬 투영이 매기므로 기기와 무관하게 같다. 정본에 두지 않는다(보고: 12 §3.5.8).

**세 깊이와 세 묶음** [제안, 03 §3.10, §3.9; 21 UP-3]. 깊이는 `glance`(한눈에)·`review`(검토)·`audit`(감사)다. 감사 깊이는 개발자 보기에서 기본으로 켜진다. 반대 근거·이의·낡음·모름은 한눈에 보기에서도 접지 않는다(03 §3.1.2 6). 방향(N)·이해(E)·실제 변화(M)는 탭으로 나누지 않고 복귀 요약, Concern 개요, 결과 확인에 함께 보인다(03 §3.9).

**전제** [03 §2.1]. 혼자 쓰는 앱이므로 팀·담당자·공유 작업 공간을 정보 구조에 넣지 않는다. UI 문구는 한국어다(결정 37, 05 ADR A7 본문).

### 2.B 주요 화면 (04)

**04의 역할** [04 §1.1, 상단 "소유"]. 화면별 목적·진입 경로·레이아웃·표시 데이터·상태별 표시·인터랙션·문구 예시·사람 조작 횟수를 정하는 화면 상세 명세다. 화면 ID와 이름은 03이, 문구·흐름 규칙은 05가, 컴포넌트는 21이, 뷰 생성은 12가 정본이다. 구현자가 이 문서만 보고 화면을 만들 수 있게 쓴다.

**모델이 초안, 사람은 반응** [결정 18, 04 §2.3]. 주 경로에 사람이 처음부터 채우는 빈 입력란을 두지 않는다. Goal, Concern, 작업 합의, 완료 기준, 기준 후보, 이의 사유는 에이전트 초안이나 선택 가능 항목에서 시작한다. 빈 입력란은 "직접 쓰기" 보조 경로로만 둔다. 사람의 조작은 초안에 대한 반응(그대로 / 고쳐서 / 아님 / 이유 없이 아님)이다. 근거는 v0.2 실사용 기록이다. 필수 필드를 `ㅇ`, `ㅁㄴㅇ` 같은 값으로 채운 기록이 있고, Inquiry Map을 사람이 직접 고치는 장면은 관찰되지 않았다(04 §2.3). 00-README 결정 18은 "대안 2~3개를 골라 받는 상호작용은 쓰지 않는다(recognition over recall)"이다.

**공통 규칙** [04 §3.0]:
- 데이터 상태 5종 [§3.0.3]: 처음 불러오는 중(뼈대, 300ms 뒤 회전 표시), 캐시 먼저("마지막으로 받은 화면" 띠), 빈 상태("없음"과 "모름"을 구분), 오류(`freshness: failed`), 찾을 수 없음(§3.0.5).
- 연결 상태 16값 [§3.0.4]: 연결됨, 느림, 다시 연결하는 중, 서버 PC에 연결할 수 없음, Helm 서버 응답 없음, 인증 실패, 키체인 거부, SSH 실패, 다른 서버, 버전 불일치, 읽기 전용, 다시 맞추는 중, 뷰 낡음, 서버 다시 시작됨, 서버 종료 중, 안전 모드. 상단 막대에 색과 글자로 모든 화면에 보인다(05 §3.9).
- 결정 막기 [§3.0.4 규칙 3–4]: 서버 `freshness`가 `current`가 아니거나 연결이 결정 불가이면 결정 버튼을 막는다. 막힌 버튼에는 이유 문장을 붙인다("연결되면 보낼 수 있습니다. 쓰던 답은 저장해 두었습니다.").
- 낡은 화면 [§3.0.4 규칙 2, 5, 6]: 마지막 뷰를 보이되 "지금"을 기준 시각 문구로 바꾼다. 재연결 뒤 바뀐 항목은 1분간 "다시 연결된 뒤 바뀜"으로 표시한다. 보내지 않은 답이 있으면 자동으로 보내지 않고 "보내지 않은 답 1개가 있습니다"를 보인다.
- 명령 공통 [§3.0.6]: 결정 의도는 `CommandIntentBase`(멱등 키, `basisSeq`)를 가진다. 보내는 동안 같은 버튼을 다시 누를 수 없고 화면 상태는 바꾸지 않는다(21 UI-D03). 결과는 뷰 갱신으로 받는다. 10초 안에 응답이 없으면 "서버가 아직 답하지 않았습니다"를 보인다.
- 거부 세 갈래 [§3.0.6]: 내용(무엇이 규칙에 맞지 않는지와 고칠 방법), 자격(누가 할 수 있는지), 경로(앱 오류로 보고 코드를 개발자 보기에 표시).
- 진행 작업 카드 [§3.0.7]: 머리(WorkUnit 번호, 이름, 상태 라벨, 맡은 역할, "단계 2/4"), 지금 하는 일, 이 일을 하는 이유, 다음 단계, 맡긴 범위(집행 수준 "실제로 막음" / "권고만"), 도움이 필요한 조건, 위험·가정, 마지막 중요한 변화, 활동 요약, 예산. "Agent is working…" 같은 문장은 쓰지 않는다.
- 질문 카드(접힘) [§3.0.7]: 화면 종류 라벨, 지금 정할 것 한 문장, 왜 지금인가, 목적 영향, 추천과 가장 강한 다른 선택(선택 요청에만), 답이 없으면(권리 게이트는 "답이 있을 때까지 멈춰 있습니다", 정보 게이트는 "임시 가정 '…'으로 계속합니다"), 만료점(정보 게이트에만), 미뤘을 때의 영향, 예상 검토 시간, 전달 방식과 시각.

**주요 화면** [04 §3.1–3.5, 보고 보완]:
- `SCR-HOME` 홈 [§3.1]. 진입: 앱 실행(변화가 기준치 미만일 때), 내비 1번, Mod+1, `G H`, 복귀 요약의 "홈으로". 구성: Goal 머리 → "마지막 확인(…) 이후" 띠(선택 필요 n, 확인하면 좋은 것 n, 에이전트가 정한 것 n, 바뀐 것 n) → "지금 주의가 필요한 것" 카드(권리 게이트를 먼저, `attention.maxVisibleDecisions`(기본 3)개까지 펼치고 나머지는 접음, 접힌 권리 게이트는 개수와 종류를 항상 표시) → 진행 중 압축 카드 → Concern 트리. 홈에 전역 대화창을 두지 않는다.
- `SCR-BRIEF` 복귀 요약 [§3.2]. 마지막 사용자 확인 지점 이후의 변화를 머리 한 줄과 절로 요약한다. 절 구성은 0절(미룬 반영 항목이 있을 때만), 1절 Goal과 바뀐 기준, 2절 Concern별 방향·이해·실제 변화, 3절 왜 중요한가, 4절 지금 선택이 필요함(권리 카드), 5절 확인하면 좋은 것, 6절 진행 중 작업, 7절 그대로 두면 일어날 일, 8·9절 접힘(보고: 아홉 절). 원본 로그를 읽지 않고 파악하게 하는 것이 목적이다(§3.2 목적). 복귀 요약은 투영이다.
- `SCR-INBOX` 질문함 [§3.3]. 사람 행동 요청 목록. 왼쪽 목록, 오른쪽 선택한 질문(`SCR-QUESTION`)의 두 칸. 진입: 내비 2번, Mod+2, `G I`, 홈의 "질문함 열기", 알림, 트레이.
- `SCR-QUESTION` 질문 [§3.4]. 질문 하나를 읽고 답한다. 종류가 합의 확인·결과 확인·Goal 확인·판단 확인·복구 선택이면 해당 화면으로 넘긴다. 권리 게이트 카드의 순서는 05 §3.10.4 고정 표현을 따른다: 지금 정할 것, 왜 지금인가, 추천, 다른 선택, 핵심 근거, 아직 모르는 점, 되돌릴 수 있나, 다시 볼 조건. 주 버튼은 최대 3개이고 나머지는 "그 밖에"에 둔다. "그 밖에"에는 기준 고치기, 질문 다시 쓰기, 먼저 알아보기, 미루기, 이의가 항상 있다(21 §3.9 R2, 05 IX-02). 권리 게이트에는 "가정대로 진행"이 없다(05 IX-03). 원함 탐구에서 온 질문에는 추천과 다른 선택이 없다(21 §3.9 R1).
- `SCR-AUTO` 에이전트가 정한 것 [§3.5]. 묻지 않고 정한 것을 종류별로 보고 이의를 건다(결정 8, 불변조건 7). 항목마다 "묻지 않은 이유"가 보여야 한다(04 §6 UT-06).
- `SCR-STIM` 자극 보드 [§3.9]. 원함 탐구의 자극에 요소 단위로 반응한다. 흐름 규칙은 05 §3.2가 정본이다. "가깝다 표시"만 있는 라운드는 바로 닫히지 않고 후속 질문이 붙는다(04 §6 UT-07).
- `SCR-AGREE` 작업 합의 [§3.11]. 에이전트가 만든 합의 초안을 읽고 확정하거나 고친다. write·send 전에 C가 필요하다(결정 15). 확정은 한 번의 조작으로 끝나고, 고친 뒤에도 확정은 한 번이다(04 §6 UT-08).
- `SCR-REVIEW` 결과 확인 [§3.12]. 두 단계다. 결과 확인 단계는 기준별 근거를 보고 판정한다(확인된 것, 확인하지 못한 것, 반대 근거, 전체 영향, 결과가 무효가 되는 조건). 그다음 전체 반영 단계에서 반영 항목을 처리한다. 결과 확인은 사람만 한다(결정 15). 사람 조작 상한은 D 1이다. 반영 항목이 남아 있으면 "완료" 문자열을 쓰지 않는다(04 §6 UT-09).

### 2.C 핵심 상호작용과 문구 규칙 (05)

**질문 받기** [결정 12, 05 §3.1]. 기록과 전달을 나눈다. 전달 방식은 즉시·협상·중재·예약 네 가지다. 알림 강도가 `interrupt`(끼어들기), `notice`(확인), `digest`(묶음)로 나뉘어 데몬이 정한다(§3.1.2). 모든 선택 요청에는 "기준 고치기, 질문 다시 쓰기, 먼저 알아보기, 미루기"를 항상 두고, "승인/거절"만 있는 응답을 만들지 않는다(IX-02, §3.1.5). 질문의 이유와 우선순위는 키로 나온다: `question.reason.*`(가치 충돌, 높은 불확실성, 권한 경계, 이견, 결과 확인, 통합, 맥락 부족)과 `question.priority.*`(권리, 합의·확인, 막힘, 만료 임박, 의존 작업 수, 결과 영향, Concern, 먼저 기록됨) (§3.1.5 표).

**대안을 보이는 규칙** [결정 18, 05 §3.1.6, IX-01·IX-05]. 사실·가능성·결과 탐구 뒤의 결정 질문에서는 추천과 가장 강한 다른 선택을 보인다. 원함 탐구에서는 "하나 고르기"를 여러 반응 중 하나("가깝다")로만 두고, 고르기만 있는 라운드는 명시적으로 닫힐 때만 닫히며 다음 라운드에 세 개 비교가 들어간다(A6). 세 개 비교는 "비슷한 둘과 다른 하나의 이유"로 묻고 "가장 좋은 것"을 묻지 않는다(IX-05).

**이의 걸기** [결정 8, 05 §3.3, IX-06]. 이유 없이도 걸 수 있고, 기본 처리는 "다시 열기"이며 조작 1회로 끝난다. 대상별 효과(§3.3.1): 에이전트가 정한 선택은 `contested`가 되고 관련 Concern이 다시 열린다. 판단은 사실 탐구가 다시 열린다. 루프 계획(에이전트가 설계한 계획 포함)은 전환이 `contested`가 되고 계획이 다시 정해진다. 기준 후보는 원함 탐구로 돌아간다. 결과 제출의 기준별 판정은 "확인 못함"이 되고 수정 요청 초안이 생긴다. 근거가 막히면 이의는 같은 처리에 합쳐진다(§4).

**합의와 결과 확인의 사람 조작** [결정 15, 05 §3.4]. 작업 합의(C)와 결과 확인(A)은 사람만 한다. write·send 전에는 C가, 완료에는 A가 필요하다(00-README 결정 15).

**자연어 입력** [05 §3.5, IX-11]. 범위를 줄이는 명확한 지시는 적용한 뒤 알린다(정정 가능). 기준이나 범위를 바꾸거나 모호하고 영향이 큰 입력은 의미 미리보기 [그렇게 기록]을 거친다.

**알림 정책** [05 §3.7, IX-07·IX-08, A8]:
- 알림은 전달된 질문에만 보낸다. 질문 기록, 진행 보고, 도구 활동, 에이전트가 정한 것, 관찰 제안은 데스크톱 OS 알림도 휴대폰 푸시도 보내지 않는다(§3.7.1).
- 같은 질문은 두 번까지다(전달 때 한 번, 만료 임박 승격 때 한 번). 데스크톱 알림과 휴대폰 푸시를 합쳐 센다.
- 기본 내용은 숨긴다. 제목 "Helm", 본문 "확인할 일이 n건 있습니다."(`notif.hidden.*`). 질문 내용은 사용자가 설정에서 켤 때만 넣는다(`notifications.showContent`, 기본 꺼짐).
- 대상(§3.7.2): 권리 게이트는 켬. 결과 확인은 데스크톱에서 배지만 쓰고 OS 알림은 `notifications.resultReview`가 `immediate`일 때만(00-README 결정 60). 합의 확인은 켬. 만료 임박 승격은 켬. 협상 전달은 기본 끔(`notifications.negotiated`). 복구 선택은 켬. 연결 끊김은 끔(앱 안 배너만).
- 알림 결정은 데몬이 한다(§3.7.1 4번). 앱은 전달 결정을 받아 표시만 정한다(20 §3.10.1).

**키보드 단축키** [05 §3.8, IX-09, A7]:
- 한 글자 단축키는 물리 키(`KeyboardEvent.code`)로 판정한다. 한글 입력 상태에서도 같은 키가 동작한다. 조합 중 이벤트는 무시한다(A7).
- 텍스트 입력에 초점이 있으면 한 글자 단축키는 동작하지 않는다. Mod 조합과 Esc만 동작한다.
- OS가 쓰는 조합(⌘H, ⌘M, ⌘Q, ⌘W, ⌘Tab, Ctrl+Alt+Del 등)은 쓰지 않는다.
- 두 키 이동(`G` 다음 키)은 1초 안에 누른다. 첫 키를 누르면 아래에 안내를 잠깐 띄운다.
- 전역: Mod+K 명령 팔레트, Mod+1~7 최상위 화면(홈, 질문함, 정한 것, Concern, Goal, 관찰 제안, 설정), Mod+, 설정, `/` 입력창, `?` 도움말. 앱 밖에서도 동작하는 "빠른 입력"은 기본 조합을 두지 않는다(macOS ⌘⇧H가 Finder와 겹침).

**접근성** [05 §3.9, 제안]. 목표는 WCAG 2.1 AA다. 상태·위험·게이트·N/E/M·품질 배지를 색만으로 나타내지 않는다. 반투명 표면의 대비는 가장 나쁜 배경에서 잰다. 모든 동작은 키보드로 된다. 영역마다 랜드마크를 둔다. 같은 카드는 30초에 한 번 이상 스크린 리더에 다시 알리지 않는다. 글자 200%에서 잘리지 않는다. `lang="ko"`, `word-break: keep-all`. 데스크톱 버튼·칩의 누르는 영역은 24×24px 이상, 모바일은 44×44pt 이상(03 §3.12). "움직임 줄이기"를 켜면 전환 애니메이션을 끈다.

**한국어 문구 지침** [05 §3.10, IX-10, A9]:
- 목소리 다섯 가지 [§3.10.1]: 직접 확인한 것을 먼저 말한다. 지금 읽어야 하는 이유를 먼저 말한다. 시스템이나 에이전트를 사람처럼 꾸미지 않는다. 불확실성을 겁주거나 숨기지 않고 다음 행동과 연결한다. 선택이 무엇을 바꾸는지 바로 보인다.
- 문장 순서 [§3.10.2]: 무엇이 달라졌는가 → 왜 중요한가 → 그대로 두면 무엇이 일어나는가 → 사용자가 무엇을 할 수 있는가.
- 문체 [§3.10.3]: 문장은 합니다체, 라벨과 머리는 명사형, 버튼은 결과를 말하는 동사구. 느낌표를 쓰지 않는다. "로딩 중..."을 쓰지 않는다. 이모지와 장식 기호를 쓰지 않는다. Goal과 Concern 밖의 영어 명사는 화면 문구에 쓰지 않는다. 레코드 종류와 이벤트 이름은 개발자 보기에서만.
- 고정 표현 [§3.10.4]: 선택 요청은 "지금 정할 것 / 왜 지금인가 / 추천 / 다른 선택 / 핵심 근거 / 아직 모르는 점 / 되돌릴 수 있나 / 다시 볼 조건". 결과 확인은 "확인된 것 / 확인하지 못한 것 / 남은 제한 / 남은 전제 / 반대 근거 / 전체 영향 / 결과가 무효가 되는 조건". 작업 합의는 "이 일을 하는 이유 / 결과(완료 기준) / 맡긴 범위 / 제출할 근거 / 멈출 조건 / 다음 확인 시점 / 에이전트가 이해한 것".
- 버튼 [§3.10.5]: "확인" 대신 "이 선택으로 진행" 또는 "(대상)을 (효과)하기". "승인" 대신 "결과 확인"(결과 확인 화면) 또는 "(대상)을 (효과)하기"(권리 게이트). "거절" 대신 "수정 요청" 또는 "거절(해결 안 됨)". "계속" 대신 "맡긴 범위 안에서 다시 시작". "취소" 대신 "작업 중단" 또는 "닫기". "자세히" 대신 "근거 보기". "Retry" 대신 "마지막 확인 지점부터 다시 실행"(작업) 또는 "다시 불러오기"(화면).
- 문구 키 [IX-10, A9, 24 ADR-05-04]: 데스크톱과 TUI와 휴대폰이 쓰는 문구·라벨 목록은 `packages/ui-language`(`@helm/ui-language`) 한 곳에 키로 둔다. 데몬은 키와 인자만 보내고 클라이언트가 문장을 만든다. 데몬이 완성 문장을 보내는 방식은 기각했다(문구 수정 때 데몬 배포가 필요해진다).

### 2.D 데스크톱 앱 (20)

**구조** [제안, 20 §3.1]. 프로세스는 Tauri 앱 하나다. 웹뷰 창 `main` 하나를 쓰고, 닫기 단추는 창을 숨긴다. 사이드카 프로세스는 없고 SSH 경로를 쓸 때만 OpenSSH 자식 프로세스가 전송마다 하나씩 생긴다. 웹뷰는 React 19 SPA다(앱에 묶어 배포, 21 UI 부품 사용). Rust(Tauri 코어)는 WSS와 SSH 전송, `helm-blob` 스킴, 프로필 파일, OS 키체인, 페어링 HTTP와 SSH, 트레이·배지·창을 맡는다. 데몬(17)이 정본과 투영과 전달 결정을 가진다. 웹뷰의 CSP에는 데몬 주소가 없고, 웹뷰가 외부와 통신하는 길은 IPC와 `helm-blob` 스킴 둘뿐이다.

**책임 분담** [20 §3.2 Rust, §3.3 웹뷰]:
- Rust의 책임: `transport/`(WSS는 rustls, SSH는 `ssh -W` 자식 프로세스), `blob.rs`·`http_stream.rs`, `profiles.rs`(연결 프로필 파일), `secrets.rs`(기기 토큰을 OS 키체인에), `pairing.rs`, `os/tray.rs`·`os/badge.rs`·`os/window.rs`, `diag.rs`, `error.rs`. 원칙: Rust는 웹뷰가 할 수 없는 일과 웹뷰에 두면 안 되는 비밀만 맡는다. Rust 코드는 Helm 도메인 타입과 JSON-RPC 메서드를 모른다. 프레임은 해석하지 않고 문자열로 넘긴다.
- Rust가 하지 않는 일: 재접속 시점 판단, JSON-RPC 요청 ID 관리, 이벤트 해석, 알림을 띄울지 판단, 트레이에 보일 숫자 계산.
- 웹뷰의 책임: 19 클라이언트 코어(`@helm/client`)가 JSON-RPC, hello, 구독·재개, 순서 검사, 명령 재전송을 맡는다. 연결 상태 기계는 19 코어가 소유하고 앱은 경로 선택과 사용자용 상태 계산을 맡는다. 뷰 캐시, 화면 조립, 의도 변환, OS 기능 호출(알림, 단축키, 딥 링크 수신)을 한다.
- 웹뷰가 하지 않는 일: 데몬 직접 연결, 토큰 읽기, 파일 시스템 접근, 셸 실행.

**"앱에 Helm 로직이 없다"의 근거** [APP-D01, 20 §2.1, §3.9.3]. APP-D01: 앱은 투영을 계산하지 않는다. 화면 데이터는 데몬의 뷰(`view.get`)를 받아 캐시하고, 이벤트는 무효화 태그로 "어느 뷰가 낡았는가"를 알리는 데만 쓴다. 이 선택은 결정 32에서 도출한다. 앱은 이벤트를 접지 않는다(ADR-20-05). 도메인 낙관적 갱신을 하지 않는다(§3.9.7, 결정 14). 알림 여부는 데몬이 기록한 전달 이벤트를 받아 정하고 앱이 스스로 판단하지 않는다(APP-D11). 트레이 숫자는 `tray` 뷰의 값을 그대로 쓴다(§3.10.2).

**기술 스택** [§3.7, 2026-10-11 기준]. npm은 `^` 없이 고정하고 Cargo는 `=x.y.z`로 고정한다. 셸 Tauri 2.12.3(2.11.6 미만 금지), `tauri-build` 2.7.2, CLI 2.12.2. 공식 플러그인은 single-instance 2.5.3(반드시 첫 번째로 등록), deep-link 2.6.1(`helm://` 스킴), notification 2.6.0, global-shortcut 2.4.1, autostart 2.7.0, window-state 2.5.0, store 2.5.0(화면 설정 `settings.json`, 비밀 금지), dialog 2.8.2, opener 2.7.1, clipboard-manager 2.4.2, log 2.10.1, os 2.4.0. 쓰지 않는 것: stronghold(2026-07 중단 공지), shell, fs, http, websocket, updater, process(§3.7.1). React는 19.3.0이다(결정 41; 버전은 §3.7.3, 보고). 00-README 결정 32의 React 18 표기는 41로 대체되었다. TanStack Query 5, zustand 5.0.15, idb 8.0.4 등 나머지 npm 버전은 §3.7.3에 있다(보고).

**상태 관리** [ADR-20-05, §3.9.3 표]:
- 데몬 뷰: TanStack Query 5 캐시 + IndexedDB 영속(§3.9.5). `staleTime: Infinity`로 두고 신선도는 시간이 아니라 이벤트로 판단한다. 포커스 때 재조회를 끈다.
- 연결 상태: 코어 상태와 앱 연결 모델(`AppConnModel`)을 zustand `connStore`에 둔다. 상태 기계는 코어, 사용자용 상태 계산은 순수 함수다.
- 휘발 스트림(에이전트 출력 글자): zustand `liveTextStore`. 정본 로그에 없으므로 재접속 때 비우고 `active`로 다시 채운다.
- 진행 중 명령함: IndexedDB `pending`과 `useCommand` 훅. 재시작해도 남는다.
- 화면 지역 상태(펼침, 탭, 입력 초안): 컴포넌트 상태, 오래 남길 것은 `uiStore`, 초안은 IndexedDB `drafts`.
- 앱 설정: `tauri-plugin-store`의 `settings.json`을 시작 때 `uiStore`로 읽는다.
- React 19 기능: `use()`와 Suspense는 1차에 쓰지 않는다. `useOptimistic`은 도메인 데이터에 쓰지 않는다. `ref`는 일반 prop이라 `forwardRef`가 필요 없다(21 §3.6, 20 §3.9.3).
- IndexedDB 이름은 `helm-desktop`이고 모든 키에 `serverId`가 붙는다(보고: 20 §3.9.5).

**연결 모델** [APP-D02~D05, D07, 20 §3.8]:
- 프로필: 서버 하나가 프로필 하나다. 경로는 1개 이상이고 배열 순서가 시도 순서다. 파일 `<app_config_dir>/profiles.json`에는 토큰이 없다(§3.8.1). 기본 템플릿 "Tailscale (권장)"은 wss 하나와 ssh 하나를, "SSH만"은 ssh 하나를 둔다.
- 경로 두 가지: `wss`는 `https://server.tail7ad0b4.ts.net:8448`(Windows의 `tailscale serve` → tailnet 리스너 `127.0.0.1:7840`)을 쓰고, `ssh`는 `ssh -W 127.0.0.1:7841`(→ loopback 리스너)을 쓴다(17 D17-09, 20 §3.1 그림).
- SSH는 Rust SSH 라이브러리가 아니라 시스템 OpenSSH 클라이언트를 자식 프로세스로 실행한다(APP-D03, ADR-20-02). 호스트 키 기본은 `strict`다. SSH 키는 전송 인증이고 기기 인증을 대신하지 않는다(APP-D04).
- 여러 경로(APP-D05, ADR-20-03, §3.8.10): 순서대로 시도하고 동시에 여러 경로를 시도하지 않는다. 네트워크 계열과 SSH 차단 계열만 다음 경로로 넘어간다. 토큰 계열(`needs_pairing`), 버전 불일치, `wrong_server`는 넘기지 않는다. 연결된 뒤에는 경로를 바꾸지 않는다. 다음에 끊기면 첫 경로부터 다시 시도한다. `pinned`이면 첫 활성 경로만 쓴다.
- 연결 상태 기계(§3.8.8): `idle → connecting → handshaking → syncing → ready`이고, 실패하면 `backoff`·`needsUser`·`closed`로 간다. 상태 기계와 백오프는 19 `HelmClient`(`@helm/client`)가 소유한다. 앱은 `MultiRouteTransport`(경로 선택기)와 앱만 아는 실패 분류를 맡는다.
- 사용자용 연결 상태(§3.8.9): 04 §3.0.4의 16값으로 계산하며 `decisionsAllowed`로 결정 버튼을 막을지 정한다. 상태 값은 21 `ConnectionUiState`와 같다.
- 인증: 기기 토큰은 Rust 키체인에만 있고 웹뷰 메모리에 두지 않는다(APP-D02). 페어링 코드 방식은 Rust가 바로 키체인에 저장하고, SSH 발급은 원격의 `helm device issue`를 실행해 결과를 키체인에 저장한다(보고: §3.8.7).
- 대용량 파일: 웹뷰는 HTTP를 직접 하지 않는다. Rust의 `helm-blob` 스킴이 기기 토큰을 붙여 `/files/b/<blobId>`를 받고 디스크에 캐시한다(APP-D12).

**재접속과 뷰 동기화** [APP-D08, D09, D10, §3.9.6–7]:
- 재접속은 저장한 위치 `{storeId, seq}`부터 재개한다. 데몬이 범위 밖이라고 하면(`2001 replay.outOfRange`) 뷰를 낡음으로 표시하거나 버리고 `head`부터 구독한다.
- 명령마다 멱등 키(`ik_<ULID>`)와 `basisSeq`를 붙인다. 응답 전에 끊긴 명령은 IndexedDB 진행 중 명령함에 두었다가 같은 키로 다시 보낸다. 연결이 없을 때 새 사람 결정은 받지 않는다(APP-D09, 판정 J-02). 오프라인 송신 큐는 두지 않는다.
- 뷰 캐시와 위치는 서버별로 IndexedDB에 영속한다. 앱을 오프라인으로 시작해도 마지막 뷰를 읽기 전용으로 보인다(APP-D10).
- 명령 결과 처리(보고: §3.9.7): 3004 conflict, 3008 alreadyResolved, 3009 superseded, 3001·3002·3005 rejected, 5003 readOnly(적용되지 않음이 확정, 자동 재전송 없음), 3007은 `retryAfterMs` 뒤 같은 키로 재시도한다.

**IPC 명령과 이벤트** [§3.4.2, §3.5]. 화면 코드는 `platform/ipc.ts`의 타입 있는 함수만 호출하고 `invoke`를 직접 부르지 않는다. 명령(`build.rs`에 21개 등록): `profiles_list`, `profile_upsert`, `profile_delete`, `credential_status`, `credential_forget`, `route_check`, `pairing_with_code`, `pairing_via_ssh`, `transport_open`, `transport_send`, `transport_close`(수신은 `Channel<TransportEvent>`로), `blob_upload`, `blob_upload_path`, `blob_cache_clear`, `tray_update`, `badge_set`, `window_reveal`, `appearance_get`, `window_effect_set`, `app_info`, `diag_bundle`. 조건부(1차 미등록): `credential_rotate`, `device_sign_challenge`. Rust→웹뷰 이벤트(`app://` 접두어): `app://navigate`, `app://tray-action`, `app://appearance`, `app://window`. 모든 명령은 `async`이고 `Result<T, AppError>`를 돌려준다.

**트레이·OS 알림** [§3.10]:
- 알림 처리 순서(§3.10.1, 1–8): 재전송 중에 받은 전달은 하나씩 띄우지 않고 센다. `channel`이 `app`이 아니거나, `surface`에 `os`가 없거나, `targetDevices`가 이 기기를 담지 않거나, `expiresAt`이 지났으면 띄우지 않는다. 같은 `deliveryId`는 한 번만 띄운다. 방해 금지(`attention.snoozeUntil`)나 조용한 시간(`attention.quietHours`) 중에는 띄우지 않는다. `interrupt`는 전달 뒤 5초 안에 OS 알림을 띄운다. 시간당 상한(`attention.interruptsPerHour`, 기기 합산)은 데몬이 센다. 창이 열려 있고 `target` 화면이 열려 있으면 OS 알림 대신 앱 안 배너로 보인다(표시 방법의 선택이고 전달 여부 판단이 아니다). 클릭은 플러그인 2.6.0부터 `onAction`으로 오고, `extra.target`으로 화면을 연다.
- 플랫폼 차이(§3.10.1 표): macOS 개발 실행 알림은 Terminal 이름으로 나오고 권한은 시스템 설정에서 정한다. `requestPermission`은 데스크톱에서 항상 허용을 돌려준다. 띄운 알림을 지우는 `removeActive`는 동작하지 않는다. Windows는 설정 > 시스템 > 알림이다.
- 트레이(`SCR-TRAY`, §3.10.2): Rust `TrayIconBuilder`로 만든다. 메뉴는 "Helm · <연결 상태>", 선택 필요 n(→ 질문함), 확인하면 좋은 것 n, 진행 중 n과 최대 5개 항목으로 구성한다. 숫자는 `tray` 뷰 값을 그대로 `tray_update`에 넘긴다. 연결이 없으면 첫 줄이 "Helm · 연결 안 됨"이고 [연결 화면 열기]가 생긴다. Windows는 왼쪽 클릭이 창 보이기, 오른쪽 클릭이 메뉴다.
- 배지(§3.10.3, 보고): macOS Dock과 Windows 작업 표시줄 오버레이에 "선택 필요" 수만 보인다.
- 창과 기동(§3.10.5, 보고): 닫기 단추는 창을 숨긴다. 로그인 시 시작은 기본으로 꺼져 있고 `--background`로 뜬다. single-instance는 첫 번째로 등록한다.
- 키체인(§3.10.7, 보고): service `dev.helm.desktop`, account `device-token/<serverId>/<deviceId>`. macOS는 자체 서명 인증서로 서명한다(ADR-20-08).

**빌드·배포·테스트** [§3.12–3.13, ADR-20-06~09]. macOS 빌드는 Mac에서 `run-on mac`으로 한다(APP-D13). Windows 설치 파일은 WSL에서 NSIS로 교차 빌드하고 GitHub Actions Windows 러너를 대체 경로로 둔다(ADR-20-06). 1차에는 자동 업데이트를 넣지 않고 앱이 hello에서 호환 범위를 확인해 맞지 않으면 갱신 방법을 안내한다(ADR-20-07, APP-D14). E2E의 주 경로는 같은 SPA를 Playwright로 가짜 데몬에 붙여 돌리는 것이고, Tauri 셸은 WebdriverIO `@wdio/tauri-service`로 macOS·Windows 스모크만 한다(ADR-20-09, APP-D15).

### 2.E UI 시스템 (21)

**UI 원칙** [21 §3.1, UP-1~16]. 상태 먼저, 대화는 보조(UP-1). 차이 먼저(UP-2). 세 깊이(UP-3). 의미는 글자·아이콘·모양으로, 색은 보조(UP-4). 구분해야 하는 것은 다르게 그린다(UP-5). 모름·이견·낡음을 숨기지 않는다(UP-6). 초안을 내밀고 반응을 받는다(UP-7). 고르기만 있는 상호작용을 만들지 않는다(UP-8). 의인화 금지(UP-9). 결정 버튼은 결과를 말하고 `[승인] [거절]` 묶음을 만들지 않는다(UP-11). 정상 진행에는 토스트와 알림을 띄우지 않는다(UP-13). 유리는 떠 있는 것에만 쓴다(UP-14). 빛은 에이전트에게만 쓴다(UP-15). 주 행동은 ink 버튼이고 강조색은 한 번만 쓴다(UP-16).

**라이브러리** [21 §2.5, 결정 41·50]. 헤드리스 부품은 Radix Primitives(`radix-ui` 1.8.0)를 바탕으로 쓰고 shadcn/ui 소스를 복사해 고쳐 쓴다(결정 50은 이를 결정 41의 "부품 직접 제작"에 포함한다). Base UI는 후보였으나 채택하지 않았고 React Aria Components는 기각했다(§2.5.2 표). 스타일은 Tailwind CSS v4와 CSS 변수 토큰과 cva를 쓴다. 아이콘은 lucide-react다. 그래프·차트 라이브러리는 1차에 넣지 않는다(ADR 21-9). assistant-ui는 대화 스레드의 primitives와 `ExternalStoreRuntime`만 쓴다(ADR 21-6).

**대안 고르기 금지 규칙** [21 §3.9, 결정 18]:
- R1: 원함 탐구에서 온 질문은 추천·다른 선택·`pickOne` 답 형태를 그리지 않는다.
- R2: 질문 카드의 주 버튼은 최대 3개이고 나머지는 "그 밖에"에 둔다. "그 밖에"에는 기준 고치기, 질문 다시 쓰기, 먼저 알아보기, 미루기가 항상 있다.
- R3: 대안 표시는 순서만 바꾼다. 부품에는 `maxOptions` 같은 자르기 prop이 없다. `initiallyVisible`은 처음 보이는 개수일 뿐이다.
- R4: 고르기 부품(`RadioGroup`, `Select`, 단일 선택 `SegmentedControl`)은 설정·다이얼·필터·분류 입력에서만 쓴다.
- R5: 사람이 채워야 하는 부품(작업 합의, Goal 수정, 기준 수정)은 초안이 있는 상태로 연다.
- R6: 반응(`near`, `triad_odd`, `strength: 2`)은 결정이 아니라 반응 관찰로만 올린다.
- R7: "A와 B 중 무엇을 원하시나요?", "어느 쪽이 좋으세요?", "계속할까요?", `[승인] [거절]` 같은 문구를 쓰지 않는다.
- 강제 방법: 부품 API와 테스트로 강제한다(ADR 21-7).

**테스트 관문** [21 §6.6, U1–U9]. U1 토큰·스타일: 대비 관문 통과, neutral 11단계, Caustic 출처 NOTICE. U2 L0: 부품마다 상태 이야기 전부, axe 위반 0, 한글 입력 상태 단축키 테스트. U3 L1: 모든 값에 골든. U4 C/A 부품: 질문 카드 상태와 깊이, 낡은 기준 거부 이야기. U5 복귀·셸: 복귀 요약 아홉 절 렌더, 셸 크롬은 유리·본문은 불투명. U6 근거 트리 단위 테스트. U7 원함 탐구 반응 두 경로. U8 나머지 시각화. U9 대화 `ExternalStoreRuntime` 연결. 전체 관문은 `just ui-check`, `just ui-test`, `just ui-visual`이다.

### 2.F 모바일 PWA (26)

**휴대폰의 범위** [결정 42, 26 §1.2–1.3]. 할 일: 질문함을 보고 질문에 답하기(묶음 답하기 포함, `SCR-M-INBOX`·`SCR-M-QUESTION`), 권리 게이트를 허락·하지 않기·미루기, 작업 합의 확인, 결과 확인(산출물을 본 뒤에만. 큰 산출물과 취향형은 미루기만), 에이전트가 정한 것에 이의(`SCR-M-AUTO`), 복귀 요약 요약판(`SCR-M-BRIEF`), 진행 중 작업을 한 줄씩 보고 안전하게 멈추기(`SCR-M-WORK`), 복구 선택, 안전 모드 풀기, 알림 받기(앱이 꺼져 있어도), 페어링·기기 권한 없애기·알림 설정. 하지 않는 일: 탐구 화면, 자극 보드, 다이얼, 관찰 제안, 변화 기록, 근거 체인, 새 일 입력. 답할 수 없는 질문에는 "데스크톱에서 답하기"와 미루기만 둔다(03 §3.12 원칙 3). 휴대폰도 데스크톱과 같은 메서드·명령·이벤트를 쓴다(03 §3.12 원칙 2).

**구현 방식 선택** [결정 47, 26 §3.1]. 후보는 네 가지다: A Tauri v2 모바일(iOS), B PWA(데몬이 서빙하고 Safari에서 홈 화면에 추가), C React Native(Expo), D 네이티브 Swift. 결정 47로 B를 택했다: 모바일 클라이언트는 데몬이 서빙하는 홈 화면 웹 앱(PWA)이고 알림은 Web Push다. 근거(§3.1.2, 외부 사실 X-1·X-2·X-4): 무료 Apple ID로 서명한 앱은 프로파일이 7일 뒤 만료되고, 무료 계정은 Push capability와 TestFlight를 쓸 수 없다. 홈 화면 웹 앱은 계정과 만료 없이 Web Push를 받는다. 경로 A(Tauri iOS + APNs)는 Apple 개발자 프로그램이 지금 없으므로 이후 검토한다(MOB-D11, 결정 57, §3.1.5 조건).

**구조** [26 §3.2]. iPhone 안에 Tailscale 앱(VPN On Demand 권장), 홈 화면 웹 앱 "Helm"(출처 `https://server.tail7ad0b4.ts.net:8448`), React 19 SPA(`/m/`), `@helm/client-react`(뷰 캐시 IndexedDB, 초안, `decisionsAllowed`), `@helm/client`(`@helm/client/browser` 전송), 서비스 워커 `/m/sw.js`(앱 껍데기 캐시, push, notificationclick), 쿠키 `__Host-helm_dt`. 데몬과는 WSS `/rpc`, HTTPS `/m/*`와 `/files/*`, 그리고 Web Push(RFC 8291 암호화)로 통한다. 패키지는 `apps/mobile`이며 데스크톱과 같은 `@helm/ui`·`@helm/client`·`@helm/client-react`·`@helm/ui-tokens`·`@helm/ui-language`를 쓴다(MOB-D01, ADR-26-01).

**데몬의 모바일 HTTP 경로** [26 §3.3.2]. 기능 플래그 `clients.mobile`(23, 기본 꺼짐)이 꺼져 있으면 아래 경로는 모두 404이고 휴대폰 페어링도 받지 않는다. `GET /m/`과 확장자 없는 경로는 `index.html`을 `no-cache`로 준다. `GET /m/assets/<해시>`는 immutable로 준다. `GET /m/sw.js`와 `GET /m/manifest.webmanifest`는 `no-cache`다. `POST /m/pair`는 페어링 코드로 쿠키를 설정하고 본문에 토큰을 싣지 않는다. `GET /m/whoami`는 쿠키로 기기 정보를 준다. `POST /m/logout`은 쿠키를 지우지만 기기 권한은 없애지 않는다. `POST /m/cmd`는 숨김 직전의 진행 중 명령 하나를 HTTP로 보낸다. 모든 경로는 `tailnet` 리스너에만 있다.

**인증: 쿠키로 나르는 기기 토큰과 scope** [MOB-D03, MOB-D13, 26 §3.3.3]. 쿠키는 `__Host-helm_dt=<기기 토큰>; Path=/; Secure; HttpOnly; SameSite=Strict`다. 스크립트는 읽지 못한다. 쿠키를 받는 곳은 tailnet 리스너의 `GET /rpc` 업그레이드, `/files/*`, `/m/whoami`, `/m/cmd`뿐이다. 데스크톱 토큰이 쿠키로 오면 1008(`carrier_mismatch`)이다. 휴대폰 기기는 `decideMobile` scope를 받는다. 화면이 쓰는 명령만 허용하고 범위·다이얼·모드·새 일·권한 명령은 거부한다.

**연결 수명주기: 보임과 숨김** [MOB-D04, 26 §3.3.5]. iOS는 백그라운드에서 연결을 유지하지 못하므로(X-8) 앱은 숨겨질 때 연결을 닫고(1000), 보이면 백오프를 무시하고 바로 다시 붙는다. 상태는 `starting`(잠금 `helm-conn-<serverId>` 획득 시 `visible`, 못 얻으면 `follower`로 읽기 전용, 페어링이 없으면 `unpaired`로 온보딩), `visible`, `hiding`(`visibilitychange` 숨김 또는 `pagehide`, `presence.report { state: "hidden" }`), `hidden`(진행 중 명령이 없거나 2초가 지나면 `client.stop()`과 가림막)이다. 접속 상태는 presence `locked`를 보내지 않고, 휴대폰의 `active` 문턱은 2분이다(MOB-D09).

**알림: Web Push** [MOB-D02, D05~D07, D14, 26 §3.4]:
- 푸시하는 것 [§3.4.2]: 질문(전달 결정이 기록되고 강도가 `interrupt` 또는 `notice`인 것: 범주 `question`, `rights_gate`, `review`, `goal`, `recovery`), 묶음(방해 금지가 끝날 때 열린 질문이 있으면 1개, 시간당 상한을 넘은 전달은 그 시간이 끝날 때 1개), 결과 확인 묶음(`notifications.resultReview`가 `daily_digest`이면 설정 시각 `resultReviewDigestAt`, 기본 19:00에 1개), 데몬 상태(안전 모드 진입, 읽기 전용 진입의 사유별 1회, 강도 `interrupt`. 풀릴 때는 보내지 않는다), 시험(`device.testPush`). 진행 보고, 에이전트가 정한 것, 관찰 제안은 보내지 않는다.
- 언제 보내나 [MOB-D05, §3.4.3]: 강도가 `interrupt` 또는 `notice`인 전달에만 보낸다. 어떤 기기든 `active`이면 보내지 않는다. `interrupt`는 연결된 기기가 있으면 60초 뒤 아직 열람이 없을 때 보낸다.
- 결과 확인 알림 설정 [MOB-D14, 00-README 결정 56]: `none`(기본, 알리지 않고 복귀 요약에서 확인), `daily_digest`(설정 시각에 묶음 1개), `immediate`(결과 확인 질문마다).
- 내용 [MOB-D07, §3.4.4]: 데몬은 payload에 문구 키와 인자를 늘 싣는다(종단 암호화). 내용을 보일지는 기기 설정 `notifications.showContent`(기본 꺼짐)로 서비스 워커가 정한다. Declarative Web Push 형식이라 서비스 워커가 깨어나지 않아도 뜬다(X-5).
- 등록 [MOB-D06, §3.4.6]: 원문 푸시 등록은 운영 테이블 `push_tokens`(09)에만 둔다. 이벤트와 08 Device의 `push`에는 해시, 앞 8자 `tokenHint`, 호스트, 설정만 둔다. 허용되지 않은 호스트를 엔드포인트로 등록하면 `push.endpoint_not_allowed`로 거부한다(MF-07).
- 키 [§3.4.7, ADR-26-02]: VAPID 개인 키는 제품 비밀이다. 데몬의 바깥 연결에 `push.apple.com`이 더해진다.

**휴대폰 화면** [03 §3.12, 26 §3.5]. 셸은 아래 탭 네 개(질문함 / 요약 / 정한 것 / 진행 중), 머리의 연결 표시, 설정 링크로 된다. 한 열이며 너비 360–430px이고 누르는 영역은 44×44pt 이상이다. 키보드 단축키는 두지 않는다. 화면은 `SCR-M-INBOX`(권리 게이트와 막는 질문을 먼저, 그 밖은 접음, 묶음 답하기), `SCR-M-QUESTION`(카드 펼침. "깊은 검토" 질문은 요약과 "데스크톱에서 보기 권장"을 붙이되 답은 할 수 있다), `SCR-M-BRIEF`(1·4·5·6·7절과 2·3절 포함한 요약판), `SCR-M-AUTO`(종류별 개수와 목록, 이의 이유는 선택, 기본 처리 "다시 열기", 목록을 열면 봤음으로 기록), `SCR-M-WORK`(진행 작업 카드 한눈에 보기, 안전하게 멈추기), `SCR-M-CONNECT`(진단 문장, 안전 모드 사유와 풀기, 이 기기 권한 없애기), `SCR-M-SETTINGS`, `SCR-M-ONBOARD`(설치 안내, 페어링 코드, 알림 켜기와 조용한 시간 제안 23:00~08:00)다.

**휴대폰에서 답하는 질문 형식** [03 §3.12 표, MOB-D08]. `answer`와 `confirm_candidate`는 답한다. `approve_action`은 허락·하지 않기·범위 줄여 진행·미루기를 쓰고, "고쳐서 허락"은 데스크톱에서 한다. `result_review`는 산출물을 연 뒤에만 결과 확인을 누를 수 있고, `mobileReviewable`이 거짓이면 미루기만 둔다. 작업 합의 확인은 이 범위로 맡기기, 넓어진 부분 빼고 맡기기, 맡기지 않기 세 버튼이다. `choose_one`은 답한다(추천 먼저, 나머지는 "+n" 펼침). `reaction`(자극 반응)은 데스크톱에서 답하기와 미루기만 둔다. 복구 선택은 답한다.

**공통 상태와 결정 버튼 활성 조건** [26 §3.5.11, 04 §3.0.4, 20 §3.8.9]. 같은 규칙을 쓴다. Tailscale이 꺼져 있으면 서버 이름을 찾지 못하고 캐시를 읽기 전용으로 보이며 "Tailscale 앱이 켜져 있는지" 확인하라고 안내한다(MF-01).

**빌드·배포** [26 §3.6, MOB-D10]. PWA 묶음은 Mac 없이 서버에서 빌드하고 데몬 릴리스에 들어가 데몬과 같은 판으로 배포된다. 정적 파일 원본은 현재 릴리스의 `web/mobile/`이다. 데몬은 시작할 때 파일 목록과 해시를 메모리에 올린다.

**지원 기기** [결정 49, MOB-D12]. iOS 26 이상의 iPhone과 iPad다. Android 경로는 두지 않는다(00-README 결정 49).

**iOS와 푸시의 외부 사실** [26 §2.3, X-1~X-16, 확인: 2026-10-12 검색]:

**휴대폰 ADR 26-01~06 제목** [24 정본과 같음]: 01 모바일은 데몬이 서빙하는 PWA로 만든다. 02 꺼져 있을 때의 알림은 데몬이 직접 보내는 Web Push다. 03 모바일 기기 토큰은 HttpOnly `__Host-` 쿠키로 나르고 scope를 줄인다. 04 휴대폰은 숨겨지면 연결을 닫고 보이면 바로 다시 붙는다. 05 휴대폰 푸시는 `interrupt`와 `notice` 질문에만, 사람이 다른 기기 앞에 있으면 보내지 않는다. 06 푸시 등록 원문은 운영 테이블에 두고 이벤트에는 해시만 둔다.

## 3. 동작 흐름

**3.1 질문에 답하기 (데스크톱·휴대폰 공통)** [03 §3.2.4, 05 §3.1, 04 §3.0.6, 20 §3.10.1, 11·12]:
1. 에이전트가 질문 레코드를 `pending`으로 기록한다. 데몬이 전달 방식(즉시·협상·중재·예약)을 정하고 `question.delivered`를 기록한다. 이 이벤트에는 `urgency`, `channel`, `surface`, `deliveryMode`, `copy`(문구 키와 인자)가 있다.
2. 데스크톱 앱은 `channel`이 `app`이고 `surface`에 `os`가 있을 때만 OS 알림을 띄운다(§3.10.1). 휴대폰은 강도가 `interrupt`·`notice`이면 푸시를 보낸다(26 §3.4.3).
3. 사람이 질문함이나 질문 화면에서 답하면 명령 의도(멱등 키와 `basisSeq`를 붙인 `question.answer` 등)가 나간다. 보내는 동안 같은 버튼은 다시 누를 수 없다. 결과는 뷰 갱신으로 받고, 받아들여졌으면 "적용됨"을 2초 보인다(04 §3.0.6).
4. 거부되면 세 갈래 문구 중 하나로 보인다. 가정이 이미 확정된 뒤 도착한 답은 3008로 거부되고, 확정 값을 보이며 쓰던 답은 이의 초안으로 옮긴다([판정 J-120], 04 §3.0.5).

**3.2 연결이 끊기거나 뷰가 낡을 때** [04 §3.0.4, 20 §3.8.8, §3.9.8]:
1. 마지막으로 받은 뷰를 읽기 전용으로 보이고, "지금"을 기준 시각 문구로 바꾼다.
2. 결정 버튼을 막고 이유 문장을 붙인다. 쓰던 답은 기기에 보존하고 자동으로 보내지 않는다.
3. 재연결되면 바뀐 항목에 1분간 "다시 연결된 뒤 바뀜"을 붙이고, 보내지 않은 답이 있으면 "보내지 않은 답 1개가 있습니다"를 보인다.

**3.3 연결 시도 순서** [20 §3.8.8, APP-D05]:
1. 활성 경로를 순서대로 `transport_open`한다. 30분 미룬 경로는 맨 뒤로 보낸다.
2. 업그레이드 101까지 가면 연결된 것이다. 토큰 계열 실패(`http_unauthorized`, `credential_missing`, `keychain_denied`)는 중단하고 `needsUser`로 간다. 네트워크 계열과 SSH 차단 계열은 다음 경로로 간다.
3. 모든 경로가 실패하면 19 `TransportFailure`로 바꾼다. 토큰이나 SSH 차단은 `blocked`(코어 `needsUser`), `daemon_unreachable`만이면 `daemonUnreachable`, 그 밖의 네트워크는 `network`(백오프)다.
4. 연결되면 경로를 고정한다. 다음 `open()`은 첫 경로부터 다시 시작한다.
5. 백오프는 0.5초에서 30초까지다. `ready`를 30초 유지하면 0으로 돌아간다(20 §3.8.8, 19 §3.10.3, 보고).

**3.4 재접속과 뷰 동기화** [20 §3.9.6, 보고]: hello 뒤 `schemaHash`, `bootEpoch`, `storeId`를 비교한다. 무효화는 키마다 150ms 디바운스 뒤 재조회한다. 위치 저장과 낡음 표시는 한 IndexedDB 트랜잭션에 쓴다. `2001` 오류는 사유별로 처리하고 `head`부터 구독한다. `ready` 뒤 낡은 열린 뷰를 최대 4개씩 다시 받는다.

**3.5 데스크톱 알림 판단** [20 §3.10.1, 1–8]: 전달 이벤트 수신 → 재전송 중이면 센다 → `channel`·`surface`·`targetDevices`·`expiresAt` 검사 → 같은 `deliveryId`면 무시 → 방해 금지·조용한 시간이면 무시 → `interrupt`는 5초 안에 OS 알림, 창이 열려 있고 화면이 열려 있으면 배너 → 시간당 상한은 데몬이 셈 → 띄울 때 `showContent`에 따라 문구 키를 고른다.

**3.6 휴대폰 푸시 흐름** [26 §3.4.3, §3.4.5, §3.4.8]: 전달 결정이 `interrupt` 또는 `notice`이면 등록된 엔드포인트로 Declarative Web Push를 보낸다. 연결된 기기가 `active`이면 보내지 않는다. `interrupt`는 60초 뒤에도 열람이 없을 때 보낸다. 서비스 워커가 알림을 띄우고, 누르면 `notificationclick`으로 그 질문을 연다. 이미 답해졌으면 04 §3.0.5 문장을 보인다.

**3.7 휴대폰의 보임과 숨김** [26 §3.3.5]: `visible` → 숨김 → `presence.report hidden` → 진행 중 명령을 `POST /m/cmd`로 보내거나 2초 기다린 뒤 `client.stop()`(1000)과 가림막 → 다시 보임 → 백오프 무시하고 재연결, 초안 유지.

**3.8 결과 확인의 두 단계** [04 §3.12, 03 §3.3.2, 00-README 결정 15]: 결과 확인 단계는 기준별 판정이다. 확인된 것과 확인하지 못한 것을 나란히 보고, 기준별로 확인 또는 확인 못함 또는 수정 요청을 정한다. 그다음 전체 반영 단계에서 반영 항목을 처리한다. 반영 항목이 남아 있으면 WorkUnit 라벨은 "결과 확인됨 · 반영 n개 남음"이고 "완료"를 쓰지 않는다. 모두 처리되면 `integrated`로 "완료"가 된다.

**3.9 조작에서 화면까지** [03 §3.1.2 3, 21 UI-D03, 20 §3.9.7]: 사용자가 버튼을 누른다 → 명령 의도가 `basisSeq`와 멱등 키를 달고 나간다 → 데몬이 판정하고 기록한다 → 뷰 무효화 이벤트가 온다 → 앱이 해당 뷰를 다시 받는다 → 화면이 바뀐다. 중간에 화면은 낙관적으로 바꾸지 않는다.

## 5. 경계 사례와 실패

(표시: 원문 절을 직접 읽은 항목은 절 번호만, 하위 에이전트 보고만 근거인 항목은 "(보고)".)

- **데몬이 꺼져 있다** [04 §3.0.4, 03 §4, 20 F-01]. 셸은 마지막 투영을 읽기 전용으로 보이고 배너와 상단 막대에 상태를 표시한다. 결정 동작은 막는다. 서버 PC 연결 불가와 "Helm 서버 응답 없음"은 `GET /healthz` 응답으로 나눈다(502~504는 Tailscale serve가 응답하고 Helm 서버가 없는 경우).
- **서버 PC가 잠듦** [20 F-02]. TCP 시간 초과나 SSH 22번 실패는 `network_unreachable`이다. 재시도하고 2분이 지나면 "서버 PC에 연결할 수 없음"을 보인다. 작업이 계속된다고 말하지 않는다.
- **Tailscale이 꺼져 있다** [20 F-04, 26 MF-01]. 서버 이름을 찾지 못한다. 휴대폰은 캐시를 읽기 전용으로 보이고 푸시는 계속 받는다.
- **serve 설정에 Helm 줄이 빠졌다** [20 F-05]. 네트워크 계열이므로 SSH 경로로 넘어간다. 같은 실패가 3라운드 이어지면 WSS 경로를 30분 미룬다.
- **기기 토큰 폐기나 만료** [20 F-06]. 폐기는 뷰·진행 중 명령·blob·키체인을 지우고 초안만 남긴다(보고). 만료는 재페어링을 안내한다.
- **SSH 호스트 키가 바뀌었다** [20 F-09]. 자동 해결하지 않는다. 경고와 함께 서버의 지문을 `helm doctor` 출력과 대조하게 한 뒤 사용자가 직접 고친다.
- **프로토콜 버전이 맞지 않는다** [20 F-15, 04 §3.0.4]. "버전 맞지 않음"을 보이고 결정을 막는다. 캐시 읽기는 된다.
- **같은 질문에 두 기기가 답했다** [20 F-20, 보고]. 먼저 도착한 답이 적용되고, 늦은 쪽은 3008·3004를 "이미 답했습니다"로 본다. 쓰던 답은 초안으로 남는다.
- **가정이 확정된 뒤 쓰던 답이 도착했다** [04 §3.0.5, 판정 J-120]. 3008로 거부된다. 확정 값을 보이고 쓰던 답은 이의 초안으로 옮긴다.
- **합의 확인 중 초안이 바뀌었다** [04 §5, 보고]. "바뀐 곳 보기"를 본 뒤에만 확정 버튼이 다시 켜진다.
- **결과 확인 중 새 반대 근거가 왔다** [04 §5, 보고]. 막지 않고 버튼 위에 문구를 둔다.
- **권리 게이트를 기본값으로 자동 답하지 않는다** [04 §4, 보고, 결정 2]. 판정 값이 없으면 "판정 없음"으로 쓰고 추측하지 않는다. 합의 확인과 결과 확인은 `question.answer`로 보내지 않는다(J-124, 3001).
- **재시작으로 중단된 작업** [03 §3.2.4·§3.3.2, 보고]. run `interrupted`는 자동 재개한다(최대 3회, 안전한 도구만). 외부 효과가 있을 수 있는 결과 불명 호출만 `recovery` 질문이 된다(권리 게이트이고 만료돼도 가정 확정이 되지 않음). 외부 효과가 없는 로컬 쓰기는 질문 없이 `toolcall.interrupted`로 닫는다. 백업 복원 뒤 첫 부팅은 안전 모드이고 멈춘 작업은 자동 재개하지 않는다(04 §5, J-152, 보고).
- **방해 금지 중 권리 게이트가 쌓였다** [05 §4]. 작업은 멈춰 기다리고 알림은 끝날 때 묶음 1개를 보낸다. 복귀 요약 4절에 모두 보인다.
- **즉시 전달 질문이 짧은 시간에 여러 개다** [05 §4]. 배너는 하나만 보이고 "외 n개"로 접는다. OS 알림은 질문마다 띄운다(즉시 전달은 상한 밖).
- **OS 알림 권한이 없다** [05 §4]. `err.notification.permissionDenied`를 설정 화면과 첫 즉시 전달 때 한 번 보이고, 반복하지 않는다.
- **원함 탐구에서 고르기만 한다** [05 A6, 04 UT-07]. 라운드를 닫지 않고 다음 라운드에 세 개 비교를 넣는다.
- **사용자가 모든 질문에 "가정대로 진행"만 누른다** [05 §4]. 화면은 막지 않는다. 가정과 실제가 같은 비율이 높으면 11·14가 정보 게이트 문턱을 올리는 조정 대상이 된다.
- **이의를 걸었는데 대상이 이미 다시 열려 있다** [05 §4]. 같은 처리에 합치고 "이미 다시 다루는 중입니다. 이의를 함께 기록했습니다."를 보인다.
- **휴대폰에서 산출물을 열기 전 결과 확인** [03 §3.12 표, 26 §3.5.4]. 결과 확인 버튼은 비활성이다. `mobileReviewable`이 거짓이면 미루기만 둔다.
- **휴대폰 알림을 눌렀는데 데몬이 꺼져 있다** [26 MF-02]. 자리 표시 카드를 보이고 "Helm 서버가 응답하지 않습니다"(502·504) 또는 "서버 PC에 연결할 수 없습니다"를 보인다.
- **알림을 눌렀는데 질문이 이미 답해졌다** [26 MF-03]. 04 §3.0.5 문장을 보이고, 앱이 보이게 되면 그 알림을 닫는다.
- **iOS 설정에서 Helm 알림을 껐다** [26 MF-04]. 다음 실행 때 `Notification.permission`이 `denied`이면 `device.unregisterPush(permission_lost)`를 보내고 설정 화면에 "iOS 설정 > 알림"을 안내한다.
- **푸시 서비스가 410·404를 돌려준다** [26 MF-05]. 등록을 지우고 `device.push_unregistered(gone)`을 기록한다. 다음 실행 때 다시 구독한다.
- **푸시 서비스 장애** [26 MF-06]. 재시도하고, 첫 시도가 모두 실패하면 `question.delivered.channel`을 `brief`로 바꾼다.
- **설치 전 브라우저 탭에서 페어링하려 함** [26 MF-08]. 연결 단계를 보이지 않고 설치 안내만 보인다.
- **저장소가 복원되어 `storeId`가 바뀌었다** [20 F-17, 보고]. `clearServer(all)`로 뷰를 지우고 `pending`에 `appState: 'storeReset'`을 붙여 자동 재전송에서 뺀다.
- **웹뷰가 임의 주소로 경로를 바꾸려 한다** [20 F-43, 보고]. Rust가 네이티브 확인 창을 띄우고, 취소되면 `user_cancelled`다.
- **macOS에서 앱을 다시 빌드한 뒤 키체인 창이 뜬다** [20 F-08]. 자체 서명 인증서로 서명하면 생기지 않을 것으로 보며 시험 항목이다.
- **Windows에 OpenSSH 클라이언트가 없다** [20 F-12]. SSH 경로만 막힌다. 선택 기능 설치를 안내하고 WSS 경로는 동작한다.
- **화면 ID가 가리키는 기능이 TUI에 없다** [03 §4]. `SCR-ONBOARD`, `SCR-TRAY`는 TUI 표에 "해당 없음"과 대체를 적는다. 사람 결정 행동이 아니므로 parity 원칙에 어긋나지 않는다.
- **화면이 최신처럼 보이면 안 되는 낡은 뷰** [03 §3.1.2 4, 04 §3.0.4]. 기준 seq와 시각, 신선도를 보인다.

## 7. 구현 리뷰 체크포인트 후보

테스트 ID 형식은 22 추적 색인의 `문서/ID`다. 아래 ID는 각 문서의 §6 표에 있는 것을 확인했다. 원문을 읽지 않은 항목은 "(보고)".

## 8. 헷갈리기 쉬운 점

- **"정한 것"과 "에이전트가 정한 것"**: 레일의 짧은 라벨은 "정한 것"이고, 객체 이름과 화면 제목은 "에이전트가 정한 것"이다. 같은 대상이다(03 §3.5.2, IA-04, 보고).
- **완료 계열 셋**: WorkUnit `integrated` = "완료". Concern `completed` = "반영 완료". WorkUnit `accepted` = "결과 확인됨 · 반영 n개 남음". 세 말이 섞이지 않게 한다(03 §3.3.2, IA-08).
- **복귀 요약의 절 이름이 화면마다 다르다**: 머리 줄 "지금 정할 것"(04 §3.2, 보고), 복귀 요약 4절 "지금 선택이 필요함"(03 §3.12 휴대폰 표, 05 §3.10.4), 홈 카드 제목 "지금 주의가 필요한 것"(04 §3.1). 같은 자리를 가리키는 말이 다르다.
- **결과 확인 반영 줄 수**: 04 §3.12 본문은 "일곱 줄", §8.1 표는 "여섯 줄"이라고 적었다(보고). 레이아웃은 일곱 줄이 기준이다.
- **`choice`와 `choose_one`**: `choice`는 질문 종류(08 `QuestionKind`)이고 원함 탐구에서는 금지다. `choose_one`은 질문 형식(11 `QuestionForm`)이다. 둘 다 원함 탐구에서 쓰지 않는다(03 §3.2.4, §3.12 표).
- **"승인"과 "허락"**: 05 §3.10.5는 "승인"을 금지 표현으로 둔다. 권리 게이트의 허락 버튼은 "허락"이고 메서드는 `approve`다(04 §3.4, 보고).
- **가정 셋**: 임시 가정(질문의 `assumption` 필드), 전제(확인 없이 믿는 것), 가정대로 정해짐(질문 상태 `assumed`). 사람이 "가정대로 진행"을 고르면 질문 상태는 `answered`(답 = 임시 가정)이고 만료로 정해지면 `assumed`다(03 §3.2.3, 04 §3.1·§3.0.5, 보고).
- **메서드와 명령 이름**: 화면은 `stimulusRound.close`(19 메서드)라고 쓰고 10 명령은 `inquiry.round.close`다(04 §3.9, 보고). 메서드 정본은 19 §3.7.1이다.
- **`autonomous.markSeen`과 `autonomous.mark_seen`**: 04(§3.5 보고)는 `autonomous.markSeen`을 쓰고, 25 용어 항목(보고)은 `autonomous.mark_seen`을 쓴다. 어느 쪽이 정본인지 확인해야 한다.
- **연결 상태 이름**: 04 §3.0.4는 16값을 쓴다. canon-2 §3.16은 `connected`·`degraded`·`reconnecting`·`offline`을 쓴다(보고). 20 `UserConnKind`와 21 `ConnectionUiState`는 04 집합을 쓴다.
- **백오프 지터**: 20 §3.8.8은 "반 지터"(19 §3.10.3 `d/2 + random()×d/2`)이고 §3.13.1은 "흔들림 ±20%"다(보고). 구현 전에 맞춰야 한다.
- **"19"가 두 뜻**: React 19(결정 41)와 클라이언트 프로토콜 문서 19. 00-README 결정 32의 React 18 표기는 결정 41로 대체되었다(00-README 32, 41).
- **방해 금지와 결정 59**: 05 §3.12(보고)와 20 §3.10.1은 방해 금지 중 데스크톱 OS 알림을 띄우지 않는 근거로 결정 59를 든다. 그러나 00-README의 결정 59 요약은 "방해 금지 예외(`notifications.dndException`)는 휴대폰 푸시에만 적용한다"이다. 인용 근거가 어긋나므로 원문 결정 기록을 열어 확인해야 한다.
- **데스크톱 결과 확인 알림**: 데스크톱은 배지만(결정 60), 휴대폰 결과 확인 알림은 설정 `notifications.resultReview`(결정 56)로 고른다. 두 설정의 기본값이 다르다(`none` 기본은 휴대폰, OS 알림은 `immediate`일 때만).
- **포트**: 8448은 Helm이 새로 쓰는 `tailscale serve` 외부 포트다. 7840은 tailnet 리스너, 7841은 loopback(SSH) 리스너다(20 §3.1). 8443~8447은 기존 serve 서비스 포트다(20 §2.2, 보고).
- **질문 종류 옛 이름**: 25 용어 항목의 `rights_permission`은 `send_approval`로, `goal_revise`는 `goal_revision`으로, `scope_exceeded`는 `scope_change`로, `HumanTouchpointKind`는 `QuestionKind`로 바뀌었다(03 §8, 보고). 11 종류 목록 한 줄에는 옛 이름 `decision_point`·`scope_expansion`·`action_approval`·`commitment_acceptance`·`result_acceptance`가 남아 있다(보고).
- **08 `QuestionKind`의 추가 종류**: `value_conflict`, `high_uncertainty`, `authority_boundary`, `disagreement`, `acceptance`, `integration`은 03 §3.2.4 표에 없다(보고). 05·15·25에는 나온다. 03과 11에서 대응을 찾기 어렵다.
- **`planAuthoring` 판정 번호**: 05 IX-13은 [판정 J-188], 03 §3.6은 [판정 J-192]를 붙인다(보고: 작성자 표시에는 J-204). 같은 설정에 판정 번호가 여럿이다.
- **Goal·Concern 영어 이름**: 03 §3.2.2의 ADR A1은 "[제안]"이고 24 ADR-03-01은 "채택(판정 J-21, 2주 뒤 재검토)"이다(보고). 상태 불일치가 있다.
- **25 용어 낡음**: 25 항목은 "`SCR-M-ONBOARD`는 03에 없다"고 적었지만 03 §3.12 표에는 있다(보고). 25가 낡았다.
- **화면 종류 라벨과 질문 게이트**: "선택 필요" 배지와 트레이 수는 전달된 권리 게이트만 센다. 정보 게이트는 배지를 바꾸지 않는다(04 §3.24, 보고). 질문함의 "선택 필요" 구역과 이름이 같다.
- **앱 두 기기의 `targetDevices`**: `targetDevices`는 데몬이 채우고 앱은 이 기기 `deviceId`가 있는지만 본다(20 §3.10.1).
- **표시 번호는 정본이 아니다**: "질문 14"는 투영이 매긴다. 정본 레코드에 표시 필드가 없다(03 §3.2.6, IA-07).

## 9. 미결·이후 단계로 미룬 것

- **03 미결 IA-Q1~Q6**: Goal·Concern 영어 이름을 2주 사용 뒤 재검토. 관찰 제안·근거 화면의 최상위 승격 여부. 여러 Goal의 홈 통합 방식. `SCR-THREAD`의 assistant-ui 사용(21 UI-D11). 진행 작업을 최상위에 둘지(동시 진행 5개 넘으면 재검토). (보고)
- **04 미결 SC-Q1, Q2, Q5, Q6, Q7**: 복귀 요약 자동 열기 기준, 끊김 중 자극 반응을 기기에 둘지, 결과 확인 전 독립 검증을 기다릴지, 깊이를 정하는 주체(데몬), 관찰 제안 채택 시 Concern을 열지 질문을 거칠지. SC-Q3·Q4는 해소되었다(보고).
- **05 §7 미결**: 이 pack에서 읽지 않았다.
- **20 §7 미결**: Q-04 기기 키 서명(18 결정 뒤), Q-05 서버 PC 직접 경로, Q-06 숨긴 창의 알림 지연(MC-10), Q-07 Windows 자격 증명 보존 범위, Q-08 macOS 키체인 창(MC-07), Q-10 상태 라이브러리 선호 확인, Q-11 Windows 빌드 경로, Q-22 `.stignore-dev`, Q-24 다른 기기 초안 알림, Q-25 `question.delivered`의 `deliveryMode` 요구(보고).
- **20의 2차 후보**: 자동 업데이트(`tauri-plugin-updater`, ADR-20-07), 토큰 교체 `credential_rotate`(§3.8.7), 직접 `ws://127.0.0.1` 경로(§3.8.10). 1차에서 하지 않는 것: isolation 패턴, 오프라인 송신 큐(판정 J-02), Apple 공증, iOS 네이티브 경로, React Compiler(Q-21), 디스크 암호화 강제(안내만, Q-13).
- **21 §7 미결**: 이 pack에서 읽지 않았다.
- **21의 후속**: 그래프·차트 라이브러리는 2차 이후(ADR 21-9).
- **26 §7 미결**: §7.1 사용자 확인 항목과 §7.2 설계 미결은 이 pack에서 읽지 않았다.
- **26의 경로 B(Tauri v2 iOS + APNs 직접)**: Apple 개발자 프로그램이 생기면 검토한다(MOB-D11, 결정 57). 검토 때 가입을 먼저 하고 §3.1.5 조건을 본다. `push.provider`에 `apns`가 예약되어 있다.
- **2단계 기능(03 §3.6 표)**: `SCR-OBSERVER` 전체, `SCR-METRICS`의 관찰 에이전트 절, `SCR-INQUIRY`의 가능성·결과 종류, `SCR-WORK`의 기대 카드와 탐침 카드, 중재 전달 표시, 검증 에이전트 표시, 다이얼 전체, `SCR-M-*` 전체(결정 42·47).

- **실기기 확인**: 26 §6.2 M-01~M-14는 운영 데몬에서 2단계 활성화 때 수행한다. 20 §6.2 MC-01~14는 Mac과 Windows에서 출시 전에 수행한다(보고).
- **이 pack이 읽지 않은 절**: 03 §3.11, §5, §8; 04 §3.5 세부 문구와 §3.15~3.27 세부; 05 §3.4·§3.5·§3.6·§7; 20 §3.9.2, §3.9.10~3.9.12, §3.12.3~3.12.5, §3.13.4~3.13.5, §5, §8; 21 §2.4, §3.10, §3.11, §3.13, §7; 26 §1.4, §3.1.4, §3.3.4, §3.3.6~3.3.8, §3.4.1, §3.4.4 세부, §3.5.5~3.5.10 세부, §3.6.2~3.6.4, §3.7, §7. 이 항목은 다른 노드나 후속 pack에서 필요하면 원문을 다시 연다.
