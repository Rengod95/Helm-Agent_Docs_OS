# 12. 데몬 운영: 설치, 시작, 종료, 백업, 안전 모드

## 데몬은 언제든 죽을 수 있다는 전제

Helm의 데몬 `helmd`는 집 PC 안의 WSL2에서 상주합니다. 운영자는 사용자 한 사람이고, 서버가 언제 재부팅될지, WSL이 언제 종료될지, 디스크가 언제 찰지 미리 알 수 없습니다. 그래서 운영 설계의 전제는 **데몬은 언제든 비정상 종료될 수 있다**는 것입니다. 정상 종료 절차가 끝까지 실행되면 기록이 깔끔하게 남지만, 실행되지 않아도 다음 시작에서 복구 절차를 실행해 같은 상태로 맞춥니다(7.1번 노드).

이 노드는 그 전제 위에서 데몬을 설치하고, 시작하고, 멈추고, 백업하고, 문제가 생겼을 때 동작을 제한하는 방식을 다룹니다. 리스너 순서, 종료 코드, 비밀 로더는 2번 노드, 백업과 복원의 DB 수준 세부는 4번 노드, 안전 모드의 동기는 7.1번 노드에서 이미 설명했으므로 여기서는 요점만 잇습니다. 이 노드에서 새로 다루는 내용은 시작 순서의 단계별 실패 결과, 안전 모드와 읽기 전용의 관계, 사건별 동작입니다.

## 프로세스와 systemd

`helmd`는 Node 프로세스 하나입니다. 커널, 저장소, 런타임, 스케줄러, 리스너가 모두 주 스레드의 이벤트 루프에서 실행되고, DB 쓰기는 주 스레드의 쓰기 연결 하나로만 합니다. 리스너가 열린 뒤에는 전체 해시 체인 검증(`verify --full`)처럼 무거운 읽기 작업을 주 스레드에서 돌리지 않고 워커 스레드의 읽기 전용 연결에서 실행합니다. 마이그레이션과 투영 재구성은 리스너를 열기 전의 시작 단계에서 실행되므로 주 스레드에서 돌려도 됩니다.

데몬은 systemd 사용자 단위(`helmd.service`)로 실행됩니다. 사용자 단위는 sudo가 필요 없습니다. 시스템 단위는 root와 `/etc` 쓰기가 필요한데 에이전트는 이런 작업을 할 수 없습니다. 사용자 단위면 도구 실행용 일회성 단위(`systemd-run --user`)도 sudo 없이 만들 수 있습니다. linger(로그인하지 않아도 사용자 단위를 유지하는 systemd 설정)가 켜져 있어서 WSL이 부팅되면 데몬이 올라옵니다.

WSL이 부팅되려면 조건이 하나 더 있습니다. Windows가 재부팅된 뒤에는 사용자가 Windows에 로그온해야 `WSL-Autostart` 작업이 배포판을 띄우므로, 로그온 전까지 데몬은 꺼져 있습니다. 로그인 전에 자동으로 시작하는 방법은 현재 없고 설계 문서에서도 미결로 남아 있습니다. 이 꺼진 구간은 복귀 요약에 "데몬 꺼짐 구간"으로 나타납니다. `wsl --shutdown`과 정전은 비정상 종료이고, 다음에 WSL이 올라올 때 시작과 복구가 이어집니다. WSL이 유휴 때문에 꺼지지 않게 하는 설정(`.wslconfig`)과 `WSL-Autostart` 작업은 dotfiles에서 관리하며, Helm에서는 `helm doctor`가 상태를 확인만 합니다.

**같은 데이터 디렉터리에는 데몬이 하나만 있어야 합니다.** 데몬은 데이터 디렉터리의 잠금 전용 SQLite 파일(`helmd.lock`)에 배타 트랜잭션을 프로세스 수명 내내 잡고 있습니다. 두 번째 데몬은 잠금을 얻지 못하고 종료 코드 3으로 끝납니다. 프로세스가 죽으면 운영체제가 잠금을 풀기 때문에 pid 파일처럼 죽은 프로세스의 흔적이 다음 시작을 막는 일이 없습니다. 이 잠금 위에 4번 노드의 부팅 번호 펜싱이 한 겹 더 있습니다.

데몬은 진단용 JSON 파일 `helmd.owner.json`도 씁니다. 이 파일은 소유 판정에 쓰이지 않고(소유 판정의 근거는 잠금뿐입니다), 진단 정보와 크래시 루프 계산용 부팅 기록, 마이그레이션 실패 표지를 담습니다.

## 설치와 업그레이드

설치는 `just daemon-install` 하나로 합니다. 환경 점검(`doctor`), 릴리스 빌드, 월 비용 상한 질문(답이 없으면 USD 50), systemd 단위 생성, 활성화, 준비 완료 대기 순서입니다. 빌드한 결과는 git 커밋 하나에서 만든 불변 디렉터리(`/srv/volumes/helm/app/releases/<릴리스 ID>/`)이고, 데몬은 `current` 심볼릭 링크가 가리키는 릴리스에서 실행됩니다. 작업 트리에서 바로 실행하면 Syncthing으로 동기화되는 `~/projects`의 변경이 실행 중인 코드에 섞입니다. 그래서 불변 디렉터리에서 실행하고, 스키마가 바뀌지 않은 업그레이드는 링크를 이전 릴리스로 돌리는 것만으로 되돌립니다.

함께 설치되는 타이머는 매일 백업(03:40), 주간 전체 검사(일요일 04:30), 일일 유지 작업(04:45), 매월 복구 훈련(1일 05:45)입니다. 홈랩 restic이 04:00에 백업을 가져가므로 백업은 20분 앞에 시작합니다. DB 1 GB 기준으로 사본 생성과 검증이 수 분 안에 끝난다고 가정한 시각이며, 검증까지 15분을 넘으면 경고합니다. 주간 전체 검사가 실패했을 때의 처리는 읽기 전용 절에서 설명합니다.

업그레이드는 `just daemon-upgrade`가 다음 순서로 실행합니다.

1. 빌드: HEAD 커밋에서 새 릴리스를 만듭니다. 이 동안 운영 데몬은 계속 실행됩니다.
2. 자체 시험: 새 릴리스의 모듈 로드와 설정 검증을 확인하고, 현재 DB의 사본으로 마이그레이션을 시험합니다. 실패하면 새 릴리스를 지우고 중단하며 운영 데몬은 그대로입니다.
3. 업그레이드 전 백업: 링크를 바꾸기 직전에 뜹니다.
4. 전환: `current` 링크를 원자적으로 바꾸고 데몬을 재시작합니다.
5. 확인: 실행 중인 `releaseId`가 새 릴리스이고, 모드가 `ready`이며, 헬스가 `critical`이 아닌지 봅니다.

4단계의 시작이 실패하거나 5단계의 확인이 실패하면 자동으로 되돌립니다. 되돌리기는 링크를 이전 릴리스로 돌린 뒤 DB의 스키마 버전을 이전 릴리스가 지원하는 최댓값과 비교합니다. DB 마이그레이션은 앞으로만 가므로(4번 노드), 새 릴리스가 마이그레이션을 이미 적용했다면 이전 릴리스는 그 DB를 열 수 없고 종료 코드 4로 거부합니다. 이 경우에는 가장 최근의 업그레이드 전 스냅숏을 복원합니다. 업그레이드 뒤에 쌓인 이벤트는 격리된 DB에만 남고, 복원 뒤 첫 부팅이므로 안전 모드로 시작합니다. 스키마가 그대로이면 링크 교체만으로 끝납니다.

## 시작 순서

시작은 0단계부터 16단계까지 정해진 순서를 따릅니다. 이 글의 단계 번호는 데몬 시작 순서표의 번호입니다. 저장소 모듈의 부팅 순서와 런타임 복구 모듈의 단계 번호는 이 표와 다르게 매겨져 있고, 설계 문서 사이에서 번호 체계를 아직 정리 중입니다.

| 단계 | 하는 일 | 실패하면 |
|---|---|---|
| 0 | 신호 처리기와 처리되지 않은 예외 처리기를 설치합니다. 시험 변수가 켜졌는데 데이터 디렉터리가 시험 경로가 아니면 거부합니다 | 종료 코드 2 |
| 1 | 설정을 읽고 검증합니다. 릴리스 매니페스트와 Node ABI를 비교합니다 | 종료 코드 2 |
| 2 | 경로를 준비합니다. 데이터 디렉터리가 동기화 폴더나 `/mnt/` 아래이면 거부하고, 여유 공간 1GiB 이상과 `.reserve`를 확인합니다 | 종료 코드 2 |
| 3 | 단일 인스턴스 잠금을 얻습니다 | 종료 코드 3 |
| 4 | 비밀을 로드합니다. `required` 키가 없으면 실패합니다 | 종료 코드 2 |
| 5 | DB를 엽니다. 이전 크래시의 WAL 복구가 여기서 끝납니다 | DB를 열 수 없으면 종료 코드 5 |
| 6 | 다운그레이드를 검사합니다. DB 스키마가 코드보다 새로우면 거부합니다 | 종료 코드 4 |
| 7 | 무결성 꼬리 검사를 합니다 | 읽기 전용 시작(`integrity_suspect`) |
| 8 | 마이그레이션을 합니다(전에 백업). 이미 적용된 마이그레이션의 체크섬이 다르면 적용하지 않습니다 | 백업·마이그레이션 실패는 종료 코드 1(같은 실패가 두 번째면 2). 체크섬 불일치는 읽기 전용 시작(`integrity_suspect`) |
| 9 | 이벤트 버전을 확인하고 투영을 따라잡거나 재구성합니다 | 모르는 버전은 종료 코드 4. 재구성 실패는 읽기 전용 시작(`recovery_failed`) |
| | 이 줄 아래부터 이벤트를 기록합니다 | |
| 10 | `bootEpoch`를 발급하고 `daemon.booted`를 기록합니다. 크래시 루프나 복원 뒤 첫 부팅이면 같은 트랜잭션에 `daemon.safe_mode_entered`도 기록합니다 | 종료 코드 1 |
| 11 | 지난 부팅의 고아 도구 프로세스를 정리합니다 | 경고만 하고 계속 |
| 12 | 런타임 복구를 실행합니다(7.1번 노드) | 복구 전체가 결정적으로 실패하면 읽기 전용 시작(`recovery_failed`) |
| 13 | 오케스트레이터를 시작합니다. 안전 모드이면 새 실행을 허가하지 않는 상태로 시작합니다 | 종료 코드 1 |
| 14 | 스케줄러를 구성하고 시작합니다. 안전 모드이면 에이전트 실행 타이머를 보류합니다 | 종료 코드 1 |
| | 이 줄 아래에서 리스너가 열립니다 | |
| 15 | 리스너를 `local`, `loopback`, `tailnet` 순서로 엽니다 | 포트 사용 중이면 종료 코드 2 |
| 16 | 모드를 `ready`(또는 `safe_mode`)로 바꾸고, 재개를 예약하고(안전 모드이면 하지 않음), 이벤트 루프 감시자를 시작합니다 | - |

손상된 DB에 쓰면 손상이 커질 수 있으므로 단계를 이 순서로 둡니다. 무결성 검사, 마이그레이션, 투영 따라잡기가 끝난 뒤에야 `daemon.booted`로 쓰기를 시작하고, 복구가 끝난 뒤에 오케스트레이터와 스케줄러를 켜고, 마지막에 리스너를 엽니다. 복구 전에 리스너가 열려 있으면 클라이언트가 아직 정리되지 않은 "실행 중" 상태를 보고 명령을 보낼 수 있기 때문입니다(2번 노드).

10단계 앞에서 실패한 부팅은 `daemon.booted`를 쓰지 않습니다. 8단계의 마이그레이션 전 백업처럼 일부 기록이 남을 수는 있지만, 실패 자체는 종료 코드, 운영 로그, `helmd.owner.json`으로만 남습니다.

복원 뒤 첫 부팅은 10단계에서 `daemon.booted`, `daemon.safe_mode_entered`(사유 `restored`), `store.restored` 순서로 기록합니다. 앞의 두 이벤트는 같은 트랜잭션에 들어갑니다. 새 `storeId`는 데몬 시작 전에 복원 CLI가 DB에 붙여 둡니다. 데몬은 리스너를 열기 전에 복원 전에 적어 둔 위험한 변경을 다시 적용하고 쓰지 않은 발송 승인을 모두 만료시킵니다.

**비밀 로드**는 4단계에서 합니다. 데몬이 `secrets run`으로 자식 로더를 실행해 필요한 키만 JSON으로 받고, 값은 메모리의 `SecretStore`에만 둡니다(2번 노드). 시작을 거부하는 비밀은 설정의 `required`에 든 키이고 기본값은 `HELM_LEDGER_HMAC_KEY` 하나입니다. 모델 키가 없어도 데몬은 뜨고, 그 제공자와 웹 검색 같은 기능만 쓸 수 없는 저하 상태가 됩니다. systemd 실행 명령을 `secrets run ... -- helmd`로 감싸지 않는 이유는 sops가 자식 명령에 SIGTERM을 전달하지 않아서, 감싸면 systemd의 종료 신호가 node에 가지 않기 때문입니다.

## 안전 모드

안전 모드는 복원 뒤 첫 부팅이거나 크래시 루프가 감지되었을 때 시작하는 모드입니다. 리스너는 열고 사람의 명령(질문 답, 결과 확인 등)은 받습니다. 반면 run 자동 재개, 에이전트 run을 시작하는 타이머(알림 타이머는 발화), 관찰 에이전트 실행, 새 실행 허가는 멈춥니다. 재시작해도 풀리지 않고, `daemon.safe_mode_exited`가 기록될 때까지 다음 시작도 안전 모드로 시작합니다.

해제는 사람만 합니다. 데스크톱이나 TUI 기기, 휴대폰, 서버 안의 대화형 관리 CLI(`helm ops safe-mode off`, 확인 문자열 입력)에서 해제할 수 있고, 스크립트처럼 비대화로 실행되는 관리 CLI는 해제할 수 없습니다.

### 크래시 루프 차단기

지난 10분 안의 비정상 시작이 이번을 포함해 3번 이상이면 안전 모드(`crash_loop`)로 시작합니다. 비정상 시작은 직전 부팅이 `daemon.stopped`를 쓰는 정상 종료로 끝나지 않은 경우입니다. 읽기 전용 시작은 `daemon.booted`가 없으므로 `helmd.owner.json`의 부팅 기록으로 함께 세고, 마지막으로 안전 모드를 해제한 이후의 시작만 셉니다.

예를 들어 03:50, 03:54, 03:58에 시작한 부팅이 모두 직전 부팅의 비정상 종료 뒤에 시작한 것이면 03:58의 세 번째 시작에서 안전 모드가 됩니다. 그 뒤에 재시작해도 해제 이벤트가 없으면 계속 안전 모드로 시작합니다. 같은 문제로 반복해서 죽는 데몬이 그때마다 같은 run을 재개하면 같은 외부 행동을 반복하게 되므로, 세 번째 시작부터 재개를 멈춥니다.

이 계산은 두 원천을 합칩니다. 하나는 10단계에서 `daemon.booted`를 쓴 부팅 중 이전 종료가 깔끔하지 않았던 것이고, 다른 하나는 `helmd.owner.json`에 남은 읽기 전용 시작입니다. 설정, 잠금, DB 열기, 마이그레이션처럼 10단계 앞에서 죽고 읽기 전용으로도 뜨지 못한 부팅은 두 원천 어디에도 들어가지 않아 셀 수 없습니다. 그런 부팅이 종료 코드 1로 반복되면 systemd가 시작 한도(10분에 5번을 넘으면 단위를 `failed`로 두고 경보 단위를 실행)에서 재시작을 멈춥니다. 10단계 뒤에서 죽는 부팅은 데몬이 세 번째에 먼저 안전 모드를 걸고, systemd 한도는 그 뒤의 안전망입니다. 3과 5라는 숫자는 이 순서가 되도록 정해 둔 값입니다.

## 읽기 전용

읽기 전용은 상태 변경 명령을 거절하고 조회와 구독만 받는 모드입니다. 스케줄러가 멈추고, 진행 중인 run은 다음 턴 경계에서 멈춥니다. 이 모드로 들어가는 길은 두 가지입니다.

시작 도중에 들어가는 길이 읽기 전용 시작입니다. 7단계나 8단계(적용된 마이그레이션의 체크섬 불일치)에서 무결성 문제가 확인되거나 9단계나 12단계의 복구가 결정적으로 실패하면, 남은 쓰기 단계를 건너뛰고 15단계에서 리스너만 엽니다. 이때는 `daemon.booted`조차 쓰지 않고, 부팅 사실을 `helmd.owner.json`과 운영 로그에만 남깁니다. 손상이 의심되는 DB에 아무것도 덧쓰지 않고, 리스너가 열려 있으므로 사람이 원격에서 상태를 보고 복원이나 재구성을 결정할 수 있습니다.

실행 중에 들어가는 길은 아래 사유 중 하나가 생겼을 때입니다. 사유는 목록으로 관리되고 하나라도 남아 있으면 읽기 전용입니다.

| 사유 | 진입 조건 | 이벤트 기록 | 해제 조건 |
|---|---|---|---|
| `disk_critical` | 데이터 디렉터리 여유가 1GiB 미만 | 여유 공간이 남아 있으면 `daemon.*`, `backup.*` 기록 | 여유가 2GiB 이상으로 돌아오면 자동 해제 |
| `integrity_suspect` | 7단계 검사 실패, 8단계 체크섬 불일치, 실행 중 `SQLITE_CORRUPT`, 체크포인트 앵커 검증 불일치 | 기록 없음 | 복원하거나 `helm ops verify --full`을 통과한 뒤 재시작 |
| `recovery_failed` | 9단계 또는 12단계의 결정적 실패 | 기록 없음 | 원인을 고친 뒤(새 릴리스, `helm ops rebuild-projections`, 복원) 재시작 |
| `projection_fault` | 투영 갱신 실패로 커밋이 롤백되는 일이 5분에 3번, 또는 같은 투영기에서 연속 2번 | 기록 없음 | `helm ops rebuild-projections`(데몬을 멈추고 오프라인 재구성)나 고친 릴리스로 업그레이드한 뒤 재시작 |
| `operator` | 관리자가 `admin.setMode`로 읽기 전용 지정 | 여유 공간이 남아 있으면 `daemon.*`, `backup.*` 기록 | 관리자가 `admin.setMode`로 `normal` 지정 |

이벤트 기록 열은 사유 전체를 보고 판단합니다. 사유가 `disk_critical`과 `operator`뿐일 때만 데몬 자신의 운영 이벤트를 씁니다. 다른 사유가 하나라도 섞여 있으면 아무것도 쓰지 않습니다. `integrity_suspect`와 `recovery_failed`는 손상이 의심되는 DB에 쓰지 않기 위해서이고, `projection_fault`는 모든 쓰기가 투영 갱신을 거치는데 그 갱신이 계속 실패해서 쓰기 자체가 되지 않기 때문입니다.

디스크는 계속 감시합니다. 여유가 5GiB 아래로 내려가면 경고하고, 1GiB 아래로 내려가면 읽기 전용이 됩니다. 예비 파일 `.reserve`(64 MiB)는 디스크가 가득 차서 외부 효과가 있는 도구 호출의 완료 커밋이 `SQLITE_FULL`로 실패한 순간을 위한 파일입니다. 이미 일어난 외부 효과의 결과를 잃지 않으려면 그 결과를 먼저 커밋해야 하므로, 런타임이 결과를 `state/pending-results/<tcId>.json`에 쓰고 데몬이 `.reserve`를 지워 자리를 만듭니다. 그 자리로 pending 결과를 먼저 커밋한 뒤 현재 epoch의 남은 run을 부팅 복구와 같은 규칙으로 정리합니다. 여유가 2GiB로 돌아오면 `.reserve`를 다시 만들고 `disk_critical`을 해제합니다. 결과 파일도 쓰지 못하면 다음 부팅의 복구가 그 호출을 결과 불명으로 처리합니다.

주간 전체 검사(일요일 04:30)나 백업 사본 검사가 실패해도 자동으로 읽기 전용이 되지 않습니다. 4번 노드에서 예고한 처리입니다. 실패하면 다음 일이 일어납니다.

1. 실패 지점을 `meta.integrity_broken_seq`로 기록합니다. 다음 부팅의 꼬리 검사가 그 지점부터 봅니다.
2. 헬스 `db_integrity`를 `critical`로 올리고 경보를 냅니다.
3. 백업 회전을 멈춥니다. 오래된 스냅숏이 삭제되지 않으므로 손상 전 스냅숏이 남습니다.
4. 사람에게 "읽기 전용으로 바꾸기 / 계속 쓰기"를 묻는 주의 항목을 띄웁니다.

손상이 과거 구간에 있어도 새 이벤트는 현재 헤드에 이어 붙으므로 계속 쓰는 선택이 가능합니다. 사람이 읽기 전용을 고르면 `helm ops read-only on`을 실행한 것과 같습니다.

### 안전 모드와 읽기 전용의 관계

두 모드는 리스너를 연다는 점이 같고 나머지는 다릅니다.

| 항목 | 안전 모드 | 읽기 전용 |
|---|---|---|
| 상태 변경 명령 | 사람의 명령을 받음 | 거절 |
| 자동 실행 | run 자동 재개, 에이전트 타이머, 관찰 에이전트, 새 실행 허가가 멈춤 | 스케줄러가 멈추고 진행 중 run이 다음 턴 경계에서 멈춤 |
| 이벤트 기록 | 기록함 | 사유에 따라 다름(위 표) |
| 해제 | 사람 명령만 | 사유별 조건 |
| 클라이언트 모드 이름 | `safeMode` | `readOnly` |

둘은 겹칠 수 있습니다. 안전 모드에서 읽기 전용 사유가 생기면 읽기 전용이 되지만 안전 모드 표시는 유지됩니다. 읽기 전용 사유가 모두 풀리면 표시가 남아 있을 때 안전 모드로, 없을 때 정상(`ready`)으로 돌아갑니다. 읽기 전용 중에 안전 모드를 해제하면 표시만 지워집니다.

## 종료

종료는 SIGTERM, SIGINT, 로컬 관리자의 `admin.drain`을 받으면 시작합니다. 순서는 다음과 같습니다.

1. 모드가 `draining`이 됩니다. 새 연결을 받지 않고 상태 변경 요청을 거절하며 읽기 요청만 받습니다. 연결된 클라이언트에는 종료 예고를 보냅니다.
2. 스케줄러를 멈추고, 관찰 실행에 `job.cancel`(사유 `shutdown`)을 보냅니다.
3. 진행 중인 run에 20초 유예를 줍니다. 모델 호출과 도구 호출이 끝나기를 기다리고 새 턴은 시작하지 않습니다. 사람 대기 중인 run은 기다리지 않습니다.
4. 남은 모델 요청을 끊고, 도구 프로세스에 SIGTERM을 보낸 뒤 5초 뒤 SIGKILL을 보냅니다. 끊긴 도구 호출은 외부 효과가 없으면 "중단됨"으로 닫고, 외부 효과가 있을 수 있으면 "결과 불명"으로 닫습니다. 결과 불명이 생긴 run은 복구 대기 상태로 남고 사람에게 복구 질문이 갑니다. 나머지 run은 사유 `daemon_shutdown`으로 중단 기록을 남깁니다.
5. 연결을 닫습니다.
6. `daemon.stopped`를 기록하고, SQLite의 WAL 체크포인트(`wal_checkpoint(TRUNCATE)`)를 실행한 뒤 DB를 닫습니다. 이 체크포인트는 WAL 파일을 DB 파일에 합치는 작업이고, 4번 노드의 HMAC 체크포인트나 7.1번 노드의 run 체크포인트와는 다른 것입니다.
7. `helmd.owner.json`에 정지 상태를 적고 잠금을 풀고 종료 코드 0으로 끝납니다.

1~3단계는 최대 20초, 4단계는 최대 6초, 5~7단계는 보통 1초 이하이므로 합계는 약 27초입니다. systemd의 `TimeoutStopSec=45s` 안에 들어오고, 45초를 넘기면 systemd가 남은 프로세스를 모두 SIGKILL합니다. 두 번째 SIGTERM이나 SIGINT가 오면 3단계 유예를 건너뛰고 4단계로 갑니다. SIGKILL이나 `wsl --shutdown`처럼 이 순서를 거치지 못하는 종료도 있지만, 다음 시작에서 복구 절차를 실행해 같은 결과로 맞춥니다.

종료 코드 0~5의 뜻은 2번 노드에서 다뤘습니다. 어느 단계에서 어느 코드로 끝나는지는 시작 순서 표의 "실패하면" 열에 있습니다. systemd 설정은 `Restart=on-failure`과 `RestartPreventExitStatus=2 3 4 5`이므로 종료 코드 1과 비정상 신호 종료(abort, SIGKILL)는 다시 띄우고, 2~5는 다시 띄워도 같은 결과라 재시작하지 않습니다. 관리 CLI는 코드 5를 "사람의 결정이 필요함(`gated`)"에 씁니다. 이때 질문 ID와 앱을 여는 방법을 출력하고 끝납니다.

## 백업과 복원

백업의 DB 수준 절차(온라인 백업 API, 사본 전체 검사, manifest)는 4번 노드에서 다뤘습니다. 이 노드에서 확인할 부분은 백업이 집 밖으로 나가는 경로와 복원 뒤 첫 부팅입니다. 백업 종류는 매일, 마이그레이션 전, 업그레이드 전, 복원 전, 수동의 다섯 가지입니다.

Helm이 restic을 직접 부르지 않으므로, 홈랩의 restic이 04:00에 검증된 스냅숏 디렉터리와 blob 디렉터리를 가져갑니다. 살아 있는 DB 파일은 가져가지 않습니다. blob은 내용 해시로 이름이 붙고 쓴 뒤 바뀌지 않으므로 스냅숏에 복사하지 않고 restic이 직접 가져갑니다. **홈랩에서 restic 대상에 `/srv/volumes/helm`을 추가하는 작업이 끝나기 전에는 Helm 데이터가 restic에 들어가지 않습니다.** 그동안은 최신 검증 스냅숏과 새 blob을 Windows D: 드라이브에 `rsync`로 임시 복사하고 복사본의 sha256을 매니페스트와 대조합니다. D:는 같은 물리 디스크라서 디스크가 고장 나면 사본도 함께 잃고 암호화도 되지 않습니다. `helm doctor`가 경고하고, 헬스 `backup_offsite`는 `degraded`로 표시됩니다.

복원은 데몬을 멈춘 상태에서 관리 CLI로 시작하고 다음 순서로 진행합니다.

1. 잠금을 얻습니다. 데몬이 실행 중이면 종료 코드 3으로 중단합니다.
2. 백업을 검증합니다. 체크섬, 무결성, 해시 체인 전체를 확인합니다.
3. 백업 시점 이후의 위험한 변경(기기 폐기, 권한 회수 등)을 현재 DB에서 읽어 따로 적어 둡니다.
4. 현재 DB를 지우지 않고 격리 폴더로 옮기고, 백업 DB를 제자리에 놓고, 새 `storeId`를 붙이고, "복원 대기" 표시를 남깁니다.
5. 데몬을 시작합니다. 10단계에서 앞 절의 순서(`daemon.booted`, `daemon.safe_mode_entered`, `store.restored`)로 기록하고, 리스너를 열기 전에 위험한 변경을 재적용하고 발송 승인을 만료시킵니다.
6. 런타임 복구는 스냅숏 시점에 실행 중이던 run을 정리만 하고 재개하지 않습니다. 자동으로 재개하면 백업 이후 이미 끝난 쓰기, push, 발송을 다시 하게 됩니다. 스냅숏 때 시작 상태였던 외부 효과 호출은 결과 불명이 됩니다.

5단계의 처리가 끝나기 전에 데몬이 죽으면 다음 부팅이 "복원 대기" 표시를 읽고 같은 처리를 다시 합니다. 재적용은 이미 적용된 상태면 건너뛰므로 반복해도 결과가 같습니다. blob만 잃은 경우는 복원이 아니므로 안전 모드로 시작하지 않습니다.

복원이 실제로 되는지는 매월 복구 훈련으로 확인합니다. 최신 스냅숏을 임시 디렉터리에 복사해 읽기 전용 훈련 모드로 열어 검증하고, 데몬은 멈추지 않으며 정본 DB에는 훈련 결과 이벤트 하나만 씁니다. 분기에 한 번 사람이 restic에서 꺼낸 파일로 같은 훈련을 하는 안이 추천값입니다. 월 자동 훈련은 홈랩 restic 비밀이 필요하므로 아직 미결입니다.

## 상태 확인과 관리 CLI

운영 상태는 `OpsStatus` 객체 하나로 모읍니다. 내부 모드(시작 중, 복구 중, 준비, 안전 모드, 읽기 전용, 종료 중)와 점검 항목이 들어 있고, 전체 건강 수준은 점검 가운데 가장 나쁜 것(정상, 저하, 심각)입니다. 노출 범위는 세 단계입니다. 서버 안의 로컬 관리자는 `OpsStatus` 전체를 `helm status --json`으로 보고, 인증된 기기는 줄인 모양의 `daemon.status`를 받고, 인증 없는 `/healthz`는 상태 문자열 하나만 돌려줍니다. `/healthz`는 `ok`와 `degraded`에 HTTP 200, 나머지에 503을 쓰며, 읽기 전용 모드는 `degraded`로 보입니다. 클라이언트 프로토콜의 모드 이름(`normal`, `safeMode`, `readOnly`, `draining`)은 내부 이름과 다르므로 코드에서 섞지 않아야 합니다. 운영 로그는 journald로 가는 JSON 줄이고 사용자 데이터의 내용은 남기지 않습니다.

관리 CLI `helm ops` 명령은 두 종류입니다. 실행 중인 데몬에 소켓으로 요청하는 명령과, 데몬이 멈춰 있을 때만 잠금을 잡고 DB를 직접 다루는 오프라인 명령(마이그레이션, 복원 등)입니다. 데몬이 실행 중인데 오프라인 명령을 실행하면 종료 코드 3으로, 데몬이 필요한 명령을 데몬 없이 실행하면 종료 코드 2로 끝납니다.

시험용 장치(특정 지점에서 SIGKILL하는 시험 종료 지점, 고장 주입)는 시험 디렉터리와 개발 디렉터리에서만 켜지고, 정식 데이터 디렉터리에서 켜려 하면 시작을 거부합니다.

## 이 노드의 기준으로 구현을 볼 때

- 단일 인스턴스 잠금이 SQLite 배타 트랜잭션으로 구현되고, 두 번째 데몬이 종료 코드 3으로 끝나는가. pid 파일에 기대지 않는가
- 시작 순서가 0~16단계 표를 따르고, 단계별 실패 결과가 표와 같은가. 10단계 앞의 실패가 이벤트를 쓰지 않고 끝나는가. 리스너가 복구 뒤(15단계)에 열리는가
- 비밀이 자식 로더로 들어오고 `process.env`에 남지 않는가. `SecretStore`가 직렬화와 로그 출력을 막는가. 시작을 거부하는 비밀이 `required`(기본 `HELM_LEDGER_HMAC_KEY`)뿐이고, 모델 키가 없어도 데몬이 뜨는가
- 7·8단계의 무결성 문제와 9·12단계의 복구 실패가 읽기 전용 시작으로 가며, 이때 `daemon.booted`를 포함해 아무것도 쓰지 않는가
- 크래시 루프 계산이 10분 창, 3회, 마지막 해제 이후 기준이고 읽기 전용 시작도 세는가. 10단계 앞에서 죽는 부팅은 세지 않고 systemd 시작 한도로 멈추는가
- 안전 모드에서 자동 재개, 에이전트 타이머, 관찰 에이전트, 새 실행 허가가 멈추는가. 비대화 CLI로 해제할 수 없는가
- 읽기 전용 사유가 목록으로 관리되고, 사유가 `disk_critical`과 `operator`뿐일 때만 운영 이벤트를 쓰는가. 사유별 해제 조건이 맞는가. 읽기 전용 중에도 안전 모드 표시가 유지되는가
- 주간 전체 검사 실패가 자동으로 읽기 전용을 만들지 않고, 실패 지점 기록, 백업 회전 중단, 사람에게 묻는 항목으로 이어지는가
- `Restart=on-failure`과 `RestartPreventExitStatus=2 3 4 5`가 설정되어 있고, 비정상 신호 종료가 재시작 대상인가
- 종료 순서가 `daemon.stopped` 기록, WAL 체크포인트, DB 닫기, 잠금 해제 순서이고, 외부 효과가 있을 수 있는 끊긴 호출이 결과 불명으로 닫히며 합계가 `TimeoutStopSec=45s` 안인가
- 업그레이드가 빌드, 자체 시험, 백업, 링크 교체, 확인 순서이고, 되돌릴 때 스키마 버전을 비교해 필요하면 스냅숏을 복원하는 분기가 있는가
- 백업이 사본을 검증한 뒤에만 완료로 기록되는가. restic이 살아 있는 DB 파일을 가져가지 않는가
- 복원이 현재 DB를 지우지 않고 격리하며, 새 `storeId`가 데몬 시작 전에 붙고, 첫 부팅이 `daemon.booted`, `daemon.safe_mode_entered`, `store.restored` 순서로 기록하고, 리스너를 열기 전에 위험 변경 재적용과 발송 승인 만료가 끝나는가
- 디스크 임계값(5GiB 경고, 1GiB 읽기 전용, 2GiB 해제)과 `.reserve`가 있고, 디스크가 가득 찼을 때 `.reserve`를 지워 pending 결과를 먼저 커밋하며, 여유가 돌아오면 `.reserve`를 다시 만드는가
- `/healthz`가 상태 문자열 하나만 돌려주는가
- 시험 종료 지점과 고장 주입이 정식 데이터 디렉터리에서 켜지지 않는가
