# 4.1 이벤트 소싱과 투영: 기록이 정본이고 화면은 계산 결과다

## 왜 테이블 대신 사건의 목록을 정본으로 두는가

보통의 웹 서비스는 현재 상태를 테이블에 저장합니다. Concern 테이블에 `status` 열이 있고, 상태가 바뀌면 그 행을 UPDATE합니다. 이 방식에서는 "지금 상태가 무엇인가"는 바로 알 수 있지만, "왜 이 상태가 되었는가", "누가 언제 무엇을 근거로 바꿨는가"는 따로 로그를 남기지 않는 한 사라집니다.

Helm은 이 정보가 제품의 핵심입니다. 1번 노드의 요구를 떠올려 보면, 에이전트가 혼자 정한 결정을 나중에 보여 주고 이의를 받아야 하고, 결과 확인이 어떤 근거와 어떤 합의 판본을 보고 이루어졌는지 남아야 하며, 하루 비운 사이 무엇이 바뀌었는지 요약해야 합니다. 모두 "현재 값"보다 "일어난 일의 순서"가 필요한 질문입니다.

그래서 Helm은 일어난 일 하나하나를 **이벤트**로 기록하고, 그 이벤트들의 순서 있는 목록(이벤트 로그)을 정본으로 둡니다. 여기서 이벤트는 커널이 명령, 관찰, 타이머를 평가한 결과의 기록입니다. 평가 결과가 상태 전이를 허용하면 전이 이벤트가 남고, 거부하면 `command.rejected` 이벤트가 남습니다. 이 글에서 "이벤트"는 이렇게 저장되는 영속 이벤트만 가리킵니다. 현재 상태는 이벤트를 처음부터 순서대로 적용해서 계산합니다. 이 설계 방식을 **이벤트 소싱**이라고 부릅니다. 대가도 있습니다. 상태를 읽을 때마다 처음부터 계산하면 느리므로 계산 결과를 따로 저장해야 하고, 이벤트의 형식을 바꾸기 까다로우며, 상태를 쓰는 코드는 상태를 직접 바꾸지 않고 이벤트를 내는 방식으로 작성해야 합니다.

## Redux를 아는 사람에게: 같은 모양, 다른 자리

React 개발자에게 가장 가까운 구조는 Redux입니다. Redux에서 화면 상태는 `reducer(state, action)`을 action마다 반복 적용한 결과이고, Helm의 커널 상태도 `apply(state, event)`를 이벤트마다 반복 적용한 결과입니다. 수식으로 쓰면 `State(seq_n) = fold(apply, State0, Events[1..n])`입니다. 왼쪽은 n번째 이벤트까지 반영한 상태이고, 오른쪽은 빈 초기 상태 `State0`에서 시작해 1번부터 n번까지의 이벤트에 `apply`를 차례로 적용한 결과입니다. Redux의 `reduce`와 같은 모양입니다. 다음 표는 Redux의 각 개념이 Helm의 무엇에 대응하는지 짝지은 것이고, 마지막 열은 대응이 달라지는 지점입니다.

| Redux | Helm | 차이 |
|---|---|---|
| dispatch(action) | `engine.submit`에 명령 제출 | Redux에서 dispatch되는 action은 "해 달라"는 의도(`SET_X`)일 수도, "일어났다"는 사실일 수도 있습니다. Helm에서 제출하는 것은 항상 의도인 명령입니다 |
| reducer 앞에는 없음 | `decide`(커널의 판정) | Redux의 reducer는 들어온 action을 거부할 수 없습니다. Helm은 `apply` 앞에 검증하고 거부하는 `decide`가 따로 있습니다. 거부도 기록됩니다 |
| reducer | `apply`(상태 전이)와 투영기 | 커널용 상태를 계산하는 함수와 화면용 테이블을 갱신하는 투영기가 따로 있습니다 |
| action 로그(로그를 남기는 경우) | 이벤트 로그 | Redux에서 action 로그는 개발 도구용 부가 기록입니다. Helm의 이벤트 로그는 정본이며 순번, 행위자, 근거가 붙고, 순서와 변조 여부를 검사하는 장치가 있습니다(아래 오해 절에서 설명) |
| store의 state | 커널 상태 | 커널 상태는 데몬 메모리에 있고, 데몬이 시작할 때 이벤트 로그(와 캐시인 스냅숏)에서 다시 만듭니다 |
| 파생 데이터(selector) | 투영 테이블 | 투영 테이블은 SQLite에 있고, 로그에서 다시 만들 수 있는 파생물입니다 |

Redux의 action을 "일어난 일"로 모델링하면 Helm의 이벤트에 가깝고, `SET_X`처럼 "해 달라"로 쓰면 Helm의 명령에 가깝습니다. 어느 쪽이든 Redux에는 거부 단계가 없다는 점이 가장 큰 차이입니다. 이 차이가 5번 노드의 커널(`decide`)을 읽는 출발점입니다.

Helm에서 **명령은 상태를 바꾸려는 의도이고, 이벤트는 커널이 평가한 결과의 기록**입니다. `agreement.confirm` 명령이 들어와 커널 검사를 통과하면 `agreement.confirmed` 이벤트가 생기고, 통과하지 못하면 `command.rejected` 이벤트가 생깁니다. 명령 이름은 명령형 동사, 이벤트 이름은 과거형 동사입니다. 이 둘이 항상 1대1은 아닙니다. 명령 하나가 이벤트를 여러 개 만들 수 있습니다. 예를 들어 사람이 결과를 확인하는 명령 하나가 확인 기록, 질문 답변, 반영 작업 생성 같은 이벤트를 한 트랜잭션에서 함께 만듭니다. 명령은 거부될 수 있지만 이벤트는 한번 기록되면 고치거나 지우지 않습니다. 잘못된 기록을 바로잡을 때도 기존 이벤트를 고치지 않고, 바로잡는 새 이벤트를 덧붙입니다.

## 커널 상태와 투영 테이블

이벤트를 접어 만든 결과는 두 가지이고, 쓰임이 다릅니다. **커널 상태**는 커널이 `decide`로 판정할 때 입력으로 받는 값입니다. 데몬 메모리의 객체이고, 시작할 때 최근 스냅숏(로그를 접은 결과를 일정 주기로 저장해 둔 캐시)에 그 뒤 이벤트만 `apply`해서 다시 만듭니다. **투영 테이블**은 화면이 조회하는 SQLite 테이블이고, 같은 트랜잭션 안에서 투영기가 이벤트마다 갱신합니다. 둘 다 로그에서 다시 만들 수 있으므로 정본이 아닙니다. 이벤트 소싱 자료에서 투영은 읽기 모델, 재구성은 재생(replay)이라는 이름으로도 나오므로, 외부 자료를 찾을 때 이 대응을 기억해 두면 됩니다.

## 정본과 정본이 아닌 것

이벤트 로그 옆에는 여러 종류의 저장물이 있고, 그중 무엇이 정본인지 구분하는 것이 구현 리뷰의 출발점입니다. 정본이 아닌 것은 로그에서 다시 만들 수 있거나, 잃어도 도메인 상태가 틀어지지 않는 운영 데이터입니다. 오른쪽 두 열에서 각 저장물이 어느 쪽인지 확인할 수 있습니다.

| 종류 | 무엇인가 | 정본인가 | 잃으면 |
|---|---|---|---|
| 영속 이벤트 | 커널이 명령, 관찰, 타이머를 평가한 결과의 기록(전이 이벤트와 `command.rejected`) | 예 | 복구할 수 없음. 백업에서 복원 |
| 명령 기록 | 들어온 명령과 처리 결과(멱등 재생용) | 아니오(로그에서 다시 만들 수 없는 운영 데이터) | 같은 명령 재시도를 판별하지 못함. 도메인 상태는 그대로 |
| 투영 | 이벤트를 접어 만든 조회용 테이블 | 아니오 | 로그에서 다시 계산 |
| 휘발 이벤트 | 토큰 스트림, 도구 출력 진행처럼 화면 갱신만을 위한 흐름 | 아니오 | 저장하지 않으므로 잃을 것이 없음 |
| trace | 모델 요청, 컨텍스트 압축, 실행 단계 같은 실행 기록 | 아니오(도메인 상태 밖) | 실행 분석이 어려워짐 |
| blob | 큰 내용(도구 출력, 이미지). 이벤트에는 내용 해시만 들어감 | 아니오(이벤트가 해시로 가리킴) | 해시가 맞는 사본이 있어야 내용을 볼 수 있음. 보존 기간이 지나면 지워질 수 있고 이벤트의 해시만 남음 |

**투영**은 Helm 설계에서 특별한 뜻으로 쓰는 말입니다. 정본(이벤트 로그)을 읽어 계산한 결과, 즉 화면에 보이는 테이블이나 모델에게 주는 문맥을 투영이라고 부르고, 이 말을 다른 뜻으로 쓰지 않습니다. 1번 노드의 불변조건 3 "투영은 정본을 쓰지 않는다"는, 화면을 계산하는 코드가 이벤트 로그에 무엇인가를 써 넣는 경로가 없어야 한다는 뜻입니다. 화면을 그리는 코드는 로그를 읽기만 하고, 사람이 화면에서 무엇을 바꾸려면 반드시 명령을 보내야 합니다.

## 한 번의 상태 변경을 따라가 보기

예를 들어 사람이 합의 카드에서 "확정"을 누르는 경우를 단계별로 따라가 보겠습니다.

1. 데스크톱 앱이 `agreement.confirm` 명령을 데몬에 보냅니다.
2. 데몬의 `engine`이 트랜잭션을 열고, 커널에 지금의 커널 상태와 명령을 넘깁니다.
3. 커널이 합의가 확정 가능한 상태인지, 행위자가 사람인지, 앱이 보던 화면이 낡지 않았는지 검사합니다. 허용하면 `agreement.confirmed` 이벤트 초안을 돌려주고, 거부하면 `command.rejected` 초안을 돌려줍니다.
4. 저장소가 초안에 다음 순번과 해시를 붙여 로그에 추가합니다.
5. 같은 트랜잭션 안에서 투영기가 합의 투영 테이블의 상태를 `active`로 고칩니다.
6. 트랜잭션이 커밋되면 구독 중인 앱들에 새 이벤트가 전달되고, 앱이 화면을 갱신합니다.

이 흐름에서 이벤트가 상태로 접히는 과정을 값으로 보면 이렇습니다. 합의가 `agreement.proposed`로 생기면 상태는 `proposed`, 판본 1입니다. 협상 끝에 `agreement.revised`가 기록되면 판본이 2로 오르고, 사람이 판본 2를 확정해 `agreement.confirmed`가 기록되면 상태가 `active`가 됩니다. 이 세 이벤트에 `apply`를 차례로 적용한 결과가 "판본 2, active"인 합의입니다.

이 예에서 규칙을 뽑으면 이렇습니다. 상태를 바꾸는 코드 경로는 "명령 → 커널 판정 → 이벤트 추가 → 투영 갱신"의 한 길뿐이고, 이벤트와 투영은 같은 트랜잭션에서 함께 커밋되거나 함께 버려집니다. 그래서 `p_*` 투영 테이블은 항상 로그와 일치합니다(지표용 투영은 커밋 뒤에 비동기로 채우므로 예외입니다). 투영 테이블이 망가지거나 계산 규칙이 바뀌면, 투영을 버리고 로그를 처음부터 다시 적용해 새로 만들면 됩니다. 이 작업을 **재구성**이라고 부릅니다. 반대로 로그는 다시 만들 방법이 없으므로, 백업은 로그를 기준으로 합니다.

처음 예로 돌아가면, 이 합의가 어떤 판본으로 언제 확정되었는지는 `agreement.confirmed` 이벤트의 판본(`revision`)과 기록 시각에 남습니다. 확정한 사람이 어떤 화면 순번을 보고 있었는지는 이벤트가 아니라 명령 기록에 남고, 명령 기록은 보존 기간이 한정되어 있습니다. 나중에 결과 확인 화면이 "이 결과는 합의 판본 2를 기준으로 제출되었다"고 보여 줄 수 있는 것은 결과 제출 이벤트에 합의 판본이 들어 있기 때문입니다.

## 전체 순서는 순번 하나로 정해진다

Helm의 이벤트 로그는 DB 전체에서 하나뿐인 순번(`seq`)을 씁니다. 프로젝트가 여러 개여도 순번은 하나이고, 빈칸 없이 1씩 증가합니다. 이 순번이 여러 곳에서 기준으로 쓰입니다.

클라이언트는 마지막으로 받은 순번을 기억했다가 재연결할 때 "이 순번 다음부터 보내 달라"고 요청합니다. 사람이 명령을 보낼 때는 화면이 보고 있던 순번(`basisSeq`)을 함께 보내고, 커널은 사람에게 보이는 내용이 그 순번 이후에 바뀌었으면 충돌로 처리합니다. 근거 링크 추가 같은 부수 변경은 여기에 세지 않으므로, 사람이 질문에 답하는 사이 에이전트가 근거를 붙여도 답은 충돌로 막히지 않습니다. 복귀 요약의 "여기까지 봤음"도 순번으로 저장됩니다. 레코드 ID에는 시각 정보가 들어 있지만, 순서 판단에는 순번만 씁니다.

## 흔한 오해

"이벤트 로그는 감사용 부가 기록이고, 진짜 데이터는 테이블에 있다." Helm에서는 테이블(투영)이 파생물이고 로그가 정본입니다. 그래서 투영 테이블에 직접 UPDATE하는 코드가 있다면, 그 변경은 다음 재구성 때 사라지고 로그와 화면이 어긋납니다. 리뷰할 때 `p_`로 시작하는 투영 테이블에 쓰는 코드가 투영기 밖에 있는지 보면 됩니다.

"거부된 명령은 아무 흔적도 남기지 않는다." Helm은 거부도 `command.rejected` 이벤트로 순번을 받아 남깁니다. 같은 명령을 다시 보냈을 때 같은 판정을 돌려주고, 나중에 왜 진행되지 않았는지 찾을 수 있도록 거부도 기록합니다.

"이벤트를 고치면 기록을 정정할 수 있다." 이벤트 테이블에는 수정과 삭제를 막는 장치가 있고, 이벤트마다 앞 이벤트의 해시를 이어 붙인 해시 체인이 있어서 직접 고친 행은 체인 검사에서 불일치로 검출됩니다. 정정은 새 이벤트로 합니다.

다음 4번 노드는 이 모델 위에서 Helm이 실제로 어떤 레코드와 이벤트를 두고, 트랜잭션, 멱등, 동시 실행 방지, 재구성을 어떻게 구현하는지 다룹니다. 해시 체인의 검증 방법과 순번 재전송처럼 구현에 가까운 내용은 4번에서 설명합니다.
