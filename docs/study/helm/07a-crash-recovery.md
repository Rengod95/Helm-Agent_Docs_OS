# 7.1 멱등과 크래시 복구: 재시작 뒤 같은 일을 두 번 하지 않기

## 무엇이 위험한가

데몬은 언제든 멈출 수 있습니다. Windows 업데이트로 PC가 재부팅되거나, WSL이 종료되거나, 메모리가 부족해 프로세스가 죽을 수 있습니다. 멈춘 순간 에이전트가 무엇을 하고 있었는지에 따라 재시작 뒤의 위험이 다릅니다. 모델 응답을 기다리던 중이었다면 응답을 버리고 다시 요청하면 그만입니다. 그런데 도구를 실행하던 중이었다면 문제가 됩니다. 파일을 반쯤 썼을 수 있고, `git push`가 이미 원격에 도착했는데 결과를 기록하지 못했을 수 있습니다. 이때 "결과가 없으니 다시 실행하자"고 하면 같은 발송이 두 번 나가고, "결과가 없으니 실패한 것으로 보자"고 하면 실제로 일어난 변경을 모르고 넘어갑니다.

Helm은 실행 의도, 실행, 결과 순서로 기록하고(결정 30), 재시작 때 결과가 없는 호출을 "중단됨"으로 정리하며, 다시 실행해도 안전한 도구만 다시 실행합니다. 이 노드의 범위는 그 규칙을 구현하는 기록과 판정입니다. 4번 노드의 멱등 키와 펜싱이 쓰이고, 7번 노드에서 본 트랜잭션 B(실행 직전의 의도 커밋)와 C(실행 직후의 결과 커밋)가 판정의 재료가 됩니다. 의도만 남은 호출은 실행 전, 실행 중, 실행 직후 가운데 어디서 끊겼는지 기록만으로 알 수 없다는 것이 이 노드 전체의 출발점입니다.

## 기록 순서가 지켜야 할 여덟 가지

복구가 기록만 보고 판단할 수 있으려면, 정상 실행 때 기록 순서가 정해진 규칙을 지켜야 합니다. 기록 순서는 CR-1부터 CR-8까지의 불변식으로 정해져 있습니다.

| 번호 | 규칙 |
|---|---|
| CR-1 | 루프가 보는 사람 입력과 주입 메시지는 루프에 넘기기 전에 커밋되어 있습니다. |
| CR-2 | 모델 응답과 그 응답의 도구 호출 목록은 도구 준비 전에 커밋되어 있습니다. |
| CR-3 | 도구는 커밋된 `toolcall.started` 없이 실행되지 않습니다. 예외는 의도와 결과를 한 트랜잭션에 쓰는 읽기 빠른 경로와 제안 도구뿐입니다. |
| CR-4 | 호출마다 종결 기록은 정확히 하나이고, 먼저 기록된 것만 남습니다. |
| CR-5 | run의 상태, 시도 번호, 부팅 번호, 재개 횟수는 이벤트로 커밋되고, 재시작 처리는 이 기록만 보고 정합니다. 종료 처리 코드는 보조일 뿐입니다. |
| CR-6 | 커밋 뒤 할 일(지시)은 커밋된 이벤트에서 다시 계산할 수 있습니다. |
| CR-7 | 스트리밍 조각과 진행 중 응답은 저장하지 않습니다. 크래시 때 그 응답은 버리고 같은 run에서 다시 요청합니다. |
| CR-8 | 끝난 run이 실행 중으로 남긴 호출(`started`·`replaying`)은 run을 끝내는 같은 트랜잭션에서 닫힙니다. 사람 승인을 기다리는 `awaiting_approval` 호출은 대상이 아니고, run이 끝난 뒤에도 남아 있다가 새 run이 이어받습니다. |

CR-5의 "종료 처리는 보조"라는 말이 중요합니다. 정상 종료 때 데몬은 진행 중인 일을 정리하지만, 크래시에는 정리할 기회가 없습니다. 그래서 복구가 종료 처리에 기대면 크래시 때 실패합니다. **복구 절차는 DB에 남은 기록만 읽고, 종료 처리가 실행됐는지는 확인하지 않습니다.**

## 도구 호출의 상태와 부팅 때 처리

도구 호출은 다음 상태를 지납니다. `requested`는 모델이 호출을 냈고 아직 실행 의도가 없는 상태, `started`는 의도가 커밋되고 결과가 없는 상태입니다. `replaying`은 재개 run이 다시 실행하는 중이고, `awaiting_approval`은 사람 승인을 기다립니다. 끝난 상태는 결과가 있는 `completed`, 실행되지 않았음이 확실한 `not_executed`, 결과를 알 수 없는 두 가지(외부 효과가 없으면 `interrupted`, 있으면 `outcome_uncertain`), 사람이 해소한 `recovered`입니다. 여기서 `interrupted`는 run 상태 `interrupted`와 이름만 같고 서로 다른 레코드의 상태입니다. 부팅 정리는 이전 부팅이 남긴 호출을 아래 표처럼 처리합니다.

| 이전 부팅이 남긴 상태 | 조건 | 처리 결과 | 기록 |
|---|---|---|---|
| (레코드 없음) | 모델 응답에 호출 ID만 있음 | `not_executed` (재시작으로 실행 안 됨) | `toolcall.skip` |
| `requested` | 유효한 승인이 있음 | 그대로 둠. 이어받는 run이 실행 | 없음 |
| `requested` | 승인이 만료됨 | `not_executed` (승인 만료) | `toolcall.skip`, `approval.expired` |
| `requested` | 승인 기록이 없음 | `not_executed` (재시작으로 실행 안 됨) | `toolcall.skip` |
| `started`, `replaying` | 쓰기 도구이고 현재 해시가 `after` | `completed` (적용된 것으로 합성) | `toolcall.complete` (hash_verified) |
| `started`, `replaying` | 재실행 가능하고 재개 대상 run | 유지. 재개 때 다시 판정 | 계획만 trace에 기록 |
| `started`, `replaying` | 그 밖이고 외부 효과 없음 | `interrupted` | `toolcall.report_unknown` |
| `started`, `replaying` | 그 밖이고 외부 효과 있음 | `outcome_uncertain` + run `awaiting_recovery` + 복구 질문 | `toolcall.report_unknown` |
| `awaiting_approval` | - | 건드리지 않음. 승인이 오면 새 run이 실행 | 없음 |
| `interrupted`, `outcome_uncertain` | 사람이 답하거나 검증 관찰이 옴 | `recovered` | `toolcall.recovered` |

`started`가 모두 "실행 도중"이라는 뜻은 아닙니다. 의도 커밋은 실행 직전에 하므로, 의도 커밋 뒤 실행 전에 취소된 호출은 `started`에서 `not_executed`로 갈 수도 있습니다. 부팅 때 남아 있는 `started`는 그런 취소 기록이 없으니 어디서 끊겼는지 모르는 호출로 다룹니다.

## 재시작 뒤 도구 호출을 어떻게 판정하는가

재시작 뒤 `started`(의도는 있고 결과는 없음) 상태로 남은 호출은 도구마다 선언된 재실행 정책으로 판정합니다. 도구는 `replay: 'never' | 'safe'`를 선언하고, 기본값은 `never`입니다. 다시 실행하려면 의도를 기록한 시점의 선언과 현재 선언이 모두 `safe`여야 하고, 나중에 도구를 `safe`로 바꿔도 과거 호출의 재실행은 허가되지 않습니다. 여기에 조건이 둘 더 있습니다. 도구 버전의 주 버전이 같아야 인자 스키마가 달라지지 않았다고 볼 수 있고, 쓰기 도구는 해시 검사 정보(guard)가 없으면 `never`로 다룹니다. 아래 표의 "결과 불명" 행은 외부 효과가 있거나 효과를 확인할 방법이 없는 도구입니다.

| 도구 | 재실행 정책 | 재시작 뒤 처리 |
|---|---|---|
| read, grep, find, ls, 조회 도구 | safe | 남은 경우 저장된 실행 인자로 다시 실행 |
| write, edit | safe(해시 검사가 있을 때만) | 현재 파일 해시가 "적용 뒤 예상 해시"면 적용된 것으로 결과 합성, "실행 전 해시"면 다시 실행, 그 밖이면 결과 불명 |
| bash | never | 결과 불명. 감지된 파일 변경을 안내에 붙임 |
| web_fetch, web_search, 하위 호출 | safe | 다시 호출(외부 효과 없음, 비용만 다시 듦) |
| browser_* | never | 송신 요청을 보내지 않았으면 중단, 보냈을 수 있으면 결과 불명과 사람 질문 |
| MCP 도구 | 설정값, 기본 never | 기본은 결과 불명 |

쓰기 도구의 해시 검사가 이 표에서 가장 정교한 부분입니다. 쓰기 도구는 의도를 기록할 때 대상 파일의 현재 해시(`before`)와 적용 뒤 나올 해시(`after`)를 함께 남깁니다. 재시작 뒤 파일을 다시 읽어 해시가 `after`와 같으면 쓰기가 이미 끝난 것이므로 결과를 "재시작 전 적용됨"으로 기록하고, `before`와 같으면 쓰기가 일어나지 않은 것이므로 다시 실행해도 안전합니다. 둘 다 아니면 무언가 중간에 끼어든 것이므로 결과 불명으로 닫습니다.

**결과 불명은 외부 효과 여부로 다시 나뉩니다.** 호출에 외부 효과가 있다고 보는 기준은 넷 가운데 하나라도 참인 경우입니다. 원시 행동이 발송(`send`)이거나, 실행에 네트워크(프록시)가 있었거나, 도구 선언의 `externalEffect`가 참이거나, 권한 판정의 `externalEffect`가 참입니다. 따라서 네트워크를 쓴 bash(`git push`, `curl`)는 외부 효과가 있는 호출로 분류됩니다. 외부 효과가 없는 로컬 작업(예: bash로 로컬 파일만 건드린 경우)의 결과 불명은 사람에게 묻지 않고 `toolcall.interrupted`로 닫고, 모델에게 "결과를 알 수 없으니 현재 상태를 확인한 뒤 진행하라"는 안내를 줍니다. 외부 효과가 있을 수 있는 호출(발송, 브라우저 제출 등)의 결과 불명은 `outcome_uncertain`으로 기록하고, 그 run을 `awaiting_recovery`로 두며, 사람에게 복구 질문을 냅니다. 사람은 "적용됨", "적용 안 됨", "직접 확인 작업 만들기" 가운데 하나를 고릅니다. 모델에게는 "사람에게 확인을 요청했으니 반복하지 말라"는 안내가 갑니다. 이 분기는 재시작 때만 쓰이지 않습니다. 데몬이 살아 있는 동안 타임아웃이나 전송 끊김으로 외부 효과가 있는 호출의 결과가 불명해질 때도 같은 규칙입니다.

## 부팅 정리의 순서

데몬 시작 순서의 한 단계로 런타임의 `recover`가 실행됩니다. 이 단계에서는 새 run을 시작하지 않고, 지난 부팅의 흔적만 정리합니다.

1. 이전 부팅의 `started`·`replaying` 도구 호출을 위 표에 따라 정리합니다. 해시로 적용이 확인된 쓰기는 결과를 합성하고, 다시 실행할 호출은 계획만 기록해 두었다가 재개 때 다시 판정하며, 나머지는 중단 또는 결과 불명으로 닫습니다.
2. `requested`로 남은 호출(실행 전)은 유효한 승인이 있으면 그대로 둡니다. 승인이 만료됐으면 "승인 만료로 실행 안 됨"으로, 승인 기록이 없으면 "재시작으로 실행 안 됨"으로 닫습니다.
3. 모델 응답에 도구 호출 ID만 있고 호출 레코드가 없는 경우도 "재시작으로 실행 안 됨"으로 닫습니다.
4. 이전 부팅의 `running`·`stopping` run은 `interrupted`로 바꿉니다. 열려 있던 모델 요청은 버렸다는 기록을 남기고, 커밋되지 않은 요약은 버립니다. 단, 1번에서 결과 불명 외부 호출이 나와 이미 `awaiting_recovery`가 된 run은 `interrupted`로 바꾸지 않고 `run.ended`도 내지 않습니다.
5. 큐에만 있던 run은 `superseded`로 끝냅니다. 사람이나 복구를 기다리던 run(`awaiting_*`)은 건드리지 않습니다. 대기 상태는 질문 레코드에 있으므로 재시작과 관계없이 그대로 유효합니다.
6. 처리하지 못한 지시를 커밋된 이벤트에서 다시 계산합니다. 같은 전달 ID와 멱등 키로 중복을 거릅니다.

각 정리 단위는 실패해도 다른 단위에 번지지 않게 감싸 실행합니다. 한 run의 정리가 실패하면 그 run을 실패로 닫고 복구 항목을 남기며, 그것조차 실패하면 데몬은 읽기 전용 상태로 시작합니다. 정리 명령에는 멱등 키가 붙습니다. run 단위는 `recover:<runId>:<attempt>`, 호출 단위는 `recover:<toolCallId>:<epoch>`이고, `epoch`는 부팅 번호입니다. 이 키는 같은 부팅 안에서 같은 정리가 두 번 제출되는 것을 막습니다. 정리 중에 다시 크래시가 나면 다음 부팅은 새 epoch이므로 호출 단위 키가 달라집니다. 그래도 같은 일이 두 번 일어나지 않는 것은, 다음 부팅의 조회가 `started`·`replaying` 상태인 호출만 대상으로 하여 이미 닫힌 호출을 뺄 수 있기 때문입니다. 호출 단위 키의 `epoch`가 호출을 만든 부팅인지 정리하는 부팅인지는 설계 문서 사이에서 아직 정리 중이고, 위 설명은 정리하는 부팅의 번호를 쓰는 부팅 정리 코드를 따랐습니다.

## 재개: 같은 run의 다음 시도

`interrupted`가 된 run을 이어서 실행하는 것을 재개라고 부릅니다. **재개는 새 run을 만들지 않고, 같은 runId의 시도 번호를 1 올립니다.** 재개 여부는 아래 표를 위에서 아래로 훑어 처음 맞는 조건으로 판정합니다.

| 순서 | 조건 | 결과 | 이유 |
|---|---|---|---|
| 1 | 안전 모드 | 재개하지 않고 대기 상태 유지 | 사람이 풀 때까지 자동으로 하지 않음 |
| 2 | 중재 run | `superseded`로 종료 | 다음 주기에 중재 run이 새로 뜸 |
| 3 | 하위 실행, 가지, 검증 run | `failed`로 종료, 부모에 알림 | 자동 재실행하지 않고 부모가 정함 |
| 4 | 탐구 run | `failed`로 종료 | 오케스트레이터가 단계를 다시 요청함 |
| 5 | Concern 닫힘 또는 WorkUnit 종결 | `superseded`로 종료 | 이어 갈 일이 사라짐 |
| 6 | WorkUnit 일시 정지 | 대기 상태 유지 | 풀릴 때까지 기다림 |
| 7 | 외부 효과가 있어 `outcome_uncertain`이 해소되지 않은 호출이 있음 | 대기 상태 유지 | 복구 질문의 답을 기다림 |
| 8 | 재개 3회 이상 | `recovery_exhausted`로 종료 | 크래시 루프 방지 |
| 9 | 그 밖 | 재개 예약(한 번에 하나, 5초 간격) | |

재개할 때는 먼저 시도 번호를 올린 `run.started`를 커밋합니다. 재개 횟수는 실제 실행 전에 차감하므로, 재개 직후 다시 크래시가 나도 무한 재개에 빠지지 않습니다. 그다음 다시 실행할 호출을 실행 직전에 다시 계산하고(부팅 때 남긴 계획은 참고일 뿐), 저장된 실행 인자로 `toolcall.intend`를 다시 제출해 커널 검사를 받습니다. 그사이 합의가 해제되었거나 범위가 좁아졌으면 재실행도 막힙니다. 통과하면 `toolcall.replay_started`를 남기고 실행한 뒤 "재실행으로 복구됨"으로 닫습니다.

사람이 승인한 행동은 실행 경로가 다릅니다. 승인된 호출은 같은 `toolCallId`로 새 run이 `toolcall.intend`를 다시 제출하고, 커널이 지문을 대조해 승인을 한 번 소진하면서 `toolcall.started`와 `approval.consumed`를 한 트랜잭션에 남깁니다. 제출 결과가 같은 멱등 키의 저장된 결과를 돌려준 것(`replayed`)이면, 이전 시도가 이미 시작했다는 뜻이므로 재개 run은 실행하지 않습니다. 그 호출은 부팅 정리가 처리하고(발송이면 `outcome_uncertain`과 복구 질문), 재개 run은 결과를 기다립니다. 그래서 승인 실행 중 크래시가 나도 같은 발송이 두 번 나가지 않습니다. 실행 직전에는 승인 때 본 파일들의 해시(`targetsDigest`)를 다시 대조하고, 달라졌으면 실행하지 않고 다시 묻습니다.

재개 첫 turn에는 안전장치가 하나 더 있습니다. 결과 불명으로 닫힌 호출 가운데 쓰기, 실행, 발송이 있었으면, 첫 turn 동안 모델이 쓸 수 있는 도구를 재개 첫 turn용으로 안전하다고 표시된 도구(읽기, 조회, 웹 읽기, 제안·선언 도구)로 좁힙니다. `write`와 `edit`는 해시 검사가 있으면 재실행해도 안전하지만 이 목록에는 들어가지 않습니다. 이 범위가 12번 문서 본문과 13번 문서 표에서 아직 다르게 적혀 있어, 설계 문서 사이에서 아직 정리 중입니다. 모델이 상태를 먼저 확인하게 하려는 것이고, 첫 turn이 끝나면 원래대로 돌아옵니다. 모델에게는 무엇이 중단되었고 결과가 어떻게 정리되었는지 안내가 주입됩니다.

재개를 포기한 run은 복귀 요약의 복구 항목에 나타나고, 사람은 "마지막 확인 지점부터 다시 실행", "그대로 두기", "확인 작업 만들기" 가운데 하나를 고릅니다. 재시작 때 미루어지는 만료(복귀 뒤 30분 등)는 3번 노드에서 다룹니다.

## 안전 모드: 자동으로 하지 말아야 할 때

두 상황에서는 데몬이 자동 재개를 멈추고 사람을 기다립니다. 하나는 크래시 루프입니다. 10분 안에 정상 종료되지 않은 부팅이 세 번 이상이면, 무언가 반복적으로 데몬을 죽이고 있다는 뜻이므로 자동으로 같은 일을 다시 시작하지 않습니다. 다른 하나는 백업 복원 뒤 첫 부팅입니다. 백업 시점에 실행 중이던 run을 자동으로 재개하면, 백업 이후 이미 끝난 쓰기, push, 발송을 다시 하게 됩니다.

안전 모드에서는 run 자동 재개, 에이전트 run을 시작하는 타이머, 관찰 에이전트, 새 실행 허가가 모두 멈춥니다. 사람이 데스크톱, 휴대폰, 대화형 CLI(`helm ops safe-mode off`)에서 안전 모드를 끄면 그때 재개 판정이 실행됩니다. 안전 모드의 운영 측면은 12번 노드에서 다룹니다.

## 정상 종료는 어떻게 다른가

정상 종료 때 데몬은 스케줄러를 멈추고, 새 run과 새 turn을 막은 뒤 진행 중인 turn을 최대 20초 기다리고, 그래도 남은 것은 중단합니다. 모델 요청을 취소하고, 도구 프로세스에는 SIGTERM을 보낸 뒤 5초 뒤 SIGKILL을 보내며, 끊긴 호출과 run을 "데몬 종료로 중단"으로 기록합니다. 결과 불명 외부 호출이 있어 이미 `awaiting_recovery`가 된 run은 부팅 정리와 같이 `interrupted`로 바꾸지 않습니다. 이 절차가 중간에 실패해도 다음 부팅의 정리 절차가 같은 기록을 읽어 같은 결과를 만들므로 복구 결과가 달라지지 않습니다. 정상 종료 처리는 복구를 빠르게 할 뿐, 복구의 정확성은 부팅 정리가 보장합니다.

디스크가 가득 차서 결과를 커밋하지 못하는 경우도 있습니다. 이때는 결과 내용을 별도 파일에 디스크 동기화까지 해서 쓰고, run을 더 진행하지 않습니다. 결과를 잃은 채 다음 일을 하지 않으려는 것입니다.

## 흔한 오해

"재시작하면 중단된 일을 처음부터 다시 하면 된다." 다시 해도 되는 일은 읽기, 해시로 확인 가능한 쓰기, 외부 효과 없는 호출뿐입니다. bash와 발송, 브라우저 조작은 다시 실행하지 않고, 결과를 모르면 모른다고 기록합니다(1번 노드의 불변조건 6, 모르는 것을 숨기지 않는다).

"결과 불명이면 사람에게 묻는다." 외부 효과가 있을 수 있는 경우에만 묻습니다. 로컬 작업의 결과 불명까지 모두 물으면 재부팅 한 번에 질문이 쏟아지므로, 그 경우는 모델이 상태를 확인하게 합니다.

"재개는 새 run이다." 재개는 같은 runId의 다음 시도이므로 재개로 새 run이 생기지 않습니다. 새 run은 사람 답을 받아 같은 thread에서 이어받을 때(`handed_off`)처럼 별도의 계기로 생깁니다. 둘을 구분해야 펜싱(시도 번호 대조)과 재개 횟수 제한이 맞게 동작합니다.

## 이 노드의 기준으로 구현을 볼 때

- 도구의 재실행 판정이 의도 시점 선언과 현재 선언, 주 버전, 쓰기 도구의 guard 유무를 모두 보는가
- 쓰기 도구가 의도 기록 때 `before`·`after` 해시를 남기고, 재시작 뒤 이것으로 판정하는가
- bash와 browser_*가 재시작 뒤 다시 실행되는 경로가 있는가
- 외부 효과가 없는 결과 불명은 질문 없이 `interrupted`, 있으면(발송, 네트워크 있는 샌드박스, 도구 선언, 권한 판정 중 하나) `outcome_uncertain` + 복구 질문으로 갈리는가
- 부팅 정리가 종료 처리 코드에 기대지 않고 기록만으로 동작하는가. 여러 번 실행해도 결과가 같은가
- `awaiting_*` run과 `awaiting_approval` 호출을 부팅 정리가 건드리지 않고, `awaiting_recovery`가 된 run을 `interrupted`로 바꾸지 않는가
- run을 끝내는 트랜잭션이 그 run의 `started`·`replaying` 호출만 닫는가
- 재개가 같은 runId의 `attempt + 1`이고, 재개 횟수가 실행 전에 차감되며, 3회 상한이 있는가
- 재실행 전에 커널 재검사(`toolcall.intend` 재제출)를 거치고, 승인 재제출이 `replayed` 결과를 돌려주면 실행하지 않는가
- 재개 첫 turn의 도구 제한이 조건에 맞게 켜지고 첫 turn 뒤 풀리는가
- 크래시 루프와 복원 뒤 첫 부팅에서 자동 재개가 멈추는가
- 장애 주입 시험이 있는가: 도구 실행 중 크래시(FI-03), `git push` 중 크래시(FI-05), 승인 실행 중 크래시(FI-14), 부팅 복구 중 다시 크래시(FI-15), 디스크 가득(FI-16), WSL 종료(FI-22)
- 복원 뒤 첫 부팅에서 미소진 승인이 닫히고 안전 모드가 켜지는가
