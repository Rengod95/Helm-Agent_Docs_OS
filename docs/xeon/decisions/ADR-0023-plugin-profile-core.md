# ADR-0023 플러그인과 프로필: 고정 코어, 세 가지 일, 주도권 스택, 검토, 프로젝트 재정의

## 1. 상태와 날짜

- 상태: draft. 아래 결정은 사용자가 2026-11-16, 2026-11-17에 정한 것이고 이 문서는 그 결정을 한 곳에 고정한다. 문서 자체의 승인은 대기 중이다. 사용자 확인이 남은 항목은 [확인 대기]로 적었고 §8에 모았다.
- 날짜: 2026-11-17
- 근거: 사용자 결정 기록 `_notes/m4-decisions.md`의 "2026-11-16~17 (사용자) 플러그인 개념과 Craft 흐름"과 그 뒤 "2026-11-17 밤" 항목들(저장소 밖 메모). 설계 정본은 이 ADR을 구현하는 설계 스펙 다섯이다: `docs/xeon/review/m5/drive-isolation.md`, `profile-project-loader.md`, `turn-record-metrics.md`, `hooks-core-boundary.md`, `docs/xeon/review/m6/craft-flows.md`. 요구와 일정은 `docs/xeon/review/m5-plan.md`와 `m6-plan.md`다.

## 2. 맥락

- 조사 여섯 건(저장소 밖 조사 메모 `research-1`~`6`)에서 사용자가 코딩 에이전트에 대해 가장 크게 불만으로 삼는 것은 셋이다. 보이지 않는다(규칙이 그 턴에 모델에게 갔는지, 훅이 막은 것인지 고장 난 것인지 모른다). 지키게 할 수 없다(지침은 권고일 뿐이고 강제는 전문가의 일이다). 믿을 수 없다(신뢰는 설치 때 한 번인데 코드는 그 뒤에 바뀌고 수단이 겹쳐 출처를 모른다).
- Fresnel은 플러그인 체계와 화면(Craft)을 이미 가졌지만 용어가 섞여 있고(확장, 플러그인, 플러그인 그룹, 애드온), 플러그인별 켜고 끄기와 층 우선순위(전역 → 프로젝트 → 대화)가 있어 같은 문제를 그대로 가진다. 주도 함수는 `loop.turn()`을 직접 부르고 기다리는 명령형이라 프로세스 경계를 넘기 어렵고 다른 플러그인에게 맡겼다 돌려받는 길이 없다. 훅은 46개가 모두 공개이고 그중 42개가 pi 이벤트를 옮긴 것이다.
- 사용자 코드(훅, 도구, 주도)는 엔진 프로세스 안에서 전체 권한으로 돈다. 검토 없이 설치되고 설치 뒤에 바뀐 내용이 그대로 실행된다.
- 사용자는 한 명인 단계라 채택률보다 "되는가"를 재는 제품이다. 에이전트를 자기 방식에 맞추는 일은 대화에서 "다음부터는 이렇게 해"라고 말한 것이 코드를 직접 쓰지 않고 강제되는 플러그인이 되는 흐름이 80~90%다.

## 3. 결정

각 항목의 상세 규칙은 괄호 안의 설계 스펙이 정한다. 표지: [결정] 사용자가 정한 것(날짜를 적는다), [제안] 작성자의 설계 선택, [권고: 메인 세션, 확인 대기] 메인 세션이 권하고 사용자가 아직 정하지 않은 것(작업 기본값으로 쓰고 사용자가 다르게 정하면 고친다), [확인 대기] 사용자 확인이 남은 것.

### 3.1 단위는 플러그인과 프로필 둘이다

1. [결정: 2026-11-16 사용자] 에이전트를 바꾸는 유일한 단위는 **플러그인**이다. 스킬 하나도, MCP 서버 하나도, 훅 스크립트도, Helm도 플러그인이다. 폴더 하나가 플러그인이다(스킬 폴더, MCP 설정, Hook 코드, Drive 코드를 같은 방식으로 읽는다).
2. [결정: 2026-11-16 사용자] **프로필**은 플러그인 목록과 각 플러그인의 설정 값에 이름을 붙인 것이고 코어의 설정 값(권한 모드, 기본 모델 등)과 시작 Drive를 함께 가진다. 별도의 "블록 설정" 개념은 없다.
3. [결정: 2026-11-16 사용자] 화면 용어는 플러그인과 프로필 둘이다. "확장", "플러그인 그룹", "애드온"은 화면에서 쓰지 않는다. 플러그인 그룹이라는 종류와 매니페스트의 `plugin-group` 종류 값은 폐기한다.

### 3.2 고정된 코어: 블록 여섯, 변경 가능한 네 겹, 잠긴 보장

1. [결정: 2026-11-16 사용자] 코어는 고정이고 플러그인이 바꿀 수 없다. 코어는 블록 여섯을 가진다: 컨텍스트 조립, 모델 호출, 도구 실행, 사람에게 묻기, 서브에이전트, 기록. 블록 안에서 권한, 샌드박스, 기록, 한도가 강제되므로 블록을 누가 어떤 순서로 부르든 관문은 그대로 지나간다. 기본 턴 흐름은 컨텍스트 조립 → 모델 호출 → 도구 실행의 표준 조합이다.
2. [결정: 2026-11-16 사용자] 기록 블록은 이벤트 구독만 있고 고치거나 막는 Hook이 없다.
3. [제안] 블록마다 네 겹을 둔다: 설정 겹(값 고치기), Inject 겹(재료 공급), 부품 교체 겹(예: 편집 도구를 `hashline edit`로), 앞뒤 Hook 겹. 맨 아래에 잠긴 보장이 있고 플러그인이 바꿀 수 없다. 블록의 설정 키는 코어 패키지가 소유한 키와 소유 플러그인이 있는 키로 나뉘고 화면이 블록별로 묶어 보인다(`hooks-core-boundary.md` §4.8).
4. [결정: 2026-11-16 사용자] 코어 루프의 교체와 블록 안의 교체는 허용하지 않는다. 플러그인은 자기 루프를 가질 수 있지만 모델·도구·사람에게 닿는 길은 코어의 블록뿐이다.

### 3.3 플러그인이 하는 일은 Inject, Hook, Drive 셋이다

1. [결정: 2026-11-17 사용자] 하는 일의 화면 이름은 영어 **Inject / Hook / Drive**다. 한국어 이름("주입", "훅", "주도", "더하기", "연결하기", "이끌기")을 만들지 않는다.
2. Inject는 블록에 재료를 공급하고 코드가 돌지 않는다(지침, 스킬, 도구 선언, MCP 서버, 서브에이전트 정의, 모델 제공자, 명령, 화면). 권고다. Hook은 블록 사이에서 고치거나 막고 코드가 돈다. 강제다. Drive는 주도권을 받아 블록으로 자기 흐름을 돌리고 코드가 돈다. 강제다. 한 플러그인이 셋을 함께 쓸 수 있다. 화면은 플러그인마다 "권고인지 강제인지"를 보인다.
3. [결정: 2026-11-17 사용자, "전체 동의"] 모든 플러그인(종류와 무관하게)은 같은 스키마로 보인다: 이름과 목적 한 문장, 하는 일 세 칸, 강제력, 실행(코드가 도는가, 격리됐는가), 비용(항상 / Drive 중 / 필요할 때), 건강, 출처와 검토, 쓰는 곳. 차이는 "하는 일" 칸을 펼쳤을 때만 나온다.

### 3.4 Hook 위치 규칙과 결정값

1. [결정: 2026-11-16, 2026-11-17 사용자] Hook 위치의 개수를 못 박지 않고 규칙으로 정한다: "블록마다 앞과 뒤 + 루프 경계 셋(대화 시작, 입력 받기, 턴 종료 직전)". 지켜보기는 이벤트 구독 하나로 합친다. 사람에게 묻기와 서브에이전트의 앞뒤는 지금 훅에 없는 새 위치다. 저장된 훅 이름 문자열은 바꾸지 않는다.
2. [결정: 2026-11-17 사용자, U3] 도구 실행 앞의 결정값은 막기(`block`), 결과 대신 주기(`replace`), 묻기(`ask`)다. 같은 위치에 여러 Hook이 있을 때 `tool.call.before`와 `agent.spawn.before`에서는 `block` > `replace` > `ask` 순으로 이긴다. 훅 등급(tier)은 셋이고 guard가 맨 앞이다. 이것이 2026-11-03의 "처음 결정으로 멈춘다"의 동작을 바꾼다. 사용자가 확인한 것은 여기까지다. 세부는 [제안]이다: 합치기를 이 두 위치에만 쓰고 다른 위치의 first 훅은 바꾸지 않는다, 모든 핸들러가 돈 뒤 정한다, 같은 종류는 순서가 앞선 쪽, 등급 이름(guard / plugin / core), 기본 순서 guard → plugin → core.
3. 훅의 결정값, 기록된 결과값, 표시값(통과, 고침, 물음, 막음, 오류, 시간 초과)은 한 번씩만 정의하고 변환표 한 벌로 잇는다(`hooks-core-boundary.md` §4.5).
4. [제안] 매니페스트 훅 선언에 낼 수 있는 결정(`decides`)을 선택으로 선언하게 해 권한 칸이 "묻는 Hook"을 정적으로 나열한다. 강제하지 않는다.

### 3.5 주도권은 프레임 스택이고 주도 함수는 단계 함수다

1. [결정: 2026-11-16, 2026-11-17 사용자] 주도권은 A → B → C → B → A로 맡겼다 돌려받는다. 코어의 기본 턴 흐름이 맨 아래 프레임(깊이 0)이고 맨 위 프레임만 주도한다. 주도권을 받는 계기는 사용자의 명령, 프로필의 시작 Drive, 현재 주도하는 쪽의 맡기기 셋뿐이다. 플러그인이 스스로 빼앗지 못한다.
   - [권고: 메인 세션, 확인 대기] 깊이 상한은 기본 3이고 맡은 쪽이 쓴 턴과 토큰은 맡긴 쪽의 한도에서 빠진다(차감 세부 포함). 작업 기본값이다.
   - [제안] 이끄는 동안의 지침은 그동안에만 모델에 들어간다.
2. [결정: 2026-11-17 사용자] 주도 함수는 **단계 함수**다: 엔진이 상태와 직전 결과를 주면 플러그인이 다음 명령 하나(`turn`, `model`, `tool`, `ask`, `spawn`, `handoff`, `commit`, `yield`, `done`)를 돌려준다. 옛 `DriveFn` 어댑터는 두지 않고 Helm과 플러그인 빌더를 새 모양으로 다시 구현한다.
3. [결정: 2026-11-17 사용자, U1] 명령 결과의 내구 기록은 대화 로그의 새 상태 사건 하나로 남긴다(재시작 뒤 같은 모델 호출을 두 번 하지 않는 유일한 길).
4. [권고: 메인 세션, 확인 대기] 사용자 명령이 구동기보다 우선한다: 주도 중에 다른 주도 명령을 치면 현재 스택을 내리고 새 주도를 시작하며 한 줄로 알리고 묻지 않는다. 사용자는 "두 번째 주도자가 올 수 있나"만 물었고 이 규칙은 메인 세션이 낸 것이다. 작업 기본값으로 두고 사용자가 다르게 정하면 고친다(§8). 이 규칙에 기대는 종료 조건(`m5-plan.md` Z4)도 같은 상태다.
   - [결정: 2026-11-17 사용자] 사용자 중지는 스택 전체와 백그라운드 서브에이전트를 함께 멈춘다.
   - [제안] 주도 중에 온 사용자 메시지는 맨 위 프레임에 바로 전달되고 플러그인이 3단계 안에 처리하지 않으면 코어 루프가 받는다.
5. [결정: 2026-11-17 사용자] 플러그인 코드가 L2 기능을 직접 부르는 길은 닫지 않고 엔진이 효과 있는 호출을 도구 실행 블록에 태운다(권한 모드, 다른 플러그인의 Hook, 실행 기록, 변경 추적이 따라온다).

### 3.6 프로필은 대화 단위이고 플러그인별 스위치가 없다

1. [결정: 2026-11-16 사용자] 대화는 프로필 하나를 따른다. 새 대화는 프로필이 골라진 채 열린다. 프로필을 고치면 그 프로필을 쓰는 대화가 다음 단계 경계에서 따라 바뀐다. 대화마다, 도중에도 바꾼다. 플러그인별 켜고 끄기와 설정 층 우선순위(전역 → 프로젝트 → 대화)는 없다. "이 대화만 다르게"는 프로필 복제로 푼다. 오류로 멈춘 플러그인은 스위치가 아니라 상태로 보인다.
2. [결정: 2026-11-16 사용자] 프로필이 권한 모드를 가진다. 지울 수 없는 내장 기본 프로필(`default`)을 두고 권한 모드는 "모두 허용"이다. 승인 카드의 "이 대화에서 계속 허용"은 대화의 실행 상태이고 전환이 지우지 않는다. 프로필 전환으로 권한이 넓어지면 표시만 하고 확인은 받지 않는다. 사용자가 두는 "모든 프로필 공통" 묶음이 모든 프로필에 항상 더해지고 코어는 프로필 밖에 항상 켜져 있다.
3. [결정: 2026-11-17 사용자] 탈출구는 프로필 칩(기본 프로필로 한 번에 전환)이다. 막은 카드에는 빼기 단추를 두지 않고 특정 플러그인은 명령 또는 다른 화면(프로필 화면)으로 뺀다.
   - [결정: 2026-11-16 사용자] 서브에이전트는 부모 프로필을 물려받는다. 프로필은 "대화를 시작할 때 누가 주도하나"(시작 Drive)를 가진다. 시작 Drive의 세부(테스트 대화에서 다시 쌓는 방식 등)는 [제안]이다.
4. [결정: 2026-11-17 사용자, U5] 프로젝트에 기본 프로필은 없다. 새 대화의 선택기는 같은 폴더에서 마지막에 쓴 프로필로 채워진다(저장 없이 계산).
5. 설정 범위는 `managed > launch > profile > local > project > user > default`이고 대화 범위는 없다. 플러그인 설정 값은 프로필마다 두고 정하지 않으면 플러그인 기본값을 쓴다. 시크릿 값은 시크릿 저장소 참조만 저장한다.

### 3.7 원본은 폴더, 앱은 검토된 사본만 실행하고 모든 생성과 변경은 검토를 지난다

1. [결정: 2026-11-16, 2026-11-17 사용자] 플러그인의 원본은 폴더이고 앱은 내용 해시로 고정한 **검토본**만 실행한다. 원본이 바뀌어도 실행 중인 것은 그대로이고 검토함에 새 버전이 올라온다. 새 플러그인, 새 버전, 원본 변경, 삭제가 모두 검토함 한 곳을 지난다.
2. [결정: 2026-11-16 사용자] 모든 생성에 사람 검토가 필수다. 에이전트(플러그인 빌더, 테스트 대화)는 Inject, Hook, Drive 세 방식을 모두 만들 수 있고 빌더는 직접 설치하지 않고 초안을 만들어 검토함으로 보낸다. 승인 전에는 어느 프로필에도 들어가지 않는다.
3. [결정: 2026-11-17 사용자] **손으로 고치는 것은 허용하지 않는다.** 수정은 담당 AI(테스트 대화, 대화의 빌더)로만 하고 그래서 검토 절차가 하나로 모인다. 손으로 고친 것으로 보이는 변경은 승인할 수 없고 되돌리기, 담당 AI에게 넘기기, 버리기가 있다.
4. [결정: 2026-11-17 사용자] 프로필 화면의 "지침 추가"는 허용된다. 사용자가 지침 한 줄을 쓰면 지침만 든 플러그인 초안이 되고 검토함을 지난다(사용자가 쓴 것이라 한 번의 확인). 이것은 손 수정 금지의 예외가 아니다.
5. [결정: 2026-11-17 사용자] 초안은 테스트 실행과 사용자가 명시한 덧씌우기에서만 검토 없이 돈다. 초안 출신 호출은 권한 모드와 무관하게 항상 승인 카드와 "초안" 표시를 띄운다(U2). 단, 테스트 실행의 드래프트 승인이 `auto`인 대화는 예외다([결정: 2026-11-18 사용자, AGE-56]). 초안의 기록은 지표 기본에서 빠진다. [권고: 메인 세션, 확인 대기] 초안은 격리된 프로세스에서 돌고 격리 1단계 전에는 돌리지 않는다.
6. 프로젝트 폴더에 든 플러그인은 허용하고, 프로젝트를 열 때 검토함에 올라오며 승인 전에는 실행되지 않는다. 번들(기본 설치, 지금은 Helm)은 사용자 등급이고 격리 대상이다. 저장소 패키지(내장)만 엔진 안에서 돈다.

### 3.8 일회 사용

1. [결정: 2026-11-17 사용자] 프로필에 없는 검토된 플러그인을 사용자가 직접 부르면 그 턴에만 적용된다(Drive는 주도권을 내려놓을 때까지). 모든 유형(Inject, Hook, Drive, 도구)에 허용한다. 구현은 "이번 턴에만 얹는 프로필 덧씌우기"다. 덧씌우기의 수명은 `turn` 또는 `release`다.
2. [결정: 2026-11-17 사용자] 입구는 입력창의 `/`다. 스킬, 명령, Drive, Hook 전용, 도구 전용 플러그인 모두 `/`로 부른다. 명령이 없는 플러그인(Hook 전용, 도구 전용)은 `/<플러그인 이름>`이 그 턴에 플러그인 전체를 얹는다. 이름 충돌은 명령·스킬이 이기고 `/plugin:<이름>`으로 한정한다 [제안]. 도구를 얹으면 그 턴의 캐시가 한 번 깨진다. 검토된 플러그인만 얹고 초안은 명시로 고를 때만 얹는다.

### 3.9 프로젝트의 재정의 (ADR-0022 §3.3과 2026-11-04 결정을 대체한다)

1. [결정: 2026-11-17 사용자] 프로젝트는 최소한의 공통 맥락만 준다. 프로젝트 하나에 루트 작업 폴더 하나가 있고 대화는 그 안의 아무 하위 폴더(대화 폴더)에서 시작하며 구성 제약이 없다. 쓰기 허용 범위는 루트 전체다. 루트에서 대화 폴더까지 경로의 지침 파일(`AGENTS.md`)이 모델 문맥에 실린다. 프로젝트가 없는 대화는 전용 기본 폴더에서 관리한다.
2. [결정: 2026-11-17 사용자] **플러그인과 프로필은 프로젝트가 아니라 대화 단위로 적용한다.** 프로젝트는 공통 지침, 공통 파일, 플러그인 설정을 함께 쓰는 묶음이 아니다. 이것은 **ADR-0022 §3.3 전체(전역 → 프로젝트 → 대화 덧씌우기, 프로젝트 층의 기본 프로필과 플러그인 그룹, 항목별 출처 배지, 덧씌우기 결과를 Registration의 thread별 켜짐으로 옮기는 규칙)와 2026-11-04 사용자 결정("프로젝트는 대화를 묶고 공통 지침·공통 파일·플러그인 설정을 함께 쓴다")을 대체한다.**
3. [결정: 2026-11-17 사용자, U6] 같은 폴더에서 대화 둘이 돌 때 코어는 알리기만 한다(막지 않고 자동 복사도 없다). "대화 시작" Hook이 폴더 경로 하나를 돌려주면 그 대화의 작업 폴더가 되고, worktree 분리는 그 위의 플러그인이다.

### 3.10 프로세스 격리는 1·2단계까지, 네트워크는 전체 허용

1. [결정: 2026-11-16, 2026-11-17 사용자] 사용자·프로젝트·번들 플러그인의 코드(훅, 도구, 주도)는 샌드박스로 감싼 플러그인 프로세스에서 돈다. 1단계는 훅과 도구, 2단계는 주도(단계 함수를 경계 너머로)다. 프로세스는 `(이름, 내용 해시 또는 draftId)`마다 하나다. 플러그인 API는 즉시 답하는 호출 없이 설계한다. 통신 지연 측정을 먼저 한다.
2. [결정: 2026-11-17 사용자] 네트워크는 전체 허용이 기본이다. 3단계(플러그인별 네트워크 허용 목록, Windows 샌드박스)는 외부 사람이 만든 플러그인을 받게 될 때 다시 본다. 남는 위험(훅이 받은 대화 내용과 도구 결과를 밖으로 보낼 수 있음)이 있다. [권고: 메인 세션, 확인 대기] 이 위험은 코드가 도는 플러그인의 검토함 카드에 고정 안내로 보이고(`m5-plan.md` R27), "격리돼 안전하다"는 파일 범위에 한정된 말이다.

### 3.11 읽기 호환은 하지 않는다

1. [결정: 2026-11-16, 2026-11-17 사용자] 다른 하네스 형식(`.mcp.json`, `.agents/skills`, 그 밖의 형식)을 인식하지 않는다. 플러그인 폴더는 Fresnel 자체 배치만 쓴다.
2. [결정: 2026-11-17 사용자] 지금 엔진이 읽는 루트 `.mcp.json`(MCP 로더)과 `.agents/skills`(폴더 신뢰의 자원 판정)는 제거한다. 변환은 별도 마이그레이션 기능으로 설계하고 만든다. 설계 단계가 먼저이고 구현 계획에서 독립 항목(M5g)이다. 이전에 "나중의 마이그레이션 패키지"로만 적었던 것을 이 결정이 구체화한다.

### 3.12 층은 코어와 플러그인 둘로 본다

1. [결정: 2026-11-17 사용자, U4] 사용자와 개념 문서에서는 "코어(블록)와 플러그인"만 쓴다. L2 가운데 코어인 부분(사람에게 묻기, 샌드박스를 거치는 파일·프로세스 서비스)은 L1로 내리고 나머지 기능(MCP, 웹, 지식, 작업 관리, 산출물, 예약 등)은 기본 설치 플러그인으로 한 등급으로 본다. 결과로 "뺄 수 없는 플러그인은 없다". 개념 초안의 "코어 플러그인은 모든 프로필에 항상 들어 있고 뺄 수 없다"를 대체한다.
2. 이것이 참이 되려면 기본 설치 플러그인이 사용자 플러그인과 같은 공개 API로 만들어져야 한다. 내장 전용 통로는 목록으로 관리하며 줄여 간다. 코드의 디렉터리 이름(`cap-*`, `group-*`)과 의존 규칙은 그대로 둔다. 문서의 층 지도 이름을 고쳐 쓸지는 [확인 대기]다.

### 3.13 기록과 지표

1. 턴 기록은 호스트의 `measure.db`를 확장해 저장하고 대화 로그에는 관찰 값을 더하지 않는다(상태 사건만 로그에 더한다). 블록별로 실린 것과 Hook의 결과, 호출 주체, 프레임, 덧씌우기·초안·테스트 표지가 남는다. 지표는 플러그인별 비용, 활동, "살펴볼 것"(발견)이다. 모든 발견에는 다음 걸음(고치기, 올리기, 빼기)이 붙는다.
2. 기록 범위는 `live`, `overlay_reviewed`, `overlay_draft`, `test`, `craft`이고 지표 기본 필터는 앞 둘이다.
3. [결정: 2026-11-12 사용자, 상시 규칙] 모델 컨텍스트는 최소로 둔다: 시스템 프롬프트, 환경 블록, 도구 설명에 요청 없이 줄을 더하지 않는다. 화면용 데이터는 모델에 가지 않는다.

### 3.14 Craft의 화면 어휘와 순환

1. [결정: 2026-11-17 사용자] Craft는 순환이다: 만들기 → 테스트 → 검토 → 프로필에 넣기 → 대화에서 쓰기 → 관찰 → 고치기. 만들기의 입구는 대화(80~90%)와 Craft 둘이고 Craft에는 전용 AI 대화창을 떠 있는 형태로 둔다. 디자인은 별도 HTML이 아니라 앱 안에 직접 만든다(Craft v2 HTML 시안은 반려).
2. [결정: 2026-11-17 사용자] Craft 전용 AI 대화는 **테스트 대화**, 초안을 기준 프로필에 얹어 돌려 보는 일은 **테스트 실행**이다. 둘은 별개다. "시험장"이라는 장소 이름은 반려했다.
3. [결정: 2026-11-17 사용자] 장소 이름은 "테스트"다("시험장"은 반려, 다른 이름은 쓰지 않는다).
4. [결정: 2026-11-17 사용자] Craft 내비는 여섯 항목(개요, 프로필, 검토함, 테스트, 지표, 플러그인)이다. 플러그인 목록은 독립 항목이고 플러그인 그래프는 개요에 둔다. 플러그인 상세와 턴 기록은 다른 곳에서 이어지는 목적 화면이다. 엔진 설정을 Craft에서 설정 화면으로 옮기는 것은 [제안]이다.
5. [권고: 메인 세션, 확인 대기] 오늘의 "성능 측정" 화면(조사 결과: 턴별 성능 화면과 승격 보고이고 비교 기능은 연결돼 있지 않다)은 지표와 턴 기록으로 흡수한다. 승격 보고는 따로 결정한다.
6. [결정: 2026-11-17 사용자] M6의 시각 방향(스펙이 아니라 메모): 앱 안의 두 번째 시도(레일, 정거장, 조각)를 보고 "방향은 나쁘지 않으나 완성도가 낮다"고 했다. 그래프와 차트를 훨씬 적극적으로 쓰고, 외부 차트 라이브러리와 최신 사례를 조사해 쓰며, 여러 대안을 한 빌드에서 바꿔 볼 수 있게 나란히 만든다. 그래서 M6의 첫 걸음은 "개요와 플러그인 상세의 대안 셋을 앱 안에 만들기"다.

## 4. 결과

### 4.1 좋은 점

- "이 대화에 무엇이 적용되고 있나"에 프로필 하나로 답할 수 있다. 플러그인 스위치와 설정 층이 사라져 출처를 따지는 일이 줄어든다.
- 검토 없이 실행된 코드가 없고(사용자가 명시로 얹은 초안 제외), 검토 뒤 원본이 바뀌어도 실행되는 것은 검토한 내용이다.
- 블록 단위의 보장 위에 모든 호출이 서므로 주도 플러그인과 사용자 플러그인이 권한, 샌드박스, 기록을 빠뜨리지 않는다.
- Hook의 막음과 고장, 무엇이 실렸는지가 턴 기록에 남아 "왜 이랬나"에 답할 수 있다.
- 플러그인이 대화를 주도하고 다른 플러그인에게 맡겼다 돌려받을 수 있으며 재시작 뒤에도 이어진다.

### 4.2 감수할 점

- 저장 문자열(이벤트 kind, 필드 이름)은 바꾸지 않고 더하기만 하므로 옛 이름이 코드에 남는다(`lease.*`, `workspace`).
- 네트워크 전체 허용 때문에 코드가 도는 플러그인은 받은 내용을 밖으로 보낼 수 있다. 검토함의 고정 안내와 검토가 유일한 방어다.
- 같은 위치 Hook의 합치기(U3)가 2026-11-03의 "처음 결정으로 멈춘다"를 바꾼다. 기존 플러그인의 동작이 달라질 수 있다.
- 읽기 호환 제거(§3.11)는 지금 `.mcp.json`과 `.agents/skills`를 쓰는 사용자에게 보이는 회귀다. 릴리스 노트와 마이그레이션 기능이 필요하다.
- 구현은 계약 동결(C0), 주도(E1~E3), 격리(P1·P2), 프로필·프로젝트·로더(M5c), 기록(M5d), Hook 정리(M5e)가 얽혀 있고 같은 파일을 여럿이 고친다. 순서 제약이 많다(`m5-plan.md`).
- 플러그인마다 프로세스 하나(§3.10)는 메모리와 시작 시간 비용이 있다. 측정 결과가 넘치면 같은 신뢰 등급끼리 묶는 설정을 둔다.

### 4.3 바뀌는 문서와 코드

문서는 층 스펙(`docs/xeon/<층>/<도메인>/spec.md`)을 구현 트랙이 코드와 같은 커밋에서 고친다. 각 설계 스펙이 어느 층 스펙을 바꾸는지는 그 문서 첫머리에 있다. `terms.json`의 새 용어 등록은 사용자가 이름을 확인한 뒤 별도 트랙이 한다(`hooks-core-boundary.md` §14에 요청 목록). 코드 변경 순서는 `m5-plan.md`다.

| dsh식 "모든 것이 플러그인": 루프 자체도 플러그인이 교체한다 | 루프와 블록 안의 교체를 허용하면 권한, 샌드박스, 기록의 보장이 깨진다. dsh는 코어에 턴·토큰 한도가 없고 계속 횟수 상한이 없어 폭주 보고가 있으며 주도권 넘기기가 없다. 우리는 블록을 고정하고 플러그인이 블록을 부르게 했다. dsh에서 보고된 문제(주도 중 사용자 메시지가 막힘, 계속 횟수 폭주, 재시작 때 입력 유실, 중복 방지 키 없음)를 설계 조건으로 가져왔다 |

| 프로세스 격리를 하지 않는다 | 사용자 코드가 엔진 안에서 전체 권한으로 돈다. 사용자가 웬만하면 하길 원했고 지연 측정(Hook 한 번 중앙값 0.02ms)이 부담이 작음을 보였다 |
| 모든 플러그인을 한 프로세스에 묶는다 | 한 플러그인의 고장·시간 초과가 다른 플러그인에 번지고 신뢰 등급이 다른 코드가 같은 프로세스에 든다. 메모리가 넘칠 때만 같은 등급끼리 묶는다 |
| 플러그인 파일을 손으로 고쳐 바로 실행한다 | 검토 절차가 둘로 갈린다. 담당 AI로만 고치고 모든 변경이 검토함을 지난다 |

## 7. 이 ADR이 바꾸지 않는 것

- 저장된 문자열(이벤트 kind, id 접두, 테이블 이름)은 그대로이고 더하기만 한다(2026-11-01 결정).
- 대화 모델 Thread / Turn / Step / Item과 Turn이라는 이름.
- ADR-0021의 플러그인 화면 두 모드(선언형, 격리 프레임). 이 ADR의 화면 칸은 그 위에서 무엇이 어디에 그려지는지와 모델에 무엇이 보이는지를 보이는 것까지만 다룬다.
- ADR-0018의 승인 프로토콜 하나. Hook의 `ask` 결정은 같은 승인 서비스로 간다.

## 8. 미결 사항

[미결] 사용자 확인이 필요한 것.

- [권고: 메인 세션, 확인 대기] 사용자 명령이 실행 중인 구동기보다 우선하는가(§3.5.4). 이 규칙과 Z4·R25의 종료 조건은 작업 기본값이다.
- [권고: 메인 세션, 확인 대기] 깊이 상한 3과 한도 차감 세부(§3.5.1), 격리 1단계 전에는 초안을 돌리지 않는 규칙(§3.7.5), 검토함 카드의 고정 안내(§3.10.2).
- [제안] 저장 문자열이 되는 이름(`drive.command_settled`, `drive.frames`, `plugin.draft.fromInstruction`, `testRun.start`, `authoring_submit`, `provenance:"user_instruction"`, `decides`)은 계약 동결(C0)에서 확정한다. 그 가운데 `drive.command_settled`는 [결정: 2026-11-20, 사용자, AGE-30 "지금 이름 그대로"]로 확정했다. `.fresnel/hooks`와 그 밖의 배치 이름, U3의 세부(§3.4.2)도 [제안]이다.
- [권고: 메인 세션, 확인 대기] "성능 측정" 화면을 지표와 턴 기록으로 흡수한다(§3.14.5). 승격 보고는 따로 결정한다.
- [확인 대기] 문서의 층 지도와 이름을 실제로 바꿀지(코드의 디렉터리 이름은 바꾸지 않는다).
- [미결] "루프"를 Craft 용어로 등록할지(권고: 등록하지 않고 "기본 턴 흐름"을 쓴다).
- [제안] 이름 충돌 규칙(`/plugin:<이름>`), 훅 선언의 `decides`, 테스트 대화의 시작 Drive 재쌓기, 초안 보관 개수 같은 구현 수준의 기본값은 각 설계 스펙의 미결 절에 있다.
- [가정] 조사에서 인용한 코드 위치는 정적 읽기 결과이고 구현 트랙의 첫 일로 다시 확인한다.
- `terms.json`에 새 용어(테스트 대화, 테스트 실행, 프로필 칩, 덧씌우기, 검토함, 검토본, 초안, 프레임, 블록, Inject / Hook / Drive 등)를 등록하고 낡은 항목(`extension`, `pluginGroup`)을 걷는 일은 사용자가 이름을 확인한 뒤 별도 트랙이 한다.
