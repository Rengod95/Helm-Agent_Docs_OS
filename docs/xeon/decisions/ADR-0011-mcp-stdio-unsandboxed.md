# ADR-0011 MCP stdio 서버: M2는 샌드박스 없이 사용자 권한으로 실행

## 1. 상태와 날짜

- 상태: accepted
- 날짜: 2026-10-25
- [결정] M2는 stdio MCP 서버를 사용자 권한으로 실행합니다. 프로젝트 정의 파일은 프로젝트 신뢰 뒤에만 읽습니다. 샌드박스는 bwrap 시험 환경이 생긴 뒤 정합니다(`review.m2-plan` §8 D6, 2026-10-23~24).
- [결정] 비밀 env를 쓰는 stdio MCP 서버는 M3로 미룹니다. M2는 포트 병합과 이 ADR만 합니다(`review.m2-plan` §9 D-c, 2026-10-25).
- 이 ADR은 D6을 plan 표에서 ADR로 옮깁니다(마일스톤 재점검 G1-04, G3-03).

## 2. 맥락

- stdio MCP 서버는 Xeon이 띄우는 자식 프로세스입니다. 서버 정의의 `command`, `args`, `env`가 실행할 프로그램을 정합니다(`L2.mcp.spec` §4.2·§4.3).
- 서버 정의는 두 곳에서 옵니다.
  - 사용자 설정 `l2.mcp.servers`: 사용자가 직접 씁니다.
  - 프로젝트 파일 `.mcp.json`, `.xeon/mcp.json`: 저장소를 받으면 같이 옵니다. 신뢰하지 않은 저장소의 파일은 임의 명령 실행과 같습니다(`architecture.security.spec` §4 T-03).
- L0 샌드박스(`xeon.sandbox`, srt 0.0.79)는 `bash` 도구를 감쌉니다. Linux는 bubblewrap과 socat, macOS는 Seatbelt를 씁니다(`L0.sandbox.spec` §3.5).
- 2026-10-25 기준으로 샌드박스 실제 시험(int)이 없습니다. 개발 기기에는 socat이 없고 CI에는 bwrap이 설치되지 않았습니다(마일스톤 재점검 G4-01). 샌드박스 네트워크 정책은 M3입니다(`review.m3-plan`).
- MCP 서버는 대부분 네트워크와 홈 디렉터리 설정 파일을 씁니다. 쓰기 경로와 네트워크 허용 목록을 서버마다 정하는 설계가 아직 없습니다.
- 비밀 env 서버를 띄우려면 기동 시점에 승인을 받아야 합니다. 승인 없는 `env` 주입은 금지입니다(`review.decisions-2` U-19). 기동 승인 단위는 설계 감사 A-04의 제안(서버 기동 승인 한 번)만 있고 설계가 없습니다.

## 3. 결정

1. [결정] M2의 stdio MCP 서버는 샌드박스 없이 Xeon 엔진과 같은 OS 사용자 권한으로 실행합니다.
2. [결정] 프로젝트 정의(`.mcp.json`, `.xeon/mcp.json`)는 프로젝트 신뢰가 `allow`일 때만 읽습니다. 신뢰가 없으면 서버 정의를 읽지 않고 진단만 남깁니다(`X.loading-trust.spec` §4.7.2). 사용자 설정의 정의는 신뢰 판정 없이 읽습니다.
3. [결정] M2는 `env`에 `secret://` 참조가 있는 stdio 서버를 띄우지 않습니다. 그 서버만 건너뛰고 진단을 남깁니다. 진단 이름은 `L2.mcp.spec`이 정합니다 [제안]. 다른 서버는 영향을 받지 않습니다.
4. [제안] 서버 정의 `env`·`headers`의 평문 값은 계속 거부합니다(`L2.mcp.spec` §10 미결 4). 3번과 합치면 M2의 stdio 서버는 비밀 없는 서버뿐입니다. HTTP 서버의 `headers` 비밀 참조는 `GuardedHttp` 주입 경로라서 이 결정의 범위 밖입니다.
5. [제안] 자식 프로세스 기동과 종료는 `McpProcessPort`(L0.process)가 맡습니다. 종료 순서(stdin 닫기, 신호, 유예, 강제 종료)는 `L0.process.spec`이 정합니다. cap-mcp는 `Bun.spawn`을 직접 부르지 않습니다(`eng.dependency-rules.guide` DR-07).
6. [제안] `xeon doctor`와 `host.status`의 MCP 항목은 stdio 서버마다 "샌드박스 없음"을 표시합니다.
7. [결정] 다시 정하는 시점은 M3입니다. 조건은 두 가지입니다. bwrap·socat이 설치된 CI에서 샌드박스 int 시험이 돌고, macOS Seatbelt 확인 결과가 `review.macos-checklist`에 기록되어야 합니다. 그때 서버별 쓰기 경로·네트워크 정책과 비밀 env 서버의 기동 승인을 함께 정합니다(`review.m3-plan`).

## 4. 결과

### 4.1 좋은 점

- `.mcp.json` 호환을 유지합니다. 사용자가 다른 도구에서 쓰던 stdio 서버를 그대로 등록할 수 있습니다.
- 시험하지 않은 샌드박스 설정이 서버를 조용히 깨뜨리는 일이 없습니다.
- 비밀 값이 승인 없이 자식 프로세스 환경으로 나가는 경로가 M2에 없습니다.

### 4.2 감수할 점

- stdio 서버는 사용자가 할 수 있는 모든 일을 할 수 있습니다. 홈 디렉터리 읽기·쓰기, 네트워크, 다른 프로세스 실행이 가능합니다.
- 프롬프트 주입으로 모델이 MCP 도구를 부를 수 있습니다. 통제는 도구 승인 규칙(`L1.tools.spec`)과 서버 허용·차단 목록(`L2.mcp.spec` §4.4)뿐입니다.
- 비밀 env가 필요한 서버(예: API 키를 env로 받는 서버)는 M2에서 쓸 수 없습니다. 사용자는 M3까지 그 서버를 다른 도구에서 씁니다.
- 프로젝트 신뢰 판정 하나가 MCP, 스킬, 프로젝트 설정의 실행 권한을 함께 엽니다. 신뢰 카드 문구가 이 범위를 보여야 합니다(G1-03, `L4.cli.spec`, `L4.desktop.spec`).

## 5. 대안

| 대안 | 내용 | 판정 | 이유 |
|---|---|---|---|
| srt로 감싸기 | `bash`처럼 L0 샌드박스로 서버를 감쌉니다 | M3에 다시 검토 | 실제 시험이 없고, 서버마다 네트워크·쓰기 정책이 필요합니다. 정책 없이 감싸면 대부분 서버가 실패합니다 |
| 프로젝트 정의 금지 | 사용자 설정의 서버만 띄웁니다 | 채택하지 않음 | `.mcp.json` 호환을 잃습니다. 프로젝트 신뢰로 같은 위험을 사용자 판단에 맡길 수 있습니다 |
| 비밀 env 서버를 M2에서 지원 | 기동 때 `env` 주입 | M3 | 기동 시점의 승인 지점이 없습니다. 승인 없는 `env` 주입은 U-19가 금지합니다 |
| 컨테이너로 실행 | Docker·Podman 안에서 서버 실행 | 채택하지 않음 | 사용자 기기에 컨테이너 런타임을 요구합니다. macOS 우선 지원(D-d)과 맞지 않습니다 |

## 6. 미결 사항

- [미결] 비밀 env 서버의 기동 승인 단위(서버별 한 번, 정의 변경 때 다시)와 승인 레코드 kind. M3 `review.m3-plan` 항목입니다.
- [미결] 서버별 샌드박스 정책의 설정 모양(쓰기 경로, 네트워크 허용 호스트).
- [가정] 3번의 진단은 서버 목록 화면과 `xeon doctor`에 보입니다. 표시 문구는 L4가 정합니다.
