# ADR-0012 실행 속도를 앱 크기보다 우선

## 1. 상태와 날짜

- 상태: accepted
- 날짜: 2026-10-25(결정 2026-10-24)
- [결정] 실행 체감 속도(빠른 시작과 종료, 끊김 없는 응답)를 앱 크기보다 우선합니다. 사이드카는 `--minify --bytecode`로 빌드하고 크기 상한은 triple별 500 MiB입니다(사용자 결정 2026-10-24, `L4.desktop.plan` §3 DESK.1 spike S2, 커밋 5229be8).
- 이 ADR은 plan에만 있던 결정을 ADR로 옮깁니다(마일스톤 재점검 G3-03). 합격선은 `eng.performance.guide`의 예산표가 맡습니다(G2-04).

## 2. 맥락

- 데스크톱 사이드카 콜드 스타트는 `--bytecode` 없이 약 285 ms, 있으면 약 131 ms였습니다. 크기는 약 12 MiB 늘었습니다(`L4.desktop.plan` §3 spike S2).
- `--bytecode`는 최상위 `await`를 거부합니다. 엔진 진입(`apps/host/src/main.ts`, `apps/cli/src/main.ts`)에서 최상위 `await`를 없앴습니다(HOST.5, CLI.5).
- 같은 원칙이 응답 경로에도 쓰였습니다. 예를 들어 `thread.read`에 `before`·`limit`를 더하는 근거가 이 결정입니다(마일스톤 재점검 G2-11).
- 측정은 사이드카 기동 한 건뿐이었습니다. 합격선과 측정 책임자가 없었습니다(G2-04).

## 3. 결정

1. [결정] 빌드 설정, 번들 방식, 기본값을 고를 때 시작·종료 시간과 응답 지연을 바이너리 크기보다 먼저 봅니다.
2. [결정] 사이드카 크기 상한은 triple별 500 MiB입니다. 상한은 회귀를 잡는 장치이고 크기를 줄이는 목표가 아닙니다(`xeon/scripts/build-sidecar.ts`).
3. [제안] 속도 예산은 `eng.performance.guide` §2 표에 둡니다. M2는 기준선을 재고, M3에서 예산을 넘으면 실패하는 게이트로 바꿉니다.
4. [제안] 측정은 `just bench`로 합니다. 콜드 스타트는 비용 없이 재고, 첫 토큰 지연은 실제 provider 호출이라 사람 확인(종료코드 3 뒤 `--yes`) 뒤에만 잽니다.

## 4. 결과

### 4.1 좋은 점

- 데스크톱과 CLI의 첫 반응이 빨라집니다.
- 크기와 속도가 부딪칠 때 판단 기준이 하나입니다.

### 4.2 감수할 점

- 배포 파일이 커집니다. 다운로드와 업데이트 크기가 늘어납니다.
- `--bytecode` 때문에 진입 코드에 최상위 `await`를 쓸 수 없습니다.
- 예산을 정하기 전까지 "속도 우선"은 방향일 뿐 합격선이 아닙니다.

## 5. 대안

| 대안 | 내용 | 판정 | 이유 |
|---|---|---|---|
| 크기 우선 | `--bytecode` 없이 빌드하고 상한을 낮게 둡니다 | 채택하지 않음 | 콜드 스타트가 두 배 이상 깁니다 |
| 둘 다 예산 | 크기와 속도에 각각 합격선을 둡니다 | 크기는 회귀 상한만 | 사용자가 크기를 기준으로 쓰지 않기로 했습니다 |

## 6. 미결 사항

- [미결] 예산 수치. `eng.performance.guide` §2 표의 값은 기준선 측정 뒤 사용자가 정합니다.
- [가정] 131 ms는 WSL2 한 기기의 측정입니다. macOS 값은 `review.macos-checklist`에서 잽니다.
