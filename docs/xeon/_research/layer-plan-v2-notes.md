  Runtime layer plan · v2 · 2026-10-21
  에이전트 런타임 층 구성 계획 (F~L3)
  v1에 대한 피드백과 추가 조사 여섯 건을 반영한 개정판입니다. 추가 조사는 패키지 채택, 프로세스·데몬, 비밀 관리, 클라이언트 설정, 작업·상호작용 능력, 확장 지점 단순화입니다. 바뀐 하위 층은 붉은 테두리로 표시했습니다. 확장 지점 목록과 Helm 내부 설계는 이 계획을 함께 확정한 뒤 시작합니다.
  층 도면
  아래에서 위로 쌓이고, 의존은 위에서 아래로 한 방향입니다. 오른쪽 X 띠는 L1~L3에 걸친 확장 지점입니다. 칸을 누르면 해당 구성표로 이동합니다.
  칸 안 목록은 1차 구성요소의 일부입니다. 숫자는 하위 층의 구성요소 수(1차/전체)입니다.

      OS 샌드박스가 왜 필요한가
      승인 프롬프트는 "이 명령을 실행해도 되는가"만 묻고, 명령이 실제로 무엇을 하는지는 보지 않습니다. 그래서 다음 같은 일을 막지 못합니다.
        npm install이나 make를 승인하면 패키지의 postinstall 스크립트까지 사용자 권한으로 실행됩니다.
        웹 페이지나 저장소 파일에 숨은 지시(프롬프트 인젝션)를 따라 모델이 ~/.ssh나 ~/.aws를 읽고 외부로 보내는 명령을 만들 수 있습니다.
      OS 샌드박스는 명령의 종류와 상관없이 커널 수준에서 범위를 제한합니다. 쓰기는 작업 폴더 안만, 비밀 폴더는 읽기 금지, 네트워크는 허용 도메인만입니다.
      범위가 보장되므로 샌드박스 안 명령은 매번 묻지 않고 자동으로 허용할 수 있습니다. 승인 프롬프트가 줄어드는 것이 실사용에서 더 큰 이득입니다.
      계획 반영: srt를 그대로 쓰고 1차에 둡니다. 기본은 켜고, 끄는 스위치는 L4 화면에 둡니다.
      입출력 가드레일은 필요한가
      가드레일은 OpenAI Agents SDK 같은 프레임워크에서 온 개념입니다. 고객 상담 봇처럼 믿을 수 없는 사용자에게 에이전트를 공개할 때, 탈옥 입력이나 주제 밖 질문, 개인정보가 섞인 출력을 막는 용도입니다.
      이 런타임의 사용자는 본인이라 같은 필요가 약합니다. 실제 위협은 도구 실행과 외부 콘텐츠에서 오고, 그것은 정책 엔진(L1-d), 샌드박스(L0-b), 비밀 마스킹(L0-c)이 처리합니다.
      계획 반영: 코어에서 빼고 보류로 둡니다. 필요하면 X의 차단 지점(first)에 붙는 선택 플러그인으로 만듭니다. 예산은 pi 방식을 따릅니다. 기본 단계·비용 상한은 두지 않고, 사용자 중단, 컨텍스트 한도, 추론 레벨별 토큰 예산만 둡니다. 상한은 L3 그룹의 구동 임대에만 걸립니다.
      웹 기본값: 유료 API는 플러그인, 기본은 로컬 도구
      동의합니다. 다만 브라우저 도구 조사에서 확인한 사실 때문에 도구마다 역할을 나눠야 합니다.
        Playwright(playwright-core): 가장 완성도가 높은 실행 계층입니다. auto-wait와 크로스 브라우저를 지원해 기본 web.browse로 둡니다.
        agent-browser: 문서 단위로 유지되는 ref, delta 스냅샷, 넓은 도메인 제한으로 빠른 조작과 토큰 절약에 강합니다. 내장 선택 provider로 둡니다.
        Stagehand v4: 핵심 이득인 액션 캐시가 Browserbase 서버에만 있어 로컬에서는 이점이 작습니다. 선택 플러그인으로 둡니다.
        moli: 대량 페이지 읽기 엔진으로 유망하지만 공개 2개월째이고 개발자가 사실상 한 명입니다. 선택 엔진으로 둡니다. Lightpanda는 AGPL이라 배포판에서 뺍니다.
      검색은 브라우저와 다른 문제입니다. 무료로 쓸 만한 검색 API가 드뭅니다. 그래서 기본은 두 가지입니다. 하나는 쓰는 모델이 지원하는 내장 웹 검색이고, 다른 하나는 자가 호스팅 SearXNG입니다. Exa, Parallel, Brave는 사용자가 키를 등록하는 플러그인으로 둡니다.
      Hermes 학습 루프를 별도 그룹으로
      좋은 방향입니다. 학습 루프는 두 부분으로 나뉩니다. 무엇을 저장하는지는 저장소 문제이고, 언제 무엇을 배울지는 정책 문제입니다. Hermes는 정책을 루프 안에 하드코딩했습니다. 그래서 카운터, 포크, 큐레이터를 끄거나 바꾸기 어렵고 안전장치도 기본으로 꺼져 있습니다.
        저장소인 스킬, 메모리, 세션 검색, 변경 원장은 L2-d에 남깁니다.
        정책은 L3 "학습 그룹"으로 옮깁니다. 카운터 트리거, 검토 포크, 큐레이터가 여기에 속합니다. Helm처럼 켜고 끌 수 있고, 다른 학습 전략으로 교체할 수 있습니다.
        학습 그룹은 구동 슬롯을 쓰지 않습니다. 검토 포크는 L1-g 백그라운드 위임 서비스로 돌립니다. 그래서 Helm이 구동 중이어도 함께 켤 수 있습니다.
        Helm은 학습 결과를 그룹 레코드와 L2-d 검색으로 읽습니다. 학습 그룹을 직접 참조하지 않습니다.
      확장 프로세스 격리는 기본값이 아니어도 된다
      동의합니다. 기본은 같은 프로세스 로드로 바꿉니다. 내장 플러그인과 사용자가 직접 설치한 플러그인이 여기에 해당합니다.
      격리는 사용자가 확장마다 켜는 선택 기능입니다. 출처를 모르는 확장, 외부 스크립트 훅이 대상입니다.
      격리하지 않은 확장도 확장 전용 테이블에 쓰므로, 코어 커밋과 같은 트랜잭션으로 원자성을 유지합니다.
      계획 반영: X-a 프로세스 격리를 2차 선택 기능으로 낮춥니다.
  확장 지점: 원시 연산 네 개
  v1의 "강제 수준 5단계 + 지점 계약 5필드"를 pi처럼 작은 원시 연산 네 개로 줄였습니다. 확장은 지점의 합성 방식을 고르지 않습니다. 지점을 선언할 때 런타임이 합성 방식(fold)을 정해 둡니다. 도구, 명령, provider 등록은 리소스 등록으로 따로 다루고, pi API를 그대로 따릅니다.
      네 연산과 v1 다섯 단계의 대응
        연산v1 단계뜻
          on(point, fn)1 관찰 · 2 차단 · 3 형성지점의 fold가 tap이면 관찰, first면 차단, chain이면 형성입니다.
          post(item, {when})4 주입입력 큐에 넣습니다. when 값은 steer, followUp, next입니다. requestId로 같은 입력이 두 번 들어가지 않게 합니다.
          drive(fn)5 구동배타 임대입니다. 경계마다 마지막으로 커밋된 상태로 다시 호출되고, 효과는 loop.turn, loop.spawn, post로만 냅니다.
          scope(id, {state})(그룹)위 등록을 한 단위로 묶어 턴 경계에서 켜고 끕니다. 상태 레코드와 정리 동작을 함께 둡니다.
      지점은 다섯 종류입니다: input, request, tool, boundary, session. pi에서 결과를 돌려받는 이벤트 약 19개가 모두 이 중 하나에 속합니다. 지점 이름은 pi 이벤트명을 그대로 씁니다.
      v1 계약 필드 다섯 개 중 네 개는 규칙으로 바뀝니다.
        강제 수준과 이벤트 모드는 연산과 fold에서 읽힙니다.
        실패 정책은 세 줄입니다. tap은 기록 후 계속, first는 거부로 처리, chain은 그 핸들러만 건너뜁니다.
        재생 규칙은 "on 핸들러는 다시 실행해도 되는 질의"라는 계약 하나입니다.
      예산은 drive 임대의 상한으로만 남습니다.
      Helm이 보이는 모양 (의사코드)
export const Helm = scope("helm", { state: doc<HelmState>() }, (g) => {
  g.on("request", (req, st) =>            // 형성 (chain)
    ({ ...req, system: req.system + lensFor(st.phase) }));
  g.on("tool.before", (call, st) =>        // 차단 (first)
    st.phase === "diverge" && isWrite(call) ? { deny: "탐구 단계는 읽기 전용" } : undefined);
  g.on("turn.end", (t, st) => g.note(signal(t)));   // 관찰 (tap)
  g.drive(async (loop, st) => {             // 구동 (배타 임대)
    while (st.phase !== "done" && loop.budget.turns > 0) {
      const views = await Promise.all(lenses(st).map(l =>
        loop.spawn({ agent: "explorer", task: l })));   // 병렬 탐색
      st = await g.commit(reduce(st, views));
      await loop.turn({ input: applyPrompt(st) });      // 현재 작업에 적용
    }
  });
});
runtime.scope("helm").disable();   // 다음 턴 경계에서 임대 반납
      pi 확장 대부분은 거의 수정 없이 올라올 것으로 예상합니다. pi.on은 이름이 같은 on으로, sendMessage는 post로 대응하기 때문입니다. 다만 실제로 올려 보지는 않았습니다.
      남는 쟁점이 둘 있습니다. boundary 지점의 "엔트리 추가 + 계속" 합성이 chain 하나로 표현되는지, 그리고 drive 함수가 재생 규율을 어긴 경우 이를 타입으로 막을 수 없다는 점입니다.
  층 사이 규칙
    1의존은 위에서 아래로만 흐릅니다. 같은 층의 다른 부품은 F에 있는 정의를 통해서만 참조합니다.
    2L3 그룹은 L2 능력의 정의(F3)만 참조하고 provider 구현은 모릅니다.
    3그룹끼리 직접 참조하지 않습니다. 그룹 사이 통신은 F4에 스키마가 있는 이벤트와 레코드로만 합니다.
    4drive 임대는 한 번에 그룹 하나만 가집니다. on, post, 백그라운드 위임은 여러 그룹이 함께 씁니다.
    5켜기와 끄기는 턴 경계에서 적용되고, 정리는 Cordis dispose로 실행됩니다.
    6모든 설정은 F5 설정 스키마 하나에서 L4 화면, 설정 파일, 명령을 함께 생성합니다.
    7이미 있는 패키지는 그대로 쓰고, 부족하면 포크합니다. 같은 기능을 처음부터 만들지 않습니다.

  이번에 확정한 것
    세션 저장은 C안입니다. SQLite 이벤트 소싱과 투영, 단일 DB 파일, 확장별 접두사 테이블을 씁니다.
    pi-ai는 npm 고정 버전으로 그대로 씁니다. 부족한 부분만 포크합니다. 다른 층도 같은 원칙을 따릅니다.
    Anthropic OAuth 위장 경로는 배포판에서 빼고 커스텀 provider 플러그인으로 제공합니다. pi-ai 안의 8곳을 래퍼(options.client, onPayload)로 떼어내는 방식을 먼저 시도합니다.
    비밀 기본값은 SOPS(age)입니다. 에이전트는 secret://이름 참조만 다룹니다.
    웹의 유료 API는 플러그인으로 둡니다. 기본은 로컬 도구입니다.
  남은 결정
    pi durable 활용 범위. 패키지 조사에서 pi durable이 L1-a, b, f, g, 구동, ExecutionEnv, 도구 본문을 이미 구현하고 있다는 것을 찾았습니다. 그러나 그대로 쓰기 어려운 점이 넷 있습니다. Chord 의존이라 Cordis와 DI가 둘이 되고, 이벤트 저널이 없고, synchronous=NORMAL이고, API가 실험 단계입니다. 권고는 혼합안입니다. env는 그대로, 도구·이미지·절단은 포크, 커널은 계획대로 둡니다. "durable 세션을 이벤트 저널 위에 얹을 수 있는가"를 1~2일 스파이크로 확인할지 정해 주십시오.
    예약, 원격, 알림을 제품 범위에 넣을지. 넣지 않으면 공유 서비스 모드(2차)까지만 만듭니다.
    데스크톱 셸 기술(Electron, Tauri 등). 엔진을 자식 프로세스로 띄우는 구조는 어느 쪽이든 같습니다.
    목표 지속(goal) 완료 판정 방식. 모델 자가 판정, 별도 판정 모델, 증거 확인 후 판정 중 하나입니다. 권고는 별도 판정 모델과 상한입니다.
    사용자 질문 도구와 계획 승인을 같은 입력 경로로 합칠지. 권고는 합치는 쪽입니다(L1-d 승인 프로토콜 하나).
    무료 검색 기본값. 모델 내장 검색과 SearXNG 중 무엇을 기본 선택으로 둘지 정해 주십시오.
