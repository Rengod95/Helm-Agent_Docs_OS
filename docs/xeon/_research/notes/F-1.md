# F-1 조사: pi 확장 이벤트 41종의 지점·fold·실패 규칙 대조

- 대상: pi 확장 이벤트 41종. F 계약의 확장 지점 선언(`on` fold tap/first/chain)이 pi의 실제 합성 규칙을 표현하는지 확인한다.
- 근거 계획: `_research/foundation-plan.md` §3, `_research/decisions-log.md` 20행(계획 v2의 `on` fold 3종), `_research/ext-points.md` §1.2
- 성격: 조사 결과. 정본이 아니며 인용용이다. 코드는 실행하지 않았다. 소스 읽기만 했다.
- 표지: [결정] 사용자 결정 기록 인용, [제안] 작성자 설계 선택, [가정] 확인하지 않은 전제, [미결] 사용자 확인 필요, [미확인] 확인하지 못한 것.

## 0. 결론

1. 이벤트는 41종이다. `ExtensionEvent` 합집합(`EXT/types.ts:1377-1409`)에서 `SessionEvent`(10종, `EXT/types.ts:848-858`)를 펼치면 41이다. `ExtensionAPI.on` 오버로드(`EXT/types.ts:1569-1636`)도 41개이며 이름 집합이 같다.
2. 41종의 fold 분포는 tap 22, 제자리 변경 tap 1, first 7, chain 9, collect 2다(§2.6).
3. emitBoundary는 chain 하나로 표현된다. 다만 단계별 검증과 최종 검증 정책은 chain 본체 밖의 규칙이다(§3.1).
4. resources_discover와 cache_warming_decision은 tap 하나로도 chain 하나로도 그대로 표현되지 않는다. 입력은 고정되고 출력만 모인다. 가장 작은 보완은 수집(collect) 리듀서 1종이다(§3.2, §3.3).
5. [결정] 계획 v2는 `on`의 fold를 tap/first/chain 3종으로 정했다(`_research/decisions-log.md` 20행). 위 보완을 넣으려면 이 결정을 바꾸거나 변형으로 정의해야 한다. [미결] 어느 쪽으로 할지 사용자 확인이 필요하다(§3.4, §7).
6. `_research/ext-points.md` §1.2에 정정할 점 3건이 있다(§4).

## 1. 확인 범위와 방법

- 경로 약어: `EXT` = `~/projects/_ref/pi-src/packages/coding-agent/src/core/extensions`, `CORE` = `~/projects/_ref/pi-src/packages/coding-agent/src/core`, `MODES` = `~/projects/_ref/pi-src/packages/coding-agent/src/modes`, `AG` = `~/projects/_ref/pi-src/packages/agent/src`, `DOC` = `~/projects/_ref/pi-src/packages/coding-agent/docs`.
- 표의 파일명만 적은 곳은 `EXT/`(`types.ts`, `runner.ts`)나 `CORE/`(그 밖의 core 파일)에 있다.
- 1차 자료: 소스 코드(위 경로), 공식 문서 `DOC/extensions.md` 96-127행과 255-264행.
- 방법: 이벤트 정의와 `on` 오버로드로 페이로드·반환 타입을 확인했다. runner의 emit 계열 메서드(클래스 13개와 자유 함수 2개) 본문을 읽어 합성·실패 규칙을 확인했다. 호출자(`CORE/agent-session.ts` 등)에서 발사 지점을 확인했다. 실패 규칙이 호출자에 미치는 영향은 `AG/agent-loop.ts`로 확인했다.
- fold 값은 runner 코드 독해에 따른 분류다. 지점 5종 배정은 [제안]이다.

## 2. 41종 매핑

### 2.0 공통 규칙 (generic emit)

- 핸들러는 확장 로드 순서와 등록 순서대로 순차 await한다. 디스패치 시작 시 목록을 스냅샷한다(`EXT/runner.ts:269-271`, `1089-1118`).
- 핸들러 예외는 `emitError`로 보고한 뒤 다음 핸들러로 넘어간다(`EXT/runner.ts:1104-1111`). 실패 규칙은 fail-open이다.
- `session_before_*` 네 종만 `cancel`이 참이면 즉시 반환한다(`EXT/runner.ts:1096-1103`). 그 밖의 결과는 마지막으로 정의된 값이 남는다(`EXT/runner.ts:1098-1099`).
- 공식 문서도 같은 원칙을 밝힌다. "Use each event's declared result type rather than assuming every return value has an effect."(`DOC/extensions.md:99`)

## 3. 판정

### 3.1 emitBoundary: chain 하나로 표현된다

근거 (`EXT/runner.ts:1029-1077`):
- 상태 전달: 핸들러는 직전까지 쌓인 entries, continue, context를 event로 받는다(`runner.ts:1041-1046`).
- 부분 패치: 반환된 entries와 continue는 undefined가 아닐 때만 반영된다(`runner.ts:1049-1050`).
- 단계별 재구성: 매 핸들러 뒤에 buildContext를 다시 호출하고 성공과 실패를 기록한다(`runner.ts:1060-1067`).
- 최종 게이트: valid는 마지막 재구성의 결과다(`runner.ts:1062`, `1064`, `1075`). 최종 상태가 무효면 `{entries: [], continue: false}`를 돌려준다(`runner.ts:1077`).

chain 본체 밖에 남는 차이 3건:
- (a) 병합 연산이 없다. 런너는 `entries = handlerResult.entries`로 교체한다(`runner.ts:1049`). 누적하려면 핸들러가 event.entries를 읽고 전체 목록을 반환해야 한다. 명세에는 "교체(전체 목록 반환)"로 쓴다 [제안].
- (b) 최종 검증 정책은 fold 종료 훅으로 분리해야 한다. 중간 단계의 무효 상태는 허용되고 emitError만 남는다(`runner.ts:1064-1066`). 최종 상태만 판정한다 [제안].
- (c) continue의 승인은 fold 밖에 있다. 호스트가 canContinue를 다시 검사하고 거부하면 continue를 버린다(`CORE/agent-session.ts:879-882`, `:1907-1910`). entries는 두 경우 모두 커밋된다(`CORE/agent-session.ts:878`, `:1902`).

보충: 결과 entries는 세션 엔트리로 커밋되므로 영속 상태가 된다. 이 점은 세션 저장 C안(SQLite 이벤트 소싱)과 맞물린다 [제안].

### 3.2 resources_discover: tap 하나로는 표현되지 않는다. 수집 리듀서가 필요하다

- 입력 고정: 핸들러가 받는 event는 `{type, cwd, reason}`뿐이며 누적 상태를 담지 않는다(`runner.ts:1490`).
- 출력 누적: 반환된 경로를 extensionPath와 함께 세 배열에 이어붙인다(`runner.ts:1495-1501`).
- tap은 결과를 버리는 연산이라 맞지 않는다. chain은 핸들러가 누적 상태를 본다는 점에서 pi와 다르다.
- 따라서 "입력은 원본, 출력은 리듀서로 모음"인 변형이 필요하다 [제안].

### 3.3 cache_warming_decision: 마지막 정의값 리듀서다. chain으로 쓰면 결과가 달라진다

- 핸들러는 원본 event를 받는다. 결과로 event.action을 덮어쓰지 않는다(`runner.ts:1121-1135`).
- 결과는 마지막으로 정의된 action이다(`runner.ts:1129`).
- tap으로 쓰면 결과 수집이 빠진다.
- chain으로 쓰면 반례가 생긴다. 핸들러 A가 "stop"을 반환하고 핸들러 B가 입력 action을 그대로 반환한다고 하자. pi에서 B는 원본 "warm"을 받으므로 결과는 "warm"이다. chain에서 B는 A의 "stop"을 받으므로 결과는 "stop"이다.
- 따라서 3.2와 같은 리듀서("마지막 정의값")로 표현된다 [제안].
- 호출 경로: `CORE/sdk.ts:338`에서 `?? event.action`으로 감싼다. `CORE/cache-warmer.ts:308-316`은 실패 시 자체 결정을 쓴다.

### 3.4 `on`의 fold 3종에 대한 판정

- [결정] 계획 v2는 fold를 tap/first/chain 3종으로 정했다(`_research/decisions-log.md` 20행).
- 41종 중 38종은 세 fold 중 하나에 그대로 맞는다. tap 22, 제자리 변경 tap 1, first 7, chain 8이다.
- before_agent_start는 systemPrompt가 chain이고 message가 수집이라 혼합이다.
- resources_discover와 cache_warming_decision 두 건은 맞지 않는다.
- 3종으로 빠지는 항목은 다음과 같다.
  - (i) 수집 리듀서: resources_discover, cache_warming_decision, before_agent_start의 message.
  - (ii) 제자리 변경 허용: before_provider_headers. 반환값 없이 인자를 수정하는 tap이다.
  - (iii) 중단 조건: first와 chain에 공통으로 필요하다. block, cancel, undecided가 아님, handled, 첫 non-undefined가 여기 속한다.
  - (iv) 실패 정책: fail-open이 기본이고 fail-closed가 세 곳이다.
  - (v) 대기 방식: await 17건과 void 5건이 섞여 있다.
  - (vi) boundary 종료 검증 훅.
- 최소 보완안 [제안]: fold를 tap, first, chain, collect 4종으로 두고, 각 지점 선언에 중단 조건, 실패 정책, 대기 여부를 명시한다. 3종 결정을 바꾸는 일이므로 [미결]로 둔다(§7).

## 4. ext-points.md §1.2 정정 사항

원문 대조 결과는 다음과 같다.

1. "emit* 14개(runner.ts 기준)"는 정확하지 않다. 클래스 메서드는 13개다(generic emit 포함: emit, emitBoundary, emitCacheWarmingDecision, emitMessageEnd, emitToolResult, emitToolCall, emitUserBash, emitContext, emitBeforeProviderRequest, emitBeforeProviderHeaders, emitBeforeAgentStart, emitResourcesDiscover, emitInput). 자유 함수는 2개다(emitSessionShutdownEvent `runner.ts:258`, emitProjectTrustEvent `runner.ts:295`). emitError(`runner.ts:742`)와 emitUIPromptEvent(`runner.ts:611`)는 보고와 발사 보조다.
2. "결과를 돌려받는 지점 약 19개(before_provider_headers 포함)"는 정정이 필요하다. before_provider_headers는 반환값을 쓰지 않고 인자를 수정한다(`runner.ts:1392-1417`, `EXT/types.ts:1607`). 반환 기반은 18개, 제자리 변경은 1개, 관찰 전용은 22개다.
3. "emitToolCall fail-closed"는 맞다. 다만 예외는 emitError로 보고되지 않고 도구 오류 결과로 모델에 전달된다(`AG/agent-loop.ts:770-775`). 공식 문서도 같은 내용이다(`DOC/extensions.md:260`).
4. "시간 한도는 러너에 없다(timeout 0건)"는 확인했다. `EXT/runner.ts`에서 timeout 문자열이 0건이다.
5. "dispatch 시작 시 스냅샷(runner.ts:269-271)"은 확인했다(`EXT/runner.ts:269`).
6. "41종 분류(시작·자원 3, 세션 10, 요청 7, 에이전트·턴·메시지 12, 도구 실행 3, 모델 2, 가로채기 4)"는 확인했다. 다만 이 분류는 지점 5종 배정과 다르다.

## 7. 미결 사항

- [미결] fold 3종에 collect를 추가할지(§3.4). 아니면 chain과 tap의 변형으로 정의할지 결정해야 한다.
