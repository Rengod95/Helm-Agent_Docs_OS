# L0-1 조사: @anthropic-ai/sandbox-runtime 0.0.81의 설정 스키마, 프록시·MITM 옵션, 위반 기록 API, 플랫폼 요구, Bun 호환성

- 대상: `@anthropic-ai/sandbox-runtime` 0.0.81 (npm 게시 2026-10-20, GitHub 태그 v0.0.81). L0 `platform-sandbox` 도메인의 채택 적합성을 확인한다.
- 근거 계획: `_research/foundation-plan.md` §2(샌드박스 채택), §3(`platform-sandbox` 배치), `_research/packages.md` 159행(L0-b), `_research/decisions-log.md` 11행(첫 지원 OS)과 13행(OS 차이 처리 규칙), `_research/refs/claude-code.md` 326행(검증 대상).
- 성격: 조사 결과. 정본이 아니며 인용용이다. 패키지 tarball과 GitHub 소스를 읽기만 했다. 내려받은 코드는 실행하지 않았다.
- 표지: [결정] 사용자 결정 인용, [제안] 작성자 설계 선택, [가정] 확인하지 않은 전제, [미결] 사용자 확인 필요, [미확인] 확인하지 못한 것.

## 0. 결론

1. [제안] 채택 판정은 유지한다. 0.0.81은 파일 읽기와 쓰기의 허용과 거부, 도메인 허용과 거부, 명령 단위 추가 허용, 외부 프록시 연결, 위반 기록을 설정과 API로 제공한다. 이 조사로 확인한 것은 설정 스키마, 소스 구조, 플랫폼 요구다. 실제 격리 효과는 실행하지 않았으므로 확인하지 않았다 [미확인].
2. MITM 옵션은 있다. 두 가지다. `network.tlsTerminate`는 내장 프록시가 HTTPS를 종단하는 실험 기능이다. `network.mitmProxy`는 도메인별 연결을 외부 MITM 프록시의 Unix 소켓으로 넘긴다. 두 옵션은 함께 쓸 수 없다(S:src/sandbox/sandbox-manager.ts:1152). 이 밖의 확장 지점은 요청 단위 콜백 `filterRequest`, 상위 프록시 `parentProxy`, 외부 프록시 포트, 외부 판정 프로세스 모드 `srt proxy`다(§4).
3. 위반 기록은 `SandboxViolationStore`(조회, 구독, 명령별 조회)와 `annotateStderrWithSandboxFailures`로 제공된다. 원천은 프록시 거부, macOS 로그 스트림, Linux의 apply-seccomp 기반 모니터다. Linux 모니터는 옵션(`enableLogMonitor`)을 켰을 때만 동작하며, 패키지 스스로 그 경로를 공격자가 제어한다고 적었다(§5).
4. 플랫폼 요구는 다음과 같다. macOS는 ripgrep 외에 설치할 것이 없다. Linux는 bubblewrap, socat, ripgrep이 필요하고 seccomp 필터는 x64와 arm64에서 번들로 온다. Windows는 alpha다. Claude Code 문서도 네이티브 Windows를 샌드박스 대상에서 뺐고 WSL2만 지원한다(§6).
5. Bun 호환성은 확인할 가치가 있다. 패키지에는 Bun 분기 코드가 여럿 있다. `tlsTerminate`는 Node 또는 Bun 1.4 이상에서만 시작된다. 이는 프로젝트 기준선 Bun 1.4와 맞는다. `bun build --compile` 실행 파일에서 헬퍼 바이너리를 찾는 방식은 번들 기준 상대 경로에 기대므로, 헬퍼를 실행 파일 옆에 두고 설정 경로로 명시해야 할 가능성이 높다 [추측]. 컴파일 산출물의 실제 동작은 확인하지 않았다 [미확인](§7).
6. [제안] 가장 큰 설계 제약은 프로세스 전역 싱글턴이다. `SandboxManager`의 설정, 프록시 서버, 위반 저장소가 모듈 수준 변수다(D:sandbox/sandbox-manager.js:35, 40-42, 228). 한 프로세스는 네트워크 정책 하나만 가진다. 세션마다 다른 도메인 정책이 필요하면 프로세스를 나누거나 명령별 허용 목록 방식을 택해야 한다(§8).
7. [제안] 파일 읽기의 기본값은 전체 허용이다. `~/.ssh`, SOPS age 키 파일 같은 시크릿 경로는 `denyRead`로 명시해야 한다. 셸 설정 파일, `.git/hooks`, `.vscode` 등은 설정 없이도 쓰기가 막힌다(README:1142-1190).
8. [제안] 샌드박스는 셸 명령과 그 자식만 감싼다. 파일 도구(read, ls)와 MCP, 훅은 밖에 있다(CC, "What the sandbox restricts"). M1의 `read`, `ls`는 L1 도구 정책으로 막아야 하고, 셸 실행과 같은 정책 원천을 써야 한다.
9. [정정] `refs/claude-code.md` 326행의 "호스트 언어가 Node가 아니면 CLI 래핑 필요 [추측]"은 근거가 없다. Bun 1.4 호스트에서 라이브러리를 직접 호출할 수 있다. 같은 파일 115행의 "탈출구(`allowUnsandboxedCommands`)"는 라이브러리 기능이 아니고 Claude Code 설정 기능이다(§9).
10. [제안] 버전 위험이 크다. 0.0.x이고 README는 "Beta Research Preview"와 설정 형식 변경 가능성을 명시했다. 2026-10-07부터 10-20까지 3회 릴리스가 나왔고, 0.0.79 이후 deny 콜백 동작이 바뀌었다(README:261-406). 정확 버전 고정, 어댑터 뒤에 가두기, 설정 스키마 검사 테스트가 필요하다.

## 3. 설정 스키마 (0.0.81)

### 3.1 최상위 키

`SandboxRuntimeConfigSchema`(`S:src/sandbox/sandbox-config.ts:1175-1266`)의 키는 다음과 같다.

- `network`(필수), `filesystem`(필수), `credentials`, `ignoreViolations`
- `enableWeakerNestedSandbox`, `allowNestedUserNamespaces`, `enableWeakerNetworkIsolation`, `allowAppleEvents`, `allowPty`
- `ripgrep`, `mandatoryDenySearchDepth`(1~10, 기본 3), `seccomp`, `bwrapPath`, `socatPath`, `javaAgentJarPath`, `windows`, `git`

`bwrapPath`, `socatPath`는 절대 경로만 받는다(`S:src/sandbox/sandbox-config.ts:103-110`).

### 3.2 filesystem (`S:src/sandbox/sandbox-config.ts:957-997`)

| 키 | 뜻 |
|---|---|
| `disabled` | true이면 파일 정책을 전부 적용하지 않는다 |
| `denyRead` | 읽기 거부 목록. 기본은 빈 목록이며 읽기는 전체 허용이다 |
| `allowRead` | `denyRead` 안에서 다시 허용한다. `allowRead`가 `denyRead`를 이긴다 |
| `allowWrite` | 쓰기 허용 목록. 기본은 쓰기 전부 거부다 |
| `denyWrite` | `allowWrite` 안에서 거부한다. `denyWrite`가 `allowWrite`를 이긴다 |
| `allowGitConfig` | true이면 `.git/config` 쓰기를 연다. `.git/hooks`는 계속 막힌다 |

항목은 문자열이거나 `{ "path": "...", "literal": true }`다. `literal`이 true이면 글로브로 읽지 않는다(README:525-588, "For embedders" 항목).

경로 문법은 OS마다 다르다.

- macOS는 gitignore식 글로브를 쓴다(`*`, `**`, `?`, `[...]`).
- Linux는 bubblewrap이 실제 경로에 바인드하므로 `allowWrite`, `denyWrite`는 리터럴 경로만 받는다. 끝의 `/**`는 버려지고 다른 글로브는 건너뛴다(README:525-588, "Path Syntax (Linux)").
- Linux에서 건너뛴 패턴은 아무것도 가리지 않는다. README는 "A skipped pattern hides nothing"이라고 적었다. `getLinuxGlobPatternWarnings()`가 건너뛴 항목 목록을 돌려준다(`D:sandbox/sandbox-manager.d.ts`). [제안] 시크릿 거부 목록은 Linux에서 글로브 대신 리터럴 경로로 적는다.

쓰기 기본 허용 경로는 다음과 같다. 자식 프로세스의 stdio, `/tmp/claude`, `~/.npm/_logs`, `~/.claude/debug`다(README:525-588).

자동 보호 경로는 `allowWrite`에 들어 있어도 쓰기가 막힌다(README:1142-1190).

- 파일: `.bashrc`, `.bash_profile`, `.zshrc`, `.zprofile`, `.profile`, `.gitconfig`, `.gitmodules`, `.ripgreprc`, `.mcp.json`
- 디렉터리: `.vscode/`, `.idea/`, `.claude/commands/`, `.claude/agents/`, `.git/hooks/`, `.git/config`

### 3.3 network (`S:src/sandbox/sandbox-config.ts:677-957`)

| 키 | 뜻 |
|---|---|
| `allowedDomains` | 허용 호스트. 빈 목록이면 네트워크가 전부 막힌다. `host:port` 형식 가능 |
| `deniedDomains` | 거부 호스트. 허용 목록보다 먼저 검사한다. 단독 `*`은 전부 거부다 |
| `deniedDomainReasons` | 거부 항목별 모델용 사유 문구 |
| `strictAllowlist` | true이면 목록 밖 호스트를 질의 콜백 없이 거부하고 명령별 목록을 무시한다 |
| `deniedResolvedAddresses` | 허용된 호스트 이름이 이 주소로 해석되면 거부한다. 사설 대역은 기본으로 막지 않는다 |
| `allowUnixSockets`, `allowAllUnixSockets` | Unix 소켓 허용. macOS는 경로 목록, Linux는 seccomp 차단을 끄는 옵션이다 |
| `allowLocalBinding` | 로컬 포트 직접 바인드 허용. 기본 false. Linux에서는 무시된다 |
| `allowMachLookup` | macOS 전용. 추가 XPC·Mach 서비스 이름 |
| `httpProxyPort`, `socksProxyPort` | 내장 프록시 대신 외부 프록시 포트를 쓴다. 외부 프록시가 도메인 필터를 맡는다 |
| `mitmProxy` | `{ socketPath, domains }`. 매칭 도메인을 외부 MITM 프록시로 보낸다 |
| `tlsTerminate` | `{ caCertPath, caKeyPath, extraCaCertPaths, excludeDomains, maxTunnels, handshakeTimeoutMs }`. 실험 기능 |
| `parentProxy` | `{ http, https, noProxy }`. 상위 기업 프록시로 체이닝한다 |
| `filterRequest` | 요청 단위 판정 콜백. JSON으로 설정할 수 없고 라이브러리 호출자만 쓴다 |
| `allowPlaintextHeaderSet`, `stripResponseHeaders`, `refuseOpaqueTunnels`, `requireHostMatch`, `ambiguousRequestTarget` | `filterRequest`와 함께 쓰는 보조 정책 |

### 3.4 credentials, 플랫폼 보조 키

- `credentials`(`S:src/sandbox/sandbox-config.ts:636`): `envVars`, `files`, `awsPairs`, `sigv4`, `allowPlaintextInject`. 각 항목의 `mode`는 `deny` 또는 `mask`다(`S:src/sandbox/sandbox-config.ts:161`). `mask`는 샌드박스 안에 sentinel을 두고, 프록시가 허용 호스트로 나가는 요청에서 실제 값으로 바꾼다. 마스킹은 `tlsTerminate`가 필요하다(`allowPlaintextInject`로 예외를 둘 수 있다). 파일 마스킹은 Linux에서만 된다. macOS는 파일을 거부한다(README:525-588, CC §Mask credentials).
- `ripgrep`: `command`, `args`, `argv0`. 기본은 PATH의 `rg`다.
- `seccomp`: `applyPath`, `argv0`. `argv0`는 apply-seccomp를 호출자 바이너리에 넣는 multicall 방식이다.
- `windows`, `git`: `srt-win` 설정과 `git.safeDirectories`.

### 3.5 런타임 변경

- `--control-fd`(README:187-256)로 config 줄을 실행 중에 보낼 수 있다. 네트워크 목록과 `network.mitmProxy`, `tlsTerminate.excludeDomains`는 다음 연결부터 적용된다.
- 파일 정책은 바뀌지 않는다. Seatbelt 프로필, bwrap 인자, Windows ACE에 이미 들어갔기 때문이다(README:187-256).
- 라이브러리 호출은 `updateConfig(newConfig: SandboxRuntimeConfig)`를 쓴다(`D:sandbox/sandbox-manager.d.ts`). 인자 타입은 전체 설정이다.

### 3.6 설정 신뢰 범위 [제안]

Claude Code는 `mask`, `tlsTerminate`, `allowPlaintextInject`, `awsPairs`, `sigv4`를 사용자 설정, 관리 설정, `--settings`에서만 받고 저장소 설정에서는 무시한다(CC, "Mask credentials"). README도 `allowAppleEvents`는 "신뢰할 수 있는 사용자 수준 설정"에서만 받으라고 적었다(README:588-604 근처 Other Configuration). [제안] Xeon의 L4 설정 계층도 같은 규칙을 둔다. 프로젝트 파일이 샌드박스 완화 옵션을 켜지 못하게 한다.

## 4. 프록시 확장 지점과 MITM 옵션

질문의 답은 다음과 같다. MITM 옵션은 있다. 확장 지점은 JSON 설정 여섯 가지, 라이브러리 콜백 세 가지, 별도 실행 모드 한 가지다.

| 지점 | 형태 | 하는 일 | 제약 |
|---|---|---|---|
| `network.tlsTerminate` | JSON, 실험 | 내장 프록시가 CONNECT를 TLS 종단하고 요청을 복호화해 `filterRequest`에 넘긴다. CA를 지정하지 않으면 임시 CA를 만든다. 샌드박스 프로세스는 MITM CA와 호스트 루트를 함께 담은 신뢰 번들을 받는다 | Node 또는 Bun 1.4 이상만 가능하다(`D:sandbox/emitted-connection.js:28-42`, `S:src/sandbox/sandbox-config.ts:943`). mTLS와 인증서 고정 클라이언트는 `excludeDomains`로 빼야 한다. 동시 종단 터널 상한은 기본 256이다(README:454-525, `maxTunnels`) |
| `network.mitmProxy` | JSON | `domains`에 매칭되는 연결을 `socketPath`의 외부 MITM 프록시로 넘긴다. SRT는 허용과 거부를 계속 판단한다 | `tlsTerminate`와 배타다(`S:src/sandbox/sandbox-manager.ts:1152`). 호스트 매칭 함수는 `D:sandbox/sandbox-manager.js:637-646`에 있다. 실제 연결 동작은 확인하지 않았다 [미확인] |
| `network.filterRequest` | 콜백 | 요청별로 allow 또는 deny를 정하고, 상태 코드, 헤더 삭제와 설정, 응답 관찰을 한다 | 옵션은 프록시 시작 시 읽힌다. `updateConfig`로 바뀌지 않는다. 평문 HTTP에서 헤더 설정은 기본 거부다(README:261-406) |
| `network.parentProxy` | JSON | SRT 자신이 기업 프록시 뒤에 있을 때 `http`, `https`로 체이닝한다 | 상위 프록시를 거치는 연결은 호스트 이름 해석 검사를 건너뛴다. 상위 프록시가 그 역할을 맡는다(README:454-525) |
| `network.httpProxyPort`, `socksProxyPort` | JSON | 내장 프록시를 띄우지 않고 외부 프록시 포트를 쓴다 | 외부 프록시가 도메인 필터를 맡는다(`S:src/sandbox/sandbox-config.ts` 설명 문자열). 이 경우 명령별 허용 목록은 적용되지 않는다(README:261-406) |
| `SandboxAskCallback` | 콜백 | 목록에 없는 호스트를 질의한다. `true`만 허용한다. `{ allow: false, reason }`으로 사유를 돌려줄 수 있다 | 0.0.79 이후 객체 응답은 `SandboxManager.askCallbackDenyReason`이 true인 릴리스에서만 안전하다(README:261-406) |
| `registerCommandNetworkLists(commandId, lists)` | 라이브러리 API | 명령 한 번의 실행 동안 추가 허용 목록을 붙인다 | id는 128비트 이상 무작위여야 한다. 전역 거부 목록은 우회하지 못한다. 같은 프로세스 안의 다른 명령이 id를 알면 그 허용을 쓸 수 있다(README:261-406). `httpProxyPort` 사용 중에는 적용되지 않는다 |
| `credentials` `mode: mask` | JSON | 환경변수나 파일 값을 sentinel로 바꾸고 송출 시 실제 값으로 치환한다 | `tlsTerminate`가 필요하다(예외는 `allowPlaintextInject`). 파일 마스킹은 Linux 전용이다 |
| `srt proxy` (decider) | 별도 실행 모드 | 샌드박스 자식 없이 HTTP 프록시만 띄운다. 각 요청은 fd로 연결된 외부 decider 프로세스가 허용한 경우에만 나간다 | 워크로드가 다른 곳에서 돌고 호스트가 프록시를 쓰는 구조용이다. 프로토콜 v1의 세부는 `SP`에 있다. 프레이밍과 종료 조건은 읽지 않았다 [미확인] |

중요한 차이는 다음과 같다.

- README의 "Advanced: Bring Your Own Proxy" 절은 "Custom proxy configuration is not yet supported in the new configuration format"라고 적었다(README:1248-1266). 0.0.81 스키마에는 `mitmProxy`, `httpProxyPort`, `socksProxyPort`가 이미 있다. 이 절은 뒤처졌다.
- CC도 같은 상태를 설명한다. 내장 프록시는 기본으로 TLS를 종단하거나 검사하지 않는다. `tlsTerminate`는 실험 설정이다(CC, 네트워크 격리 절).
- 연결 판정 순서는 README가 명시한다. ① `deniedDomains` 일치면 거부, ② `allowedDomains` 일치면 허용, ③ `strictAllowlist`면 거부, ④ 연결이 제시한 id의 명령별 목록 일치면 허용, ⑤ 콜백이 있으면 콜백, 없으면 거부다(README:261-406).

원천은 세 가지다.

- 프록시 거부: HTTP 403(`X-Proxy-Error: blocked-by-sandbox-runtime`)과 SOCKS 거부가 저장소에 들어간다. 사유 문구는 제어 문자와 보이지 않는 문자를 지우고 500자로 자른다(`D:sandbox/sandbox-violation-store.d.ts`의 `sanitizeDenialReason`, README:261-406).
- macOS: `initialize(config, cb, enableLogMonitor = true)`를 주면 시스템 샌드박스 로그 스트림을 구독한다(`D:sandbox/sandbox-manager.js:845-847`, README:1220-1230).
- Linux: 같은 옵션에서 `startLinuxSandboxViolationMonitor`가 동작한다(`D:sandbox/sandbox-manager.js:849-851`). apply-seccomp가 쓰기 시도 syscall을 보고하고, 모니터가 설정과 대조한다. 커널이 보고하는 것은 시도이지 거부가 아니다. 경로는 샌드박스 프로세스 메모리에서 읽으므로 공격자가 제어하며 경쟁 상태가 있다. 패키지는 이 값을 정책 판단에 쓰지 말고 진단에만 쓰라고 명시했다(`D:sandbox/linux-violation-monitor.js:1-30`).

[미확인] README:1229-1230은 Linux에는 내장 위반 보고가 없고 `strace`로 찾으라고 적었다. 이는 0.0.81 코드와 맞지 않는다. 위의 Linux 모니터는 옵션을 켜야 동작한다.

Linux의 추가 조건은 다음과 같다(README:682-730, CC "Set up Linux and WSL2").

- Ubuntu 24.04 이후는 `kernel.apparmor_restrict_unprivileged_userns`가 bwrap의 사용자 네임스페이스를 막는다. sysctl을 끄거나 bwrap에 AppArmor 프로필을 준다.
- 루트로 실행하면 호출 프로세스에 `CAP_SETFCAP`이 있어야 한다(README:682-730).
- 비 x64, arm64에서 seccomp 필터를 빌드하려면 gcc 또는 clang과 libseccomp-dev가 필요하다.

[제안] 중첩 네임스페이스 기본 거부는 L2 브라우저 도구에 직접 영향을 준다. Chromium과 Electron의 네임스페이스 샌드박스, rootless podman, `unshare -r`는 샌드박스 안에서 `EPERM`으로 실패한다(README:682-740). Playwright를 샌드박스 셸에서 띄울 계획이면 `allowNestedUserNamespaces: true`가 필요하다. 이 옵션은 쓰기 거부를 무력화할 수 있다고 README가 경고한다(README:682-740, "The command stays in the namespaces made for it" 절). [미결] (§10)

Windows 상태는 다음과 같다.

- README는 Windows를 "alpha"로 표기했다(README:740-790). 설치는 1회 관리자 승인이 필요하고, 사용자 프로필을 샌드박스가 읽을 수 있게 열어 준다(README:740-790).
- 알려진 제약에는 다음이 있다(README:1000-1011). SMB 공유 접근과 WSL 기동은 WFP 펜스 밖이다. 익명 토큰이나 파생 토큰을 쓰는 프로세스는 펜스를 우회한다. `getaddrinfo`의 시스템 리졸버 조회는 막히지 않는다.
- Claude Code는 네이티브 Windows에서 명령을 샌드박스 없이 실행한다(CC, 첫 문단).
- 결정: "첫 지원 OS는 macOS, Linux(WSL 포함). Windows 네이티브는 나중"(`_research/decisions-log.md` 11행). 따라서 M0~M1 범위에서 Windows 어댑터는 만들지 않는다 [제안].

## 7. Bun 런타임과 `bun build --compile`

### 7.1 패키지가 Bun을 다루는 방식

패키지는 Node 기준으로 설계됐고 Bun 분기가 여럿 있다. 근거는 다음과 같다.

- 실행 중인 런타임을 검사한다. `process.versions.bun`으로 Bun과 Node를 구분하고, TLS 종단은 Bun 1.4 미만에서 시작 전에 실패한다(`D:sandbox/emitted-connection.js:28-42`). 오류 문구는 `tlsTerminate needs Node, or Bun 1.4 or later (this is Bun …)`이다.
- Bun HTTP 클라이언트 우회가 있다. Bun 1.3.x 이하의 `node:http` 클라이언트는 사용자 정의 `lookup`으로 해석한 뒤 스트리밍 요청 본문을 떨어뜨리거나 반복한다(oven-sh/bun#7471). 패키지는 주소 리터럴로 직접 연결하고 SNI만 호스트 이름으로 둔다(`D:sandbox/parent-proxy.js:450-462`). 패키지 주석은 Bun 1.4가 바닥이 되면 우회를 걷어낸다고 적었다.
- 제어 채널 읽기: Bun에서는 `net.Socket({ fd })`가 읽지 못해 fs 스트림을 쓴다(`D:cli.js:70-78`).
- TLS 종단 서버: Bun 서버가 `emit('connection')`으로 넘긴 소켓을 받는 방식이 Node와 다르다. 패키지는 Bun 서버 동작 차이를 주석으로 기록했다(`D:sandbox/tls-terminate-proxy.js:91-97, 168-177, 203-209`).
- 빌드 스크립트: `package.json`에 `"test": "bun test"`와 `"build:srt-proxy": "bun build src/proxy-main.ts --compile …"`가 있다. 개발팀이 Bun 테스트와 Bun 컴파일을 이미 쓴다는 간접 근거다. 다만 tarball에는 컴파일된 `srt-proxy` 바이너리가 없다.

### 7.2 요구와 제약

- `tlsTerminate`는 Node 또는 Bun 1.4 이상이다. Xeon의 기준선 Bun 1.4와 맞는다([결정] foundation-plan §1, 2).
- Bun에서 TLS 종단 업로드는 상한 없이 버퍼링될 수 있다. 상대 서버가 읽기를 멈춘 경우다. 패키지는 업로드가 많을 수 있는 샌드박스에서는 Node를 쓰라고 적었다(README:1070-1095).
- `TRACK` 요청에 대해 Bun 1.3은 응답 없이 연결을 닫는다(README:454-525, 요청 재작성 단락).

### 7.3 단일 실행 파일(사이드카) 판단

- 임베드: `bun build --compile`은 가져온 모듈과 패키지를 실행 파일에 넣고 Bun 런타임 사본을 함께 넣는다. 가져온 자산은 `/$bunfs/` 접두사 경로로 돌아온다(BUN, "What gets embedded").
- 헬퍼 바이너리 탐색: 패키지는 헬퍼를 `dirname(fileURLToPath(import.meta.url))` 기준 상대 경로에서 찾는다.
  - apply-seccomp: `D:sandbox/generate-seccomp-filter.js:118-123`
  - 자바 에이전트 jar: `D:sandbox/java-proxy-agent.js:59`
  - srt-win.exe: `D:sandbox/windows-sandbox-utils.js:138`
- BUN 문서는 `import.meta.url`이 컴파일 산출물 안에서 무엇을 가리키는지 명시하지 않는다. 따라서 상대 경로 탐색이 실행 파일 옆 파일을 찾는지는 확인하지 못했다 [미확인]. 찾지 못하면 샌드박스 시작이 실패할 수 있으므로 시작 시 검사해야 한다.
- 대응 경로 [제안]
  - apply-seccomp는 `seccomp.applyPath`로 지정하거나, `seccomp.argv0` multicall 방식으로 호출자 바이너리 안에 넣는다(`D:sandbox/linux-sandbox-utils.js:1001-1002, 1385-1392`). 두 번째 방식이면 단일 실행 파일로 끝난다.
  - bwrap, socat, rg, jar, srt-win은 `bwrapPath`, `socatPath`, `ripgrep.command`, `javaAgentJarPath`, `windows` 설정으로 절대 경로를 준다(`S:src/sandbox/sandbox-config.ts:1221-1266`).
- 외부 바이너리 실행: 패키지는 `node:child_process`로 bwrap, socat, rg, sandbox-exec를 실행한다. `Bun.spawn`은 쓰지 않는다(`D:sandbox/*.js`의 import). Bun 문서는 spawn 동작을 다루지 않는다 [미확인].
- 판단 [제안]: Bun 1.4 기준 사이드카 구성은 가능성이 높다. 다만 세 가지를 실제 빌드로 확인해야 한다. (a) 헬퍼 탐색 경로, (b) `tlsTerminate` 실사용 시 메모리 상한, (c) `bun build --compile` 산출물에서 샌드박스 명령 한 번 실행. 이 셋은 M0 스파이크로 묶는 것을 권한다. 실행은 이번 조사 범위가 아니다.

## 8. 어댑터 설계 함의 (L0 `platform-sandbox`)

- 싱글턴 [제안]: `SandboxManager`는 프로세스당 하나다. 어댑터는 이를 인스턴스로 감싸고 Cordis 서비스로 등록하되, 프로세스당 정책 하나를 전제로 둔다. 세션마다 다른 네트워크 정책이 필요하면 엔진을 프로세스로 나눈다. 계획 v2의 프로세스 구조(CLI in-process, 데스크톱 자식 엔진, `_research/decisions-log.md` 20행)와 맞는다.
- 호출 형태 [제안]: `wrapWithSandbox(command, …)`는 셸 문자열을 돌려주고, `wrapWithSandboxArgv(command, …, cwd, options)`는 `{ argv, env }`를 돌려준다(`D:sandbox/sandbox-manager.d.ts`). `packages.md` 159행이 말한 "`wrapWithSandbox(cmd)`로 Shell.exec 데코레이터"는 인용 문제를 남긴다. argv 형태를 `Bun.spawn`에 직접 넘기는 것을 권한다.
- 명령별 파일 정책: `wrapWithSandbox`의 `customConfig`는 파일 정책(`denyRead`, `allowRead`, `allowWrite`, `denyWrite`, `disabled`), `credentials`, `git.safeDirectories`를 명령마다 바꾼다(`D:sandbox/sandbox-manager.js:1838-1908`). 네트워크 설정은 명령마다 바뀌지 않는다.
- 명령별 네트워크 목록 [제안]: 전역 `allowedDomains`를 비우고 각 명령이 자기 목록을 등록하는 방식이 가능하다. 전역 `deniedDomains`는 여전히 우선한다. 다만 이 방식은 같은 프로세스 안의 다른 명령이 id를 알면 허용을 빌릴 수 있다. 같은 세션 안의 격리 경계로 쓰지 않는다. id는 128비트 이상 무작위로 만든다(README:261-406).
- 생명주기: `initialize`는 한 번 호출한다. 명령마다 `wrapWithSandbox`(또는 `wrapWithSandboxArgv`)로 감싼다. 명령이 끝나면 `cleanupAfterCommand()`를 부른다. 종료 시 `reset()`을 부른다. Linux에서 존재하지 않는 거부 경로에 만든 마운트 지점은 `cleanupAfterCommand()`가 지운다(README:1142-1190). 래핑이 예외로 실패한 경우에는 `cleanupAfterCommand()`를 부르면 안 된다. 실행 중인 다른 샌드박스의 마운트 지점이 날아간다(README:1096-1141, "Note (Linux, large profiles)" 절의 "A wrap that threw has already released what it held").
- 의존성 점검: `checkDependencies()`와 `checkDependenciesAsync()`로 필수 도구 존재를 점검한다(`D:sandbox/sandbox-manager.d.ts`).
- 오류 분기: `LinuxSandboxProfileError`의 `.code`로 분기한다. 메시지 문자열로 분기하지 않는다(README:1046-1141). `WindowsSandboxError`도 같은 방식이다.
- 콜백 응답: `SandboxAskCallback`은 `true`만 허용한다. 객체 응답을 쓰기 전에 `SandboxManager.askCallbackDenyReason`을 확인한다(README:261-406).
- 설정 검증: 설정 객체는 `SandboxRuntimeConfigSchema`로 검증된다(`S:src/sandbox/sandbox-config.ts:1175`). L4 설정 화면에서 받은 값은 이 스키마를 통과해야 한다.
- 파일 도구와의 관계: 샌드박스는 셸 명령만 감싼다(CC). `read`, `ls` 같은 in-process 도구는 샌드박스 밖이다. 두 경로가 같은 정책을 쓰도록 정책 원천을 한 곳에 둔다 [제안].
- 시크릿 설계와의 관계 [제안]: `credentials` 마스킹은 "에이전트는 값을 모른 채 참조로 쓴다"는 방향과 같다. 다만 `tlsTerminate`에 의존하고 Bun 1.4 이상이 필요하며 실험 기능이다. L0-secrets 설계와 맞춰 어느 쪽을 쓸지 정해야 한다(§10 [미결]).

## 10. 결정, 제안, 가정, 미결 정리

[결정]

- 샌드박스 패키지로 `@anthropic-ai/sandbox-runtime`을 쓴다(`_research/foundation-plan.md` §2 승인 표).
- 첫 지원 OS는 macOS와 Linux(WSL 포함)다. Windows 네이티브는 나중이다(`_research/decisions-log.md` 11행).
- OS별로 달라지는 부분은 공통 인터페이스 뒤에 두고, 소비자 코드에 OS 분기를 두지 않는다(`_research/decisions-log.md` 13행).

[제안]

- 0.0.81을 정확 버전으로 고정한다. 어댑터 뒤에 두고, 설정 스키마 검사 테스트를 둔다. 0.0.x의 설정 형식 변화에 대비한다.
- 패키지의 플랫폼 분기는 L0 어댑터 안에만 둔다. `D:sandbox/` 내부 분기는 패키지 것이므로 손대지 않는다.
- 프로세스당 네트워크 정책을 하나로 둔다. 세션별 정책이 필요하면 엔진 프로세스를 나눈다. 명령별 목록은 보조로만 쓴다.
- 파일 정책의 원천을 하나로 둔다. 셸 명령(sandbox)과 `read`, `ls`(L1 도구)가 같은 정의를 쓴다.
- 시크릿 경로(SOPS age 키, `~/.ssh` 등)는 `denyRead`에 리터럴로 적는다. Linux에서 글로브가 건너뛰어지는 경우를 피한다.
- 헬퍼 바이너리 경로는 시작 시 검사한다. 사이드카 구성에서는 `seccomp.argv0` 또는 `applyPath`, `bwrapPath`, `socatPath`, `ripgrep.command`를 명시한다.
- argv 형태 `wrapWithSandboxArgv`를 `Bun.spawn`에 넘긴다.
- 샌드박스 완화 옵션(`mask`, `tlsTerminate`, `allowNestedUserNamespaces`, `allowAppleEvents`, `allowAllUnixSockets`, `enableWeakerNestedSandbox`)은 신뢰된 사용자 설정에서만 받는다(§3.6).

[가정]

- Xeon 엔진의 런타임은 Bun 1.4 이상이다(`_research/foundation-plan.md` §2). 이 가정이 깨지면 `tlsTerminate`는 쓸 수 없다.
- 샌드박스가 막는 범위는 패키지 README의 설명과 같다. 이번 조사에서 실행으로 확인하지는 않았다.

[미결]

- 중첩 사용자 네임스페이스: L2 브라우저 도구(Playwright 등)를 샌드박스 안에서 돌릴지 정해야 한다. 돌린다면 `allowNestedUserNamespaces: true`를 받아들이고 그 경우 쓰기 거부가 무력화되는 위험을 감수해야 한다.
- `tlsTerminate`와 `credentials mask`: 시크릿 참조 설계(L0-secrets)가 이 기능을 쓸지 정해야 한다. 쓴다면 실험 기능, Bun 1.4 의존, Bun 업로드 메모리 문제를 함께 감수해야 한다.
- 샌드박스 밖 재시도 탈출구: Claude Code에는 있고 라이브러리에는 없다. Xeon에서 둘지 정해야 한다.
- 비 x64, arm64 Linux 지원: 이 아키텍처에서는 seccomp 필터가 번들되지 않는다. 지원 범위에서 빼거나 `allowAllUnixSockets`를 받아들여야 한다.
- 명령별 네트워크 목록의 신뢰 경계: 같은 프로세스 안 명령들의 격리를 요구하는지 정해야 한다. 요구한다면 프로세스 분리가 필요하다.
- Windows 어댑터: `decisions-log.md` 11행에 따라 M0~M1 범위 밖으로 둔다. 이 판단은 사용자 확인이 필요하다.
