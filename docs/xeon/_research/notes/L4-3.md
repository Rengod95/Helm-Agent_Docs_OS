# L4-3 조사: 설정 화면의 클라이언트 값 검사 가능성

- 대상 질문: `settings.list`가 주는 `SettingDefWire.type`(JSON Schema 객체)을 클라이언트(설정 화면)가 TypeBox 1.4 검사기로 직접 검사할 수 있는가. 아니면 서버 검사에만 기대고 `range` 기반 경량 검사만 해야 하는가.
- 근거 명세: `docs/xeon/F/wire-settings/spec.md` §3.8.2, §4.10, §4.11, §9 S6, §10 6번
- 근거 소스: `xeon/node_modules/typebox` 1.4.2 (읽기만 했다. 코드를 실행하지 않았다.)
- 결정 근거: [결정] 스키마는 TypeBox 1.4로 승인되어 있다(`_research/foundation-plan.md` §2).
- 성격: 조사 결과. 정본이 아니며 인용용이다.

## 1. 결론

- [제안] 클라이언트는 `SettingDefWire`의 값을 직접 검사할 수 있다. 검사 함수는 `typebox/schema`의 `Check`이며, 이 함수는 JSON Schema 객체를 입력으로 받는다. `typebox/value`의 `Value.Check`도 같은 함수로 위임한다.
- 현재 와이어 형태만으로는 바로 쓸 수 없다. `SettingDefWire.type`에는 `range`가 합쳐져 있지 않다. 명세 §3.8.2는 `type`과 `range`를 따로 싣는다. 클라이언트는 §4.10 3번의 병합 규칙(`minimum`, `maximum`, `enum`)을 적용해야 한다. 이 병합을 서버와 클라이언트가 같은 함수로 쓰도록 F에 두는 것을 제안한다(§4 P1).
- [제안] `range`만 보는 경량 검사는 기본 경로로 쓰지 않는다. `range`는 `pattern`, `minLength`, `items` 같은 `type`의 나머지 제약을 빠뜨린다. 전체 JSON Schema 검사도 비용이 작고 서버 결과와 같은 객체로 판정한다.
- [제안] 최종 판정은 서버 `settings.set`(`checkSettingWrite`)에 둔다. 클라이언트 검사는 입력 중 안내용이다. 범위 허용(`allowedScopes`)은 정의에 있으므로 클라이언트가 미리 막을 수 있다. 잠금(`locked`), 비밀 값 거부(`settings.secretValue`)는 현재 상태가 필요하므로 서버 전용이다.
- [가정] 클라이언트와 서버가 같은 TypeBox 버전의 같은 검사 엔진을 쓰고, 병합 객체가 같으면 명세 S6의 동치가 성립한다. 이 판단은 소스 읽기에 근거한다. 실행으로 확인하지 않았다(§5).

## 2. 확인한 사실

### 2.1 현재 상태

- `xeon/packages/contracts/src/`에는 `index.ts`만 있다. `wire-settings/settings/` 디렉터리는 없다. `SettingDefWire` 구현의 현재 상태는 읽을 수 없고, 명세만 대상으로 했다.
- `xeon/packages/*/package.json` 어디에도 `typebox` 의존 선언이 없다. 루트 `xeon/package.json:36`은 `"typebox": "catalog:"`를 쓰고, `xeon/package.json:48`에 `"typebox": "1.4.2"`가 있다.
- `xeon/node_modules/typebox`는 1.4.2 한 벌뿐이다. 1.3.27은 설치되어 있지 않다.

### 2.2 와이어 형태 (명세)

- `SettingDefWire`(spec.md:754-765)는 `type: Type.Record(Type.String(), Type.Unknown())`, 즉 JSON Schema 객체를 싣고, `range`는 `Optional(SettingRange)`로 따로 둔다.
- `settings.list`의 결과는 `{ defs: SettingDefWire[] }`다(spec.md:286, 336).
- D6(spec.md:778)은 `type`에 `minimum`·`maximum`·`enum`을 두면서 `range`도 두는 정의를 거부한다. 따라서 `range`가 있는 정의에서 범위 제약은 `range`에만 있다. 와이어 `type`만 보면 범위가 빠진다.
- §4.10 3번(spec.md:1011)은 서버가 `def.type`의 JSON Schema에 `range`를 합쳐 `properties[key]`를 만든다고 정한다. 클라이언트가 필요한 객체가 이 병합 결과인데, 와이어에는 실리지 않는다.

### 2.3 TypeBox 1.4.2 검사 경로

- `typebox/value`의 `Check`는 `schema` 엔진의 `Check`를 그대로 호출한다(`xeon/node_modules/typebox/build/value/check/check.mjs:3, 5-11`).
- `typebox/schema`의 `Check`는 `Engine.CheckSchema`를 바로 호출한다(`build/schema/check.mjs:6-13`). 입력 타입은 `XSchema`이고, 이는 `object | boolean`이다(`build/schema/types/schema.d.mts:1, 7`, `build/schema/check.d.mts:4`).
- `Value.Check`의 시그니처는 `TSchema`를 받는다(`build/value/check/check.d.mts:3`). `TSchema`의 본문은 빈 인터페이스다(`build/type/types/schema.d.mts:1-2`). 그래서 JSON Schema 객체도 컴파일 시 제약을 통과한다.
- 공식 readme는 Schema 컴파일러가 "TypeBox 타입과 일반 JSON Schema 객체를 모두 받는다"고 설명한다(`readme.md:169`, 1차 자료).
- `CheckSchema`(`build/schema/engine/schema.mjs:257-`)는 `Schema.IsX` 키워드 분기만 본다. `~kind`를 읽는 분기는 없다. `$schema`, `x-xeon`, `deprecated` 같은 키는 분기에 해당하지 않아 무시된다. [소스 읽기 기준. 분기 전체를 한 줄씩 대조하지는 않았다.]

### 2.4 Kind 표현

- TypeBox 1.4.2는 심볼을 쓰지 않는다. 종류 표지는 `'~kind'` 문자열 키다(예: `build/type/types/number.mjs:13`). 명세 전제("TypeBox 심볼 없음")는 맞다.
- `Memory.Create`는 이 키를 기본적으로 열거 불가능하게 정의한다(`build/system/memory/create.mjs:14-20, 29-35`). `enumerableKind`의 기본값은 `false`다(`build/system/settings/settings.mjs:13`). 그래서 `JSON.stringify`를 거친 와이어 객체에는 `~kind`가 남지 않는다. 설정을 켜면 남지만, 검사 경로는 이 키를 읽지 않으므로 결과는 같다. [소스 기준]

### 2.5 평가 방식과 CSP

- `Check` 경로는 코드를 생성하지 않는다. 인터프리터 `Engine.CheckSchema`만 쓴다(`build/schema/check.mjs:13`). `new Function`을 쓰지 않는다.
- `Compile` 경로만 코드를 생성한다. `Environment.CanEvaluate()`가 참이면 `globalThis.Function`으로 코드를 만들고, 거짓이면 같은 인터프리터로 돌아간다(`build/schema/build.mjs:36-40`, `build/system/environment/evaluate.mjs:35-37`).
- `CanEvaluate`는 첫 호출 때 `Evaluate('null')()`을 한 번 시도하고, 실패하면 거짓을 캐시한다(`evaluate.mjs:7-24`). `unsafe-eval`이 막힌 WebView에서도 예외로 멈추지 않는다.
- 설정 화면의 입력 한 건 검사는 `Check`로 충분하다. 목록 전체를 반복 검사하는 경우에만 `Compile`을 고려한다.

### 2.6 pattern과 format

- `pattern`은 `new RegExp(pattern, 'u')`로 만들고 `test`로 판정한다(`build/schema/engine/_regexp.mjs:2-4`, `build/schema/engine/pattern.mjs`의 `CheckPattern`). 부분 일치이므로 `^…$`로 묶인 패턴만 쓴다. 명세의 `SETTING_KEY_PATTERN`, `SecretRef`, `SEMVER_PATTERN`은 모두 묶여 있다(spec.md §3.8.1, F/capabilities spec).
- 등록되지 않은 `format`은 항상 통과한다(`build/format/_registry.mjs:65-67`, `?? true`). 명세의 `SettingDef` 스키마는 `format`을 쓰지 않는다 [명세 기준]. 나중에 `format`을 쓰면 클라이언트와 서버의 형식 등록이 같아야 S6이 성립한다.

### 2.7 타입 수준

- `Value.Check`의 `value is Static<Type>`에서, `~kind`가 없는 객체는 `Static`의 마지막 분기인 `XStatic`으로 간다(`build/type/types/static.d.mts:37`). `Record<string, unknown>` 입력에서 타입 좁힘 결과가 무엇인지는 실행하지 않아 확인하지 못했다 [미확인]. 호출하는 쪽은 불리언 결과만 쓰는 편이 안전하다.

## 3. 질문별 답

Q1. 클라이언트가 `SettingDefWire.type`을 TypeBox 1.4 검사기로 직접 검사할 수 있는가.

- 가능하다. `typebox/schema`의 `Check`를 쓴다(§2.3). 입력 객체는 `type`에 `range`를 병합한 것이어야 한다(§2.2). 병합 규칙은 `range.min` → `minimum`, `range.max` → `maximum`, `range.enum` → `enum`이다(spec.md §4.10 3번).

Q2. 서버 검사에만 의존해야 하는가.

- 값 검사는 클라이언트가 해도 된다. 상태가 필요한 검사만 서버에 남는다. 서버 판정 항목은 다음과 같다. `managed` 잠금(`settings.locked`, spec §9 S4), 비밀 값 직접 쓰기 거부(`settings.secretValue`, §9 S8), 범위 허용 재확인(`settings.scopeNotAllowed`, §9 S3)이다.

Q3. `range` 기반 경량 검사만 해야 하는가.

- 아니다. `range`만 보면 `type`의 `pattern`(키 패턴, `secret://` 참조), `minLength`, `items`(`list`, `table` 위젯)를 검사하지 못한다. 전체 JSON Schema 검사는 같은 객체로 서버와 같은 결과를 준다.
- [제안] 입력 위젯이 문자열을 보내는 경우 검사 전에 JSON으로 해석해야 한다. 명세 §4.11의 CLI 규칙(JSON 해석, 실패 시 문자열)을 UI도 쓴다.

## 4. 명세에 대한 제안

- [제안] P1. `F/wire-settings` §3.8.2에 검사용 병합 함수를 명시한다. 예: `toValueJsonSchema(def: SettingDefWire): JsonSchemaDocument`. 서버의 `settingsJsonSchema`(§4.10 3번)와 클라이언트 검사가 이 함수를 같이 쓰면 S6이 구조적으로 성립한다. 함수는 F 순수 함수이므로 UI가 import해도 층 규칙을 위반하지 않는다 [가정: `contracts`가 L4 UI에서 import 가능한 층 규칙 해석].
- [제안] P2. S6 속성 기반 테스트에 와이어 경로를 넣는다. 서버 정의, `SettingDefWire` JSON 직렬화, 클라이언트 검사 함수, 결과 비교 순서다.
- [미결] P3. TypeBox 버전(명세 §10 6번). 조사 노트 `_research/notes/F-2.md` §2 2번은 1.3.27과 1.4.2의 `TSchema`, `Static` 선언이 같다고 적었다. 그 노트는 npm 배포본으로 확인했다. 이 노트는 1.3.27 소스를 대조하지 않았다 [미확인]. 클라이언트 번들과 서버가 같은 버전을 쓰도록 맞춘다.
- [제안] P4. 클라이언트 번들에는 `typebox/schema` 서브패스만 넣는다. 루트 `typebox`를 넣지 않는다. 번들 크기는 측정하지 않았다 [미확인].

## 5. 미확인 사항

- 실행 검증을 하지 않았다. 이 노트의 동작은 소스 읽기에 근거한다. 실행 검증은 S6 속성 기반 테스트가 맡는다.
- 1.3.27 소스를 대조하지 않았다(§4 P3).
- 데스크톱 WebView의 CSP 설정은 명세와 `docs/xeon`에 정의가 없다 [미결]. `Check` 경로는 `unsafe-eval`을 쓰지 않는다(§2.5). `Compile`도 실패 시 같은 인터프리터로 돌아간다.
- 타입 좁힘 결과(§2.7)는 확인하지 못했다.
- Ajv 같은 다른 JSON Schema 검사기는 확인하지 않았다. 이 노트의 "호환 검사기"는 `typebox/schema`만 가리킨다.
- `contracts`의 `wire-settings` 구현이 없어 실제 `SettingDefWire` 정의와 대조하지 못했다.
- `CheckSchema`의 키워드 분기 전체를 한 줄씩 대조하지 않았다(§2.3).
