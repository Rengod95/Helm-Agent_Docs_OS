# Cordis fiber 생애주기 조사: scope 토글, 재적용, 해제 순서 (X-2)

- 작성일: 2026-10-21
- 대상: `xeon/vendor/cordis/src`(커밋 df4431e, `UPSTREAM.json` 기준, 표기 rc.11)
- 목적: X 확장 체계의 scope 켜기-끄기-켜기를 Cordis fiber로 어떻게 표현하는지 확인한다. 재적용 API, dispose 시 비동기 작업의 처리, `ctx.on`의 `assertActive` 가드, 서비스 공급자 해제 순서와 소비자 재시작을 소스 읽기로 대조한다.
- 원칙: 소스와 문서를 읽기만 했다. 코드를 실행하지 않았고 테스트를 돌리지 않았다.
- 인용 표기: `fiber.ts:줄`처럼 `xeon/vendor/cordis/src/` 기준으로 줄여 쓴다. "(추론)"은 소스 줄에서 도출했으나 실행으로 확인하지 않은 판정이다. "[미확인]"은 소스로도 확인하지 못한 항목이다.
- 표지: [결정] 사용자 결정 인용. [제안] 작성자 설계 선택. [가정] 확인하지 않은 전제. [미결] 사용자 확인 필요. [미확인] 확인하지 못한 항목.

## 0. 결론

1. Cordis에는 scope 객체가 없다. 확장 단위는 fiber(플러그인 적용 1회)다. 켜기는 `ctx.plugin()`으로 새 fiber를 만들고, 끄기는 `fiber.dispose()`, 다시 켜기는 `ctx.plugin()`을 다시 호출해 새 fiber를 만든다. 해제된 fiber는 다시 살아나지 않는다(`fiber.ts:136`, `173`, `218-221`).
2. 같은 fiber를 다시 적용하는 `restart()`는 살아 있는 fiber에서만 의미가 있다. 해제된 fiber에서는 거부된 Promise를 돌려주고(`fiber.ts:489-491`), 실패한 fiber에서는 아무 일도 일어나지 않은 채 원래 오류를 다시 던진다(`fiber.ts:400`, `485`). 실패 복구 경로는 `update()`다(`fiber.ts:504`).
3. dispose는 등록 해제기를 실행하지만 진행 중인 핸들러를 취소하지 않는다. Cordis에는 취소 신호가 없고, fiber 해제는 리스너가 돌려준 Promise를 추적하지 않는다. 비동기 effect는 setup이 끝난 뒤에 해제된다(`fiber.ts:320-324`).
4. `ctx.on`은 `uid`가 null인 fiber에서만 던진다(`fiber.ts:218-221`, `events.ts:168`). PENDING, LOADING, ACTIVE, FAILED, UNLOADING 상태에서는 던지지 않고 등록이 성공한다. 그 등록은 다음 해제 때까지 남는다. "비활성 fiber의 등록 차단"은 Cordis가 보장하지 않는다.
5. 공급자 해제는 소비자 해제가 먼저다. 공급자가 ACTIVE를 떠나는 순간 소비자의 공급이 끊기고, 소비자 해제가 끝난 뒤 공급자 effect가 해제된다(`fiber.ts:362-366`, `449-451`, `465-469`). 공급자가 다시 ACTIVE가 되면 소비자는 epoch 변화로 apply가 다시 호출된다(`fiber.ts:383-412`, `414-424`).
6. [제안] X는 Cordis fiber를 scope 단위로 감싸고, 턴 경계 적용, 실행 세대(generation) 토큰, 취소 신호, 등록 가드를 X 쪽에서 구현한다. Cordis는 이 네 가지를 제공하지 않는다.

## 2. fiber 상태와 전이

- 상태는 6종이다(`fiber.ts:78-85`): PENDING, LOADING, ACTIVE, FAILED, DISPOSED, UNLOADING.
- 상태는 `_updateState`가 정한다(`fiber.ts:353-356`). 콜백이 상태를 돌려주지 않으면 `_getState`가 계산한다(`fiber.ts:346-351`). uid가 null이면 DISPOSED, `_error`가 있으면 FAILED, epoch가 INACTIVE가 아니면 ACTIVE, 그 밖에는 PENDING이다.
- 전이는 epoch가 정한다. `_refresh`가 `revision`과 주입 서비스의 impl uid 목록으로 epoch 문자열을 만든다. 주입 서비스가 하나라도 없으면 epoch는 INACTIVE다(`fiber.ts:383-394`). `_setEpoch`는 INACTIVE에서 벗어날 때 `_reload`를, 그 밖의 변화에 `_unload`를 시작한다(`fiber.ts:396-412`).
- uid는 해제 시작 직후에 null이 된다(`fiber.ts:173`). 이때 상태는 `_setEpoch`의 콜백이 돌려준 UNLOADING으로 보이고, 해제가 끝난 뒤에야 DISPOSED가 된다(`fiber.ts:191`). 따라서 상태만 보고 "해제 시작"을 판정하면 놓칠 수 있다. 가드는 uid로 해야 한다.

| 상태 | uid | 주된 원인 | `assertActive` 통과 | 근거 |
|---|---|---|---|---|
| PENDING | 있음 | 주입 서비스 부재(epoch INACTIVE) | 통과 | `fiber.ts:346-351`, `383-392` |
| LOADING | 있음 | apply 실행 중 | 통과 | `fiber.ts:414-443` |
| ACTIVE | 있음 | apply 완료 | 통과 | `fiber.ts:435-442` |
| FAILED | 있음 | apply 또는 설정 검증 오류(`_error`) | 통과 | `fiber.ts:426-434`, `348` |
| UNLOADING | 있음 | epoch 변화 또는 의존 소실로 해제 중 | 통과 | `fiber.ts:445-479` |
| UNLOADING | null | `dispose()` 호출 직후 | 던짐 | `fiber.ts:173`, `181`, `218-221` |
| DISPOSED | null | 해제 완료 | 던짐 | `fiber.ts:191`, `347` |

- 루트 fiber는 uid가 0이고(`fiber.ts:195`) 항상 통과한다.

## 3. 켜기, 끄기, 다시 켜기

### 3.1 켜기

- `ctx.plugin(P, config)`는 `RegistryService.plugin`이다(`registry.ts:193-213`). 호출 측 fiber가 활성이어야 한다(`registry.ts:197`).
- 런타임은 플러그인 함수를 키로 `_internal`에 둔다(`registry.ts:127`, `199-205`). 같은 플러그인의 fiber들은 `runtime.fibers`를 공유하므로 한 플러그인에 fiber를 여러 개 둘 수 있다.
- fiber의 uid는 `registry.counter`에서 받는다(`fiber.ts:136`, `registry.ts:136-138`).
- 반환값은 Fiber에 `then`을 더한 객체다(`registry.ts:208-212`). `await`는 진행 중인 로드가 끝날 때까지 기다리고, 실패가 있으면 던진다(`fiber.ts:481-487`). PENDING 상태여도 로드가 끝났으면 resolve된다.
- 설정 검증 실패는 `resolveConfig`가 `ValidationError`로 던지고(`fiber.ts:34-46`, `events.ts:71-73`), `_reload`의 catch가 `_error`에 기록해 FAILED가 된다(`fiber.ts:426-434`).
- `ctx.inject(deps, fn)`은 `inject`를 선언한 플러그인을 만드는 `plugin`의 얇은 래퍼다(`registry.ts:189-191`). 주입 조건부 켜기는 이 경로다.

### 3.2 끄기

- `fiber.dispose()`는 `parent.fiber.effect`가 돌려준 wrapper다(`fiber.ts:164-193`). 실행되는 해제기는 `fiber.ts:172-192`다.
  - uid를 null로 바꾼다(`173`).
  - 런타임 목록에서 자기를 뺀다. 마지막 fiber였으면 레지스트리에서 런타임을 지운다(`175-180`).
  - epoch를 INACTIVE로 바꾸고 `_unload`를 시작한다(`181`).
  - 진행 중인 로드(`inertia`)가 비워질 때까지 해제가 보류된다(`185-187`). `await fiber.dispose()`는 해제 완료 뒤에 이어진다.
- 자동 끄기: 주입 서비스가 사라지면 명시적 dispose 없이 PENDING이 되어 해제된다(`fiber.ts:369-381`, `383-394`, `reflect.ts:240-259`). 서비스가 다시 공급되면 `_reload`로 다시 켜진다.
- `registry.delete(P)`는 런타임을 지운 뒤 그 플러그인의 모든 fiber에 `dispose()`를 호출하지만 기다리지 않는다(`registry.ts:162-171`).

### 3.3 다시 켜기와 재적용 API

| 목적 | API | 조건 | 결과 | 근거 |
|---|---|---|---|---|
| 새로 켜기 | `ctx.plugin(P, cfg)` | 호출 측 fiber 활성 | 새 Fiber | `registry.ts:193-213`, `197` |
| 끄기 | `fiber.dispose()` | 아직 해제 전 | 해제 완료 Promise | `fiber.ts:172-192` |
| 같은 플러그인 다시 켜기 | `ctx.plugin(P, cfg)` 재호출 | 호출 측 fiber 활성 | 이전 것과 다른 새 Fiber | `fiber.ts:136` |
| 살아 있는 fiber 재적용 | `fiber.restart()` | 살아 있음 | unload 후 reload | `fiber.ts:489-495` |
| 살아 있는 fiber 설정 변경 | `fiber.update(cfg)` | 살아 있음 | `internal/update` 거친 뒤 재시작. FAILED 복구 | `fiber.ts:497-517` |
| 플러그인 전부 끄기 | `ctx.registry.delete(P)` | 없음 | 런타임 삭제, 모든 fiber dispose 호출(대기 없음) | `registry.ts:162-171` |

- 다시 켜기는 `ctx.plugin(P, config)` 재호출이다. 결과는 새 fiber다(`fiber.ts:136`). 이전 fiber 객체와 그 effect는 재사용되지 않는다. 이전 closure가 옛 ctx를 쥐고 있다면 그 ctx는 해제된 fiber를 가리킨다(`fiber.ts:137`).
- 런타임은 남아 있으면 재사용되고, 마지막 fiber가 해제되어 지워졌으면 새로 만들어진다(`registry.ts:199-205`, `fiber.ts:175-178`). 플러그인 함수의 모듈 스코프 변수는 그대로 남고, ctx 스코프 상태는 새로 만들어진다(추론).
- `update(config)`는 해제된 fiber에서 동기로 던진다(`fiber.ts:499`, 함수가 async가 아니다). `internal/update` waterfall을 거치므로 플러그인이 `ctx.on('internal/update', (config, next) => …)`로 재시작을 거부할 수 있다(`events.ts:54-69`, `fiber.ts:507-516`). `next`를 부르지 않으면 재시작은 일어나지 않는다(`fiber.ts:510`).
- `restart()`는 revision을 올리고 `_refresh`로 epoch를 바꾼 뒤 `await`한다(`fiber.ts:489-495`). 활성 상태에서는 unload 후 reload가 된다.
  - `restart`는 `async` 함수다. 해제된 fiber에서는 던지지 않고 거부된 Promise를 돌려준다(`fiber.ts:491`). 호출자가 잡지 않으면 처리되지 않은 거부가 된다(추론).
  - FAILED fiber에서는 `_setEpoch`가 `_error` 가드 때문에 아무것도 하지 않고(`fiber.ts:400`), `await`가 같은 오류를 다시 던진다(`fiber.ts:485`). 복구는 `update()`다. 소스 주석도 같다(`fiber.ts:399`).
  - PENDING fiber에서는 주입 부재 때문에 epoch가 INACTIVE로 같아서 변화가 없다(`fiber.ts:383-402`).

## 4. dispose 시 진행 중인 비동기 작업

### 4.1 리스너

- 리스너 등록은 effect다(`events.ts:142-149`). 해제기 `() => this.unregister(name, callback)`가 `_hooks`에서 리스너를 뺀다(`events.ts:147`, `151-160`). 이후 새로 시작하는 디스패치는 이 리스너를 호출하지 않는다.
- 해제기의 실행 시점은 fiber 해제 목록을 비우는 시점이다(`fiber.ts:453`). 그 시점은 공급 서비스의 소비자가 모두 내려간 뒤다(`fiber.ts:449-451`). 공급 서비스가 없으면 해제 시작 뒤 마이크로태스크 한 번 뒤다(`fiber.ts:453-458`). 소스 주석은 이 순서를 의도로 적는다. 공급자는 소비자가 내려가는 동안 자기 서비스에 접근할 수 있어야 한다(`fiber.ts:446-448`).
- 디스패치 도중 해제: `_resolve`가 콜백 배열을 `map`으로 복사한다(`events.ts:83-86`). `serial`, `bail`, `waterfall`은 이 복사본을 순회하므로(`events.ts:110-115`, `117-123`, `125-140`), 디스패치가 시작된 뒤 해제된 리스너도 같은 디스패치의 뒤쪽 순서에서는 호출된다(추론).
- 진행 중인 리스너 Promise에는 취소 신호가 없다. fiber 해제는 리스너 Promise를 추적하지 않으므로 기다리지 않는다. `emit`은 리스너의 반환값을 버린다(`events.ts:104-107`). 비동기 리스너가 거부하면 처리되지 않은 거부가 된다(추론). `parallel`은 `Promise.allSettled`로 모두 끝난 뒤 실패가 있으면 `AggregateError`를 호출자에게 던진다(`events.ts:95-102`).

### 4.2 effect

- 동기 effect의 해제기는 역순으로 순차 실행된다(`fiber.ts:281-290`). 앞 해제기가 Promise를 돌려주면 다음 해제기는 그 뒤에 실행된다.
- Promise를 돌려주는 effect는 wrapper가 task가 끝난 뒤에 해제한다(`fiber.ts:320-324`). setup 중에 dispose해도 setup이 끝난 뒤 해제기가 실행된다. setup 중 수집된 해제기도 포함된다(`fiber.ts:230-236`).
- async iterable effect는 `runner.epoch`가 바뀌면 다음 반복 전에 루프를 끝낸다(`fiber.ts:260-261`). 이미 시작된 `iter.next()`는 끝까지 실행된다. `iter.return()`은 호출하지 않는다(`fiber.ts:254-266`에서 확인). 따라서 생성기의 `finally`는 실행되지 않는다(추론).
- 같은 fiber 안의 effect들은 `Promise.all`로 해제가 동시에 시작된다(`fiber.ts:453-463`). 해제 목록은 역순이지만 서로의 완료를 기다리지 않는다. 순서가 필요한 정리는 한 effect 안에 묶어야 한다. `arch-1.md §2`의 "정리 순서 2"와 같은 결론이다.

### 4.3 apply가 끝나지 않은 상태에서 해제

- `_unload`는 진행 중인 로드(`inertia`)가 끝날 때까지 해제를 보류한다(`fiber.ts:185-187`). apply가 Promise를 돌려주면 그 Promise가 끝난 뒤에 해제가 시작된다.
- apply 중 등록된 effect는 `collect`로 fiber의 `_disposables`에 쌓이고, 해제 때 함께 정리된다(`fiber.ts:131-133`, `445-463`).
- 따라서 apply가 끝나지 않으면 해제도 끝나지 않는다. Cordis는 apply를 취소하지 않는다.

### 4.4 해제 뒤 ctx 접근

- 해제된 fiber의 ctx로 `on`, `once`, `effect`, `provide`, `accessor`, `mixin`, `plugin`, `inject`를 부르면 모두 던진다. 이들은 전부 `fiber.effect`나 `ctx.plugin`을 거치고, 그 안에서 `assertActive`가 호출되기 때문이다(`fiber.ts:276`, `events.ts:168`, `registry.ts:197`, `reflect.ts:203`, `262-263`, `273`).
- 해제된 fiber에서 주입 서비스를 읽는 경로는 `committed`가 `undefined`가 된 뒤(`fiber.ts:470`) `locate`가 실패해 "cannot get required service ... in inactive context"로 던지는 것으로 읽힌다(`reflect.ts:114-120`, 추론).

## 5. ctx.on과 assertActive

- `on`은 먼저 `this.ctx.fiber.assertActive()`를 부른다(`events.ts:168`). `assertActive`는 `this.uid !== null`만 검사한다(`fiber.ts:218-221`). 던지는 값은 `CordisError('INACTIVE_EFFECT')`이고, 메시지는 "cannot create effect on inactive context"다(`fiber.ts:96-98`).
- 질문에 대한 답은 다음과 같다. 비활성 fiber라도 uid가 남아 있으면 `ctx.on`은 던지지 않는다. 해당하는 상태는 PENDING(의존 부재), UNLOADING(해제 중이지만 uid 유지), FAILED다. 던지는 경우는 uid가 null인 경우뿐이며, 이는 `dispose()`가 시작된 뒤다(`fiber.ts:173`).
- 등록은 effect로 fiber에 쌓이고(`events.ts:142-149`, `fiber.ts:336`), 다음 해제 때 정리된다. 이로부터 두 결과가 나온다(추론).
  1. PENDING 상태에서 만들어진 등록은 살아 있는 리스너로 남는다. 예를 들어 이전 실행이 남긴 비동기 콜백이 PENDING 중에 `ctx.on`을 부르면, 리스너는 fiber가 PENDING이어도 `emit`에서 호출된다. 다음 해제 때까지 남는다.
  2. 옛 closure는 같은 ctx 객체를 쓴다. ctx는 생성 때 한 번 만들어지고 `_reload`마다 재사용된다(`fiber.ts:137`, `146`, `152`). 실행 세대를 가리는 장치가 Cordis에는 없다. 재적용 뒤의 옛 콜백이 새 실행의 등록을 늘릴 수 있다.
- 따라서 X가 "비활성 scope의 등록 차단"을 원하면 Cordis의 가드에 기대면 안 된다. §7에서 X 쪽 가드를 제안한다.

## 6. 서비스 공급자 해제 순서와 소비자 재시작

### 6.1 공급자 fiber 해제

| 단계 | 일어나는 일 | 근거 |
|---|---|---|
| 1 | 공급자 `dispose()`가 uid를 null로 바꾸고 `_setEpoch(INACTIVE)`로 `_unload`를 시작한다 | `fiber.ts:173`, `181`, `396-412` |
| 2 | 공급자 `_unload`는 자기 공급 서비스의 소비자가 모두 내려갈 때까지 해제를 보류한다 | `fiber.ts:449-451` |
| 3 | 공급자 상태가 UNLOADING이 되고, 공급 서비스마다 notify가 나간다. `_getImpl(strict)`가 상태 ACTIVE 검사에서 실패한다 | `fiber.ts:355`, `362-366`, `reflect.ts:185` |
| 4 | 소비자의 `_checkImpl`이 `_store`에서 항목을 지우고, `_refresh`가 epoch를 INACTIVE로 만든다. 소비자 `_unload`가 시작된다 | `fiber.ts:369-381`, `383-394`, `396-412` |
| 5 | 소비자 `_unload`가 소비자의 effect 전체를 `Promise.all`로 해제한다 | `fiber.ts:449-463` |
| 6 | 소비자 `_unload` 끝에 `committed`의 dependents에서 자기를 빼고, 공급자의 `release`와 `_release` 함수를 호출한다 | `fiber.ts:465-469` |
| 7 | 공급자 `_unload`가 다시 진행해 자기 effect를 `Promise.all`로 해제한다. provide 해제기는 store에서 항목을 지우고(`reflect.ts:223`), notify를 다시 보내고(`reflect.ts:224`), dependents가 0이므로 즉시 통과해 provisions에서 빠진다(`reflect.ts:229-235`) | `fiber.ts:449-463`, `reflect.ts:222-236` |
| 8 | 공급자 `_unload`가 끝나고 DISPOSED가 된다 | `fiber.ts:470-478`, `191` |

- 7단계에서 provide 해제기와 공급자의 나머지 effect는 같은 `Promise.all`에서 동시에 시작된다. 둘 사이 순서는 보장되지 않는다(`fiber.ts:453-463`).

### 6.2 개별 provide 해제

- `ctx.provide` 해제기(`reflect.ts:222-236`)는 store 삭제(`223`), notify(`224`), 공급자 release 대기(`229-232`), provisions 제거(`235`) 순서다.
- 소비자는 notify에서 `_checkImpl` 실패로 해제를 시작한다. 소비자가 `dependents`에서 빠지면 `impl.release`가 호출되어 대기가 풀린다(`fiber.ts:465-468`).

### 6.3 공급자 재활성과 소비자 재시작

| 단계 | 일어나는 일 | 근거 |
|---|---|---|
| 1 | 공급자 apply 중의 `provide`는 notify하지 않는다. 상태가 ACTIVE일 때만 notify한다 | `reflect.ts:219-221` |
| 2 | 공급자 `_reload`가 끝나 ACTIVE가 되면 `_updateState`가 공급 서비스마다 notify를 보낸다 | `fiber.ts:435-442`, `362-366` |
| 3 | 소비자 `_checkImpl`이 새 impl을 `_store`에 넣는다 | `fiber.ts:369-381`, `reflect.ts:181-187` |
| 4 | 소비자 `_refresh`가 impl uid를 포함한 새 epoch를 만든다 | `fiber.ts:384-392` |
| 5 | 소비자 `_setEpoch`가 INACTIVE에서 벗어나므로 `_reload`가 시작되고, apply가 다시 호출된다 | `fiber.ts:404-406`, `414-424`, `143`, `152` |

- 소비자의 config는 바뀌지 않는다. `_execute`는 `this.config`를 `internal/config` waterfall로 다시 거친다(`fiber.ts:143`, `events.ts:71-73`).
- 연쇄 효과: 공급자의 해제와 재적용은 그 서비스의 소비자 전체를 해제하고 다시 적용한다. 소비자의 재적용은 공급자에 영향을 주지 않는다(`fiber.ts:416-419`, `449-451`, 추론).
- [미확인] 교착 가능성: 부모 소비자가 자기 자식 fiber가 공급하는 서비스를 주입하는 구성에서는 해제 순서가 맞물릴 수 있다. 자식의 해제는 부모가 dependents에서 빠지기를 기다리고(`fiber.ts:449-451`), 부모는 `Promise.all`로 자식 해제가 끝난 뒤에야 `committed`를 놓는다(`fiber.ts:453-469`). 다만 이 구성이 기동 순서상 성립하는지는 확인하지 못했다.

## 7. X 설계 함의 [제안]

1. scope 한 개는 활성 Cordis fiber 한 개에 대응시킨다. X 레지스트리는 scope id에서 현재 fiber(없으면 없음)로 가는 표를 관리한다. 켜기는 `ctx.plugin`, 끄기는 `dispose`, 설정 변경은 `update`, 다시 켜기는 새 `ctx.plugin`이다. 해제된 fiber는 다시 쓰지 않는다.
2. 턴 경계 적용은 X의 몫이다. Cordis의 dispose, `ctx.plugin`, `update`는 호출 즉시 실행되며 턴 경계 게이팅이 없다(`arch-1.md §2`). `architecture/layers/spec.md:63`의 "켜기와 끄기는 턴 경계에서 적용된다"는 X가 큐로 구현해야 한다.
3. 실행 세대 토큰: scope를 켤 때마다 generation 값을 만들고, X 래퍼가 등록과 핸들러 실행 때 generation을 대조한다. 옛 closure가 새 세대에 등록하는 일을 막는다. Cordis에는 세대 구분이 없다(§5).
4. 취소 신호: Cordis에는 취소 토큰이 없다. `foundation-plan.md §1` 행 1의 로컬 `CancelScope` 타입을 X 핸들러 인자로 넘기고, scope 해제 때 신호를 보낸다. 신호를 받은 핸들러가 멈추는 책임은 핸들러에 있다.
5. 등록 가드: X 래퍼의 `on` 계열은 `fiber.uid !== null`과 `fiber.state === FiberState.ACTIVE`를 확인한 뒤 등록하고, 등록 해제 함수를 X가 추적한다. 상태 전이는 `internal/status` 이벤트로 관찰할 수 있다(`fiber.ts:358`). `FiberState`는 `const enum`이다(`fiber.ts:78`). X가 이를 import해 쓰는 경로는 실행하지 않아 [미확인]이다.
6. 실패 처리: `await fiber`의 오류를 X 상태 FAILED로 노출하고, 재시도는 `update()`로 한다. FAILED fiber에 `restart()`를 쓰지 않는다(§3.3).
7. 해제 순서: 공급 서비스의 소비자는 먼저 내려간다는 순서를 X의 서비스 계약 문서에 적는다. 한 scope 안의 정리 순서가 중요하면 한 effect로 묶는다(§4.2).
8. 자동 토글: 주입 누락으로 생기는 PENDING과 명시 끄기로 생기는 DISPOSED를 X 상태에서 구분해 보여준다. 둘 다 "비활성"으로 보이지만 리스너 생존 조건이 다르다(§5).
9. 소비자 재시작 연쇄: L2 능력(공급자)을 끄면 그 능력을 주입받는 L3 그룹(소비자)도 해제된다. `architecture/layers/spec.md:60`은 L3가 능력을 F3 정의와 Cordis 주입으로 쓴다고 적는다. 이 설계는 연쇄 해제를 받아들인다는 뜻이므로, 능력 해제 때 그룹이 함께 내려간다는 동작을 명시해야 한다.

## 8. 미결 사항

- [미결] X scope 상태를 Cordis 상태(PENDING, UNLOADING 등)와 맞출지, X 상태(활성, 보류, 해제 중, 해제됨, 실패)로 줄일지.
- [미결] 취소 신호의 범위(턴, scope, 프로세스)와 주입 방식.
- [미결] 실행 세대 토큰과 등록 가드를 X 래퍼에 둘지, Cordis 판본 교체(upstream 변경 확인) 뒤로 미룰지.
- [미결] 능력 해제 때 그룹을 함께 내리는 연쇄를 제품 동작으로 받아들일지.
