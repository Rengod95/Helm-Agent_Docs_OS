# L3-1 조사: L1-g 백그라운드 위임의 호출 인터페이스와 학습 검토 포크

- 질문: L1-g 백그라운드 위임의 호출 인터페이스(F 서비스 키와 시그니처, requestId 멱등, 완료 통지 경로, 도구 허용목록, 프롬프트 캐시 접두 공유, 부모 중단 전파)가 `GroupApi.delegate`와 학습 검토 포크에 충분한가.
- 조사일: 2026-10-21. 저장소 `/home/user/projects/helm/code/helm`, 브랜치 `xeon/foundation`.
- 1차 자료: pi 소스 `~/projects/_ref/pi-src`, 커밋 `cdaf6c227d4718a72b59ccd02152c9614df44cfc`(2026-10-11). 아래 `durable spec`은 `packages/durable/docs/spec.md`의 줄 번호다.

## 1. 결론

- 판정: 현재 계약으로는 충분하지 않다. 다섯 가지 이유가 있다.
  1. `GroupApi.delegate`는 없다. F의 `ScopeApi`(`F/extensions/spec.md` §3.2)와 `ADR-0007-ext-points.md:142-155`의 `GroupApi`에 위임 연산이 없다.
  2. 위임 생성 연산 `LoopHandle.spawn`은 `drive` 임대 안에서만 쓴다(`F/extensions/spec.md:286-293`, §4.6 `:772`). 학습 그룹은 `drive`를 쓰지 않으므로 호출 경로가 없다.
  3. 에이전트 서비스 키가 없다. `F/capabilities/spec.md`에 해당 키가 없고 `L1.agents.spec`도 아직 없다(`docs/xeon/L1/` 디렉터리 부재 확인).
  4. `requestId` 기본값(`${leaseId}:${순번}`, `F/extensions/spec.md:775`)은 임대가 있을 때만 생긴다. 학습 그룹의 위임 호출에는 멱등 키가 자동으로 붙지 않는다.
  5. `on` 핸들러에서 위임을 직접 시작하면 F §4.3(`:743-749`)의 재생 계약을 어긴다. 허용된 외부 효과는 `post`, `commit`, `record` 셋뿐이다.
- [결정] 학습 그룹은 `drive`를 쓰지 않고, 검토 포크는 L1-g 백그라운드 위임으로 돈다(`F/extensions/spec.md:771`, `_research/decisions-log.md` 20행 메모).
- 완료 통지는 `post`의 `kind: "user"`로 넣으면 사용자 발화처럼 대화에 섞인다. `kind: "context"`로 넣으면 섞임을 피할 수 있다(§3.3).
- 프롬프트 캐시 접두 공유는 조건부로 가능하다. 도구 배열이 부모와 달라지면 공유가 깨진다(§3.6).
- 부모 중단 전파는 설계 문장과 pi 정본이 어긋난다. 백그라운드 위임은 durable의 경계이므로 부모의 abort가 자동으로 전파되지 않는다(§3.7).

## 3. 항목별 판정

### 3.1 호출 인터페이스(서비스 키와 시그니처)

- 서비스 호출 경로는 있다. `ScopeApi.capability<Api>(key: ServiceKey<Api>): Api`(`F/extensions/spec.md:344`), `ServiceKey`는 브랜드 토큰이다(`F/capabilities/spec.md:282-289`).
- 위임 시그니처는 F에 없다. `SpawnSpec{agent, task, requestId?, background?}`(`F/extensions/spec.md:274-280`)와 `SpawnOutcome{childThreadId, status: "completed"|"aborted"|"error", answer?}`(`:282-287`)는 `LoopHandle`(`:286-293`)에만 있고, `drive` 임대에서만 얻는다.
- `SpawnOutcome.status`에는 접수 상태가 없다. `background: true`로 호출해도 반환 타입은 완료 결과를 가정한다. 시그니처가 백그라운드 의미를 나타내지 못한다.
- `ExtensionManifest`에는 `tasks`, `delegate`, `background` 필드가 없다(`F/extensions/spec.md` §3.1). 그룹이 백그라운드 태스크를 선언하는 경로도 없다.
- 판정: 미달. 학습 그룹에는 호출 경로가 없다.
- [제안] F에 `agents` 능력과 서비스 키를 둔다. 초안:

```ts
// 제안 초안. F.capabilities(키)와 F.extensions(호출 타입)에 나눠 둔다
interface AgentsApi {
  delegate(spec: DelegateSpec, ctx: { readonly signal: AbortSignal }): Promise<DelegateReceipt>;
}
interface DelegateSpec {
  readonly agent: string;                       // L1.agents 정의 이름
  readonly task: string;
  readonly requestId: string;                   // 필수. 부모 대화 범위 멱등 키(1~64자)
  readonly background: boolean;
  readonly toolPolicy?: { readonly allow?: readonly string[]; readonly deny?: readonly string[] };
}
interface DelegateReceipt {
  readonly childThreadId: ThreadId;
  readonly status: "accepted" | "duplicate";    // 백그라운드 접수와 멱등 재호출을 구분
}
```

- [제안] `SpawnSpec`/`SpawnOutcome`은 `drive` 전용으로 두고, 학습 그룹은 `AgentsApi`를 쓴다.

### 3.2 requestId 멱등

- F `post`: `PostOptions.requestId`는 필수이고 대화 범위 멱등 키다(`F/extensions/spec.md:224-228`, §4.4 `:751-760`).
- F `SpawnSpec.requestId`는 선택이다(`:278`). 기본값 `${leaseId}:${순번}`은 임대 안에서만 만든다(`:775`). 학습 그룹은 임대가 없으므로 기본값이 없다.
- durable: 대화 안에서 `requestId`는 쓰기 전에 중복을 거른다. 같은 키를 다른 종류 제출에 쓰면 거부한다(durable spec `2300`).
durable은 자식 생성의 중복을 소유 간선 검색으로 막는다. `tx.scanConversations({ ownerTaskId })`로 기존 자식을 찾고, 없을 때만 만든다. `requestId`는 자식에게 보내는 제출에만 쓰며, 그 키는 `subagent:${api.taskId}`다(durable spec `3202-3266` 예제). 제공자 호출 ID는 세션 안에서 유일하지 않으므로 키로 쓰지 않는다(`3207`).
- `architecture/runtime-flow/design.md:241`의 "자식 제출의 requestId는 부모에서 파생해 재개 때 중복 생성을 막는다"는 부정확하다. 중복 생성은 소유 간선 검색이 막고, `requestId`는 자식에게 보내는 제출의 중복을 막는다. [제안] 문장을 고친다.
- 판정: 조건부 충분. 키 파생 규칙(태스크 id 또는 턴 id와 호출 종류의 조합)과 소유 간선 검색을 F 계약에 넣으면 충분하다.

### 3.3 완료 통지 경로와 대화 섞임

- 계획 원문: "완료 결과를 합성 입력으로 부모 inbox에 넣습니다"(`_research/layer-plan-v2.json:879`, `_research/item-catalog.md:223`). 출처는 OpenCode의 completion 통지다(`items-from-refs.md:139`).
- durable 정본: reporter 태스크가 결과를 부모에 `whenBusy: "followUp"` 입력으로 게시한다(durable spec `3261-3266`). 입력 제출은 사용자 메시지 항목(`pi.user`)을 만든다(durable spec `902-903`). 그러므로 durable 방식의 완료 통지는 사용자 메시지로 대화에 섞인다.
- durable의 `write` 제출은 실행을 시작하지 않는다(durable spec `906`, 표 `2291`). 즉 기록만 하고 턴은 시작하지 않는 모드가 있다.
- F 쪽: `PostItem`의 `kind: "user"`는 사용자 메시지이고, `kind: "context"`는 `XeonCustomMessage`다(`F/extensions/spec.md:211-217`, `F/conversation/spec.md:309-316`). `details`는 모델에 보내지 않는다(`F/conversation/spec.md:315`). `display`는 UI 표시만 정한다.
- F `post`의 `when`(steer, followUp, next)은 모델 호출을 일으키는 입력으로 정의되어 있다(`F/extensions/spec.md` §4.4). 유휴 상태에서 `post`가 턴을 시작하는지, 턴 없이 기록만 하는 모드가 있는지는 F에 없다. [미결]
- 판정: 완료 통지는 `kind: "context"`로 보내야 사용자 발화와 구분된다. 다만 `context`는 모델 컨텍스트에 들어가므로 다음 모델 호출에 영향을 준다. 통지가 새 턴을 시작할지는 [미결]이다.
- [제안] `customType: "grp.learning.review.result"`, `display: true`, `details`에 제안 목록을 넣는다. 승인 대기열과 연결한다.

### 3.4 on 핸들러 안에서 시작할 때의 재생 계약

- F §4.3(`F/extensions/spec.md:743-749`): on 핸들러는 다시 실행해도 되는 질의다. 커밋 전에 프로세스가 끝나면 같은 지점이 다시 발화한다. 외부 효과는 `post`(멱등 키 필수), `commit`, `record`로만 낸다.
- `architecture/runtime-flow/design.md` §5: "`on` 핸들러는 외부 효과를 내지 않는다."
- `HandlerContext`(`F/extensions/spec.md:187-193`)는 `scopeId`, `state`, `threadId`, `signal`만 준다. `taskId`, 메모, 커밋 연산이 없다. 그래서 on 핸들러 안에서 소유 간선을 검색하거나 첫 기록자 결정을 저장할 수단이 없다.
- durable 훅도 같은 규칙을 쓴다. 훅 API는 `taskId`, `models`, `memo`만 준다(durable spec `2663-2672` 근처 `HookApi`). 태스크를 만들 수 없다. 훅은 커밋 전에 실행되고 커밋 전 크래시 뒤 다시 실행될 수 있다(durable spec `2645`).
- 판정: on 핸들러가 위임을 직접 시작하면 재생 계약을 어긴다. 근거는 F §4.3이다.
- [제안] 경로: on 핸들러는 `record("grp.learning.review.requested", subject, {requestId})`나 `post`로 요청만 커밋한다. 실제 위임은 L1-g 워커가 요청 키마다 한 번만 시작한다. 이 워커를 누가 등록하는지 F가 정해야 한다. 학습 그룹에는 `drive`가 없으므로 등록 경로가 필요하다 [미결].

### 3.5 도구 허용목록

- 계획의 1차 항목은 "자식별 도구 차단 목록"이다(`_research/layer-plan-v2.json:858`, `_research/items-from-refs.md:136`). 질문의 "허용목록"과 다르다. [미결] 차단과 허용 중 하나를 정한다.
- durable은 둘 다 준다. 도구 필터가 배열이면 허용목록이고, `{ remove }`면 차단 목록이다(durable spec `442`, 해석 규칙 `2560-2572`).
- durable 자식은 부모의 agent를 복사해 시작하고, 재귀를 막기 위해 확장을 제거해 도구를 뺀다(durable spec `3226-3229`, `3286`).
- 실행 시점 검사: 요청에 제공되지 않은 도구 호출은 `tool_unavailable`로 거부한다(durable spec `3142`). 차단은 제공 목록과 실행 검사 둘 다로 건다.
- F: 자식 도구 필터를 나타내는 타입이 없다. 도구 목록은 서브에이전트 정의 파일에 들어가는데, 그 파일은 2차 항목이다(`_research/layer-plan-v2.json:886`). 1차 차단 목록을 담을 자리가 F에 없다.
- 판정: 미달. [제안] §3.1의 `DelegateSpec.toolPolicy`와 L1-d의 실행 시 검사를 짝으로 둔다.

### 3.6 프롬프트 캐시 접두 공유

- Anthropic 공식 문서: 캐시 접두는 `tools`, `system`, `messages` 순서로 만들어진다. 도구 정의(이름, 설명, 매개변수)를 바꾸면 전체 캐시가 무효화된다. 변경은 그 층과 그 아래 모든 층을 무효화한다.
- pi-ai Anthropic 구현: 시스템 블록(`packages/ai/src/api/anthropic-messages.ts:1165-1190`), 마지막 user·system 메시지(`:1483-1505`), 마지막 도구 정의(`:1608`)에 `cache_control`을 붙인다. 도구 배열이 다르면 마지막 도구의 표식 위치와 접두 전체가 달라진다.
- durable 자식은 부모 도구를 복사한 뒤 확장을 빼므로(durable spec `3226-3229`) 기본 설정에서도 도구 배열이 부모와 다르다. 메시지 접두를 공유하려면 부모 이력에서 `fork`해야 한다(durable spec `5085`). `createConversation`은 빈 이력으로 시작한다.
- 학습 검토 포크가 같은 접두를 쓰려면 네 조건이 모두 필요하다.
  1. 모델이 같다.
  2. 도구 배열이 부모와 같다(순서 포함). 차단을 도구 배열 변경으로 걸면 안 된다.
  3. 시스템 프롬프트가 같다. 검토 지시는 마지막 user 메시지로 넣는다.
  4. 메시지 접두가 같다. 부모 이력의 특정 항목에서 `fork`한다.
- [제안] 도구 제한은 실행 시 검사로 건다. `first` 지점 `tool_call`에서 `ctx.threadId`로 검토 포크만 거부한다. 다만 그룹 핸들러가 어느 대화에 적용되는지 F에 규칙이 없다 [미결].
- 판정: 조건부 충분. `layer-plan-v2.json:1525`의 "같은 프롬프트 캐시 접두를 써서 비용을 줄입니다"는 네 조건을 적지 않았다. [제안] 학습 검토 포크 항목에 네 조건을 명시한다.
- [미확인] 캐시 TTL, 최소 접두 길이, 실제 비용 절감 폭.

### 3.7 부모 중단 전파

- `architecture/runtime-flow/design.md:241`: "부모가 중단되면 abort가 소유 트리를 따라 자식에게 전파되고, 자식은 부모보다 오래 살지 않는다." 이 문장은 전경 자식에만 맞는다.
- durable 정본: 소유 작업의 중단은 아래로 전파된다(durable spec `2156-2200` §5.5). 그러나 백그라운드 태스크는 경계다. 일반 순회는 그 태스크와 아래 소유 트리를 건너뛴다(durable spec `2006`). 백그라운드는 대화가 소유한 태스크에만 허용하고, 자식 태스크에는 허용하지 않는다(§5.5).
- durable에서 백그라운드 위임은 앵커 태스크, 자식 대화, reporter 세 구성요소로 이뤄진다(durable spec `3248-3266`).
- 따라서 학습 검토 포크를 백그라운드로 두면 부모 abort와 부모 유휴 판정에서 빠진다. 취소하려면 명시적으로 `background` 경계를 넘는 호출이 필요하다.
- F 쪽 미정: 학습 그룹을 끄면 진행 중인 검토 포크를 어떻게 하는지 정의가 없다. `F/extensions/spec.md` §4.5(761-767)의 정리 순서(on 제외, drive 반납, onDispose)에는 자식 작업 정리가 없다 [미결].
- 프로세스가 중단되면 durable의 `close()`는 기록 없이 모든 실행을 멈추고, 다음 열기에서 재개한다(durable spec 2000-2030 범위). reporter는 요청 키로 중복 게시를 거른다(`3261-3266`).
- 판정: 설계 문장을 나눠 쓴다. [제안] "전경 위임은 부모 abort가 전파되고, 백그라운드 위임은 명시 취소만 전파된다."

### 3.8 `GroupApi.delegate` 전제 확인

- `GroupApi.delegate`는 어느 문서에도 없다. `ADR-0007-ext-points.md:142-155`의 `GroupApi`는 `on`, `post`, `drive`, `commit`만 가진다.
- `delegate`라는 말은 `F/wire-settings/spec.md:599`(`thread.locked`의 옵션 값)와 `architecture/runtime-flow/design.md` 흐름도의 프로세스 위임 노드에만 나온다. `engineering/*/guide.md`의 `GroupApi<HelmState>`는 예시 코드다.
- 따라서 "GroupApi.delegate가 충분하다"는 전제는 성립하지 않는다. §3.1의 `AgentsApi` 제안으로 대체해야 한다.
