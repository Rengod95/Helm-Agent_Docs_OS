- 대상: F 계약(`contracts`)이 재노출할 이름의 형태 확인
- 근거 계획: `_research/foundation-plan.md` §2 스택, `_research/packages.md` §1.1·§4.1·§5·§7
- 성격: 조사 결과. 정본이 아니며 인용용이다.

## 2. 결론

1. 요청된 10개 이름은 pi-ai 1.3.0과 pi-agent-core 1.3.0에서 1.1.0과 같은 형태로 내보내진다. 1.1.0과 실제로 다른 점은 세 가지다.
   - `ToolCall.argumentsError` 필드 추가
   - `AssistantMessageFrame` 재수출 제거
   - agent-core가 pi-ai에 거는 의존 범위가 `^1.1.0`에서 `1.3.0` 정확 고정으로 바뀜
2. TypeBox는 pi-ai와 agent-core가 `1.3.27`에 정확히 묶여 있다. 1.4.2와 `TSchema`, `Static` 선언은 내용이 같다. 버전 선택은 [미결]이다(§7).
3. MCP client 2.3.1은 `input_required` 결과 타입 `InputRequiredResult`, 판별 함수 `isInputRequiredResult`, 래퍼 `withInputRequired`를 공개 export한다. 주석에 나오는 `inputRequired()` 빌더는 client 공개 진입점에 없다.

## 5. 이름별 구현 메모

### 5.1 pi-ai 1.3.0

- 진입점: `dist/index.d.ts:24`이 `./types.ts`를 `export *`로 재수출한다. 위 이름 대부분이 여기서 나온다. `dist/index.d.ts:1-2`는 TypeBox의 `Static`, `TSchema`, `Type`을 재수출한다.
- `Message`는 4종이다.
  - `SystemMessage`: `role: "system"`, `content`, `sections?`, `toolsAdded?`, `toolsRemoved?`
  - `UserMessage`: `role: "user"`
  - `AssistantMessage`: `role: "assistant"`
  - `ToolResultMessage`: `role: "toolResult"`
- `ToolResultMessage`는 `IsJsonCompatible<TDetails>` 조건부 타입이다. `TDetails`가 JSON 호환이 아니면 `never`가 된다(`dist/types.d.ts:414`). F가 제네릭 인자를 쓰면 이 조건을 확인한다 [제안].
- `StopReason`은 `"pending" | "stop" | "length" | "toolUse" | "error" | "aborted" | "deferred"`다(`dist/types.d.ts:301`).
  - `done` 이벤트의 `reason`은 `Extract<StopReason, "stop" | "length" | "toolUse" | "deferred">`로 좁혀진다.
  - `error` 이벤트의 `reason`은 `"aborted" | "error"`다.
  - `AssistantMessage.deferred?: DeferredHandle`가 있다(`dist/types.d.ts:362` 이후). `DeferredHandle`(`dist/types.d.ts:319`)은 `provider`, `modelId`, `api`, `id`, `expiresAt?`, `pollAfterMs?`, `data?`로 구성된다. 실제 동작은 [미확인]이다.
- `AssistantMessageEvent`는 12종이다: `start`, `text_start`, `text_delta`, `text_end`, `thinking_start`, `thinking_delta`, `thinking_end`, `toolcall_start`, `toolcall_delta`, `toolcall_end`, `done`, `error`.
- `ModelThinkingLevel`은 `off | minimal | low | medium | high | xhigh | max` 7종이다(`dist/providers/model-schema.d.ts:8`).
  - pi-ai는 같은 모듈에서 `ThinkingLevel`도 재수출한다(`dist/types.d.ts:17`). 이 값은 `off`가 없는 6종이다(`dist/providers/model-schema.d.ts:79`).
  - agent-core의 `ThinkingLevel`(`agent/dist/types.d.ts:300`)은 `off`를 포함한 7종이다. 같은 이름에 다른 집합이다.
- `Tool`: `name`, `description`, `parameters: TSchema`, `constrainedSampling?` (`dist/types.d.ts:522-527`).
- `Context`: `systemPrompt?`, `messages`, `tools?`(`dist/types.d.ts:537`). 입력용 타입이다. provider 쪽은 `TranscriptContext`를 받는다(`dist/types.d.ts:549`). F는 이 구분을 주석으로 남긴다 [제안].

### 5.2 pi-agent-core 1.3.0

- 진입점: `agent/dist/index.d.ts:1-5`가 `agent`, `agent-loop`, `proxy`, `stream-fn`, `types`를 재수출한다. pi-ai의 타입은 재수출하지 않는다. `agent/dist/types.d.ts:1`은 pi-ai에서 타입을 가져오기만 한다. 따라서 F는 `Message`, `StopReason` 같은 이름을 pi-ai에서 직접 가져와야 한다.
- `AgentTool`은 pi-ai `Tool`을 확장한다(`agent/dist/types.d.ts:409`). 추가 필드는 `label`, `prepareArguments?`, `outputSchema?`, `execute`, `replay?`, `executionMode?`다.
- `replay?: "never" | "safe"`는 `agent/dist/types.d.ts:428`이다. 바로 위 주석은 "Recovery policy for an effect whose durable intent exists but whose outcome is unknown."이다(`agent/dist/types.d.ts:427`). F2의 효과 재생 정책 필드로 쓸 수 있다.
- `AgentEvent`는 10종이다(`agent/dist/types.d.ts:452`): `agent_start`, `agent_end`, `turn_start`, `turn_end`, `message_start`, `message_update`, `message_end`, `tool_execution_start`, `tool_execution_update`, `tool_execution_end`. `tool_execution_end`에는 `durationMs?`가 있다.
- `CustomAgentMessages`는 빈 인터페이스다(`agent/dist/types.d.ts:315`). `AgentMessage = Message | CustomAgentMessages[keyof CustomAgentMessages]`다(`agent/dist/types.d.ts:322`). 확장은 선언 병합으로 한다.
  - 주석 예시는 `declare module "@mariozechner/agent"`라는 옛 패키지 이름을 쓴다(`agent/dist/types.d.ts:307`, 원문 `agent/src/types.ts:357`). F에서는 `declare module "@earendil-works/pi-agent-core"`로 써야 한다 [제안].

### 5.3 TypeBox

- pi-ai 1.3.0과 agent-core 1.3.0은 모두 `"typebox": "1.3.27"`로 정확 고정한다.
- pi-ai `dist` 안의 import 구문은 `from "typebox"` 10건, `"typebox/compile"` 1건, `"typebox/value"` 1건이다.
- typebox 1.3.27 루트:
  - `build/index.d.mts:6`: `export * as Type from './typebox.mjs'`. 따라서 `import { Type } from "typebox"`의 `Type`은 네임스페이스 객체다.
  - `TSchema`: `build/type/types/schema.d.mts:1`
  - `Static`: `build/type/types/static.d.mts:45`
  - `Enum`, `TEnum`: `build/typebox.d.mts:40`
  - 하위 경로: `./value`, `./compile`, `./schema`, `./type`, `./error`, `./format`, `./guard`, `./system` (`package.json` exports)
- typebox 1.4.2는 루트 구조가 같다. `build/type/types/schema.d.mts`와 `build/type/types/static.d.mts`는 1.3.27과 내용이 같다. 1.4.2는 메타 스키마(`schema/meta/draft_*`), `guard/unicode`, `system/memory/deep` 등 모듈을 더 가진다.
- 판단: F가 1.4.2를 쓰면 pi-ai가 끌어오는 1.3.27과 두 벌이 설치될 수 있다. 설치 중복 여부와 런타임 호환은 [미확인]이다.

### 5.4 MCP client 2.3.1 (`input_required`)

- 공개 export: `dist/index.d.mts:3646`의 export 목록에 `InputRequiredResult`, `InputRequiredOptions`, `isInputRequiredResult`, `withInputRequired`, `ResultTypeMap`이 있다. 런타임 export 목록(`dist/index.mjs:5887`)에도 `isInputRequiredResult`, `withInputRequired`가 있다.
- `InputRequiredResult` 정의는 `dist/index-J2FaQ-KY.d.cts:708-713`다.
  - `extends Result`
  - `resultType: 'input_required'`(709행). 판별자다.
  - `inputRequests?: InputRequests`(711행)
  - `requestState?: string`(713행)
  - 두 필드 중 최소 하나는 있어야 한다는 규칙은 주석 695행에 있다.
- 판별 함수: `isInputRequiredResult(value: unknown): value is InputRequiredResult` (`dist/index-J2FaQ-KY.d.cts:1551`).
- 래퍼: `withInputRequired(schema)`는 결과 스키마를 `InferOutput<S> | InputRequiredResult`로 감싼다 (`dist/index-J2FaQ-KY.d.cts:1324`).
- 옵션:
  - 클라이언트 옵션 `inputRequired?: InputRequiredOptions`(`dist/index.d.mts:1965`). `InputRequiredOptions` 정의는 `dist/index-J2FaQ-KY.d.cts:1330`이다.
  - 요청 옵션 `allowInputRequired: true`는 수동 모드에서 쓴다(`dist/index-J2FaQ-KY.d.cts:1314-1317`, 요청 옵션 필드는 1883행).
- 빌더의 불일치:
  - d.ts 주석은 "`inputRequired()` builder"를 말한다(`dist/index-J2FaQ-KY.d.cts:686`, `1545`).
  - 소스맵에 든 원문(`core-internal/src/shared/inputRequired.ts:132`)은 `export const inputRequired: InputRequiredBuilder`를 정의한다.
  - 그러나 client의 공개 d.ts(`dist/index.d.mts`)와 런타임 export 목록(`dist/index.mjs:5887`)에는 `inputRequired`가 없다.
  - 같은 주석에 손으로 만든 객체 리터럴도 합법이라고 적혀 있다(`dist/index-J2FaQ-KY.d.cts:686-687`). 빌더 export 여부는 서버 패키지에서 확인해야 하므로 [미확인]이다.
- 판별자 위치: 주석에 따르면 `resultType`은 핸들러가 쓰는 값이고, 완료된 결과에서는 소비자 쪽에 보이지 않는다(`dist/index-J2FaQ-KY.d.cts:690-692`). F의 결과 상태 유니온에서 `input_required` 변형을 어느 층에 둘지는 설계 사항이다 [제안].
- 의존: `@modelcontextprotocol/client` 2.3.1은 `@modelcontextprotocol/core` 2.3.1을 의존한다(`package.json` dependencies). client d.ts 안에 해당 정의가 번들되어 있어 이 조사에서는 client 선언만으로 이름을 확인했다. core의 export 목록은 받지 않았다 [미확인].

## 6. F 계약에 대한 제안

1. 정확 고정 [제안]: `@earendil-works/pi-ai` 1.3.0, `@earendil-works/pi-agent-core` 1.3.0, `typebox` 1.3.27, `@modelcontextprotocol/client` 2.3.1.
2. 재노출 목록 [제안]: §3 표의 이름에 `ToolCall`, `Static`, `TSchema`, `Type`을 더한다. `AssistantMessageFrame`은 뺀다.
3. 이름 충돌 [제안]: `ThinkingLevel`은 F에서 재노출하지 않는다. `ModelThinkingLevel`만 쓴다. agent-core의 `ThinkingLevel`(7종)과 pi-ai의 `ThinkingLevel`(6종)은 집합이 다르다.
4. 도구 호출 [제안]: F의 도구 호출 스키마에 `argumentsError`를 포함한다.
5. 확장 선언 [제안]: agent-core의 `CustomAgentMessages` 선언 병합 대상은 `@earendil-works/pi-agent-core`로 한다.
6. 재생 정책 [제안]: `AgentTool.replay`의 값 `"never" | "safe"`를 F2 효과 재생 정책의 값 집합으로 쓴다. 두 값 외에 다른 값이 필요하면 F에서 따로 정의한다.
7. 입력 타입 [제안]: `Context`(입력)와 `TranscriptContext`(provider 입력)의 구분을 F 주석에 남긴다.
8. 줄 번호 [제안]: packages.md §4.1의 줄 번호는 1.1.0 기준이다. 1.3.0 기준으로 고칠 때 §4의 차이 표를 쓴다.

## 7. 미결 사항

- [미결] TypeBox 버전. 계획서 §2는 "TypeBox 1.4"로 적었다. pi-ai와 agent-core가 1.3.27로 정확 고정되어 있어 1.4.2를 쓰면 두 벌이 생길 수 있다. 선언은 같으므로 1.3.27 고정을 [제안]한다. 사용자 확인이 필요하다.
- [미결] `inputRequired()` 빌더를 F가 쓸 필요가 있는지. 서버 쪽에서 `input_required` 결과를 만들 때 필요하면 `@modelcontextprotocol/server` 2.3.1의 export를 확인한다.

## 8. [미확인] 목록

- 런타임 동작 전체: 실행하지 않았다. Bun 1.4에서 pi-ai 1.3.0이 로드되는지 확인하지 않았다. pi-ai의 `engines`는 `node >=22.19.0`이다.
- pi-ai 1.3.0 provider 구현: `argumentsError`를 채우는 조건, `deferred` 재조회 흐름은 선언과 주석만 봤다.
- npm 배포본과 Git 태그의 일치: 소스맵 원문을 1차 자료로 썼고 태그는 대조하지 않았다.
- `@modelcontextprotocol/core` 2.3.1과 `@modelcontextprotocol/server` 2.3.1의 export 목록.
- typebox 1.4.2의 런타임 호환. 선언만 비교했다.
- pi-ai CHANGELOG 원문. 이번에 받지 않았고 packages.md §7의 기재를 따랐다.
