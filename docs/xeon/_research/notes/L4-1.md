# L4-1 조사: pi-tui의 bun build --compile 단일 바이너리 사용 가능성

- 대상 질문: `@earendil-works/pi-tui`를 `bun build --compile` 단일 바이너리에서 쓸 수 있는가. 확인 항목은 npm 최신 버전과 pi-ai·pi-agent-core 1.3.0의 정렬, native `.node` 애드온(클립보드, 키 modifier)의 필수 여부와 실패 시 동작, Bun 동작 근거, compile 바이너리에서 `.node`를 임베드하고 로드하는 방법이다.
- 근거 계획: `_research/foundation-plan.md` §1(런타임 Bun 1.4), §2(스택: pi-ai·pi-agent-core 1.3.0 정확 고정), §7(사이드카 단일 바이너리 크기와 Windows 서명은 L4 plan에서 다룬다).
- 근거 결정: `_research/decisions-log.md` 19행(다른 층도 패키지 사용·포크를 적극 채택), 25행(런타임 Bun 1.4).
- 1차 자료:
  - pi 소스 `~/projects/_ref/pi-src`(HEAD `cdaf6c2`). 읽기만 했다. 참조 트리의 `packages/tui/package.json`은 버전 1.1.0이다(`:3`).
  - npm 레지스트리: `https://registry.npmjs.org/@earendil-works/pi-tui/latest`, 같은 호스트의 `pi-ai`, `pi-agent-core` 메타데이터와 버전별 매니페스트. 1.3.0 tarball은 scratchpad에 내려받아 목록과 `dist/`, native 바이너리 해시만 확인했다.
  - Bun 공식 문서: `https://bun.com/docs/bundler/executables`(페이지 헤더는 Bun v1.4.3). 절은 "Embed N-API Addons", "Embed assets & files", "Embed directories", "Supported targets"다.
- 성격: 조사 결과. 정본이 아니며 인용용이다. 코드는 실행하지 않았다. 소스 읽기, 메타데이터 조회, 바이너리 헤더 읽기(`readelf -d`, `readelf --dyn-syms`)만 했다.
- 표지: [결정] 사용자 결정 인용, [제안] 작성자 설계 선택, [가정] 확인하지 않은 전제, [미결] 사용자 확인 필요, [미확인] 확인하지 못한 것.

## 0. 결론

1. 단일 파일로 실행은 가능하다. 다만 `bun build --compile`은 pi-tui의 `.node` 애드온을 자동으로 담지 않는다. pi-tui 로더가 후보 경로를 계산해 `require`하기 때문이다(§5.1).
2. 애드온은 전부 선택이다. pi-tui 내부 호출처는 `undefined`나 `false`를 받는 폴백을 가지거나 `try/catch`로 감싸져 있다. 애드온이 없어도 pi-tui는 시작하며, 빠지는 기능은 macOS Apple Terminal과 Windows의 Shift+Enter 판별, Windows의 Shift+Tab 판별, 네이티브 클립보드 경로다(§3).
3. 배포 형태는 pi와 같은 사이드카 디렉터리가 현실적이다. `bun build --compile` 결과물 옆에 `native/<os>/prebuilds/<os>-<arch>/`를 두면 후보 4번 경로로 로드된다. pi가 릴리즈에서 쓰는 방식이다(§5.2). [제안] L4 1차 배포는 이 방식을 쓴다.
4. npm `latest`는 세 패키지 모두 1.3.0이다. pi-ai와 pi-agent-core는 1.3.0을 같은 묶음에서 배포했다. 다만 pi-tui는 pi-ai에 의존하지 않으므로 정렬은 버전 번호와 배포 시점의 일치다(§2). [제안] pi-tui를 1.3.0으로 정확 고정한다.
5. [미결] foundation-plan §2 스택 표에 pi-tui 행이 없다. L4 CLI 렌더링 라이브러리를 pi-tui로 할지 아직 정해지지 않았다. 이 결정이 먼저다(§6).
6. [미확인] pi-tui 1.3.0을 Bun 1.4.3 `--compile` 바이너리에서 실행한 증거는 없다. 근거는 pi 자신이 Bun 1.3.14로 pi-tui를 포함한 바이너리를 릴리즈한다는 소스 사실뿐이다(§4).

## 3. native 애드온: 필수 여부와 실패 시 동작

### 3.1 로더 구조

- 아키텍처 게이트: x64와 arm64만 허용한다(`TUI/src/native-platform.ts:29-30`). 다른 아키텍처는 `undefined`다.
- 파일 경로: `native/<os>/prebuilds/<os>-<arch>/<os>-platform[-x11].node`(`native-platform.ts:31-37`).
- 후보 경로 순서(`TUI/src/native-module-path.ts:14-27`):
  1. `resolvePackage("@earendil-works/pi-tui")` 기준 경로. 설치본에서만 성공한다. standalone에서는 던져지고 건너뛴다.
  2. `<모듈 디렉터리>/../<nativePath>`
  3. `<모듈 디렉터리>/<nativePath>`
  4. `dirname(process.execPath)/<nativePath>`
- 로드: 후보를 순서대로 `cjsRequire`하고, 실패는 `try/catch`로 넘어간다. `getText`와 `getImage` 함수가 있어야 성공으로 본다(`native-platform.ts:38-51`). 전부 실패하면 `undefined`를 캐시한다(`:51`).
- 플랫폼별 export:

| 헬퍼 | 소스 | export 함수 |
|---|---|---|
| darwin | `TUI/native/darwin/src/darwin-platform.m:126-130` | isModifierPressed, getText, setText, getImage, getFilePaths |
| win32 | `TUI/native/win32/src/win32-platform.c:235-239` | enableVirtualTerminalInput, isModifierPressed, getText, setText, getImage |
| linux (x11) | `TUI/native/linux/src/linux-platform-x11.c:271-272` | getText, getImage |

- 선택 지점:
  - `getNativePlatformHelper()`는 darwin과 win32에서만 로드한다(`native-platform.ts:55-58`).
  - `getNativeClipboard()`는 linux에서 `DISPLAY`가 없으면 `undefined`다(`:61-64`). 로드 캐시는 실패를 저장하지만 디스플레이 가용성은 호출마다 확인한다(`:25` 주석).
  - linux 헬퍼는 `libxcb.so.1`을 링크 시점에 요구한다. `readelf -d`에서 NEEDED는 이 항목 하나다(linux-x64, linux-arm64 공통). 라이브러리가 없으면 `dlopen` 단계에서 실패하고 로더의 `try/catch`가 잡는다.
- 런타임 심볼: `TUI/native/napi.h:4`는 헬퍼가 Node와 Bun 양쪽의 N-API 함수를 `dlsym(RTLD_DEFAULT, ...)`로 찾는다고 적는다(`napi.h:48-56`). Node 헤더나 링크 의존 없이 빌드된다.

### 3.2 호출처와 폴백

| 기능 | 호출처 | 헬퍼가 없을 때 |
|---|---|---|
| Shift+Enter 판별(Apple Terminal, win32) | `TUI/src/terminal.ts:392-399`, `TUI/src/native-modifiers.ts:5-13` | `isNativeModifierPressed`가 `false`를 돌려준다. 입력은 `\r`(Enter)로 남는다. |
| Shift+Tab 판별(win32) | `TUI/src/terminal.ts:420`(함수), `:219`(호출) | `enableVirtualTerminalInput`이 없으면 VT 입력 설정을 건너뛴다. 주석에 "Shift+Tab won't be distinguishable from Tab"이 적혀 있다. |
| 클립보드 읽기(linux) | `CA/src/utils/clipboard.ts:54-72` | wl-paste, xclip, xsel 순서로 시도한 뒤 네이티브 `getText`를 쓴다. |
| 클립보드 쓰기(linux) | `CA/src/utils/clipboard.ts:87` | 네이티브 `setText`를 건너뛴다. termux-clipboard-set, wl-copy, xclip, xsel 순서로 시도하고, WSL 경로, OSC 52, 오류 순서다(`:81-144`). |
| 클립보드 쓰기(darwin, win32) | `clipboard.ts:87-96` | 네이티브 `setText`를 먼저 쓰고, 실패하면 pbcopy 또는 clip으로 간다. |
| 파일 경로 읽기(darwin) | `clipboard.ts:76-79` | `getFilePaths`가 없으면 `undefined`다. 이 함수에는 `try`가 없다. |
| 이미지 읽기 | `CA/src/utils/clipboard-image.ts:194` | 명령 도구를 먼저 시도한 뒤 네이티브 `getImage`를 쓴다. |

- pi-tui 내부 호출처는 모두 옵셔널 체이닝(`?.`)이나 `try/catch`로 감싸져 있다. 헬퍼가 없어도 pi-tui는 시작한다. 호출처 가운데 coding-agent 쪽 예외는 아래 줄에 적는다.
- 네이티브 전송 실패는 거부(reject)로 전달된다(`native-platform.ts:9-13` 주석). `CA/src/utils/clipboard.ts:76-79`의 `readClipboardFilePaths`는 `try` 없이 `await`한다. 이 함수의 호출측이 오류를 막는지는 [미확인]이다.
- linux 헬퍼는 읽기 전용이다. 쓰기는 명령 도구로만 한다. 따라서 Linux에서 애드온의 실효는 명령 도구가 없을 때의 텍스트·이미지 읽기에 그친다.
- Shift+Enter 판별은 `sequence === "\r"`이고 Apple Terminal 또는 win32일 때만 켜진다(`terminal.ts:392-393`). Linux에서는 애드온과 무관하게 이 경로가 열리지 않는다.

### 3.3 판정

- 필수가 아니다. 애드온이 없어도 pi-tui 전체가 돈다. 빠지는 기능은 (a) Apple Terminal과 Windows의 Shift+Enter, (b) Windows의 Shift+Tab, (c) 네이티브 클립보드 경로다. 클립보드는 대부분 명령 도구로 대체된다.
- 크기는 작다. 참조 트리의 `.node` 파일은 linux-x64 18,008 B, linux-arm64 67,240 B, darwin-arm64 52,024 B, win32-x64 8,704 B다(`ls -l` 결과). 세 파일은 1.3.0과 sha256이 같다. 단일 바이너리 크기에 미치는 영향은 작다.
- [제안] L4 CLI 문서에 애드온을 "있으면 쓰는 선택 기능"으로 적는다. Windows Shift+Tab 판별을 제품 기능으로 정하면 사이드카 배치가 필수가 된다(§6).

## 4. Bun 동작 근거

- pi 자신이 pi-tui를 포함한 Bun 바이너리를 릴리즈한다. `CA/package.json:44`의 `build:binary`가 `bun build --compile ... ./dist/bun/cli.js`를 쓴다. `scripts/build-binaries.sh:133-135`는 `--external` 없이 빌드하므로 pi-tui는 번들에 들어간다. `CA/src/utils/clipboard.ts:5`가 pi-tui를 import한다.
- pi의 Bun 버전은 1.3.14다(`.github/workflows/build-binaries.yml:44`). Xeon 계획은 Bun 1.4다(`foundation-plan.md` §1 "런타임" 행). 두 버전 차이는 검증 대상이다.
- pi의 x64 타깃은 `bun-<os>-<arch>-baseline`이다(`scripts/build-binaries.sh:119-121`). Bun 1.4 문서는 `-baseline`과 `-modern`을 호환용으로 받으며 같은 바이너리로 해석한다고 쓴다(Supported targets 절).
- Bun 1.4 문서는 musl 타깃(`bun-linux-x64-musl`, `bun-linux-arm64-musl`)을 든다(Supported targets 절). pi 빌드 스크립트는 musl을 쓰지 않는다.
- `TUI/native/linux/README.md:3`은 glibc와 musl 프리빌드를 주장한다. 디렉터리에는 glibc 빌드만 있다(`prebuilds/linux-x64`, `prebuilds/linux-arm64`). musl에서의 로드 동작은 [미확인]이다.
- pi-tui 엔진 선언은 Node만 든다(`TUI/package.json:50-52`, `node >=22.19.0`). Bun은 선언되어 있지 않다. Bun 호환은 pi의 Bun 릴리즈에 기대는 간접 근거다.
- pi 소스는 standalone 바이너리를 `import.meta.url`의 `$bunfs`, `~BUN`, `%7EBUN`으로 식별한다(`CA/src/config.ts:19-22`).
- pi는 wasm을 Bun 임베드로 다룬다. `CA/src/bun/runtime-setup.ts:4`는 "Bun loads .wasm imports as files: embedded in compiled executables"라고 적는다. `.node`는 같은 방식으로 임베드하지 않는다.
- 참고: `docs/design/07-pi-reuse-and-fork.md:131`에 따르면 Happy Agent는 2026-10-10에 pi-tui를 걷어냈다. 이유는 기록에 없다[미확인].
- [미확인] 실제 실행, 즉 pi-tui 1.3.0을 Bun 1.4.3 `--compile` 바이너리에서 띄우고 입력과 렌더링을 확인하는 일은 하지 않았다. §7의 절차로 검증해야 한다.

## 5. compile 바이너리의 `.node` 임베드와 로드

### 5.1 자동 포함이 되지 않는 이유

- Bun 문서 "Embed N-API Addons"는 `require("./addon.node")`처럼 파일 경로를 문자열 리터럴로 `require`하는 예를 든다. 계산된 경로를 여는 경우는 문서에 없다[미확인].
- pi-tui는 후보 경로를 계산해 `cjsRequire(modulePath)`로 로드한다(`TUI/src/native-platform.ts:40-42`). 경로가 변수이므로 번들러가 `.node`를 찾지 못한다.
- 따라서 `bun build --compile`만 실행하면 애드온이 들어가지 않는다. 바이너리는 애드온 없이 폴백으로 동작한다. (소스 독해에 따른 판단이다. 실행 검증은 [미확인]이다.)

### 5.2 방법 A: 사이드카 디렉터리(pi 방식, [제안] 1차 배포안)

- 배치: 바이너리 옆에 `native/<os>/prebuilds/<os>-<arch>/`를 둔다. pi는 `scripts/build-binaries.sh:155-159`에서 대상 아키텍처 디렉터리만 복사한다. 아카이브는 플랫폼 디렉터리 단위다.
- 로드 경로: 후보 4번 `dirname(process.execPath)/native/...`(`native-module-path.ts:27`). 테스트가 이 후보를 명시적으로 검증한다(`TUI/test/native-module-path.test.ts:26-44`).
- [가정] Bun 1.4 standalone에서 `process.execPath`는 바이너리 경로다. Bun 문서에는 이 항목이 없다. pi의 릴리즈 배치가 이 가정에 기댄다. 실행 검증은 [미확인]이다.
- 장점: pi 릴리즈와 같은 구조다. 애드온이 디스크 파일이므로 `dlopen`이 확실하다. 추가 크기는 작다(§3.3).
- 단점: 배포물이 여러 파일이다. 설치와 업데이트 때 바이너리와 `native/`를 함께 옮겨야 한다. macOS 공증에서 이 `.node` 파일의 서명 요구는 [미확인]이다. Windows 서명은 foundation-plan §7이 L4 plan으로 넘겼다.

### 5.3 방법 B: 바이너리 내부 임베드(미채택, 조건부)

- Bun 문서 방법은 셋이다. `import addon from "./x.node" with { type: "file" }`, `--asset ./native`(디렉터리 임베드), 추가 엔트리포인트. 셋 모두 번들 안의 가상 경로로 노출된다. 파일 임포트는 `/$bunfs/...`를, 디렉터리 임베드는 `import.meta.dir` 아래를 쓴다("Embed assets & files", "Embed directories" 절).
- 문제 1: pi-tui 로더는 외부에서 후보 경로를 바꿀 수 없다. `getNativeModuleCandidates`는 패키지 진입점에서 export되지 않는다. `TUI/src/index.ts:112`는 `getNativeClipboard`와 타입만 export한다.
- 문제 2: `/$bunfs` 경로를 `dlopen`할 수 있는지 Bun 문서에 없다[미확인].
- [제안] 임베드가 필수가 되면 다음 중 하나를 쓴다.
  - B1: 시작할 때 `Bun.embeddedFiles`에서 `.node`를 꺼내 캐시 디렉터리에 쓰고, 그 디렉터리를 후보로 넣도록 pi-tui를 얇게 포크한다. 변경은 후보 계산 한 곳(`native-module-path.ts:14-27`)에 국한된다. `decisions-log.md` 19행의 "다른 층도 패키지 사용·포크를 적극 채택"과 맞는다.
  - B2: 캐시에 쓰고 설치 디렉터리에 링크를 둔다. 설치 위치에 쓰기 때문에 권하지 않는다.
- 크기: 위에서 확인한 네 파일의 합계는 약 146 KB다. 임베드의 크기 비용은 작다.

### 5.4 정리

- 단일 파일로 실행은 된다. 네이티브 기능까지 쓰려면 사이드카 디렉터리가 있어야 한다.
- [제안] 1차는 방법 A다. 방법 B1은 단일 파일 배포가 필수 요구로 확정될 때 연다.

## 6. 미결 사항

- [미결] L4 CLI 렌더링 라이브러리로 pi-tui를 쓸지. foundation-plan §2 스택 표에 TUI 행이 없고, `_research/layer-plan-v2.json`의 L4 항목에도 TUI 라이브러리 언급이 없다(텍스트 검색). 이 결정 뒤에 §2·§3·§5를 적용한다.
- [미결] 릴리즈 형태. 사이드카 디렉터리 배포를 받아들이는지, 단일 파일을 요구하고 B1 포크를 감수하는지.
- [미결] Windows Shift+Tab 판별을 제품 기능으로 요구하는지. 요구하면 사이드카 배치가 필수다.
- [미결] macOS 공증과 Windows 서명에서 사이드카 `.node`를 어떻게 다룰지.
- [제안] pi-tui 1.3.0 정확 고정과 배포물 LICENSE 포함은 채택 결정과 함께 확정한다.

## 7. 확인하지 않은 항목과 실행 전 확인 절차

이 조사는 코드를 실행하지 않았다. 아래는 구현 단계에서 확인할 절차다.

1. 임시 디렉터리에 `@earendil-works/pi-tui@1.3.0`을 설치하고 Bun 1.4.3으로 `bun build --compile` 최소 바이너리를 만든다. 애드온 없이 시작과 종료를 확인한다.
2. 바이너리 옆에 `native/linux/prebuilds/linux-x64/`를 두고 `DISPLAY`를 설정한다. `getNativeClipboard()?.getText()`가 값을 주는지 확인한다. 헬퍼 디렉터리를 치우고 같은 호출이 `undefined`를 주는지 확인한다.
3. `--asset ./native`로 임베드한 뒤 `/$bunfs` 경로에서 `require`가 성공하는지 확인한다(§5.3).
4. macOS Apple Terminal과 Windows Terminal에서 Shift+Enter와 Shift+Tab 판별을 확인한다.
5. musl 타깃(`bun-linux-x64-musl`)에서 애드온 로드를 확인한다.
6. `process.execPath`가 standalone에서 바이너리 경로인지 확인한다(§5.2의 [가정]).
