## 0. 요약

1. [실측] bun:ffi로 libc의 `flock(LOCK_EX|LOCK_NB)`을 호출한다. `dlopen("libc.so.6")`로 연 심볼이 Bun 1.4.3 실행과 `bun build --compile` 단일 바이너리(90.8 MB) 양쪽에서 같은 결과를 냈다. 잠금 보유 프로세스를 SIGKILL하면 경합 프로세스가 명령 시작을 포함해 약 10 ms 안에 잠금을 얻었다.
2. [실측] Bun 1.4.3의 `fs.openSync`로 연 fd에는 O_CLOEXEC가 설정된다(`/proc/self/fdinfo` flags 02102002). 잠금 보유 프로세스가 자식(`sleep 300`)을 띄운 뒤 SIGKILL되어도 잠금은 풀렸다. 자식은 fd를 물려받지 않았다.
3. [실측] Linux 추상 소켓 `Bun.listen({ unix: "\0이름" })`은 동작한다. 보유 중에는 EADDRINUSE(errno 98)가 나고, 보유 프로세스가 SIGKILL되면 즉시 획득된다. 파일이 남지 않는다. Bun 공식 문서와 타입 선언에는 추상 네임스페이스 언급이 없다 [미확인: 문서].
4. [실측] 파일 경로 Unix 소켓은 SIGKILL 뒤 소켓 파일이 남고 같은 경로 바인드는 EADDRINUSE가 된다. `connect`가 ECONNREFUSED로 실패하면 stale로 보고 unlink한 뒤 재바인드할 수 있다. 판정과 unlink 사이에는 경쟁이 있다 [추론, §2.4].
5. [추론] proper-lockfile은 기본 설정에서 크래시 뒤 약 5~10초 뒤에 인수된다(stale 기본 10 s, mtime 갱신 주기 5 s). 실측은 하지 않았다.
6. [소스] oh-my-pi는 Linux 추상 소켓, Windows named mutex, 그 밖의 Unix `flock` 사이드카 순서로 세션 임대를 구현한다. `docs/session.md:540`, `session-storage.ts:610-631`, pi-natives 소스 3개를 대조해 확인했다.
7. [제안] LockProvider 구현 수단은 bun:ffi `flock` 사이드카로 정한다. macOS와 Linux는 같은 호출을 쓴다. 추상 소켓은 Linux 전용 대안으로만 기록한다. Windows 수단은 미결이다.
8. [제안] 펜싱은 DB 임대 행의 epoch로 둔다. `design.md` §3.3 미결 T-4의 제안 (b)다. OS 잠금만으로는 쓰기 트랜잭션 안에서 소유를 확인할 수 없고, 홈 디렉터리가 다른 프로세스와는 잠금이 공유되지 않는다.
9. [추론] DB 임대만 쓰는 후퇴안의 비용은 크래시 뒤 인수까지 기본 설정에서 최대 30초다(`design.md:119`, `:939`). flock은 같은 상황에서 명령 시작을 포함해 약 10 ms다. 정합성은 epoch로 같다. 감수할 비용은 인수 지연 약 30초, 같은 기계에서 PID·시작 시각을 검사하는 코드, 세션마다 5초 주기의 FULL 하트비트 커밋이다(§4.3).

## 2. 질문별 결과

### 2.1 bun:ffi로 flock·fcntl 호출

- [문서] bun.com/docs/api/ffi 요약에는 libc 호출 예제가 없다.
- [문서] `ffi.d.ts:566`: `dlopen`의 인자는 "Library name or file path, passed to `dlopen()`"이다. bare name은 시스템 로더가 찾는다.
- [실측] Linux x64, Bun 1.4.3:

| 항목 | 결과 |
|---|---|
| `dlopen("libc.so.6", { flock: { args: [i32, i32], returns: i32 } })` | 성공 |
| 보유 프로세스의 `flock(fd, LOCK_EX\|LOCK_NB)` | rc 0 |
| 경합 프로세스 | rc -1, 종료코드 3 |
| 보유 프로세스 SIGKILL 뒤 경합 프로세스 | rc 0, 명령 시작을 포함해 10 ms |

- [소스·문서] flock(2)은 잠금을 open file description에 붙인다. 같은 프로세스라도 같은 파일을 독립 fd로 열면 서로 경합한다("these file descriptors are treated independently by flock()"). 설계는 flock을 쓴다.
- [미확인] fcntl 잠금 실측은 하지 않았다. POSIX record lock이 프로세스 단위라 fd를 하나만 닫아도 잠금 전체가 풀린다는 점은 일반 지식이다. POSIX 명세 원문은 확인하지 않았다.
- macOS: OMP는 macOS에서 `libc::flock`을 쓴다(`file_lock/unix.rs:23`). Bun `dlopen`에 넣을 macOS 라이브러리 이름(`libSystem.B.dylib` 등)은 실측하지 않았다 [미확인].
- Windows: bun:ffi로 `LockFileEx` 또는 `CreateMutexW`를 부르는 방식은 실측하지 않았다 [미확인]. OMP는 `CreateMutexExW`를 쓴다(`file_lock/windows.rs:36`, `:111`). Bun FFI 문서 요약에는 Windows HANDLE을 `ptr` 대신 64비트 부호 없는 정수 타입으로 받으라는 권고가 있다 [문서 요약, 원문 미대조].

### 2.2 bun build --compile에서 bun:ffi 동작

- [실측] `bun build --compile lock.ts --outfile lockbin`이 성공했다. 산출물은 90,798,048 바이트다. 보유(rc 0), 경합(rc -1), SIGKILL 뒤 재획득(rc 0)이 Bun 실행과 같았다.
- [문서] bun.com/docs/bundler/executables에는 FFI, dlopen, 공유 라이브러리 언급이 없다 [미확인: 문서]. 시스템 libc는 `dlopen`이 시스템 로더로 열므로 임베드 없이 동작한다. 이 경로는 실측으로 확인했다. 라이브러리를 바이너리에 넣는 방식은 시험하지 않았다.
- [문서 요약] 같은 페이지에는 바이너리가 아직 크다는 문장이 있다. 크기는 L4 plan에서 다룬다(`_research/foundation-plan.md §7`).

### 2.3 자식 프로세스 상속과 해제 시점

- [실측 T2] 잠금 보유 프로세스가 `Bun.spawn(["sleep","300"], {stdio: ignore})`를 띄운 뒤 SIGKILL되었다. 자식은 살아 있었고, 경합 프로세스는 rc 0으로 잠금을 얻었다. 잠금 fd의 flags 02102002에는 O_CLOEXEC(02000000)가 포함된다.
- 해석 [추론]: Bun 1.4.3의 `fs.openSync`는 O_CLOEXEC로 연다. exec된 자식은 fd를 물려받지 않는다. 이 결과는 `Bun.spawn` 한 경로에 한정된다 [미확인: fork 계열과 다른 spawn 옵션].
- [문서·소스] flock(2): "the lock is released either by an explicit LOCK_UN operation on any of these duplicate file descriptors, or when all such file descriptors have been closed." 프로세스가 죽으면 커널이 fd를 닫으므로 잠금이 풀린다.
- [제안] 잠금 획득 직후 Linux에서는 `/proc/self/fdinfo`, macOS에서는 `fcntl(F_GETFD)`로 FD_CLOEXEC를 확인하는 테스트를 둔다. macOS 쪽은 [미확인].

### 2.4 추상 소켓과 파일 경로 소켓 (Bun.listen unix)

- [문서] `bun.d.ts:7401-7406`: `UnixSocketOptions.unix: string`, 설명은 "The unix socket to listen on or connect to". bun.com/reference/bun/listen도 같은 한 줄이다. 추상 네임스페이스와 기존 경로 처리 설명은 없다 [미확인: 문서]. Unix 소켓 전용 공식 절은 찾지 못했다. bun.com/docs/runtime/networking/tcp에는 unix 절이 없다.
- [실측 T3] `@이름`을 `\0이름`으로 바꿔 바인드했다.

| 시나리오 | 결과 |
|---|---|
| 추상 이름 `\0…` 보유 | 성공 |
| 같은 이름 경합 | EADDRINUSE(errno 98) |
| 보유 프로세스 SIGKILL 뒤 경합 | 성공. 파일 없음 |
| 파일 경로 소켓 보유 | 성공 |
| 같은 경로 경합 | EADDRINUSE |
| 보유 프로세스 SIGKILL 뒤 소켓 파일 | 남음(`srwxrwxr-x`) |
| SIGKILL 뒤 같은 경로 바인드 | EADDRINUSE |
| SIGKILL 뒤 connect 프로브 | ECONNREFUSED → unlink → 재바인드 성공 |
| 살아 있는 보유자에 connect | 연결 성공(live). 바인드는 EADDRINUSE |

- [추론] 파일 소켓 프로브의 경쟁: 두 프로세스가 같은 stale 소켓을 동시에 ECONNREFUSED로 판정하면, 한쪽이 바인드한 살아 있는 소켓을 다른 쪽이 unlink할 수 있다. 막으려면 부가 잠금이 필요하고 결국 flock으로 수렴한다. 이 경쟁은 실측하지 않았다 [미확인].
- [소스] OMP는 Linux에서 `UnixDatagram::bind_addr`로 추상 이름에 바인드한다(`file_lock/linux.rs:16-17`). Bun.listen은 선언상 스트림 소켓만 노출한다. datagram에 해당하는 Bun API는 확인하지 못했다 [미확인].

### 2.5 oh-my-pi 세션 임대 대조

- [소스] `docs/session.md:539`: 쓰기 게시용 교차 프로세스 publish lock이 있다.
- [소스] `docs/session.md:540`: 세션 id 기준 OS 임대. "on Linux an abstract socket and on Windows a named mutex, neither of which creates a file; on macOS and other non-Linux Unix a `flock` on a sidecar in that directory."
- [소스] `docs/session.md:540`: "Processes with different home or state directories do not meet in this lease." 홈이나 상태 디렉터리가 다르면 잠금이 공유되지 않는다. OS 잠금만으로는 막지 못하는 경우이며, 펜싱이 필요한 근거다.
- [소스] `docs/session.md:541`: 임대를 다른 프로세스가 쥐고 있으면 형제 파일로 옮겨 쓰고 `parentSession`으로 연결한다.
- [소스] `session-storage.ts:611-614`: 키는 세션 id(정규식 `^[A-Za-z0-9_-]{1,128}$`에 맞을 때)이고, 그 밖에는 wyhash 이름이다. 사이드카는 `<session-owners>/<이름>`이다.
- [소스] `session-storage.ts:617-618` 주석: 사이드카는 비워 두고 삭제하지 않는다. flock 파일을 unlink하면 옛 inode의 보유자와 새 inode의 생성자가 한 임대를 둘로 나눌 수 있다. [제안] 제품 LockProvider에도 같은 규칙을 적용한다.
- [소스] `session-storage.ts:620-629`: 사이드카 디렉터리를 0700이고 현재 사용자 소유인지 검사한다.
- [소스] `file-lock.ts:26-29`: 경합 재시도 기본값은 50회, 100 ms 간격이다. 대기 상한은 약 5초다.
- [소스] `file_lock/mod.rs:32-39`: 이름은 경로에 대한 xxh64 두 값을 이어 붙인 `omp-file-lock-…`이다.

### 2.6 proper-lockfile

- [문서] README(master) 기준 [미확인: 4.1.2 대조]:
  - `stale`: 기본 10000 ms, 최소 5000 ms.
  - `update`: 기본 stale/2. 최소 1000 ms, 최대 stale/2.
  - `retries`: 기본 0.
  - mkdir 전략을 쓴다. 잠금 경로는 대상 경로에 `.lock`을 붙인다.
  - SIGKILL이나 VM 치명 오류로 죽으면 잠금이 제거되지 않는다. 판정은 mtime이 stale을 넘었는지로 한다.
- [추론] 크래시 뒤 인수: 마지막 mtime 갱신은 크래시 직전 5초 안에 있다. stale 10초 뒤에 stale로 판정되므로 크래시 뒤 약 5~10초를 기다린다. 최소 설정(stale 5초)이면 약 2.5~5초다. 실측하지 않았다 [미확인].
- [인용] `process.md §5`가 적은 pi durable의 10초 stale 대기(`PX/durable/sessions.ts:47`)는 로컬 소스가 없어 확인하지 못했다 [미확인].
- [인용] `packages.md §4.2`의 "2021 이후 갱신 없음"은 확인하지 않았다 [미확인].

### 2.7 WSL 파일시스템

- `df -T`로 확인한 결과 홈 디렉터리 `/home/user`는 ext4다. 실측은 모두 ext4에서 했다.
- `/mnt/c`(Windows 드라이브, 9p/drvfs): flock 동작을 실측하지 않았다 [미확인]. 검색 결과에는 WSL에서 fcntl 잠금이 기대대로 동작하지 않았다는 보고(Bitcoin Core #18700 설명, GHC ghcup의 EINVAL 보고)가 있다. 최신 WSL의 상태는 확인하지 못했다 [미확인].
- [제안] 잠금 사이드카와 DB 파일은 WSL 안의 ext4에 둔다. 기본 데이터 경로는 L4 plan에서 정한다.

## 4. 결정 근거와 제안

### 4.1 LockProvider 구현 수단

- [결정] 첫 지원 OS는 macOS와 Linux(WSL 포함)이고 Windows 네이티브는 나중이다(`_research/decisions-log.md` 2026-10-19 답). 사용자는 OS별 차이를 공통 인터페이스 뒤에 두고 구현만 바꾸라고 했다(`_research/decisions-log.md` 2026-10-19 설계 규칙).
- [제안] 1안(권고): bun:ffi `flock`과 세션 id 키 사이드카. `LOCK_EX|LOCK_NB`를 쓰고, 획득 뒤 O_CLOEXEC를 테스트로 고정하며, 사이드카는 삭제하지 않고, 디렉터리는 0700과 소유자를 검사한다. macOS와 Linux가 같은 코드를 쓴다.
- [미결] Windows: `CreateMutexW`(named mutex, OMP와 같은 발상) 또는 `LockFileEx` 중 하나를 실측 뒤 정한다.
- [제안] 추상 소켓은 Linux 전용이라 채택하지 않고 기록만 한다. 채택하면 OS별 수단이 늘어나 시험 면이 커진다.
- [제안] 파일 소켓 프로브는 경쟁 조건이 있어 채택하지 않는다.
- [제안] 인터페이스 초안(F 타입 이름은 F 문서가 정한다):

```ts
interface LockProvider {
  /** 세션 쓰기 소유를 취득한다. 실패하면 null. 프로세스가 죽으면 OS가 해제한다. */
  tryAcquire(sessionId: SessionId): LockHandle | null;
}
interface LockHandle {
  readonly sessionId: SessionId;
  release(): void;
}
```

### 4.2 미결 T-4 판정

- [제안] `engineering/transactions/design.md` §3.3 미결 T-4의 (b), "OS 잠금으로 생존을 판정하고 DB 임대 행의 epoch로 펜싱한다"를 권한다.
  - 근거 1: 실측에서 크래시 뒤 인수가 즉시 된다. (a)안의 최대 30초 대기를 피한다.
  - 근거 2: OS 잠금은 SQLite 쓰기 트랜잭션 안에서 확인할 수 없다(`design.md:99`). epoch 확인은 쓰기 트랜잭션 안에서 한다(§3.3 항목 3).
  - 근거 3: 홈 디렉터리가 다르면 잠금이 공유되지 않는다(`session.md:540`). epoch가 이 경우도 막는다.
- [결과] `adr.0004`의 [결정](`ADR-0004-session-storage.md:106`, "세션 id를 키로 한 OS 잠금")을 개정해야 한다. `ADR-0004`의 [미결](`:154`)과 같은 질문이다 [미결: 사용자 확인].

### 4.3 DB 임대만 쓰는 후퇴안의 비용

| 항목 | 내용 |
|---|---|
| 크래시 뒤 인수 지연 | 기본 설정에서 최대 30초(하트비트 5초, 만료 30초: `design.md:119`, `:939`). 실측 flock(명령 시작 포함 약 10 ms)과 비교하면 약 3,000배다 [계산] |
| 같은 기계에서 지연 줄이기 | PID와 시작 시각 지문으로 죽은 소유자를 판정하면 지연이 준다(`design.md:939` (a), `process.md §5`의 Hermes 방식). 대신 PID 재사용과 시작 시각 조회 코드가 생긴다 |
| 쓰기 비용 | 세션마다 5초 주기 하트비트 커밋 1회다. 모든 커밋이 FULL이므로 fsync가 1회 든다(`design.md:89`). 빈도는 낮다 |
| 정합성 | epoch 펜싱으로 유지된다. 기능 손실은 없다 |
| 사용자 체감 | 재시작 직후 최대 30초 동안 세션이 사용 중으로 보인다 [추론] |
| 살아 있으나 멈춘 소유자 | flock과 같다. 인수되지 않는다. 펜싱이 필요한 경우가 같다 [추론] |

- 결론 [제안]: 후퇴안은 정합성 비용이 없다. 감수할 비용은 크래시 복구 지연(약 30초)과 같은 기계 한정의 PID 검사 코드다.
