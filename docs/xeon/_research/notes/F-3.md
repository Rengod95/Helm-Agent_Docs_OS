# F-3. pi durable의 체크포인트·효과 기록 필드와 재생 규칙

정본 아님. F 계약(`F.records`, StepCheckpoint, effect.intent/exec/result)의 근거로 인용한다.

## 0. 조사 기준과 범위

- 소스: pi 저장소 커밋 `cdaf6c22`(2026-10-11), 패키지 `@earendil-works/pi-durable` 1.1.0.
- 경로 표기: `durable/`은 `~/projects/_ref/pi-src/packages/durable/`이다. `agent/`와 `coding-agent/`도 같은 방식으로 `~/projects/_ref/pi-src/packages/` 아래를 가리킨다. 본문의 `harness/tool.ts`처럼 쓴 경로는 `durable/src/` 기준이다.
- 확인 방법: 소스 읽기, 테스트 이름과 본문 읽기, `grep`. 내려받은 코드는 실행하지 않았다.
- 확인 위치: `durable/src/tasks.ts`, `entries.ts`, `types.ts`, `harness/generation.ts`, `harness/tool.ts`, `harness/submissions.ts`, `harness/scheduler.ts`, `harness/types.ts`, `storage/sqlite/migrations.ts`, `storage/sqlite/storage.ts`, `storage/memory.ts`, `durable/docs/spec.md`(1805-1810, 1826-1837, 1886-1901, 1917-1935, 2082-2108, 2288-2301, 2936-2940, 3159-3163, 3234, 4132, 4826-4834), `durable/test/`.
- 표지: 소스에서 직접 확인한 사실은 근거만 단다. 확인하지 못한 사항은 [미확인]으로 쓴다.

## 1. 요약

- 태스크 레코드에는 최상위 `phase` 필드가 없다. 레코드 수준의 고정값은 `state.status` 다섯 개(`pending`, `running`, `waiting`, `completing`, `terminal`)다. `phase`는 `state.checkpoint` 안의 판별자이며, 값 집합은 정의(`TaskDefinition`)마다 다르다. (§2)
- 도구 호출은 "의도 커밋 → 실행 → 결과 커밋" 순서다. 의도 커밋은 `{ phase: "execute", arguments, replay }`를 저장하고, 결과 커밋은 종료 상태와 결과 항목을 한 커밋에 쓴다. (§4.1)
- 모델 요청에는 별도의 의도 커밋이 없다. `request` 체크포인트가 의도 역할을 하고, 재개하면 요청을 다시 보낸다. (§4.2)
- 재실행은 저장된 `replay`와 현재 선언이 모두 `"safe"`일 때만 한다. 기본값은 `"unsafe"`다. pi 소스에서 기본 도구 중 `safe`를 선언한 것은 없다. (§5)
- `requestId`는 대화 안에서 제출(submission)을 중복 제거한다. 저장소 스키마에는 UNIQUE 제약이 없고, 중복 제거는 Session 커밋 안의 조회로 한다. (§6)
- pi durable은 exactly-once를 약속하지 않는다. 명세가 이 점을 명시한다(spec 2936-2940). (§6, §7)

## 2. 저장 단위와 phase

### 2.1 태스크 레코드 필드

`TaskRecord`(`durable/src/types.ts:539-585`)의 필드는 다음과 같다.

| 필드 | 뜻 | 근거 |
|---|---|---|
| `id` | `TaskId`(정수 ID, 결과 타입 브랜드) | types.ts:29, 539-541 |
| `conversationId` | 소속 대화. 생성 뒤 바뀌지 않는다 | spec 1805; types.ts:539-541 |
| `kind` | 등록된 정의 이름(예: `pi.tool`, `pi.generation`) | types.ts:543 |
| `version` | 정의 버전. 마이그레이션 기준 | types.ts:545; `ToolTask`는 `version: 2`(harness/tool.ts:113-115) |
| `input` | 생성 시 입력(정의 타입 `I`). 살아 있는 동안과 종료 뒤에도 보존 | types.ts:547 |
| `owner`, `background`, `abortRequested`, `abortReason`, `abandonOnRestart` | 소유 관계와 중단 표지 | types.ts:549-561 |
| `startedAt`, `endedAt` | Session이 기록하는 시각 | types.ts:563-571 |

### 2.2 `state.status`: 레코드 수준의 고정값

`TaskState`(`types.ts:502-537`)의 `status` 값은 다섯 개다. SQLite `tasks` 테이블의 CHECK 제약도 같은 다섯 값을 강제한다(`durable/src/storage/sqlite/migrations.ts:41`).

| status | 저장되는 것 | 근거 |
|---|---|---|
| `pending` | `checkpoint` | types.ts:503-508 |
| `running` | `checkpoint` | types.ts:510-515 |
| `waiting` | `checkpoint`, `on`(태스크 ID 목록), `policy`(`failFast` 또는 `allSettled`) | types.ts:517-524 |
| `completing` | `outcome`(체크포인트 없음). 결과는 정해졌고, 소유한 일반 하위 작업이 모두 끝나면 `terminal`이 된다 | types.ts:526-531 |
| `terminal` | `outcome`(체크포인트 없음). 영속 결과 수신표 | types.ts:533-537 |

### 2.3 phase: 정의별 판별자

- `TaskDefinition.phases`는 `S["phase"]`를 키로 하는 완전 맵이다(`types.ts:243-253`, `durable/src/tasks.ts:4`). 값 집합은 정의마다 다르다.
- 정의별 phase 집합과 초기 phase는 다음과 같다.

| 정의 | 초기 phase | phase 집합 | 근거 |
|---|---|---|---|
| `pi.tool` (`ToolTask`) | `call` | `call`, `execute` | harness/tool.ts:113-122, 169 |
| `pi.generation` (`GenerationTask`) | `prepare` | `prepare`, `request`, `retry`, `poll`, `tools` | harness/generation.ts:115-119, 51-90 |

- 스키마에 phase 열은 없다. `tasks` 테이블은 `id`, `conversation_id`, `kind`, `status`, `abort_requested`, `background`, `record`(JSON)만 가진다(migrations.ts:37-45). 체크포인트는 `record` JSON 안에 있다(storage/sqlite/storage.ts:805-815).

**답:** "task 레코드의 phase 고정값"은 존재하지 않는다. 고정되는 것은 `status`의 다섯 값이다. phase는 정의마다 정해지는 값이다.

## 3. StepCheckpoint

- 체크포인트는 `phase`를 판별자로 갖는 유니온이다. 타입 제약은 `S extends { phase: string }`이다(`types.ts:243`).
- 매 커밋마다 체크포인트 전체를 교체한다(spec 1809-1810: "each durable checkpoint is a full replacement"). 체크포인트가 바뀌지 않으면 단계는 fault로 끝난다(types.ts:145-148; spec 1886-1890 규칙 5·6).
- 과거 버전의 레코드는 `migrate(input, checkpoint, fromVersion)`로 바꾼다. 예약 단계에서 상태 전이와 함께 적용된다(types.ts:256-263, spec 1899-1901).

생성 체크포인트(`harness/generation.ts:51-90`)의 필드:

| phase | 필드 | 뜻 |
|---|---|---|
| `prepare` | `attempt`, `compacted?`, `overflow?` | 재시도 번호, 대기 대상인 컴팩션 태스크, 컴팩션을 일으킨 오류 문구 |
| `request` | `attempt`, `compacted?`, `model`(provider, modelId), `thinkingLevel`, `streamOptions`, `cutoff` | 요청 설정 전부. 재전송 때 그대로 쓴다. `cutoff`는 요청에 포함된 마지막 항목 ID |
| `retry` | `attempt`, `compacted?`, `until` | 재시도 시각 |
| `poll` | `attempt`, `compacted?`, `model`, `cutoff`, `handle`, `pollAt` | 지연 응답 핸들과 다음 폴링 시각 |
| `tools` | `assistant`(항목 ID), `tools`(태스크 ID 목록), `pending`(호출 ID 목록) | 도구 라운드 대기 상태 |

도구 체크포인트(`harness/tool.ts:64-67`)는 두 가지다.

- `{ phase: "call" }`
- `{ phase: "execute", arguments: JsonObject, replay: "safe" | "unsafe" }`

## 4. 효과 기록 순서

### 4.1 도구 호출(`pi.tool`)

순서는 `call` 핸들러 한 번 안에서 나뉜다. 의도 커밋과 결과 커밋이 경계가 되고, 그 사이에 진행 커밋이 끼어들 수 있다.

1. 호출 읽기와 해석(harness/tool.ts:123-133): 호출을 읽고(124), 도구를 이름으로 찾고(125), `prepareArguments`로 보정하고(130), 검증한다(131-133). 찾지 못하면 `tool_unavailable` 결과로 바로 정착한다(126-129).
2. 훅과 최종 인수(136-155): `beforeTool` 훅을 실행하고(136-146), 다시 검증하고(151-153), strict JSON으로 복사한다(155). 이 시점의 인수가 최종 인수다.
3. 의도 커밋(156-165): 같은 커밋에서 라이브 슬롯을 `running`으로 바꾸고, 체크포인트를 `{ phase: "execute", arguments: final, replay: tool.replay ?? "unsafe" }`로 바꾼다(163-164). 실행은 이 커밋 뒤에 한다(166).
4. 실행(harness/tool.ts:263-429): `tool.execute(args, api, context)`를 호출한다(400). 진행 출력은 `publishProgress`가 조절된 커밋으로 `pi.live` 문서에 쓴다(435-483). 이 문서는 대화 범위이며 결과 기록이 아니다(`harness/live.ts:98-104`).
5. 결과 커밋(`settle`, 570-631): 실행 뒤 중첩 호출을 정리하고(417, 587), 같은 커밋에서 (a) `appendToolResult`로 결과 항목을 추가하고(609), (b) 사용량을 기록하고(839), (c) 종료 상태를 쓴다(624-629). 종료 상태는 `completed`, `failed`(오류 메시지 포함), `aborted` 중 하나다.

결과 항목은 `pi.tool-result` 종류이며, 내용 끝에 진단 블록이 붙는다(harness/tool.ts:817-841, 827-828; `durable/src/entries.ts:21-24`). 항목의 `data`에는 구조화된 `diagnostics`가 들어간다.

### 4.2 모델 요청(`pi.generation`)

1. 준비(`prepare`, generation.ts:125-181): 같은 커밋에서 `pi.system` 항목을 추가하고, `request` 체크포인트를 쓴다(165-181). 이 커밋이 요청 의도의 기록이다.
2. 요청(`request`, generation.ts:184-209): 첫 커밋은 중단된 부분 응답을 정리하고 `live.generation`을 표시한다(187-192). 그 뒤 `beforeRequest` 훅을 실행하고, 공급자 세션 ID를 얻고(204), 응답을 스트리밍한 뒤(207), `classify`로 넘긴다(209). 요청 자체에는 별도 의도 커밋이 없다.
3. 분류(`classify`, generation.ts:423-): 지연 응답이면 `poll` 체크포인트를 쓴다(439-450). 최종 응답이면 `answer`가 한 커밋에서 `pi.assistant` 항목을 추가하고 `completed`로 끝낸다(517-531).
4. 도구 라운드(`startToolRound`, generation.ts:549-594): 한 커밋에서 어시스턴트 항목, 제공되지 않은 도구의 결과 항목(575-580), 도구 태스크 생성, 라이브 슬롯, `tools` 체크포인트를 쓴다.

재개 규칙: `request`에서 재개하면 요청을 다시 보낸다. 준비 단계를 반복하지 않는다. 테스트 `durable/test/harness-generation-recovery.test.ts:74`("resends a request interrupted before any partial without repeating preparation")가 이를 확인한다. 공급자 쪽에서 같은 요청이 중복 처리되는지는 [미확인]이다. durable은 `sessionId`를 옵션으로 넘길 뿐이다(`harness/provider.ts`, generation.ts:204).

| 개념 | pi에서 저장되는 것 | 저장 위치 | 근거 |
|---|---|---|---|
| effect.intent (도구) | `phase: "execute"`, `arguments`(보정·훅·검증 이후 최종값), `replay` | 태스크 `state.checkpoint` | harness/tool.ts:163, 64-67 |
| effect.intent (모델) | `request`의 `attempt`, `model`, `thinkingLevel`, `streamOptions`, `cutoff` | 태스크 `state.checkpoint` | generation.ts:60-70, 181 |
| effect.intent (지연 응답) | `poll`의 `handle`, `pollAt` | 태스크 `state.checkpoint` | generation.ts:72-80, 439-450 |
| effect.intent (외부 멱등 키의 예) | `{ phase: "charge", key }`. 키는 준비 단계에서 만든다 | 예시 코드 | spec 1826-1837 |
| effect.exec | 별도 기록 없음. 상태는 `running`이고 체크포인트가 그대로 남는다. 진행 출력은 `pi.live` | 대화 범위 문서 | tool.ts:166, 400, 435-483 |
| effect.result (도구) | `outcome`(`status`, `result`, `error`), 결과 항목(`content`, `data.diagnostics`), 사용량 | 태스크 `outcome` + 대화 항목 | types.ts:458-500; tool.ts:570-630, 839 |
| effect.result (모델) | `result: { entryId }`, `pi.assistant` 항목 | 태스크 `outcome` + 대화 항목 | generation.ts:92, 524-531 |
| effect.result (중첩 호출) | `taskId`, `structuredOutput`, `isError`, `details`, `diagnostics`, `usage`, `durationMs` | 태스크 범위 문서 `NestedCallDoc` | tool.ts:84-102, 637-654 |

`outcome`의 종류(types.ts:465-500):

- `completed`: `result` 필수
- `failed`: `error`(`{ message, detail? }`) 필수, `result` 선택
- `aborted`: `reason`과 `result` 선택
- `orphaned`: `reason` 필수(정의나 마이그레이션을 쓸 수 없음)
- `faulted`: `error` 필수(단계가 던졌거나 진행이 없었음)

## 5. replay safe/unsafe 처리

| 상황 | 처리 | 근거 |
|---|---|---|
| `replay` 선언이 없음 | `unsafe`로 본다 | harness/types.ts:289-290 ("Default `unsafe`"); tool.ts:163 |
| 의도 커밋 | 최종 `replay` 값을 체크포인트에 저장 | tool.ts:163 |
| 재개, `execute` 단계 | 저장 값과 현재 선언이 모두 `safe`일 때만 재실행한다. 재실행 전에 진행 출력을 지운다 | tool.ts:169-181 (조건 173, 초기화 175-179) |
| 재개, 조건 미충족 | `failed`로 정착한다. 메시지는 "was interrupted and may have partially run". 부분 출력을 결과에 담는다 | tool.ts:182-185, 624-627 |
| 재시작 중단, `execute` 단계 | `aborted`로 정착한다. 코드 `interrupted`, "may have partially run" | tool.ts:188-198 |
| 재시작 중단, `call` 단계 | `aborted`로 정착한다. 코드 `abandoned`, "was not started" | tool.ts:191-196 |
| 재개 때 인수 | 저장된 인수로 `execute`를 호출한다. `beforeTool`은 다시 실행하지 않는다 | spec 3159-3163; tool.ts:169-171 |
| 중첩 호출 | 호출자가 `safe`가 아니면 자식 태스크에 `abandonOnRestart`를 준다 | tool.ts:346, 376; harness/types.ts:233-234; spec 2082-2108 |
| 중첩 호출의 재시작 | `abandonOnRestart` 자식은 재시작 때 `abortReason: "restart"`로 중단되고 재실행하지 않는다 | spec 2082-2108; harness/scheduler.ts:304(실행 중 상태를 pending으로 되돌림) |

테스트 근거:

- `durable/test/harness-tools-recovery.test.ts:109-125`: `unsafe`, `execute` 체크포인트에서 재개하면 부분 출력을 담은 오류 결과로 답한다.
- `durable/test/harness-tools-recovery.test.ts:136-156`: "reruns a tool only when both the stored and the current replay policy are safe".

**기본 도구 선언:** `durable/src/`, `coding-agent/src/`, `agent/src/` 전체에서 `replay` 선언을 검색했다. 선언은 `coding-agent/src/experimental/durable/subagent.ts:33`과 `coding-agent/src/experimental/vacation/vacation.ts:44`의 `"safe"` 두 곳뿐이다. 읽기·쓰기·편집·bash 도구에는 선언이 없다. 따라서 기본 도구는 모두 `unsafe`다. 기존 `refs/pi-durable.md:229`가 미확인으로 남긴 항목이 이로써 확인된다.

**이름 차이:** `agent/src/types.ts:489-490`의 `AgentTool.replay?: "never" | "safe"`는 값 집합과 기본값이 다르다(기본값 없음). durable은 `"safe" | "unsafe"`, 기본 `unsafe`다. Xeon의 F 계약은 이름을 하나로 정해야 한다(§8.3 [미결] 1).

**모델 요청:** 재시작 때 재전송이 기본이다. replay 플래그가 없다(generation.ts:184-209; `durable/test/harness-generation-recovery.test.ts:74`).

## 6. requestId 멱등

- 필드: `SubmissionRecordBase.requestId?: string`(`durable/src/types.ts:374-375`). 주석은 "Host-provided deduplication key, scoped to the conversation"이다.
- 규칙(`durable/src/harness/submissions.ts:146-160`): 같은 대화에 같은 `requestId`가 있으면 기존 제출 ID를 반환하고 아무것도 쓰지 않는다(155-158). 기존 제출의 종류(`input` 또는 `write`)가 다르면 오류를 낸다(159).
- 제출 생성 시 상태(167-205): `input`은 `placed`(유휴, 빈 수신함), `write`는 `done`, 바쁨 또는 수신함이 차 있으면 `queued`다.
- 메모리 저장소: `submissionIdsByRequest` 맵으로 중복을 막는다(`storage/memory.ts:394-408`, 조회 595-605).
- SQLite 저장소: `submissions.request_id` 열과 `submissions_by_request` 인덱스를 둔다(`storage/sqlite/migrations.ts:51-58`). 이 인덱스는 UNIQUE가 아니다. 조회는 `storage/sqlite/storage.ts:498-510`이다.
- [가정] UNIQUE 제약이 없으므로 중복 제거는 Session 커밋의 직렬화에 기댄다. 같은 커밋 안에서 조회하고 쓰는 순서가 보장된다고 본다. 직렬화 방식은 `types.ts:191-203`(Session 라인 커밋)과 spec 4826-4834로 확인했다. 저장소별 격리 수준은 [미확인]이다.
- 재개 뒤 재제출: 저장소 오류 뒤 커밋 여부를 알 수 없으므로 같은 `requestId`로 다시 제출한다. 이미 받아들여진 제출을 찾는다(spec 4826-4834).
- 호출자가 쓰는 `requestId` 예: 서브에이전트 `subagent:${taskId}`(spec 3234), 컴팩션 `compaction:<taskId>`(spec 4132).
- 중첩 호출 멱등: 키(`<callId>/<key>`)로 식별한다. 같은 이름과 같은 인수면 기존 태스크를 돌려준다(harness/tool.ts:675-689). 다른 도구나 인수면 오류를 낸다(686).
- 메모 멱등: `runtime.memo(name, candidate)`는 최초 쓰기 승자를 반환한다(types.ts:204-206). 중첩 호출 기록에 쓴다(tool.ts:81, 365, 585).
- 명세의 한계: "This is not exactly-once execution... a replay-safe tool with external effects still needs its own idempotency"(spec 2936-2940). 외부 효과의 멱등은 도구 자체 몫이다.

## 7. Xeon F.records에 대한 제안

- [제안] StepCheckpoint: 레코드 필드는 `kind`, `version`, `status`(고정 5값), `checkpoint`, `on`, `policy`, `outcome`, `startedAt`, `endedAt`, `abortRequested`, `abortReason`, `abandonOnRestart`, `owner`, `background`로 둔다. `phase`는 `checkpoint` 안의 판별자로만 둔다. 정의마다 값 집합이 다르므로 레코드 최상위 필드로 두면 타입이 정의마다 갈린다(§2.3).
- [제안] effect.intent: `{ phase, arguments(최종값), replay }`를 기본형으로 한다. 외부 멱등 키가 있는 효과는 `key`를 같은 체크포인트에 함께 쓴다(spec 1826-1837 예).
- [제안] effect.exec: 별도 레코드를 두지 않는다(pi와 같다). 진행 상태는 대화 범위 문서에 두되 결과 기록과 분리한다(pi의 `pi.live`에 해당한다).
- [제안] effect.result: `outcome`(`status`, `result?`, `error?: { message, detail? }`, `reason?`)과 결과 항목을 같은 커밋에 쓴다(tool.ts:588-630). 사용량도 같은 커밋에 쓴다(tool.ts:596, 839). 이 규칙을 `eng.transactions.design`에 옮긴다.
- [제안] 재생 규칙: 기본 `unsafe`. 재개 때 저장 값과 현재 선언이 모두 `safe`일 때만 재실행한다. 아니면 중단 결과를 합성한다. 이는 `process.md:175`의 채택안과 같다.
- [제안] 모델 요청: 재전송을 기본으로 두되, 요청마다 멱등 키를 둘지는 §8.3 [미결] 2에서 결정한다.

## 8. 한계, 미확인 사항, 미결 사항

### 8.1 [미확인]

- pi-ai의 `DeferredHandle` 구조와 지연 응답 프로토콜. 이 패키지 밖(`@earendil-works/pi-ai`)에 있다.
- 공급자 쪽 멱등성(같은 `sessionId`로 재전송할 때 중복 생성·과금이 생기는지).
- SQLite 저장소의 커밋 격리 수준과 잠금 방식. 이 조사는 명세의 원자성 진술(spec 4826-4828: "commits are atomic")만 확인했다.
- `scheduler.ts`의 나머지 본문. 재개 때 실행 중 상태를 pending으로 되돌리는 부분(scheduler.ts:304)만 확인했다.
- `pi-ai`의 `Usage`와 `ToolResultMessage` 세부 타입.

### 8.2 기존 조사 정정 및 보완

- `refs/pi-durable.md:164`가 든 `tool.ts:160-165`의 의도 커밋 범위는 실제로 156-165다(체크포인트 쓰기는 163).
- `refs/pi-durable.md:229`가 미확인으로 남긴 기본 도구 선언은 이 조사에서 "선언 없음"으로 확인했다(§5).

### 8.3 [미결]

1. `replay` 이름 통일: durable의 `"safe" | "unsafe"`(기본 `unsafe`)와 agent-core의 `"never" | "safe"`(기본값 없음) 중 하나로 정한다. 사용자 확인이 필요하다.
2. 모델 요청 재전송 정책: 재전송을 허용할지, 요청마다 멱등 키를 둘지 정한다.
3. 중단 결과 코드 집합: durable은 `interrupted`, `abandoned`, `aborted`를 쓴다. Xeon의 결과 코드 목록을 F 문서에서 확정한다.
