# L3-3. Helm·학습 그룹의 능력 요구와 L2-d 쓰기 API 구분

정본 아니다. `L3.helm.spec`, `L3.learning.spec`, `L2.knowledge.spec`, `L2.work.spec`, `L2.web.spec`을 쓸 때 근거로 인용한다.

## 0. 조사 범위와 기준

- 질문은 두 가지다.
  - (1) Helm과 학습 그룹이 `requires`·`optional`로 선언할 능력 ID와 서비스 키는 무엇인가.
  - (2) L2-d 쓰기 API가 제안 보관(승인 전), 승인 뒤 쓰기, 스캔, 원장 기록을 구분해 제공하는가.
- 근거의 순서는 다음과 같다. F 계약(`F/capabilities/spec.md`, `F/extensions/spec.md`), 승인 계획(`_research/foundation-plan.md`), 사용자 결정(`_research/decisions-log.md`), 층 구성 계획 v2(`_research/layer-plan-v2.json`, `layer-plan-v2-notes.md`), 엔지니어링·제품 문서, 조사 자료(`_research/refs/hermes.md`) 순이다.
- 확인 시점은 2026-10-21이다. 소스는 `xeon/packages/*/src/index.ts`를 읽었다. 모두 `export {};` 한 줄이다(예: `xeon/packages/cap-knowledge/src/index.ts` 1행). Hermes 저장소(커밋 `0319e113c9602b86ffda350e931cb4b035e1d5d8`, 작업 공간 `scratchpad/ext/hermes/repo`)는 읽기만 했고 실행하지 않았다.
- 표지는 다음과 같이 쓴다. `[결정]`은 사용자 결정이다. `[제안]`은 이 노트의 제안이다. `[가정]`은 확인하지 않은 전제다. `[미결]`은 사용자 확인이 필요한 항목이다. `[미확인]`은 확인하지 못한 것이다. 표지 없이 "문서 명시"라고 쓴 것은 해당 문서에 그대로 적혀 있다는 뜻이다.
- 이 시점에 없는 문서는 다음과 같다. 해당 문서가 생기면 §3과 §4를 다시 대조해야 한다.
  - `docs/xeon/L2/knowledge/spec.md`, `L2/work/spec.md`, `L2/web/spec.md`(병행 작성 중)
  - `docs/xeon/X/primitives/spec.md`(서비스 이름 유도 규칙, 사용 가능 여부 확인 API), `X/loading-trust/spec.md`
  - `docs/xeon/L1/agents/spec.md`(백그라운드 위임), `L3/helm/spec.md`, `L3/learning/spec.md`
  - `xeon/packages/contracts/src/capabilities/`(디렉터리 없음)

## 1. 요약

- 문서에 명시된 능력 ID는 `web.search` 하나다(F/capabilities 537행, ADR-0005 §3.4). 나머지 ID는 층 계획의 구성요소 이름과 F 예시 `knowledge.memory.read`(F/capabilities 78행)에서 이 노트가 제안했다. 모두 [제안]이다.
- 서비스 키는 두 체계가 충돌한다. F는 능력별 `ServiceKey`와 `ScopeApi.capability(key)`를 쓴다. 엔지니어링 문서 context-map §5.3은 `xeon.web`, `xeon.knowledge`, `xeon.work` 같은 도메인 단위 Cordis 이름을 쓴다(C1).
- L2-d 쓰기 API는 승인 전 보관, 승인 뒤 쓰기, 스캔, 원장 기록의 역할을 문서에서 구분하고 있다. 그러나 이를 공개 메서드로 나눴다는 근거는 없다. 보관 대기열의 소유도 L2-d(context-map)와 L3-c(계획 v2)로 갈린다(C2). 따라서 "구분해 제공한다"고 판정할 수 없다[미결].
- 학습 그룹은 drive를 쓰지 않는다[결정]. 그런데 검토 포크는 L1 백그라운드 위임으로 돌린다고 한다. `ScopeApi`에는 위임 호출 표면이 없고, `spawn`은 `drive` 함수가 받는 `LoopHandle`에만 있다(G1). 이 간극이 가장 큰 설계 문제다.
- Hermes 소스를 확인했다. 쓰기 뒤 스캔, 부수 효과로 쓰는 원장, 기본값 꺼짐이다. Xeon은 이 셋을 반대로 가야 한다[제안](§4.3).

## 2. 계약 기준 (F)

- 능력 ID 형식은 `^[a-z][a-z0-9-]{0,31}(\.[a-z][a-z0-9-]{0,31}){1,3}$`이다. 2~4 세그먼트이며, 첫 세그먼트가 L2 도메인 이름이면 내장 전용이다(F/capabilities 80행, 106행).
- 서비스 키는 `serviceKey(def)`가 만든다. 반환 타입은 `ServiceKey<CapabilityApi<D>>`이고 런타임 값은 `capability`와 `version`뿐이다(F/capabilities 282-292행).
- 그룹의 소비 경로는 `ScopeApi.capability(key)`다. 키의 능력은 매니페스트 `requires` 또는 `optional`에 있어야 한다(F/extensions 344행). 선언하지 않은 호출은 `validateUsage`의 `capability_undeclared` 오류다(F/extensions 808행).
- 매니페스트 요구 항목은 `{ id: CapabilityId, range: SemVerRange }` 형식이다(F/extensions 95-98행). `requires`와 `optional`을 같은 목록에 둘 수 없다(F/extensions 793행 `capability_both`).
- 능력 정의의 `requires`(F/capabilities 261행)는 능력이 다른 능력을 전제한다는 뜻이다. 매니페스트의 `requires`는 확장이 능력을 쓴다는 뜻이다. 이 노트는 후자만 다룬다.
- `optional`로 선언한 소비자는 호출 전에 사용 가능 여부를 확인해야 한다(F/capabilities 653행). 확인 API는 X.primitives가 정하므로 아직 없다[미확인].
- 그룹 경로의 서비스 호출은 tool 지점을 지나지 않는다(F/capabilities 542행). 따라서 쓰기 승인 게이트는 도구 훅에 두면 안 되고, 서비스 메서드 안에 있어야 한다[제안].
- 내장 L2 정의를 둘 위치는 `contracts/src/capabilities/defs/<domain>.ts`라는 제안이며 미결이다(F/capabilities 543행, §10).
- [결정] 학습 그룹은 drive를 쓰지 않으므로 Helm과 함께 켤 수 있다(`_research/decisions-log.md` 20행, `layer-plan-v2-notes.md` 40-41행, F/extensions 771행).

### 3.2 requires와 optional 제안

| 그룹 | requires [제안] | optional [제안] | 이유 |
|---|---|---|---|
| Helm | `web.search`, `knowledge.memory.read`, `knowledge.skill.read`, `knowledge.session.search`, `work.task.create` | `web.fetch`, `web.browse` | 탐구 루프의 검색, 지식 소비, 발견 기록 작업 연결은 없으면 기능이 비게 된다. 본문 읽기와 브라우저는 대체 경로가 있다 |
| 학습 그룹 | `knowledge.memory.read`, `knowledge.skill.read`, `knowledge.session.search`, `knowledge.change.propose` | 없음 | 중복 확인과 후보 보관이 필요하다. 적용 호출 주체는 G5에서 정한다 |

- Helm이 학습 결과를 읽는 경로는 `readsRecordKinds: ["grp.learning.*"]`와 `readRecords`, 그리고 `knowledge.skill.read` 검색이다. 학습 그룹의 능력을 직접 요구하지 않는다(F/extensions 826행, `layer-plan-v2-notes.md` 42행). context-map CM-06 예시(526행)도 같은 방식이다.
- 학습 그룹의 레코드 쓰기는 `ScopeApi.record`로 하며 능력이 아니다. 종류는 `grp.learning.skill.proposed`다(F/extensions 824행, 826행).
- Helm의 탐구 구동이 쓰는 `loop.turn`과 `loop.spawn`은 능력이 아니다(F/extensions 289-291행, `LoopHandle`).

### 3.3 requires 미충족의 처리

- 집합 검사는 미충족 `requires`를 경고로만 낸다(F/extensions §4.7 818행 `capability_unprovided`, F/capabilities 648행 `requires_unresolved`). 그룹 로드를 거부하는지는 X.loading-trust가 정하므로 [미확인]이다.

## 4. L2-d 쓰기 API: 역할 구분과 메서드 표면

### 4.1 문서가 가진 신호

| 역할 | 문서 위치 | 메서드 표면 | 판정 |
|---|---|---|---|
| 제안 보관(승인 전) | context-map 68행 `cap_knowledge_*`의 "제안 대기열". UC-3 4단계 "후보는 승인 대기열에 들어간다"(128행). layer-plan L3-c "승인 대기열"(1531행, 자체) | 없음 | 역할 있음. 소유 상충(G2) |
| 승인 결정 | context-map 68행이 `xeon.approvals`를 소비한다. 계획 v2의 L1 승인 프로토콜 | L1 ApprovalService | L2-d 바깥 |
| 스캔 | layer-plan L2-d "쓰기 승인과 스캔"(1068행). UC-3 대안 흐름 "쓰기 스캔 실패 시 L2-d 쓰기 승인과 스캔이 거부하고 후보를 거절 상태로 둔다"(134행) | 없음 | 쓰기 경로 안에 있다고 읽힌다. 별도 노출 여부는 [미확인] |
| 승인 뒤 쓰기 | UC-3 6단계 "승인한 후보만 L2-d 저장소에 쓰고 변경 원장에 기록한다"(130행) | 없음 | 역할 있음. 메서드 없음 |
| 원장 기록 | layer-plan L2-d 1061행, UC-3 130행 | 없음 | 역할 있음. 쓰기와 같은 트랜잭션인지는 [미결] |
| 롤백 | layer-plan L2-d 1061행, UC-3 135행 | 없음 | 역할 있음 |

결론은 다음과 같다. 역할 구분은 문서에 있다. 그러나 이를 공개 메서드로 나눴다는 문서는 없다. 따라서 L2-d 쓰기 API가 구분해 제공한다고 판정할 수 없다[미결].

### 4.2 참고: Hermes 소스 확인 (커밋 0319e113)

- 보관과 쓰기의 분리. `tools/write_approval.py` 74-86행 `stage_write`는 `payload`를 "승인 시 쓰기를 재생하는 정확한 인자"로 저장한다. 201-213행 `evaluate_gate`는 스킬 쓰기를 항상 스테이징하고 메모리 쓰기는 대화형일 때만 인라인 확인한다. 77-78행에 따르면 디스크 쓰기가 실패해도 레코드를 돌려주며, 이는 보관이 best-effort라는 뜻이다[원문].
- 스캔은 쓰기 뒤에 한다. `tools/skill_manager_tool.py` 395-415행 `_guarded_write`는 원자 쓰기, 스캔, 차단 시 원복 순서다. 차단되기 전까지 검사되지 않은 내용이 디스크에 있다[원문].
- 원장은 부수 효과다. 731-745행 `_record_success`는 `suppress(Exception)` 안에서 원장을 쓴다. `tools/skill_ledger.py` 7행은 "TELEMETRY, NOT A GATE"라고 적는다. 원장 쓰기가 실패해도 변경은 남는다. 롤백만 닫힌 상태로 실패한다(`skill_ledger.py` 1-10행)[원문].
- 기본값은 꺼짐이다. `hermes_cli/config_defaults.py` 1333행(메모리 `write_approval` false), 1488행(`guard_agent_created` false), 1497행(스킬 `write_approval` false). 기본 설정에서 승인과 스캔이 모두 꺼진다[원문].
- 이 확인은 `_research/refs/hermes.md` 25-29행, 248-253행, 261-262행의 서술과 맞는다.

### 4.3 제안: Xeon L2-d 쓰기 경로 [제안]

1. 게이트 위치: 승인과 스캔은 서비스 메서드 안에 둔다. 도구 경로(`tool_call` 지점)와 그룹 경로(서비스 직접 호출)가 모두 이 메서드를 지난다(F/capabilities 542행).
2. 제안 보관: `propose`는 스캔 결과와 함께 대기열 행을 저장하고, 스킬이나 메모리 파일은 바꾸지 않는다. 행 저장과 실패 응답을 한 트랜잭션에 둔다. Hermes처럼 best-effort로 보관하지 않는다.
3. 승인 뒤 쓰기: `apply`는 승인된 내용의 해시를 확인하고, 스캔을 다시 하고, 파일 쓰기와 원장 행을 한 트랜잭션에 넣는다. 단일 DB 결정(ADR-0004)이 이를 가능하게 한다.
4. 기본값은 켜짐이다(layer-plan L2-d 1068행, L3-c 1514행). Hermes 기본 꺼짐과 다르며, 이는 의도된 차이다.
5. 롤백: 원장 행의 after 해시가 현재 내용과 같을 때만 되돌린다. 다르면 거부한다.

## 5. 상충과 미결

- C1 서비스 키 이름. F/capabilities 297행은 Cordis 서비스 이름을 X가 `CapabilityId`에서 유도한다고 쓴다. context-map 332-334행은 `xeon.web`, `xeon.knowledge`, `xeon.work`와 인터페이스 `WebService`, `KnowledgeService`, `WorkService`를 쓴다. 두 규칙은 함께 성립하지 않는다. CM-04에 따라 context-map을 먼저 고칠 수 있다[미결].
- C2 제안 대기열의 소유. context-map 68행(L2-d), layer-plan L3-c 1531행(그룹 자체), UC-3 128행과 139행(L4 데스크톱 승인 대기열)이 서로 다르다. [제안] 데이터는 L2-d가 소유하고, 승인 결정은 L1-d 승인 프로토콜이 하며, 목록 화면은 L4가 그린다.
- C3 접근 경로. context-map 74행과 75행(helm, learning 행)과 CM-06 예시(526행)는 `inject`로 `xeon.knowledge`, `xeon.work`, `xeon.agents`를 직접 주입한다. F는 `ScopeApi.capability(key)`만 허용하고 미선언 호출을 `validateUsage`로 거부한다(F/extensions 808행). `inject` 경로는 이 검사를 건너뛴다. 한 가지 규칙으로 정해야 한다[미결].
- G1 백그라운드 위임 표면이 없다. layer-plan L3-c 1524행과 `layer-plan-v2-notes.md` 40-41행은 검토 포크를 L1-g 백그라운드 위임으로 돌린다고 한다. F/extensions 770-771행도 백그라운드 위임을 여러 그룹이 함께 쓴다고 쓴다. 그런데 `ScopeApi`(F/extensions 334-349행)에는 위임 메서드가 없다. `spawn`은 `LoopHandle`(289-291행)에만 있고 `drive` 함수에만 주어진다. 학습 그룹은 drive를 쓰지 않으므로 호출 경로가 없다[미결].
- G2 쓰기 대기열과 보관의 소유. C2와 같다. 쓰기 API가 보관 메서드를 가질지도 여기서 정한다[미결].
- G3 능력 ID의 단위. F 예시는 관심사별 세 세그먼트(`knowledge.memory.read`)를 쓴다. context-map CM-06 예시는 `knowledge.search({ kinds })`처럼 하나로 묶는다. 관심사별로 나눌지, 도메인 하나에 메서드를 여럿 둘지 정해야 한다[미결].
- G4 도구 없는 쓰기 능력. 학습 쓰기는 모델 도구가 없어도 된다. F/capabilities 596행은 `tools: []`를 허용하되 확정은 미결이라고 적는다.
- G5 적용 호출 주체. 사용자가 승인한 뒤 누가 `apply`를 부르는지 문서에 없다. 후보는 L4 → L1-d 승인 응답 → L2-d 콜백, 또는 학습 그룹 호출 중 하나일 수 있다[미결].
- G6 requires 미충족의 로드 처리. §3.3에서 확인하지 못했다[미확인].
- G7 정의 위치. F/capabilities 543행과 §10 미결이다[미결].
