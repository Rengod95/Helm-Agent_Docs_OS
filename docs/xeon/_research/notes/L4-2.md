# 조사 L4-2: bun build --compile 사이드카의 macOS 서명과 공증 절차

## 1. 질문과 범위

- 질문: `bun build --compile`로 만든 macOS 바이너리를 Tauri 2 사이드카(`bundle.externalBin`)로 넣어 공증(notarization)할 때 필요한 절차는 무엇인가.
- 확인 항목은 네 가지다.
  1. Bun 산출물에 필요한 hardened runtime entitlements (JIT, unsigned executable memory 등)
  2. Tauri 번들러가 externalBin과 리소스 dylib(FTS5용 커스텀 SQLite)을 자동 서명하는지
  3. 수동 codesign이 필요한 대상
  4. 공증 요건과 검증 방법
- 범위 밖: Windows 서명, Linux 빌드, 사이드카 크기(arch-2 §4.2에서 [미확인]으로 남긴 항목), 자식 프로세스 수명.
- [결정] 엔진은 `bun build --compile` 사이드카로 넣고, UI와는 stdio JSON-RPC로 잇는다. 근거: `foundation-plan.md §1` 3번.
- [결정] macOS에서 FTS5가 포함된 SQLite는 `Database.setCustomSQLite`로 지정한다. 근거: `foundation-plan.md §2` DB 행.
- [결정] 사이드카 크기와 Windows 서명은 L4 plan에서 다룬다. 근거: `foundation-plan.md §7` 위험 목록 마지막 항목. 이 문서는 macOS 절차만 다룬다.

## 2. 결론

1. 자동 서명 범위: Tauri 번들러는 `bundle.externalBin`의 사이드카와 `bundle.macOS.frameworks`로 지정한 dylib을 서명 대상에 넣는다. `bundle.resources`로 복사되는 파일은 서명 대상에 들어가지 않는다 (§6).
2. 사이드카는 `hardened_runtime` 기본값(true)에 따라 `--options runtime`으로 서명된다. 별도 설정이 없어도 hardened runtime이 켜진다 (§6).
3. entitlements: Bun 공식 예시에 있는 다섯 키 중 출발점은 JIT 관련 두 키다 [제안]. 두 키의 실제 필요 여부는 실측으로 정한다. 나머지 세 키는 근거가 없거나 Apple 문서와 충돌하므로 실측 뒤에 넣는다. `disable-library-validation`은 Apple 문서가 플러그인을 호스트하지 않는 실행 파일에는 쓰지 말라고 한다 (§5).
4. 한계: Tauri는 `bundle.macOS.entitlements` 하나를 모든 서명 대상에 똑같이 붙인다 (`sign.rs:53-68`). 사이드카에만 JIT 권한을 주려면 자동 서명을 끄고 수동 서명 파이프라인을 써야 한다 [제안] (§9).
5. 타임스탬프: Tauri가 호출하는 `codesign` 인자 목록에 `--timestamp`가 없다 (`keychain.rs:221-239`). Apple은 보안 타임스탬프를 공증 요건으로 든다. 실제 실패 여부는 미확인이다 (§7).
6. 공증 요건: Developer ID Application 인증서, hardened runtime, 보안 타임스탬프, `get-task-allow` 금지가 핵심이다 (§10). 공증 대상은 `.app` 번들이다 (`app.rs:140`).
7. 실측 없음: 이 조사는 Linux 환경에서 소스와 문서만 대조했다. macOS에서 실제로 서명과 공증을 통과시킨 결과는 확인하지 못했다 [미확인].

## 4. Bun 산출물의 서명 상태

### 4.1 Bun이 자동으로 붙이는 서명

- arm64 Mach-O 출력에는 Bun이 ad hoc 서명을 붙인다. 조건은 `CPU_TYPE_ARM64`이고 `BUN_NO_CODESIGN_MACHO_BINARY` 플래그가 꺼져 있을 때다 (`macho.rs@bun-v1.4.3:518-520`).
- 코드 디렉터리 flags는 `0x20002`다 (`macho.rs@bun-v1.4.3:723`). `cs_blobs.h`의 상수로 보면 `CS_ADHOC`(0x2)과 `CS_LINKER_SIGNED`(0x20000)다. `CS_RUNTIME`(0x10000)은 없다.
- 따라서 Bun이 붙인 서명만으로는 hardened runtime이 켜지지 않는다.
- x86_64 Mach-O는 이 함수의 else 분기에서 그냥 쓰인다 (`macho.rs@bun-v1.4.3:518-528`). 이 경로에서는 서명하지 않는다. 템플릿 바이너리의 기존 서명 상태는 [미확인]이다.
- Tauri는 `codesign --force`로 서명하므로 기존 서명을 교체한다 (`keychain.rs:221`). Bun의 서명은 배포 빌드에서 남지 않는다.
- [미확인] `build_and_sign` 호출이 호스트 OS와 무관하게 darwin 대상 교차 컴파일에서도 실행되는지는 확인하지 못했다. 상위 `cfg` 조건을 대조하지 않았다 (`StandaloneModuleGraph.rs:2417-2442`).

### 4.2 Bun 공식 서명 절차

- 절차 (`executables.mdx@bun-v1.4.3:1134-1175`): `codesign --deep --force -vvvv --sign ID [--entitlements entitlements.plist] ./myapp`, 검증은 `codesign -vvv --verify ./myapp`. Bun v1.2.4 이상이 필요하다.
- Bun 가이드도 같은 절차다. 인자 순서만 다르다 (`--entitlements`를 앞에 둔다).
- Bun 문서는 `--options runtime`과 `--timestamp`를 쓰지 않는다. 줄 범위 안에 없다. 공증 요건은 §10의 Apple 원문으로 채운다.
- Bun 문서의 plist 키는 다섯 개다 (`executables.mdx@bun-v1.4.3:1147-1158`): `allow-jit`, `allow-unsigned-executable-memory`, `disable-executable-page-protection`, `allow-dyld-environment-variables`, `disable-library-validation`.

## 5. Entitlements 판단

| 키 | Bun 문서 | 근거 | 판단 |
|---|---|---|---|
| `com.apple.security.cs.allow-jit` | 포함 | hardened runtime은 JIT을 제한한다. 제한된 기능은 개별 예외 entitlement로 푼다. "Make sure to use only the entitlements that are absolutely necessary for your app's functionality." (hardened-runtime DocC) | [제안] 포함 |
| `com.apple.security.cs.allow-unsigned-executable-memory` | 포함 | Apple 본문에서 정의를 확인하지 못했다 [미확인] | [제안] `allow-jit`으로 부족할 때만. macOS 실측으로 결정 |
| `com.apple.security.cs.disable-executable-page-protection` | 포함 | 근거 미확인 [미확인] | [제안] 제외하고 실측 |
| `com.apple.security.cs.allow-dyld-environment-variables` | 포함 | 근거 미확인 [미확인] | [제안] 제외하고 실측 |
| `com.apple.security.cs.disable-library-validation` | 포함 | "Don't disable library validation for executables that don't host plug-ins because library validation protects them from loading untrusted code." (resolving-issues DocC) | [제안] 제외. 대신 dylib을 같은 식별자로 서명 |
| `com.apple.security.get-task-allow` | 없음 | "Don't include the com.apple.security.get-task-allow entitlement with the value set to any variation of true." (notarizing DocC) | 금지 |

- 상속: "You add entitlements only to executables. Shared libraries, frameworks, and in-process plug-ins inherit the entitlements of their host executable." (hardened-runtime DocC). 따라서 dylib에 별도 entitlements를 줄 이유가 없다 [제안]. Tauri는 같은 plist를 dylib에도 붙인다 (`sign.rs:53-68`). 그 결과가 공증에 문제인지는 [미확인]이다.
- 앱 본체: 사이드카에만 JIT이 필요하다면 본체 entitlements는 비우는 것이 맞다 [제안]. WKWebView가 별도 프로세스로 도는지는 이번 조사에서 확인하지 않았다 [가정].
- 최소 집합 확정: macOS에서 `codesign -d --entitlements :- <경로>`로 확인하고, 실제 실행 테스트로 막힘 여부를 본다 [미확인].

## 6. Tauri 번들러의 자동 서명 범위

| 대상 | 번들 내 위치 | 서명 대상 등록 | runtime 옵션 | 근거 |
|---|---|---|---|---|
| 앱 메인 바이너리 | `Contents/MacOS/` | 등록 (`is_an_executable: true`) | 예 | `app.rs:107-110` |
| externalBin 사이드카 | `Contents/MacOS/<이름>` (triple 접미사 제거) | 등록 (`is_an_executable: true`) | 예 | `app.rs:99-105`, `settings.rs:1204-1216`, `sign.rs:68` |
| frameworks 디렉터리 | `Contents/Frameworks/` | 등록 | 아니오 (`is_an_executable: false`) | `app.rs:382-392`, `app.rs:461` |
| frameworks의 `.dylib` | `Contents/Frameworks/<이름>.dylib` | 등록 (`is_an_executable: false`) | 아니오 | `app.rs:404-416` |
| `bundle.resources` | `Contents/Resources/` | 등록 없음. 복사만 한다 (`settings.copy_resources`) | 없음 | `app.rs:97` |
| `.app` 번들 | 최상위 | 등록 (`is_an_executable: true`) | 예 | `app.rs:120-127` |
| DMG | 배포 파일 | 서명 (`is_an_executable: false`). 공증 호출은 없다 | 아니오 | `dmg/mod.rs:193-206` |

- 서명 인자: `codesign --force -s <ID> [--options runtime] [--keychain <경로>] [--entitlements <plist>] <경로>` (`keychain.rs:221-239`). `--deep`은 쓰지 않는다.
- 서명 순서: "Sign frameworks and sidecar binaries first, per apple, signing must be done inside out" (`app.rs:120`). 안쪽(프레임워크, 사이드카)이 먼저, `.app`이 마지막이다.
- entitlements: `settings.macos().entitlements` 하나를 모든 대상에 적용한다 (`sign.rs:53-68`).
- 서명 생략: identity가 없고 `APPLE_CERTIFICATE`도 없으면 `keychain()`이 `None`을 반환한다 (`sign.rs:19-42`). 그 경우 서명과 공증 블록이 통째로 건너뛰어진다 (`app.rs:115-117`). 로컬 개발 빌드에서는 Bun의 ad hoc 서명만 남는다.
- ad hoc 서명 설정(`"signingIdentity": "-"`)도 Tauri 문서에 있다 (`tauri-docs Sign/macos.mdx:211`). Apple 공증은 Developer ID 인증서로 서명한 것만 받는다 (resolving-issues DocC: "You can only notarize apps that you sign with a Developer ID certificate."; `tauri-docs Sign/macos.mdx:184`). 따라서 ad hoc 서명은 배포 빌드에 쓸 수 없다.

## 7. 타임스탬프와 공증 자격 증명

- Apple 요건: "Include a secure timestamp with your code-signing signature." 수동 서명에서는 `codesign`에 옵션을 직접 준다 (resolving-issues DocC: "by using the option directly with the codesign utility if you sign manually").
- Tauri의 `codesign` 인자 목록(`keychain.rs:221-239`)에는 `--timestamp`가 없다. 실패로 이어지는지는 [미확인]이다. `codesign` 기본 동작을 실측하지 않았다.
- 확인 방법: `codesign -dvv <경로>` 출력에 `Timestamp` 행이 있으면 타임스탬프가 있다. `Signed Time` 행만 있으면 없다 (resolving-issues DocC 설명).
- 공증 자격 증명: `APPLE_API_KEY`, `APPLE_API_ISSUER`, `APPLE_API_KEY_PATH` 또는 `APPLE_ID`, `APPLE_PASSWORD`, `APPLE_TEAM_ID` (`sign.rs:96-160`, `tauri-docs Sign/macos.mdx:161-181`). `APPLE_ID` 조합에서 `APPLE_TEAM_ID`가 없으면 오류다 (`sign.rs:110`).
- 무료 Apple 개발자 계정은 공증이 안 된다 (`tauri-docs Sign/macos.mdx:18`).

## 8. FTS5 커스텀 SQLite dylib

- Bun: `Database.setCustomSQLite(path)`에는 SQLite `.dylib` 파일 경로를 넘긴다. 실행 파일 경로가 아니다. 모든 `Database` 생성 전에 호출한다 (`sqlite.mdx@bun-v1.4.3:646` 부근).
- 번들 위치: `bundle.macOS.frameworks`에 dylib을 넣는다 [제안]. Tauri가 `Contents/Frameworks/`로 복사하고 서명한다 (`app.rs:404-416`). `bundle.resources`에 넣으면 서명 등록이 없다 (`app.rs:97`).
- 서명 ID: 프레임워크 dylib은 같은 identity로 서명된다. 같은 Team ID이면 library validation을 통과한다는 규칙은 Apple 원문에서 확인하지 못했다 [미확인]. WebFetch 요약에는 있었으나 DocC 본문에는 없었다.
- 경로 해석: 사이드카 실행 파일 기준 상대 경로(예: `../Frameworks/libsqlite3.dylib`)를 쓰고 절대 경로로 고정한다 [제안]. Bun 문서는 상대 경로를 현재 작업 디렉터리 기준으로 해석한다고 적는다 (`arch-2.md §4.2`).
- 외부 경로 dylib 금지 [제안]: Homebrew 등 외부 dylib은 번들 identity와 다르므로 library validation에서 막힐 가능성이 있다 [미확인].
- FTS5 존재 확인: 시작할 때 검사한다 (`foundation-plan.md §2`, `§7`).

## 9. 수동 codesign이 필요한 대상

| 상황 | 수동 필요 대상 | 이유 |
|---|---|---|
| FTS5 dylib을 `bundle.resources`에 둘 때 | dylib | 서명 등록이 없다 (`app.rs:97`) |
| 사이드카에만 JIT 권한을 줄 때 | 사이드카 (앱 본체는 빈 entitlements) | Tauri가 entitlements를 모든 대상에 같게 붙인다 (`sign.rs:53-68`) |
| 타임스탬프가 빠졌을 때 | 모든 Mach-O와 `.app` | `keychain.rs:221-239`에 `--timestamp`가 없다 |
| 자동 서명을 끌 때 | 전부, 그리고 공증 | identity가 없으면 서명과 공증이 생략된다 (`sign.rs:19-42`) |
| DMG를 배포할 때 | DMG 공증과 staple [미확인] | `dmg/mod.rs`에 공증 호출이 없다 |

수동 파이프라인 예시. 실행하지 않았다. 명령 형태는 일반 사용법이며 [가정]이다. 옵션 세부는 Apple 원문으로 대조하지 않았다 [미확인].

```sh
# 안쪽 → 바깥쪽 순서. 식별자와 프로필은 환경 변수로 넘긴다. 값은 출력하지 않는다.
codesign --force --options runtime --timestamp -s "$IDENTITY" Xeon.app/Contents/Frameworks/libsqlite3.dylib
codesign --force --options runtime --timestamp --entitlements engine.entitlements -s "$IDENTITY" Xeon.app/Contents/MacOS/xeon-engine
codesign --force --options runtime --timestamp -s "$IDENTITY" Xeon.app
codesign --verify --deep --strict --verbose=2 Xeon.app
ditto -c -k --keepParent Xeon.app Xeon.zip
xcrun notarytool submit Xeon.zip --keychain-profile "$PROFILE" --wait
xcrun stapler staple Xeon.app
```

- `--deep`은 검증에만 쓴다. Apple 원문도 검증 목적으로 설명한다 (resolving-issues DocC: "You use the deep option to ensure the utility checks nested code content").

## 10. 공증 요건 (Apple 원문)

notarizing DocC 본문의 요건이다.

- "Enable code-signing for all of the executables you distribute, and ensure that executables have valid code signatures"
- "Use a 'Developer ID' application ... certificate for your code-signing signature. (Don't use a Mac Distribution, ad hoc, Apple Developer, or local development certificate.)"
- "Enable the Hardened Runtime capability for your app and command line targets"
- "Include a secure timestamp with your code-signing signature."
- "Don't include the com.apple.security.get-task-allow entitlement with the value set to any variation of true."
- "Link against the macOS 10.9 or later SDK" (Bun 바이너리의 SDK 버전은 [미확인])

- 사이드카는 "command line target"에 해당하므로 hardened runtime이 필요하다 [가정].
- "all of the executables you distribute": Resources 안의 Mach-O를 실행 파일로 보는지는 [미확인]이다. 보수적으로 모든 Mach-O에 서명하는 것을 권한다 [제안].

## 11. 제안 (L4 plan 입력)

1. 번들 구성 [제안]: 엔진은 `externalBin`, FTS5 dylib은 `bundle.macOS.frameworks`에 둔다. `bundle.resources`에 Mach-O를 두지 않는다. CI에서 `Contents/Resources` 아래 Mach-O를 찾는 검사를 넣는다.
2. entitlements [제안]: 최소 집합을 실측해서 확정한다. `disable-library-validation`은 넣지 않는다.
3. 서명 방식 [미결]: (a) Tauri 자동 서명을 쓰고 entitlements 공유와 타임스탬프 부재를 감수한다. (b) 자동 서명을 끄고 수동 파이프라인으로 사이드카 전용 entitlements와 `--timestamp`를 준다.
4. 검증 CI [제안]: `codesign -dvv`로 Timestamp 행 확인, `codesign --verify --deep --strict`, `xcrun notarytool log`로 공증 로그 보관, `xcrun stapler validate`.
5. 경로와 환경 [제안]: `arch-2.md §4.2`와 같다. 엔진 경로를 절대 경로로 고정하고, `BUN_OPTIONS`를 엔진 환경에서 제거한다.

## 12. 미확인과 미결

- [미확인] 실제 Bun 1.4.3 산출물의 macOS 서명과 공증 통과 여부. 이 조사는 macOS 실측을 하지 않았다.
- [미확인] JSC가 필요로 하는 최소 entitlement 조합.
- [미확인] `codesign` 기본 타임스탬프 동작. Tauri 2.12 경로에서 공증이 실제로 실패하는지.
- [미확인] Resources 안의 Mach-O를 공증 검사가 실행 파일로 보는지.
- [미확인] DMG 공증이 필요한지와 Tauri의 DMG 서명 설정(`dmg/mod.rs:193-206`)이 충분한지.
- [미확인] Apple 원문의 "같은 Team ID" library validation 규칙, `allow-unsigned-executable-memory`의 정의. DocC 본문에서 찾지 못했다.
- [미확인] `build_and_sign`의 교차 컴파일 조건과 x86_64 템플릿 서명 상태.
- [미확인] universal 빌드(두 triple의 lipo)와 그 서명 순서.
- [미결] 서명 방식 (§11-3). 사용자 확인이 필요하다.
- [미결] 배포 채널: DMG 배포 여부, Developer ID Application 인증서와 공증 계정의 보유 여부.
