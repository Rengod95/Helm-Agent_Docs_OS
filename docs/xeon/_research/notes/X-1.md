# X-1 조사: pi 메시지 주입 경로의 큐 위치와 요청 시작 규칙

- 대상: pi 확장의 주입 경로 셋이다. `sendMessage`의 `deliverAs`·`triggerTurn`, `sendUserMessage`의 `deliverAs`, 경계 지점 `turn_end`·`agent_before_settle`의 `continue: true`. 각 경로가 메시지를 어느 큐에 넣는지, 요청을 호출 없이 시작하는지 확인한다.
- 목적: ADR-0007 §6의 `post.when = next` 미결 항목과 pi 어댑터의 `sendMessage` 매핑에 근거를 준다.
- 근거 계획: `_research/foundation-plan.md` §2(pi-agent-core 고정), `_research/ext-points.md` §1.2, `decisions/ADR-0007-ext-points.md` §3.1·§6.
- 성격: 조사 결과다. 정본이 아니며 인용용이다. 소스 읽기만 했고 코드는 실행하지 않았다.
- 표지: [결정] 사용자 결정 인용, [제안] 작성자 설계 선택, [가정] 확인하지 않은 전제, [미결] 사용자 확인 필요, [미확인] 확인하지 못한 것.

## 0. 결론

1. `deliverAs: "nextTurn"`은 요청을 시작하지 않는다. 메시지는 메모리 배열 `_pendingNextTurnMessages`에 남고, 유휴 상태에서 실행되는 다음 `prompt()`가 사용자 메시지 뒤에 붙여 소비한다. 이 경로에서 `triggerTurn` 값은 읽히지 않는다(`CA/agent-session.ts:398, 2306-2307, 2088-2092`).
2. 요청을 호출 없이 시작하는 경로는 둘뿐이다. 유휴 상태의 `sendMessage(…, {triggerTurn: true})`가 즉시 실행을 시작하는 경로(`CA/agent-session.ts:2314-2319`)와, 경계 지점의 `continue: true`(조건부, §3)다.
3. 실행 중에는 `triggerTurn`이 `false`가 아니면 메시지가 steer 큐에 들어간다(`deliverAs: "followUp"`이면 followUp 큐). `triggerTurn`을 생략해도 이 분기가 선택된다(`CA/agent-session.ts:2308-2313`). 두 큐는 같은 실행 안에서 소비되므로 실행 중에는 사용자 입력 없이도 요청이 한 번 더 나간다.
4. `continue: true`는 큐가 아니다. 불리언 플래그다. 요청이 나가려면 마지막 메시지가 사용자·도구 결과·커스텀 메시지 중 하나이거나 큐에 입력이 있어야 한다. 조건을 만족하지 않으면 요청은 나가지 않고 `<boundary>` 오류만 보고된다(`CA/agent-session.ts:879-882, 999-1021, 1906-1910`).
5. 대기 중 사용자 입력이 있을 때만 붙는지에 대한 답은 다음과 같다. `nextTurn`은 그렇다. 다음 사용자 입력이 와야 붙는다. `continue`는 아니다. 입력 없이 맥락 조건만으로 요청을 만든다. steer와 followUp은 실행 중에만 소비되므로 실행이 살아 있으면 입력 없이도 소비된다.
6. 소비 순서는 steer, followUp, 맥락만 있는 요청(explicit continuation)이다(`AG/agent-loop.ts:294-314`). followUp이 있으면 explicit continuation은 소멸한다(`AG/agent-loop.ts:302-307`).
7. 대기 항목 저장소 넷(steer, followUp, nextTurn, pendingCustom)은 모두 프로세스 메모리에 있다. 세션 기록은 소비 시점에만 생긴다. 프로세스가 끝나면 소비되지 않은 항목은 남지 않는다(§6).
8. [제안] ADR-0007 §3.1의 `next` 대응 행은 두 기능을 한 항목에 합쳤다. pi에서 "다음 사용자 입력에 붙기"는 `nextTurn`이, "경계 뒤 요청을 시작하기"는 `continue`가 맡는다. §4에서 두 안을 비교하고 권고안을 낸다.

## 3. continue: true의 조건과 실패

### 3.1 경계 결과 합성

- 핸들러는 등록 순서대로 실행된다. 각 핸들러는 지금까지의 `entries`와 `continue` 값을 이벤트로 받는다(`EXT/runner.ts:1029-1044`).
- `entries`는 반환되면 덮어쓴다. 누적은 핸들러가 이전 배열을 포함해 돌려주는 방식으로만 된다(`EXT/runner.ts:1029-1076`).
- `continue`는 마지막으로 정의된 값이 이긴다(같은 범위).
- 핸들러가 던지면 그 오류만 보고되고 나머지 핸들러는 계속 실행된다(같은 범위의 catch).
- 마지막 `buildContext`가 실패하면 `entries`와 `continue`를 모두 버린다(`valid: false`, `EXT/runner.ts:1075-1076` 부근).
- 공식 선언: `BoundaryResult`는 `{entries?, continue?}`다(`EXT/types.ts:994-997`). "May append entries and ensure one next provider request"(`EXT/types.ts:999`).

### 3.2 검사

- `turn_end`: 엔트리를 커밋한 뒤 `_buildBoundaryContext([], "turn_end").canContinue`가 거짓이면 `continue`를 무시하고 오류를 보고한다(879-882).
- `agent_before_settle`: 같은 검사를 하고, `shouldContinue = continue || 큐 있음`으로 정한다. 검사에 걸리면 `continue`가 `true`였을 때만 오류를 보고한다(1906-1910).
- `canContinue`(999-1021)는 다음 중 하나가 참이면 참이다. 마지막 LLM 메시지가 `assistant`가 아니다. 펜딩 커스텀 메시지가 있다. 큐가 있다. `agent_before_settle`은 마지막이 `assistant`일 때 큐 조건만 인정한다.
- 실패: `<boundary>` 확장 오류 `"<event> requested continuation without runnable model context"`(1030-1036). 요청은 나가지 않는다.

### 3.3 요청이 나가는 방식

- turn_end 경로: `finishTurn`이 `{action:"continue"}`를 돌려주면 `explicitContinuation`이 참이 된다(`AG/agent-loop.ts:286-294`). 그다음 steer 큐를 폴링한다. 큐가 비고 도구 호출도 없으면 followUp을 확인한다. followUp이 있으면 그 항목이 요청을 만들고 플래그는 꺼진다(302-307). 둘 다 없으면 맥락만 있는 요청이 한 번 나간다(311-314). 이 요청은 주석 그대로 "one context-only turn"이다.
- agent_before_settle 경로: `_runAgentPrompt` 루프가 `agent.continue()`를 부른다(1833-1842). 마지막 메시지가 assistant이면 steer를, 그다음 followUp을 꺼내 실행한다. 둘 다 없으면 오류다(`AG/agent.ts:384-411`). 마지막 메시지가 사용자·도구 결과·커스텀이면 `runContinuation`이 현재 전사로 실행한다(`AG/agent.ts:448-456`).
- 커스텀 메시지는 LLM에 `user` 역할로 변환된다(`CA/messages.ts:162-168`). 경계에서 추가한 커스텀 엔트리는 다음 요청에서 사용자 메시지처럼 작동한다.
- 연속 상한: pi 코드에는 연속 `continue`의 상한이 없다. `_runAgentPrompt`의 `while`(1833-1842)과 `explicitContinuation` 재진입(`AG/agent-loop.ts:311-314`)에 카운터가 없다. 공식 문서도 "an unconditional continuation can loop"라고 경고한다(`DOC/extensions.md:117`).

## 4. post.when = next의 의미(ADR-0007 §6)

### 4.1 확인된 사실

- pi `nextTurn`은 요청을 시작하지 않는다. 다음 사용자 입력에 붙는 대기 항목이다(2306-2307, 2088-2092).
- 소비된 `nextTurn` 메시지는 사용자 메시지 뒤, 실행 시작 메시지 배열에 들어간다(2088-2110). 실행 시작 메시지는 전사에 기록되므로 이후 요청의 맥락에도 남는다. "정확히 한 요청에 들어간다"와 다르다.
- 사용자 입력이 오지 않으면 대기 항목은 메모리에 남는다. 시작 조건이 없다.
- 호출 없이 요청을 시작하는 pi 경로는 둘뿐이다. 유휴 `triggerTurn`(2314-2319)과 경계 `continue`(§3)다. 둘 다 "다음 사용자 입력에 붙기"가 아니다.
- ADR-0007 §3.1 `next` 행의 문구 "경계 뒤 정확히 한 요청에 들어간다"는 pi의 두 기능을 합친 것이다. ADR §6이 세운 [가정] "pi nextTurn의 정확한 동작은 확인하지 않았다"는 이 조사로 확인되었다.

### 4.2 xeon 안

[결정] 연산 4개(`on`, `post`, `drive`, `scope`)와 `post`의 `when` 세 값은 사용자 확인 범위다(ADR-0007 §1, `_research/decisions-log.md` 20행). 이 절은 `when` 값의 뜻만 다룬다.

| 안 | `post.when = next` 뜻 | 시작 주체 | 장점 | 단점 |
|---|---|---|---|---|
| 1. pi 그대로 | 다음 사용자 입력에 붙고 시작하지 않는다 | 사용자 입력 또는 `drive` | pi `nextTurn`과 1:1이다. 주입과 구동의 구분을 지킨다 | 경계 뒤 요청을 원하는 사용처는 `drive`를 써야 한다 |
| 2. 시작 포함 | 경계 뒤 요청 1회를 시작한다 | `post` 자체 | 사용처가 단순하다 | pi에 1:1 대응이 없다. 어댑터가 `continue`와 엔트리 조합으로 흉내를 내고 `canContinue` 조건을 맞춰야 한다 |
| 3. 시작 값 분리 | `next`는 안 1. 시작 값 `start`를 따로 둔다(유휴면 즉시 실행, 실행 중이면 followUp 큐) | `post(start)` 또는 `drive` | pi 유휴 `triggerTurn`(2314-2319)과 1:1이다. 시작 의미가 `when`에 명시된다 | `when` 값이 4개가 된다. ADR §3.1 표를 고쳐야 한다 |

- [제안] 안 1과 안 3을 합쳐 권고한다. `post`는 주입만 하고, 시작은 `drive`(구동)와 `start` 값으로만 한다. 근거는 두 가지다. ADR-0007 §3.1이 `post`를 "4 주입", `drive`를 "5 구동"으로 나눴다. pi에서 자가 시작은 경계 `continue`가 맡는데, 이는 ADR의 `drive`가 경계마다 다시 호출되는 규율과 같은 계열이다.
- [미결] 유휴 상태에서 `post`가 어떻게 동작할지 ADR에 정의가 없다. 시작할지, 오류로 할지, 보관만 할지를 정해야 한다. 이 항목은 안 3을 채택하든 안 1로 가든 남는다.
- [미결] `post.when = next`의 시작 여부(안 1과 안 2 가운데 선택)는 사용자 확인이 필요하다.

### 4.3 pi 어댑터 `sendMessage` 매핑

[제안] 안 1과 안 3을 기준으로 한 매핑이다.

| pi 호출 | 상태 | xeon 대응 |
|---|---|---|
| `sendMessage(m, {deliverAs:"nextTurn"})` | 무관 | `post(item, {when:"next", requestId})` |
| `sendMessage(m)` 또는 `{triggerTurn:true}`, `deliverAs` 생략 | 실행 중 | `post(item, {when:"steer", requestId})` |
| `sendMessage(m, {deliverAs:"followUp"})` | 실행 중 | `post(item, {when:"followUp", requestId})` |
| `sendMessage(m, {triggerTurn:true})` | 유휴 | `post(item, {when:"start"})`(안 3 채택 시) 또는 `drive` 시작 |
| `sendMessage(m, {triggerTurn:false})` | 실행 중 | 대응 없음. "실행 끝에 기록만"은 `post` 값에 없다. [미결] |
| `sendMessage(m)`, 유휴, 트리거 없음 | 유휴 | 대응 없음. 세션 기록만 남긴다. [미결] |
| `sendUserMessage(text, {deliverAs})` | 실행 중 | steer 또는 followUp과 같다. 사용자 입력 출처를 항목에 싣는다 |
| `continue: true` + `entries` | 경계 | 경계 지점의 반환값(`entries`, `continue`)을 `drive` 반환이나 `chain` 반환으로 옮긴다. 지점 선언은 `X.primitives.spec`이 정한다 |

- [제안] `requestId` 파생 규칙을 고친다. ADR-0007 §3.7은 "메시지 내용과 호출 순번에서 requestId를 파생한다"고 적었다. pi에서는 같은 문구를 정상적으로 여러 번 주입하는 경우가 있다. 내용만으로 파생하면 정상 재주입이 멱등 처리로 사라진다. 파생 키는 확장 id, 턴 번호, 호출 순번으로 바꾼다. 재생 때 같은 값이 나오도록 턴 번호를 쓴다.

## 5. 기존 문서의 정정 목록

1. `_research/ext-points.md:48`: "스트리밍 중이면 deliverAs로 큐 종류를 고른다"는 부정확하다. `nextTurn`은 실행 상태와 무관하게 별도 배열로 간다. 실행 중에 `triggerTurn`을 생략하면 `deliverAs`와 상관없이 steer 또는 followUp이 된다(2308-2313).
2. `_research/ext-points.md:237`: "`{entries, continue}`는 `chain` + `post(next)`로 매핑한다"와 "`sendUserMessage/sendMessage`는 `post`의 별칭"은 정정이 필요하다. `continue`는 큐 항목이 아니다(§0 4번). 유휴 `triggerTurn`과 세션 기록만 하는 경로는 `post`의 `when` 값에 없다(§4.3).
3. `decisions/ADR-0007-ext-points.md` §3.1 `next` 행: pi 대응을 `nextTurn`과 경계 `continue`로 함께 적은 것은 두 기능의 합성이다. §4.2 안으로 나눈다.
4. `ADR-0007` §3.1 `steer` 행: "다음 도구 라운드 뒤"는 좁다. pi는 `getSteeringMessages`를 턴마다 부르므로(`AG/agent-loop.ts:295`) 도구 호출이 없는 마지막 답변 뒤에 들어온 steer도 다음 요청을 만든다. [제안] 행을 "다음 턴 경계 뒤(도구 호출 유무와 무관)"로 고친다.
5. `ADR-0007` §6의 `next` 항목의 [가정] 문구는 이 조사로 확인되었다. [제안] 항목을 "확인됨: nextTurn은 시작하지 않는다(X-1 §4.1)"로 갱신한다.
6. `ADR-0007` §3.1 `followUp` 행("에이전트 정착 뒤")은 맞다. pi도 도구 호출과 steer가 없을 때만 followUp을 전달한다(`CA/agent-session.ts:2221`, `AG/agent-loop.ts:302`).

## 6. 메모리 저장과 복원

- 대기 저장소는 네 곳이다. 실제 큐는 `Agent`의 `PendingMessageQueue`다(`AG/agent.ts:143-170`). 세션 쪽에는 표시·복원용 문자열 배열 `_steeringMessages`, `_followUpMessages`가 있다(`CA/agent-session.ts:394-396`). 나머지는 `_pendingNextTurnMessages`(398)와 `_pendingCustomMessages`(400)다. 모두 메모리 필드다.
- 세션 기록은 소비 시점에 생긴다. 사용자·어시스턴트·도구 결과 메시지는 `message_end`에서 `appendMessage`로 기록된다(`CA/agent-session.ts:1144-1166`). 커스텀 메시지는 `_appendCustomMessage`나 flush에서 기록된다.
- 대기 필드를 세션 복원 경로에서 다시 채우는 코드는 찾지 못했다(grep 확인). `_pendingNextTurnMessages`는 `CA/agent-session.ts`에서 398, 2089-2092, 2306-2307의 세 곳에만 나온다. 프로세스가 끝나면 대기 항목은 사라진다.
- [제안] xeon의 `post`는 ADR-0004의 이벤트 소싱에 맞춰 enqueue 시점에 이벤트를 먼저 기록하고, 소비 시점에 투영을 갱신한다. pi처럼 메모리 큐만 두면 재개 때 `post` 항목이 사라진다.

## 7. 미확인과 한계

- [미확인] pi-agent-core 1.3.0 소스. 이 조사는 커밋 `cdaf6c22`(1.1.0)를 기준으로 했다(§1).
- [미확인] 실행으로 요청 횟수를 세지는 않았다. 소스 읽기로 추론했다.

- [미확인] `agent_settled` 이후 `_deferredSettledActions` 실행이 재귀적으로 얼마나 깊어질 수 있는지. 연기 처리 자체는 확인했다(2315-2318, 1090-1094).
- [미확인] oh-my-pi의 `SESSION_STOP_CONTINUATION_CAP = 8`(`_research/ext-points.md` §2, 69행 인용)은 이 조사에서 확인하지 않았다. pi에는 해당 상한이 없다(§3.3).
