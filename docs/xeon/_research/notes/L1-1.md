## 0. 결론

1. 1.3.0은 1.1.0 소스와 같다 [확인]. `agent-loop.ts`, `agent.ts`, `types.ts`, `proxy.ts`, `stream-fn.ts`, `index.ts` 여섯 파일이 바이트 단위로 같다. 달라진 것은 `package.json`의 버전과 `pi-ai` 고정 버전뿐이다. CL13의 1.2.0·1.3.0 절은 본문이 비어 있다.
2. (a) 훅 일곱 종(`prepareRequest`, `prepareNextTurn`, `finishTurn`, `beforeToolCall`, `afterToolCall`, `getSteeringMessages`, `getFollowUpMessages`)은 1.3.0에 모두 있고 시그니처도 같다 [확인].
3. (b) 루프의 `emit`은 모두 `await`된다. Agent의 싱크는 리스너를 구독 순서대로 `await`한다. 리스너 Promise가 끝나야 루프가 다음 단계로 넘어간다. 리스너의 예외는 삼키지 않고 run 실패로 전파된다 [확인].
4. (c) `tool_execution_start`는 `beforeToolCall`보다 앞에 발화한다. 순차·병렬 모드 모두 같다. 병렬 모드는 배치 안 모든 준비(검증과 `beforeToolCall`)가 끝난 뒤에 `execute()`를 시작한다 [확인].
5. (d) 공개 API `Agent.prompt`·`continue`는 실행 중 재진입을 거부한다. 저수준 `runAgentLoop`·`runAgentLoopContinue`에는 가드가 없고, `runAgentLoopContinue`는 넘긴 `messages` 배열을 직접 바꾼다. 순차 모드에서는 `Agent.state.messages`와 루프의 `currentContext.messages`가 배치 동안 서로 다르다 [확인]. 단계 중간 재진입은 금지한다 [제안]. 단계 중간의 상태 교체는 훅 반환값으로만 한다.
6. (e) `BeforeToolCallResult`에는 1.3.0에서도 인자 재작성 필드가 없다. 루프가 읽는 필드는 `block`, `reason`, `terminate` 셋뿐이다 [확인]. 인자를 바꾸는 경로는 `tool.prepareArguments`(검증 전, 컨텍스트 없음)와 `beforeToolCall` 인자 객체의 제자리 변경(검증본 복제라 실행에 반영됨, 문서 계약 아님)뿐이다.
7. 07 §3.5 패치 A1~A6은 1.3.0 소스에서도 미적용 상태다. A7은 주석 보강 전 상태다. 07의 줄 번호는 1.3.0 TS와 같아 그대로 맞다 [확인]. 1.3.0에서 새로 생긴 차이는 `pi-ai`의 `validateToolArguments`가 `argumentsError`를 던지는 한 곳뿐이다 [확인].

## 3. 질문별 답

### (a) 훅 일곱 종의 존재와 시그니처 [확인]

- 1.3.0의 `AgentLoopConfig`에 새로 생긴 훅은 없다. Agent 옵션에는 `prepareNextTurnWithContext`, `steeringMode`, `followUpMode`, `toolExecution`, `onPayload`, `onResponse`, `onProviderStreamEvent`가 있다(AG/agent.ts:114-135).

### (b) emit과 리스너의 await [확인]

- 루프는 모든 `emit`을 `await`한다(AG/agent-loop.ts:117-124, 146-151, 176 외 다수).
- Agent가 넘기는 싱크는 `(event) => this.processEvents(event)`다(AG/agent.ts:441, 453).
- `processEvents`는 먼저 상태를 갱신한다(AG/agent.ts:575-583). 그다음 `for (const listener of this.listeners) await listener(event, signal)`로 구독 순서대로 각 리스너를 await한다(AG/agent.ts:609-611). `subscribe` 주석이 이 규칙을 명시한다(AG/agent.ts:259-261).
- 따라서 리스너 안에서 `effect.intent`를 `await`로 커밋하면, 커밋이 끝날 때까지 루프는 다음 단계로 가지 않는다.
- 훅도 모두 `await`된다. 호출 위치는 `getSteeringMessages`(176, 205, 295), `prepareNextTurn`(186), `prepareRequest`(219-226), `beforeToolCall`(728-737), `afterToolCall`(872-882), `finishTurn`(252, 286), `getFollowUpMessages`(302)다.
- 예외 전파 [확인]:
  - 리스너 예외는 삼키지 않는다. `emit`이 거부되고 `runLoop`가 거부된다. `runWithLifecycle`의 catch가 `handleRunFailure`를 부른다(AG/agent.ts:523-528, 532-547). 합성된 error 메시지가 리스너에 다시 발화되고, 그 뒤 `finally`에서 `finishRun`이 실행된다.
  - `beforeToolCall` 예외는 `prepareToolCall`의 try/catch가 잡아 실행을 막고 오류 결과로 바꾼다(AG/agent-loop.ts:725-776). `afterToolCall` 예외는 `finalizeExecutedToolCall`의 catch가 잡아 결과를 오류로 바꾼다(AG/agent-loop.ts:871-901).
  - 루프 훅 예외(`prepareRequest`, `prepareNextTurn`, `finishTurn`, `getSteeringMessages`, `getFollowUpMessages`)는 잡히지 않아 run 실패가 된다. 계약 주석은 `convertToLlm`(types.ts:203), `transformContext`(231), `getApiKey`(252), `getSteeringMessages`(291), `getFollowUpMessages`(304)에 "던지지 않는다"를 적는다. `prepareRequest`, `prepareNextTurn`, `finishTurn`에는 계약 주석이 없다.

### (c) tool_execution_start 발화 시점 [확인]

- 순차 모드(AG/agent-loop.ts:541-549): `tool_execution_start`(543) → `prepareToolCall`(549) → 인자 검증(727) → `beforeToolCall`(728-737) → `execute`(558).
- 병렬 모드(AG/agent-loop.ts:596-604): 호출마다 `tool_execution_start`(598) → `prepareToolCall`(604). 실행은 준비 루프가 끝난 뒤 `finalizedCalls.map`에서 시작한다(646-648).
- 미발견 도구와 인자 검증 실패도 start 뒤에 일어난다(716-722, 727).
- 길이 초과 응답(`stopReason: "length"`)은 훅 없이 start → end → 결과 순서다(AG/agent-loop.ts:478-502, 485).
- 결론: start는 `beforeToolCall` 이전에 발화한다. 차단될 호출에도 start가 발화한다. `Agent`는 start에서 `pendingToolCalls`에 추가한다(AG/agent.ts:580-583). 따라서 start 리스너를 효과 의도의 근거로 쓰면 차단될 호출까지 기록된다 [제안]. 의도는 `beforeToolCall`에서 기록한다.
- 병렬 모드의 실제 순서: start₁, 준비₁(beforeToolCall₁), start₂, 준비₂, …, startₙ, 준비ₙ을 거친 뒤 execute₁…ₙ이 시작한다(AG/agent-loop.ts:646-648). 즉 한 배치의 모든 `beforeToolCall`은 어떤 `execute()`보다 먼저 끝난다. 중단 신호가 오면 준비 루프가 `break`한다(613-615, 641-643).
- 순차 모드 순서: start → beforeToolCall → execute → afterToolCall → tool_execution_end → toolResult의 message_start·message_end → 다음 호출(AG/agent-loop.ts:541-575).

### (d) 단계 중간 재진입 [확인, 판단은 제안]

1. Agent 공개 API: `prompt()`와 `continue()`는 `activeRun`이 있으면 throw한다(AG/agent.ts:373-377, 384-386, 507-509). `activeRun`은 리스너가 끝날 때까지 유지된다(AG/agent.ts:517, 527-528). 훅과 리스너 안에서 `continue()`를 부르면 항상 거부된다.
2. 저수준 함수: `index.ts`가 `export * from "./agent-loop.ts"`로 내보낸다(AG/index.ts:2). `runAgentLoop`, `runAgentLoopContinue`, `agentLoop`, `agentLoopContinue`에는 가드가 없다.
   - `runAgentLoop`는 `messages`를 새 배열로 복사한다(AG/agent-loop.ts:112-115).
   - `runAgentLoopContinue`는 얕은 복사만 한다(144). 그래서 `messages` 배열이 호출자와 공유되고, 루프가 그 배열에 push한다(418, 449, 274-277).
   - `prepareNextTurn`의 `context`(188)와 `prepareRequest`의 `context`(228)도 복사 없이 쓴다. 07 §3.5 A1의 근거가 이 세 곳이다.
3. `runToolCall`: 공개 함수다(AG/agent-loop.ts:811-819). 한 호출에 대해 준비·검증·`beforeToolCall`·실행·`afterToolCall`을 수행하고 이벤트와 메시지는 내지 않는다. 도구가 다른 도구를 부를 때 쓰는 정식 경로이며 루프 재진입이 아니다. README가 `examples/mcp-codemode`의 사용 예를 적는다(AG/README.md:508). CL13에는 항목이 없다 [확인].
4. 배치 중간 상태 [확인]:
   - 순차 모드: 도구 결과의 `message_end`가 리스너를 거칠 때 `Agent.state.messages`에 들어간다(AG/agent.ts:575-577). 루프의 `currentContext.messages`에는 배치가 끝난 뒤 들어간다(AG/agent-loop.ts:274-277). 배치 전체 동안 두 배열이 다르다.
   - 병렬 모드: 결과 메시지는 모든 실행이 끝난 뒤 원래 순서로 방출된다(AG/agent-loop.ts:650-653). 그 방출 구간에서만 두 배열이 다르다.
5. 판단 [제안]: 단계 중간 재진입은 금지한다. 단계 중간의 상태 교체는 루프가 정한 자리에서 훅 반환값으로만 한다.
   - `prepareRequest`: 매 요청 직전 context·model·thinkingLevel을 교체한다(AG/agent-loop.ts:219-239). 큐를 폴링하지 않는다. CL13 0.87.0 절의 예는 "선택된 입력을 발화한 뒤 정식 context를 설치"하는 용도다.
   - `prepareNextTurn`: 다음 턴 직전에 context, messages 추가, model, thinkingLevel을 교체한다(AG/agent-loop.ts:186-201). 다음 턴이 시작될 때만 호출된다(183-186, CL13 0.84.4 절).
   - `finishTurn`의 `{action:"continue"}`: 다음 provider 요청 한 번을 보장한다(AG/agent-loop.ts:286-314). error·aborted 응답에서는 결정이 무시된다(252).

### (e) BeforeToolCallResult의 인자 재작성 [확인, 2차 판단 입력]

- 1.3.0 정의: `{ block?: boolean; reason?: string; terminate?: boolean }`(AG/types.ts:66-74, D13 types.d.ts:44-52). `args` 필드가 없다. `AfterToolCallResult`(AG/types.ts:92-104)에도 없다.
- 루프가 읽는 필드는 `block`, `reason`, `terminate` 셋뿐이다(AG/agent-loop.ts:745-749).
- 인자를 바꾸는 경로는 다음 셋이다.
  1. `tool.prepareArguments(args)`: 검증 전에 호출된다(AG/agent-loop.ts:694-706, 726). 도구 정의에 묶이고 컨텍스트를 받지 않는다. 호출별 정책에는 쓸 수 없다(AG/types.ts:469-473).
  2. `beforeToolCall` 컨텍스트의 `args`를 제자리 변경: `args`는 `validateToolArguments`가 만든 `structuredClone` 복제본이다(pi-ai 1.3.0 `utils/validation.ts:321`, 로컬 1.1.0은 318). 같은 객체가 `prepared.args`에 담겨 `execute()`에 넘어간다(AG/agent-loop.ts:764-768, 832). 따라서 제자리 변경은 실행에 반영된다. assistant 메시지의 `toolCall.arguments`는 바뀌지 않는다. 이 동작은 문서 계약이 아니다. 07 §3.5 A4의 주석도 같은 판단이다.
  3. 원본 `toolCall.arguments`의 변경: 검증이 이미 끝난 뒤이므로 실행 인자에 반영되지 않는다(AG/agent-loop.ts:727, 764-768).
- 결론 [확인]: 1.3.0에도 `BeforeToolCallResult`의 인자 재작성 필드는 없다. 07 §3.5 A4(`BeforeToolCallResult.args` 추가와 재검증)는 여전히 필요하다.
- [제안] 2차 판단: 인자 교체를 계약으로 두려면 A4를 유지한다. 근거는 두 가지다. 첫째, 1.3.0의 공식 경로는 `prepareArguments`뿐이고 호출별 정책을 담지 못한다. 둘째, 제자리 변경은 동작하지만 문서 계약이 없어 버전 올림에서 깨질 수 있다.

- 병렬 모드는 준비를 순서대로 하고 실행만 동시에 한다(586-658). 일치. 646-648로 "의도 기록이 실행 전에 모두 끝난다"는 성질이 확인된다.

## 6. 구속 후보 (L1.loop.spec, L1.tools.spec 입력)

1. 효과 의도 기록은 `beforeToolCall`에서 한다. start 리스너는 차단 호출에도 발화하므로 근거로 쓰지 않는다 [제안].
2. 병렬 모드는 배치의 모든 `beforeToolCall`이 끝난 뒤 실행을 시작한다(AG/agent-loop.ts:646-648). 한 배치 전체의 의도 기록을 실행 전에 끝낼 수 있다 [확인].
3. 준비와 `execute()` 사이에는 중단 확인만 있고 훅이 없다(AG/agent-loop.ts:757-763, 832). A5가 필요한 이유다.
4. 리스너 예외는 run 실패다. 의도 기록이 실패하면 리스너가 던져 실행을 막을 수 있다. 다만 합성된 error 메시지가 리스너에 다시 발화된다(AG/agent.ts:532-547) [확인].
5. `runAgentLoopContinue`는 호출자 배열을 바꾼다(AG/agent-loop.ts:144, 418). 호출자는 얕은 복사를 피해야 한다 [제안].
6. `runToolCall`(AG/agent-loop.ts:811-819)은 도구가 다른 도구를 부를 때 쓰는 경로다.
7. `prepareNextTurn`은 끝난 run과 error·aborted 뒤에는 호출되지 않는다(AG/agent-loop.ts:183-186, 245-256, CL13 0.84.4 절) [확인].
8. Agent 수준 `prepareNextTurn`은 `(signal?)`이고 루프 수준은 `(context)`다(AG/agent.ts:127-129, AG/agent.ts:484-491 래퍼) [확인].
