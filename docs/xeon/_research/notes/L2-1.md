## 1. 요약

1. 2.3.1은 2026-07-28 사양의 다중 왕복 요청(MRTR, `input_required` 재시도), `subscriptions/listen`, OAuth 헬퍼를 공개 API로 노출한다 [확인]. `packages.md`에서 "SDK API 미확인"으로 남은 MRTR과 구독 항목이 해소된다.
2. 2026 Tasks 확장(`io.modelcontextprotocol/tasks`)은 2.3.1에 구현되어 있지 않다 [확인]. 확장 식별자, `resultType: "task"`, `pollIntervalMs`, `tasks/update` 구현 코드가 없다. `tasks/get`과 `tasks/cancel`은 명시 스키마 경로로 보낼 수 있다는 예외만 있다. `packages.md`의 Tasks "그대로" 판정은 수정해야 한다. Xeon은 Tasks 어댑터를 직접 두어야 한다 [제안].
3. elicitation, sampling, roots 처리는 `setRequestHandler(메서드명, 핸들러)`로 등록한다 [확인]. 2026 사양에서 이 세 요청은 서버 주도 요청이 아니고 MRTR의 `inputRequests`로만 도달한다. roots와 sampling은 2026-07-28에서 deprecated다 [확인].
4. 버전 협상 기본값은 `legacy`다 [확인]. 2026 경로를 쓰려면 `versionNegotiation: { mode: 'auto' }`(탐침 후 폴백) 또는 `{ pin: '2026-07-28' }`(고정)을 명시해야 한다.
5. 확인하지 못한 항목은 Tasks 명세 본문의 필드, 실제 전송 실행, CIMD 세부 동작, v1.32.1 주장이다(§10).

## 3. 다중 왕복 요청 (MRTR, `input_required` 재시도)

- 결과 타입: `InputRequiredResult { resultType: 'input_required'; inputRequests?; requestState? }` [확인] `pkg:dist/index-B-4n9P0J.d.mts:705`. `isInputRequiredResult`는 `:1548`, `withInputRequired(schema)`는 `:1321`.
- 자동 모드(기본): `ClientOptions.inputRequired.autoFulfill` 기본값 `true`, `maxRounds` 기본값 `10` [확인] `src:src/core-internal/src/shared/inputRequiredDriver.ts:30`, `:36`, `:80-81`. 옵션 타입은 `pkg:dist/index-B-4n9P0J.d.mts:1327`.
- 흐름: `input_required` 결과를 받으면 드라이버가 `inputRequests`의 각 항목을 같은 클라이언트에 등록된 핸들러로 디스패치한다 [확인] `src:src/core-internal/src/shared/inputRequiredEngine.ts:122-163`. 등록된 핸들러가 없으면 `SdkError`를 던진다 (같은 파일 `:145-151`).
- 재시도: 원래 params에 `inputResponses`와 `requestState`를 더해 새 요청 ID로 다시 보낸다 [확인] `src:src/core-internal/src/shared/protocol.ts:165`, `:153`. `requestState`는 바이트 단위로 되돌려 보낸다 (사양 MRTR 클라이언트 요구 2, 3: https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/mrtr).
- 라운드 초과: `SdkErrorCode.InputRequiredRoundsExceeded`를 던진다 [확인] `src:src/core-internal/src/shared/inputRequiredDriver.ts:229-231`.
- 수동 모드: `autoFulfill: false`이면 `input_required`가 타입 있는 오류가 된다 [확인] `pkg:dist/index-B-4n9P0J.d.mts:1327-1340`. 호출 단위로 `allowInputRequired: true`를 주면 `input_required` 값을 그대로 받는다 (`:1880`). 결과 타입을 쓰려면 스키마를 `withInputRequired()`로 감싼다 (`pkg:dist/index.d.mts:1949-1968`의 설명).
- 반환 타입: `callTool()` 등은 평범한 결과 타입을 반환하고, 중간 라운드는 호출 안에서 처리된다 [확인] `pkg:dist/index.d.mts:1949-1958` 설명.
- 사양 제약: `input_required` 응답은 `tools/call`, `prompts/get`, `resources/read`에만 허용된다. 서버는 클라이언트가 선언하지 않은 입력 종류를 보내면 안 된다 [확인] (MRTR 페이지 "Supported Requests", 서버 요구 7).
- 판정: MRTR의 SDK API 모양은 확인 완료다 [확인]. `packages.md` L2-b "서버 주도 요청"의 "SDK API 모양은 미확인"은 해소된다.

## 4. Tasks 확장 (`io.modelcontextprotocol/tasks`)

### 4.1 SDK 2.3.1의 구현 상태

- 확장 식별자 `io.modelcontextprotocol/tasks`: 배포 파일과 소스맵 원본 전체에서 0건이다 [확인] (`grep`으로 확인).
- 2026 `CreateTaskResult`(`resultType: "task"`), `pollIntervalMs`: 0건이다 [확인]. `ttlMs`는 2025 쪽 `TaskMetadata`에만 있다.
- `tasks/update`: 메서드 이름은 `Mcp-Name` 헤더 표에 이름만 있고 스키마와 핸들러가 없다 [확인] `src:src/core-internal/src/shared/inboundClassification.ts:489-491`.
- 2025-11-25 Tasks 와이어 스키마는 2025 레지스트리에만 있다 [확인] `src:src/core-internal/src/wire/rev2025-11-25/registry.ts:85-88`, `:172-175`, `src:src/core-internal/src/wire/rev2025-11-25/buildSchemas.ts:2075`, `:2134`. 2026 레지스트리(`rev2026-07-28/buildSchemas.ts`)에는 `tasks/*` 요청 스키마가 없다 [확인].
- 공개 타입은 "SDK 런타임 없음"으로 표기되어 있다 [확인] `pkg:dist/index-B-4n9P0J.d.mts:721-728`(`TaskRequestMethod`, 주석 "Task methods are 2025-11-25 wire vocabulary with no SDK runtime"). `isTaskAugmentedRequestParams`는 `@deprecated`다 (`:1555-1558`).
- `TaskRequestMethod`는 `RequestMethod`에서 제외되어 스펙 메서드 오버로드로 `tasks/*`를 보낼 수 없다 [확인] `pkg:dist/index-B-4n9P0J.d.mts:730`.

### 4.2 명시 스키마 경로 (코드 읽기에서 얻은 우회 경로)

- `request(request, resultSchema, options)` 오버로드는 `tasks/get`과 `tasks/cancel`에 대해서만 era 게이트를 건너뛴다 [확인] `src:src/core-internal/src/shared/protocol.ts:1287-1289`, `src:src/core-internal/src/wire/codec.ts:340-342`(주석 "The names SEP-2663 re-defines for the Tasks extension"). 2026 연결에서 그 밖의 `tasks/*` 스펙 메서드(`tasks/result`, `tasks/list`)는 `MethodNotSupportedByProtocolVersion`을 던진다 (`src:src/core-internal/src/shared/protocol.ts:1344-1350`).
- `tasks/update`는 스펙 메서드 목록 밖의 확장 메서드다. 그래서 era 게이트 없이 명시 스키마로 보낼 수 있다 [추측] (`src:src/core-internal/src/wire/codec.ts:331-334`, `src:src/core-internal/src/shared/protocol.ts:1014-1016`).
- 요청 전송 경로는 `_requestWithSchemaViaCodec`가 맡고 결과 검증은 넘겨받은 스키마로 한다 [확인] `src:src/core-internal/src/shared/protocol.ts:1379`.
- 실제 전송은 실행하지 않았다. 위 경로로 `tasks/get`이 와이어에 나가는지는 [미확인]이다.
- 서버 측에는 명시 스키마 핸들러 등록이 가능하다 [확인] `src:src/core-internal/src/shared/protocol.ts:1714-1776`. 주석 1012행도 Tasks 확장 이름이 명시 스키마로 등록될 때 예외를 둔다고 적는다.
- 클라이언트 측 `CreateTaskResult` 판별, 폴링 루프, `tasks/update` 응답 처리 로직은 없다 [확인].

### 4.3 능력 선언

- 2026 능력 스키마에 `extensions: Record<string, JSONObject>`가 있다 [확인] `src:src/core-internal/src/wire/rev2026-07-28/buildSchemas.ts:276`, `:300`, `:647`, `:657`.
- `registerCapabilities(capabilities)`는 `client.ts:789`에 있고, 요청별 `_meta`의 `clientCapabilities`는 `this._capabilities`에서 만든다 [확인] `src:index/src/client/client.ts:709`. 따라서 `registerCapabilities({ extensions: { 'io.modelcontextprotocol/tasks': {} } })`가 요청마다 실린다는 것이 코드 읽기 결과다 [추측]. 실제 전송은 확인하지 않았다.

### 4.4 사양 (공식 개요 페이지)

- 출처: https://modelcontextprotocol.io/extensions/tasks/overview (SEP-2663, 명세 본문은 `ext-tasks` 저장소에 있다고 한다).
- 흐름: 클라이언트는 요청별 능력에 확장 키를 넣는다. 서버는 `CreateTaskResult`(`resultType: "task"`, `taskId`, 초기 `status`, `ttlMs`, `pollIntervalMs`)를 돌려준다. 클라이언트는 `tasks/get`으로 폴링한다. 상태가 `input_required`이면 `tasks/get` 응답에 `inputRequests`가 실린다. 클라이언트는 `tasks/update`로 `inputResponses`를 보낸다. `tasks/cancel`은 협조적 취소다 [확인, 개요 페이지 기준].
- 상태 값: `working`, `input_required`, `completed`, `failed`, `cancelled`. 종료 상태는 `completed`, `failed`, `cancelled`다 [확인, 개요 페이지].
- 사양 변경 목록: `tasks/result`는 `tasks/get` 폴링으로 대체되고, `tasks/list`는 제거되고, 서버는 옵트인 없이 태스크 핸들을 돌려줄 수 있다 [확인] https://modelcontextprotocol.io/specification/2026-07-28/changelog 항목 6.

### 4.5 판정

- `packages.md` §4.4 L2-b "MCP Tasks: 그대로(공식 v2 확장)"는 수정해야 한다 [확인]. SDK 2.3.1은 Tasks 확장을 구현하지 않고, 명시 스키마 우회만 가능하다.
- [제안] Xeon은 Tasks 어댑터를 L2-b 안에 둔다. 어댑터는 `client.request(..., resultSchema)`로 `tasks/get`, `tasks/update`, `tasks/cancel`을 보내고, `CreateTaskResult` 판별과 폴링은 어댑터가 맡는다. 2026 경로에서 `tasks/result`와 `tasks/list`는 쓰지 않는다.
- [미결] `notifications/tasks` 알림의 존재 여부는 상충한다. 개요 페이지는 `subscriptions/listen`으로 `notifications/tasks`를 받는다고 쓰고, changelog 항목 Deprecated와 SDK의 2026 알림 목록은 `tasks/status` 삭제를 기록한다 [미결]. 명세 본문으로 확인해야 한다.

## 5. elicitation, sampling, roots 처리 훅

- 등록 API: `setRequestHandler(method, handler)`를 쓴다 [확인] `pkg:dist/index-B-4n9P0J.d.mts:2346`. 명시 스키마 형태는 `:2347`이다. 클라이언트 문서 예시는 `sampling/createMessage` 핸들러를 보여준다 [확인] `src:index/src/client/client.ts:501-515`.
- 능력 선언: `elicitation`(`form`, `url`), `roots`, `sampling`을 `registerCapabilities`로 선언한다 [확인] `src:index/src/client/client.ts:789`. 미선언 상태에서 해당 핸들러가 호출되면 `CapabilityNotSupported` 계열 오류가 난다 [확인] `src:index/src/client/client.ts:1516-1520`, `:1528-1532`.
- elicitation 검증: `_wrapHandler`가 `elicitation/create` 요청과 결과를 스키마로 검증하고, 선언된 모드(form/url)로 요청을 거른다 [확인] `src:index/src/client/client.ts:813-881`. 모드 판정은 `getSupportedElicitationModes`를 쓴다 (`pkg:dist/index.d.mts:1888`).
- 2026 전송: elicitation, sampling, roots는 와이어 메서드가 아니다. 등록 핸들러로는 MRTR 드라이버가 `inputRequests` 항목을 전달한다 [확인] `src:src/core-internal/src/shared/protocol.ts:1720-1745` 주석("reach a handler only as embedded input requests dispatched by the multi-round-trip driver").
- 인바운드 드롭: 2026 연결에서 들어온 서버 측 요청 `request`는 응답하지 않고 `onerror`로 드롭한다 [확인] `pkg:dist/index.d.mts` Client의 `_shouldDropInbound` 주석.
- deprecated: `roots/list`, `sampling/createMessage`, `roots.listChanged`는 2026-07-28에서 deprecated다. 최소 12개월 동안 동작한다 [확인] `src:index/src/client/client.ts:506-509`, `:1475-1479`, changelog Deprecated 항목 1 (https://modelcontextprotocol.io/specification/2026-07-28/changelog).
- 사양 상태: 서버가 보낼 수 있는 `inputRequests`는 `elicitation/create`, `sampling/createMessage`, `roots/list` 셋이다 [확인] (MRTR 서버 요구 2).
- elicitation 보안 규칙: 비밀번호, API 키, 접근 토큰, 결제 정보는 form 모드로 요청하면 안 되고 URL 모드를 써야 한다 [확인] (https://modelcontextprotocol.io/specification/2026-07-28/client/elicitation, 경고 블록). URL 모드의 `elicitationId`와 `notifications/elicitation/complete`는 2026에서 제거되었다 [확인] (changelog 항목 11).

## 6. `subscriptions/listen`

- API: `Client.listen(filter: SubscriptionFilter, options?): Promise<McpSubscription>` [확인] `pkg:dist/index.d.mts:2609`.
- 필터 필드: `toolsListChanged`, `promptsListChanged`, `resourcesListChanged`, `resourceSubscriptions` [확인] `src:src/core-internal/src/wire/rev2026-07-28/buildSchemas.ts:1063-1068`.
- 핸들: `honoredFilter`(서버가 승인한 부분 필터), `close()`(멱등, `notifications/cancelled` 전송과 스트림 중단을 둘 다 한다), `closed: Promise<'local' | 'graceful' | 'remote'>` [확인] `pkg:dist/index.d.mts:2104-2115`.
- 알림: 열린 구독의 변경 알림은 `setNotificationHandler`로 등록한 핸들러에 전달된다 [확인] `pkg:dist/index.d.mts` `listen` 설명. 구독 ID는 `listen` 요청의 JSON-RPC ID다.
- 2025 연결: `listen()`은 `MethodNotSupportedByProtocolVersion`을 던지고 `resources/subscribe`와 `ClientOptions.listChanged`를 안내한다 [확인] `pkg:dist/index.d.mts:2609` 설명.
- 자동 개방: `ClientOptions.listChanged`를 쓰면 2026 연결에서 구독을 자동으로 연다. 자동 구독은 `autoOpenedSubscription`으로 노출되고 `src:index/src/client/client.ts:1252`에서 `listen()`을 호출한다 [확인].
- 재연결: SDK는 자동 재-listen을 하지 않는다 [확인] `pkg:dist/index.d.mts:2609` 설명. 사양은 stdio 재연결 시 재-listen을 요구한다 [확인] (https://modelcontextprotocol.io/specification/2026-07-28/basic/patterns/subscriptions).
- 사양 종료 규칙: 서버 종료는 성공 응답(`resultType: "complete"`)으로 알리고, 연결이 응답 없이 끊기면 비정상 종료다 [확인] (같은 사양 페이지, Graceful Closure).

## 7. OAuth 헬퍼

- 공급자 인터페이스 `OAuthClientProvider`: `redirectUrl`, `clientMetadata`, `clientMetadataUrl?`, `state?()`, `clientInformation()`, `saveClientInformation?`, `tokens()`, `saveTokens()`, `redirectToAuthorization(url)`, `saveCodeVerifier()`, `codeVerifier()`, `addClientAuthentication?`, `dpop?()`, `validateResourceURL?`, `invalidateCredentials?`, `prepareTokenRequest?`, `saveAuthorizationServerUrl?`, `authorizationServerUrl?()`, `saveResourceUrl?` [확인] `pkg:dist/index.d.mts:430-627`. 주요 항목은 `:440`(`clientMetadataUrl`), `:483`(`tokens`), `:496`(`redirectToAuthorization`)에 있다.
- 흐름 함수: `auth(provider, options)`는 `'AUTHORIZED'` 또는 `'REDIRECT'`를 반환한다 [확인] `pkg:dist/index.d.mts:858`, `:678`. `'REDIRECT'`이면 `redirectToAuthorization`을 거친 뒤 `finishAuth(code, iss?)`를 호출한다 [확인] `pkg:dist/index.d.mts:3606`(Streamable HTTP), `:3286`(SSE).
- 전송 연결: `StreamableHTTPClientTransport`의 `authProvider`는 `AuthProvider` 또는 `OAuthClientProvider`를 받는다 [확인] `src:index/src/client/streamableHttp.ts:175`, `:383-385`. 401이면 `onUnauthorized`를 호출하고, 없으면 `UnauthorizedError`를 던진다 (`:162-165`).
- step-up: 403 `insufficient_scope`에서 요청 범위와 토큰 범위의 합집합으로 재인증한다 [확인] `src:index/src/client/streamableHttp.ts:430-470`. 재시도 상한은 `_maxStepUpRetries`다.
- 다른 공급자: `ClientCredentialsProvider`(`pkg:dist/index.d.mts:1290`), `PrivateKeyJwtProvider`(`:1374`), `CrossAppAccessProvider`(`:1576`), DPoP `generateDpopKeyPair`(`:129`). `withOAuth(provider, baseUrl?)`는 일반 fetch용 미들웨어이고 MCP 전송에는 필요 없다고 주석에 적혀 있다 [확인] `pkg:dist/index.d.mts:2956` 주석.
- RFC 9207 `iss`: `validateAuthorizationResponseIssuer`가 있다 [확인] 이름과 시그니처 `pkg:dist/index.d.mts:693`. 판정 표의 동작 세부는 [미확인]이다.
- 등록: `registerClient`(DCR, `pkg:dist/index.d.mts:1205`)와 `clientMetadataUrl`(CIMD 필드)이 있다 [확인]. CIMD의 실제 동작 세부는 [미확인]이다.
- 사양 2026: CIMD는 SHOULD, DCR은 deprecated다. resource 파라미터(RFC 8707)는 MUST다. 보호 자원 메타데이터(RFC 9728)는 서버 MUST다 [확인] (https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization).

## 8. 버전 협상과 무상태 전환

- 기본 모드는 `legacy`다 [확인] `src:index/src/client/versionNegotiation.ts:112`, `pkg:dist/index.d.mts:1859-1865`. 2026 경로는 명시해야 켜진다.
- 모드: `'legacy'`(협상 없음, 2025 연결 순서), `'auto'`(탐침 후 폴백), `{ pin: '2026-07-28' }`(고정, 실패 시 오류). `pin` 값이 2026 이후가 아니면 오류를 던진다 [확인] `src:index/src/client/versionNegotiation.ts:137-145`.
- 요청별 `_meta` 자동 첨부: 2026 연결에서 모든 요청과 알림에 프로토콜 버전, 클라이언트 정보, 능력 키를 붙인다. 사용자 제공 `_meta` 키가 우선한다 [확인] `pkg:dist/index.d.mts:1941` 설명, `src:index/src/client/client.ts:700-709`.
- 사양 변경: `initialize`와 `notifications/initialized`가 제거되었다. `server/discover`가 추가되었다. `ping`, `logging/setLevel`, `notifications/roots/list_changed`가 제거되었다. SSE 재개가 제거되었고 끊긴 요청은 새 ID로 다시 보내야 한다 [확인] (changelog 항목 2, 3, 5, 9).
- `Client.discover(options?)`와 `getProtocolEra()`가 있다 [확인] `pkg:dist/index.d.mts` Client 클래스 선언.

## 10. 미확인과 미결

- [미확인] Tasks 명세 본문의 필드. 확인 시도: https://github.com/modelcontextprotocol/ext-tasks 페이지는 README와 저장소 목록만 보여 주었다. 다음 확인 위치는 저장소의 `specification/` 또는 `seps/` 디렉터리, 그리고 `schema/2026-07-28/schema.ts`다. Task 객체, `tasks/get`과 `tasks/update`의 요청·응답 필드, 알림 목록이 여기에 해당한다.

- [미확인] `registerCapabilities({ extensions })`가 요청 `_meta`에 실제로 실리는지. §4.3은 코드 읽기 결과다.
- [미확인] v1.32.1 SDK의 2026 미지원 주장(`packages.md` L2-b). 이번 조사 범위 밖이다.
