## 0. 한 장 요약

세 가지를 따로 하면 같은 코드(`ext-host/src/primitives/lease.ts`, `LoopHandle`, 플러그인 API)를 세 번 뜯는다. 그래서 하나의 설계로 묶고 순서만 나눈다.

핵심: **주도 함수를 "명령을 돌려주는 단계 함수"로 바꾼다** [결정]. 지금 주도 함수는 `loop.turn()` 같은 호출을 직접 하고 기다린다. 새 모양에서는 엔진이 "상태와 직전 결과"를 주면 플러그인이 "다음에 할 일 하나"를 돌려준다. 작성 편의를 위해 SDK에 generator 형태의 도우미(`yield turn(…)`)를 둘 수 있지만 엔진 계약은 단계 함수 하나다. 대안("지금의 명령형 `loop.turn()` + 재실행 방식에 맡기기만 더하기")은 채택하지 않는다. 이 한 가지가 세 문제를 함께 푼다.

| 문제 | 단계 함수가 푸는 방식 |
|---|---|
| 맡기기(B → C → B) | "C에게 맡겨라"가 명령의 한 종류다. 엔진이 스택을 쌓고, C가 끝나면 그 결과를 B의 다음 단계 입력으로 준다 |
| 블록을 낱개로 부르기 | 블록 하나가 명령 하나다. 엔진이 실행하므로 권한·샌드박스·기록이 반드시 따라온다 |
| 프로세스 격리 | 명령과 결과가 JSON이라 프로세스 경계를 그대로 넘는다. 즉시 답해야 하는 호출(`budget`, `wants`)이 사라지고 진행 중 명령의 취소는 엔진이 맡는다 |
| 재시작 뒤 이어 하기 | "상태를 보고 다시 판단"하는 방식이라 그대로다. 명령마다 요청 id가 있어, 기록이 남는 명령은 재시작 뒤 결과를 돌려주고 다시 실행하지 않는다. 기록이 남지 않는 명령(`model`)은 1.1의 [결정: 2026-11-17 사용자, U1]이다 |

### 공통 어휘 (C, D, E, F가 같은 말을 쓴다)

| 말 | 정의 | 저장 문자열 |
|---|---|---|
| 플러그인 정체(`pluginId`) | 플러그인 이름(`ExtensionNameSchema`). 폴더 이름이 아니라 매니페스트 이름 | 바꾸지 않는다 |
| 플러그인 버전 정체(`versionId`) | 검토본은 내용 해시 `sha256:<hex>`(D §4.6.1). 초안은 `draft:<draftId>:<해시 앞 8자>`. 매니페스트 `version`은 표시용이고 정체가 아니다 | `lease.acquired.contentHash`(선택), 기록의 `versionId` |
| 프레임 깊이(`frameDepth`) | 주도권 스택의 깊이. 코어 루프가 0, 첫 플러그인 프레임이 1. 저장된 `depth`는 스택 인덱스(코어 위 첫 프레임이 0)이므로 읽기의 frameDepth는 `depth + 1`이다. 옛 기록은 `depth` 0으로 읽는다 | `lease.acquired.depth`(선택) |
| 에이전트 깊이(`agentDepth`) | 서브에이전트 중첩 깊이. 승인 서비스가 `depth !== 0`이면 묻지 않는 그 값 | 기존 |
| 호출 깊이(`callDepth`) | 훅 안에서 시작한 플러그인 호출의 중첩. 설정 `l1.tools.pluginCallDepth`(F §5.3 U-8) | 기존 |
| 초안 / 검토본 일회 덧씌우기 / 테스트 실행 표지 | 기록의 `scope`: `live`, `overlay_reviewed`, `overlay_draft`, `test`, `craft`(E §3.2). 덧씌우기의 `until`은 `turn` 또는 `release` | E가 정본 |
| 훅 위치와 이름 | 위치는 `HookPosition`(블록 앞·뒤, 루프 경계 셋, 이벤트, 내부), 이름은 저장된 훅 이름 문자열(바뀌지 않음) | F §4.1이 정본 |
| 훅 결정값 / 기록된 결과값 | 결정값은 `block`, `ask`, `replace`(F §4.2). 기록된 결과값은 `passed/modified/blocked/failed/skipped`와 `reason`, `decision`(E §3.2). 둘의 대응표는 F §4.5 | F(결정), E(기록) |
| 프레임 종료 사유 | `lease.released.reason`의 저장값(2.6의 표). 이름을 새로 짓지 않는다 | 기존 값 + `done` |
| 설정 범위 | `managed > launch > profile > local > project > user > default`(D §3.3). `thread` 범위는 없다 | D가 정본 |

## 1. 주도 단계 함수

### 1.1 모양 [안]

```ts
// 플러그인이 등록한다. 순수 함수에 가깝다: 입력을 보고 다음 명령 하나를 돌려준다.
type DriveStep<S> = (input: {
  state: Readonly<S>;          // 플러그인의 커밋된 상태 문서
  last: StepResult | null;     // 직전 명령의 결과. 처음이면 null
  budget: DriveBudget;         // 남은 턴·서브에이전트·토큰 (값으로 준다)
  frame: { frameDepth: number; calledBy: PluginId | null; input: Json | null };
}) => Promise<DriveCommand>;

type DriveCommand =
  | { do: "turn"; input: PostItem; note?: string }            // 코어 루프 한 바퀴
  | { do: "model"; messages: Msg[]; label?: string }           // 모델 호출 한 번 (대화에 안 남는 판정용). 기록의 role은 "drive"
  | { do: "tool"; name: string; args: Json }                   // 도구 실행 한 번 (관문 전체를 지난다)
  | { do: "ask"; card: AskCard }                               // 사람에게 묻기
  | { do: "spawn"; agent: string; task: string }               // 서브에이전트
  | { do: "handoff"; to: PluginId; input: Json }               // 다른 플러그인에게 맡기기
  | { do: "commit"; state: S; then: DriveCommand }             // 상태를 남기고 이어서
  | { do: "yield" }                                            // 지금은 할 일 없음 (주도권 유지, 다음 경계에 다시 물음)
  | { do: "done"; result?: Json };                             // 끝. 주도권을 내려놓고 결과를 돌려준다

/** 엔진이 다음 단계의 last로 주는 값. 명령 결과, 훅이 낸 결정, 사용자·맡기기 복귀를 한 합집합으로 정의한다 */
type StepResult =
  | { kind: "ok"; of: "turn" | "model" | "tool" | "spawn"; value: Json | null }
  | { kind: "ask"; answer: "answered" | "cancelled" | "expired" | "noninteractive"; value: Json | null }
  | { kind: "blocked"; by: { plugin: string | null; hook: string | null }; reason: string }          // 훅이 막음(tool, spawn)
  | { kind: "denied"; by: "policy" | "human" | "noninteractive"; reason: string | null }           // 정책·사람·무인 실행의 거부
  | { kind: "replaced"; by: { plugin: string | null; hook: string | null }; value: Json | null }   // 훅이 결과를 대신 줌(tool의 replace, spawn의 replace{report})
  | { kind: "refused"; code: string }                                                              // 깊이 상한, hook_cycle, hook_depth, replay_mode_denied 등. 예외가 아니다
  | { kind: "aborted" }                                                                            // 사용자 중지·정지로 명령이 끝나지 않음
  | { kind: "user"; message: PostItem }                                                            // 주도 중에 온 사용자 메시지(2.4)
  | { kind: "handoff"; status: "done" | "aborted"; result: Json | null };                         // 맡긴 프레임의 끝(2.1, 2.4)
```

- `blocked`, `denied`, `replaced`, `ask`의 변형은 F §4.2·§4.3(훅의 막기·묻기·결과 대신 주기)과 승인 서비스의 해결값에서 온다. `spawn`이 `agent.spawn.before`에 막히거나 서브에이전트 안(`agentDepth > 0`)에서 묻기가 거부되는 경우도 같은 합집합이다.
- 명령마다 엔진이 요청 id를 붙인다(`lineageId + 프레임 깊이 + 단계 번호`). 재시작해서 같은 단계가 다시 돌아도 이미 실행한 명령은 기록된 결과를 돌려준다. 지금의 `requestId` 멱등 규칙을 그대로 쓴다.
- `wants(state)`는 없앤다. "지금은 할 일 없음"은 `yield`, "이 대화에서 물러남"은 `done`이다. 엔진이 후보를 추측해 고르지 않으므로(2.2) 필요 없다.
- 옛 `DriveFn(loop, state)`를 받아 주는 어댑터는 두지 않는다 [결정]. Helm과 플러그인 빌더는 새 모양으로 다시 구현한다(변경 비용이 적은 지금 한다). 외부에 공개한 적 없는 API라 호환 부담이 없다.
- **명령 결과의 내구 기록** [결정: 2026-11-17 사용자, U1]. `turn`, `ask`, `spawn`, `commit`은 기존 이벤트(`turn.started`, `approval.*`, `agent.*`, 상태 커밋)로 남고 `tool`은 `effect.*`로 남는다. 남지 않던 `model`의 결과와 턴 밖 명령의 자리는 **대화 로그에 새 상태 사건 하나**(이름은 [제안] `drive.command_settled`: 요청 id, 명령 종류, 결과 요약 또는 결과 참조)로 남긴다. 재시작 뒤 같은 모델 호출을 두 번 하지 않는 유일한 길이고 관찰이 아니라 상태 사건이라 E §3.4의 구분에 맞다. 대안(안 남기고 다시 부름)은 비용·비결정이라 채택하지 않았다. 새 종류는 `F.records` 카탈로그와 문서 대조 시험에 더한다(D §3.2와 같은 규칙).

### 1.2 명령과 블록의 대응

| 명령 | 블록 | 따라오는 보장 | 지금 |
|---|---|---|---|
| `turn` | 컨텍스트 조립 → 모델 호출 → 도구 실행 반복 | 전부 | 있음 (`loop.turn`) |
| `model` | 모델 호출 | 요청 가드, 토큰 집계, 주도 한도 차감, 기록. 지나는 훅은 모델 호출 앞 훅(`request.provider.before`, `guard.model.before`)뿐이다. 컨텍스트 조립 앞 훅(`request.context.before`, `request.system.before`)은 지나지 않는다: 턴 조립 전용이고 `ModelService.complete`는 조립을 부르지 않는다(`core-context/src/assemble.ts:139-160`, `core-models/src/pipeline.ts:349-366`) | 있음 (E2). `ModelsPort.completeForPlugin`(core-models), 역할 `judge`. 토큰은 주도 한도에서 뺀다. 판정 API(`agents.judge`)는 내장 전용으로 남는다 |
| `tool` | 도구 실행 | 플러그인 판정 훅(`tool.call.before`, `guard.tool.before`), 권한 모드, 승인, 샌드박스, 실행 기록, 결과 훅(`tool.result`), 변경 추적. 모델이 부른 도구와 같은 관문이고 호출 주체는 `plugin:<이름>`이다 | 있음 (E2). `ToolsPort.executeForPlugin`(core-tools), `via: drive`. 횟수 한도는 없고 토큰 소진만 막는다 |
| `ask` | 사람에게 묻기 | 답이 올 때까지 멈춤, 복원. `ask.human.before` 훅이 카드를 취소하거나 답을 대신 낼 수 있다(F §4.3.1) | 있음 (`loop.ask`) |
| `spawn` | 서브에이전트 | 부모 프로필·권한·작업 폴더 상속. `agent.spawn.before/after` 훅(F §4.3.3) | 있음. 작업 폴더 상속 버그는 고쳐졌다(4절 F2) |
| `commit` | 기록 | 재시작 안전 | 있음 |

- 컨텍스트 조립만 따로 부르는 명령은 두지 않는다. `turn`에 들어 있다. 조립 방식을 바꾸고 싶으면 컨텍스트 조립 앞뒤 훅을 쓴다.
- `model` 명령으로 보낸 요청과 응답은 대화 본문에는 안 보이지만 턴 기록에는 남는다("모델에 보이는 것은 기록된다"와 같은 원칙). 턴 기록의 `ModelCall.role`은 `drive`이고 `label`이 자유 문자열이다(E §3.2). 이것이 "턴 기록에 남는다"이며 대화 로그의 내구 기록(1.1 [결정: 2026-11-17 사용자, U1])과는 별개다.
- 턴 밖 명령(`model`, `tool`, `commit`, `yield`)은 턴 기록에서 `StepRecord`가 아니라 프레임 표지의 명령 수와 `pluginCalls`로 잡힌다(E §3.2).

### 1.3 플러그인 코드가 직접 부르는 기능 호출 [결정: 2026-11-17 사용자]

주도 플러그인(과 모든 플러그인)이 L2 기능을 `g.capability(...)`로 직접 부르는 길은 닫지 않는다. 능력은 줄이지 않고 경로만 하나로 모은다: **엔진이 효과 있는 기능 호출을 도구 실행 블록에 태운다**. 권한 모드, 다른 플러그인의 훅, 실행 기록, 변경 추적이 따라온다. 격리 프로세스의 호출도 같다(3.2).

- 진입점은 `ToolService.executeForPlugin`이다(F §4.6). 주도 함수의 `tool` 명령, `g.capability(...)`의 효과 있는 메서드, 효과 작업자가 모두 같은 진입점을 부른다. 서비스를 직접 부르는 줄은 남기지 않는다.
- 효과 없는 읽기 호출(`readOnly: true`이고 도구 매핑이 없는 메서드)은 가벼운 길이다. 서비스 안의 안전장치(루트, 보호 경로, 샌드박스)는 그대로 돌고 호출 한 줄이 턴 기록에 남는다(F §5.3 U-1·U-2). 읽기 전용 기능을 경계 너머로 요청·응답으로 여는 것은 이 규칙으로 확정된다.
- 호출 주체는 `plugin:<이름>`이다. 격리된 호출자의 신원은 연결을 연 호스트가 붙이고 요청 본문의 주장은 무시한다(F §5.3 U-9).
- 이 호출이 쓰는 한도는 2.3을 따른다.
- 구현 상태(층 C, 2026-11-18): 효과 있는 호출은 `g.capability`의 래퍼가 `ToolsPort.executeForPlugin`으로 보내고(도구 매핑이 있거나 readOnly가 아닌 메서드, 없는 도구는 합성 항목 `cap:<기능>.<메서드>`), 효과 작업자도 같은 진입점을 부른다. 설정 `l1.tools.pluginCalls`(이름 [제안], 기본 참)를 끄면 옛 직접 경로다. 가벼운 경로의 턴 기록 줄은 M5d를 기다린다. 자세한 내용은 `hooks-core-boundary.md` 4.6 구현 기록이다.

## 2. 주도권 스택

### 2.1 구조 [안]

- 대화의 "락 한 칸"을 **프레임 스택**으로 바꾼다. 맨 위 프레임만 주도한다. 프레임은 `{ leaseId, lineageId, plugin, parent, frameDepth, 상태(`driving` 주도 중 | `waiting` 기다림 | `asking` 질문 대기), 한도 }`를 가진다.
- `handoff` 명령: 엔진이 C의 프레임을 위에 쌓고 B의 프레임을 "기다림"으로 둔다. C가 `done`을 내면 C 프레임을 내리고, 그 결과를 B의 다음 단계의 `last: { kind: "handoff", status: "done", result }`로 준다.
- 기다리는 프레임은 함수가 떠 있지 않다. 스택은 기록으로만 존재한다. 그래서 재시작 복원이 "기록에서 스택을 다시 세우고 맨 위에게 다시 묻는다"로 끝난다. 사람에게 물을 때 락을 놓았다가 같은 계통으로 되찾는 지금의 처리와 같은 방식이다.
- 깊이 상한: 기본 8(코어 포함 9단) [결정: 2026-11-17 사용자]. 설정 `x.primitives.driveMaxDepth`로 바꾼다(2.3). 넘으면 `handoff`가 `{ kind: "refused", code: "depth_limit" }` 결과를 돌려준다(예외 아님).
- 자기 자신이나 이미 스택에 있는 플러그인에게는 맡길 수 없다(되돌이 방지).
- 질문 대기(`ask`)는 임대를 반납하지 않는다. 프레임 상태만 `asking`이 된다. 재시작하면 프레임이 복원되고, 단계 함수가 같은 `requestId`로 `ask`를 다시 내면 승인 서비스가 기존 미해결 승인을 돌려줘 다시 기다린다(4절 F6). 사유 `waiting`의 `lease.released`는 더 쓰지 않는다. 옛 기록을 읽을 때만 그 값을 받는다(2.6 표).
- 같은 이름의 플러그인이 두 버전으로 동시에 도는 일이 생긴다: 새 검토본이 승인되면 열린 대화는 다음 경계에서 새 세대로 바뀌지만(D §4.6.7) 그 사이 낡은 세대를 쥔 프레임과 새 세대가 한 프로세스 키 둘로 공존할 수 있고, 같은 이름의 초안이 한 대화에서 검토본을 대신하기도 한다(D §4.3.8). 프레임은 `plugin`과 함께 `versionId`를 가진다.

### 2.2 주도권을 받는 계기 [결정: 2026-11-17 사용자]

셋뿐이다. 엔진이 후보 중에서 고르는 지금의 중재(`DriveArbiter`, `activeDriver` 설정, 대기 계수, 거절 이벤트)는 없앤다.

| 계기 | 방법 |
|---|---|
| 사용자의 명령 | 플러그인이 등록한 명령(`/helm`)이 "주도 시작"을 뜻한다. 그 플러그인이 프로필에 든 것이든 덧씌우기(일회 사용)로 `E(T)`에 든 것이든 같다. 덧씌우기라면 순서는 `overlay_on`을 남긴 다음 프레임을 쌓는다 |
| 프로필의 시작 설정 | 프로필에 "시작할 때 주도"가 있으면 대화의 첫 턴 앞에서 그 플러그인의 프레임을 쌓는다. 스택이 비어 있을 때만이다 |
| 현재 주도하는 쪽의 `handoff` | 2.1 |

- **사용자 명령이 구동기보다 우선한다** [결정: 2026-11-17 사용자]. 주도 중에 사용자가 다른 주도 명령을 치면 돌고 있는 단계는 끊지 않고 끝까지 간 뒤, 그 단계의 경계에서 스택 전체를 내리고(해제 사유 `revoked`) 새 주도를 시작한다. 묻지 않고 한 줄로 알린다(`core.deps.report` info `scope_notice`). 내려간 쪽의 상태는 커밋돼 있어 다시 명령하면 이어 갈 수 있다. 주도 중에 다른 주도가 시작되는 경우는 사용자의 명령 하나뿐이다(프로필 시작은 스택이 빌 때만, 맡기기는 맨 위가 부른다).
- 구현 정정(E3, 2026-11-18): 전환의 시점은 정책 한 곳(`packages/ext-host/src/primitives/switch-policy.ts`의 `USER_SWITCH_AT`, 기본 `step_boundary`)이 정한다. 맨 위가 실행 중이 아니면(유휴, 맡기기 대기) 명령 시점에 바로 내리고, 질문 대기면 기다림을 끊고 바로 내린다. 맨 위가 `done`으로 끝났고 사용자 명령이 기다리면 맨 위는 사유 `done`으로 내려가고 아래 프레임만 `revoked`로 내린다(아래 프레임이 맡긴 결과를 받고 한 단계 더 돌지 않게). 같은 scope의 명령은 전환이 아니므로 버린다. `task_end`로 바꾸면 스택이 자연히 비기 전에는 바꾸지 않는다.
- 플러그인 빌더처럼 "모델이 필요하다고 판단할 때" 시작하는 경우: 모델이 부르는 도구가 주도 시작을 요청하고, 그 요청은 현재 맨 위(코어 루프 포함)의 `handoff`로 처리된다. 코어 루프도 맡길 수 있는 프레임 0으로 본다. [안]

### 2.3 한도

- 프레임마다 한도를 가진다. `handoff`로 생긴 프레임의 한도는 **맡긴 쪽의 남은 한도를 넘지 못하고**, 맡은 쪽이 쓴 만큼 맡긴 쪽에서도 빠진다(E3에서 구현: 부여 때 맡긴 쪽의 남은 양으로 한 번 더 줄이고, 쓴 양은 스택 아래 모든 프레임에 더한다). 프레임 한도의 사용량은 `used {turns, spawns, tokens}`로 기록한다(E §3.2).
- `model` 명령의 토큰도 한도에서 빠진다(enE2m에서 구현: `charge`로 스택 전체에 더한다). 도구 명령은 프레임마다 횟수 상한 `MAX_DRIVE_TOOL_COMMANDS`(64)를 가진다 [제안: enE2m, 값과 "한도 키가 아니라 엔진 상수"는 사용자 확인 대기. 도구 호출은 토큰을 쓰지 않고 성공하면 효과로 세므로 도구 명령만 연속으로 내는 단계 함수를 다른 한도가 막지 못한다. [근거: xeon/packages/ext-host/src/primitives/lease.ts]]. 훅 안에서 부른 `agents.judge`, `models.complete` 같은 플러그인 호출도 같다. 부른 시점에 주도 프레임이 없는 보통 턴이면 코어 루프(프레임 0)의 한도에서 뺀다.
- 기본 한도(4턴, 서브에이전트 8번, 40만 토큰)는 그대로 둔다. 프로필이 바꿀 수 있는 것은 코어 설정 값이다: `x.primitives.driveDefaultLimits`(기본 한도)와 깊이 상한 키 `x.primitives.driveMaxDepth`(기본 8 [결정: 2026-11-17 사용자]. 이름은 [제안]이고 C0에서 확정한다. 정의는 F 부록 A의 `x.primitives.*` 줄)는 `profile` 범위를 연다. 한도 차감의 세부(맡은 쪽이 쓴 만큼 맡긴 쪽에서 빠진다)는 [권고: 메인 세션, 확인 대기]다. E3는 이 권고를 작업 기본값으로 구현했다. 천장 `x.primitives.driveLimits`는 프로필이 바꾸지 못한다(D §3.3).

### 2.4 사용자 개입 [결정]

- **중지**: 스택 전체를 내리고 모든 덧씌우기를 해제하며 코어 루프로 돌아간다. **백그라운드 서브에이전트도 멈춘다** [결정: 사용자 2026-11-17 "포함"]. 멈춘 자식의 상태는 `interrupted`다(E §7). F1의 중지 반납은 4절에 있고, 스택 전체 내림은 E3에서 구현했다. 남은 것은 백그라운드 서브에이전트의 정지(E1)다.
- **주도 중에 온 사용자 메시지**: 맨 위 프레임의 다음 단계에 `last: { kind: "user", message }`로 전달한다. 플러그인이 받아서 `turn`으로 돌리든 `done`으로 물러나든 정한다. 플러그인이 3단계 안에 처리하지 않으면 엔진이 스택을 내리고 코어 루프가 그 메시지를 받는다(사용자 말이 묻히지 않게). 돌려받은 메시지는 입력 큐에 `followUp`으로 들어가 유휴 thread에서도 turn을 시작한다(`next`는 도는 turn에 붙기만 한다). `yield`로 넘긴 단계도 한 단계로 세므로, 단계 함수가 `yield`만 해도 메시지는 3단계 안에 돌아온다. 호스트의 `turn.start`는 전달된 입력에 turn 없이 `{ delivered: true }`를 돌려준다(F wire §3.3.1 0b). 주도 중이거나 서브에이전트(`spawn`)를 기다리는 중에 온 메시지도 맨 위 프레임에 바로 전달한다. 기다리는 명령 때문에 입력이 쌓이지 않는다(2.7). [안] 이 메시지의 수는 프레임 표지에 센다(E §3.2 `userMessages`).
- **플러그인이 프로필에서 빠지거나 오류로 멈춤**: 그 프레임과 그 위의 프레임을 모두 내린다. 진행 중 명령은 취소한다. 아래 프레임에는 `last: { kind: "handoff", status: "aborted" }`가 간다. 맨 아래 프레임이면 코어 루프로 돌아간다.

### 2.5 지침의 범위

주도 중에만 실리는 지침은 턴 시작 훅, 곧 `input.agent.before`(collect)에서 넣는다. 그 훅의 입력에 `driver`(맨 위 프레임의 플러그인, 주도 중이 아니면 null)와 `stack`(아래에서 위 순서의 플러그인 이름, 주도 중이 아니면 빈 배열)을 더한다. 턴을 누가 시작했는지는 이미 기록되므로(`turn.started.scopeId`) 전달 경로만 잇는다. 플러그인은 `driver`가 자기일 때만 지침을 넣는다(F §11).

### 2.6 기록과 화면

- 기록: `lease.acquired`에 선택 필드 셋을 한 번에 더한다: `parent: leaseId`(맡긴 쪽 프레임이다. 사용자 명령이나 프로필 시작으로 쌓인 프레임에는 싣지 않는다), `depth`(스택 인덱스. 코어 위 첫 프레임이 0이고 읽기의 frameDepth는 이 값에 1을 더한다), `contentHash`(그 프레임을 낸 플러그인의 `versionId`. 지금 값이 없는 경로는 싣지 않는다). 모두 선택이라 `version`을 올리지 않고 옛 기록은 깊이 0으로 읽는다(`leaseEpoch`가 같은 방식의 선례, `records/catalog/extension-ops.ts`). 새 이벤트 종류를 만들지 않는다. 저장된 문자열은 바꾸지 않는다(2026-11-01 결정).
- 프레임이 내려가는 이유는 기존 `lease.released.reason` 값으로 적고, 종료 사유 표를 이 문서가 정한다. 값 하나(`done`)만 더한다. 읽는 쪽은 모르는 값을 통과시켜야 한다.

| 사건 | `lease.released.reason` | 아래 프레임이 받는 `last` |
|---|---|---|
| 단계 함수가 `done` | `done` (신규) | `{ kind: "handoff", status: "done", result }` |
| 사용자 중지, 사용자 명령에 의한 교체 | `revoked`(중지 때 이 값으로 반납: 커밋 `117b90719`) | `aborted` |
| 프로필에서 빠짐(`E(T)`에서 제외) | `disabled` | `aborted` |
| 한도 소진 | `budget` | `aborted` |
| 오류 정지 | `error` | `aborted` |
| 유휴(할 일 없음) | `idle` | `aborted` |
| 재시작 | `restart` | `aborted`(살아 있는 아래 프레임만. 그 프레임과 위 프레임은 `restart`로 내려간다) |
| 맡기기로 아래 프레임이 기다림 | 반납하지 않는다. 프레임 상태 `waiting`만 바뀐다. 사유 `waiting`의 `lease.released`는 더 쓰지 않는다(옛 기록 읽기용) | - |
| 질문 대기(`ask`) | 반납하지 않는다. 프레임 상태 `asking`만 바뀐다(임대 유지). 재시작 뒤에도 같은 `requestId`로 다시 기다린다. 사유 `waiting`을 쓰지 않는다(옛 기록 읽기용) | - |

- 맡긴 쪽이 받는 값(E3 구현): 맡은 프레임이 `done`으로 내려가면 `done`(결과 포함), 그 밖의 사유로 위쪽이 내려가면 `aborted`다. 이 값이 아래 프레임의 다음 단계 `last`다.
- 앱과의 통신 [M6 요청 E-1 반영]: "주도자 하나"를 돌려주던 읽기 결과(`group.driveLock`)를 프레임 목록으로 바꾼다. 새 읽기 `drive.frames { threadId }` → `{ frames: { depth; plugin: string | null; versionId: string | null; leaseId: string | null; state: "driving" | "waiting" | "asking"; used: { turns; spawns; tokens }; limits }[] }`(맨 아래가 코어 루프 깊이 0)와 알림 `drive.framesChanged { threadId }`다. 화면의 `기본 › Helm › 검증`이 이것을 읽는다. 프레임이 내려간 사유는 `lease.released.reason`으로 읽는다: 사용자 명령에 의한 교체도 위 표의 `revoked`가 이미 덮으므로 새 값을 만들지 않는다. `WIRE_PROTOCOL_VERSION`을 올린다. 프로토콜 버전은 M5 트랙(C, D, E, F)이 각자 올리지 않고 통합 담당이 한 번에 올린다 [안].

### 2.7 dsh 소스 조사에서 얻은 조건

dsh는 단계 함수 방식이 아니다. 명령형 `while(true)` 루프이고, 플러그인은 입력함에 메시지를 넣는 부수효과로 계속을 지시한다. 코어에 턴·토큰 한도가 없고, 주도권 넘기기는 없으며(위임은 별도 자식 에이전트), 구동기 교체는 자리가 하나라 사실상 막혀 있다. 그 방식에서 보고된 문제를 이 설계의 조건으로 넣는다. 수용 기준은 A·B에 옮긴다.

- 주도 중이거나 `spawn`을 기다리는 중에 온 사용자 메시지는 맨 위 프레임에 바로 전달된다(dsh 토론 #12208: 최대 26분 막힘). 2.4의 "3단계 안에 처리하지 않으면 스택을 내린다"와 함께 적용한다.
- 계속 횟수에는 반드시 상한이 있다(dsh는 Stop 훅 계속에 상한이 없어 폭주 보고가 있음). 프레임 한도와 턴 종료 직전 훅의 계속 상한(지금 `l1.loop.gate.maxContinues` 8)을 유지한다.
- 종료와 재시작에서 대기 중인 명령과 입력이 지워지지 않는다(dsh 토론 #12258). 복원 시험 항목으로 둔다. 질문 대기 상태의 복원(4절 F6)이 이 조건의 일부다.
- 명령과 끼워 넣는 메시지에는 요청 id가 있다(dsh는 중복 방지 키가 없음).

## 3. 플러그인 격리 (1·2단계) [결정: 2단계까지 한다]

### 3.1 구조 [안]

- 신뢰 등급이 사용자·프로젝트인 플러그인은 **플러그인 호스트 프로세스**에서 돈다. 엔진이 자기 실행 파일을 다른 모드로 띄운다(`process.execPath` + 하위 명령. 이미 있는 방식). 그 프로세스를 OS 샌드박스로 감싼다(MCP 서버를 띄울 때 쓰는 `wrapArgv` 경로). 통신은 앱과 엔진 사이에 쓰는 줄 단위 JSON과 취소 규약을 그대로 쓴다.
- 신뢰 등급과 출처의 대응(D §4.6.9): 저장소 패키지(`core-*`, `cap-*`, `group-*`)만 `builtin`이고 엔진 프로세스 안에서 돈다. **릴리스가 동봉하는 기본 설치 플러그인(`bundled` 출처, 지금은 Helm)은 사용자 등급이라 격리 대상이다.** Helm은 `builtin: false`로 로드되고(`ext-host/src/loading-trust/entry-loader.ts:266`) 공개 API(`g.drive`, `g.capability`, `g.record`, `g.commit`)만 쓰므로 이미 사용자 플러그인과 같은 격이다(F §6.2). 단계 함수로 옮긴 뒤(E1) 격리한다(P2). 내장 전용 통로를 쓰는 쪽은 `cap-*`와 `group-learning`이다.
- 프로세스는 **대화 사이에 공유하고 오래 띄워 둔다.** 프로세스 키는 플러그인 이름이 아니라 `(이름, 내용 해시 또는 draftId)`다. 같은 키를 쓰는 모든 대화가 한 프로세스를 나눠 쓴다. 새 검토본이 승인되어 한 대화의 세대가 바뀌면 낡은 세대의 프로세스는 그 세대를 쥔 대화가 없어질 때 내리고, 초안은 검토본과 다른 키라 따로 돈다. 처음 띄우는 데 약 21ms, 왕복 약 0.02ms로 측정됐다(빈 자식). 실제 호스트의 처음 띄우기는 소스 실행 0.14~0.22 s, 컴파일 바이너리 0.04~0.05 s다(contracts를 싣는 비용이 대부분). 5 MB 입력의 왕복은 중앙값 14 ms(1 MB는 1.6 ms)다.
- 새 코드의 자리: 단계 실행기와 플러그인 호스트 프로세스는 `ext-host` 안의 모듈이다. 경계 너머의 얇은 대리 객체는 `group-sdk`에 둔다. `ext-host`는 L1 서비스를 `contracts`의 포트로만 부른다. 플러그인은 `core-*`를 import하지 않는다(F §6.3 DR-15).

### 3.2 플러그인 API를 경계 너머로

플러그인이 받는 객체 `g`와 같은 모양을 플러그인 호스트 쪽에 다시 만든다(얇은 대리 객체). 원칙: **즉시 답하는 호출을 없앤다.**

| 지금 | 경계 너머에서 [안] |
|---|---|
| 훅 핸들러 등록(`on`) | 플러그인이 시작할 때 "어느 훅을 듣는지"를 한 번 알린다. 엔진이 훅마다 요청을 보내고 결과를 받는다. 입력과 결과는 이미 전부 JSON이다 |
| 도구 `execute`, 명령·메서드 핸들러 | 같은 방식. 엔진이 호출 요청을 보낸다 |
| `state()`, 설정 값, 플래그를 즉시 읽기 | 요청마다 엔진이 필요한 값을 함께 실어 보낸다(훅 요청에 그 플러그인의 상태와 설정 스냅샷 포함). 256KB 상태도 왕복 0.13ms다 |
| `commit`, `record`, `post` | 비동기 요청. 결과를 기다린다 |
| `capability()`로 L2 기능 쓰기 | 닫지 않는다. 효과 있는 호출은 요청·응답으로 엔진에 이르러 `executeForPlugin`(도구 실행 블록)을 지난다. 읽기 전용 호출은 가벼운 길이다(1.3). 신원은 호스트가 붙인다 |
| `g.delegate`, `agents.judge`, `models.complete` | 공개 기능이다(F §6.2). 요청·응답으로 엔진에 이르고 각각 서브에이전트 블록(`agent.spawn.before`), 판정, 모델 호출 앞 훅을 지난다. 주도 한도에서 차감한다(2.3). 대리 객체 `g`에 이 항목이 있다 |
| 스트림을 지켜보는 훅(토큰마다) | 응답을 기다리지 않는 알림으로 보낸다. 2,000개를 3ms 안에 보낸다. 스펙이 이 훅들을 격리 불가로 뺀 것을 되돌린다 |
| `onDispose`, 상태 이전(`migrateState`) | 프로세스 시작·종료 규약의 일부로: 시작할 때 엔진이 저장된 상태와 버전을 주고 플러그인이 이전한 상태를 돌려준다 |
| 주도(`drive`) | 1절의 단계 함수. 엔진이 단계 요청을 보내고 명령을 받는다 |

P1 프로토콜 한 표 [제안: C0 (7)에서 확정]. 모든 메시지는 줄 단위 JSON이고 요청은 `id`가 있고 알림은 없다. 이 표의 이름과 필드가 C0에서 동결되기 전에 P1이 구현하는 것은 측정(메모리, 5MB 입력)뿐이다.

| 메시지 | 방향 | 종류 | 필드 | 동결 전에 정할 것 |
|---|---|---|---|---|
| `host.init` | 엔진 → 플러그인 | 요청 | `protocolVersion`, `pluginId`, `versionId`, `state`, `stateVersion`, `settings`. 응답: `protocolVersion`, 듣는 훅 이름 목록, 도구·명령·메서드 선언, `drive` 여부, 이전한 `state` | 버전이 안 맞을 때의 처리(종료 이유 `process_exit`), 응답 시간 한도, 프로토콜 버전을 올리는 책임자 |
| `hook.invoke` | 엔진 → 플러그인 | 요청 | `hook`, `input`, 상태·설정 스냅샷, `replay?`, `caller`, `deadlineMs`. 응답: 결과 또는 오류 | 훅 종류별 결과 모양(결정값은 F §4.2), 시간 초과 때의 프로세스 정지 방식 |
| `tool.execute`, `command.run`, `method.call` | 엔진 → 플러그인 | 요청 | 이름, 인자, 상태·설정 스냅샷, `caller`, `deadlineMs`. 응답: 결과 또는 오류 | 인자·결과 크기 상한(5MB 측정 뒤) |
| `drive.step` | 엔진 → 플러그인 | 요청 | `frame`, `state`, `last`(1.1의 `StepResult`), 요청 id. 응답: `DriveCommand`와 새 상태 | 명령 요청 id의 형식, 재시작 뒤 같은 요청 id 재전달 규칙 |
| `event.notify` | 엔진 → 플러그인 | 알림 | `eventKey`, 이벤트 | 전달 순서와 재전달(아래 이벤트 전달 규약) |
| `request.cancel` | 엔진 → 플러그인 | 알림 | 취소할 요청 `id` | 취소 뒤 늦게 온 응답을 버리는 규칙 |
| `engine.call` | 플러그인 → 엔진 | 요청 | `method`(`capability`, `delegate`, `judge`, `complete`, `commit`, `record`, `post`), `params`, 호출을 낳은 요청 `id`. 응답: 결과 또는 오류 | 호스트가 붙이는 호출자 신원(`plugin:<이름>`), `replay` 때의 거부(`replay_mode_denied`) |
| `host.dispose` | 엔진 → 플러그인 | 요청 | `reason`. 응답: 마지막 `state` | 응답 없이 끊길 때의 상태 보존 |
| 표준오류 | 플러그인 → 엔진 | 메시지 아님(스트림) | 줄 | 길이 상한과 시크릿 마스킹(`pluginStderr`) |

경계 규약 (P1 프로토콜 동결 전에 정해 둘 것):

- **이벤트 전달.** 요청과 알림을 구분한다. `first`/`chain`/`collect` 훅은 응답을 기다리는 요청이고 시간 한도를 가진다. 이벤트 구독(`tap`)은 응답 없는 알림이다. 알림도 같은 대화 안에서 한 구독자에게 발화 순서대로 하나씩 전달하고, 커밋 전에 끊기면 같은 `eventKey`로 다시 전달할 수 있으므로 적어도 한 번이며 핸들러는 `eventKey`로 멱등해야 한다. 이미 커밋된 결과가 있는 이벤트는 다시 전달하지 않는다. 이벤트 처리의 지연이 턴의 결과를 바꾸지 못한다(F §4.4.1이 같은 규약을 정의한다).
  - **구현 정정(P2, 2026-11-18).** 엔진은 스트림 알림을 흐름 키(등록, 지점, handlerIndex, 대화)마다 센다. 자식이 `event.done`(플러그인 → 엔진 알림)으로 처리 끝을 확인하기 전에 보낸 수가 상한 `NOTIFY_INFLIGHT_MAX`(8) [제안]에 닿으면, 다음 알림은 대기 칸 하나에 덮어쓰고 덮인 수를 `dropped`로 싣는다. 확인이 오면 대기 칸을 보낸다. 보내기는 기다리지 않는다. 확인이 `NOTIFY_STALL_MS`(30초) [제안] 동안 풀리지 않으면 미확인 수를 0으로 되돌리고 진단을 남긴다. 그래서 "같은 구독자에게 발화 순서대로 하나씩"은 상한 안에서만 지켜진다. 상한을 넘는 `every` 구독의 덮인 알림은 빠진다. 이 충돌은 [미결] [근거: xeon/packages/ext-host/src/isolation/notify-gate.ts] (F.extensions 부록의 흐름 제어).
- **돌려 보기 요청 플래그.** 요청에 `replay: true`를 실을 수 있다. 엔진은 그 요청 안에서 `commit`, `record`, `post`를 성공 응답으로 받되 버리고, `capability`와 `tool` 명령은 `replay_mode_denied`로 거부한다. 상태 읽기는 현재 커밋된 상태의 사본이다(E §4.8이 이 플래그를 쓴다).
- **호출자 신원.** 격리된 호출자의 신원 `plugin:<이름>`은 연결을 연 호스트가 붙인다(3.1).
- **표준오류와 종료.** 플러그인 프로세스의 표준오류는 엔진이 모아 턴 기록과 플러그인 상세에 잇는다(길이 상한, 시크릿 마스킹, E §3.2 `pluginStderr`). 프로세스 종료·강제 종료는 새 훅 실패 이유 `process_exit`, `process_killed`로 기록한다(3.3).
- 단계 함수의 입출력 형식은 1.1의 `DriveStep`, `DriveCommand`, `StepResult`다.

> **구현 정정(P2, 2026-11-18).** (1) `drive.step`의 실제 모양: params는 `DriveStepParams`(`PluginCallContext`에 `registration`, `last`(직전 `StepResult` 또는 첫 단계의 null), `budget`, `frame`{`frameDepth`, `calledBy`, `input`})이고, 응답은 `DriveStepReply` = `{command, limits}`다(`isolation-protocol.ts`). 엔진은 `command`를 `DriveCommandSchema`로 검사하고, 모양이 맞지 않으면 그 단계를 오류로 처리한다(프로세스는 산다). (2) 한도 캐시: 선언의 `drive.limits`로 시작하고 단계 응답의 `limits`로 바뀐다. 다만 임대의 한도는 임대를 받을 때 읽으므로(`grantOf`) 바뀐 값은 **다음 임대부터** 반영된다. 실행 중인 임대의 한도는 바뀌지 않는다. (3) 단계 시간 한도: `drive.step` 요청에 `deadlineMs`를 싣고, 감독이 그 시간을 넘기면 프로세스를 멈춘다(`process_killed`). 값은 상수 `DRIVE_STEP_DEADLINE_MS = 120_000`(제안값, 설정 키 항목은 정해지지 않았다)이고 엔진 시험은 `driveStepDeadlineMs`로 주입한다. (4) 상태 이전은 `host.init` 응답이 아니라 `state.migrate` 요청으로 한다(`hasMigration`이 참일 때만). 위 표의 "상태 이전" 행은 이 방식이 정본이다.

> **구현 정정(P2, 2026-11-18, 오류 종류).** 엔진 호출 실패는 원래 오류의 종류를 `origin`으로 싣고(기능 오류는 `CapabilityError`의 데이터, 확장 오류는 `PrimitiveError`의 코드), 자식은 엔진 안과 같은 오류로 되던진다. `origin`이 없으면 Helm의 검색 실패 같은 기능 오류가 단계 오류가 되어 조사가 끝나지 않았다(F.extensions 부록). 프로토콜 버전은 1 그대로다.

### 3.3 실패와 수명

- 시간 한도는 지금 값 그대로(막는 훅 30초, 고치는 훅 10초, 지켜보는 훅 5초). 지금은 시간 초과가 결과만 버리고 코드는 계속 돈다. 격리하면 **실제로 멈출 수 있다**(프로세스 종료 후 재시작).
- 프로세스가 죽으면: 진행 중이던 요청은 그 훅의 실패 규칙대로 처리(막는 훅은 막음, 고치는 훅은 건너뜀)하고, 한 번 다시 띄운다. 이유는 `process_exit`(스스로 끝남)과 `process_killed`(엔진이 시간 초과로 종료)이고 기록에 새 이유 문자열로 더해진다(E §3.2). 또 죽으면 지금의 자동 끄기 질문("끌까요?")으로 간다.
- 프로필 변경은 단계 경계에서 적용한다(지금과 같음). 어느 대화도 쓰지 않는 키의 프로세스는 내린다.

> **구현 정정(P2, 2026-11-18).** 기능 호출의 실패는 프로세스 실패가 아니다. 자식이 `CapabilityError`로 받아 엔진 안과 같이 단계 안에서 저하 처리한다(3.2의 오류 종류 정정). 단계 중 프로세스가 끝나면(`process_exit`) 또는 시간 한도를 넘어 멈춰지면(`process_killed`) 그 프레임과 위 프레임을 `error` 사유로 내리고, 보고 코드는 그 이유다. 이때 주도 등록은 오류로 표시되지 않는다(`driveError`를 켜지 않는다). 다음 시작 요청에서 감독이 프로세스를 다시 띄우고 새 프레임을 맡는다. 새 임대는 새 계통 id를 쓰므로 죽기 전에 기록된 턴을 같은 id로 다시 부르지 않는다. 단계 함수가 같은 턴을 다시 내면 그 턴은 다시 돈다. 호스트 재시작은 열린 임대를 같은 계통으로 되살리므로 기록된 턴이 기록된 결과로 돌아온다(`isolated-drive.test.ts`의 재시작 시험). 단계 함수가 던지거나 명령 모양이 맞지 않으면 그 단계는 오류이고 주도 등록을 `error`로 표시한다. 질문 대기(`ask`)는 엔진이 명령으로 실행하므로 단계 시간에 들지 않는다. [미결] [근거: packages/ext-host/src/isolation/engine-calls.ts의 `awaitUser` 분기] 단계 함수 안의 `awaitUser` 대기는 시간 한도에 든다. 엔진 안의 drive는 핸들러 예산이 없어 대기를 세지 않는데, 격리에서는 감독의 시간 한도가 대기 중에도 돈다. 대기를 한도에서 빼려면 단계 요청에 시계 멈춤을 붙여야 한다.

> **구현 정정(P2, 2026-11-18, 동등성 시험).** `packages/ext-host/test/isolation/parity-drive.test.ts`는 주도 시나리오(단일 플러그인의 명령 순서·기록·상태, A→B→A 맡기기의 네 배치, 깊이 상한과 자기 맡기기의 거부, B의 프로세스 죽음과 던짐)를 엔진 안과 격리에서 값으로 비교하고 같다. 알려진 차이는 하나다: 프로세스 죽음은 주도 등록을 `registered`로 두고 진단 코드가 `process_exit`이며, 단계 안의 던짐은 `error`와 `handler_failed`다.

### 3.4 샌드박스 범위와 네트워크 [결정: 2026-11-16, 2026-11-17 사용자]

- 플러그인 프로세스가 읽을 수 있는 것: 자기 패키지 폴더, 곧 검토본 `tree/`(초안은 `drafts/<draftId>/tree/`)와 런타임. 모두 읽기 전용이다. 쓸 수 있는 것: 없음(상태는 엔진을 통해서만).
- **네트워크는 전체 허용이 기본이다.** 지금 샌드박스의 네트워크 정책이 전역이라 플러그인별 허용 목록을 줄 수 없고, 플러그인별 허용 목록은 외부 사람이 만든 플러그인을 받게 될 때 다시 본다(격리 3단계). 남는 위험: 플러그인이 훅으로 받은 대화 내용과 도구 결과를 밖으로 보낼 수 있다. 이 위험은 `m5-plan.md` R27과 검토함 카드에서 숨기지 않는다(카드의 고정 안내는 [권고: 메인 세션, 확인 대기]이고 위험을 숨기지 않는다는 원칙은 사용자 결정이다). 초안은 격리 프로세스에서 돌지만 네트워크가 열려 있으므로 "격리돼 있어 안전하다"는 파일 읽기·쓰기 범위에 한정된 말이다. 검토 전 코드가 실제 작업에 이르는 문제(권한 모드)는 D §4.3.8과 F §5.3 U-6의 [결정: 2026-11-17 사용자, U2]다.
- Windows에는 샌드박스가 없다. 프로세스 분리만 되고 제한은 걸리지 않는다. 화면에 그 사실을 보인다. 3단계.

### 3.5 화면과의 관계

- 검토함의 "하는 일" 표에 "코드 실행: 격리됨/엔진 안"이 들어간다. 네트워크는 전체 허용으로 고정이라 칸을 두지 않고, 코드가 도는 플러그인의 카드에 고정 안내 한 줄을 둔다 [권고: 메인 세션, 확인 대기].
- 플러그인 화면(주입된 UI)은 지금도 선언형이고 앱이 그린다. 격리와 무관하다.

### 3.6 플러그인마다 프로세스 하나의 부작용과 대응 [결정: 반영]

| 부작용 | 내용 | 대응 |
|---|---|---|
| 메모리 | 프로세스마다 런타임이 따로 뜬다. **측정(2026-11-18, M1 Pro, Bun 1.4.3, 소스 실행)**: 빈 Bun 자식 15.8 MB(훅 0개든 20개든 같다), 5개 합 79 MB, 20개 합 316 MB. 실제 호스트(`plugin-host --stdio`, contracts·ext-host·group-sdk를 싣는다)는 최고 RSS 70~72 MB라 5개 약 0.35 GB, 20개 약 1.4 GB다. 컴파일 바이너리 경로의 RSS는 76~77 MB다. 판단: 코드 플러그인이 동시에 활성인 수가 한 자릿수면 버틴다. 20개 동시는 1.4 GB로 경계이고 유휴 내리기(60초)가 줄이므로 "같은 신뢰 등급끼리 한 프로세스" 설정은 지금 만들지 않고 사용자 판단으로 둔다 | 코드가 도는 플러그인만 프로세스를 가진다(지침·스킬·MCP 설정만 든 플러그인은 프로세스가 없다). 처음 불릴 때 띄우고, 한동안 안 불리면 내린다. P1의 첫 일로 메모리를 잰다. 넘치면 "같은 신뢰 등급끼리 한 프로세스"로 묶는 설정을 둔다 |
| 큰 입력의 직렬화 | 컨텍스트 조립·모델 호출 훅은 메시지 목록 전체를 받는다. 수 MB를 훅마다, 플러그인마다 직렬화한다(256KB에 0.13ms로 쟀고 그 이상은 재지 않았다) | 그 훅을 듣는 플러그인에게만 보낸다. 통신 프레임 상한(지금 1MiB)을 넘는 입력은 나눠 보내거나 참조로 넘긴다. P1에서 5MB 입력으로 잰다 |
| 플러그인끼리 메모리 공유 불가 | 한 저자의 두 플러그인이 객체를 나눠 쓸 수 없다 | 의도한 결과다. 엔진의 상태·기록·기능을 통해서만 주고받는다 |
| 즉시 답하는 호출이 없어짐 | 모든 API가 비동기가 된다 | 요청마다 상태와 설정 스냅샷을 실어 보낸다(3.2) |
| 고아 프로세스 | 엔진이 죽으면 플러그인 프로세스가 남을 수 있다 | 부모가 사라지면 스스로 끝나게 하고(표준입력 닫힘 감지), 엔진 시작 때 남은 것을 정리한다. 구현됨(P2): 띄울 때 `<상태>/plugin-hosts/<pid>.json`에 기록하고 끝나면 지운다. 엔진 시작 때 죽은 엔진의 기록을 읽어, 명령줄이 플러그인 호스트인 살아 있는 pid에만 SIGTERM과 유예 뒤 SIGKILL을 보낸다(`apps/host/src/assembly/plugin-host-orphans.ts`) |
| 진단이 어려워짐 | 로그와 스택이 프로세스마다 흩어진다 | 표준오류를 엔진이 모아 턴 기록과 플러그인 상세에 잇는다(3.2) |
| 부분 실패 | 턴 중간에 한 플러그인만 죽을 수 있다 | 훅 종류별 실패 규칙을 그대로 적용하고 한 번 다시 띄운다(3.3) |
| 의존성 중복 | 플러그인마다 자기 패키지를 따로 읽는다 | 버전 충돌이 없어지는 이점이기도 하다. 디스크와 메모리 중복은 감수한다 |

이점: 한 플러그인의 충돌·멈춤·무한 반복이 엔진과 다른 플러그인에 번지지 않는다. 시간 초과 때 실제로 멈출 수 있다. 플러그인마다 샌드박스 범위를 줄 수 있다. 다시 불러오기가 프로세스 재시작으로 단순해진다. 플러그인 수가 많을 때의 메모리는 재지 않았다(7절). 프로세스 단위의 기본은 "코드 플러그인 하나(버전 하나)에 하나"이고, 메모리가 문제되면 같은 신뢰 등급끼리 한 프로세스로 바꾼다.

## 7. 확인하지 못한 것

- 조사 넷의 코드 위치는 정적 읽기 결과이고 실행으로 확인하지 않았다.
- 실제 엔진의 샌드박스 래퍼로는 지연을 재지 못했다(패키지가 워크트리에 설치돼 있지 않아 `sandbox-exec`로 대신 쟀다).
- 플러그인 프로세스가 여럿일 때의 메모리와 시작 시간 합계: M5b-1에서 쟀다(§3.6). 남은 것은 실제 플러그인(큰 의존)을 싣은 호스트의 메모리다.
- Linux에서의 지연과 샌드박스 요구 사항(bwrap 등).
- 6절의 [권고](한도 차감 세부)와 층 지도 이름이 사용자 확인 대기다. 사용자 명령 우선과 깊이 상한 8은 2026-11-17 사용자 결정으로 닫혔다. 이름 [제안]인 `drive.command_settled`와 `x.primitives.driveMaxDepth`는 C0에서 확정한다(`m5-plan.md` C0 (6)).

## 8. 층 개념과 층 재편 [결정: 2026-11-17 사용자, U4]

- 사용자와 개념 문서에서는 "코어(블록)와 플러그인" 둘만 쓴다. 코어 엔진(블록과 그 보장)을 뺀 모든 것은 플러그인이다. 지금의 L2(파일·셸, MCP, 웹, 지식, 작업 관리, 예약 등)는 "도구를 주입하는 기본 설치 플러그인"이고, L3(Helm, 학습, 가이드)는 "훅과 주도를 쓰는 기본 설치 플러그인"이다. 차이는 층이 아니라 그 플러그인이 하는 일(Inject / Hook / Drive)이다.
- 층 지도: F 계약 / X 플러그인 체계 / L0 플랫폼 / L1 코어(블록 여섯과 보장. 기록 블록은 이벤트 구독만 있고 고치거나 막는 훅이 없다) / 플러그인(한 층: 기본 설치와 사용자 제작이 같은 격) / L4 앱.
- L1으로 내릴 기준: 빠지면 블록의 보장이 깨지는 것. 사람에게 묻기(`dialog.ask`), 샌드박스를 거치는 파일·프로세스 서비스. 모델용 도구(`read`, `edit`, `bash` 등)와 MCP·웹·지식·작업 관리·산출물·예약은 플러그인이다. 명령 등록·상태 표시·첨부는 코드 확인 뒤 정한다. 코드 이동(사람에게 묻기를 코어로, 파일·셸 패키지를 서비스와 도구로 나누기)은 한꺼번에 하지 않고 E2에서 경계를 정할 때 함께 한다. 크기와 이동 목록은 F §6.1이 조사했다.
- 결과: **뺄 수 없는 플러그인이 없다**(코어는 코어, 플러그인은 전부 넣고 뺄 수 있다). 프로필은 "플러그인 목록과 설정 값 + 코어의 설정 값"이다. 이것이 개념 초안의 "코어 플러그인은 모든 프로필에 항상 들어 있고 뺄 수 없다"를 대체한다(ADR §3.12, §6).
- 이것이 참이 되려면 기본 설치 플러그인이 사용자 플러그인과 같은 공개 API로 만들어져야 한다. 지금은 내장 전용 통로가 있다(모델 서비스, 컨텍스트 서비스, 판정 API, `g.delegate`). 단계 함수의 `model`·`tool`·`spawn` 명령과 엔진이 태워 주는 기능 호출이 이 차이를 줄이고, 남는 내장 전용 통로는 F §6.2의 목록으로 관리하며 줄여 간다. Helm은 이미 공개 API만 쓴다(3.1).
- 코드: 디렉터리 이름(`cap-*`, `group-*`)과 의존 규칙(기능 패키지끼리 import하지 않는다 등)은 그대로 둔다. 이름을 바꾸는 일은 이득이 작고 범위가 크다. 문서의 층 지도 이름을 고쳐 쓸지는 [확인 대기]다.
- 격리는 층이 아니라 신뢰 등급으로 정한다(3.1): 저장소 패키지(`builtin`)는 엔진 안, 번들·사용자·프로젝트는 플러그인 프로세스.
