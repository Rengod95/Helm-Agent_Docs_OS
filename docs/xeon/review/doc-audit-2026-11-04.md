# 문서 감사: 최근 사용자 결정과 옛 문서 대조 (2026-11-04)

발단: 메인 세션이 "엔진에는 훅 순서 입력이 없다"고 사용자에게 틀리게 말했습니다. 근거는 `desktop-ux/spec.md` §6.28의 옛 문장이었습니다. 사용자는 2026-11-03에 훅 순서를 자유롭게 하기로 했고(15-2) `hooks.order.*`와 `x.operations.hookOrder`는 병합되어 있습니다.

## 1. 방법과 한계

- 기준은 새 것이 이깁니다. `_notes/m4-decisions.md`, 결정 목록과 아침 보고, 문서의 `[결정: 날짜 사용자]` 표지, 코드 순입니다.
- Haiku 에이전트 11개가 디렉터리별로 읽고 표를 냈습니다. 표의 행은 에이전트 주장이고, 고친 것은 모두 제가 원문 줄을 열어 확인한 것만입니다.
- 에이전트 대부분은 줄마다 읽지 않고 키워드와 표지로 훑었습니다. 그래서 놓친 문장이 있을 수 있습니다(재현율 보장 없음). `docs/xeon` 안 `.md` 약 300개를 대상으로 했고 `_research/`는 뺐습니다.
- `just verify`, CI는 돌리지 않았습니다. `just docs-route --check`는 오류 0(경고 6은 감사 전부터 있던 id 이름 경고), `just terms check`는 위반 0(경고 51은 그대로)입니다.

## 2. 종류별 개수

에이전트가 확인했다고 낸 행 수와 제가 고친 수입니다. 한 행이 두 종류에 걸치면 주된 쪽으로 셌습니다.

## 3. 고친 것

커밋은 4개입니다(해시는 §8).

1. 훅 순서·플러그인 화면 위치·권한 판정
   - `desktop-ux` §6.28: "런타임에 순서 입력 없음" 문장과 배지(DP-56)를 15-2 결정과 `hooks.order.*`에 맞게 고쳤습니다. 기본은 guard 맨 앞이고 사용자가 풀 수 있으며, 건너뛰는 순서는 경고 모달로 알립니다.
   - `desktop-ux` §6.22.0 "층 패널" 행: 남은 미결을 정확히 적었습니다. 입력이 없어서가 아니라 "이 패널 순서가 그 입력과 같은 것인지"가 시안 Q2로 열려 있습니다.
   - `X/operations` §4.1.3 예 1: 권한 판정은 도구 파이프라인의 고정 단계 5b·5c입니다(`packages/core-tools/src/pipeline.ts`). core-tools는 `on` 핸들러를 등록하지 않습니다(grep 0건). 예는 가정의 `guard` 핸들러 G로 다시 썼고, §4.1.4 쪽 `GUARD_EXTENSIONS` 문장도 맞췄습니다.
   - 플러그인 화면 이동 `[결정: 2026-11-04 사용자]`: ADR-0021 `page` 행, `desktop-ux` §4.9 내비 문장과 진입 문장에 "대화 영역 내비로 옮김, 크래프트 내비 여섯 유지, 아직 안 만듦"을 적었습니다. 시안 그림은 옛 모양이라고 밝혔습니다. 완료로 표시하지 않았습니다.
2. 닫힌 미결과 용어
   - 설정 범위 `session`을 `launch`로 고쳤습니다(F, X, L0, L1, L3, L4 해당 줄). 저장 문자열과 코드 id는 그대로입니다.
   - 매니페스트 `kind` 문장을 `plugins[]`와 `group` 선언으로, 훅 종류 `session`을 `thread`로, "임시 이름 Fresnel"을 확정으로 고쳤습니다.
   - 닫힌 결정 반영: Stagehand 승인, 루프백 endpoint 설치 확인, B12 놓친 예약 한 번 따라잡기, A2(M4 확인 줄, M5 교체), R4 훅 이름 별칭 없음, R15, B16, ULID 단조성, D-M3-05.
   - 시안 답 반영(아직 안 만듦): Q3 재생 막대 없음, Q4 자동 꺼짐 위치, Q8 "모두 거절", Q9 앱 안 설치.
3. host-service: B11(승인 대기는 live), B12, 파일 감시, `launch` 범위 이름.
4. 크래프트 용어, 팔레트·핸들러 시간·버전 기록 gap 표식 몇 곳, 비워 둔 "작업대" 몇 곳, `m4-plan.md` §0a 상태표와 이 문서.

시안 Q2(층 패널 순서)와 훅 순서 범위 좁히기는 아직 답이 없어서 답을 적지 않았습니다.

## 4. 고치지 않고 남긴 것 (이유 포함)

- `[gap:W-xx]`와 "지금" 칸(`desktop-ux` §10 약 40행, §6.24~6.26): 에이전트가 코드에 처리기가 있다고 보고했지만, 행마다 wire 이름과 상태를 줄별로 확인하지 못했습니다. 한 곳씩 고치면 표가 일부만 맞게 됩니다. 별도 트랙에서 `handlers/m4/*`와 대조해 한 번에 고치길 권합니다.
- "프로젝트"를 쓰는 산문(L0 sandbox, L1 tools·agents·models·persistence, L2 README·knowledge, L4 settings-ui·cli·host-service, security 등 약 60줄): 바꿀 말이 "작업 폴더"인지 사용자가 아직 확정하지 않았고(ADR-0022 표는 신뢰 등급 라벨을 아직 "이 프로젝트"로 둠), 코드 id `project`와 섞입니다. 구현은 M5입니다.
- "세션"이 대화 뜻인 산문(L2 schedule·web, L4 cli, L0 process, 엔지니어링 문서 약 100줄): 코드 id `fresnel.session`, 세션 DB, 브라우저 세션과 섞여 있어 줄별 판단이 필요합니다.
- CLI를 제품 표면처럼 쓴 문장(L3 authoring §4.5 전체, L3 slots, L4 settings-ui의 `fresnel secret add` 안내, desktop-ux의 "터미널(fresnel CLI)이 쓰고 있어요", ADR-0021 §3.9 "CLI 대체"): 삭제나 문구 교체가 큽니다. 코드 문구(`ko.json`)와 같이 바꿔야 하므로 코드 트랙이 필요합니다.
- 제목 띠(DP-05 "최상단 띠 없음" 대비 desktop-ux 52·203·504·507·730·735·1194행): 에이전트 주장이 맞아 보이지만 결정 날짜는 2026-10-30이고 이 줄들이 시안 설명인지 현행인지 확인하지 못했습니다.
- `desktop-ux` 2113행(층 패널)과 2221행(§6.22.6 "순서는 표시용")은 서로 다른 말을 합니다. Q2가 열려 있어 둘 다 그대로 둡니다.
- 옛 시안·와이어프레임 그림, 구현 기록 절(`plan.md` §8~§13 등)은 과거 기록 표지가 있다고 보고 손대지 않았습니다.
- 에이전트가 보고했지만 빠뜨린 것: L4 `cli`·`release` 일부 B 행, `desktop-ux` 1~1250행의 B 행 중 `[gap:W-05]` 등. 위 gap 항목과 같은 이유로 한 번에 처리해야 합니다.

## 8. 재발 방지 제안 (구현하지 않음)

권고 하나: **`[결정: 날짜 사용자]`가 붙은 줄에 "대체: 문서id#절" 표지를 의무로 하는 정적 검사**를 `docs-route`에 넣는 것이 아니라, 더 작게 **"없다·미결" 문장은 근거 인용을 의무로 하는 검사**를 권합니다.

- 규칙: 본문에서 "없다", "아직 없", "입력이 없", "[미결]"로 쓴 줄은 같은 줄이나 바로 아래에 `[근거: 코드경로 | 질문번호 | 결정날짜]` 중 하나를 달아야 합니다. `docs-route --check`가 줄 단위로 찾고, 없으면 경고(나중에 오류).
- 이번 사고에 효과가 있는 이유: 2655행은 "런타임에 순서 입력이 없습니다"만 있고 근거가 없었습니다. 근거를 달게 하면 쓸 때 코드를 열어야 하고, 읽는 에이전트는 근거의 날짜와 코드 경로로 낡은지 바로 판단합니다.
- 비용: 기존 "없다/미결" 문장이 수백 줄이라 처음엔 경고가 많이 나옵니다(경고만 켜고 새 줄에만 오류로 시작). 오탐 방지를 위해 문장 패턴을 좁혀야 하고, 근거를 가짜로 달 수 있어 사람 검토는 여전히 필요합니다. 구현은 `scripts/docs-route`의 줄 검사 한 함수와 시험 하나로 작아 보입니다.
- 나머지 두 안과 비교: (a) "superseded by" 표지는 새 결정이 옛 문장을 찾아 표지를 달아야 해서 결정 때마다 사람이 grep해야 하고, 이번에 놓친 이유가 바로 그것입니다. (c) 현재 결정만 모은 생성 파일은 에이전트 맥락엔 가장 좋지만 `m4-decisions.md`가 자유 서식이라 생성 규칙부터 필요해 비용이 큽니다. 권고안을 한 뒤 (c)를 따로 검토하는 순서가 낫습니다.
