# M5 구현 계획 (플러그인 기반)

- 기준: 브랜치 `m4/cyP`(`xeon/foundation`에서 이어진 M4 통합 브랜치)와 ADR-0023. 코드 사실은 정적 읽기이고 구현 트랙의 첫 일로 해당 줄을 다시 읽어 확인한다.
- 원천: `docs/xeon/decisions/ADR-0023-plugin-profile-core.md`(결정), 설계 스펙 넷 `docs/xeon/review/m5/drive-isolation.md`, `profile-project-loader.md`, `turn-record-metrics.md`, `hooks-core-boundary.md`, 화면 스펙 `docs/xeon/review/m6/craft-flows.md`, 개정 전 계획 `review.m4-plan`(M5로 이월된 항목), `product.scope.spec` §4(M5 행), 사용자 결정 기록 `_notes/m4-decisions.md`(저장소 밖 메모).
- 기간은 지금의 리드 병렬 방식 기준 어림이고 측정한 값이 아니다.
- 종료 조건 번호: M3는 X1…, M4는 Y1…, 이 문서(M5)는 **Z1…**을 쓴다. M6의 종료 조건은 `docs/xeon/review/m6-plan.md`의 W1…이다. 각 조건은 요구(R번호)와 시험으로 묶는다.
- 공통 규칙은 `review.m4-plan`을 따른다: 한 커밋 한 층, 층 스펙 문서는 같은 커밋, contracts는 지정 트랙만, `as`·`!`·`any`·`Reflect.get` 금지, 값 비교 시험, 명시적 `git add`. 전체 검사(`just verify`)와 CI는 병합 직전에만 돈다. CI는 최소로(land 직전 한 번) 쓰고 러너는 ubuntu-24.04로 고정한다(커밋 `d599b1c71`): 샌드박스가 ubuntu-26.04 러너 이미지에서 시작하지 않기 때문이다 [결정: 2026-11-17 사용자]. 리눅스에서만 나는 시험 실패는 CI가 아니라 Docker에서 재현한다. 이름 대응: "PRD"로 인용된 옛 문서는 이 문서다(R번호 그대로이고 "PRD §7"은 이 문서 §14다). "craft-flow"·"flow"는 `docs/xeon/review/m6/craft-flows.md` 제1부(흐름 n), "개념 문서"는 ADR-0023(대체한 절은 ADR §6), "로드맵"은 이 문서 §7과 `m6-plan.md`다.

## 2. 문제와 목표

코딩 에이전트를 자기 방식에 맞추려는 사용자는 지금 어떤 도구에서도 세 가지를 얻지 못한다. 조사 여섯 건(`research-1`~`6`)의 근거다.

- **보이지 않는다.** 규칙이 그 턴에 모델에게 갔는지, 훅이 막은 것인지 고장 난 것인지, 무엇이 왜 로드됐는지 알 수 없다.
- **지키게 할 수 없다.** 지침은 권고일 뿐이고, 강제하려면 셸 스크립트와 JSON 규약을 아는 전문가여야 한다. 승인도 "매번 묻기"와 "전부 통과" 둘뿐이다.
- **믿을 수 없다.** 신뢰는 설치 때 한 번인데 코드는 그 뒤에 바뀌고, 수단(규칙, 스킬, 훅, 모드, 플러그인)이 겹쳐 어디서 온 설정인지 모른다.

Fresnel은 플러그인 체계와 화면(Craft)을 이미 가졌지만, 용어가 섞이고(확장, 플러그인, 그룹, 애드온), 플러그인별 켜고 끄기와 층 우선순위가 있어 같은 문제를 그대로 가진다.

### 목표

1. 사용자가 "이 대화에 무엇이 적용되고 있나"에 프로필 하나로 답할 수 있다.
2. 어느 턴이든 "무엇이 실렸고 어느 플러그인이 무엇을 했나"를 턴 기록에서 확인할 수 있다. 의도된 막음과 고장이 구분된다.
3. 대화에서 "다음부터는 이렇게 해"라고 말한 것이 코드를 직접 쓰지 않고도 강제되는 플러그인이 된다.
4. 검토를 거치지 않은 코드는 실제 대화에서 돌지 않는다(사용자가 명시적으로 얹은 초안 제외). 검토 뒤 원본이 바뀌어도 실행되는 것은 검토한 내용이다.
5. 플러그인이 대화를 주도하고, 다른 플러그인에게 맡겼다 돌려받을 수 있다. 그 동안에도 권한·샌드박스·기록은 빠지지 않는다.

## 3. 하지 않는 것

| 하지 않는 것 | 이유 |
|---|---|
| 플러그인별 켜고 끄는 스위치, 설정 층 우선순위 | "프로필 하나"라는 답을 흐린다. 프로필에 넣고 뺀다 |
| 코어 루프의 교체, 블록 속의 교체 | 관문과 기록의 보장이 깨진다 |
| 다른 하네스 형식을 그대로 읽는 호환 | 자체 구조가 묶인다. 지금 엔진이 읽는 `.mcp.json`·`.agents/skills`도 제거한다 [결정: 2026-11-17 사용자]. 완전한 이식은 별도 마이그레이션 기능(로드맵 M5g, 설계 먼저)이 맡는다 |
| 플러그인 파일을 손으로 고쳐 바로 실행 | 검토 절차가 둘로 갈린다. 수정은 담당 AI로만 |
| 플러그인 마켓, 외부 배포 | 지금은 본인과 에이전트가 만든 것만 다룬다 |
| 플러그인별 네트워크 허용 목록, Windows 샌드박스 | 격리 3단계. 지금 샌드박스 구조로는 못 준다. 외부 사람이 만든 플러그인을 받게 될 때 다시 본다. 그 전의 기본은 전체 허용이다(R27) |
| 디자인 시안을 HTML로 따로 만드는 일 | Craft v2 HTML 시안은 반려됐다. 디자인은 앱 안에 직접 만든다 [결정: 2026-11-17 사용자] |
| 새 브랜드 용어 | 화면 용어는 플러그인, 프로필, Inject / Hook / Drive, 블록 이름, 권고·강제뿐 |

## 4. 사용자 이야기

- 대화 중에 에이전트가 원치 않는 일을 했을 때, 그 줄을 골라 "다음부터 물어봐"라고 하면 그 일을 막는 플러그인 초안이 생기기를 원한다. 같은 일을 다시 겪지 않기 위해서다.
- 초안을 실제 프로필에 넣기 전에, 그것이 지난 턴에서 무엇을 했을지와 지금 써 보면 어떤지 확인하고 싶다. 내 작업을 망치지 않기 위해서다.
- 새 대화를 열 때 "개발"이나 "글쓰기" 같은 프로필을 골라 그 일에 맞는 플러그인만 쓰고 싶다. 필요 없는 도구가 컨텍스트를 차지하지 않게 하기 위해서다.
- 에이전트가 지침을 안 따랐을 때, 그 지침이 그 턴에 실렸는지부터 확인하고 싶다. 모델 탓인지 설정 탓인지 가리기 위해서다.
- 플러그인이 모든 것을 막아 대화가 망가졌을 때, 한 번의 조작으로 빠져나오고 싶다.
- 내가 만든 플러그인이 실제로 일하는지, 안 쓰이는지, 느린지를 숫자로 보고 그 자리에서 고치고 싶다.
- Helm 같은 플러그인이 대화를 이끄는 동안, 지금 누가 이끄는지 보이고 언제든 멈출 수 있기를 원한다.
- 저장소에 든 플러그인이 내가 승인하기 전에는 실행되지 않기를 원한다.
- Helm이 이끄는 중에 다른 주도 명령을 치면 묻지 않고 바로 넘어가고, 내려간 쪽은 다시 명령해 이어 가고 싶다.

## 5. 요구 사항 (R1~R34, 확인 방법 포함)

R34(Craft 내비, 여섯 항목)는 M6의 요구이고 `m6-plan.md`에서 종료 조건을 갖는다. 나머지는 이 문서의 종료 조건 Z로 묶는다(§12).

### P0: 이것 없이는 성립하지 않는다

| # | 요구 | 확인 방법 |
|---|---|---|
| R1 | 대화는 프로필 하나를 참조한다. 프로필을 고치면 그 프로필을 쓰는 대화가 다음 단계 경계에서 따라 바뀐다 | 프로필에서 플러그인을 빼면, 그 프로필을 쓰는 열린 대화의 다음 단계에서 그 플러그인의 도구와 Hook이 사라진다 |
| R2 | 플러그인별 스위치가 없다. 내장 기본 프로필은 지울 수 없고 권한 모드 "모두 허용"이다. 프로필은 권한 모드를 가진다(R28) | 화면과 wire에 플러그인별 켜기·끄기 조작이 없다 |
| R3 | 새 대화는 프로필이 골라진 채 열리고(선택기의 기본값은 같은 폴더에서 마지막에 쓴 프로필 [결정: 2026-11-17 사용자, U5]), 대화마다, 도중에도 바꿀 수 있다. 프로필 칩에서 기본 프로필로 한 번에 전환한다 | 모든 도구 호출을 막는 Hook이 든 프로필에서 칩으로 전환하면 다음 턴이 정상으로 돈다 |
| R4 | 폴더 하나가 플러그인이다. 스킬 폴더, MCP 설정, Hook 코드, Drive 코드를 Fresnel 자체 배치로 같은 방식으로 읽는다. 다른 하네스 형식(`.mcp.json`, `.agents/skills` 등)은 인식하지 않는다. 지금 엔진이 읽는 부분은 제거하고 변환은 별도 마이그레이션 기능(로드맵 M5g)으로 설계한다 [결정: 2026-11-17 사용자] | 스킬 파일만 든 폴더가 포장 없이 플러그인으로 잡히고, 프로필에 넣으면 스킬 목록에 실린다. `.agents/skills`와 루트 `.mcp.json`은 후보로 잡히지 않는다(Z14) |
| R5 | 앱은 검토된 사본만 실행한다. 원본 폴더가 달라지면 실행 중인 것은 그대로이고 검토함에 새 버전이 올라온다 | 검토 뒤 원본의 Hook 코드를 바꿔도 다음 턴의 동작이 바뀌지 않고, 검토함에 한 건이 생긴다 |
| R6 | 모든 생성과 변경은 검토함을 지난다. 검토에는 공통 스키마(목적, 하는 일 세 칸, 강제력 권고/강제, 실행, 비용, 건강, 출처·검토, 쓰는 곳), 이전 버전과의 "하는 일의 차이", 증거가 보인다. 코드가 도는 플러그인(Hook, Drive)은 같은 검토를 받되 카드에 "코드가 직접 실행됨"과 격리 여부가 보인다 | 에이전트가 만든 플러그인이 승인 전에는 어느 프로필에도 들어가지 않는다 |
| R7 | 주도 함수는 단계 함수다. 명령은 turn, model, tool, ask, spawn, handoff, commit, yield, done이고 엔진이 블록으로 실행한다. 옛 주도 함수 어댑터는 두지 않는다 | Helm과 빌더가 새 모양으로 돌고, 재시작 뒤 같은 명령을 두 번 실행하지 않으며 반대로 대기 중이던 명령과 입력이 지워지지 않는다. 명령과 끼워 넣는 메시지에는 요청 id가 있다. 주도 명령 결과의 내구 기록 방식은 [결정: 2026-11-17 사용자, U1]이다: E1(Z2)은 상태 사건 종류가 카탈로그에 있는 것까지, `model`·`tool` 명령 결과가 그 사건으로 남는 것은 E2(Z3)가 시험한다 |
| R8 | 주도권은 프레임 스택이다. 맡기면 맡은 쪽이 주도하고 끝나면 결과와 함께 돌아온다. 한도는 맡긴 쪽의 남은 한도를 넘지 못한다 | A → B → C → B → A 시나리오 시험. 깊이 상한(기본 3 [권고: 메인 세션, 확인 대기])을 넘으면 거부 결과. 주도 중이거나 서브에이전트를 기다리는 중에 온 사용자 메시지가 맨 위 프레임에 바로 전달되고, 3단계 안에 처리하지 않으면 코어 루프가 받는다. 계속 횟수에는 상한이 있다(턴 종료 직전 훅의 계속 8, `gate.maxContinues`. Z4가 시험한다). 주도 중 다른 주도 명령은 R25 |
| R9 | 사용자가 중지하면 스택 전체와 백그라운드 서브에이전트가 멈추고 코어 루프로 돌아간다 [결정: 사용자 2026-11-17, 백그라운드 포함] | 중지 뒤 주도 함수가 다시 불리지 않는다(주도권 반납은 E0에서 끝남. 스택 전체 내림은 E3, 백그라운드 서브에이전트 정지는 E1에 남음) |
