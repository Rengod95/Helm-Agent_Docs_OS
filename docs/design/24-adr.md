# 24. 아키텍처 결정 기록 (ADR)

- 작성: P3 아키텍트, 2026-10-11 (1단계 초안). 이후 모든 설계 에이전트와 조정자가 더한다(브리프 §3.4 "P3 시작, 전원 추가").
- 상태: 설계 초안.
- 함께 읽을 문서: `process/00-design-brief.md`(이하 "브리프"), [06 시스템 아키텍처](06-system-architecture.md)
- 표시 규칙: 브리프 §5.2. 외부 사실의 확인 수준과 출처 줄임말은 06 머리말과 같다.

## 1. 목적과 범위

- 이 문서는 Helm 설계의 결정과 그 이유, 버린 대안을 한곳에 모은다. 대화 [157]에서 "각 결정은 결정 기록(ADR) 형식으로 남긴다"고 정했다(extracts-4 18-3, 대화 L4396).
- 다루는 것: 브리프 §2의 구조 결정(19~24, 26~40)과 원전을 바꾼 이론 결정 중 구조에 영향을 주는 것(2, 3, 5, 18), 원전의 이전 결정(D1~D3), 06이 내린 결정(ADR-06-01~16), 다른 문서가 정할 ADR 예정 목록.
- 다루지 않는 것: 결정의 세부 명세. ADR은 결정과 이유만 적고, 명세는 "관련 문서"의 절을 참조한다.

## 2. 형식과 번호 규칙

### 2.1 번호

`ADR-SS-NN`

- `SS`: 결정이 나온 문서 번호 두 자리. `00`은 설계 브리프, `06`은 시스템 아키텍처, 그 밖은 해당 설계 문서 번호(`07`, `09`, …, `25`). 원전(v0.1·v0.2)의 이전 결정은 `P0`을 쓴다(`ADR-P0-D1`).
- `NN`: 그 문서 안의 순번 두 자리. **브리프 결정은 결정 번호와 같게 둔다**(예: 브리프 결정 26 = `ADR-00-26`). 그래서 브리프 번호로 바로 찾을 수 있다.
- 한 번 쓴 번호는 다시 쓰지 않는다. 결정이 바뀌면 새 번호를 쓰고 옛 ADR의 상태를 "대체됨"으로 바꾼다.

### 2.2 상태 값

| 상태 | 뜻 |
|---|---|
| 결정 | 제품 소유자가 정했다(브리프 §2의 [결정] 항목, 또는 이후 사용자 확인) |
| 제안 | 조정자나 설계 에이전트가 정했고, 바꾸려면 근거와 함께 이 문서를 고친다(브리프 §2.3) |
| 후보 | 아직 정하지 않았다. 소유 문서가 정한다 |
| 대체됨 → ADR-x | 다른 ADR로 바뀌었다. 내용은 지우지 않는다 |
| 폐기 | 이유와 함께 버렸다 |

### 2.3 양식

모든 ADR은 아래 항목을 가진다. "평가"는 원전의 아키텍처 결정 평가 질문 8개(canon §13.14, F07 §14)에 짧게 답한 것이다: ① 어느 공리에서 필요한가 ② N/E/M 중 어떤 상태를 다루는가 ③ 정본인가 투영인가 어댑터인가 ④ 어떤 이벤트와 불변조건이 필요한가 ⑤ 사람의 상황 인식과 방향 수정 능력을 높이는가 ⑥ 사용자의 주의력을 어디서 아끼고 어디에 쓰게 하는가 ⑦ 실패했을 때 원본 근거와 상태를 복구할 수 있는가 ⑧ 특정 모델·도구 없이도 의미가 유지되는가. 해당이 없으면 "해당 없음"이라고 적는다.

```markdown
### ADR-SS-NN 제목
- 상태: … · 날짜: YYYY-MM-DD · 결정자: … · 출처: …
- 맥락: 무엇을 정해야 했고 무엇이 제약이었나
- 결정: 정한 것 (한두 문장)
- 근거: 왜
- 기각한 대안: 대안과 버린 이유
- 결과: 이 결정으로 지켜야 할 것, 생기는 비용과 위험
- 평가: ①… ②… ③… ④… ⑤… ⑥… ⑦… ⑧…
- 관련 문서: 파일 이름과 절
```

### 2.4 고치는 규칙

1. 결정의 내용을 바꾸면 새 ADR을 만들고 옛 ADR을 "대체됨"으로 표시한다. 오탈자나 참조 절 번호 수정은 제자리에서 고친다.
2. [결정] ADR(제품 소유자 결정)은 설계 에이전트가 바꾸지 않는다. 이의는 최종 보고의 "브리프에 대한 이의"로 올린다(브리프 머리말).
3. 다른 문서의 에이전트는 이 파일을 직접 고치지 않는다. 자기 문서 끝 "ADR 후보" 절에 적고, 조정자가 2단계에서 §8로 옮긴다(§8 규칙).

## 5. 브리프 결정 ADR

### 5.1 원전을 바꾼 이론 결정(구조에 영향을 주는 것)

#### ADR-00-02 Effect class와 가역성 판별은 Helm 밖(권한 레이어)

- 상태: 결정 · 날짜: 2026-10-11 · 결정자: 제품 소유자 · 출처: 브리프 결정 2, v0.3 §5-2, 대화 L3340, L3363
- 맥락: 원전 kernel 문서는 행동을 R0~R4로 고정 분류했고, 공리 A7은 권한이 가역성·파급 범위·관측 가능성에 따라 달라진다고 해서 둘이 맞지 않았다(extracts-4 1-25).
- 결정: Effect class(R0~R4)와 행동의 가역성 판별을 Helm에서 뺀다. 에이전트 권한 레이어가 정하고, Helm은 그 판정 결과를 받아 쓴다.
- 근거: 사용자 진술 "요즘 LLM 모델은 이를 알아서 판별할 정도로 … HELM 연구에서 다룰 게 아니라 에이전트 권한레벨에서 설계와 원칙을 정하는 것"(대화 L3363).
- 기각한 대안: (1) 고정 R0~R4 목록. (2) 관찰 가능한 사실(백업, git 추적, flag, 공개 범위)에서 등급을 계산하는 Claude 대안(대화 L3353). 대화에서 Claude가 "정의가 없으면 그 판단을 모델이 매번 하게 된다"는 위험을 남겼다(extracts-4 1-26).
- 결과: 구조상 "권한 레이어"는 Helm 커널 밖의 판정 입력이다. 1차 구현에서는 13(도구 범위 검사·격리)과 18(보안)이 이 자리를 채운다. 06의 커널 순수성 규칙(R5)과 별개로, 권한 레이어 판정은 `engine` 입력에 값으로 들어온다. 정보가 밖으로 나가는 행동(send, 비밀 노출)을 권한 레이어에서 고정 규칙으로 둘지는 13·18의 미결이다(extracts-4 d3).
- 평가: ① A7(위험 판별은 넘김) ② M(행동), P ③ 어댑터·권한 레이어 ④ 권한 판정 결과를 관찰로 기록 ⑤ 해당 없음 ⑥ 해당 없음 ⑦ 해당 없음 ⑧ 권한 레이어가 바뀌어도 Helm 의미는 유지

- 맥락: Tailscale은 Windows 호스트에만 있고, homelab 서비스는 127.0.0.1 바인딩 + Windows `tailscale serve`로 공개한다(브리프 §2.5).
- 결정: 데몬은 WSL 안 127.0.0.1에만 바인딩하고 Windows 호스트의 `tailscale serve`가 HTTPS/WSS를 붙인다. 인증은 Tailscale 신원 헤더 + 기기별 bearer 토큰. Funnel은 쓰지 않는다.
- 근거: homelab과 같은 방식이라 운영 부담이 작다. 데몬이 TLS·인증서를 다루지 않는다.
- 기각한 대안: WSL 안에 Tailscale 설치(homelab 기각안 "서비스별 사이드카"), Tailscale IP 직접 바인딩(Paseo 방식, 신원 헤더 없음 [원문 `pi-cases-notes.md` §12.2-9]), 데몬이 `tailscale serve`를 직접 실행(OpenClaw 방식, 같은 절), Cloudflare Tunnel 공개, E2E relay.
- 결과: 같은 호스트의 프로세스가 신원 헤더를 위조할 수 있으므로 헤더는 보조 신호이고 기기 토큰이 필수다(06 §3.8.2, §3.7.4). serve 설정은 homelab `serve.table`에서 사람이 관리한다. 같은 구성을 쓰는 사례는 OpenClaw(serve + 헤더 whois 대조 + 기기 토큰)뿐이다 [원문 `pi-cases-notes.md` §13.4].
- 평가: ① A6(사람 권한 보호) ② 해당 없음 ③ 데몬 경계 ④ 기기 등록·폐기 기록 ⑤ 외부에서 상황 확인 ⑥ 해당 없음 ⑦ serve가 멈추면 SSH 경로(ADR-00-38) ⑧ 유지
- 관련 문서: 17, 18, 06 §3.8

#### ADR-00-30 크래시 복구: 실행 의도 → 실행 → 결과, 중단됨 정리

- 상태: 제안(조정자 기본값) · 날짜: 2026-10-11 · 결정자: 조정자 · 출처: 브리프 결정 30, pi-facts-1 §0-8, backend-oss §1.2
- 맥락: pi-durable 명세 5.2(effect sandwich), OpenCode v2 write-ahead claim. 사례 세 곳(happy-agent, pi-fabric, openclaw)이 "결과 없는 도구 호출을 다시 실행하지 않는다"를 공통으로 쓴다 [원문 `pi-cases-notes.md` §1-2]. 재시작 후 진행 중 턴을 이어 실행하는 사례에는 OpenCode v2, Codex, pi-durable 외에 happy-agent와 openclaw도 있다 [원문 `pi-cases-notes.md` §13.1].
- 결정: 실행 의도 → 실행 → 결과 순으로 기록하고, 재시작 시 중단된 도구 호출을 "중단됨"으로 정리한다. 다시 실행해도 안전한 도구만 재실행한다.
- 근거: "복구는 DB의 성질이지 종료 훅의 성질이 아니다"(OpenCode v2 주석, backend-oss §1.2).
- 기각한 대안: 종료 훅에만 기대는 복구, 메시지 단위 체크포인트만(Absurd 패턴, 도구 실행 중 크래시를 구분 못 함 [원문 `pi-cases-notes.md` §13.2]).
- 결과: 시작 순서에 복구 단계가 리스너보다 먼저 온다(06 §3.6.6). 데몬 세대(epoch)로 이전 세대의 "실행 중" 상태를 정리한다. 재실행 판정은 "의도 기록 시점 선언 safe AND 현재 선언 safe"를 12가 검토한다 [원문 `pi-cases-notes.md` §12.1-1].
- 평가: ① A14 ② M ③ 정본(실행 기록) ④ 실행 의도·결과·중단됨 이벤트 ⑤ 중단 사실을 보인다 ⑥ 해당 없음 ⑦ 이 결정이 복구 그 자체 ⑧ 유지
- 관련 문서: 12, 13, 17, 06 §3.6.6

#### ADR-00-31 클라이언트 프로토콜: JSON-RPC 2.0 over WebSocket, seq, `lastSeq` 재전송

- 상태: 제안(조정자 기본값) · 날짜: 2026-10-11 · 결정자: 조정자 · 출처: 브리프 결정 31, backend-oss §3
- 맥락: 표준 프로토콜(ACP, AG-UI, MCP)과 pi-protocol은 끊긴 동안의 이벤트를 다시 보내지 않는다(backend-oss §0-4, pi-facts-2 §0-2). 사례 8곳에도 데몬 재시작을 넘는 네트워크 재전송 구현은 없다 [원문 `pi-cases-notes.md` §13.4].
- 결정: JSON-RPC 2.0 over WebSocket. 이벤트에 단조 증가 seq를 붙이고 재접속 시 `lastSeq`부터 다시 보낸다. 큰 데이터는 HTTP.

- 결과: 재전송은 SQLite seq로 새로 설계한다. 사례에서 가져올 것은 재접속 순서·스냅숏 경계·세대 감지다 [원문 `pi-cases-notes.md` §12.1-5]. 두 접속 경로에서 의미가 같아야 한다(ADR-00-38, ADR-06-13). 스트리밍 델타는 seq 없는 휘발 알림이다(06 §3.6.5).
- 평가: ① A11, A12 ② 해당 없음 ③ 클라이언트 계약 ④ seq 체계 ⑤ 끊겨도 놓치지 않는다 ⑥ 해당 없음 ⑦ 재접속 재전송 ⑧ 유지
- 관련 문서: 19, 06 §3.7

### ADR-06-01 토폴로지: 배치 C의 구조, 1차 구현은 데몬 내장 런타임

- 맥락: 대화 [156]~[157]의 배치 A(서버가 런타임을 품음), B(pi가 Helm을 품음), C(데몬이 상태, 런타임은 붙었다 떨어짐)가 감사에서 "빠진 덩어리"로 지적됐다(audit §1.3). 결정 22·23·34가 이후에 나왔다.

### ADR-06-02 프로세스 구성: 단일 데몬·단일 writer, 도구는 자식 프로세스, 관찰 에이전트는 일회성 별도 프로세스

- 맥락: pi-durable은 저장소 하나에 프로세스 하나라 관찰 에이전트를 같은 프로세스 task로 두게 했다(v0.3 12 §2 원칙 2). 대화의 관찰 에이전트 C는 런타임 밖 별도 프로세스였다(extracts-1 E1-073). 서버 메모리 예산이 크지 않다(WSL 상한 10 GB).
- 결정: `helmd` 한 프로세스가 정본에 쓰는 유일한 프로세스다. 쓰기는 동기 `engine.submit`·`transact`로 직렬화한다. 도구는 자식 프로세스, codemode와 무거운 읽기 작업은 워커 스레드. 관찰 에이전트는 데몬 감독기가 `fork`로 띄우는 일회성 자식 프로세스이고, DB는 읽기 전용 리더로 읽고 제출·모델 호출은 Node IPC로 데몬에 맡긴다(16 OB-1, §3.2). 단일 writer 잠금은 별도 SQLite 잠금 파일의 쓰기 트랜잭션을 프로세스 수명 동안 유지하는 방식이다(17 D17-02).
- 근거: 1인용이라 쓰기 직렬화로 충분하다. 잠금 파일 방식은 프로세스가 죽으면 운영체제가 푼다(happy-agent, pi-fabric [원문 `pi-cases-notes.md` §12.1-4]). 관찰 에이전트를 분리하면 작업 세션을 건드리지 않고(extracts-1 E1-073), 일회성이면 상주 메모리를 쓰지 않는다.
- 기각한 대안: 세션별 worker 프로세스(pi 실험 서버, openclaw의 writer claim·admission 복잡도 [원문 S4/openclaw-runtime §5 피할 것 1]), 관찰 에이전트 상주, 관찰 에이전트를 데몬 안 task로(쓰기 권한 분리를 import 규칙으로만 지켜야 함), pid 파일 잠금.
- 결과: 트랜잭션 안 I/O 금지(06 §3.6.5). 관찰 에이전트의 쓰기 권한 없음은 프로세스 경계(읽기 전용 리더)와 IPC 채널에서 데몬이 행위자를 `agent:observer`로 고정하는 것으로 지킨다. 관찰 프로세스는 비밀을 갖지 않는다. 16의 ADR 후보 OBS-ADR-1과 같은 내용이다.
- 평가: ① A6, A14 ② 전부 ③ 배치 ④ 해당 없음 ⑤ 해당 없음 ⑥ 해당 없음 ⑦ 잠금이 자동으로 풀린다 ⑧ 해당 없음
- 관련 문서: 06 §3.6.3~§3.6.6, 16, 17

### ADR-06-03 패키지 경계: 브리프 목록 + `engine`, `testkit`

- 맥락: 브리프 §3.1 목록에는 상태 변경 트랜잭션 조율(단일 변경 경로)과 공용 시험 도우미의 자리가 없다. 클라이언트 쪽 재접속 로직의 자리도 정해야 했다.
- 결정: `@helm/engine`(단일 변경 경로, 이벤트·실행 기록 append 유일 위치)과 `@helm/testkit`(개발 전용 범용 도우미, `domain`에만 의존)을 더한다. 클라이언트 코어는 별도 패키지 대신 `@helm/protocol/client` 하위 경로에 둔다(19 결정을 받음). 런타임 어댑터 계약은 `@helm/runtime/adapter`, 관찰 에이전트의 순수 지표 함수와 IPC 타입은 `@helm/observer/metrics`·`ipc`(16), vendor는 `@helm/vendor-pi-agent-core`·`@helm/vendor-pi-tools`(07). `store`는 `read`·`write`·`admin` 하위 경로로 쓰기 API를 나눈다.
- 근거: 상태 변경 입력이 다섯 곳(사람, 모델, 도구, 타이머, 관찰자)에서 오므로 한 패키지가 트랜잭션을 맡아야 "append는 여기서만"을 import 규칙으로 지킬 수 있다. 클라이언트 세 종류는 한 벌의 코어를 쓴다(OpenClaw의 중복 구현을 피함 [원문 S4/openclaw-gateway §4 피할 것 1]).
- 기각한 대안: 조율을 `store`에(저장소가 커널을 알게 됨), `runtime`에(데몬 처리기 경로가 런타임 전체에 의존), `daemon`에(런타임 훅이 데몬에 의존하는 역방향). 별도 `@helm/client` 패키지(06 1차 초안. 19가 `protocol/client`로 정해 목적이 같으므로 접음). `@helm/config`, `@helm/scheduler`, `@helm/adapter-contract` 별도 패키지(지금은 이득이 적음). `testkit`이 위 레이어에 의존하는 안(프로젝트 참조 순환).
- 결과: 06 §3.4.1 의존 허용 표가 원본이 되고 `scripts/architecture-rules.ts`로 옮긴다.
- 평가: ① A6, A11(투영이 정본을 쓰지 않음) ② 전부 ③ 구조 ④ 해당 없음 ⑤ 해당 없음 ⑥ 해당 없음 ⑦ 해당 없음 ⑧ 런타임을 바꿔도 `engine` 이하가 유지
- 관련 문서: 06 §3.3, §3.4

### ADR-06-08 TypeScript 6.0

### ADR-06-09 SQLite 드라이버 better-sqlite3 유지

- 평가: ① 해당 없음 ② 해당 없음 ③ 정본 저장 기술 ④ 해당 없음 ⑤ 해당 없음 ⑥ 해당 없음 ⑦ 온라인 백업 ⑧ 드라이버 교체 범위를 한 파일로

### ADR-06-10 런타임 능력 목록 통합과 등급 파생

- 맥락: 원전 능력 목록이 문서판 키 8개와 실행 후보 Level 4개 × `enforced/advisory/unavailable` 두 판이고 Level 이름도 두 판이다(canon-2 §1.15, §4.3). 대화의 내부 루프 계약 능력 5개(extracts-3 X3-8-21)도 있다. canon-2 §11의 ADR 후보 "Level 정의 통일"이다.
- 결정: 능력 키 각각에 보장 수준(`enforced | detected | advisory | unavailable`, 13 §2와 같음)을 적는 한 판으로 합치고, Level A~D는 저장하지 않고 키에서 계산해 화면에만 쓴다. 키 목록은 06 §3.13.4 초안을 13이 확정한다.
- 근거: Level 하나로는 어떤 능력이 빠졌는지 알 수 없고, 보장 수준 낮추기 규칙은 능력 단위로 정해진다(X3-8-22).
- 기각한 대안: 문서판만, Level만.
- 결과: `enforced`와 `advisory`를 화면과 감사 기록에서 구분한다(canon-2 §1.20). client contract와 adapter protocol은 각자 적합성 시험을 둔다(C8).
- 평가: ① A7, A12 ② M ③ 어댑터 ④ 능력 목록 제출 기록 ⑤ 낮아진 보장을 보인다 ⑥ 해당 없음 ⑦ 해당 없음 ⑧ 이 결정의 목적
- 관련 문서: 06 §3.13.4, 13

### ADR-06-11 설정: dotfiles의 TOML, 데몬은 읽기만, 의미 설정은 이벤트

- 맥락: 사용자 규칙 "앱 설정은 dotfiles에 둔다". 다이얼·모드·정책은 Helm 의미(P 평면)다.
- 결정: 운영 설정만 `~/.config/helm/helmd.toml`(dotfiles 관리) + `helmd.local.toml`(미추적)에 TOML로 둔다. 우선순위는 기본값 < 파일 < 로컬 < 지정한 환경 변수(17 목록) < 인자. 최상위 구조는 06, 절 내용은 소유 문서(운영 절은 17). 데몬은 설정 파일에 쓰지 않는다. 의미 설정은 도메인 이벤트로 정본에 기록한다. 설정에는 비밀이 없다. `SIGHUP`으로 일부 절만 다시 읽는다.
- 근거: 운영 설정과 Helm 의미를 섞으면 "화면에서 바꾼 다이얼"이 파일과 DB 두 곳에 생긴다.
- 기각한 대안: JSON(주석을 쓸 수 없다. 17 초안이 `helmd.json`을 적었으나 형식은 06을 따른다고 했으므로 17에 이름 변경을 요구), JSONC(표준 파서가 없다), YAML(파서가 크다), DB에 운영 설정(데몬이 뜨기 전에 필요한 값이 있다).
- 결과: 06 §3.10의 스키마·핫 리로드 표. 모르는 키는 오류.
- 평가: ① A15(다이얼 변경은 이벤트) ② P ③ 정본 밖(운영) ④ 의미 설정 변경 이벤트 ⑤ 해당 없음 ⑥ 해당 없음 ⑦ dotfiles 저장소 ⑧ 해당 없음
- 관련 문서: 06 §3.10, 14

### ADR-06-12 로깅: pino → journald, 관측 흐름 4개 분리, 내용 미기록

- 맥락: 원전은 도메인 원장, 운영 로그, 실험 측정, 원시 trace를 섞지 말라고 한다(canon-2 §1.22). homelab은 systemd + journald를 쓴다.
- 결정: 운영 로그는 pino JSON 줄을 stdout → journald로. L0~L3은 주입된 `Logger` 인터페이스만 쓰고 `kernel`은 로그를 남기지 않는다. 비밀과 도메인 내용은 로그에 넣지 않고 ID·크기·해시만 남긴다. 진단 span(pi-telemetry)은 기본 noop.
- 근거: 로그에 프롬프트·출력이 들어가면 비밀이 새고 정본과 중복된다.
- 기각한 대안: 파일 로그와 회전, 로그를 SQLite에, OTLP 내보내기.
- 결과: 진단 명령 목록(06 §3.11.4).
- 평가: ① A14(실패 신호는 운영 로그와 도메인 거부 기록으로 나뉜다) ② 해당 없음 ③ 정본 밖 ④ 해당 없음 ⑤ 해당 없음 ⑥ 해당 없음 ⑦ journald 보존 ⑧ 해당 없음
- 관련 문서: 06 §3.11, 17

### ADR-06-13 연결 처리 3층과 "리스너는 출발지 주소를 신뢰 근거로 쓰지 않는다"

- 맥락: 결정 38은 두 접속 경로에서 같은 의미를 요구한다. 도구 자식 프로세스는 데몬과 같은 OS 사용자로 돌아 소켓·로컬 포트에 접속할 수 있다. serve 뒤의 데몬에는 원격 요청도 127.0.0.1에서 온다.
- 결정: 연결 처리를 리스너(`tailnet` 7840, `loopback` 7841, `local` `rpc.sock`, 17 D17-09) · 인증층(hello에서 판정, 19 P-03) · 프로토콜층(한 벌의 처리기)으로 나눈다. 리스너는 출발지 주소(127.0.0.1)를 신뢰 근거로 쓰지 않는다. TCP 리스너는 기기 토큰이 필수다. 소켓 파일 권한에 기댄 로컬 관리자 주체는 `local`에서만 받고, 그 조건으로 도구 실행 격리가 소켓·데이터·설정 디렉터리를 가린다(방식은 13·18).
- 근거: pi-server의 "인증은 리스너 몫" 경계(pi-facts-2 §0-3), OpenClaw의 loopback 자동 승인 위험(pi-cases-notes §12.2-8). 결과 확인은 사람만(결정 15)을 도구 경로로 우회하지 못하게 한다.
- 기각한 대안: 격리 없이 로컬 소켓 연결을 소유자로 신뢰, 리스너마다 다른 처리기, SSH 경로용 별도 프레임 형식(06 1차 초안의 stdio 프레임. 19 P-02로 접음).
- 결과: 같은 대본을 세 리스너에서 돌리는 동등성 시험(06 §6 S5·S6). 격리를 못 쓰는 환경은 `advisory`로 표시하고, 그때 로컬 관리자 주체를 어떻게 할지는 18이 정한다(06 §7 O-10).
- 평가: ① A6, A10 ② A ③ 데몬 경계 ④ 기기·자격 증명 기록 ⑤ 해당 없음 ⑥ 해당 없음 ⑦ 해당 없음 ⑧ 해당 없음
- 관련 문서: 06 §3.7.2, §3.7.4, 18, 19

### ADR-06-14 이전 구현(`@helmdocs/*`, Docs-Agent OS)을 `legacy/`로

- 평가: ① 해당 없음 ② 해당 없음 ③ 저장소 정리 ④ 해당 없음 ⑤ 해당 없음 ⑥ 해당 없음 ⑦ Git 이력 ⑧ 해당 없음

### ADR-06-15 빌드: `tsc -b`, 번들러 없음, `source` 조건

- 맥락: Node 패키지 빌드 방식과 개발 실행 방식을 정해야 한다. pi 저장소는 패키지마다 `tsc`, 번들러 없음, `source` 조건을 쓴다.
- 결정: Node 패키지는 `tsc -b`로 `dist/`에 내보내고 운영 데몬은 `dist`에서 실행한다. `exports`에 `source`(src) / `default`(dist) 조건을 둔다. 개발과 테스트는 `source` 조건으로 소스를 바로 읽는다. 데스크톱만 Vite.
- 근거: 단일 서버 배포라 번들이 필요 없다. pi와 같은 방식이면 vendor 코드와 섞기 쉽다.
- 기각한 대안: esbuild·tsdown 번들, tsx 같은 실행기 의존.
- 결과: 소스 직접 실행이 워크스페이스 패키지에서 되는지 구현 첫 단계에서 확인한다(06 §3.12.4 [가정], §6 S1).
- 평가: 해당 없음(도구)
- 관련 문서: 06 §3.12.4

### ADR-06-16 린트·형식: ESLint + typescript-eslint + Prettier

- 맥락: pi 저장소는 Biome을 쓴다. 사용자 템플릿 `node.just`의 `check`·`lint`는 ESLint를 전제한다. 의존 규칙 일부(R4~R7, R9)를 패키지별 금지 import·전역·구문 규칙으로 검사해야 한다.

- 근거: 템플릿 레시피를 고치지 않고 쓴다. 패키지별 `no-restricted-*` 규칙과 타입 정보 규칙을 쓸 수 있다.

- 결과: TypeScript 버전 상한이 typescript-eslint 지원 범위에 묶인다(ADR-06-08).
- 평가: 해당 없음(도구)
- 관련 문서: 06 §3.5.3, §3.12.1

## 8. 다른 문서에서 올라온 ADR 후보

이 절은 비워 둔다. 조정자가 2단계에서 각 문서 끝 "ADR 후보" 절의 항목을 옮긴다.

옮기는 규칙:

1. 번호는 `ADR-SS-NN`이다(§2.1). `SS`는 후보가 나온 문서 번호, `NN`은 그 문서 안에서 01부터 차례로 붙인다. 같은 문서의 후보가 나중에 더 오면 이어서 붙인다.
2. 브리프 결정과 같은 내용을 다시 정한 후보는 새 번호를 만들지 않고 해당 `ADR-00-xx`의 "결과"에 덧붙인다. 브리프 결정을 바꾸는 후보는 새 번호로 만들고 `ADR-00-xx`의 상태를 "대체됨 → …"으로 고친다([결정] 항목은 사용자 확인이 있어야 바꾼다).
3. 06의 ADR(ADR-06-xx)과 충돌하는 후보는 06 소유자(P3)와 조정자가 함께 정리하고, 바뀌면 옛 ADR을 "대체됨"으로 표시한다.
4. §7 예정 목록에 있던 항목이면 그 행을 지우지 않고 "→ ADR-SS-NN"을 덧붙인다.
5. 양식은 §2.3을 따른다. 평가 8개 중 답할 수 없는 것은 "해당 없음"으로 적는다.
6. §3 색인 표에 행을 더한다.
