# 24. 아키텍처 결정 기록 (ADR)

- 작성: P3 아키텍트, 2026-10-11 (1단계 초안), 2026-10-12 (2a단계: 결정 41~46, 다른 문서 ADR 후보 옮기기; 4단계: 결정 47~51, 판정 J-119~J-151, 26 후보; 2026-10-14: 결정 52~57, 판정 J-155~J-190). 다른 문서의 에이전트는 자기 문서 끝 "ADR 후보" 절에 적고, 이 파일은 P3만 고친다(§2.4 3번).
- 상태: 설계 초안 3판. 기준은 브리프 결정 1~57과 판정 J-01~J-240이다.
- 함께 읽을 문서: `process/00-design-brief.md`(이하 "브리프"), [06 시스템 아키텍처](06-system-architecture.md)
- 표시 규칙: 브리프 §5.2(판정 J-144). ADR 상태 "결정"은 사용자가 정한 것에만 쓴다. 조정자 기본값(브리프 결정 26~37 가운데 사용자가 따로 확인하지 않은 것)은 "제안(결정 n 기본값)", 조정자 판정은 "제안(판정 n)" 또는 "채택(판정 J-nn)"으로 적는다. 외부 사실의 확인 수준과 출처 줄임말은 06 머리말과 같다.
- 문서 구성: 이 문서는 브리프 §5.3 여덟 절 대신 ADR 문서의 구성을 쓴다(판정 J-151). 대응은 §1.1 표에 있다.

## 1. 목적과 범위

- 이 문서는 Helm 설계의 결정과 그 이유, 버린 대안을 한곳에 모은다. 대화 [157]에서 "각 결정은 결정 기록(ADR) 형식으로 남긴다"고 정했다(extracts-4 18-3, 대화 L4396).
- 다루는 것: 브리프 §2의 구조 결정(19~24, 26~57)과 원전을 바꾼 이론 결정 중 구조에 영향을 주는 것(2, 3, 5, 18), 원전의 이전 결정(D1~D3), 06이 내린 결정과 06이 반영한 판정(ADR-06-01~21), 다른 문서에서 옮긴 ADR(§8), 아직 정하지 않은 ADR 예정 목록(§7).
- 다루지 않는 것: 결정의 세부 명세. ADR은 결정과 이유만 적고, 명세는 "관련 문서"의 절을 참조한다.

## 2. 형식과 번호 규칙

### 2.1 번호

`ADR-SS-NN`

- `SS`: 결정이 나온 문서 번호 두 자리. `00`은 설계 브리프, `06`은 시스템 아키텍처, 그 밖은 해당 설계 문서 번호(`07`, `09`, …, `25`). 원전(v0.1·v0.2)의 이전 결정은 `P0`을 쓴다(`ADR-P0-D1`).
- `NN`: 그 문서 안의 순번 두 자리. **브리프 결정은 결정 번호와 같게 둔다**(예: 브리프 결정 26 = `ADR-00-26`). 그래서 브리프 번호로 바로 찾을 수 있다.
- 한 번 쓴 번호는 다시 쓰지 않는다. 결정이 바뀌면 새 번호를 쓰고 옛 ADR의 상태를 "대체됨"으로 바꾼다.

### 2.2 상태 값

| 상태 | 뜻 |
|---|---|
| 결정 | 제품 소유자가 정했다(브리프 §2의 [결정] 항목, 또는 이후 사용자 확인) |
| 제안 | 조정자나 설계 에이전트가 정했고, 바꾸려면 근거와 함께 이 문서를 고친다(브리프 §2.3) |
| 후보 | 아직 정하지 않았다. 소유 문서가 정한다 |
| 채택(판정 J-xx) / 채택 → ADR-x | 다른 문서의 제안을 조정자 판정이 확정했다. "→ ADR-x"는 그 판정을 적은 ADR |
| 대체됨 → ADR-x | 다른 ADR로 바뀌었다. 내용은 지우지 않는다 |
| 합침 → ADR-x | 같은 내용의 다른 ADR이 정본이다. 번호는 남기고 내용은 그 ADR을 본다(§8.1) |
| 다시 확인 | 원 문서가 개정 중이거나 상위 결정과 어긋나 소유 문서가 다시 낸다 |
| 폐기 | 이유와 함께 버렸다 |

### 2.3 양식

모든 ADR은 아래 항목을 가진다. "평가"는 원전의 아키텍처 결정 평가 질문 8개(canon §13.14, F07 §14)에 짧게 답한 것이다: ① 어느 공리에서 필요한가 ② N/E/M 중 어떤 상태를 다루는가 ③ 정본인가 투영인가 어댑터인가 ④ 어떤 이벤트와 불변조건이 필요한가 ⑤ 사람의 상황 인식과 방향 수정 능력을 높이는가 ⑥ 사용자의 주의력을 어디서 아끼고 어디에 쓰게 하는가 ⑦ 실패했을 때 원본 근거와 상태를 복구할 수 있는가 ⑧ 특정 모델·도구 없이도 의미가 유지되는가. 해당이 없으면 "해당 없음"이라고 적는다.

```markdown
### ADR-SS-NN 제목
- 상태: … · 날짜: YYYY-MM-DD · 결정자: … · 출처: …
- 맥락: 무엇을 정해야 했고 무엇이 제약이었나
- 결정: 정한 것 (한두 문장)
- 근거: 왜
- 기각한 대안: 대안과 버린 이유
- 결과: 이 결정으로 지켜야 할 것, 생기는 비용과 위험
- 평가: ①… ②… ③… ④… ⑤… ⑥… ⑦… ⑧…
- 관련 문서: 파일 이름과 절
```

### 2.4 고치는 규칙

1. 결정의 내용을 바꾸면 새 ADR을 만들고 옛 ADR을 "대체됨"으로 표시한다. 오탈자나 참조 절 번호 수정은 제자리에서 고친다.
2. [결정] ADR(제품 소유자 결정)은 설계 에이전트가 바꾸지 않는다. 이의는 최종 보고의 "브리프에 대한 이의"로 올린다(브리프 머리말).
3. 다른 문서의 에이전트는 이 파일을 직접 고치지 않는다. 자기 문서 끝 "ADR 후보" 절에 적고, P3가 조정자 지시에 따라 §8로 옮긴다(§8 규칙).

#### ADR-00-26 원격 접속: Windows 호스트 Tailscale serve + 127.0.0.1 + 신원 헤더·기기 토큰

- 상태: 제안(결정 26 기본값) · 날짜: 2026-10-11 · 결정자: 조정자 · 출처: 브리프 결정 26, `docs/v0.3/audit/backend-oss-research.md` §5
- 맥락: Tailscale은 Windows 호스트에만 있고, homelab 서비스는 127.0.0.1 바인딩 + Windows `tailscale serve`로 공개한다(브리프 §2.5).
- 결정: 데몬은 WSL 안 127.0.0.1에만 바인딩하고 Windows 호스트의 `tailscale serve`가 HTTPS/WSS를 붙인다. 인증은 Tailscale 신원 헤더 + 기기별 bearer 토큰. Funnel은 쓰지 않는다.
- 근거: homelab과 같은 방식이라 운영 부담이 작다. 데몬이 TLS·인증서를 다루지 않는다.
- 기각한 대안: WSL 안에 Tailscale 설치(homelab 기각안 "서비스별 사이드카"), Tailscale IP 직접 바인딩(Paseo 방식, 신원 헤더 없음 [원문 `pi-cases-notes.md` §12.2-9]), 데몬이 `tailscale serve`를 직접 실행(OpenClaw 방식, 같은 절), Cloudflare Tunnel 공개, E2E relay.
- 결과: 같은 호스트의 프로세스가 신원 헤더를 위조할 수 있으므로 헤더는 보조 신호이고 기기 토큰이 필수다(06 §3.8.2, §3.7.4, ADR-18-01). 127.0.0.1 바인딩은 격리 경계가 아니다(ADR-00-46). serve 설정은 homelab `serve.table`에서 사람이 관리한다. 같은 구성을 쓰는 사례는 OpenClaw(serve + 헤더 whois 대조 + 기기 토큰)뿐이다 [원문 `pi-cases-notes.md` §13.4].
- 평가: ① A6(사람 권한 보호) ② 해당 없음 ③ 데몬 경계 ④ 기기 등록·폐기 기록 ⑤ 외부에서 상황 확인 ⑥ 해당 없음 ⑦ serve가 멈추면 SSH 경로(ADR-00-38) ⑧ 유지
- 관련 문서: 17, 18, 06 §3.8

#### ADR-00-28 에이전트 루프: pi-agent-core 포크, 커널 검사는 루프 훅

- 맥락: 원전 experimental.v0는 JSONL 원장이었다(canon §20.3 #4). pi 세션 파일과 Helm 기록을 따로 쓰면 한쪽만 기록되는 경우가 생긴다(v0.3 14 §3.1). 사례 8곳 모두 클라이언트용 이벤트 seq를 메모리에만 두었다 [원문 `pi-cases-notes.md` §1-1, §12.2-1].
- 결정: 모든 상태는 Helm 이벤트 로그(SQLite, WAL, WSL ext4, `/srv/volumes/helm/data/helm.sqlite`)에서 재구성 가능해야 한다. pi 세션 파일이나 pi-durable 저장소를 기준 원본으로 쓰지 않는다.
- 근거: 기준 원본이 하나일 때 공리가 런타임 종류와 무관하게 성립한다(v0.3 14 §1). seq를 SQLite에 두면 데몬 재시작 뒤에도 `lastSeq` 재전송이 이어진다.
- 기각한 대안: JSONL 원장, pi-durable 저장소, pi 세션 JSONL과 이중 기록.
- 결과: DB 하나·전역 seq(ADR-06-05), JSONL은 내보내기 전용(ADR-06-06), 쓰기는 `engine`만(ADR-06-04). 투영은 쓰기 트랜잭션 안에서 갱신하고 outbox를 두지 않는다(ADR-09-04). 대화 기록과 도구 입출력도 이벤트 로그와 blob에 둔다(ADR-09-07). 이벤트 이름에는 평면 접두사를 쓰지 않는다. 평면은 envelope의 `plane`과 카탈로그 메타에 둔다(ADR-09-09).
- 평가: ① A11, A13, A14 ② 전부 ③ 정본 ④ 모든 이벤트 ⑤ 해당 없음 ⑥ 해당 없음 ⑦ 로그 재생, 해시 체인, 스냅숏 ⑧ DB 파일만으로 읽기·내보내기
- 관련 문서: 09, 06 §3.9

#### ADR-00-30 크래시 복구: 실행 의도 → 실행 → 결과, 중단됨 정리

- 상태: 제안(결정 30 기본값) · 날짜: 2026-10-11 · 결정자: 조정자 · 출처: 브리프 결정 30, pi-facts-1 §0-8, backend-oss §1.2
- 맥락: pi-durable 명세 5.2(effect sandwich), OpenCode v2 write-ahead claim. 사례 세 곳(happy-agent, pi-fabric, openclaw)이 "결과 없는 도구 호출을 다시 실행하지 않는다"를 공통으로 쓴다 [원문 `pi-cases-notes.md` §1-2]. 재시작 후 진행 중 턴을 이어 실행하는 사례에는 OpenCode v2, Codex, pi-durable 외에 happy-agent와 openclaw도 있다 [원문 `pi-cases-notes.md` §13.1].
- 결정: 실행 의도 → 실행 → 결과 순으로 기록하고, 재시작 시 중단된 도구 호출을 "중단됨"으로 정리한다. 다시 실행해도 안전한 도구만 재실행한다.
- 근거: "복구는 DB의 성질이지 종료 훅의 성질이 아니다"(OpenCode v2 주석, backend-oss §1.2).
- 기각한 대안: 종료 훅에만 기대는 복구, 메시지 단위 체크포인트만(Absurd 패턴, 도구 실행 중 크래시를 구분 못 함 [원문 `pi-cases-notes.md` §13.2]).
- 결과: 시작 순서에 복구 단계가 리스너보다 먼저 온다(06 §3.6.6). 데몬 세대(epoch)로 이전 세대의 "실행 중" 상태를 정리한다. 재실행 판정은 "의도 기록 시점 선언 safe AND 현재 선언 safe"로 12가 정했다(ADR-12-02) [원문 `pi-cases-notes.md` §12.1-1]. 실행 소유권 펜싱은 ADR-12-04, 단일 쓰기는 ADR-09-06.
- 평가: ① A14 ② M ③ 정본(실행 기록) ④ 실행 의도·결과·중단됨 이벤트 ⑤ 중단 사실을 보인다 ⑥ 해당 없음 ⑦ 이 결정이 복구 그 자체 ⑧ 유지
- 관련 문서: 12, 13, 17, 06 §3.6.6

#### ADR-00-31 클라이언트 프로토콜: JSON-RPC 2.0 over WebSocket, seq, `lastSeq` 재전송

- 상태: 제안(결정 31 기본값) · 날짜: 2026-10-11 · 결정자: 조정자 · 출처: 브리프 결정 31, backend-oss §3
- 맥락: 표준 프로토콜(ACP, AG-UI, MCP)과 pi-protocol은 끊긴 동안의 이벤트를 다시 보내지 않는다(backend-oss §0-4, pi-facts-2 §0-2). 사례 8곳에도 데몬 재시작을 넘는 네트워크 재전송 구현은 없다 [원문 `pi-cases-notes.md` §13.4].
- 결정: JSON-RPC 2.0 over WebSocket. 이벤트에 단조 증가 seq를 붙이고 재접속 시 `lastSeq`부터 다시 보낸다. 큰 데이터는 HTTP.
- 근거: 데몬 이벤트 로그의 seq를 그대로 쓰면 재접속 처리가 단순하다.
- 기각한 대안: pi-protocol + pi-server(CBOR, 인증 없음, 재전송 없음, experimental, pi-facts-2 §12.3), HTTP + SSE(experimental.v0), AssistantTransport(sync server가 enterprise 전용).
- 결과: 재전송은 SQLite seq로 새로 설계한다. 사례에서 가져올 것은 재접속 순서·스냅숏 경계·세대 감지다 [원문 `pi-cases-notes.md` §12.1-5]. 두 접속 경로에서 의미가 같아야 한다(ADR-00-38, ADR-06-13). 스트리밍 델타는 seq 없는 휘발 알림이다(06 §3.6.5, ADR-19-05). 세부: 재개 위치 `{storeId, seq}`와 `(from, to]` 구간(ADR-19-03), 뷰 무효화(ADR-19-04), 명령의 멱등 키와 `basisSeq`(ADR-19-06), 파일 경로(ADR-19-07), 버전(ADR-19-08).
- 평가: ① A11, A12 ② 해당 없음 ③ 클라이언트 계약 ④ seq 체계 ⑤ 끊겨도 놓치지 않는다 ⑥ 해당 없음 ⑦ 재접속 재전송 ⑧ 유지
- 관련 문서: 19, 06 §3.7

### ADR-06-01 토폴로지: 배치 C의 구조, 1차 구현은 데몬 내장 런타임

### ADR-06-02 프로세스 구성: 단일 데몬·단일 writer, 도구는 자식 프로세스, 관찰 에이전트는 일회성 별도 프로세스

- 맥락: pi-durable은 저장소 하나에 프로세스 하나라 관찰 에이전트를 같은 프로세스 task로 두게 했다(v0.3 12 §2 원칙 2). 대화의 관찰 에이전트 C는 런타임 밖 별도 프로세스였다(extracts-1 E1-073). 서버 메모리 예산이 크지 않다(WSL 상한 10 GB).
- 결정: `helmd` 한 프로세스가 정본에 쓰는 유일한 프로세스다. 쓰기는 동기 `engine.submit`·`transact`로 직렬화한다. 도구는 자식 프로세스, codemode와 무거운 읽기 작업은 워커 스레드. 관찰 에이전트는 데몬 감독기가 `fork`로 띄우는 일회성 자식 프로세스이고, DB는 읽기 전용 리더로 읽고 제출·모델 호출은 Node IPC로 데몬에 맡긴다(16 OB-1, §3.2). 단일 writer 잠금은 별도 SQLite 잠금 파일의 쓰기 트랜잭션을 프로세스 수명 동안 유지하는 방식이다(17 D17-02).
- 근거: 1인용이라 쓰기 직렬화로 충분하다. 잠금 파일 방식은 프로세스가 죽으면 운영체제가 푼다(happy-agent, pi-fabric [원문 `pi-cases-notes.md` §12.1-4]). 관찰 에이전트를 분리하면 작업 세션을 건드리지 않고(extracts-1 E1-073), 일회성이면 상주 메모리를 쓰지 않는다.
- 기각한 대안: 세션별 worker 프로세스(pi 실험 서버, openclaw의 writer claim·admission 복잡도 [원문 S4/openclaw-runtime §5 피할 것 1]), 관찰 에이전트 상주, 관찰 에이전트를 데몬 안 task로(쓰기 권한 분리를 import 규칙으로만 지켜야 함), pid 파일 잠금.
- 결과: 트랜잭션 안 I/O 금지(06 §3.6.5). 관찰 에이전트의 쓰기 권한 없음은 프로세스 경계(읽기 전용 리더)와 IPC 채널에서 데몬이 행위자를 `agent:observer`, 채널을 `aux_agent`로 고정하는 것으로 지킨다. 관찰 프로세스는 비밀을 갖지 않고 클라이언트 프로토콜을 쓰지 않는다(판정 §2). 16의 ADR 후보 OBS-ADR-1(ADR-16-01)을 이 ADR에 합쳤다. 16이 더한 것: 격리 실행을 켤 때는 `systemd-run --user --pipe --wait` 일회성 단위로 띄운다. 단일 writer 잠금의 세부는 ADR-09-06(17 ADR 후보 2를 합침). 자원 요구(대기 CPU 2% 이하, RSS 1 GB 이하, 01 NFR-C-4)는 06 §3.6.3.
- 평가: ① A6, A14 ② 전부 ③ 배치 ④ 해당 없음 ⑤ 해당 없음 ⑥ 해당 없음 ⑦ 잠금이 자동으로 풀린다 ⑧ 해당 없음
- 관련 문서: 06 §3.6.3~§3.6.6, 16, 17

### ADR-06-13 연결 처리 3층과 "리스너는 출발지 주소를 신뢰 근거로 쓰지 않는다"

- 맥락: 결정 38은 두 접속 경로에서 같은 의미를 요구한다. 도구 자식 프로세스는 데몬과 같은 OS 사용자로 돌아 소켓·로컬 포트에 접속할 수 있다. serve 뒤의 데몬에는 원격 요청도 127.0.0.1에서 온다.
- 결정: 연결 처리를 리스너(`tailnet` 7840, `loopback` 7841, `local` `rpc.sock`, 17 D17-09) · 인증층(hello에서 판정, 19 P-03) · 프로토콜층(한 벌의 처리기)으로 나눈다. 리스너는 출발지 주소(127.0.0.1)를 신뢰 근거로 쓰지 않는다. TCP 리스너는 기기 토큰이 필수다. 소켓 파일 권한에 기댄 로컬 관리자 주체는 `local`에서만 받고, 그 조건으로 도구 실행 격리가 소켓·데이터·설정 디렉터리를 가린다(방식은 13·18).
- 근거: pi-server의 "인증은 리스너 몫" 경계(pi-facts-2 §0-3), OpenClaw의 loopback 자동 승인 위험(pi-cases-notes §12.2-8). 결과 확인은 사람만(결정 15)을 도구 경로로 우회하지 못하게 한다.
- 기각한 대안: 격리 없이 로컬 소켓 연결을 소유자로 신뢰, 리스너마다 다른 처리기, SSH 경로용 별도 프레임 형식(06 1차 초안의 stdio 프레임. 19 P-02로 접음).

### ADR-06-21 단일 변경 경로는 저장소의 동기 대화형 쓰기 트랜잭션 위에서 돈다

- 맥락: `engine.transact(fn)`은 대화형 트랜잭션인데 저장소에는 입력 배열을 미리 받는 `commit`·`commitBatch`만 있었다. `KernelState`는 커밋 뒤에만 갱신되어 같은 트랜잭션 안 두 번째 제출이 첫 결과를 보지 못했다. 12·13의 제안 도구 경로(의도 → 제안 → 완료)가 이것에 기댄다.

- 기각한 대안: 입력 배열만 받는 `commitBatch`(앞 결과에 따라 뒤 입력을 정할 수 없다), 비동기 트랜잭션(트랜잭션 안 I/O 금지와 충돌).

- 평가: ① A14 ② 전부 ③ 정본 ④ 모든 이벤트 ⑤ 해당 없음 ⑥ 해당 없음 ⑦ 롤백이 상태 사본까지 버린다 ⑧ 유지

## 8. 다른 문서에서 올라온 ADR 후보

2a단계(2026-10-12)에 01~21 각 문서 끝 "ADR 후보" 절의 항목을 옮겼다. 옮긴 사람은 P3이고, 조정자 지시와 판정(`process/rulings-stage2a.md`)을 따랐다.

옮기는 규칙:

1. 번호는 `ADR-SS-NN`이다(§2.1). `SS`는 후보가 나온 문서 번호, `NN`은 그 문서 안에서 01부터 차례로 붙인다. 같은 문서의 후보가 나중에 더 오면 이어서 붙인다.
2. 브리프 결정과 같은 내용을 다시 정한 후보는 새 번호를 만들지 않고 해당 `ADR-00-xx`의 "결과"에 덧붙인다. 브리프 결정을 바꾸는 후보는 새 번호로 만들고 `ADR-00-xx`의 상태를 "대체됨 → …"으로 고친다([결정] 항목은 사용자 확인이 있어야 바꾼다).
3. 06의 ADR(ADR-06-xx)과 충돌하는 후보는 06 소유자(P3)와 조정자가 함께 정리하고, 바뀌면 옛 ADR을 "대체됨"으로 표시한다.
4. §7 예정 목록에 있던 항목이면 그 행을 지우지 않고 "→ ADR-SS-NN"을 덧붙인다.
5. 양식은 §2.3을 따른다. 평가 8개 중 답할 수 없는 것은 "해당 없음"으로 적는다. 다만 다른 문서에서 옮긴 후보는 전문을 원 문서에 두고 이 절에는 요지와 원 위치만 적는다(§8.1).
6. §3 색인 표에 행을 더한다.

### 8.1 옮긴 방식 (2026-10-12, 2a단계)

- 각 문서 끝의 "ADR 후보" 절은 원 문서에 그대로 둔다. 맥락·근거·기각한 대안·결과의 전문은 원 문서가 맡고, 이 절은 번호, 제목, 상태, 결정 요지, 원 위치, 다른 ADR과의 관계를 적는다(규칙 5의 양식은 원 문서 쪽 항목으로 채운 것으로 본다). 평가 8개가 원 문서에 없으면 소유 문서가 3단계에서 채운다.
- 번호의 `NN`은 원 문서 안의 순서를 그대로 따른다. 다른 ADR에 합친 후보도 번호를 남기고 상태를 "합침 → ADR-x"로 적는다. 그래서 원 문서의 후보 번호와 이 문서의 번호가 한 줄로 대응한다.
- "원 위치"는 원 문서의 "ADR 후보" 절 안 항목 이름이다. 행 번호는 문서가 고쳐질 때 바뀌므로 적지 않는다.
- 상태 값: 원 문서가 "제안"이면 제안, 조정자 판정으로 정해진 것은 "채택(판정 J-xx)"로 적는다. "합침"은 같은 내용의 다른 ADR이 정본이라는 뜻이다(§2.2 "대체됨"과 달리 내용이 바뀐 것이 아니다).
- 21은 2a단계에서 전면 개정했다. 21 행은 개정판(2026-10-12 12:50)의 후보를 옮긴 것이다(§8.19). 1단계 판의 후보 2(React 18 유지)는 결정 41로 해소되어 번호를 주지 않았다.

#### ADR-18-06 네트워크를 허용한 도구 실행도 네임스페이스를 분리하고 CONNECT 프록시만 통과시킨다

- 상태: 채택(판정 J-134) · 날짜: 2026-10-12 · 결정자: 조정자 판정 · 출처: rulings-needed K-16, V4
- 맥락: `--share-net` 실행은 루프백의 데몬 리스너와 Caddy 관리 API(인증 없음, 홈랩 H-5)에 접속할 수 있었다. 결정 46으로 루프백은 격리 경계가 아니다.
- 결정: 1차부터 네트워크 허용 실행도 네트워크 네임스페이스를 분리하고, 바깥 연결은 데몬 쪽 CONNECT 프록시로만 낸다. 프록시는 이름을 풀고 루프백·사설 대역·CGNAT·tailnet·링크 로컬 주소를 막는다. 외부 공개 인터넷은 `net:public`으로 연다([결정 55]). 차단 대역은 어떤 부여로도 열리지 않는다. 23에 스파이크를 두고, 실패하면 네트워크 허용 실행을 실행마다 사람 승인으로 하고 홈랩 H-5를 먼저 한다.
- 근거: 도구가 같은 호스트의 인증 없는 관리 API와 데몬 리스너에 접속하는 경로를 구조로 없앤다. 별도 네트워크 네임스페이스 안에서 bind로 넣은 Unix 소켓에 연결할 수 있음을 실험으로 확인했고, 추가 설치(pasta 등)가 필요 없다.
- 기각한 대안: `--share-net` 유지와 경고만(T-M5), 네트워크 허용 실행 금지(작업 범위가 줄어든다), pasta·slirp4netns(설치 필요), 사용자 BPF 필터(권한 문제).
- 결과: 13 §3.6, 18 §3.11.9, 06 §3.7.4 9번. 프록시의 허용 목록과 감사 기록은 18이 정한다. 프록시 환경 변수를 무시하는 프로그램은 바깥으로 나가지 못한다(fail closed). 08 `ResourceScope.net`의 `net:public`은 공개 인터넷 전체이고 루프백·사설·CGNAT·tailnet을 뺀다(판정 J-190 (2)).
- 평가: ① A6 ② M ③ 실행 환경 ④ 차단 기록 ⑤ 사람 결정 경로를 지킨다 ⑥ 실패 시 실행마다 승인으로 주의 비용이 는다 ⑦ 해당 없음 ⑧ 유지

  - 서버 측 `web_search`·`web_fetch`는 MVP에서 쓰지 않는다. 툴셋 판 이름(`browser_toolset_*`, `computer_toolset_*`)은 [검색] 수준이므로 구현 전에 공식 문서로 확인한다(13 O-13-18).
- 근거:
  - 서버 측 `web_fetch`는 JS 페이지를 실행하지 못하고, `sha256`·`finalUrl`과 리디렉션마다의 프록시 판정을 줄 수 없다. 13 §3.2.4 계약과 맞지 않는다(조사 §5.1).
  - 서버 측 `web_search`는 결과가 `encrypted_content`로 오므로 다음 턴에 되돌려야 하고 `pause_turn`도 처리해야 한다. 원문 URL과 해시가 Helm 기록에 남지 않는다(조사 §4.1, §8.4).
  - oh-my-pi는 의존하지도 vendor하지도 않는다(ADR-07-08). 해시라인은 Helm이 직접 만들고 기본은 `replace`다. 해시라인의 이득은 저자의 자체 벤치에서만 확인되었으므로 모델별 A/B 뒤에 켠다.
  - 브라우저는 읽기 멤버를 먼저 두고, 1단계에서 비-GET 요청을 거부한다(13 §3.10.1). 상호작용은 요청 가로채기가 붙은 뒤에 연다.
  - 컴퓨터 사용은 픽셀 클릭이 제출인지 알 수 없으므로 세션 전체를 `uncertain`으로 다룬다. 브라우저가 안정된 뒤에 둔다(조사 §6.7).
- 기각한 대안: 웹 도구를 P2로 미루기([결정 55]가 기각), 해시라인을 MVP+1로 미루기(판정 J-190이 MVP로 정함), 서버 측 도구 혼용(위 근거), Playwright MCP(send 판정과 ref 수명을 통제할 수 없다), Windows 호스트 조작 포함(범위 밖, 별도 설계).
- 결과: 01 MVP 목록에 웹 도구와 해시라인을 더한다(13 §5.2 01 행). 사람 작업(판정 J-190 (6)): `bubblewrap`(필수), `fonts-noto-cjk`(권고), 컴퓨터 사용 단계의 `xdotool`·`openbox`·`x11-utils`·`scrot`, 비밀 `BRAVE_SEARCH_API_KEY`(필수)·`TAVILY_API_KEY`(선택). 23 스파이크(판정 J-190 (7)): S1 안 Chrome 기동, netshim 경유 성능, 요청 가로채기 누락, Brave 약관의 결과 저장 조항, 한글 변환 품질, Chrome 실제 메모리, 해시라인 대 `replace` A/B. 기본은 `replace`다. 모델별로 해시라인을 켤지는 A/B 결과를 본 뒤 정한다(07 §7 M12).
- 평가: ① A7 ② E ③ 도구 계층 ④ `toolcall.*` 기록과 도구 결과의 `structuredContent` ⑤ 해당 없음 ⑥ 외부 효과가 있는 호출만 사람에게 묻는다 ⑦ 도구 호출 기록과 `replay` 값(`safe`·`never`)으로 복구한다 ⑧ 유지(도구 계약은 Helm 함수 도구)

#### ADR-13-10 브라우저 격리: S1 샌드박스, 실행별 네트워크 격리, CDP 파이프, 비밀 없음

- 상태: 제안(판정 J-190) · 날짜: 2026-10-14 · 결정자: 조정자 판정 · 출처: [결정 55], 판정 J-190 (1)·(3)·(4), 조사 `research-browser.md` §2.1, §6
- 맥락: 브라우저는 페이지 내용이 신뢰할 수 없는 입력이고(주입), 폼 제출·업로드·다운로드로 외부 효과를 낼 수 있다. Stagehand의 `act`·`extract`는 설정한 모델 제공자 키로 자체 LLM을 불러서, 비용·비밀·기록 경계가 Helm과 겹친다. Playwright MCP는 send 판정과 ref 수명을 통제할 수 없고, README가 보안 경계가 아니라고 밝힌다.
- 결정:
  - 실행 주체는 `helm-browserd`(Node 24 + playwright-core)다. S1(bubblewrap)에서 돈다. S1b는 "신호 격리 없음" 경고를 붙여 허용하고, S0에서는 브라우저 도구를 등록하지 않는다.
  - 네트워크는 실행마다 네임스페이스를 분리한다. Chrome은 `--proxy-server`로 샌드박스 안의 `helm-netshim`을 거쳐 데몬 CONNECT 프록시로만 나간다(ADR-18-06). 프록시가 호스트를, browserd가 메서드를 판정한다.
  - CDP는 `--remote-debugging-pipe`로 browserd와만 잇는다. 디버그 포트를 열지 않는다.
  - Chrome 내부 샌드박스를 켠다. 끌 수밖에 없을 때만 `--no-sandbox`를 S1·S1b에서 쓰고 상태 점검에 표시한다.
  - 프로필은 실행마다 새로 만들어 작업 공간 밖 tmpfs에 두고, 실행이 끝나면 지운다. 호스트 프로필과 쿠키를 가져오지 않는다. 지속 프로필(브라우저 신원)은 MVP 밖이다.
  - browserd는 비밀과 모델 키를 갖지 않는다(18 R-2). 모델 호출은 데몬만 한다.
  - 다운로드는 기본 거부다. 합의가 허용하면 `drafts/<concernId>/downloads/` 한 곳에만 받고, 파일당 50 MiB·실행당 200 MiB 상한을 두며 실행 권한을 주지 않는다. 업로드(`file_upload`)는 기본 꺼짐이고, 켜면 항상 `send`다. 위치·카메라·알림 권한과 클립보드는 거부한다.
  - 요청 가로채기(CDP `Fetch`)로 비-GET 요청과 합의 밖 호스트로의 이동을 잡는다. 폼 제출, 변경 요청, `sendBeacon`, 합의 밖 이동은 보류하고 `send`로 권리 게이트에 묻는다(요청 판정 표는 18 §3.11.11). 웹 내용을 본 run은 `taint.web`을 달고, 이후 `send`는 합의가 허용했어도 `ask`다(13 §3.10.1, 판정 J-190 (3)). 1단계(읽기 전용)는 비-GET을 보류하지 않고 거부한다.
  - 결과 투영: 페이지 내용은 `<untrusted source="browser">`로 감싸고, 스크린샷은 최근 3장만 남긴다(판정 J-190 (4)).
- 근거: 모델 호출과 비밀을 데몬 한 곳에 둔다(18 R-2). 출처 허용 목록은 리디렉션에 적용되지 않으므로(Playwright MCP 문서), 주입 방어는 네트워크 층에서 강제한다. 메서드 판정은 프록시가 볼 수 없는 HTTPS 경로와 본문을 다루므로 browserd가 맡는다. 루프백 포트는 같은 호스트의 다른 프로세스가 열 수 있으므로(ADR-00-46) 디버그 포트를 두지 않는다.
- 기각한 대안: 호스트 Chrome 프로필·쿠키 재사용(신원 노출), TCP 디버그 포트(루프백을 같은 호스트의 다른 프로세스가 연다), 브라우저 내부 출처 허용 목록에 의존(리디렉션으로 우회된다), Stagehand 핵심 사용(자체 LLM 호출로 비용·비밀 경계가 겹친다), Playwright MCP(send 판정과 ref 수명을 통제할 수 없다), browser-use(Python이고 자체 에이전트 루프가 Helm 루프와 겹친다).
- 결과: 실행 단위 메모리 2500 MiB, CPU 200%, 동시 세션 2, 탭 5(13 §3.2.5). 23 스파이크 확인 항목: S1 안 Chrome 기동과 bubblewrap 중첩 userns 동작, `/dev/shm`, netshim 경유 성능, 요청 가로채기가 `sendBeacon`·`keepalive`·서비스 워커 요청을 놓치지 않는지. 놓치면 `send` 판정이 빠진다. 사람 작업: `bubblewrap`(필수), `fonts-noto-cjk`(권고).
- 평가: ① A6, A7 ② E ③ 실행 환경 ④ 요청 목록(`requests[]`)과 `taint.web` 기록 ⑤ 해당 없음 ⑥ 외부 효과가 있는 요청만 사람에게 묻는다 ⑦ 크래시 때 외부 효과 호출은 `outcome: 'uncertain'`으로 기록하고 재실행하지 않는다 ⑧ 유지(도구 이름은 툴셋을 따르고 의미는 Helm이 정한다)
- 관련 문서: 13 §3.2.5, §3.6.3, §3.10.1, 18 §3.11.9, 12 PJ-7, 06(프로세스 위치), 23

#### ADR-13-11 검색 제공자: Helm 함수 도구, Brave 기본과 Tavily 예비, 제공자 인터페이스 뒤에 둔다

- 상태: 제안(판정 J-190) · 날짜: 2026-10-14 · 결정자: 조정자 판정 · 출처: [결정 55], 판정 J-190 (1)·(5)·(6), 조사 `research-browser.md` §4
- 맥락: [결정 55]가 웹 검색을 MVP에 넣고 외부 자율 탐색을 필수로 했다. 검색 제공자는 키·비용·결과 형식·약관이 서로 다르다. Anthropic 서버 측 `web_search`는 원문 URL과 해시를 Helm 기록에 남기지 않고, `encrypted_content`를 되돌려야 한다.
- 결정: `web_search`는 Helm 함수 도구다(읽기 원시 행동, `replay: 'safe'`). `search(query, opts)` 제공자 인터페이스 뒤에 Brave를 기본으로, Tavily를 예비로 둔다. 설정 `tools.webSearch { providers: ['brave', 'tavily'], monthlyCap }`의 순서대로 시도한다. 기본 제공자가 실패하면 예비를 한 번 부른다. Tavily 키가 없으면 예비를 끈다. 월 상한을 넘으면 제공자를 부르지 않고 `web.quota_exceeded`로 끝낸다. 질의는 18의 `mask()`를 거친 뒤 보낸다. 제목과 요약은 `<untrusted source="web">`로 감싼다. 키는 `BRAVE_SEARCH_API_KEY`(필수)와 `TAVILY_API_KEY`(선택)이며 `SecretStore`에서 읽는다.
- 근거: Brave는 독립 색인이고, 1,000건당 $5에 매월 $5 무료 크레딧이 자동으로 붙는다. 하루 수십 건이면 월 무료 크레딧 안에 들어갈 가능성이 크다(조사 §4.2). Tavily는 카드 없이 시작할 수 있어 예비와 개발용에 맞다. 제공자 인터페이스 뒤에 두면 다른 제공자로 바꾸기 쉽다.
- 기각한 대안: Anthropic 서버 측 `web_search`(위 근거), Tavily 기본(요약형 `content`가 주입 표면을 한 번 더 늘린다), Exa(의미 검색이 강하지만 2차 후보, 1,000건당 $4부터), SearXNG 자가 호스팅(상위 엔진의 차단과 CAPTCHA가 잦고 운영 부담이 크다, 비권고), Brave 단독(기본 제공자가 막히면 검색이 멎는다).
- 결과: Brave 약관의 결과 저장 조항을 23 스파이크로 확인한다. 검색 결과를 ledger에 저장하는 것이 저장 권리가 필요한 범주인지 본다(판정 J-190 (7)). 질의는 제3자 제공자에게 나간다. 검색 질의는 읽기라 `send`로 보지 않고 `taint.web`과 무관하게 허용하며, `queryMasked`로 가린 뒤 보낸다(판정 J-207이 13 §7 O-13-15를 정했다. 조사 §8.3 T-B8). 월 상한과 키 이름은 17의 `tools.webSearch`와 `secrets.keys`에 적는다(판정 J-190 (6)).
- 평가: ① A5 ② E ③ 어댑터(제공자 인터페이스) ④ `web.quota_exceeded`, 결과 `structuredContent.provider` ⑤ 해당 없음 ⑥ 해당 없음(월 상한이 비용을 막는다) ⑦ 읽기 원시 행동이라 `replay: 'safe'` ⑧ 유지(제공자가 바뀌어도 인터페이스 뒤에서 의미가 같다)
- 관련 문서: 13 §3.2.4, §3.6.4, §7 O-13-15, 17, 18 §3.10.4, 23
