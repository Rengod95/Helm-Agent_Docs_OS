## 1. 목적과 범위

### 1.1 이 문서가 정하는 것

1. Helm이 무엇인지(제품 정의)와 누구를 위한 것인지
2. Helm이 해결하려는 문제와 그 근거
3. 제품 원칙과 각 원칙을 확인하는 판정 질문
4. v0.2 실사용 증거와 그것이 설계에 주는 제약
5. C/A 우선, 사람 조작 2회 상한, 2주 우회율 지표의 정의
6. 적용 범주를 한정하는 이유, 진입 경로 세 가지, 진입 조건과 판정 규칙
7. MVP 범위(기능 × 단계)와 단계 사이의 증거 관문

9. 성공 지표와 반증 가설(H1~H10, V1~V9)의 연결. 측정 방법은 16이 소유한다.

## 3. 명세 본문

### 3.1 제품 정의

#### 3.1.1 한 문장 [제안]

> Helm은 한 사람이 에이전트와 함께 일할 때, 자신이 실제로 원하는 것을 자극과 반응으로 찾고, 무엇을 어디까지 맡겼고 결과를 무엇으로 확인했는지 남기며, 자리를 비워도 일이 이어지고 돌아왔을 때 바로 다시 판단할 수 있게 하는 개인용 에이전트 작업 시스템이다.

문장의 각 부분과 결정의 대응은 다음과 같다.

| 부분 | 근거 |
|---|---|
| 한 사람, 개인용 | 결정 24, 대화 L1586("나를 위한 에이전트루프") |
| 원하는 것을 자극과 반응으로 찾음 | 결정 1, 18 |
| 무엇을 어디까지 맡겼고 무엇으로 확인했는지 | 결정 15(1)(2), C/A 우선(§3.5) |
| 자리를 비워도 이어짐 | 결정 22 |
| 돌아왔을 때 바로 다시 판단 | 원전의 Return Brief(foundations/06 §5), 결정 10 |

#### 3.1.2 구성 요소 [결정 19~23, 33, 38, 41; 제안: 결정 26·27·28·29 기본값]

```text
[Mac 노트북 / Windows 호스트]                 [홈 서버: Windows 11 호스트 안의 WSL2 Ubuntu]
 Helm 데스크톱 앱 (Tauri v2 + React 19)        helmd (상주 데몬, systemd)
   얇은 클라이언트, Helm 로직 없음      ⇄       ├─ 커널: 검증·상태 전이·정책 (모델은 제안만)
   접속 (a) Tailscale serve 경유 WSS            ├─ 이벤트 로그: SQLite WAL (기준 원본, /srv/volumes/helm)
   접속 (b) SSH 경유                            ├─ 자체 런타임: 에이전트 루프(pi-agent-core 포크),
                                                │   모델 계층(pi-ai), 도구(coding-agent 도구 + Helm 제안 도구)
[이후 단계] SSH → WSL → Helm TUI (pi-tui)      ├─ 탐구 엔진, 스케줄러(타이머·가정 만료·기대 기한)
                                                └─ [이후 단계] 관찰 에이전트(별도 프로세스, 쓰기 권한 없음)
 관리 CLI `helm` (서버에서): 페어링, 상태, 백업, 복구
```

- 사용자가 직접 실행하는 것은 데스크톱 앱 하나다. 데몬은 서버에서 항상 돈다. 앱을 닫아도 진행 중인 작업은 계속된다 [결정 22].
- pi CLI와 Claude Code는 Helm 밖에서 평소처럼 쓴다. 이후 단계에서 런타임 어댑터로 Helm에 붙일 수 있다 [제안: 결정 34 기본값]. 그 전까지 Helm은 허용된 프로젝트 폴더의 외부 세션 로그를 관찰 에이전트의 입력으로만 읽는다 [결정 35].
- 프로세스 배치와 패키지 경계의 최종 정의는 06이 소유한다.

#### 3.1.3 사용자가 다루는 단위

| 단위 | 사용자에게 보이는 뜻 | 정본 정의 |
|---|---|---|
| Goal | 프로젝트 단위의 궁극 목표. Concern을 거치며 다듬어진다 | 결정 11, 08 |
| Concern | 10단계 과정을 돌릴 후보가 되는 상황(문제, 기회, 위험, 불확실성, 취향 결정, 반복 마찰) | 결정 11, 08 |
| WorkUnit | Concern 안에서 실제로 실행되는 일(탐구, 탐침, 변경, 반영) | 브리프 §6, 08 |
| 작업 합의 | 목적, 완료 기준, 범위, 금지 행동, 제출할 근거, 멈출 조건 | 브리프 §6, 08 |
| 결과 확인 | 에이전트가 제출한 결과를 사람이 받아들이거나 고치게 하는 일 | 결정 15(2), 08 |
| 질문 | 에이전트가 사람에게 물을 것. 기록과 전달이 나뉜다 | 결정 12, 11 |
| 에이전트가 정한 것 | 묻지 않고 정한 결정. 나중에 이의를 걸 수 있다 | 결정 8, 11 |
| 선호 모델 | 원함 탐구에서 쌓인 기준, 무게, 좋은 예와 싫은 예 | 결정 1, 15 |

사용자에게 N/E/M, A/P, OPD+C, 루프 식별자 같은 내부 용어를 외우게 하지 않는다. 화면 문구에서 어떤 이름을 쓸지는 05가 정한다 [제안].

#### 3.1.4 Helm이 하는 일

v0.3 01 §1.2를 따른다. 1~4는 [결정 1, 18]에 기댄다. 5~7의 실행 쪽 일은 결정 15·22를 이 문서가 풀어 쓴 것이다 [제안].

1. 사용자가 표현한 요구를 출발점으로 삼되 확정된 정의로 취급하지 않는다.
2. 서로 다른 관점, 다른 분야의 사고방식, 레퍼런스를 자극으로 제시한다.
3. 사용자의 반응을 근거로 실제 요구를 찾는다.
4. 찾은 요구를 Goal과 완료 기준에 반영하고, 이후 작업에서 계속 다듬는다.

여기에 실행 쪽 일이 더해진다.

5. 정한 일을 작업 합의로 맡기고, 합의 범위 안에서 에이전트가 실행한다(C).
6. 에이전트의 완료 주장을 근거와 함께 받고, 사람이 확인하고, 전체에 반영한다(A).
7. 사람이 없어도 일이 진행되고, 돌아온 사람에게 바뀐 것과 판단할 것을 보여 준다(O).

#### 3.1.5 일반 에이전트 하네스와의 차이 [제안]

foundations/09 §15와 v0.3 01 §1.5를 개인용 제품 기준으로 합쳤다.

| 질문 | 일반 에이전트 하네스(채팅 중심) | Helm |
|---|---|---|
| 출발점 | 사용자의 지시문 | 지시문은 출발점일 뿐, 실제 요구는 반응으로 찾음 |
| 사람이 하는 일 | 지시를 쓰고 결과를 승인 | 초안에 반응·수정하고, 맡길 범위와 결과를 확정 |
| 기본 화면 | 시간순 대화와 도구 호출 | 열린 Goal·Concern의 상태, 질문함, 에이전트가 정한 것 |
| 지시와 합의 | 처음 보낸 지시가 합의 역할을 함. 범위·멈출 조건·제출할 근거가 비어 있음 | 작업 합의 레코드. 범위 밖 호출은 커널이 막음 |
| 완료 | 모델이 "완료했습니다"라고 쓰면 제출·확인·반영이 한꺼번에 끝난 것처럼 됨 | 결과 제출 → 결과 확인 → 전체 반영을 나눔 |
| 묻지 않고 정한 것 | 대화 속에 흩어짐 | 따로 모이고 이의를 걸 수 있음 |
| 자리를 비우면 | 세션이 닫히면 멈춤 | 데몬이 계속 진행, 질문은 쌓였다가 전달 방식에 따라 전달 |
| 기록 | 대화 기록 | 이벤트 로그(기준 원본)와 그 투영 |

두 번째·세 번째 행의 근거는 대화 L2104–2109(X3-2-04)다. 원전 표(canon §15.14) 10행 중 기본 단위, 에이전트 역할, 컨텍스트, 진척, 실패 행은 따로 두지 않았다. 각각 §3.1.3 단위 표, §3.1.6 비대칭 표, PR-08과 공리 A11, §3.1.6 정당화된 진척, 공리 A14에서 다룬다.

#### 3.1.6 원전에서 이어받는 것

v0.1·v0.2 원전의 정의 중 이 제품이 그대로 이어받는 것을 적는다. 원전의 정의 판본 전체는 canon §3.1에 있다.

**최상위 목적과 정당화된 진척** (foundations/00 §1, §3, 09 §1)

> 인간의 주의력과 판단권을 보존하면서, 상호작용을 통해 결과의 정당성·품질·일관성을 높인다.

```text
justified_progress = validated_change + reduced_relevant_uncertainty
                   + increased_system_coherence + retained_human_agency
```

정당화된 진척의 네 조건: (1) 실제로 무언가가 가치 있는 방향으로 바뀌었다 (2) 그 변화가 목적에 맞다고 믿을 근거가 있다 (3) 누가 어떤 trade-off와 책임을 받아들였는지 명확하다 (4) 지역 변화가 전체와 맞고 다음 변화에 대응할 능력이 남아 있다. Helm은 원함 발견을 출발 동기로 두지만 [결정 1], 진척을 재는 기준은 이 네 조건이다 [제안]. 파일 수, 메시지 수, 실행 시간은 보조 지표다(공리 A2).

| 일 | 사람 | 에이전트 |

**좋은 경험과 즐거움** (friendly 00 §5, foundations/06 §11)

좋은 경험: 흩어진 상황이 이해 가능한 모습으로 정리된다 / 내가 바꾼 기준이 에이전트의 방향을 실제로 바꾼다 / 반복 작업을 보지 않아도 중요한 위험은 놓치지 않는다 / 결과를 단순 승인한 것이 아니라 함께 만들었다고 느낀다 / 시간이 지나도 다시 시작하는 비용이 낮다 / 쓸수록 나의 위임 방식과 판단 규칙이 좋아진다. 즐거움은 이해가 정리되는 만족, 기준이 반영되는 저자성, 탐구의 긴장, 통합의 완결감, 쓸수록 나아지는 유능감, 적은 조작으로 큰일을 맡기는 레버리지에서 나온다. 게임화는 쓰지 않는다(NG-07). SDT(자기결정성 이론)의 세 요소 중 자율성과 유능감은 SC-5와 경험 질문으로 잰다. 관계성은 1인 제품에 사람 사이 관계가 없어 쓰지 않는다. 사용자의 행동이 결과에 미친 영향을 사후에 보여 준다(foundations/06 §11). 이 항목들은 성공 기준 SC-5와 경험 평가 질문(§3.10.3)의 근거다.

원칙 뒤의 이론 근거 가운데 감사 보고(§2, §3.1, §3.5)가 따로 적으라고 한 것은 다음과 같다.

- "목표 공간은 사용자만 안다"는 처음 주장은 대화 중에 정정되었다. 목표와 해법은 함께 바뀌고(공진화, Dorst & Cross), 선호는 비교하면서 만들어진다(선호 구성, Dewey). 그래서 원함 탐구는 자극을 통해 사용자가 선호를 만들어 가도록 돕는다(PR-02, PR-03).
- 문서를 상태로 쓰지 않는다. 상태는 이벤트 로그와 그 투영이다(PR-08, 결정 29 기본값).
- 온톨로지를 먼저 완성하지 않는다. 레코드 종류는 실사용 증거를 보며 늘린다(PR-11).
- Concern 분해 자체를 루프로 다루자는 것은 사용자의 아이디어다(구조 루프 S, 3단계).

### 3.5 C/A 우선

#### 3.5.1 사용자 진술과 이유

- 진술: "최근 작업 하나를 Concern으로 놓았을 때 O, I, C, A 중 어느 루프를 가장 대충 지나갔거나 건너뛰었나"라는 질문(대화 L2016)에 사용자는 "C와 A"라고 답했다(대화 L2019). 이 답은 사용자 본인의 진술이며, 이 절의 설계 근거다.
- 왜 C와 A를 먼저 만드는가(대화 L2100–2115, Claude의 분석, 사용자 이의 없음).
  1. O와 I는 모델의 판단이 많이 필요해 코드로 강제하기 어렵다. C와 A는 대부분 상태 기록과 검사라서 코드로 강제하기 쉽다.
  2. 채팅 런타임에서는 지시가 곧 합의 역할을 하고, "완료했습니다" 한마디로 제출·확인·반영이 끝난 것처럼 된다(§3.1.5).
  3. C를 건너뛰면 A에서 확인할 기준도 없다. 둘은 함께 빠진다.
  4. C·A에 해당하는 공리(A6, A7, A10, A13)는 코드로 검사할 수 있다.
- A를 사람이 해야 하는 이유(사용자 진술, 대화 L3069): "책임소재를 질 대상이 없음, 확인과 반영이라는 것 또한 LLM이 진행하면 불확정성이 반드시 따라올 수밖에 없기 때문". 결과 확인은 사람만 한다 [결정 15(2), 공리 A6]. 2단계의 검증 에이전트를 새 컨텍스트와 가능하면 다른 모델로 두는 것도 같은 이유에서다. 결과를 만든 모델이 같은 조건에서 확인하면 그 불확실성이 확인에도 그대로 남는다(감사 보고 §3.1).
- 가장 큰 위험(대화 L2158): 이 장치 자체를 건너뛰게 되는 것이다. 건너뛴 이유가 귀찮음이라면 엔진이 묻는 횟수가 늘수록 또 우회하게 된다. 그래서 C/A는 빠뜨리지 않되 사람의 몫을 최소로 둔다.

#### 3.5.2 사람 조작 2회 상한 [제안]

원문(대화 L2160): "사람이 하는 일은 고르기 두 번이 상한입니다. 합의 확인 한 번, 결과 확인 한 번입니다. 나머지는 모델이 초안을 채우고 엔진이 검사합니다."

이를 측정 가능한 규칙으로 정의한다.

**용어**

| 용어 | 정의 |
|---|---|
| 결정 조작 | Helm이 사람에게 제시한 것(작업 합의 초안, 결과 제출, 질문, 기준 후보, Goal 수정 제안, Concern 열기 제안, 에이전트가 정한 것, 관찰 제안)에 대해 사람이 결정을 보내는 입력 1건. 셈법 세 가지는 아래 "셈법" 표를 따른다 |
| 입력 | 사람이 먼저 시작한 입력(새 요청, 실행 중 지시, 다이얼 변경)과 원함 탐구의 반응. 결정 조작과 따로 센다 |
| 보기 | 화면 열기, 펼치기, 근거 보기, 복귀 요약 읽음 표시. 조작으로 세지 않는다 |
| 정상 경로 | 변경 WorkUnit 하나(약속형 C + 확인형 A)가 범위 확대, 권리 게이트, 수정 요청, 실패 없이 끝나는 경로 |

**셈법** (CA-6이 쓰는 계산. 02·03·04·26의 조작 수는 이 표를 따른다)

| 경우 | 셈 |
|---|---|
| 묶어 답하기 | 질문 여러 개를 한 화면에서 답하면 질문 수만큼 센다. 결과 확인에 묶여 같은 조작으로 답한 질문(11 §3.15)은 결과 확인 1회에 포함한다. 질문 하나에 담긴 여러 기준은 1회다([판정 J-23], 02 UQ-11) |
| 반영 항목 처리 | 결과 확인 화면의 전역 처리 방침(두 값, R-OP-3)은 결과 확인 1회에 포함한다. 펼친 반영 단계에서 항목 하나를 따로 미루거나 바꾸는 것은 선택 조작이며 결정 조작으로 세지 않는다 |
| 고쳐서 확정 | 초안을 고친 뒤 한 번 제출하면 1회다(`agreement.confirm`에 구조화된 고침 `edits`를 함께 보냄, 10 `Partial<AgreementContent>`). 고침을 먼저 보내 새 초안을 받고 다시 확정하면 고침은 입력(I), 확정은 1회다 |
| 화면 경로 | 화면을 몇 번 거쳤는지는 세지 않는다. 03의 경로 수는 보기 수다 |

**규칙**

- R-OP-1: 정상 경로에서 결정 조작은 2회 이하다. (1) 작업 합의 확정 1회, (2) 결과 확인 1회.
- R-OP-2: 다음 두 경우에는 합의 확정 질문을 하지 않는다. 합의는 짧은 확인 문구(echo)로만 보이고 언제든 고칠 수 있으며, 합의 확정 조작은 0회다.
  - (a) 증명 가능한 포함: 사람이 이미 확정한 구조화된 범위 안에 새 합의가 들어 있음을 커널이 증명할 수 있을 때. 범위의 출처는 둘이다. 하나는 선택 요청에서 사람이 직접 고른 선택지다. 선택지는 구조화된 범위(`scope: Scope`)를 가지며, 질문 화면은 그 범위를 커널 값 그대로 보인다. 가정 확정이나 맡기기로 생긴 선택은 출처가 되지 않는다. 커널은 합의 범위 ⊆ 선택 범위를 검사하고 활성 방식 `choice_scope`로 기록한다([판정 J-133], J-90). 다른 하나는 사람이 맡겨 둔 권한(Grant)이다(08 `Activation` 방식 `grant`, 09 `agreement.activated_by_grant`). 근거는 canon-2 §4.6 Authority Carry-forward의 UX 결론("Do not ask again when the next Work Agreement is a proven subset of a visible, current Human instruction")이다.
  - (b) 명확한 직접 지시의 echo: 앱이 지시를 보내기 전에 합의 echo 미리보기를 보이고, 사람이 그 지시를 보내는 것이 합의 확정을 겸한다(10 §3.6.7: 사람 채널 `agreement.propose`+`confirmNow`, 08 `Activation` 방식 `direct_instruction`). 순서: 입력 중 미리보기(19 `composer.preview`)가 진입 예비 판정과 echo를 함께 돌려주고, 보내기 버튼 문구에 echo를 담는다. echo의 구조화 범위는 코드가 지시 문장에서 경로 토큰을 뽑아 만들고, 커널은 "지시 관찰에 나온 경로 ⊇ 합의 경로"를 검사한다. 모델이 범위를 만들었거나, 미리보기 없이 보냈거나, 보낸 뒤의 진입 판정이 미리보기와 다르면 확정 질문으로 돌린다 [제안]. 합의는 정책이 정한 작은 범위(지시에 이름이 나온 대상만 쓰기, send 없음, 의존성 추가 없음, 프로젝트 밖 쓰기 없음) 안에 있어야 한다. 지시는 입력(I)으로 세고 결정 조작을 더하지 않는다. 사람 확인 없이 정책만으로 합의를 만드는 경로는 없다(10 §5.3). 가벼운 작업(§3.6.4)의 기본 경로다(v0.2 CLI 경험의 자연어 → 상태 규칙 1, canon-2 §3.6).
  - 자연어 지시를 구조화된 범위로 옮기는 일은 모델의 제안이므로, 위 두 경우가 아니면 증명된 것으로 보지 않고 확정 질문을 한다. 범위 판정과 작은 범위의 정의는 10·11이 정한다.
- R-OP-3: 결과 확인 1회 안에서 반영 항목의 처리 방침을 함께 고른다. 방침은 전역 두 값("에이전트가 모두 진행"(기본) / "남는 제한은 미루고 나머지 진행", 04 §3.12)이다. 반영 항목마다 따로 묻지 않는다. 조건부 확인의 조건은 같은 트랜잭션에서 미룬 반영 항목(다시 볼 조건 = 조건 문장)이 되므로 조작을 더하지 않는다([판정 J-125]).
- R-OP-4: 정상 경로 밖에서 생기는 결정 조작은 상한에 넣지 않고 사유와 함께 센다. 사유 코드: `scope_expansion`(범위 확대 선택 요청), `rights_gate`(권리 게이트, 예: send), `correction_cycle`(수정 요청 뒤 재제출에 대한 결과 확인), `reinquiry`("기준이 틀림"이나 "먼저 탐구"로 탐구를 다시 함), `goal_change`(Goal 수정 확정), `contest`(이의 걸기와 그에 따른 재결정 답), `promotion`(Concern 열기 제안에 대한 답, 14 §3.14.4). 11 §3.10.3의 `rework`는 `correction_cycle`과 같은 뜻으로 보고 이름을 하나로 맞춘다(§5.2).
- R-OP-5: 돌아보기 한 줄("다음 합의에서 바꿀 것")은 선택 사항이며 조작으로 세지 않는다(대화 L2141).
- R-OP-6: 상한은 C/A 경로에만 적용한다. 원함 탐구의 반응(입력)과 탐구 뒤의 선택 요청은 별도로 센다. 원함 탐구의 피로는 라운드당 자극 수 다이얼과 반응 수 지표로 다룬다(15, 16).

**측정에 필요한 기록 형태** [제안, 계산은 16 §3.22.3]

정상 경로 여부와 사유는 저장하지 않고 이벤트 종류로 계산한다([판정 J-76]). 16의 `human_op` 사실이 아래 값을 가진다(사실 이름 `normalPath`·`opReason`). 08 `HumanOpMeta`의 `followedRecommendation`(추천을 그대로 따랐는가)과 `extraReason`(사람이 덧붙인 이유, 자유 문장)은 다른 뜻이고 이 계산에 쓰지 않는다.

```ts
/** 사람의 결정 조작 1건. 16이 사람 결정 이벤트에서 계산하는 사실(human_op). */
interface HumanDecisionOp {
  opId: string;                 // ev_ 접두사 이벤트 id를 그대로 쓸 수 있음
  at: number;                   // epoch ms
  deviceId: string;             // dv_...
  workUnitId?: string;          // wu_...
  concernId?: string;           // cn_...
  target:
    | "agreement" | "outcome" | "question" | "criterion"
    | "goal_revision" | "concern_open_suggestion" | "autonomous_choice"
    | "policy_proposal";
  normalPath: boolean;          // R-OP-1 상한에 들어가는가 (16 계산)
  opReason?:                    // 정상 경로 밖 사유 코드 (16 계산)
    | "scope_expansion" | "rights_gate" | "correction_cycle"
    | "reinquiry" | "goal_change" | "contest" | "promotion";
  editedDraft: boolean;         // 초안을 고쳐서 확정했는가 (PR-01 지표)
}
```

- 수용 조건: 정상 경로를 재현하는 가짜 모델 대본(02 UC-07 기본 흐름)에서 16 계산의 `normalPath === true`인 조작이 2건 이하이고, R-OP-2 조건을 만족하는 대본에서는 1건이다.
- 상한을 넘는 설계가 필요하다고 판단되면 그 설계 문서는 이유를 적고 이 문서의 미결 사항(§7)에 올린다.

### 3.6 적용 범주와 진입

#### 3.6.1 범주를 한정하는 이유 [제안]

대화 L2451–2454의 네 이유를 따른다.

1. **비용이 이득을 넘는 작업이 대부분이다.** Helm은 라운드, 질문, 기록, 확인이라는 비용을 낸다. 이 비용은 문제 정의가 불확실하거나, 사용자가 원하는 것을 아직 모르거나, 작업이 여러 날과 여러 작업에 걸칠 때 회수된다. 스택 트레이스가 원인을 가리키는 버그나 스펙이 정해진 구현에서는 마찰만 남는다.
2. **C와 A를 건너뛰게 된 이유와 같다.** 마찰이 있으면 우회한다. 모든 작업에 걸면 우회 습관이 Helm이 필요한 작업까지 번진다(공리 A12).
3. **기록이 쌓이는 곳이 일정해야 배울 수 있다.** 선호 모델, 이의 패턴, 합의 템플릿 개선은 비슷한 모양의 문제가 반복될 때 의미가 생긴다.
4. **"전부 적용하되 가벼운 것은 압축한다"도 결국 입구에서 분류해야 한다.** 그렇다면 입구 분류를 명시적으로 두는 편이 단순하다.

범주는 문제의 모양으로 정한다. 업무 분야("프론트엔드 성능")는 기준이 되지 않는다(대화 L2447, v0.3 01 §3.2).

#### 3.6.2 진입 경로 [제안]

대화 L2458–2465의 세 경로를 데스크톱 앱 기준으로 옮긴다.

| 경로 | 무엇이 일어나는가 | 앱에서의 모습(화면 이름은 03이 확정) |
|---|---|---|
| E1 시작 시 진입 | 새 요청을 받으면 진입 판정(§3.6.3)을 하고, 조건을 만족하면 Concern으로 시작한다 | "새 일" 입력 → 판정 결과와 함께 Concern이 열림. 판정은 에이전트가 정한 것으로 기록되어 이의를 걸 수 있다 |
| E2 작업 중 제안(승격) | 가벼운 작업으로 진행하다가 승격 신호(§3.6.5)가 나오면 "Concern으로 열까요?"를 질문으로 기록한다 | 질문함에 Concern 열기 제안이 쌓인다(정보 게이트, 기본 전달 협상). 수락하면 진행 중 기록을 가지고 Concern이 열린다 |
| E3 직접 지정 | 사람이 직접 Concern을 연다 | "Concern으로 열기" 명령. 이후 단계의 TUI에서는 `/focus`(대화 L2464) |
| 반대 방향(강등) | Concern 안에서 문제가 단순하다고 확인되면 증명 부담 다이얼을 낮추거나 가벼운 작업으로 내린다 | 강등도 에이전트가 정한 것으로 기록되고 이의를 걸 수 있다(v0.3 01 §3.7) |

- 이후 단계의 관찰 에이전트(§3.8)는 Helm 밖 세션 로그(pi, Claude Code)에서 승격 신호를 찾아 제안함에 올릴 수 있다. 이 경로는 E2의 변형이다.
- 모델은 신호가 있는지와 그 근거만 표시하고, "몇 개 이상이면 진입" 같은 규칙은 코드가 적용한다(대화 L2467, 결정 14).

#### 3.6.3 진입 조건과 판정 규칙 [제안]

v0.3 01 §3.3의 다섯 조건을 쓴다. 대화의 원래 목록(L2469–2477)에 있던 "되돌리기 비쌈"은 결정 2에 따라 빼고 "원하는 것이 취향에 달림"을 넣었다.

| ID | 14의 신호 id | 조건 | 확인하는 질문 | 신호 근거의 예 |
|---|---|---|---|---|
| EC-1 | `goal_vague` | 목표가 흐림 | 완료 기준을 한 문장으로 쓸 수 없는가 | 요청 문장, 사용자의 "잘 모르겠는데" 발화 |
| EC-2 | `paths_diverge` | 관점이나 해법이 나뉨 | 원인이나 해법 후보가 둘 이상인데 아직 어느 쪽인지 모르는가 | 모델이 낸 후보 목록, 서로 다른 관찰 |
| EC-3 | `taste_dependent` | 원하는 것이 취향에 달림 | 정답이 사용자의 취향이나 가치 판단에 달려 있는가 | 요청 대상(글 톤, 기획 방향, 디자인), 사용자 발화 |
| EC-4 | `long_running` | 오래 걸림 | 여러 세션이나 여러 날에 걸치는가 | 작업 규모 추정, 사용자 발화 |
| EC-5 | `entangled` | 다른 것과 얽힘 | 다른 결정, 다른 작업, 다른 사람의 일에 영향을 주는가 | 열린 Concern·Goal과의 관계, 공유 파일 |

- 진입 규칙: 다섯 조건 중 **근거 있는 참 신호가 두 개 이상**이면 Concern으로 진입한다(대화 L2469, v0.3 01 §3.3). 근거(`evidenceRefs`)가 없는 참 신호와 "모름"은 세지 않는다(결정 14의 "모델이 구조화된 값을 선언하면 결정은 코드가 한다").
- 제외 규칙: 그냥 해 보고 결과를 보는 비용이 탐구 비용보다 작으면 진입하지 않는다(대화 L2479). 제외 판정은 모델이 근거와 함께 선언하고, 진입 규칙보다 우선한다. 단 EC-3(취향)이 참이면 제외 규칙을 쓰지 않는다. 취향형 작업은 "해 보고 결과를 보는 것"으로 원하는 것을 찾을 수 없기 때문이다 [제안].
- 문턱 "두 개"는 고정값이며 다이얼로 두지 않는다. 2~4주 범주 지표(§3.6.7)를 본 뒤 바꿀지 정한다(§7 OQ-04).
- 사용자가 E3로 직접 지정하면 조건과 무관하게 진입한다. 사용자가 "되돌리기 비싸다"고 말한 것은 사용자 발화 관찰로 남고 E3의 근거로 쓰일 수 있다. Helm은 가역성을 스스로 계산하지 않는다 [결정 2].
- 판정은 혼자 정한 결정(kind `entry`)으로 기록되고 이의를 받는다. 판정 때문에 사람 조작을 늘리지 않는다. 이의 기록은 범주 지표와 문턱 조정의 자료가 된다.
- 14 §3.14.3이 이 규칙과 아래 타입을 그대로 쓴다. 판정 함수 `assessEntry`의 위치는 14 §6.1(`@helm/kernel`의 오케스트레이션 코어)이다. 신호 선언은 모델의 제안 종류 `entry_signals`로 들어온다.

판정 알고리즘(의사 코드):

```text
assessEntry(request, signals, exclusion):
  if request.explicitConcern:                         return enter(reason="direct")
  trueCount = count(s in signals where s.value == "yes" and s.evidenceRefs nonEmpty)
  excluded  = exclusion.value == "yes" and not (signals[taste_dependent].value == "yes" and signals[taste_dependent].evidenceRefs nonEmpty)
  if excluded:                                        return light(reason="exclusion")
  if trueCount >= 2:                                  return enter(reason="conditions")
  return light(reason="below_threshold")
  # 결과는 혼자 정한 결정(kind entry, why_not_asked = "진입 판정은 정책으로 처리")으로 기록
```

```ts
/** 진입 신호 선언. 신호 id는 08 §3.5 `EntrySignal`을 쓴다. 최종 스키마는 08·14. */
type EntrySignalId = "goal_vague" | "paths_diverge" | "taste_dependent" | "long_running" | "entangled"; // EC-1..EC-5
interface EntrySignalDeclaration {
  signal: EntrySignalId;
  value: "yes" | "no" | "unknown";
  evidenceRefs: string[];   // ob_... (사람 발화도 관찰). 비어 있으면 참으로 세지 않음
  note: string;             // 모델이 쓴 한두 문장
}
interface EntryAssessment {
  requestRef: string;       // 사람의 요청 관찰 ob_...
  signals: EntrySignalDeclaration[];
  exclusion: { value: "yes" | "no" | "unknown"; reason: string; evidenceRefs: string[] };
  decision: "enter" | "suggest" | "skip";   // 09 `entry.evaluated.decision`과 같은 값. skip = 가벼운 작업
  resultReason: "direct" | "conditions" | "exclusion" | "below_threshold";
}
// 기록: 09 `entry.evaluated`
```

#### 3.6.4 가벼운 작업 [제안, 조정자 판정 J-01]

진입하지 않은 요청도 Helm 안에서 처리할 수 있다. 이 문서는 이것을 "가벼운 작업"이라 부른다(14 §3.14.2의 "일반 세션"과 같은 대상).

- 위치: 프로젝트마다 하나 있는 "가벼운 작업" 보관 Concern(08 ConcernKind `light_work`, 14 §3.14.2) 아래의 WorkUnit으로 둔다. 보관 Concern에는 상황 판정, 루프 계획, 탐구를 하지 않는다. 보관 Concern은 프로젝트의 Goal에 연결되고, 확정된 Goal이 없으면 프로젝트 자리표시 Goal("이름 없는 Goal", 03 IA-03, 14 §3.14.6)에 연결되므로 공리 A1을 지킨다.
- 의존 규칙 (1)(2)와 불변조건은 압축된 형태로 지킨다 [결정 15, 17; 판정 J-01]. write·send에는 작업 합의가 필요하며 R-OP-2(b)의 직접 지시 echo로 충족한다. "완료"에는 결과 확인이 필요하며 한 화면 확인으로 한다. 사람이 미리 승인한 정책이 그 작업 종류를 정확히 덮을 때 정책으로 처리하는 길은 MVP에서 쓰지 않고 2단계 이후 검토한다([판정 J-89], §7 OQ-15)(v0.2 CLI-G01 F6의 "승인된 policy가 정확히 덮으면" 조건, 브리프 §6 선택 정의). 그런 정책은 사람이 설정이나 관찰 제안 채택으로 만든다.
- 근거: 결정 17(불변조건 5는 어떤 모드·다이얼에서도 바뀌지 않음), v0.2 Quick 규칙("완료를 수락과 동일시하는 것은 Quick에서도 금지", canon §16.6), OPD+C 지표 "의도·합의에 연결되지 않은 실제 변경 수(목표 0)".
- 예: "README 오타 고쳐 줘"(v0.2 CLI-Q01), "이 함수 이름을 items로 바꿔 줘".
- 가벼운 작업 중 승격 신호가 나오면 E2 경로로 Concern 열기를 제안한다. 수락하면 새 Concern이 열리고, 보관 Concern 아래에서 한 작업의 관찰과 도구 호출 기록을 참조한다.

v0.3 01 §3.7을 따른다. 감지 지점은 턴 경계와 실행 마무리 직전이다(대화 L2524의 `turn_end`, `agent_before_settle`에 해당하는 자체 런타임 훅, 12가 정함).

v0.2 CLI 경험 문서의 다섯 질문(canon-2 §3.2: 어디로 가는가 / 지금 무엇을 풀고 있는가 / 무엇이 사실이고 무엇이 아직 가능성인가 / 무엇을 어디까지 맡겼는가 / 무엇을 왜 완료로 받아들였는가)은 CAP-1, CAP-2·5, CAP-7, CAP-8·9에 들어 있다. 03은 이 다섯 질문으로 상태 표시줄과 홈의 정보 구조를 점검한다 [제안].

화면의 주의 부담 기준(canon-2 §3.18의 Attention 기준, 숫자는 초기 가설) [제안]:

- 기본 화면에서 일상적인 도구 활동이 절반을 넘지 않는다.
- 동시에 사람의 답을 기다리는 질문은 기본 3개까지 펼쳐 보이고 나머지는 우선순위대로 접는다. 권리 게이트 질문은 접어도 개수와 존재를 항상 표시한다(canon-3 §7.1 C3).
- 작업을 막지 않는 권리 게이트(결과 확인, Goal 수정)는 기록은 즉시 하고 전달은 다음 작업 경계 또는 검토 창에 한다. 가정 확정은 하지 않는다. 홈에서는 접고 개수를 보인다. 가벼운 작업의 결과는 묶어 확인할 수 있고 주의 비용을 낮게 센다. 작업을 막는 권리 게이트는 즉시 전달한다. 휴대폰 푸시는 결정 48(`interrupt`·`notice`)을 따른다([판정 J-132]). 이 문단이 03·04·11·14의 홈 접기 규칙의 기준이다.
- 같은 미해결 질문을 중복 요청하지 않는다(X-11).
- Concern 하나에서 결과를 바꾸는 선택 요청이 3개를 넘으면 각각의 필요성을 다시 본다(16의 검토 지표).

### 3.8 MVP 범위

#### 3.8.3 MVP 완료 기준

1. 02의 MVP 유즈케이스(§3.1 목록에서 단계가 MVP인 것) 수용 기준을 가짜 모델 대본과 E2E 테스트로 통과한다.
2. 실제 모델로 다음 세 작업을 끝까지 수행한 기록이 이벤트 로그에 있다: 취향형 작업 1건(UC-01), 원인 조사 1건(UC-02), 변경 WorkUnit 1건(UC-07).
3. 데스크톱 앱 macOS·Windows 두 기기에서 Tailscale 경로와 SSH 경로로 각각 질문에 답한 기록이 있다(UC-04).
4. 데몬을 강제 종료하고 다시 시작했을 때 진행 중이던 WorkUnit이 "중단됨"으로 정리되고 재개되며, 확인된 이벤트가 하나도 사라지지 않는다(UC-10).
5. 저장소의 `just verify`가 통과한다(레시피 목록은 06·23).

#### 3.8.4 단계 사이의 증거 관문 [제안]

v0.2에서 지연 복귀 실험을 열어 두고 결과 없이 구현으로 넘어간 일이 있었다(EV-8). 같은 일을 막기 위해 단계 사이에 사람의 실사용 증거를 남기는 관문을 둔다.

**G0: 원함 탐구를 커널에 정식 연결하기 전** (15 §3.15.2 E0)

제품 소유자의 실제 흐린 작업 다섯 개(취향형 둘 이상)로 앵커링 → 발산 → 검토 → 대비 압축 + 질문 하나를 평가 하네스(`just eval-inquiry`)로 돌리고, 보기 전과 본 뒤의 목표·완료 기준, 변화 정도, 피로를 기록한다. 취향형 과제는 "대안 2~3개를 받아 고르기" 비교 조건도 돈다(Helm 화면 밖의 평가용 조건이므로 결정 18과 충돌하지 않는다). 의미 있는 변화가 1건 이하이면 발산 설계를 다시 본다. 절차와 판정은 15가 소유한다. V1의 첫 비교 자료가 여기서 나온다. 구현을 한 번에 하는 경우([판정 J-11], 23 D23-4)에는 "커널에 정식 연결하기 전"을 "MVP 실사용 시작 전"으로 읽는다.

| G1-5 계속 쓰기 | "다음 작업에서도 Helm을 쓰겠는가"와 이유. 16 §3.27.4 자기보고(부담 6문항, 주도성 탐색 질문)를 G1 기간에 한 번 기록 | 답과 자기보고 기록이 있음 |

판정: 모두 통과 → 2단계 진행 / 일부 미통과 → 2단계 범위를 조정하고 미통과 항목의 원인을 MVP에서 먼저 고침 / 원함 탐구나 C/A가 쓰이지 않음 → 제품 정의를 다시 검토(§3.10.4).

**G2: 2단계 → 3단계** (2단계 실사용 14일 뒤): 렌즈 채택률(V6), 관찰 에이전트 제안 채택률과 채택 후 패턴 감소, 질문 지표(전달 수, 가정 확정 후 이의 비율), 피로 평가. 세부는 16이 정한다.

- 관문 기록은 Helm 자신의 Concern("Helm 사용 평가")으로 남긴다. 이 Concern의 결과 확인이 관문 통과다 [제안].
- 브리프 §1은 "설계가 끝난 뒤 한 번에 구현"을 목표로 한다. 구현을 한 번에 하더라도 관문은 "기능을 켜는 순서"로 지킨다: 2단계 기능은 구현돼 있어도 G1 기록 전에는 기본값을 꺼 둔다 [제안]. 이 긴장은 최종 보고의 "브리프에 대한 이의"에 적었다.

#### 3.8.5 원전의 성숙도·첫 제품 경계와의 대조

foundations/09 §12의 제품 성숙도(Level 0~5)와 §13의 첫 제품 경계를 이 MVP와 비교한다. 원전은 "첫 실제 제품은 Level 1과 2에 집중한다"고 했다. 이 MVP는 결정 22(클라이언트 없이 계속)와 C/A 우선(§3.5)에 따라 Level 3·4의 핵심도 함께 넣는다 [제안].

|---|---|---|

원전 §13의 NOT YET 항목 중 "전체 조직 governance"는 범위 밖(NS-02), "자동 권한 확대"는 계속 하지 않는다(범위 확대는 항상 선택 요청, §3.5.2 R-OP-4), "모든 agent tool 통합"은 이후 단계(외부 어댑터), "fully autonomous orchestration"은 비목표(NG-02)다. "formal assurance case everywhere"는 하지 않는다(근거 체인과 결과 확인으로 대신하고, 형식 보증 사례는 만들지 않는다). "graph database dependency"는 두지 않는다(정본은 SQLite 이벤트 로그, 결정 29 기본값).

v0.2 정제 후보의 수락 기준 9개(foundations/10 §12) 중 이 제품에서 여전히 확인할 것은 다음 넷이다. #3(강도 조절이 같은 불변조건을 지키며 부담만 바꾼다) → 증명 부담 다이얼(14)과 불변조건 테스트(10), #6(형식 검사를 통과한 쓰레기 입력이 "blind spot 없음"으로 올라가지 않는다) → 품질 상태(08)와 02 UC-06 수용 기준, #8(결과 제출·확인·반영 중 하나를 빼면 무엇을 잃는지 실제 사례로 확인) → G1-2, #9(원본 기록을 다시 읽는 양과 방향 수정 비용이 줄어든다) → H1, H5. #1·#2(제품과 런타임의 차이, 자체 agent 우선)는 결정 23으로 정리됐고, #7(두 런타임에서 같은 유즈케이스 재현)은 외부 어댑터 단계로 미룬다. #4(엔티티마다 사용자 질문·불변조건 연결)는 08의 레코드 정의와 10의 불변조건 표가 맡고, #5(경계를 예제로 설명)는 02 유즈케이스 단계 흐름이 맡으므로 이 문서에서 따로 확인하지 않는다.

#### 3.10.3 제품 성공 기준 [제안]

foundations/08 §7의 초기 성공 기준 다섯을 개인용 제품에 맞게 고쳤다. 원문 4번("ContextProjection이 전체 문서 읽기보다 적은 비용으로 중요 제약을 보존한다", canon §14.7)은 런타임 품질에 관한 것이어서 사용자가 직접 겪는 성공 기준(SC)으로 두지 않고 가설 H7과 그 지표(16 §3.25)로 잰다. SC-4·SC-6은 새로 더했다. "수치는 실사용 기준선을 잰 뒤 보정한다"는 원문 원칙을 따른다.

#### 3.10.4 다시 검토할 신호 [제안]

foundations/08 §6과 foundations/09 §17을 개인용으로 줄였다. 원전의 피벗 기준 7개와 반증 조건 9개 가운데 여러 사람을 전제한 것(Kanban 조건, facilitator 등)은 뺐고, 항목별 대응은 16 §3.28에 있다. 아래가 반복되면 제품 정의(이 문서)를 다시 연다.

1. 복귀 요약을 읽어도 원본 로그를 거의 항상 다시 읽는다(H1).
2. 질문 대부분이 추천을 그대로 받아들이는 것으로 끝난다(H4, approval theater).
3. 작업 합의의 비용이 줄어든 재작업보다 크고, 사용자가 합의를 계속 우회한다(H2, V8).
4. 원함 탐구가 고르기보다 나은 결과를 주지 못하거나 사용자가 지쳐 쓰지 않는다(V1).
5. 사용자 참여가 품질이나 주도성 없이 작업량만 늘린다(H8).
6. 사용자가 Helm보다 pi·Claude Code를 직접 쓰는 쪽을 계속 고른다(SC-6).

## ADR 후보

### ADR 후보 P1-1: MVP에 원함 탐구와 C/A를 함께 넣는다

- 상태: 제안
- 맥락: 대화의 구현 순서 제안은 C/A → O → I였다(대화 L2256–2261, L2815–2821). 사용자는 C와 A를 가장 많이 건너뛴다고 답했다(L2019). 한편 Helm의 출발 동기는 원함 발견이다(결정 1).
- 결정: MVP는 C/A, O(복귀 요약), I.fact, I.want를 모두 넣는다. MVP 안의 순서는 C/A → O → I.fact → I.want로 한다.
- 근거: 원함 탐구가 없는 MVP는 출발 동기를 시험하지 못한다(V1). C/A가 없는 MVP는 사용자가 건너뛰는 부분을 시험하지 못한다(V8). 둘 다 G1의 증거 항목이다.
- 기각한 대안: (a) C/A만으로 MVP: 출발 동기 검증이 늦어진다. (b) 원함 탐구만으로 MVP: 실행이 없는 탐구 도구가 되어 결과 확인까지의 흐름을 시험하지 못한다.
- 결과: MVP 범위가 커진다. 발산 서브시스템은 최소판(앵커링, 대비 압축 순서, 정지 규칙)만 MVP에 넣는다.

### ADR 후보 P1-2: 사람 조작 2회 상한을 정상 경로의 설계 제약으로 둔다

- 상태: 제안
- 맥락: C/A를 건너뛰는 이유가 귀찮음이라면 묻는 횟수가 늘수록 더 건너뛴다(대화 L2158). Claude는 "고르기 두 번이 상한"을 제안했다(L2160). 사용자는 답하지 않았다.
- 결정: 변경 WorkUnit 정상 경로의 결정 조작은 2회 이하(R-OP-1~R-OP-6). 비확장 합의는 다시 묻지 않는다. 정상 경로 밖 조작은 사유와 함께 센다.
- 근거: 측정 가능한 상한이 있어야 설계 문서들이 질문을 더하는 방향으로 흐르지 않는다. 비확장 합의 규칙은 v0.2 authority carry-forward에서 확인된 UX 결론이다(canon-2 §4.6).
- 기각한 대안: (a) 상한 없이 지표만 본다: 설계 단계에서 질문이 늘어나는 것을 막을 수 없다. (b) Concern 전체에 상한: 탐구의 선택 요청까지 막는다.
- 결과: 04·10·11·14가 이 상한을 검토 기준으로 쓴다. CA-6이 위반을 잡는다.

### ADR 후보 P1-3: 진입 조건에서 "되돌리기 비쌈"을 빼고 "원하는 것이 취향에 달림"을 넣는다

- 상태: 제안(v0.3 01 §3.3을 설계에 확정)
- 맥락: 대화의 진입 조건(L2469–2477)에는 "되돌리기 비쌈"이 있었다. 결정 2로 가역성 판별이 Helm 범위 밖이 됐다.
- 결정: 진입 조건 EC-1~EC-5(§3.6.3). 두 개 이상이면 진입. 취향 조건이 참이면 제외 규칙을 쓰지 않는다. 사용자가 "되돌리기 비싸다"고 말하면 직접 지정의 근거로 쓴다.
- 근거: 결정 1·2와 맞다. 취향형 작업은 "해 보고 보는 것"으로 원하는 것을 찾을 수 없다.
- 기각한 대안: 권한 레이어의 위험 값을 진입 조건으로 받기: 진입 판정이 권한 레이어에 묶이고, 권한 레이어 값은 행동 단위라 요청 단위 판정에 맞지 않는다.
- 결과: 14·12가 이 규칙을 구현한다. V7과 CT 지표로 확인한다.

### ADR 후보 P1-4: 범주 밖 요청은 Helm 안의 "가벼운 작업"으로 처리한다

- 상태: 채택(조정자 판정 J-01)
- 맥락: 대화의 진입 경로는 "평소에는 일반 pi로 작업"을 전제했다(L2458). 자체 런타임과 데스크톱 앱이 생기면서 Helm 안에서도 범주 밖 요청을 받게 됐다.
- 결정: 범주 밖 요청은 프로젝트별 "가벼운 작업" 보관 Concern(14) 아래에서 압축된 C/A로 처리한다. 불변조건과 의존 규칙 (1)(2)는 그대로 지킨다(직접 지시 echo로 C, 한 화면 확인으로 A. 정책으로 결과를 확인하는 길은 2단계 이후 검토, 판정 J-89). 승격 신호가 나오면 새 Concern 열기를 제안한다. 조정자 판정 J-01로 확정됐다.
- 근거: 사용자가 요청마다 "이건 Helm, 저건 pi"를 정하게 하면 진입 판정을 사람에게 넘기는 셈이다. 가벼운 작업에서도 기록이 남아야 승격 신호와 CT-2를 잴 수 있다.
- 기각한 대안: (a) 범주 밖 요청을 거절하고 pi로 보냄: 사용 흐름이 끊긴다. (b) 모든 요청을 Concern으로: PR-10 위반.
- 결과: 08이 가벼운 작업의 Goal 연결을 정한다(OQ-05). 03·04가 가벼운 작업의 화면을 정한다.

### ADR 후보 P1-5: 증거 관문을 기능 켜는 순서로 지킨다

- 상태: 채택(조정자 판정 J-11)
- 맥락: 브리프 §1은 설계 뒤 한 번에 구현을 목표로 한다. v0.2에서는 사람 증거 없이 구현이 앞서 나간 일이 있었다(EV-8, canon-2 §10 L1).
- 결정: 구현 일정과 무관하게 2단계 기능은 G1 관문 기록 전까지 기본값 꺼짐으로 둔다. 관문 기록은 Helm 안의 Concern으로 남긴다.
- 근거: 구현을 한 번에 하더라도, 사용 순서를 나눠야 MVP 기능의 효과를 따로 볼 수 있다.
- 기각한 대안: (a) 관문 없이 모든 기능을 켬: 무엇이 효과를 냈는지 알 수 없다. (b) 구현 자체를 관문 뒤로 미룸: 브리프 §1과 충돌한다.
- 결과: 06이 기능 플래그 구조를, 23이 관문 일정을 둔다.
