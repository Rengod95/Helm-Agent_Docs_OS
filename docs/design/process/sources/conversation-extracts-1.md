## 1. 출발 요구와 벤더 중립 하네스 원칙 ([1]~[2])

### 1.1 사용자의 출발 요구

- **E1-001** L3 [사용자] 목표: "vendor free agent skill, extention, workflow 등 클로드코드나 코덱스 처럼 특정 에이전트 프로바이더에 종속되지않는 나만의 에이전트를 개발". 당장은 pi를 쓰지만, "어떤 상황 어떤에이전트 런타임을 쓰더라도 동일하게 내 개발 및 에이전트 기반 자체 하네스 환경을 구축해놓은 걸 그대로 사용하려는 목적의 중립 에이전트 기술들을 구축하고 설계". [이후 변경 가능: 브리프 결정 23·34. Helm은 자체 런타임을 만들고, 벤더 중립은 런타임 어댑터 인터페이스로 유지한다]
- **E1-002** L6 [Claude] 기본 방침: pi를 당장 쓰더라도 하네스의 "본체"는 pi 밖에 두고 pi는 여러 어댑터 중 하나로 다룬다. 원칙 문장: "표준으로 이미 이식 가능한 것은 표준을 그대로 쓰고, 이식이 안 되는 것은 런타임 바깥의 실행 파일로 내리고, 런타임별 차이는 얇은 어댑터에만 가두는 것".

### 1.2 이식성 3계층 (L8–21)

- **E1-003** L10–13 [Claude] 계층 A, 표준 자체가 중립인 것(어댑터 거의 불필요)
  - Skills(SKILL.md): agentskills.io 표준. Claude Code, Cursor, Codex, Gemini CLI, VS Code 등 27개 이상 지원 [검색]. pi는 프로젝트 `.pi/skills/`, 전역 `~/.pi/agent/skills/`를 읽는다 [검색]. 경로 차이는 심볼릭 링크로 해결.
  - AGENTS.md: 항상 로드되는 프로젝트 컨텍스트. CLAUDE.md를 쓰는 런타임은 AGENTS.md를 import하는 한 줄 shim을 둔다.
  - MCP: 외부 시스템 연결용. "pi는 MCP를 기본 내장하지 않고 CLI 도구와 확장으로 해결하는 철학" — **[정정] L330에서 Claude가 스스로 고침. pi 1.0에는 MCP가 내장되어 있다(E1-092, E1-109)**.
- **E1-004** L15–18 [Claude] 계층 B, 런타임 바깥 실행 파일로 내리는 것("중립성의 실질적인 핵심")
  - 결정적 로직은 전부 CLI로(예: `ak <command>`, JSON 출력, `--help` 충실). 근거: 모든 에이전트가 공통으로 가진 유일한 도구가 셸이므로 CLI가 가장 이식성 높은 도구 인터페이스. 스킬은 CLI를 부르는 "사용 설명서" 역할만.
  - 가드레일은 에이전트 밖에서 강제. 금지 경로, 위험 명령 패턴 같은 정책은 `policies/*.yaml` 데이터로 두고 판정은 `ak guard check`. 최종 방어선은 git hook, CI, 컨테이너/샌드박스처럼 어떤 런타임도 우회할 수 없는 곳. "런타임 hook은 '빠른 피드백'이지 유일한 방어선이 아닙니다."
  - 상태와 메모리는 repo 안의 파일(markdown/JSON). 런타임 고유 메모리·세션 기능에 의존하면 그 순간 종속된다. [이후 변경 가능: 브리프 결정 29. Helm의 기준 원본은 SQLite 이벤트 로그다. "런타임 고유 세션 기능을 기준 원본으로 쓰지 않는다"는 취지는 결정 29에 남아 있다]
- **E1-005** L20–21 [Claude] 계층 C, 개념은 같으나 형식이 제각각이라 어댑터가 필요한 것: Hooks(라이프사이클 이벤트), subagent 정의, slash command/prompt template, 권한 설정.

### 1.3 중립 스키마 + 어댑터 (L23–40)

- **E1-006** L25 [Claude] 계층 C는 자체 중립 포맷을 정의하고, 런타임별로 변환하거나 런타임이 직접 읽게 한다.
- **E1-007** L27–34 [Claude] 중립 형식과 런타임별 매핑 표(원문 그대로)

| 개념 | 중립 형식 (본체) | pi | Claude Code | Codex |
|---|---|---|---|---|
| 상시 지침 | `AGENTS.md` (조각 합성) | 그대로 | CLAUDE.md shim | 그대로 |
| 스킬 | `skills/*/SKILL.md` | 심링크 | 심링크 | 심링크 |
| 도구 | `ak` CLI (+선택적 MCP) | bash로 호출 | bash / MCP | bash / MCP |
| 훅 | `hooks.yaml`: 중립 이벤트 → `ak hook <event>` | 브리지 extension이 런타임에 읽음 | settings.json hooks로 생성 | 지원 범위 버전별 확인, 없으면 fallback |
| 서브에이전트 | `agents/*.md` (role, 모델 힌트, 도구 힌트) | subagent extension용 생성 | `.claude/agents/` 생성 | 미지원 시 외부 runner로 |
| 커맨드 | `commands/*.md` | prompt template | slash command | 버전별 확인 |

- **E1-008** L37 [Claude] **중립 이벤트 어휘를 직접 정의**한다. 예: `session_start`, `pre_tool`, `post_tool`, `pre_commit`, `stop`. 런타임 이벤트 이름에 맞추지 말고 내 어휘를 각 런타임에 매핑. (브리프 §3.5 "중립 이벤트 어휘"로 이어짐 → 06·13 담당)
- **E1-009** L38 [Claude] **capability matrix + graceful degradation**: 어떤 런타임에 훅이 없으면 (1) AGENTS.md 지침으로 약화시키고 (2) git hook/CI에서 강제. "기능이 빠져도 하네스가 '깨지지 않고 약해지기만' 해야 합니다." (브리프 §3.5 "능력이 없으면 보장 수준을 낮춰 동작"으로 이어짐, 결정 34의 "각 런타임의 훅·권한 콜백까지라는 한계")
- **E1-010** L39 [Claude] pi 어댑터는 파일 생성보다 브리지 하나로. pi extension은 TypeScript로 도구와 이벤트 핸들러를 등록할 수 있으므로 `hooks.yaml`과 `agents/`를 읽어 동적으로 등록하는 `neutral-bridge` extension 하나만 둔다. [이후 변경 가능: 브리프 결정 23·33·34. pi CLI는 이후 단계의 런타임 어댑터(pi RPC) 대상]
- **E1-011** L40 [Claude] 스킬 본문에서 런타임 고유 도구명("Read tool", "Bash tool")이나 특정 모델의 프롬프트 관습에 의존하지 않는다. `allowed-tools` 같은 필드는 런타임마다 해석이 달라 힌트로만 취급.

### 1.4 워크플로는 두 종류 (L42–49)

- **E1-012** L44 [Claude] 에이전트 안쪽 워크플로: 한 세션 안에서 따라가는 절차(예: "PR 준비": lint → test → 변경 요약 → 커밋 메시지). 스킬 + 체크리스트 + `ak` 명령으로 표현하면 그대로 이식된다.
- **E1-013** L45–49 [Claude] 에이전트 바깥쪽 오케스트레이션: 여러 단계·여러 에이전트·루프·재시도가 필요한 것(plan → implement → review → fix 루프). 에이전트에게 시키지 않고 **외부 runner**가 돌린다.
  - `workflows/*.yaml`에 단계, 입출력, 종료 조건을 정의.
  - runner는 `AgentDriver` 인터페이스 하나만 안다: `run({ prompt, cwd, role, budget }) → { output, artifacts, exitStatus }`.
  - 드라이버 구현은 각 런타임의 headless 모드(`pi -p`, `claude -p`, `codex exec` 등)를 감싼다. ACP(Agent Client Protocol) 같은 런타임 중립 구동 프로토콜을 드라이버 계층에 쓰는 선택지도 있다.
  - 단계 간 데이터는 반드시 파일로 넘긴다(`.harness/runs/<id>/plan.md` 등). 대화 컨텍스트로 넘기면 런타임에 묶인다.
  - [이후 변경 가능: 브리프 결정 34. 런타임 어댑터 인터페이스(드라이버·하위 실행 계약)로 이어지되 1차 구현은 Helm 자체 런타임 하나. 브리프 §3.5 "드라이버·하위 실행 계약"]

### 1.5 저장소 구조 예시 (L51–73)

- **E1-014** L53–71 [Claude] `agent-kit/` 구조 예시(원문)

```
agent-kit/
├─ AGENTS.md                # 합성 결과 (instructions/*에서 생성)
├─ instructions/            # 지침 조각: 코딩 규칙, 커밋 규칙, 리뷰 기준…
├─ skills/<name>/           # SKILL.md + scripts/ + references/
├─ cli/                     # `ak` (TS, Node) — 결정적 로직 전부
├─ policies/                # guard 규칙 (데이터)
├─ hooks.yaml               # 중립 이벤트 → ak hook 매핑
├─ agents/                  # 역할 정의 (planner, reviewer…)
├─ commands/                # 프롬프트 템플릿
├─ workflows/               # 오케스트레이션 정의 (yaml)
├─ runner/                  # workflow runner + AgentDriver 구현들
├─ adapters/
│  ├─ pi/                   # neutral-bridge extension
│  ├─ claude-code/          # settings/agents/commands 생성기
│  └─ codex/
├─ evals/                   # 런타임별 적합성 테스트
└─ ak sync --target pi|claude-code|codex   # 설치/링크/생성
```

  [이후 변경 가능: 브리프 §3.1. Helm 저장소 구조는 `helm/packages/*`, `apps/*`, `vendor/` 모노레포로 정해졌다]

"반드시 지켜져야 하는 것"은 처음부터 텍스트 쪽에 두지 말고 훅이나 정책 코드 쪽으로 분류한다. (관련: 12 런타임 엔진의 투영·컨텍스트 생성, 브리프 결정 14 "모델은 제안하고 커널이 상태를 바꾼다")

## 4. 도구 수, 도구 승격 기준, bash 우회 문제 ([8]~[9])

- **E1-055** L202 [사용자] 진술: "모델 바깥에서 강제하는것이 에이전트 런타임의 존재 이유이자 역할". 질문: 많은 도구를 제시하는 것과 극소수 도구만 주는 것 중 어느 쪽이 정확성·효율이 높은가.
- **E1-056** L205 [Claude] 답: 대부분의 코딩 작업에서는 **극소수 범용 도구 + 필요할 때만 드러나는 전용 도구** 조합이 정확성·효율 모두 낫다.
- **E1-057** L207 [Claude] 도구가 많을 때의 비용: 도구 정의가 매 턴 컨텍스트를 차지(도구 묶음 하나가 수천~수만 토큰, E1-033). 더 큰 문제는 선택 비용. 기능이 겹치는 도구(`search_files`, `grep`, `find_in_repo`, bash의 rg)가 여럿이면 선택에 추론을 쓰고 미묘한 차이로 실수한다. "툴 수가 늘수록 정확도가 떨어지는 건 개수 자체보다 **겹침과 모호함** 때문".
- **E1-058** L209–212 [Claude] bash 하나로 다 되지는 않는다. 전용 도구가 나은 경우:
  - 출력이 구조화되고 깨끗할 때: 정확한 문자열 매칭으로 실패를 명확히 알리는 edit 도구가 sed 한 줄보다 오류가 적다. bash 출력은 노이즈가 많고 잘리기도 한다.
  - 상태를 가질 때: 브라우저 세션, 장기 실행 프로세스, 인증 컨텍스트처럼 호출 사이 상태가 필요할 때.
  - 런타임이 개입해야 할 때.
- **E1-059** L214 [Claude] **핵심 긴장: 도구를 줄일수록 런타임은 의도를 볼 수 없다.** 전용 도구는 런타임 입장에서 "의도가 드러나는 개입 지점". `Edit(path=src/auth.ts)`는 경로를 보고 허용·차단·로깅할 수 있지만 `bash -c "python - <<EOF ..."`는 의도를 알기 어렵다.
- **E1-060** L214 [Claude][검색] **bash 우회 사례(u1f992의 메모)**: Claude Code의 특정 모드가 파일 접근을 Read/Edit 대신 Bash로 하도록 유도하자, Read/Edit에 걸어 둔 훅과 경로별 규칙이 전부 무력화됐다. "bash만 주는 미니멀리즘은 모델의 자유도는 최대화하지만, 런타임의 강제 능력은 최소화". (브리프 §3.5 "bash·execute로 쓰기 범위 검사 우회 문제" → 13 담당)
- **E1-061** L214 [Claude] pi가 미니멀하면서도 extension으로 도구를 교체하거나 감쌀 수 있게 열어 둔 이유. Armin이 bash 도구 자체를 uv-aware 버전으로 바꿔치기한 예. "적은 툴"과 "강제 가능성"을 둘 다 잡으려면 **범용 도구 자체를 런타임이 감싸야** 한다. [검색]
- **E1-062** L216 [Claude] 모델에 따라 답이 다르다. 프론티어 모델은 셸·파일 조작에 많이 훈련돼 bash 중심이 잘 통한다. 작은·로컬 모델은 도구 정의가 명확하고 개수가 적을수록 안정적. 중립 하네스는 이 차이도 고려해야 한다. [추정]
- **E1-063** L218–221 [Claude] 하네스 설계 기준
  1. 항상 노출하는 핵심은 read, write/edit, bash 정도의 범용 도구로 최소화.
  2. **전용 도구 승격 기준**은 개수가 아니라 세 가지: (a) 런타임이 인자를 보고 개입해야 하는가, (b) 호출 간 상태가 필요한가, (c) 출력 구조가 정확성에 결정적인가. 셋 다 아니면 `ak` 같은 CLI로 두고 스킬로 사용법만 알린다(점진적 공개).
  3. bash 자체를 감싸 정책 검사(`ak guard check`)를 통과시킨다. "그래야 툴이 적어도 런타임이 눈을 뜨고 있을 수 있어요."
- **E1-064** L223 [Claude] 요약 문장(원문): "정확성을 떨어뜨리는 건 툴의 개수보다 겹침이고, 툴을 줄일 때 잃는 건 효율이 아니라 런타임의 통제력이라서, 통제가 필요한 지점에만 전용 툴을 두는 게 최적점".

## 5. 결정성과 토큰 효율 ([10]~[11])

- **E1-065** L226 [사용자] 질문: 결정성이 높은 작업일수록 토큰 효율성이 매우 올라간다고 볼 수 있나.
- **E1-066** L229 [Claude][정정: 사용자 진술(E1-065)을 다듬음] 방향은 맞지만 정확히는 "결정적인 작업이 원래 토큰 효율적"이 아니라 "**결정성이 높을수록 그 작업을 모델 밖으로 빼냈을 때 아낄 수 있는 토큰이 커진다**". 결정적 작업도 모델이 직접 하면 가장 비싼 편에 속한다. 예: 파일 200개 import 경로 변경을 edit 도구로 하나씩 하면 읽기·생성·확인 토큰이 쌓이고 오류 확률도 누적된다. 스크립트 한 번이면 "스크립트를 쓰고 실행하고 요약 결과를 확인"하는 토큰만 쓴다.
- **E1-067** L233–236 [Claude] 절감 지점: 추론 토큰(정답이 정해진 일을 다시 생각하지 않음), 왕복 횟수(여러 도구 호출이 한 번으로, 턴마다 다시 읽히는 컨텍스트 비용도 감소), 재시도 비용(결정적 코드는 같은 입력에 같은 결과, 확률적 실수를 고치는 루프 제거. 토큰보다 더 큰 이득인 경우가 많다).
- **E1-068** L238–241 [Claude] 주의점
  - 도구 출력 설계가 절반. 기본은 짧은 요약과 JSON, 상세는 플래그나 파일로.
  - 도구를 만드는 비용은 반복으로 회수된다. 한 번만 할 일은 모델이 일회용 스크립트를 짜서 돌리는 게 최적(Armin의 "throwaway code" 글). **같은 스크립트를 세 번째 짜고 있다면 그때 `ak` 명령으로 승격**.
  - 판단이 섞인 작업을 억지로 결정화하면 손해. 규칙이 계속 예외를 만나는 일을 코드로 고정하면 예외 처리에 토큰을 더 쓰거나 잘못된 결과를 통과시킨다.
- **E1-069** L243 [Claude] 원칙: 워크플로의 각 단계를 "결정적인가, 판단이 필요한가"로 분류하고, 결정적인 부분은 CLI·훅·외부 runner로 보내 모델 토큰은 판단이 필요한 지점에만 쓴다. "정확성, 비용, 재현성 세 가지가 모두 같은 방향". (브리프 결정 14 "모델이 구조화된 값을 선언할 수 있으면 결정은 코드가 한다"와 같은 방향)

## 6. 관찰 에이전트 C ([12]~[15])

이 범위에서 관찰 에이전트 C는 사용자가 처음 제안한 아이디어다. 브리프 결정 35와 용어집의 "관찰 에이전트"(기록을 읽어 반복 패턴을 찾고 절차·스킬·정책 수정안을 제안하는 별도 프로세스, 쓰기 권한 없음)로 이어진다. 담당은 16 관찰 에이전트 문서.

### 6.1 사용자 아이디어

- **E1-070** L246 [사용자] 아이디어(원문): "예로 내가 A라는 프로젝트를 에이전트 모델과 같이 작업하는데에 몰두하고 있잖아. 그리고 그 세션에서 인터렉션하는 모델 또한 A라는 프로젝트 구현에 집중하고있겠지, 이 세션에 대해 전혀 관련이 없는 다른 에이전트 C가 접근해서 세션에서 발생한 여러 반복되는 패턴이나 작업 흐름을 분석하고 추출해서 워크플로우 스크립트로 정적인 익스텐션이나 스킬을 제안하는 이런 흐름이 가능해? 이걸 런타임 에서 구현가능하냐는거임".
- **E1-071** L249 [Claude] 질문 재진술: "작업 중인 세션 A에는 개입하지 않으면서, 별개의 관찰자 에이전트 C가 세션 기록을 사후에 분석해 반복 패턴을 스킬, 확장, 스크립트로 제안하는 흐름을 런타임 수준에서 만들 수 있냐". 답: 가능.

### 6.2 가능한 이유와 위치

- **E1-072** L253–255 [Claude] 필요한 재료 두 가지
  1. 세션이 기록으로 남아야 한다. pi는 세션을 JSONL로 저장한다. Armin의 agent-stuff에 있는 `analyze-edits.py`가 pi 세션 JSONL에서 edit 도구 사용 패턴을 분석한다(관찰자 C의 원시 형태) [검색]. Claude Code와 Codex도 세션 기록을 로컬 파일로 남긴다.
  2. 분석을 시작할 신호. 세션 종료나 N턴 경과 같은 이벤트를 extension·훅으로 받거나 cron으로 세션 폴더를 주기적으로 훑는다.
- **E1-073** L257 [Claude] **런타임이 할 일은 "기록하고 신호 보내기"까지이고, C는 런타임 바깥에서 돈다.** C를 세션 A 안의 서브에이전트로 두면 A의 컨텍스트를 건드리거나 같은 모델의 관점에 갇힌다. 별도 프로세스에서 돌려야 (a) A의 몰입을 해치지 않고 (b) 분석에 더 싼 모델을 쓸 수 있으며 (c) pi, Claude, Codex 세션을 한꺼번에 볼 수 있어 벤더 중립도 유지된다.

### 6.3 C 구조 6단계 (L259–284)

- **E1-074** L261–282 [Claude] 구조(원문)

```
[세션 A: pi / Claude / Codex]
   │ 세션 로그(JSONL) + 종료 이벤트
   ▼
① 트레이스 정규화 (런타임별 어댑터 → 공통 스키마)
   user_msg / tool_call(name, args) / result(exit, size) / tokens / correction
   ▼
② 결정적 마이닝 (코드, LLM 없음)
   - 반복되는 툴 호출 시퀀스 (n-gram, 세션 간 빈도)
   - 같은 bash 명령 조합, 같은 파일 반복 읽기
   - 실패 → 재시도 루프, 사용자의 정정("아니 그거 말고")
   - 토큰을 많이 쓴 구간
   ▼
③ 관찰자 C (LLM, 후보 클러스터만 입력)
   "이건 스킬인가 / ak CLI인가 / 훅(강제)인가 / 그냥 우연인가" 판정 + 초안 작성
   ▼
④ 제안함(inbox): 근거(세션 id, 빈도, 추정 절감 토큰) + 초안
   ▼  사람이 승인
⑤ 중립 본체에 반영 → ak sync로 모든 런타임에 배포
   ▼
⑥ 효과 측정: 채택 후 해당 패턴의 빈도·토큰이 실제로 줄었는지 다시 마이닝
```

  - 공통 트레이스 스키마 필드: `user_msg`, `tool_call(name, args)`, `result(exit, size)`, `tokens`, `correction`.
  - [이후 변경 가능: 브리프 결정 35. 관찰 입력 1단계는 Helm 기록 전체 + 사용자가 허용한 프로젝트 폴더의 외부 에이전트 세션 로그(pi, Claude Code, Codex). ⑤의 `ak sync`·중립 본체 반영은 Helm 구조에서 다시 정해야 한다. 브리프 용어집: 관찰 에이전트는 쓰기 권한 없음, 수정안 제안만]
- **E1-075** L284 [Claude] ②를 코드로 두는 것이 중요. 수백 개 세션 원문을 C에 통째로 넣으면 비싸고 부정확하다. 반복 탐지는 코드가 맡고 "코드로 굳힐 가치가 있는 패턴인가"라는 판단만 C에게. ③의 분류 기준은 앞의 기준 그대로: 판단이 필요한 절차 → 스킬, 완전히 결정적인 반복 → CLI, 반드시 지켜져야 하는 규칙 → 훅.

### 6.4 주의점 (L286–291)

- **E1-076** L288 [Claude] 세션 기록은 **신뢰할 수 없는 데이터**. 웹 페이지, 이슈 본문, 도구 출력이 섞여 있어 C가 그 안의 문장을 지시로 받아들이면 오염된 스킬을 제안할 수 있다. pi extension은 임의 코드를 실행하므로 **자동 설치 금지**, 항상 사람 승인. (E1-216의 Factorio 사례가 실증)
- **E1-077** L289 [Claude] 비밀 정보가 로그에 섞여 있을 수 있다. 정규화 단계에서 마스킹.
- **E1-078** L290 [Claude] 제안 피로. 문턱(예: "N개 이상 세션에서, 추정 절감량 X 이상")을 두고, **기각한 제안은 다시 올라오지 않게 기록**.
- **E1-079** L291 [Claude] 같은 의도, 다른 표면. 명령 문자열을 그대로 비교하지 말고 정규화(경로, 인자 추상화) 후 묶는다. 이 부분은 C의 판단을 일부 빌려야 할 수도 있다.
- **E1-080** L293 [Claude] 이 패턴은 제품에도 들어오는 중(Claude 앱에 반복 절차를 스킬로 제안하는 기능). 다만 한 런타임 안에 갇혀 있고, 사용자의 구상은 여러 런타임 세션을 공통 스키마로 모아 중립 본체로 환류시키는 구조라 범위가 다르다. "지난번 조사에서도 거의 아무도 안 하고 있던 영역".
- **E1-081** L295 [Claude] 답 없는 제안: pi 세션 JSONL → 공통 트레이스 정규화기와 반복 시퀀스 마이너를 TypeScript로 프로토타이핑(실제 세션 파일 요청).

### 6.5 트리거 주체와 비결정성의 위치 ([14]~[15])

- **E1-082** L298 [사용자 동의] "좋은거같음" — C 구조(E1-073~E1-079)에 동의. 이어서 사용자 진술:
  - "하나의 런타임 프로세스 안에서, 메인 에이전트가 개별 서브에이전트에게 작업을 지시하는건, 서브에이전트 스폰 조차 비결정성에 의존하는 거"
  - "내가 하나의 작업에 매몰되더라도, 그동안 각 세션 작업을 통합해서 보고해주는 에이전트가 별다른 지시나 메인 세션 작업에서의 트리거가 없더라도 자동으로 구조화 시킬 수 있다는 거지?"
  - (브리프 결정 22 "진행 중인 작업은 클라이언트가 없어도 계속된다"와 같은 방향의 요구)

- **E1-095** L360–378 [Claude] signal 확장 초안(원문). 이벤트 페이로드의 정확한 타입은 `extensions/types.ts` 기준으로 맞춰야 하고 `getSessionFile`은 "실제 API 이름 확인 필요"라고 Claude가 명시했다.

```ts
import type { ExtensionAPI } from "@earendil-works/pi-coding-agent";
import { writeFile, mkdir } from "node:fs/promises";

export default function (pi: ExtensionAPI) {
  const enqueue = async (ctx: any, reason: string) => {
    const file = ctx.sessionManager.getSessionFile?.(); // 실제 API 이름 확인 필요
    if (!file) return;
    await mkdir(`${process.env.HOME}/.agent-kit/queue`, { recursive: true });
    await writeFile(
      `${process.env.HOME}/.agent-kit/queue/${Date.now()}.json`,
      JSON.stringify({ file, reason, at: new Date().toISOString() }),
    );
  };
  pi.on("agent_settled", (_e, ctx) => enqueue(ctx, "settled"));
  pi.on("session_shutdown", (_e, ctx) => enqueue(ctx, "shutdown"));
}
```

### 7.3 구현 주의점 (L381–389)

- **E1-096** L383 [Claude][검색: pi 문서] **분석 로직을 pi extension 안에 넣지 않는다.** pi 문서는 factory에서 프로세스, 워처, 타이머를 시작하지 말라고 한다. extension은 pi 프로세스와 같은 OS 권한으로 돌며 프롬프트, 파일, 자격증명, 세션 기록에 모두 접근할 수 있다. 확장은 신호만, 관찰자는 독립 데몬. 런타임이 바뀌어도 정규화 어댑터와 C를 부르는 드라이버만 교체하면 된다.
- **E1-097** L384 [Claude][검색: pi 문서] **pi 세션은 분기(branch)를 가진 트리.** 문서는 버려진 분기가 다른 역사를 나타내니 파일의 모든 엔트리로 상태를 재구성하지 말라고 한다. 마이닝 시 "실제로 채택된 경로"와 "버린 시도"를 구분해야 한다. 버린 분기는 "모델이 헤맨 지점" 신호로 쓸 수 있다. (브리프 §3.5 "pi 세션·패키지 특성(트리, …)" → 07 담당)
- **E1-098** L385 [Claude] **C 자신의 세션을 분석 대상에서 뺀다.** `--no-session`으로 돌리거나 C 전용 작업 디렉터리를 제외하지 않으면 C가 자기 분석 세션을 다시 분석하는 재귀가 생긴다.
- **E1-099** L386 [Claude] 진행 중인 세션은 증분으로 읽는다. queue에 오프셋을 기록해 같은 구간을 두 번 분석하지 않는다.
- **E1-100** L387 [Claude][검색] **스케줄러는 pi 밖에.** pi에는 cron 같은 기능이 없다. launchd/cron이나 데몬 내부 타이머로 "트리거 누락 대비 주기 스캔"을 둔다. 세션 이벤트와 주기 스캔을 함께 쓰면 놓치는 세션이 없다. (브리프 결정 22 데몬 상주, 12 스케줄러)
- **E1-101** L389 [Claude] Pi 1.0과 함께 Pi Durable이 발표됐는데 장시간 실행·백그라운드 작업 관련일 수 있으나 아직 내용 미확인. 관찰자 데몬을 만들기 전에 볼 가치가 있다. (→ [21]에서 확인, E1-114~E1-115, E1-120)
- **E1-102** L391 [Claude] 답 없는 제안: ① signal 확장, ② pi JSONL 정규화기(트리에서 활성 분기만 추출), ③ 반복 도구 시퀀스 마이너를 TypeScript 프로토타입으로. 실제 세션 파일 요청. 사용자는 pi 1.x 분석을 요청했다.

- **E1-111** L430 [Claude][검색: changelog] 실제 기능은 0.99.0(9월 29일)에 들어왔다. codemode, tool search, MCP가 내장 확장으로 추가. codemode는 모델이 쓴 JavaScript를 QuickJS 샌드박스에서 실행해 pi 도구를 호출. 같은 릴리스에서 확장 도구 API 확장: `exposure`(`direct`, `model-only`, `codemode`, `deferred`, `hidden`), `namespace`, `annotations`, `outputSchema`와 `structuredContent`, `ctx.executeTool()` 중첩 호출. 0.99.2부터 기본 codemode 노출의 MCP 서버가 codemode 설명에 나열되지 않고 첫 프롬프트도 막지 않으며, 스크립트가 `searchTools()`로 찾아 쓴다.

### 8.4 Pi Durable (L447–458)

- **E1-114** L449 [Claude][검색] Pi 코딩 에이전트는 터미널에서 한 사람이 조작하고, 프로세스가 죽으면 사람이 보고 다시 이어가는 도구이며 1.0도 그 역할. Durable의 목표: "어디서든 돌고, 여러 화면에서 접근하고, 대화가 무한히 이어지고, 장애에서 살아남고, 여러 사람이 같은 에이전트를 조종하는" 하네스. 코딩 에이전트 대체가 아니라 코딩 에이전트를 포함한 모든 에이전트 앱을 만드는 프레임워크. (Helm의 데몬 상주·원격 접속 요구(브리프 결정 21·22)와 같은 문제 영역)
- **E1-115** L451–458 [Claude][검색] 핵심 개념
  - 스토리지 위에 열리는 하네스: 메모리, SQLite, JSONL 스토리지 기본 제공. 커스텀 백엔드용 적합성 테스트(conformance suite).
  - 크래시 복구: 실행의 모든 단계가 체크포인트를 남기는 task. 프로세스가 죽으면 새 프로세스가 미완료 task를 찾아 이어 실행. 도구는 `replay: "safe"`로 선언된 경우에만 다시 실행되고, 아니면 모델에게 중단됐다고 알린다. (브리프 결정 30 "다시 실행해도 안전한 도구만 재실행", "중단됨"으로 정리)
  - 동시 대화와 포크: 하나의 하네스가 여러 대화를 동시에 돌리고 각 대화는 모델, 도구, 확장, 작업 디렉터리를 따로 가진다. 저렴한 모델에 읽기 전용 도구만 가진 리뷰어를 옆에 둘 수 있다.
  - 백그라운드 task: 대화에 속하지만 현재 작업과 분리, Esc를 눌러도 멈추지 않음.
  - 문서(documents): todo, plan 같은 앱 상태를 타입 있는 JSON으로 트랜스크립트 옆에 같은 원자적 커밋으로 저장.
  - 전체 소스 테스트 제외 약 1만 5천 줄(에이전트가 읽고 이해할 수 있는 규모).
  - 실험 단계, API 변경 가능 명시.

### 9.1 통제 수준 네 단계 (L489–500)

- **E1-124** L491–498 [Claude][검색: Philipp Schmid, "Four Subagents Patterns in 2026"] 메인 에이전트가 서브에이전트 생명주기를 얼마나 통제하는지에 따른 분류(원문)

| 패턴 | 툴 | 메인 에이전트 역할 | 수명 |
|---|---|---|---|
| ① Inline Tool | `call_agent` | 호출자 | 단일 작업 |
| ② Fan-Out | `spawn_agent`, `wait_agent` | 배분자 | 단일 작업 |
| ③ Agent Pool | spawn, send, wait, list, kill | 조정자 | 여러 턴 |
| ④ Teams | 위 전부 + 에이전트 간 `send_message` | 감독자 | 지속 |

- **E1-125** L500 [Claude][검색] 핵심 주장: 단계가 올라갈수록 더 강한 모델이 필요. ①은 도구 호출만 되면 어떤 모델이든, ②는 언제 기다릴지 판단, ③은 여러 에이전트 상태를 턴 사이에 추적, ④는 모든 에이전트가 프론티어급. 권장은 ①로 시작, 대부분 ①에서 끝난다.

### 9.2 컨텍스트 상속: Fresh / Fork (L502–506)

- **E1-126** L504 [Claude][검색] Claude Code: 이름 있는 서브에이전트는 빈 컨텍스트로 시작, fork된 서브에이전트는 현재 대화(기록, 시스템 프롬프트, 모델, 도구)를 물려받는다. fork는 같은 배경지식이 필요한 곁가지 작업에 적합.
- **E1-127** L506 [Claude][검색] Codex: 기본이 fork. 자식이 부모 컨텍스트, 샌드박스 정책, 런타임 설정을 물려받아 자식이 늘수록 컨텍스트 압박. 커뮤니티 대안은 `codex exec`로 완전히 분리된 프로세스를 띄우고 결과만 부모에 넣는 **detached 패턴**. 전문 에이전트를 다섯 개 이상 돌리면 검토 권고. "런타임 바깥에서 헤드리스로 띄우는 드라이버"(E1-013)와 같은 방향.

### 9.4 Agent Teams (L518–525)

- **E1-131** L520 [Claude][검색] Claude Code가 2월 실험 기능으로 낸 Agent Teams가 ④의 대표. 팀원은 각자 컨텍스트 창을 가진 독립 Claude Code 세션이고 **공유 작업 목록과 mailbox**로 조율. 컨텍스트를 공유하지 않고 소통은 작업 목록과 mailbox로만 명시적으로. 작업은 팀원이 스스로 가져가고 **파일 잠금**으로 같은 작업 동시 점유를 막는다.

### 9.5 코드로 지휘하는 서브에이전트 (L527–536)

- **E1-133** L531 [Claude][검색] RLM(Recursive Language Models): MIT의 Alex Zhang이 2025년 10월 블로그로 처음 소개, 이후 정식 논문. Prime Intellect가 "2026년의 패러다임"으로 꼽음. 큰 입력을 컨텍스트에 넣지 않고 지속되는 Python REPL에서 데이터를 살펴보고 변환하며 REPL 안에서 하위 LLM을 호출.
- **E1-134** L532 [Claude][검색] LangChain Deep Agents: 7월에 RLM 지원을 "dynamic subagents"로 추가. REPL에서 코드로 서브에이전트를 배분하고 입력 조각마다 재귀 처리. 스스로는 "재귀 에이전트(recursive agents)"에 더 가깝다고 설명.
- **E1-135** L533 [Claude][검색] Prime Agent(8월 논문): 지속 IPython REPL로 RLM 추상화를 따르고, 재귀 서브에이전트들이 에이전트 간 직접 통신으로 협업. ARC-AGI-3 Best@1이 30% → 95.5% 보고.
- **E1-136** L534 [Claude][검색] pi codemode도 같은 계열. "앞서 본 Linear 이슈 분석 예시"(이 범위의 앞부분에는 나오지 않는다. Earendil 글의 예시로 보인다)처럼 모델이 JavaScript로 워커 4개를 병렬로 돌리며 MCP 도구와 분류 모델을 조합하고, 결과는 컨텍스트가 아니라 codemode 저장소에 남긴다.
- **E1-137** L536 [Claude] 중요성: 도구 호출 방식에서는 "몇 개를 띄울지, 언제 기다릴지"를 모델이 매 턴 확률적으로 판단. 코드 방식에서는 **모델이 한 번 지휘 프로그램을 쓰고 그 실행은 결정적**. 비결정성이 "프로그램을 쓰는 순간" 한 곳으로 모이고 중간 결과는 변수에 담겨 메인 컨텍스트를 오염시키지 않는다. (사용자 진술 E1-082 "서브에이전트 스폰조차 비결정성"에 대한 답)

### 9.6 Durable 서브에이전트와 goal 루프 (L538–542)

- **E1-138** L540 [Claude][검색] 서브에이전트 = 소유된 대화(Pi Durable): 내장 서브에이전트는 없지만 몇 줄이면 만든다. 서브에이전트가 별도 대화로 존재해 크래시 이후에도 이어 실행. 재실행이 안전한 서브에이전트 도구는 기존 서브에이전트를 다시 찾아 답을 기다린다. **task와 대화가 하나의 소유 트리**를 이뤄 상위 작업을 중단하면 하위부터 차례로 정리된다.
- **E1-139** L541 [Claude][검색] 목표 상속과 judge(redcode PR #144): 부모에게 활성 목표가 있으면 서브에이전트 첫 프롬프트에 목표와 완료 조건을 담은 `<goal>` 블록을 넣는다. 백그라운드 자식이 도는 동안 부모 루프는 턴을 쓰지 않고 대기하다가, 자식 보고가 들어오면 judge가 다시 평가해 목표 완료 여부를 정한다.
- **E1-140** L542 [Claude][검색] Huntley의 Ralph에서 시작된 "loop engineering"의 연장. Claude Code에는 `/loop`, `/schedule`이 있고 Anthropic은 `/goal`을 목표 기반 실행 패턴으로 설명.

### 9.7 하네스 시사점 (L544–552)

- **E1-141** L546–548 [Claude] "서브에이전트 스폰조차 모델의 비결정성에 의존한다"는 사용자 지적에 업계가 두 방향으로 답하고 있다.
  1. 코드로 지휘하기(RLM, codemode, dynamic subagents): 비결정성을 프로그램 작성 시점 한 곳으로.
  2. 바깥에서 지휘하기(detached 프로세스, durable task, goal 루프, 스케줄): 트리거를 코드로.
- **E1-142** L550 [Claude] Agent Teams는 비결정성을 늘리는 방향이라, 프론티어 모델과 토큰 비용을 감당할 수 있는 탐색형 작업에만 쓰이는 추세.

### 10.2 문제: context rot (L605–615)

- **E1-149** L609 [Claude][검색][정정: Anthropic의 context rot 정의를 RLM 저자가 고친 내용 소개] context rot: Anthropic 정의는 토큰 수가 늘수록 정보를 정확히 떠올리는 능력이 떨어지는 현상. RLM 저자는 이 정의가 완전히 맞지 않다고 지적. needle-in-a-haystack에서는 최신 모델이 90% 이상. 실제로 무너지는 것은 "하나를 찾는" 작업이 아니라 **긴 입력 전체에 걸쳐 수천 개 항목을 의미적으로 연결해야 하는 작업**.
- **E1-150** L611–613 [Claude] 기존 해법의 한계: 더 긴 컨텍스트 창(담을 수는 있어도 무뎌짐은 그대로), 요약(compaction, 손실 압축)과 검색(RAG, 무엇이 관련 있는지 미리 알아야 함). 질문이 전체를 훑어야 답할 수 있는 형태면 둘 다 약하다.
- **E1-151** L615 [Claude][검색] 저자의 출발점: 컨텍스트를 두 번의 모델 호출로 나누고 세 번째 호출에서 합치면 열화를 피할 수 있다는 직관. 이 "나누고 합친다"를 모델이 코드로 직접 하게 만든 것이 RLM.

### 10.3 메커니즘 (L619–649)

- **E1-152** L623–628 [Claude][검색] 공식 구현 흐름
  1. 루트 LM(depth=0)은 질문만 받는다. 긴 입력은 Python REPL 노트북에 변수로 미리 로드되고, 루트는 변수의 존재와 크기만 안다.
  2. 루트 LM은 코드 블록을 출력하고 REPL이 실행, 출력이 루트 컨텍스트로 돌아온다. 출력은 **잘린(truncated) 형태**로만 돌아온다(루트 컨텍스트 보호 장치).
  3. 코드 안에서 하위 LM(depth=1)을 함수처럼 호출. 엿보기, 나누기, 검색, 조각별 하위 질의.
  4. 종료 방법 두 가지: `FINAL(answer)`로 직접 출력, 또는 REPL 변수로 답을 만들어 `FINAL_VAR(변수명)`으로 반환.
- **E1-153** L632–647 [Claude] 루트 LM 코드 예시: (1) 엿보기 `print(len(context))`, `print(context[:2000])` (2) 좁히기: 코드로 후보 거르기(LLM 호출 없음, 결정적) (3) 나누고 맡기기: `llm_query(...)`를 조각(50행)마다 (4) 합치기는 코드로, `FINAL_VAR(answer)`.
- **E1-154** L649 [Claude][검색] 핵심: 루트 LM 컨텍스트에 들어가는 것은 "데이터"가 아니라 "데이터를 다룬 결과의 요약"뿐. 저자가 꼽은 첫째 이점: 루트가 전체 컨텍스트를 직접 보지 않아 입력 컨텍스트가 천천히 늘어 막히는 일이 드물다.

```js

const candidates = mineRepeatedSequences(sessions); // 결정적 마이닝 (코드)
const verdicts = await Promise.all(           // 후보 클러스터마다 하위 LM 판단 (병렬)
  candidates.map(c => llmQuery(`이 반복 패턴은 스킬/CLI/훅/우연 중 무엇인가?\n${c.sample}`))

// C의 루트 컨텍스트에는 verdicts 요약표만 들어간다
```

- **E1-173** L762–767 [Claude] 실무 규칙

### 11.1 codemode는 도구 하나 (L820–836)

- **E1-178** L824 [Claude][소스 확인·검색] pi codemode는 RLM 구조를 **도구 하나**로 포장. 모델은 `codemode` 도구를 호출하며 인자로 JavaScript를 넘긴다. 코드는 QuickJS 샌드박스에서 **async 함수 본문**으로 실행되어 최상위 `await`와 `return`을 쓸 수 있다. 코드 안에서 `tools.<name>(args)`로 세션의 다른 도구를 부른다.
- **E1-179** L828–834 [Claude] RLM ↔ codemode 대응 표(원문)

| RLM (1장) | pi codemode |
|---|---|
| Python REPL | QuickJS 샌드박스 |
| `context` 변수 | 스크립트 안의 지역 변수 |

### 11.3 스크립트 한 번의 생애 (L865–889)

- **E1-188** L867–871 [Claude][소스 확인·검색] 순서
  1. 옵션 파싱: 첫 줄 `// @options: {...}`에서 `max_output_tokens`(기본 10000)와 `timeout_ms`.
  2. 실행: 새 worker와 VM에서 실행. 도구 호출은 호스트로 넘어가 실행되고 결과가 VM으로 돌아온다.
  3. 결과 형태: `outputSchema`를 선언한 도구는 구조화 객체로, 나머지는 문자열로. 예: `bash`는 `{ output, truncated, full_output_path?, exit_code, wall_time_seconds }`를 돌려주고, 0이 아닌 종료 코드도 예외가 아니라 값으로 받는다.
  4. 출력 조립: 모델에게는 스크립트 출력만 전달되고 중간 데이터는 샌드박스에 남는다. 출력이 상한을 넘으면 앞뒤만 남기고 전체는 임시 파일에 써서 경로를 알려 준다.
- **E1-189** L873–887 [Claude][실험 D] 실패 시 의미론(원문 코드와 결과)

```js
// 실험 D: 중간에 실패하는 스크립트
store("x", 1);                              // 상태 쓰기 시도
text("1단계 완료");                          // 출력
await tools.read_log({ offset: 0, limit: 1 }); // 실제 툴 호출

```
```
[D] 실패 스크립트: ok = false / 남은 출력 = ["1단계 완료"]
    / 이미 실행된 툴 호출 = 1 / storeWrites 존재 = false
```

  세 가지가 다르게 처리된다: **출력은 실패 지점까지 남고, 이미 일어난 도구 호출은 되돌려지지 않으며, `store()` 쓰기는 버려진다.** 문서도 쓰기는 스크립트가 성공했을 때만 유지된다고 명시. "상태 쓰기"만 원자적이고 외부 부수효과는 원자적이지 않다.
- **E1-190** L889 [Claude][검색: 문서] 실무 함의: 부수효과가 있는 도구(파일 쓰기, 배포, 메시지 전송)를 스크립트 중간에 넣으면 실패 후 재시도 때 같은 일이 두 번 일어날 수 있다. 일부 실패에도 성공 결과를 지키려면 `Promise.allSettled()` 권장(문서). (브리프 결정 30 크래시 복구·재실행 안전성과 같은 문제)

### 11.4 실험: 컨텍스트와 벽시계 시간 (L893–926)

- **E1-191** L895–907 [Claude][실험 A] 설계: 1장과 같은 6,000행 데이터를 `read_log` 도구(500행씩 페이지, 구조화 출력)로 노출하고, 200ms 걸리는 `classify` 도구를 하위 모델 대역으로. 직접 호출 쪽은 각 도구 결과가 모델 컨텍스트로 돌아간다고 가정해 계산. 스크립트(원문):

```js

const first = await tools.read_log({ offset: 0, limit: 500 });
const pages = []; for (let off = 0; off < first.total; off += 500) pages.push(off);
const all = (await Promise.all(pages.map(o => tools.read_log({ offset: o, limit: 500 }))))
  .flatMap(p => p.lines);                     // 6000행은 샌드박스 변수에만 존재
const mine = all.filter(byTargetUser);         // 코드로 거르기
const counts = await Promise.all(chunks(mine, 20).map(c => tools.classify({ items: c })));
store("numeric_by_chunk", counts);             // 다음 스크립트가 쓸 상태
return { filtered: mine.length, numeric: sum(counts) }; // 모델이 보는 건 이것뿐
```

### 11.5 상태: store()와 트랜스크립트 (L930–947)

- **E1-196** L936–939 [Claude][실험 B] 결과(원문)

- **E1-197** L941 [Claude][실험·소스 확인] 메커니즘: 샌드박스는 아무것도 기억하지 않는다. 스크립트가 성공하면 쓴 값을 `storeWrites`(`{ set, delete }`)로 호스트에 돌려주고, 다음 실행 때 호스트가 `store` 옵션으로 다시 넣는다. pi 쪽에서는 값을 저장한 성공 스크립트마다 세션 트랜스크립트에 `codemode-store` 커스텀 엔트리가 추가되고, 세션 재개 시 값이 복원되며, **각 대화 분기는 자기 경로에서 쓴 값만 본다.**

### 11.6 노출(exposure)과 설명 비용 (L951–972)

- **E1-201** L953 [Claude] 기초: 도구를 쓰려면 이름, 설명, 인자 스키마가 매 요청 프롬프트에 들어가야 한다("선언"). 도구가 많을수록 선언이 길어지고 매 요청 반복 비용.
- **E1-202** L955–958 [Claude][소스 확인·검색] codemode 관련 노출 등급 셋
  - `direct`: 모델에게 선언. codemode가 켜져 있으면 설명 끝에 "스크립트에서 이렇게 부르면 이런 값이 돌아온다"는 한 줄이 붙는다.
