# Helm 설계 브리프 (모든 설계·검증 에이전트 공통)

- 작성: 2026-10-11, 조정자(메인 세션). 저장소 경로 기준으로 고친 판
- 2026-10-11 Claude Code 이관 후 수정: §4 입력 자료의 경로를 실제 위치로 고침(pi 소스·사례 저장소는 `~/projects/_ref/`, 0단계 산출물 파일 이름), §3.5 감사 보고 경로 수정
- 이 문서는 설계 작업의 공통 전제다. 모든 에이전트는 작업 전에 이 문서를 처음부터 끝까지 읽는다.
- 이 문서와 다른 자료가 충돌하면 이 문서가 우선한다. 이 문서 자체에 문제가 있다고 판단하면 최종 보고의 "브리프에 대한 이의"에 적는다(임의로 무시하지 않는다).

## 1. 목표

제품 소유자(사용자, 1인)가 설계가 끝난 뒤 **한 번에 구현**할 수 있도록, Helm의 전체 설계를 구현 가능한 수준까지 완성한다.

- 대상: 제품 기획과 유즈케이스·시나리오, UX, 전체 아키텍처와 레이어, Helm 도메인 모델과 커널, 런타임(에이전트 루프, 도구, 모델 계층, 크래시 복구, 스케줄러), 루프·모드·탐구 엔진, 관찰 에이전트, 데몬과 운영, 클라이언트 프로토콜, 보안, 데스크톱 앱, pi 패키지 활용·포크 계획, 테스트 전략, 구현 계획.
- "구현 가능한 수준"의 뜻
  - 타입과 스키마는 TypeScript 코드 블록으로 적는다.
  - 상태 기계는 표(상태 × 이벤트 → 다음 상태, 가드, 부수 효과)로 적는다.
  - 알고리즘은 의사 코드나 단계 목록으로 적는다.
  - 실패·예외·경계 사례를 빠짐없이 적는다.
  - 다른 문서와의 경계(제공하는 것, 요구하는 것)를 적는다.
  - 모듈마다 완료 기준(테스트로 확인할 조건)을 적는다.
- 정하지 못한 것은 숨기지 않는다. "미결 사항" 절에 선택지와 추천 기본값을 적는다. 구현자가 기본값으로 진행할 수 있어야 한다.

## 2. 확정된 결정

출처 표기: [v0.3 §5-n]은 `docs/v0.3/00-README.md` §5의 n번, [대화]는 2026-10-11 대화.

### 2.1 Helm 이론 (v0.3에서 결정)

1. Helm의 출발 동기는 원함 발견이다. 사용자가 글로 표현한 요구와 실제 요구는 다를 수 있고, 자극을 비교해 본 뒤에야 원하는 것을 알게 된다. 발산은 이 동기를 위한 방법이다. 첫 출발점은 취향이 정답인 작업(글의 톤, 기획 방향, 디자인)이었다. [v0.3 §5-1]
2. Effect class와 가역성 판별은 Helm 범위가 아니다. 권한 레이어의 일이다. [v0.3 §5-2]
3. 모드는 페르소나가 아니다. 루프 계획 기본값, 능력 부분집합, 다이얼 값의 설정이다. [v0.3 §5-3]
4. 능력은 원시 행동(read, write, execute, send, spawn, ask)과 기록 능력(observe, propose, attest, accept, integrate)으로 정의한다. [v0.3 §5-4]
5. 루프(O, I, C, A, S)는 한 작업 안에서 필요에 따라 조합하고 언제든 전환한다. 커널이 강제하는 것은 의존 규칙뿐이다. [v0.3 §5-5]
6. 상황 유형(Cynefin 다섯 유형)은 바뀔 수 있는 상태다. [v0.3 §5-6, §5-16]
7. 탐구는 네 종류(사실, 원함, 가능성, 결과)다. [v0.3 §5-7]
8. 혼자 정한 결정을 기록하고 나중에 확인·이의를 걸 수 있다(불변조건 7). [v0.3 §5-8]
9. 외부 응답은 탐구 중 발견된 관찰로 다룬다. [v0.3 §5-9]
10. OPD+C를 위한 장기 관찰·제어 공간이 클라이언트 UX의 주요 구현 대상이다. 대화 중심 UI(opencode류)와 다른 상태 중심 UI다. [v0.3 §5-10]
11. Goal은 프로젝트 단위 궁극 목표이며 Concern 사이클을 거치며 정제된다. Concern은 10단계 과정을 돌릴 후보가 되는 상황 그 자체다. [v0.3 §5-11, 12]
12. 묻기 재설계: 기록과 전달 분리, 권리 게이트와 정보 게이트, 전달 방식(즉시·협상·중재·예약), 질문 레코드와 가정 만료점. 다이얼 수치는 [제안]. [v0.3 §5-13]
13. 다른 분야의 방법을 지금 문제에 적용하는 개념의 이름은 Method Transfer. "투영"은 정본을 읽어 만든 화면·컨텍스트라는 뜻으로만 쓴다. [v0.3 §5-14]
14. 커널 원칙: 모델은 제안하고, 커널이 상태를 바꾼다. 결정 주체 분류의 원칙("모델이 구조화된 값을 선언할 수 있으면 결정은 코드가 한다")도 결정. 분류 표의 각 행은 [제안]. [v0.3 §5-15, 08 §4]
15. 의존 규칙 중 (1) write·send에는 작업 합의(C) 필요, (2) "완료"에는 결과 확인(A) 필요, (3) 판단 승격에는 I의 근거 필요 — 셋은 [결정]. (4) 하위 Concern 재조합 후 닫힘, (5) Goal 변경 시 사람 확인 — 둘은 [제안]. [03 §5]
16. 질문 조건: AND를 기본으로 하고 조건별 문턱 다이얼을 둔다 [제안]. 사용자가 AND/OR을 고르는 옵션은 실제 사용 후 결정한다. [06 §2.1]
17. 불변조건 1~7 (`docs/v0.3/00-README.md` §2.4)은 어떤 모드·다이얼에서도 바뀌지 않는다.
18. 대안 2~3개를 던지고 고르게 하는 상호작용은 거부되었다. 원함 탐구에서는 반응(요소 단위, 이유 없는 반응 포함)을 받고 기록한다. "모델이 초안을 쓰고 사람은 반응·수정한다"(recognition over recall)가 핵심 원칙이다. [대화, 감사 보고 §3.3]

### 2.2 제품·구조 (2026-10-11 결정)

19. 클라이언트는 웹이 아니다. **데스크톱 앱을 먼저** 만들고, 이후 SSH로 쓰는 TUI 경로를 더한다. [v0.3 §5-17]
20. Helm은 제품 소유자의 **개인 WSL2 서버**(Windows PC 안의 WSL2)에서 실행한다. [v0.3 §5-18]
21. 클라이언트는 **외부(원격)에서 접속**할 수 있어야 한다. [v0.3 §5-19]
22. 진행 중인 작업은 **클라이언트가 없어도 계속**된다. 데몬이 상주한다. [v0.3 §5-20, 대화]
23. **자체 런타임을 만든다.** pi 패키지(pi-ai, pi-agent-core, coding-agent의 도구, pi-tui, pi-mcp, pi-codemode, pi-durable의 설계·코드 등) 중 재활용 가능한 것은 가져와서 적극 활용한다. 필요하면 소스를 가져와 고쳐 쓴다("포크해서 새로 만드는 느낌"). [대화]
24. **혼자 쓰는 앱**이다. 데스크톱 앱은 macOS와 Windows를 지원하고, 혼자 쓰므로 Apple 공증·서명 배포는 범위 밖이다. [대화]
25. 사용 사례는 "유즈케이스" 또는 "시나리오"라고 쓴다. "시나리오"는 결과 탐구와 테스트 시나리오에도 쓰이므로, 제품 사용 사례는 "유즈케이스"를 우선한다. [v0.3 §5-22]

### 2.3 조정자가 정한 기본값 (구조 일관성을 위한 [제안], 바꾸려면 근거와 함께 ADR에 기록)

26. 원격 접속: Windows 호스트에 Tailscale, `tailscale serve`로 HTTPS/WSS 노출, 데몬은 WSL 안 127.0.0.1에만 바인딩. 인증은 Tailscale 신원 헤더 + 기기별 bearer 토큰. Tailscale Funnel은 쓰지 않는다. (근거: `docs/v0.3/audit/backend-oss-research.md` §5)
27. 모델 계층: pi-ai를 가져와(포크 또는 고정 의존) Helm 안의 얇은 인터페이스 뒤에 둔다.
28. 에이전트 루프: pi-agent-core를 포크해 Helm 런타임 루프로 쓴다. 커널 검사는 루프 훅(`beforeToolCall`, `afterToolCall`, `prepareRequest`, `subscribe`의 `message_end`)에 연결한다.
29. 기준 원본: Helm 이벤트 로그(SQLite, WAL, WSL ext4 영역). 모든 상태는 로그에서 재구성 가능해야 한다. pi 세션 파일이나 pi-durable 저장소를 기준 원본으로 쓰지 않는다. pi-durable은 설계·코드 참고용이다(특히 `docs/spec.md` 5.2 실행 의도 → 실행 → 결과 기록).
30. 크래시 복구: 실행 의도 → 실행 → 결과 순으로 기록하고, 재시작 시 중단된 도구 호출을 "중단됨"으로 정리한다. 다시 실행해도 안전한 도구만 재실행한다. 재시작 복구는 OpenCode v2의 write-ahead claim 방식을 참고한다("복구는 DB의 성질이지 종료 훅의 성질이 아니다").
31. 클라이언트 프로토콜: JSON-RPC 2.0 over WebSocket, 이벤트는 단조 증가 시퀀스 번호를 붙여 보내고 재접속 시 `lastSeq`부터 재전송. 큰 데이터(이미지 자극 등)는 HTTP로 받는다.
32. 데스크톱 앱: Tauri v2 + React 18 + TypeScript + Vite. 앱은 데몬에 붙는 얇은 클라이언트다(앱 쪽에 Helm 로직 없음). 사용자는 React 18 CSR 시니어이므로 React 18 기준으로 설계한다.
33. TUI 경로(이후 단계): SSH로 WSL에 들어가 pi-tui로 만든 Helm TUI 클라이언트를 실행한다. pi CLI 자체를 쓰는 경로는 나중에 런타임 어댑터(pi RPC)로 열어 둔다. [결정, 2026-10-11 사용자 확인]
34. 벤더 중립: 런타임 어댑터 인터페이스를 지금 정의한다. 1차 구현은 Helm 자체 런타임 하나. Claude Code, Codex, pi CLI(RPC), ACP 어댑터는 이후 단계지만, 인터페이스와 커널 검사 지점(각 런타임의 훅·권한 콜백까지라는 한계 포함)은 지금 설계한다.
35. 관찰 에이전트 입력: 1단계 = Helm 기록 전체 + 사용자가 허용한 프로젝트 폴더의 외부 에이전트 세션 로그(pi, Claude Code, Codex). 단계별 확장 표는 `docs/v0.3/audit/` 자료와 HANDOFF 참고. [결정, 2026-10-11 사용자 확인]
36. 언어·도구 기본값: TypeScript 5.x strict, ESM, Node.js 22 LTS, pnpm workspace 모노레포, Vitest, 스키마는 TypeBox(pi-ai와 맞춤), SQLite 드라이버는 `better-sqlite3`(동기, WAL). 아키텍트가 바꿀 수 있으나 ADR로 남긴다.
37. UI 문구 언어: 한국어.

### 2.4 2026-10-11 사용자 추가 결정 (Claude Code 이관 후)

38. **데스크톱 앱도 SSH로 데몬에 접속할 수 있어야 한다.** [결정] 데스크톱 앱의 접속 방식은 두 가지다: (a) Tailscale serve를 거친 WSS(결정 26), (b) SSH(WSL OpenSSH, 키 인증)를 거친 접속. (b)의 구체 방식(SSH 로컬 포트 포워딩으로 127.0.0.1의 데몬 WebSocket에 붙기, 또는 SSH exec 채널의 stdio로 프로토콜 프레임 주고받기 등)과 그때의 인증(SSH 키로 충분한지, 기기 토큰을 함께 쓰는지)은 P11(17·18), P12(19), P13(20)이 정하고 ADR로 남긴다. 두 방식에서 프로토콜 메시지와 재전송 의미는 같아야 한다.
39. TUI 경로는 결정 33대로 pi-tui 기반 Helm TUI다. [결정]
40. 설계 문서는 `docs/design/`에 쓰고, 단계가 끝날 때마다 설계 브랜치(`design/helm-v1`)에 로컬 커밋한다. push는 사용자 확인 후. [결정]

### 2.4b 2026-10-12 사용자 결정과 조정자 판정 (1단계 이후)

41. **데스크톱 앱은 React 19를 쓴다.** [결정, 사용자] 결정 32의 "React 18"을 대체한다. UI 부품은 Helm이 직접 만든다(Caustic React 부품을 가져오지 않는다). 시각 언어는 최근 에이전트 클라이언트(Codex, Claude Code 데스크톱 등)의 디자인 시스템을 참고한 글래스모피즘 기반으로 한다. 반투명 표면·흐림은 시각 표현이며 브리프 §5.1의 "의인화 금지"(문장 규칙)와 무관하다.
42. **휴대폰에서도 질문에 답할 수 있어야 한다.** [결정, 사용자] 모바일 클라이언트를 범위에 넣는다. 데스크톱 앱 MVP 다음 단계에 둔다(결정 19의 순서 유지). 구현 방식(Tauri v2 모바일, PWA 등)과 알림 경로는 `26-mobile-client.md`(P15)가 정하고 01·03·06·18·19·20이 맞춘다.
43. **Caustic 토큰은 복사해서 가져온다(의존하지 않는다).** [결정, 사용자] neutral 색 단계 수가 많으므로 Helm에 맞게 줄여 다시 정한다. 사용자는 impeccable(프론트엔드 디자인 도구)을 써도 된다고 했다.
44. **Node 24 LTS, TypeScript 6.0.** [조정자 판정, ADR-06-07·06-08 채택] 결정 36의 Node 22·TS 5.x를 대체한다. pi 기준은 태그 `v1.1.0`(커밋 `abe508e1`, npm 1.1.0과 동일, ADR-07-1)이며 §4의 `cdaf6c2`는 참고 판이다. 문서의 pi 행 번호는 `v1.1.0` 기준으로 적는다.
45. **비밀 주입**: 데몬은 시작 단계에서 `secrets run`을 자식 로더로 써서 값을 받아 메모리(SecretStore)에만 둔다(ADR-17-3). §2.5의 "just 레시피가 `secrets run`으로 자식 프로세스에만 주입"은 일회성 레시피에 적용되고, 상주 데몬은 이 방식을 따른다.
46. **루프백 바인딩은 격리 경계가 아니다.** `networkingMode=mirrored`에서 127.0.0.1은 Windows 프로세스와 WSL의 모든 프로세스가 열 수 있다. 모든 리스너는 자격 증명(기기 토큰 등)을 요구하고, 모델이 실행하는 도구는 격리해 데몬 소켓·데이터·설정을 볼 수 없게 한다(06 §3.7.4, 13 §3.6, 18 D18-04).

### 2.5 운영 환경 사실 (홈랩 문서 기준, 데몬·보안·아키텍처 설계의 전제)

출처: `~/projects/homelab/context/{index,machines,network,storage,decisions}.md` (읽기 전용 참고. 이 저장소에 쓰지 않는다). 홈랩의 기각된 안(`decisions.md`)은 다시 제안하지 않는다.

- 서버: Windows 11 호스트(`server`, Ryzen 5 PRO 6650H, RAM 15.2 GB, Wi-Fi 전용) 안의 WSL2 Ubuntu 24.04. WSL 메모리 상한 10 GB + swap 8 GB, `networkingMode=mirrored`(호스트와 주소 공유), `vmIdleTimeout=-1`.
- Tailscale은 **Windows 호스트에만** 있다. Tailscale SSH는 쓰지 않는다. WSL OpenSSH가 22번(tailnet에서만, Hyper-V 방화벽, 키 인증만). Windows sshd는 2222번(WSL이 죽었을 때용).
- `tailscale serve`는 Windows 호스트에서 돌고 서비스별 포트(8443~8447 사용 중)를 `127.0.0.1` 바인딩 서비스로 넘긴다. 443은 Caddy로 TLS 패스스루. 새 서비스는 `serve.table`에 한 줄을 먼저 더한다. 컨테이너·서비스의 호스트 포트는 `127.0.0.1`에만 바인딩한다.
- Windows 호스트의 변경(방화벽, tailscale serve 설정 등)은 에이전트가 직접 하지 않는다. 검토 가능한 멱등 `.ps1` 스크립트를 쓰고 사람이 관리자 권한으로 실행한다.
- `~/projects`는 Syncthing으로 Mac과 양방향 동기화된다. SQLite 같은 DB 파일은 동기화 폴더에 두면 깨질 수 있으므로 **Helm의 런타임 데이터(이벤트 로그 DB 등)는 `~/projects` 밖**에 둔다. 홈랩 관례상 런타임 데이터는 `/srv/volumes/<서비스>/`(WSL 전용, 동기화 안 됨, restic 백업 대상 여부는 P11이 확인). 슬러그는 `helm`.
- 백업: restic(서버). Mac·iPhone의 동기화 사본은 백업이 아니다.
- 상시 작업 엔진은 just + systemd(홈랩 결정). n8n·Node-RED는 기각. Paseo는 설치했다가 전부 제거했다.
- 비밀: 원본은 SOPS `secrets/<범위>.sops.yaml`. 제품 비밀은 `~/projects/helm/secrets/<env>.sops.yaml`. 실행 시 just 레시피가 `secrets run`으로 자식 프로세스에만 주입한다. 저장소가 읽는 키 이름은 `.env.example`에 적는다. 모델 API 키 등 데몬 비밀은 이 체계를 따른다(서버 쪽에 별도 비밀 저장소를 만들지 않는다). 클라이언트 기기(Mac·Windows)의 기기 토큰 보관은 OS 키체인을 쓸 수 있다.
- 빌드·검증·배포는 저장소 `justfile` 레시피로만 한다(`just verify` 통과 = 작업 완료). 지금 저장소에는 justfile이 없다. 06·23은 레시피 목록(setup, check, verify, dev, build, daemon 설치 등)을 설계에 포함한다.
- iOS·macOS 빌드는 Mac에서만 된다(서버가 `run-on mac`으로 지시). 데스크톱 앱의 macOS 빌드도 Mac에서 한다. Windows 빌드는 Windows 호스트의 도구를 쓰지 않는 방향(호스트 PATH에 Node 등이 없음)이므로 P13이 빌드 경로(예: CI, 크로스 빌드, 수동 절차)를 정한다.

## 5. 작성 규칙

### 5.1 문체

- 한국어 한다체. 담백하게 사실대로 쓴다.
- 쓰지 않는 표현: '축', '박다', '가른다', '닿다', 사물을 주어로 세운 의인화("연구가 ~에 도달했다", "코드가 쥐고 있다", "~가 막아 줬다", 발견에 쓰는 "드러났다"), "A가 아니라 B다" 식의 짧은 구호 반복.
- 제품 사용 사례는 "유즈케이스". 이야기 내용으로서의 "장면 묘사"는 괜찮다.
- 영어 식별자(타입 이름, 함수 이름, 이벤트 이름)는 코드 표기를 쓴다.

### 5.2 표시

- 절 제목이나 항목에 `[결정]`(제품 소유자가 정한 것, 2장 근거 필요), `[제안]`(설계자가 정한 것), `[가정]`(확인되지 않은 전제)을 붙인다.
- 외부 사실에는 확인 수준을 붙인다: `[원문]`(소스·문서 직접 확인), `[실험]`(코드 실행 확인), `[검색]`, `[지식]`(재확인 안 함).
- 대화나 이전 문서에서 가져온 내용은 출처를 적는다(예: "대화 seg2 L342", "v0.3 06 §3.4").

### 5.3 문서 구성

모든 설계 문서는 다음 절을 포함한다(내용에 맞게 하위 절 추가).

1. 목적과 범위 (다루지 않는 것 포함)
2. 전제와 결정 (근거 포함)
3. 명세 본문 (타입, 스키마, 상태 기계, 알고리즘, 시퀀스)
4. 실패·예외·경계 사례
5. 다른 문서와의 인터페이스 (이 문서가 제공하는 것 / 다른 문서에 요구하는 것)
6. 구현 단위와 완료 기준 (모듈·파일 단위, 테스트로 확인할 조건)
7. 미결 사항 (선택지, 추천 기본값)
8. 출처

### 5.4 품질 기준

- 다른 문서를 참조할 때는 파일 이름과 절 번호를 쓴다.
- 이름이 다른 문서와 겹치거나 다르면, 3장 공통 계약과 용어집 초안(6장)을 따른다.
- pi API를 언급하면 소스 파일 경로를 적는다.
- 모르는 것을 아는 것처럼 쓰지 않는다.
- 분량 제한은 없다. 중복 없이 필요한 만큼 쓴다. 다른 문서가 소유한 내용은 반복하지 말고 참조한다.

## 6. 용어집 초안 (25 용어집의 출발점)

| 용어 | 뜻 |
|---|---|
| Goal | 프로젝트 단위 궁극 목표. Concern 사이클로 정제된다 |
| Concern | 10단계 과정을 돌릴 후보가 되는 상황 그 자체(문제, 기회, 위험, 불확실성, 취향 결정) |
| WorkUnit | Concern 안의 실행 단위(탐구, 탐침, 변경, 반영) |
| N / E / M | 방향(Normative) / 이해(Epistemic) / 실제(Material). 관찰은 E에 속한다 |
| A / P | 능력(Authority) / 정책(Policy). 판별 질문: "상황이 바뀌면 답도 바뀌는가?" 바뀌면 P |
| 관찰 | 실제 실행 기록(도구 결과, 외부 응답)을 출처로 갖는 E 레코드 |
| 추측 | 해석(Interpretation)과 가능성(Possibility)의 묶음 이름. 레코드는 둘로 구분한다 |
| 판단 (Finding) | 근거, 반증 탐색, 구분 확인을 거쳐 승격된 E 레코드. 이 문서 묶음에서 "판단"은 Finding만 가리킨다 |
| 선택 (Choice) | 사람이 고르거나 맡긴 범위 안의 정책이 적용될 때만 생긴다. 추천은 선택이 아니다 |
| 작업 합의 (Agreement) | 목적, 완료 기준, 범위, 금지 행동, 제출할 근거, 멈출 조건 |
| 결과 제출 / 결과 확인 / 전체 반영 | 에이전트의 완료 주장 / 사람의 확인(명세대로 만들었는가) / 다른 관점·작업에서도 맞는지 반영(올바른 것을 만들었는가) |
| 질문 레코드 | 묻기의 기록. 전달은 별도 결정. 임시 가정과 가정 만료점을 가진다 |
| 권리 게이트 / 정보 게이트 | 사람만 정할 권리가 있는 것 / 사람의 답이 정보로서 가치가 있는 것 |
| 전달 방식 | 즉시, 협상, 중재, 예약 |
| 혼자 정한 결정 | 묻지 않고 정한 선택. `why_not_asked`를 남기고 이의를 받을 수 있다. 화면 이름은 "에이전트가 정한 것" |
| 모드 | 루프 계획 기본값 + 능력 부분집합 + 다이얼 값 |
| 다이얼 | 질문·탐구·자율성의 정도를 조절하는 설정 (정본 목록: v0.3 07 §3) |
| 루프 식별자 | v0.3 03 §2.1 표 (I.fact, I.want, I.possibility, I.outcome, C.commit, C.probe, C.emergency, A.confirm, A.watch, A.reflect, S.*) |
| Method Transfer | 다른 분야의 방법·사고방식을 지금 문제에 적용하는 가능성 탐구 내 동작 |
| 투영 | 정본(이벤트 로그)을 읽어 만든 화면이나 모델 컨텍스트. 정본을 쓰지 않는다 |
| 상황 유형 | 명확, 복잡, 복합, 혼돈, 혼란 (Cynefin) |
| 기대 레코드 | 외부에 요청을 보낼 때 남기는 기한 있는 기록. 기한이 지나면 "응답 없음" 관찰 |
| 예측 | 결과 탐구의 Prediction 레코드 |
| 선호 모델 | 원함 탐구에서 쌓이는 기준 후보와 반응 기록 |
| 탐침 | 탐침형 C에서 해 보며 아는 작은 실행 |
| 관찰 에이전트 | 기록을 읽어 반복 패턴을 찾고 절차·스킬·정책 수정안을 제안하는 별도 프로세스. 쓰기 권한 없음 |
| 검증 에이전트 | 새 컨텍스트(가능하면 다른 모델)에서 반대 근거만 제안하는 에이전트 |
| 중재자 | 질문 전달 시점과 묶음을 정하는 에이전트(중재 전달 방식) |

## 7. 작업 방식

- 자기 문서만 쓰고 고친다. 다른 문서에 필요한 내용은 최종 보고의 "다른 문서에 대한 요구"에 적는다.
- 다른 에이전트가 같은 시기에 다른 문서를 쓰고 있다. 다른 문서가 이미 있으면 읽고 맞춘다. 없으면 3장 계약을 따른다.
- 작업 중 메모나 초안이 필요하면 `.helm-design-work/<에이전트 이름>/` (커밋하지 않음)을 쓴다.
- 이후 단계에서 조정자가 같은 에이전트에게 통합·수정을 요청할 수 있다.
- 최종 메시지(한국어)에 다음을 쓴다.
  1. 작성한 파일과 각 파일의 절 목록
  2. 주요 설계 결정과 근거 (5~15개)
  3. 다른 문서에 대한 요구 (문서 번호별)
  4. 미결 사항과 추천 기본값
  5. 브리프에 대한 이의 (있으면)
