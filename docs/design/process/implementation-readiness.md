## A. 구현 시작 전 사용자가 정해야 할 것

답이 없으면 설계의 추천 기본값으로 진행한다. "막히는 곳"은 정하지 않았을 때 멈추거나 되돌려야 하는 마일스톤이다. 마일스톤 ID는 23 §3.3.2와 §3.4의 것이다.

### A-1. 구현 기준 커밋과 병합 방식 (HT-01)

- 배경: 구현은 새 통합 브랜치 `impl/helm-v1`에서 한다. 이 브랜치를 어디서 딸지 정해야 한다. 지금 설계 문서는 `design/helm-v1` 브랜치에만 있고 `main`에는 없다.
- 선택지: (a) `design/helm-v1`을 `main`에 병합한 뒤 `main`에서 `impl/helm-v1`을 만든다. 설계와 구현의 이력이 한 줄이 된다. (b) 설계 브랜치에서 바로 `impl/helm-v1`을 만든다. 병합 판단을 미루지만 `main`이 오래 비어 있다.
- 설계의 추천: 사용자 규칙(병합은 확인 뒤)에 따라 사용자가 고른다. 설계는 (a)를 약하게 선호한다. 설계 마감 시점의 커밋이 구현 기준으로 분명해진다.
- 막히는 곳: M0-01. 구현 전체의 첫 작업이다.

### A-2. 월·일 모델 비용 상한 (HT-13, 01 OQ-06, 12 O-12-07, 판정 J-22)

- 배경: 에이전트가 모델 API를 부르는 비용이 한 달에 얼마까지 나가도 되는지 정한다. 설계 값은 가정이다. 월 USD 50, 일 USD 10(월의 5분의 1)이다.
- 선택지: (a) 월 USD 50, 일 USD 10 그대로. 상한에 닿으면 새 요청을 멈추고 사람에게 묻는다. (b) 더 높은 값. 긴 탐구가 덜 끊기지만 설정 실수의 피해가 커진다. (c) 더 낮은 값. 안전하지만 하루 안에 작업이 자주 멈춘다.
- 설계의 추천: (a)로 시작하고 2주 사용 뒤 16 지표로 조정한다.
- 막히는 곳: 월 상한은 M11-12(서버 설치 때 관리 CLI가 묻는다). 일 상한은 M7-08(예산 원장)이 기본값으로 쓴다. 답이 없어도 기본값으로 진행된다.

### A-3. 해시라인 편집의 기본값 (12 O-12-17, 13 O-13-17, SP-23)

- 배경: 에이전트가 파일을 고칠 때 방식이 둘이다. `replace`는 바꿀 문자열을 그대로 찾아 바꾼다. `hashline`은 줄마다 짧은 해시 표식을 붙여 그 표식으로 줄을 지정한다. 해시라인이 더 정확하다는 근거는 oh-my-pi 쪽 자체 벤치뿐이다.
- 선택지: (a) 기본 `replace`, 해시라인은 모델 계열별로 켠다. 안전하고 단순하다. (b) 처음부터 해시라인 기본. 편집 실패가 줄 수 있으나 근거가 약하고 `stale_snapshot` 실패가 늘 수 있다.
- 설계의 추천: (a). 구현 뒤 고정 과제 세트로 SP-23을 재고, 해시라인 성공률이 더 높고 `stale_snapshot` 실패가 늘지 않는 계열에서만 `ai.editMode`를 `hashline`으로 켠다.
- 막히는 곳: 없다. 기본 `replace`로 M7-19가 진행된다. 사용자는 SP-23 결과가 나온 뒤 계열별 값을 확인하면 된다.

### A-4. 웹 검색 제공자 약관의 결과 저장 조항 (SP-20, 결정 55)

- 배경: 웹 검색의 기본 제공자는 Brave다. Brave 약관이 검색 결과를 저장하는 일을 제한한다. Helm은 도구 결과 본문을 기록(ledger)에 보존하므로 충돌할 수 있다. 약관을 사람이 직접 읽어 확인한 적이 없다.
- 선택지: (a) 결과 본문은 기록에 남기지 않고 질의와 URL만 남긴다. 약관 충돌을 피하지만 나중에 같은 검색 결과를 다시 볼 수 없다. (b) 약관을 읽어 허용되면 본문도 남긴다. (c) 충돌하면 기본 제공자를 Tavily로 바꾼다. 결정 55의 변경이라 사용자 확인이 필요하다.
- 설계의 추천: (a)로 구현하고, M6-17 전에 사용자가 약관 조항과 보존 정책을 나란히 놓고 충돌 여부를 한 줄 기록한다. 충돌이 남으면 (c)를 사용자에게 묻는다.
- 막히는 곳: M6-17(웹 검색 도구). 검색 도구 자체는 (a)로 만들 수 있어 구현은 막히지 않는다. 사람 작업은 HT-26(검색 키 발급).

### A-5. Anthropic 브라우저·컴퓨터 사용 툴셋 이름과 서버 측 도구 형식 (13 O-13-18, 판정 J-190 (5))

- 배경: Anthropic이 모델에 직접 제공하는 서버 측 웹 검색·페치 도구와, 브라우저·컴퓨터 사용 툴셋의 이름(`browser_toolset_*`, `computer_toolset_*`)과 형식은 설계 시점에 검색으로만 확인했고 원문으로 확인하지 않았다. 구현 시점에 이름이나 형식이 달라졌을 수 있다.
- 선택지: (a) 서버 측 도구는 쓰지 않고, Helm이 제공자 API(Brave)와 자체 도구(`web_fetch`, `browserd`)를 쓴다. 툴셋 이름은 확인 전까지 코드에 쓰지 않는다. (b) 구현 직전에 공식 문서로 확인해 쓸 수 있으면 쓴다.
- 설계의 추천: (a)가 기본, (b)는 구현자가 M6-17 전(툴셋은 M6-19 전)에 공식 문서를 읽고 기록한다. 사용자가 정할 일은 "서버 측 도구를 쓰고 싶은가" 한 가지다.
- 막히는 곳: 없다. (a)로 M6-17과 M6-19가 진행된다.

### A-6. 보호 파일 탐색 예외: 이름이 `secrets`인 소스 폴더 (13 O-13-21)

- 배경: 도구는 작업 공간 안의 `.env`와 `secrets/` 폴더를 에이전트가 읽지 못하게 막는다. 기본은 깊이와 관계없이 이름이 `secrets`인 폴더를 막는 것이다. 그런데 Helm 자신의 소스에 `packages/tools/src/secrets/redact.ts`가 있다. Helm이 자기 저장소를 고칠 때 이 폴더를 못 읽는다.
- 선택지: (a) 깊이와 관계없이 막는다. 가장 안전하지만 Helm이 자기 소스의 해당 폴더를 못 고친다. (b) 작업 공간 루트의 `secrets/`만 막는다. 하위 폴더의 비밀을 놓칠 수 있다. (c) 기본은 (a)로 두고 저장소별 예외 목록을 설정에 둔다. 예외 설정이 새 공격면이 된다.
- 설계의 추천: (a)로 시작하고, Helm 저장소에서는 폴더 이름을 `secrets`가 아닌 이름(예: `redaction`)으로 바꾸는 쪽이 가장 단순하다. 폴더 이름 변경은 23 M6-11의 산출 경로 한 곳이다. 예외 설정은 두지 않는다.
- 막히는 곳: M6-11. 이름 변경이든 예외든 1단계(메인 오케스트레이터)가 M6-11 전에 판정해야 한다. 사용자가 (c)를 원하면 18에 새 규칙을 쓴다.

### A-7. CI 범위 (HD-1, 06 O-11)

- 배경: `just verify`를 어디서 돌릴지 정한다. 기존 저장소에는 GitHub Actions 설정이 있고, M0-01이 이를 지운다.
- 선택지: (a) `verify`는 서버에서만 돌리고 GitHub Actions는 Windows 데스크톱 빌드에만 쓴다(push는 사람 확인 뒤). (b) Actions로도 `verify`를 돌린다. 이력 검증이 쉬워지지만 push가 잦아지고 사용자 확인이 늘어난다.
- 설계의 추천: (a)(D23-7).
- 막히는 곳: M0-01(기존 `ci.yml`·`publish.yml` 삭제 범위).

### A-8. macOS 최소 판 (HT-07, 21 U-14)

- 배경: 데스크톱 앱의 유리 효과(`backdrop-filter`)는 Safari 18 이상의 웹뷰가 필요하다. 실제 쓰는 Mac의 macOS 판을 알아야 지원 최소 판을 확정할 수 있다.
- 선택지: (a) 설계 기준 macOS 14.0·Safari 18 이상. Mac이 더 낮은 판이면 올려야 한다. (b) 낮은 판까지 지원하려고 효과를 줄인다. 설계(21)를 다시 열어야 한다.
- 설계의 추천: 사용자가 Mac의 macOS 판 번호를 알려 주면 (a)로 확정한다.
- 막히는 곳: M13b-02(Mac 셸 확인) 전. 그전까지는 막히지 않는다.

### A-9. 동기화 제외 목록 `.stignore-dev` (HT-14, 20 Q-22)

- 배경: dotfiles의 Syncthing 동기화가 `.worktrees`(구현 갈래 작업 폴더)와 Cargo `target` 폴더까지 Mac·Windows로 퍼 나른다. 큰 폴더라 동기화가 느려지고 충돌이 생길 수 있다.
- 선택지: (a) dotfiles `.stignore-dev`에 `.worktrees`와 `target`을 제외로 더한다. dotfiles 수정은 사용자가 한다. (b) 하지 않는다. Cargo는 `CARGO_TARGET_DIR` 우회로 피하지만 `.worktrees`는 동기화된다.
- 설계의 추천: (a). 한 줄 추가로 끝난다.
- 막히는 곳: `.worktrees`는 M0-01, Cargo는 M13b-02. 답이 없으면 우회로 진행되지만 `.worktrees` 동기화 부담이 남는다.

### A-10. Caustic 저장소 LICENSE (HT-15, 21 U-07, 판정 J-88)

- 배경: 시각 토큰은 Caustic 저장소에서 복사해 Helm에 맞게 줄여 쓴다(결정 43). Caustic 쪽에 LICENSE 파일이 없다. Helm은 NOTICE에 출처를 기록하는 것으로 처리한다.
- 선택지: (a) Caustic에 LICENSE를 더한다(사용자의 판단과 작업). (b) 더하지 않고 NOTICE만 둔다.
- 설계의 추천: 급하지 않다. 둘 다 구현을 막지 않는다. 혼자 쓰는 앱이므로 (b)로 진행해도 된다.
- 막히는 곳: 없다(M13a-01은 NOTICE 기록으로 진행).

### A-11. 관찰 에이전트 외부 세션 발췌 전송 (HD-4, 16 OQ-16-03)

- 배경: 관찰 에이전트가 다른 에이전트 세션의 사용자·어시스턴트 문장(최대 400자)을 읽고 모델 API로 보내 분석할지 정한다. 개인 대화 내용이 외부 API로 나가는 일이다.
- 선택지: (a) 보내지 않고 문장 특징(길이, 시각 등)만 쓴다. (b) 보낸다. 분석이 정밀해지지만 내용이 외부로 나간다.
- 설계의 추천: (a). 2단계 기능이라 A2 때 다시 묻는다.
- 막히는 곳: A2(2단계 활성화). 그전에는 막히지 않는다.

## D. 설계에 남은 알려진 위험·약점

W4(2차 검증)와 W5(보완)의 결과에서 구현 중 비용이 큰 것을 골랐다.

1. 정본이 문서 여러 곳에 걸쳐 있어 불일치가 계속 생긴다. 26개 문서, 합계 수만 줄이다. 2차 검증에서 높음 21건이 나왔고 W5 보완 중에도 같은 종류의 잔여가 나왔다(EngineInput 정의 세 벌, 크래시 루프 입력 둘, 푸시 표시 필드 이름 둘). 구현자가 두 문서를 다르게 읽으면 코드가 서로 어긋난다. 대응: 23 §3.9의 설계 변경 절차와 근거 절 대조 체크리스트, 이름 정본 표(06 패키지, 08 레코드, 09 이벤트, 10 명령, 19 메서드). 구현 중 새 불일치는 판정 문서에 계속 적는다.
2. 모바일 연결(SP-15)이 미확인이다. `tailscale serve`가 쿠키·Origin 헤더를 통과시키는지 확인하지 않았고, 대체 전송 방식을 두지 않기로 했다(J-241). 실패하면 M17 설계가 흔들리고 사용자 결정이 필요하다. 대응: 쿠키·Origin은 SP-10과 함께 M11-12에서 먼저 확인한다(J-276). Web Push는 실기기가 필요하다.
3. 도구 격리 스파이크 묶음이 모두 미확인이다. SP-04(bubblewrap), SP-16(네트워크 네임스페이스와 CONNECT 프록시), SP-17(Chrome을 bubblewrap 안에서 실행), SP-18(`helm-netshim` 지연), SP-19(요청 가로채기가 `sendBeacon`·keepalive·서비스 워커 요청을 놓치면 권리 게이트를 우회한다). 하나라도 실패하면 브라우저 상호작용 범위가 줄거나 네트워크 도구마다 사람 승인이 필요해진다. 대응: 각 스파이크의 대체 경로(23 §3.7.1)와 18 S-19의 기능 끄기. M6 시작을 HT-05에 묶었다.
4. 복원 뒤 권한 변경 확인 불가 주의 항목과 지침 파일 변경 확인 질문이 MVP에 없다([결정 62]). 백업을 복원하면 복원 뒤에 줄였던 기기 권한이 되살아날 수 있고, 작업 공간의 지침 파일(`AGENTS.md` 등)이 바뀌어도 사람에게 묻지 않는다. MVP는 사용자 한 사람이고 복원이 드물어 감수한 위험이다. 대응: 2단계 첫 항목으로 올리고, 복원 직후에는 사용자가 기기 목록(`helm devices`)을 직접 확인한다.
5. 결과 확인 대기 알림이 기본 "알리지 않음"이고 데스크톱은 배지만이다([결정 60], J-189). 사용자가 앱을 열지 않으면 확인 대기를 늦게 안다. 대응: 하루 한 번 묶음 푸시나 즉시 푸시를 설정에서 켠다. G1 평가에서 놓친 확인 건수를 본다.
6. 구현 에이전트 구성의 품질 위험. 결정 58로 실작업자가 Haiku 5.5 xhigh이고 등급 C(커널, 저장소 커밋, 격리, 인증)도 맡는다. 근거 절 대조 체크리스트와 하위 조정자 검토에 품질이 기댄다. 대응: 반복 실패하면 등급을 올려 하위 조정자(Sonnet high)가 직접 한다(23 F23-17). 설계 단계에서 Haiku가 만든 수정이 W5에서도 반복 확인이 필요했던 경험이 있다.
7. 모델 비용 상한이 가정이다. 월 USD 50, 일 USD 10은 근거 없는 값이고, 긴 탐구가 상한에 자주 닿으면 작업이 끊긴다. 대응: 설치 때 묻고, 2주 사용 뒤 16 지표로 조정한다. 상한 초과 시 새 요청을 멈추고 사람에게 묻는다.
8. 외부 의존이 설계 시점의 최신판 가정에 기댄다. pi 포크 유지 부담(SP-05), pnpm 11·TypeScript 6.0·Tauri 2.6·Node 24 등의 판 핀, 서버 측 툴셋 이름(A-5). 약 115줄의 `[검색]` 표시가 원문 확인 전이다. 대응: 구현자가 판 핀을 쓰기 전에 원문을 확인하고 스파이크 기록(`docs/specs/spikes/SP-xx.md`)에 남긴다.
9. 현재 저장소에 `justfile`이 없어 `just verify`가 아직 존재하지 않는다. M0-04 전에는 문서·코드 검사를 모두 수작업(grep, 열 수·코드 블록 점검)에 의존한다. 대응: M0를 첫 주에 끝내고 이후 모든 작업은 `just verify`를 통과한 뒤 넘긴다.
10. 웹 검색 제공자 약관(A-4)과 `secrets` 폴더 이름 충돌(A-6)처럼 구현 한복판에서야 드러나는 소규모 충돌이 더 있을 수 있다. 대응: 마일스톤 시작 전에 하위 조정자가 해당 마일스톤의 미결 항목(23 §3.8)을 훑고 1단계에 올린다.
